# DERBY WATCH（`apps/derby/derby_watch.js` と `chunks.txt` のチャンク）

観戦が主体の競馬ゲーム。夜の 1000 m のコース（直線か楕円、レースごとに種で決まる。下の「楕円」。ナイター）を、手続き描画（`pocket.kasane.procedural`）の線分だけの疑似 3D で見せる。遊びはレース前に1頭を選んで賭け、レース中はカメラを切り替えるだけ。設計・実測・上限の使用率・実機で確かめる項目は [docs/apps/derby-watch.md](../../docs/apps/derby-watch.md)。このファイルはコードの隣に置く「なぜ」のメモ（ソースのコメントはゲストのヒープを食うので短くしてある）。

## なぜ馬で、なぜ直線か

- **馬にした。** 線だけの 240×135 でも、脚4本・首・騎手の勝負服で「走っている生き物」と「どの馬か」が同時に読める。犬（グレイハウンド）は背が低く、同じ画面では脚と胴が数ピクセルにつぶれる。写真判定とオッズ（単勝）も競馬の方が見慣れている。
- **1000 m の直線（千直）にした。** 横から追うカメラ（コースと平行）なら、奥行きごとの変換が「拡大＋平行移動」になり、VM の ADD の繰り返しだけで柵の支柱・観客席・芝の刈り目を描ける（割り算が要らない）。コースと直交する線（刈り目・ゲート・決勝線）は消失点 (120, 地平線) に集まるので、疑似 3D の「消失点へ向かう線」は刈り目が担う。コーナーのある周回コースは透視の割り算が点ごとに要り、VM では描けない（当時の判断。後に首振りカメラが VM の Newton 法で逆数を出すようになり、楕円は首振りの側で描いた。下の「首振りカメラ」「楕円」）。
- **ナイターにした。** 塗りつぶしが無いので背景は1色（`beginFrame` の色）。空と芝を塗り分けられないなら、暗い背景に明るい線（照明に浮かぶコース）の方が線画として成り立つ。

実在の馬名・競馬場・団体は使っていない。馬名はポケットコンピュータにちなむ造語（BIT DASH、HEX HOOF…）。勝負服の色は枠番ごとの8色（白・灰・赤・青・黄・緑・橙・桃）で、特定の団体の配色ではない。

## レースのモデル（arithmetic only）

`step()` は加減乗除と比較だけで書いた（`Math.sin`/`exp` を使わない）。IEEE の倍精度の四則は処理系に依らないので、同じ種なら host（V8・QuickJS）でも実機でも同じレースになる（V8 と QuickJS 32/64 bit で全桁一致を確認、docs の「再現性」）。脚の振りなど描画の値だけ `Math.sin` を使う（描画はレースに影響しない）。

各馬の能力（種から）: 巡航速度 `top`（16.6〜16.8 m/s）、スタミナ `st`、末脚 `kick`、脚質 `sty`（逃げ FRONT／先行 STALK／差し CLOSE）、出遅れ `re`、加速 `acc`、毛色。1 ステップ 0.05 秒（表示は 1 フレーム 1 ステップ＝実時間の 1.5 倍速、ゴール前 20 m からは 4 フレーム 1 ステップのスロー）。

| 項 | 定数 | 意味 |
| --- | --- | --- |
| 前半のペース | `PACE` | 距離の 50〜66%（脚質で遅くなる）までは `top×(1−PACE×sty)`。差しほど控える |
| 馬群 | `PK0` `PK1` | 前半は先頭との差 1 m あたり +0.03 m/s（上限 0.5）で追走する（馬群がばらけない） |
| 風 | `WIND` | 先頭（差 1 m 未満）はスタミナを 1.5 倍使う |
| スタミナ | `EB` `ST0` `ST1` | `top×0.97` を超える速さの分だけ減る。尽きると `top×FADE` へ落ちる |
| 末脚 | `KI0` `KI1` `KS` | 後半は `top×(1+kick×(1+KS×sty))` |
| 競り合い | `BG` `BK` | 後半、先頭との差が 4 m 未満の馬は差 1 m あたり +0.15 m/s。接戦のゴールを作る項（これが無いと着差の中央値が 2 m 以上になった） |
| 当日の出来 | `FORM` | レースごとに ±0.3 m/s。オッズには見えない |
| ゆらぎ | `WR` `WS` | ゆっくりした乱歩（伸び・もたれ） |
| つまずき | — | 1 ステップ 0.06% で 0.5 秒だけ 10% 減速 |

値は `node tools/games/tune_derby.mjs 4000` の Monte Carlo（4,000 レース）で決めた。狙いは「人気馬が勝ちすぎない」「ゴール前が接戦」「脚質で偏らない」。結果（host）: 1 番人気の勝率 42.7%、脚質別の勝率 27/32/41%、1・2 着差の中央値 0.58 m、ハナ差（0.12 m 未満）12.5%、アタマ差以内 51.5%、ラスト 300 m の先頭交代の中央値 2 回。`DERBY_SET="FORM=1,BK=.3" node tools/games/tune_derby.mjs` で定数を試せる。

## 種

レースの種は起動ごとに変わる。評価中に `pocket.random.seed()`（実機は `esp_random()`）を 1 回引き（`HW`）、保存済みのレース番号 `sn`（通算カウンタ。保存が無ければ 0）と混ぜて基準 `base = rng(HW ^ sn·φ)()·2³²` にし、レースの種を `base + raceNo·φ`、そのレースのノイズの列を `rng(seed + 0x5bd1e995)` にする。以前は `0x3e1b7 + raceNo·φ` で、同じ番号のレースがいつも同じ展開になり、保存を消すと同じレースが再現して結果を覚えられた。

- **加算にした理由。** mulberry32 は状態が定数ずつ進むカウンタなので、2 本の列が重なるかは種の差だけで決まる。加算なら差が `base` に依らないので、「レース 1〜20,975 とデモ 1,000 レースのどの列も重ならない」を全セッションについて 1 回の計算で言える（`python3 tools/games/derby_seeds.py`）。
- **通算カウンタに保存のレース番号を使った理由。** `esp_random()` は RF が止まっていると擬似乱数扱い（common-api §8.1）で、起動ごとに同じ値が出る可能性を否定できない。保存のレース番号が違えば基準も変わる。起動回数を保存に足す案は、読み書きの式だけで host のコンパイルのピークが +348 B で、評価の余裕（3.8〜5.6 KB）を食うのでやめた。
- **再生とデモ。** `R` は同じ `F` を走らせるので全桁一致のまま。デモのレース番号は `1e6 + n` のままで、種はレース番号の純関数なので、プレイヤーの次のレースの種はデモの前後で変わらない。
- **host。** `tools/games/test_derby_host.c` の `pocket.random.seed()` は固定値（`DERBY_HW`）を返すので台本は決定的。`run_derby.py` がログの種を `derby_seeds.py` の式と照合する。

## オッズ

パドックに入ったとき、能力値から各馬の強さ `exp(17.2·top + 2.6·st − 2.3·re + 0.5·(acc + [差し]))` を出して 8 頭で正規化し（Luce モデル）、勝率 p に控除 20% を掛けてオッズ `0.8/p·(1 + 0.0015/p)`（0.1 刻み、1.1〜999）にする。重みは `node tools/games/tune_derby.mjs` の条件付きロジットの最尤推定を丸めた値。後ろの `(1 + 0.0015/p)` は大穴の裾の補正（弱い馬の実際の勝率は Luce の予測より低い）。結果、賭けの期待値はどの勝率の区間・人気順でも 0.75〜0.86（8 万レース、docs の「オッズの較正」）。

- **楕円では**、強さを `0.92·(直線の強さ) + 0.15·(3.5 − i)/3.5`（i は枠、内ほど強い）にし、オッズの係数を 7.87（直線は 8）にする。賭ける側に見える情報（能力値・コースの種類・枠）だけから作り、カーブで馬ごとに引く乱数は入れない。値は `tools/games/derby_corner.mjs public` の推定（docs/apps/derby-corner-model.md）。`tune_derby.mjs --course=oval` で、各群の期待値が 0.784〜0.847（4 万レース）。
- **以前は**、乱数を切った同じモデルを 9 フレームかけて走らせ、完走時間 T の softmax（`TAU = 0.23`）にしていた。後半の競り合いの項が乱数なしの走りでは全員を先頭へ寄せるので T が能力差を潰し、1 番人気の期待値が 1.18（本命を買い続けるのが最適）、3〜4 番人気が 0.61 だった。T のどんな単調な写像でも人気順ごとには直らないので、T をやめた（9 フレームの計算も無くなった）。
- **末脚 `kick` は入れていない。** 他の能力値を入れると重みがほぼ 0 だった。
- **上限を 999 にした。** 99.9 で止めると、それより弱い馬の期待値が上限で削られる。セルは 10 倍以上を整数で出すので 3 文字。
- `run_derby.py` が `tune_derby.mjs 20000 --check` を走らせ、各群の期待値が `0.8 ± (0.06 + 2.5·標準誤差)` に入ることを確かめる。

## 描画の組み立て

- **カメラは横から。** 奥行き d の層は `x = 120 + (w − cx)·f/d`、地面 `y = hy + h·f/d`。8 レーンの奥行きは 12 m×1.085^j（等比）にした。等比だとゲートの枠（レーン境界ごとの柱）を VM の MUL 1 回ずつで歩ける。
- **plan は 29 本まで同時に使う**（上限 32。パドックの 12 本＋ゲートからの 17 本、うち首振りの 4 本。観客は横見と首振りで 1 本の `crowd`、2026-10-01 の P24 から）。場面ごとに登録・解除する（下）。plan は firmware の flash の表にあり、名前で登録する（下の「ファイルの構成」）。
- **走る馬（遠景）** は `runner` plan（40 命令・16 レジスタ）を8頭ぶん、毛色・勝負服・帽子の色を定数に焼いて登録する（1 頭 1 plan）。入力 8 個（腰の x、背の y、1 単位の px、地面の y、後脚2・前脚2 の蹄の x）を JS が毎フレーム計算する。点は 2.5 単位の格子に並べ、`2.5S` と `−2.5S` の2レジスタを足していくだけで全頂点を作る（1 頂点 1 命令。素直に `SET+MUL+ADD` だと 1 座標 3 命令で 64 命令に収まらなかった）。
- **大写しの馬（CLOSE カメラ・パドック・結果）** は型付き点列（`affineQ14Points`）。点列の変換は登録時に固定なので、**画面上で動かない馬にだけ使える**。そこで CLOSE カメラを「選んだ馬の腰が常に (92, 88)、1 単位 4 px」になるよう、レーンごとに焦点距離 `f = 24·d` を決めた。ギャロップの 6 コマ（`g0`〜`g5`、各 36 点、半ピクセル座標で倍率 0.5）を登録しておき、脚の位相でコマを選ぶ（MEGADEMO の ZENITH の「ロール角ごとの点列表」と同じ考え）。騎手（`silk`）は VM で、勝負服の色を入力にして8頭で共有する。頂点は馬のモデルから焼いた定数（`HX`,`HY` を変えたら作り直す）。
- **奥から手前へ** 描く: スタンド → 観客 → **大型画面（面の塗り・中継映像・ベゼル・脚）** → 向こう正面の柵 → 芝の刈り目 → 距離標・決勝柱 → ゲート → 馬（外枠＝奥から） → 手前の柵 → ミニマップ。隠面消去が無いので、手前の柵は馬の脚の上に重なる（柵越しに見る絵）。
- **写真判定** は決勝線の延長上から線に沿って見る（`cx = 1000`）。このとき決勝線はどの奥行きでも x = 120 の縦線になる（本物の写真判定カメラと同じ幾何）。各馬は「勝ち馬が線を越えた瞬間の位置」に置き、view の image を 2 倍に拡大して見せる。

騎手の `silk` プログラムは次の生成器の出力をそのまま貼った（生成器をソースに置くとコンパイルのピークが約 2 KB 増えた）。`HX`,`HY`,`HS` か馬の形を変えたら作り直す。

```js
// node: 騎手の頂点（単位、腰が原点）。長靴・膝・鞍・肩・手、帽子の4点
const HX = 92, HY = 88, HS = 4, P = [5.3, 2, 6.1, .9, 4.3, -.9, 6.8, -3.4, 8.7, -2, 6.9, -4.3, 6.9, -5.6, 8.9, -5.6, 8.9, -4.3];
let s = 'I8,0 I9,1';
for (let i = 0; i < 18; ++i) {
  const r = i < 10 ? i % 8 : i - 10;
  s += ' S' + r + ',' + Math.round(i & 1 ? HY + HS * P[i] : HX + HS * P[i]) + (i & 1 ? ' A' + r + ',' + r + ',9' : '');
  if (i === 7) s += ' V0,1 l8,2,3 l8,4,5 l8,6,7';
  if (i === 9) s += ' l8,0,1';
}
console.log(s + ' C5,65535');
```

## 大型画面（ターフビジョン）

内馬場（コースの向こう側、観客席の手前）に立つ大型画面。**ワールドに固定された物体**で、ゲーム演出のカメラのパン・ズームで画面上の位置と大きさが変わる。中には「先頭集団を追う中継カメラ」の映像が映る。設計の経緯・実測は docs の「大型画面と演出カメラ」。

- **置き場所** `VS = [840, 34, 20, 6, 16]`: 中心 x = 840 m（ゴールの 160 m 手前）、奥行き 34 m（向こう正面の柵 22.6 m とスタンド 40 m の間）、幅 40 m、下端 6 m・上端 16 m（4:1）。
- **面（画面の枠内）は面0の中で塗る。** `vis` plan が面の内側を 1 行 1 本の水平線で塗り（入力 6 の色）、その外側に 1 px 外から `b` 本のベゼルの輪（`b` = 0.4 m を px にした値、最低 1）、上端の明かり、2 本の脚（柱）を地面まで描く。矩形は JS が `rnd()` した整数（`vr`）で、塗り・ベゼル・中継映像・文字のすべてがこの同じ整数を使う（host が全フレームで一致を検査）。
- **中継映像** は同じ `course()` を別のカメラで呼んで、面の中に描く: 焦点距離 `85×(面の幅/120)`、高さ 3 m、地平線は面の上端から `4.8×(面の幅/120)`、先頭の 6 m 後ろ。描くのは柵 2 本（支柱は面の中だけ）と、**先頭から `FN[tier]` 頭（LIGHT 3・MID 4・HEAVY 6）のうち面に丸ごと入る馬だけ**（面からはみ出す線を出さない。画家のアルゴリズムで、塗りの上に描けば後ろのスタンドは隠れる）。
- **文字**（残り距離と上位 3 頭「167M 3-5-1」、`LIVE`、点滅するランプ）は Kasane の view ノード 3 つ（text 2・rect 1）。面が 100 px 以上の幅で見えている間だけ出し、毎フレーム `setRect` で面に合わせる（`setRect` は clip を動かさないので、clip はパネル全体）。文字は面の大きさで拡縮しないので、小さく映る FIELD では出さない。
- **点灯の演出**: その日初めて見えてから 8 フレームは黒、3 フレーム灰色、それから映像（`von`）。
- **見えない条件**（`vr = null`）: レース以外、HEAD ON、画面の外、**上端が y < 13**（ミニマップ y 2〜12 に被る。CLOSE では常にこれ）、幅が 8 px 未満または 160 px 超（1 draw のラスタ上限 8,192 の手前で止める。今のカメラで最大は VISION の 153 px）。
- **遮蔽**: 面は向こう正面の柵より奥にあり、下端 6 m は「どのカメラでも、手前の物（馬・柵・距離標 4 m・ゲート 2.6 m）の上端より画面上で上」になる高さにした（`(h − 6)/34 < (h − e)/d` がすべてのカメラの高さ h で成り立つ）。host は面の後に描いた線分のうち面に丸ごと入らないものをラスタ化し、面の中の画素が 0 であることを全フレームで確かめる。

### なぜ面を 2 枚にしなかったか

最初は「面1（`createSurface`）に中継を描き、image ノードで貼る」形で作った（host の全検査も通った）。実機では起動（評価）の直後に空き 56,696 B・**最大連続 10,240 B** で、面1のフレーム（10,246 B の連続領域が 2 枚）が確保できず `frame allocation failed` で起動に失敗した（評価中・最初のフレーム・以後のフレームのどれでも）。ネイティブを変えずに 20 KB を空ける手は無く、面1の更新のたびに面0が止まる（表示待ち候補は全面で 1 枚）問題も無くなるので、面0の中に塗りと中継を描く形に変えた。

## 監督（カメラの自動切替）と角度

レース中はキーを押さなければ監督がカメラを選ぶ（先頭の位置 L で決める。1 回切り替えたら 45 フレームは保つ）。

| 先頭の位置 | カメラ |
| --- | --- |
| 0〜150 m | WIDE（ゲートの plan を外すまでは横見） |
| 150〜400 m | FIELD（馬群の広がり） |
| 400〜700 m | WIDE。先頭が替わったら 60 フレーム、新しい先頭の CLOSE |
| 700 m〜`VS[0]−60` | CLOSE（先頭。ラスト 300 m） |
| `VS[0]±60` m | **VISION**（低い横位置 `[130, 1.6, 84]`。カメラは大型画面の前 ±30 m に留まるので、馬群が画面の下を駆け抜ける） |
| 930 m〜、1・2 着の差 1.5 m 未満 | **HEAD ON**（接戦のときだけ。スローになるまで保つ） |
| 980 m〜 | FINISH（スロー、従来どおり） |

**WIDE は首振りの台になることがある**（下の「首振りカメラ」）: 監督の WIDE も手動の WIDE も、レース中にゲートの plan を外した後（先頭が 120 m を過ぎた後）は、先頭がどの首振りの台からも 60 m（`PAN[0]`）より遠ければ、一番近い台（`WIDE 1`〜`WIDE 3`）に替わる。近ければ横見の WIDE のまま。HEAD ON・VISION・CLOSE・FIELD・FINISH は首振りにならない。

**HEAD ON（正面）**: 決勝線の 12 m 先・高さ 2.2 m・内外の中央に置いた静止カメラが、コースを逆向きに見る。馬ごとに奥行き z が違うので透視の割り算が要るが、**割り算は JS が馬ごとに 1 回**（`q = 400/z`）して、正面の馬の plan `fr`（56 命令、入力 7 個: x・地面の y・1 単位の px・毛色・勝負服・左右の前脚の上げ幅）に渡す。カメラが動かないので、柵・決勝線・スタンド・大型画面（真横から見た薄い台形）は 1 本の型付き点列 `hd`（44 点）に焼いた。点は次で作った（カメラを変えたら作り直す）:

```python
XC, C0, H, F, HY = 1012, 16.5, 2.2, 400, 50        # カメラの x・横位置・高さ、焦点距離、地平線
P = lambda x, lat, e: (round(120 + (lat - C0) * F / (XC - x)), round(HY + (H - e) * F / (XC - x)))
# 消失点 (120, 50) から: 柵の上端 (x=1004, 横 11 / 22.6, 高さ 1.1)、地面の線、決勝線 (x=1000)、
# 刈り目 (x=950, 900)、大型画面 (x 820〜860, 横 34, 高さ 6〜16) と脚、スタンド (横 40) の柱 6 本
```

**できなかった角度**: 動く斜めのカメラ。直線は透視でも直線なので柵は JS の端点 2 つで描けるが、支柱・刈り目・観客・馬の奥行きが 1 本ずつ違い、VM に割り算が無い。BIG WAVE の級数（`1/(d+D)` を 3 次で打ち切る）は 1 plan の命令とレジスタを使い切っており（62/64・16/16）、馬の横向きの絵を斜めに歪める変換（射影）は入力 8 個に入らない。HEAD ON はカメラを止めることで背景を定数にし、馬だけを JS の割り算で置いて成り立たせた。VISION は横からのまま高さと地平線だけを変えた「低い角度」。

## コースの表とカメラの表（2026-09-30）

首振りカメラと楕円の下ごしらえ（docs の「コースの表とカメラの表」）。この 2 つの表の上に首振りカメラ（下）を載せた。

- **コースは区間の表** `CRS = [[長さ, 曲率], …]`（view）。`pose(g, w)` は、スタートから g m・横見のカメラの線から w m 外（横見の奥行き: 内柵 11、画面 34、スタンド 40）の点と接線 `[x, z, tx, tz]`。直線は 1 区間で、`[g, w, 1, 0]` を丸め誤差なしで返す。大型画面の 4 隅は `pose` から取る。
- **カメラは 1 台 1 行の表** `CAMS = [f, 高さ, 地平線, lead, 平滑, lo, hi]`。横見の台はコースの法線を向き、`cx` は先頭の `lead/f` m 手前（平滑の台はカットの間で緩やかに追う）で `lo..hi` に留まる。CLOSE は走路ごとに決め、HEAD ON は静止画（`paint`）。行 7〜9 は首振りの台で、形が違う（`[最小の f, 高さ, 地平線, g, w]`、下）。

## 首振りカメラ（WIDE 1〜3、q24 段階 3、2026-10-01）

コースの手前に立つ 3 台の固定カメラが、先頭を向いて首を振る。横見（カメラがコースの法線を向いて平行に動く）と違い、奥行きが点ごとに変わるので、透視の割り算を VM の Newton 法の逆数で行う（docs の「首振りカメラの費用」）。

- **台**: `CAMS` の行 7〜9、`[200, 6, 28, g, −14]`（g = 100・460・820 m、横見の線から 14 m 手前、高さ 6 m、地平線 y 28）。高さと地平線は首振りの plan に焼いてあるので、行を変えても plan は変わらない。
- **向きと焦点距離**: 台から先頭（内外の中央）への単位ベクトルを向き、f は先頭の馬が `PAN[1]` = 14 px に見える長さ（`14·距離/2.4`）を最小 200・最大 `PAN[2]` = 1,500 に収める。`pc = [台の x, z, 向き x, z, f, 先頭までの距離]`。
- **投影** `pj(x, z)`: 世界の点を `[X'', Z']` にする（画面の x = X''/Z'、1 m の px = 1/Z'）。JS が割るのは draw の最初の点と、距離標・走者・大型画面の 4 隅だけ。
- **列の描き方** `ser()`: コースに沿う物（柵・観客・芝の縞）は、奥行き w の線の上に s m ごとの点を「奥から手前へ」並べ、VM が前の点の 1/Z' から Newton 法 3 段で次の 1/Z' を出す（前の点の方が遠いので下から近づき、発散しない）。JS は視野（x −40〜280、奥行き 0.02f〜先頭の 75 m 先。LIGHT は 150 m 先）で列を切り出し、点が L px より詰まる奥では間隔を倍々に広げる（LOD。1 歩は奥行きの 0.3 以下）。
- **plan**（ゲートで登録、計 4 本）: `prail`（柵と支柱、49 命令）、`pt`（芝の縞。`t0`・`t1` の 2 本、`$0` が緑、59 命令）、`hl`（スタンドの段と大型画面の面を描く横線、27 命令）。観客は横見と同じ `crowd`（下の「観客」）を、スタンドの段（`hl`）と同じ弦のループで弦ごとに 1 回描く（`ser()` の `b < 0` の枝）。
- **描く順**（`pan()`）: スタンドの柱と屋根 → 段（`hl`）→ 観客 → 大型画面（面・ベゼル・中継）→ 向こうの柵 → 芝の縞 → 距離標・決勝柱 → 走者（`runner` を共用）→ 手前の柵。支柱の最小の間隔は 4 px、大型画面が見えている間は 8 px（その分の JS と VM を中継に回す）。
- **大型画面**: 4 隅を `pj` して、横見と同じ判定（幅 8〜160 px、上端 y ≥ 13）を通ったときだけ描く。面の塗りとベゼルは `hl`、中継は横見と同じ `feed()`（縮尺は面の幅/120 と高さ/30 の小さい方）。
- **HEAD ON との関係**: HEAD ON は監督の行 6 のまま（静止画）。首振りは WIDE だけを置き換えるので、接戦のゴール前は従来どおり HEAD ON → FINISH になる。
- **fps**: 首振り WIDE は 30 fps を割る（実機 MID 25.3〜25.5、HEAVY 24.6〜25.0 fps。JS のターン 20〜22 ms、横見の WIDE は 15.9 ms）。レースの絵の約 4 分の 1 が首振り。ユーザーの決定（q24）で、楕円コースまで入れてから fps の影響を見る（docs の derby-pan-memory.md §10・§11）。
- **host の検査**: 首振りのフレームの全点を倍精度の厳密な投影と比べる（誤差 0.1 px 未満、実測の最大 0.075 px）。`DERBY_PAN=1e9` で首振りを止めると、横見の画素は首振りを入れる前と全構成で同じ。

## 楕円（q24 段階 4、2026-10-01）

レースごとに、直線（千直）か楕円かを種で決める。パドックの 1 行目に `1000M OVAL` / `1000M STRAIGHT` と出る（既存の text。view の ref は増やしていない）。

- **コース**: 内柵 1,600 m の楕円。直線 423 m、内柵で半径 120 m の右回りのコーナー。レース 1,000 m は、向こう正面（0〜273 m）→ コーナー（273〜650 m）→ ホームストレート（650〜1,000 m。ゴールは直線の 350 m 地点）。ホームストレートは直線のコースと同じ線の上にあるので、大型画面・決勝線・HEAD ON・写真判定・FINISH・VISION はそのまま使える。コースの先（1,073 m 以降）と手前（−150 m 以前）はまっすぐ延ばしていて、2 つ目のコーナーは描かない。
- **選び方**: `field(seed)` が、補正の 8 回の後、同じ別の乱数列（`seed + 0x2545f491`）の 9 回目で選ぶ。楕円の確率は `OV[0]` = 1/2。レースとオッズの乱数列は変えていないので、直線のレースは楕円を入れる前と全桁一致する。R の再生とデモは種が同じなので、同じコースになる。
- **カーブの補正**: 自分の x が 273〜650 m の間だけ、1 ステップの前進に `(1 + a·(3.5 − i)/3.5)·(1 + s·(2u − 1))` を掛ける（`a` 0.25%、`s` 2%、i は枠、u は上の乱数列）。速さ・脚の回転・体力には掛けない（docs/apps/derby-corner-model.md）。結果（host 4 万レース）: 枠の勝率は内 14.1% から外 11.0%、本命 40.4%。
- **描画**:
  - `pose(g, w)` が区間の表でコーナーを通る。柵・スタンド・観客・刈り目・距離標・走者・大型画面は、首振りではすべて `pose` を通る。
  - 首振りの列（`ser()`）は、コーナーを 16 本の弦（`PAN[3]`）に分けて弦ごとに描く。弦の端は列ごとの格子に丸めるので、隣の弦とは柱の上で接する。
  - 弦の端は 1 フレームに 1 回だけカメラ座標にする（`VE`）。列ごとに、視野に入らない弦は算術だけで飛ばす（`ou()`）。直線は弦 1 本で、この判定も通らない。
- **カメラ**:
  - コーナーの WIDE は、常に一番近い首振り台にする。FIELD は向こう正面だけ（監督の `L < OB`）。
  - 楕円の WIDE 2 の台は、コーナーの中心近く（内柵から約 110 m 内側。`CAMS` の行の 6 番目の要素）に置く。先頭まで遠いので f が長く（約 700）、視野に入る弦が減る。直線の台は変えていない。
  - **横見のカメラ（WIDE・FIELD・CLOSE）は曲げない**。コーナーでは、柵に沿って展開した直線として映る。各カメラの高さ・地平線でコーナーを描くには、首振りの plan（高さ 6 m・地平線 28 を焼いてある。入力 8 個は使い切り）が足りない。
- **fps**（実機、2026-10-01）: 首振り WIDE は、直線で 24.8〜24.9 fps（MID）、楕円のコーナーで 15.1 fps、楕円のホームストレート側で 19.1 fps。横見のカメラは直線と同じ（約 29〜30 fps、VISION 25.6 fps）。
  - コーナーの費用は弦の本体の回数（1 フレーム約 20 回、直線は 6 回）と pose の三角関数（実機の `Math.sin` は 1 回 18.7 µs）。
  - 弦の本数を 16 → 10 にしても、実機の fps は変わらなかった。
  - 詳細は docs/apps/derby-pan-memory.md §12。

## plan の登録（場面ごと、1 フレーム 1 本）

| 場面 | 登録 | 解除 |
| --- | --- | --- |
| 起動 | パドックの 12 本を最初のフレームから 1 フレーム 1 本（評価中は登録しない） | — |
| ゲート | `gate`・`r0`〜`r7`・`map`・`vis`・`fr`・`hd` と首振りの `prail`・`t0`・`t1`・`hl`（17 本）を 1 フレーム 1 本。**馬が1頭ずつゲートに入る演出が、そのまま読み込み** | — |
| レース | なし（`tab` を押したときだけスタンド・観客の 2 本） | 先頭が 120 m を過ぎたら `gate` |
| 写真 | `photo`（静止画の間なので引っかかりが見えない） | — |
| 結果 | `conf`（紙吹雪） | `r0`〜`r7`・`map`・`vis`・`fr`・`hd`・首振りの 5 本・`photo` |
| 次のレース／再戦 | 次の場面の分 | `conf` |

登録は `pocket.memory.info().internalFreeBytes` が 18,432 B 以上のときだけ。実機（2026-09-30、大型画面を足した後）で、登録したターンの heap の落ち込みは最大 12.6 KB（ゲート）、パドックで 8.1 KB だったので、門で登録しても 5 KB 以上残る（MEGADEMO が破綻とみなした 4 KB の上）。門の値は以前 22,528 B（MEGADEMO の値）だったが、大型画面の分だけゲートでの空きが減り（登録の始まりで最小 25.5 KB）、余裕が 3 KB しか無かったので下げた。ゲートは 300 フレーム待っても全部そろわなければ `GO LOADSTALL` を出して走らせる（そろわない馬は描かれない）。

**評価中（トップレベル）に `load()` を呼ばない。** 実機の `internalFreeBytes` はターンの始めに採るので、ソースの評価中は `null` で、門（`null < 18432` は真）を越えられない。値はターンの中では変わらないので、「登録できるまで回す」ループは終わらない。2026-09-30 まで起動時に `while (queue.length && reg < 3) load();` があり、実機ではこれが 2 秒の評価期限まで回って起動に失敗していた（docs の「実機での測定」）。host の台本も評価中は `null` を返すようにした。

## 音

`pocket.audio.tone` は1声の正弦波（20〜8000 Hz、1 回に 1 音、鳴っている間の次の要求は BUSY）なので、音符の列を 1 音ずつ鳴らす小さな列にした。ゲート入りのファンファーレ（ド・ミ・ソ・ド、特定の曲ではない）、発走の鐘（高い音 3 回）、写真判定のシャッター音（2637 Hz を 25 ms）、当たり・外れの短い音形。**歓声（雑音）は出せない**（正弦波しか無く、PCM を JS から流すのは common-api §9 が禁じている）ので、歓声は見せていない（以前は観客の点の明滅で代えていたが、P24 の観客は明滅しない。下の「観客」）。`audio.cue('move'/'accept')` は選択・決定の操作音。最初の tone は、ホームから流れているプレイヤーの音楽を止める（`pocket_av_background_stop("tone")`）。

## デモ（アトラクト）モード

パドックで 15 秒（`DEMO_IDLE_S`）キーが無いと、ゲームが自分で1レースを走らせる。画面の右下（`[212,109,238,120]`、下の HUD 行の上）に `DEMO` が点滅し、どのキーでもパドックへ戻る。詳細と検証は docs の「デモモード」。

- **タイトルはパドック。** このアプリに独立したタイトル画面は無く、起動直後に最初に出る待機状態がパドック（馬を選ぶ前）なので、そこを「タイトル」とみなした。次のレースのパドックも同じ扱い（15 秒触らなければデモ）。
- **時計は `pocket.time.now()`**（起動からの単調なミリ秒、どのアプリにも入る面）。放置はフレーム数ではなく壁時計で数える。fps が落ちても 15 秒は 15 秒。キーを押している間・フレームの外で押して離した `A D E S 1 R , / tab`・`frame(buttons)` のパッドのビットが、計時をやり直す。
- **ゲームの経路をそのまま通す。** デモの操縦は `attract()` が1フレームに1つの「キー」を `dk` に置くだけで、`frame()` の `P()` は `dk` があればそれを押下として読む。A/D の選択と `1` の決定は、人が押したときと同じ行を通る。走らせる馬は奇数回目のデモが1番人気、偶数回目が2番人気（オッズ順、同率は枠の若い方）で、A/D の短い方向へ 12 フレームに1歩動かしてから `1`。賭け金は 100 固定。レース中はキーを送らず、カメラは監督（自動切替）に任せる（大型画面との統合で、240 フレームごとの `/` をやめた。`/` は監督を 5 秒止めるので、VISION や HEAD ON が出にくくなる）。結果を 150 フレーム（`DEMO_RES`）見せてパドックへ戻る。
- **プレイヤーの状態を汚さない。** デモの開始で持ち点・レース番号・選んだ馬・賭け金・音の出口（`A`）を `bk` に退避し、終わりで戻す。デモのレース番号は `1e6 + n`（n はデモの回数）で、種はセッションの基準とレース番号から決まるので、プレイヤーの種の列（1, 2, 3…）を進めない。100 万レースはプレイヤーが届かない（1 レース 50 秒で約 1.6 年）。`save()` はデモ中は何もしない。Back の保存ターンは先にデモを終えて（退避を戻して）から保存するので、デモの持ち点は書かれない。
- **無音。** デモ中は `A = null`（tone も cue も呼ばない）。放置された機械が勝手に鳴ると困るのと、最初の `tone` がホームから流れている音楽を止める（`pocket_av_background_stop("tone")`）ので、デモが始まるだけで音楽が止まってしまう。デモの終わりで残りの音符を捨てる。
- **キーで抜ける。** デモ中に押されたキー（`input.keys.down()` に新しく入ったキー、フレームの外で押して離したゲームのキー、`frame(buttons)` のパッドのビット）で、そのフレームのうちにパドックへ戻る。そのフレームは `dk = ''` なので、押したキーはゲームの操作として二度読まれない。途中で抜けたときは走者・写真の plan を解除して、タイトルと同じ 12 本に戻す。
- **`DEMO` は view のテキスト 1 つ**（`R.dm`、場面を組むたびに作り、`setVisible` で出し入れ）。パドックの ref は 30→31（上限 32）、レースは大型画面の文字 3 つと合わせて 10。大型画面と `DEMO` は重ならない（画面と脚の下端は最も低い VISION でも y = 90、`DEMO` は y 109〜120）。通常のゲーム中は非表示で、LIGHT・HEAVY の全画素ハッシュは追加の前と同じ。
- **デモ中のパドックの 1 行目は `RACE n` を出さない**（デモのレース番号 1000001 を見せても意味が無い）。
- **デモの幕**（2026-09-30）。放置の最後の 0.5 秒でパドックが黒へ溶け、黒のままデモへ切り替え、0.7 秒黒を保ってから 0.3 秒で戻る。キーで抜けたときは状態をそのフレームで戻し、画だけが黒から 0.3 秒で戻る（入力は遅れない）。幕は全画面の黒い rect 1 つ（`R.fd`、`R.t` の後・`R.dm` の前）の α で、α 0 の間は `setVisible(false)`。α は壁時計だけから `frame()` の頭（`attract` の後）で 1 式（`nw`・`idle`・`fe`）、ゲームは読まない。長さと段は `FX = [下りる ms, 黒の ms, 戻る ms, α の段数]` の 1 か所。パドックの ref は 32/32 で余りが無い。見出し（`DEMO PLAY`）は実機の評価の余裕を割ったので入れていない。詳細は docs の「デモの幕」。

## ゲスト heap とソースの書き方（デモと大型画面の統合、2026-09-30）

**以下はチャンクに分ける前の記録。** 分割後は評価の余裕が約 30 KB あるので、ここの「数十バイト単位の節約」の規則は必須ではなくなった。ただし、書き方の性質（クロージャ・大きな関数・spread）はそのまま当てはまり、1 つのチャンクを 15 KB 以上に育てると同じ問題に戻る。

評価（コンパイル）のゲスト heap が最も細い資源で、実機の余裕は 3.8〜5.6 KB（docs の「デモと大型画面の統合」）。次を守る。

- **配列リテラルの中で文字列を spread しない**（`[...'adesr1,/', 'tab']`）。実機ではこの 1 文が評価中にゲスト heap を上限まで使い切った（`vm/main` のデモ単体が起動しなかった原因）。host の QuickJS では起きないので、host の試験では見つからない。`GK` は `split(' ')` で作る。
- **クロージャ（アロー関数を含む）は 1 つでコンパイルのピークを約 0.3〜0.5 KB 使う**（host の実測。文は 1 つ約 65 B）。一度きりの `map`・`forEach`・`reduce` はループで書く（`odds()`・`race()`・`hud()` の能力バー・`settle()` のログ・ミニマップ）。効果の無いコールバックには `Boolean` を使う（`nop`）。`build()` の `map`・`forEach` はループにすると文が増えて逆に +192 B だったので残した。
- **大きな関数を作らない。** 1 つの関数のバイトコードのバッファは 1.5 倍の段で伸びる（… 5,166 → 7,749 → 11,623 B）ので、段を越えると一度に数 KB 増える。大型画面の矩形と draw の組み立てを `frame_()` から `paint()` に出したのはこのため。
- **コメントはピークに効かない**（host で確かめた。評価はソースを flash から直接読む）。CLAUDE.md の「ソースのバイト数がヒープを食う」は、コードの量については当たるが、コメントと字下げには当たらない（このアプリの host の実測）。
- 変えたら `DERBY_COMPILE_ONLY=1` で host のピークを見る（最終 +116,880 B、実機の失敗は +122,444 B で観測）。ただし spread やフレームの連続領域のように host のピークに出ない失敗があるので、最後は実機で起動を確かめる。
- **host のピークは実機の成否の順序すら外すことがある**（デモの幕、2026-09-30）。host で 500 B 低い版が、実機で詰め物 60 文を入れると OOM した。幕の見出しは 4 通りとも実機で詰め物 60 文が通らず、式 1 つの差で成否が反転した。**ソースを変えたら、実機で IIFE の末尾に何もしない 60 文の関数を足して起動すること**（余裕 3.8 KB の確認）。
- `step()` は `const y = s.x[i] = x + (s.v[i] = v) * dt` などの書き方で、host のバイトコードのバッファが 2,296 B の段の 30 B 手前にいる（2026-09-30）。足すと host のピークが約 1.1 KB 跳ねる。

## 持ち点の保存

`pocket.storage`（`storage.kv`、キー `derby.v1`、`{v:1, pts, race}`）。起動時に読み、結果が出たとき・次のレースへ進むとき・Back の保存ターンで書く。`storage.kv` はマニフェストに書かなくても全アプリに入る面（`app_session.c` が owner を設定して常に install する）なので、`main/pocket/app_registry.c` の行は変えていない。持ち点が 50 を切ったら 1000 に戻す。

## 観客（P24、2026-10-01）

観客席の観客は、模様線（`LINE_PATTERN`、[crowd-primitives-design.md](../../docs/kasane/crowd-primitives-design.md)）で描く。1 本の線に 24 セル（1 セル 0.4 m）の模様を持たせ、模様のビットが 1 のセルだけを塗る。

- **plan**: `crowd`（`derby_prog.js`、56 命令）1 本を横見と首振りで共用する。入力は両端の座標・段の送り（両端の −2.4 m / Z'。遠近の重みを兼ねる）・両端の模様の位置（セル）。1 段は模様線 3 本で、体 2 本（段の線とその 1 px 上）と頭 1 本（2 px 上）。段ごとに服の色が 2 色で交互になり、模様が `KN[3][3]` セルずれる。
- **調整する値は `KN`（`derby_prog.js`）の 1 か所**:
  - 段階ごとの 7・8 番目: 頭と体の模様（24 ビット。1 人 3 セル、頭は真ん中のセル）。
  - `KN[3]` = [肌の色, 服の色 1, 服の色 2, 段ごとの模様のずれ（セル）, 空席の色（−1 で描かない）, 1 m あたりのセル数]。
  - 段の数は従来どおり段階ごとの 2 番目（LIGHT 2・MID 3・HEAVY 4）。
- **位相の流し方**: 模様はコース上の位置（横見は柱 `j` から、首振りは弦の端のコース位置）に固定してあり、カメラが動くとスタンドと一緒に流れる。
- 首振りでは、両端の奥行きが違う線を VM が 2・4・8 本の弦に割り、模様の間隔を奥ほど詰める。
