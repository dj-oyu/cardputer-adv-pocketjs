# MUSIC — ホーム画面のプレイヤー

**overlayアプリ**。Appsからは起動しない。Settings → HOME OVERLAY → MUSIC を選ぶと
**XMBが終了してこれがその場所に立つ**（`docs/common-api.md` 3.1）。背景のシーンは
下で描かれ続ける。

| キー | 動作 |
| --- | --- |
| ENTER | 再生 / 一時停止。曲が無ければファイルを選ぶ |
| LEFT | 別のファイルを選ぶ |
| RIGHT | 次の曲へ |
| ↑ | 共有するフォルダーを選び直す |
| `-` / `=` | **音量。シェルのキーで、このアプリには届かない**（下記） |
| **ESC** | **overlayを降ろしてXMBへ戻る。シェルの予約キーで、このアプリには届かない** |

曲が終わると `fs.nextFile` で同じフォルダーの次へ自動で進み、末尾で先頭へ戻る。

**フォルダーの選び直しに専用キーが要る理由。** `requestFolder` は
`pickFile` が `PERMISSION_DENIED` を返したときにしか呼ばれない設計だったので、
**一度共有すると refusal が起きなくなり、別のフォルダーへ移る道が消えていた**。
間違ったフォルダーを選んだ人が戻れない。↑がその道である。

## 音量はこのアプリのものではない

`-` と `=` はシェルが取る。プレイヤーを見ながら押せば音量は変わるが、
**変えているのはシェルであってこのアプリではない**し、どのアプリにもできない。
自分で音量を上げられるアプリは、誰も見ていないあいだに上げられるアプリである。
だから `pocket.audio` に音量は無い。

表示もシェルが出す（右上に1.5秒バーが出る）。overlayの上に描かれるが、
3.1の規則に穴を開けてはいない — 規則は「overlayがシェルの**同意の面**を覆えない」で、
シェルがoverlayを覆う向きは最初から問題になっていない。

NVSへ保存されるので再起動しても残る。段が5つで上寄りなのは、
0x60より下がこの基板のスピーカーでは部屋の雑音に埋もれるからである。

## ui.* が無い

overlayセッションにRust UIコアは無い（`pocket_overlay.h` に理由）。描画は
`pocket.overlay` の表示リストで、矩形と文字列だけ。シェルがシーンの上へ合成する。

**はみ出しは切り取られず拒否される。** これは仕様であって不便ではない——1文字はみ出した
行は作者が知るべき間違いで、末尾が消えた表示は知らせたことにならない。実際この
アプリは実機で2回それに落ちた:

- `title.slice(0, 23)` は**コード単位**を数え、`overlay.text` は**バイト**を数える。
  `02 インザハウス.mp3` は14文字28バイト。`cut()` が面と同じ数え方をする。
- 44文字のヒント行は47バイト上限には収まるが、`8 + 44*6 = 272px` で**240pxの
  パネルに入らない**。バイト上限とパネル幅は別の制限で、小さいほうは常に同じではない。

## 長さを表示しない

MP3の `durationMs` は再生が終わるまで `null` で、`seekable:false`。したがって
「何%まで来たか」は原理的に出せない。バーは1分周期で満ちて繰り返すだけで、
**「まだ動いている」しか言わない**。0msを長さのように見せるよりは正直である。

## 次の曲を誰が持つか

ホストが持つ（`pocket.fs.nextFile`）。理由は2つある。

**判断が1つの場所に残る。** 拡張子フィルター、`.` 始まりの除外、
`sd_name_reserved`——「再生できるファイルとは何か」の判定は全部
`file_picker.c` にあり、ピッカーが人に見せている行と同じものである。アプリが
`fs.list` で自前に走査すると、その判定の**2つ目の実装**がJavaScript側にできて、
ずれても何も失敗しない。

**リストを持たずに順序が手に入る。** `fs.list` が整列しないのは全件を同時に
保持しないためで、その拒否は正しい。だが**後続を1つ訊くだけなら保持は要らない**——
1周して「現在より大きい名前のうち最小のもの」を覚えれば、時間O(n)、メモリO(1)、
ゲストのヒープ消費ゼロ。曲順が要るのにリストは要らなかった。

## 進捗の見せ方が2つあるのはなぜか

**長さが分かるときだけバーを描く。** MP3の総フレーム数はXing/Info/VBRIタグに
正確に書かれていて、それを読めば `durationMs` が出る（`pocket_mp3_total_frames`）。
無い場合は**推測しない** — CBR前提の「バイト数÷ビットレート」は定ビットレートなら
正確で可変なら黙って外れ、どちらかをファイルは教えてくれない。

タグが無いときは**光が左から右へ流れる**。位置を一切主張しない絵で、
「鳴っている」だけを言う。部分的に満ちたバーはどうしても位置を主張してしまう。

**実機のこのアルバムは20曲すべてタグ無し**だったので、カード上では光のほうしか
出ていない。タグがある側は `tools/test_mp3_duration.c` がホストで検査する——
「無い」だけを通るテストは、動く実装と何もしない実装を区別できない。

## 実測（2026-09-09、実機）

```
overlay: OVERLAY_COST free_before=268708 free_after=158840 floor=57344
mp3: MP3DEC packets=537 frames=336666 faults=0 mean_us=6093 worst_us=6982
background: fps=26.4 draw=16.03 hud=3.87 (ovl=3.44 menu=0.04) send=8.76
再生中の空き free=154200 / 抜けた後 free=273892 largest=102400
```

**ホーム画面は再生中に30 → 26 fpsへ落ちる。** 内訳を見ると原因はoverlayではない:
`ovl` は3.4ms（帯の外の項目を飛ばす前は5.33ms）で、増えているのは
`send` 7.08→8.8ms と `prep` である。パネル転送とシーンが、復号器とカード読み出しと
CPUを取り合っている。**光のアニメーションを30Hzから15Hzに落としても変わらなかった** ——
測ってから書いている。

**リークは見えない。** 2回の走行で、抜けた後の `free` が 273,068 と 273,892、
`largest` はどちらも 102,400。曲数も再生時間も違う2回で同じ場所に戻る。

**最悪ターンの188msは「ゲストが188ms動いた」ではない。** `overlay_budget` も
ゲストの割り込み期限も**実時間**を測るので、uiタスクが復号器（優先度6）・
オーディオ（7）・カード読み出しに横取りされている時間がそのまま入る。
このREADMEは以前これを「`open()` がカードを読むターン」と書き、次に
「おそらくフォントアトラス構築」と書いた——**どちらも当て推量で、どちらも外している**。
分かっているのは測り方だけで、188msに何が入っていたかは特定していない。

この測り方は実害を出した。FLOWER背景（`draw=71ms`、`kernel=53ms`）で再生すると、
**文字を数えるだけの5行のループが `InternalError: interrupted` で落ちた**。
50msの割り込み期限が、ゲストの仕事ではなく機械の混雑を測っていたためである。
期限は前景と同じ250msにした。費用の制御は別機構（`budget_us` の連続超過）で、
そちらは理由の付いた停止を出す。**暴走検知と費用制御を1つの数で兼ねてはいけない。**

**未測定:** カードの読み出しの計時、長時間（数十分）の再生、
188msのターンが何をしているか。
