# miccheck

`pocket.audio.capture`（docs/common-api.md §9 のマイク）が実機で立つかを見る1本。表示は
持たず、`console.log` の行が結果そのもの。`tools/pocket_bridge.py demo --source
apps/miccheck/miccheck.js` で Playground に打ち込んで走らせる。

ソースのバイト数はそのままゲストのヒープを食うので、理由はここに置いてアプリ側には
置かない。

## 何を主張する行なのか

| 行 | 通れば言えること |
| --- | --- |
| `CAP true/true null` | capabilityが実装済みで、コーデックが見えている |
| `LIM 24000/1/2048` | 公開している上限が**コードで強制している値**と一致する |
| `RATE16 INVALID_ARGUMENT` | 16000 Hzを黙って24000に読み替えていない |
| `REC1 open` / `REC1 n=… peak=… clip=…` | 1回目の録音が実際に音を運び、歪んでいない |
| `REC2 …` / `REC3 …` | **セッション内の2回目・3回目の録音も音を運ぶ** |
| `DONE` | 途中でrejectして落ちていない |

**REC2とREC3は「セッション内で録音し直せるか」の答え。** 一時期「2回目の録音は無音になる」と
疑い、`i2s_del_channel` が全二重の成立を戻さないという機構をドライバのソースから読んで、
RXチャネルを再起動まで保持する変更（6,144バイト常駐）まで入れた。**その不具合は製品側には
存在しなかった**——見えていたのは音をまったく読めていない診断の中だけで、その対照行も無音
だった。3回とも同程度のpeakが出るので疑いは消え、6,144バイトも消えた。
**ドライバのソースから読んだ機構は、製品の経路に訊くまでは仮説である。**

**`clip` は0でなければならない。** 0でなければ `0x17` を下げる（下げても失うのはint16の
レンジだけで、S/Nは失わない——このゲインは変換の後にあるから。上げる方は歪ませる危険が
あるので、迷ったら下げる）。8ステップずつ下げて測り直すのが手順で、**デシベル計算から新しい値を
導かないこと**——このレジスタのステップ幅はこの機体で検証されていない。

**`peak` は距離と声の大きさの関数であって、機体の性質ではない。** 同じレジスタで、5行の
スイープ時は最大8,395（26%）、その数分後は22,539 / 30,528 / 31,779（69/93/97%、声を張った）、
さらに後の普通の声では17,816 / 22,559 / 27,825（54/69/85%、`clip=0`）。違いは距離と声量だけで
4倍動く。だから**単独のpeak値を「このゲインは余裕がある」の根拠にしてはいけない**——それは
この機能が一日繰り返した失敗そのもの。正確な言い方は「普通に話す分には歪まない、声を張れば
歪む」で、「歪まない」ではない。

`peak` の読み方: 静かな部屋で数十〜数百、マイクに向かって話せば1〜3万台。1桁のままなら入力
経路が開いていない。

## マイクはアナログ入力（`0x14=0x1a`）。PDMではなかった

一日の最後まで逆を信じていた。PDMピンにはDCオフセットが乗っているだけでマイクは無く、ADCの
ハイパスがそれを約450msかけて除去する——その除去途中の値を全員が「音」として測っていた。

```
analog  2033  885  309  228  342  1312  587  1152  928  865   <- 声（150msごとのrms）
pdm     3660 3660   25    0    0     0    0     0    0    0   <- 定数、そして無音
```

analogはバケットごとに動く。pdmは300msのあいだ**桁まで同じ数**で、その後0へ落ちる——定数で
あって音ではない。**PDM時代に取ったpeakはすべて無効**で、当時の録音長0.64秒が450msの窓に
ほぼ収まっていたため、オフセットが声のように見えていた。

## 録音インジケータとレベル計

録音中は画面右上に赤い点が出る。描いているのは `board_present()`（`main/hal/board.c`）で、
パネルへの転送路はここ1本しかないので、アプリが何を描いても点はその後に載る。§9が
「ホストが録音状態を表示する」をホスト側の義務と書いているのはこの意味。アプリが描画を
止めた場合に備えて、録音中は0.5秒に一度だけ再描画を要求する。

点の左に6セルのレベル計が出る（倍々スケール、最下段が約1/64）。**色が変わるのはクリップの
ときだけ**——最上段が琥珀になる。赤は「録音中」に予約されている。話しているのにセルが1つも
点かないなら小さすぎ、琥珀が出るなら大きすぎ。実測（`0x16=7` / `0x17=0xc8`）では普通の声の
peakが54〜85%なので、**普通に話す分には琥珀は出ず、声を張れば出る**。

**次に実機を触る人へ、意図的な確認を1つ。** 声を張って琥珀セルを出し、そのとき同じ録音の
`clip=` が0でなくなることを確かめてほしい。画面の表示とログが同じ出来事について一致するかの
検査で、「計器が正しいこと」と「計器が妥当であること」は別だという、この機能が一日かけて
学んだ区別そのもの。メーター自体はまだ「ついでに見えた」以上の確認をされていない。

ホスト側で確かめられる範囲（連続性・overflow・close・セッション終了・インジケータ・レベル計）は
`tools/test_pocket_capture.c` が実物のQuickJSと実物の `pocket_capture.c` / `pocket_api.c`
を ASan/UBSan で回して見ている。

```
wsl -e bash -lc "cd /mnt/c/devs/m5stack/cardputer-adv-pocketjs && bash tools/build_pocket_capture_test.sh && /tmp/test-pocket-capture"
```
