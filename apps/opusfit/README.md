# opusfit — largest free block を誰が削るのか

**いまこのアプリが答えようとしている問いは「収まるか」ではない。それは答えが出た**
（2026-09-09、実測: リンクした無線の横でOpusが最後まで鳴り、`underruns=0`）。
**いま追っているのは、繰り返すと largest free block が縮んでいくことである。**

同じ段の同じ状態で比べられる1組がある（実測、前回の走行）:

```
cycle 0  flash+play   largest 31,744
cycle 1  flash+play   largest 11,776
```

**同じ段で3分の1になっている。** free ではなく largest なので、これは会計の話ではなく
断片化の話に見える。**5回目の再生で鳴らなくなるストリームは、最初から鳴らないものより悪い。**
だから今回の不足（接続が largest を 31,744 → 19,456 にする件）より先にこれを見る。

## 3つの仕事を分けて回す

前回の走行は無線・プレイヤー・接続を**同時に**回していたので、「何かが漏れている」以上のことが
言えなかった。今回は1つずつ、それぞれ4回。

| 仕事 | やること | 何を分離するか |
| --- | --- | --- |
| `radio` | acquire → 30f → lease close → 120f | **無線だけ。** 音もHTTPも無い |
| `player` | open(assets) → play → 60f → close | **プレイヤーだけ。** 無線を上げない |
| `conn` | acquire → open(http) → 30f → close → lease close | **接続だけ。play() を呼ばない** |

`conn` が `play()` を呼ばないのが要点で、そうすると復号器もPCMリングも生まれないから、
この仕事が持っていくものは**接続そのもの**（受信タスク、httpクライアント、パケットリング）に限られる。

各回 `<kind>.<n>.before` と `<kind>.<n>.after` を出す。**`after` が回を追って下がる仕事が犯人で、
`before` に戻る仕事は無罪。** 失敗しても同じ形で畳んでから `after` を出す——
漏らす失敗こそが探しているものだから。

## 走行前の予測（実測が入る前に書く）

**`player` が犯人だと予測する。導出であり、根拠は前回の走行そのものにある。**

```
cold                     largest 62,464
after.flash（無線なし）   largest 43,008     -19,456
```

**無線が上がる前に、フラッシュからの再生1回で largest が19KiB落ちている。**
`conn` も `radio` もまだ関わっていない。

これが正しければ、**断片化はこの機能のものではなく、既存のプレイヤー経路のもの**である。
`apps/opusplay` は14サイクルを綺麗に回したが、あれが定常性を確認していたのは
`deltaTenthMs` と free であって **largest ではない**。誰も見ていなかった数字は、
失敗しないという意味で通っているように見える。

**反証条件:**

1. `player.n.after` が横ばいなら予測は外れで、犯人は `radio` か `conn`。
2. `radio.n.after` が単調に下がるなら、原因は無線で、**Opusとは無関係に全機能へ効く**。
   lwIPが返さない約4.8KiBは既知だが、それは free の話で largest の話ではない。
3. `conn.n.after` だけが下がるなら、それは私の受信経路であり、私が直す。
4. **どれも下がらないなら、前回の drift は3つの相互作用であって単独の犯人はいない。**
   そのときは同時に回す形に戻して、順序を変えながら測る必要がある。

**この計測器自身がプールの中に座っている。** ソース4,267バイト、ホストの実測比 4.5:1 で
ゲストヒープ約19KiB。数字の隣に必ず書くこと。
