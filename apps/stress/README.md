# STRESS TEST（`apps/stress/stress.js`）

ゲストのヒープと描画に同時に負荷をかける試験用アプリ。見た目は夕暮れのサーフの海で、80s・vaporwave・lo-fi の
ネオンのポスターの色（縞の夕日と水面の照り返し、瞬く星、透視でうねる波、ヤシのシルエット、魚群、跳ねるイルカ、
泡、ヤシの葉の縁を流れる光、走査線と VHS のトラッキングのノイズ）。メニューの index 7。

**2026-11-03 に描画を Shiki に移した。** それまでは Kasane の保持シーン（75 コマンド、キャッシュの
テンプレートとインスタンス、半透明の図形）で海を描いていた。いまは画面の全体を `pocket.kasane.shiki` の
組み込みの式 12 本（`stress_prog.js`）が毎フレーム描き、式は実機では JIT の対象になる
（[docs/kasane/shiki-jit.md](../../docs/kasane/shiki-jit.md)）。保持シーンは Shiki の画面（`tx.image`）と
その上の HUD（題字・段階・状態の 2 行・メーター）の 9 コマンドだけ。下の「実測」以降の節は、移す前の版の記録。

## 何をするか

- **メモリ**: 毎フレーム 2 個の塊を足す（オブジェクト 24 個の配列、長い文字列、`Float32Array`、
  `DataView`+`ArrayBuffer`、`Int16Array`。5 回に 1 回は循環参照のごみも作り、循環回収を働かせる）。
  塊の数が段階の上限を超えたら古い半分を捨てる。
  - Enter で段階を回す: LV1 15 個 → LV2 35 個 → LV3 上限なし。
  - LV3 は実際に確保失敗まで積み、捕まえてすべて捨て、また積む（`STRESS_OOM`）。確保失敗は
    `app_session.c` がログに残すだけで、アプリは続く。途中で失敗した `replace` は参照をすべて古くするので、
    失敗したフレームの次はシーンを作り直す。途中で失敗した Shiki のフレームは、次の `beginFrame` が捨て直す。
  - `pocket.memory.onPressure` はレベル・原因を購読する。LV3 では割り当て失敗 bit の通知時に
    保持プールを破棄する。初回 OOM を意図的に残し、通知 callback 内ではログや追加配列を作らない。
- **ネイティブの `Uint8Array`**（F3b の実機確認、`docs/vm/builtin-floor-plan.md` §17.3）: 2 フレームに 1 回
  `assets:/hello.js` を 1 KB ずつ `pocket.fs` で読む。読んだ塊もメモリの負荷に入る。最初の塊で、JS がまだ
  グローバルの `Uint8Array` を読んでいない状態から、ネイティブが作ったものの `prototype`・`constructor` が
  グローバルと一致するかを確かめる（`STRESS_NATIVE ok|NG`）。
- **描画**: 1 フレームに `drawMany` 1 回で 18 回の draw（奥から手前へ、1 回の入力は 5 個）。空と海は 1 行おきに
  線で塗り、間の行はフレームの背景色のまま（走査線）。全行を塗っていた版の半分の画素で、画素を書くだけの仕事
  （メモリの速さで決まる部分）を減らし、線分とラスタを形のある描画に回す。1 回の draw のラスタの上限 8,192 で、
  240 px の行は 34 行まで、だから空と海は 2 本の帯。線分は 1 フレーム約 900 本で、上限 1,024 の近くまで使う
  （ヤシの葉の分割数と波の刻みは、この上限で決めた）。段階は描画の量を
  変えない（ヒープの段階だけを比べるため）。120 フレームごとに HUD を `replace` で作り直す。

## Shiki の式（`stress_prog.js`）

| 式 | 入力 | データ領域 | 描くもの |
| --- | --- | --- | --- |
| `sky` | 開始行・行数 | `ramp`（`u16`、135 行の色） | 1 行おきの全幅の横線。行の色を表から引く（`LOOKUP`）。間の行は背景色（走査線） |
| `stars` | 時刻の位相 | `at`（`i16`、位置・位相）、`tw`（`u16`、明るさ 8 段の色） | 星 24 個。`sin` の明るさで色を引く |
| `sun` | なし | `rows`（`u16`、行・半幅・色） | 夕日の縞。隙間の行は JS が毎フレーム画面外（y 300）へ動かし、縞が上へ流れる |
| `glow` | 時刻の位相 | なし | 水面の照り返し 14 本。2 色を交互に、`sin` で息づかせる |
| `waves` | 時刻の位相 | `wc`（`u16`、12 本の色） | 水平線から手前へ 12 本のうねりの折れ線（間隔は奥行きの 2 乗、振幅は手前ほど大きい） |
| `trunk`・`crown` | 根元・向き・揺れ | `fr`（`i16`、葉の制御点と先端） | ヤシの幹（`CUBIC` 3 本）と葉 7 枚（1 枚に `CUBIC` 3 本で幅を出す）。左右 2 本で向きを反転 |
| `rim` | 根元・向き・揺れ・位相 | `rf`（`i16`、葉の縁の 1/3・2/3・先端）、`lt`（`u16`、光の 8 段の色） | 葉の上の縁の光。葉ごとに `sin` で明るさを変え、光が葉から葉へ流れる。`CUBIC` の色は登録時に決まって動かせないので、縁は曲線上の点を JS が起動時に計算した折れ線（`LINE_C`）。揺れの分は、各点の先端の重みだけ式が足す |
| `fish` | 群の位置 | `school`（`u16`、位置・色） | 1 群 9 匹。胴の三角と尾 |
| `dolphin` | 位置 | `shape`（`i16`、輪郭の点） | 輪郭の折れ線と腹の線。2 頭は色違いの 2 つの handle |
| `bubbles` | なし | `ring`（`i16`、位置・半径） | 8 角形の輪。位置は JS が毎フレーム窓に書く |
| `vhs` | 行・位相 | なし | トラッキングのノイズ。5 秒ごとに 14 フレームだけ画面を下りる（ほかの時は画面外） |

- 水平線（y 60）と夕日の中心（x 176）は `stress_prog.js` と `stress.js` の両方に書いた定数で、同じ値を保つ。
- 色は RGB565 で、JS が起動時に `rgb()` で変える。Shiki の線に透明度は無いので、旧版の半透明（魚群・泡）は不透明になった。
- `sin` の位相は JS が 2π で折り返して渡す（Shiki の `sin` は Q16 のラジアン、BIG WAVE と同じ）。
- 式は組み込みの表（`stress.<name>`）。`stress_prog.js` の `@shiki` 関数をビルドが flash の表にし、チャンクからは消す（`chunks.txt` の `prog`。アプリは読み込まない）。
- Shiki の区画は既定の 48 KiB（マニフェストは `kasane.shiki` を required に挙げる。Shiki が無いと描けないため）。host（m32）の使用量は約 30 KB（フレーム 2 枚・式・領域）。実機では同じ区画に JIT のコードが加わる（未測定）。
- ゲストのヒープ（host、m32、上限 160 KiB で評価）: 評価後 61,991 B。同じ条件で旧版は 54,941 B（+7.1 KB）。

## Kasane の制約（旧版で踏んだもの）

旧版（保持シーンだけで海を描いた版）で踏んだ制約。Kasane のエラーメッセージの改善はこの経験から入った。

- `replace` は `tx.background()` が無いと `INVALID_ARGUMENT` で断る。
- 角丸の半径は 8 まで（形状の幅・高さの半分以下も必要）。
- キャッシュのコマンドは同じ Kasane ホスト内の全テンプレート合計で 48。インスタンスごとにテンプレートのコマンド数をシーンの 80 から使う。
- 作ったときの `bounds` が既定の `clip` になる。`setRect` で動かす図形は `clip` を明示しないと、元の位置と重なる部分しか描かれない。

## ログ（USB）

| 行 | 意味 |
| --- | --- |
| `STRESS_READY` | 評価が終わった |
| `STRESS_NATIVE ok len=N` | ネイティブ生成の `Uint8Array` がグローバルと一致（`NG` なら不一致） |
| `STRESS f= lvl= pool= peak= oom= cyc= nat= natOk= err= cmds= native= pressure= pe= trim= shiki=` | 60 フレームごと。`pressure`〜`trim` は現在の圧迫マスク・通知回数・通知による破棄回数、`shiki=` は Shiki の区画の使用量／大きさ（Shiki 版で末尾に足した） |
| `STRESS_LEVEL n` | Enter で段階が変わった |
| `STRESS_OOM n= at=` | 確保失敗を捕まえた |
| `STRESS_SUSPECT n= at=` | OOM 例外の文字列確保も失敗した疑い。試験側は同一ターンの VM OOM 記録がある場合のみ許容 |
| `STRESS_FAIL where ...` | 確保失敗以外の例外（数は `err=`） |

描画の時間はファームの `KASANE_PAINT turn_ms= render_ms= ...`（30 フレームごと）で見る。

## 回し方

- 実機: `python tools/stress_app.py --port COM3 [--seconds 20] [--log FILE]` が起動・3 段階・終了を通しで回し、
  段階ごとの fps・`turn_ms`/`render_ms` の中央値・OOM 回数を JSON で出して `STRESS_APP_PASS|FAIL` を判定する。
  画面を確認するときは `--launch-only` を付ける。`STRESS_READY` と60フレーム進行を確認して
  ポートを閉じ、アプリは終了しない。
- ホスト: `bash tools/build_stress_app_test.sh && /tmp/test-stress-app`（WSL、Node 16 以上）。実物の QuickJS・
  `pocket.kasane`・`pocket.kasane.shiki`（式は firmware と同じ組み込みの表）で 900 フレーム回し、
  Kasane の検証に通らないシーン、Shiki の draw の失敗、例外を焼く前に見つける。
  `STRESS_PPM=<prefix>` で 90・240・420 フレーム目の画面を PPM に書く。
  - `M32=1 bash tools/build_stress_app_test.sh && /tmp/test-stress-app-m32` は実機と同じ 8 B の JSValue・4 B のポインタ
    （`tools/vmtest/m32_sysroot.sh`）で同じ検査をする。64 ビットのホストはオブジェクトの大きさが実機と違うので、
    ヒープの数字はこちらで見る。`STRESS_HEAP_LIMIT=163840` を付けると評価から実機と同じ上限で回し、評価後の使用量を出す。
  - Shiki 版の結果（2026-11-03、host）: 64 ビット ASan・m32 ASan とも PASS。HUD 9 コマンド、OOM から回復。
    `STRESS_HEAP_LIMIT=163840` の m32 でも PASS（OOM 12 回から回復、例外・描画の失敗は 0）。
  - 2026-11-03 に stub の数え方を直した: OOM が stub の `read()` の中（`Uint8Array` の確保）に当たると、読み終わりを数えず
    `reads=449/448` で FAIL していた（旧版の `stress.js` でも同じ。失敗した読みも Promise は settle するので、`finally` で数える）。
  - `STRESS_DISPATCH_FAULT=1` の変種は、注入のスクリプト自身が例外を出して FAIL する。変更前の `51f5feb` でも同じ（未調査）。
- 実機: Shiki 版はまだ実機で確かめていない（fps・`turn_ms`・`render_ms`・JIT の結果・空きヒープ）。

## メモリ通知統合後の実機確認（2026-09-27）

`feature/kasane` に `vm/main` の F3c と STRESS シーン再生成修正を統合した
Cardputer ADV、各段階20秒。75コマンド、`STRESS_APP_PASS`。LV1/LV2/LV3 の fps は
29.7/29.7/26.2、`render_ms` 中央値は 6.49/6.43/6.72 ms。LV3 は18回の OOM から
回復し、低メモリ通知36回、通知による保持プール破棄18回、描画・アプリのエラー0。
ソース評価後の `js=` は 59,960。ホスト900フレーム試験も PASS。

QuickJS は極限の OOM でエラーメッセージ文字列さえ確保できず、単なる `InternalError`
として見える場合がある。アプリはこれを `STRESS_SUSPECT` として分けて記録し、
ホスト試験は同一フレームの OOM canary、実機試験は同一ターンの VM OOM ログとの
対応を要求する。対応のない `InternalError` は引き続き FAIL とする。

## Kasane キャッシュ配置の実機 A/B/A（2026-09-26）

同じ75コマンドのアプリ、Cardputer ADV、COM3、各段階20秒、計数OFFで、変更後→変更前
（`3b94d0f`）→変更後を独立bootで測った。`turn_ms` はJS `frame()` とそのjob処理の合計で、
Kasane API単独の時間ではない。`render_ms` は転送を除いた描画時間、`send_ms` はLCD転送時間。

| 段階 | 変更後1: fps / turn / render / send | 変更前: fps / turn / render / send | 変更後2: fps / turn / render / send |
| --- | --- | --- | --- |
| LV1 | 25.7 / 8.64 / 21.26 / 4.15 | 25.7 / 8.72 / 21.20 / 4.11 | 25.7 / 8.65 / 21.22 / 4.14 |
| LV2 | 25.7 / 8.60 / 20.98 / 4.08 | 25.7 / 8.65 / 20.94 / 4.04 | 25.7 / 8.60 / 20.98 / 4.07 |
| LV3 | 22.2 / 16.47 / 22.62 / 4.13 | 22.7 / 17.60 / 21.99 / 4.16 | 22.3 / 16.43 / 22.60 / 4.14 |

時間は各30描画窓の中央値、単位ms。全run `STRESS_APP_PASS`、75コマンド維持、LV3で
15回OOMし復帰、Kasaneエラー0。LV1/2では`turn_ms`が0.05〜0.08 ms短くなったがfpsと
描画時間の改善は検出できない。LV3はOOM周期・描画時間もずれたため速度向上を主張しない。
テンプレートextent追加により表示されたnative予約量は13,108→13,172 B（+64 B）。
このA/B/Aはキャッシュ変更だけを切り替えた同一binary試験ではない。変更後imageには成功経路の
JS診断分岐と、STRESSが使わないschema slot走査変更も入るため、0.05〜0.08 msをキャッシュ単独の
因果値とは断定しない。コード上は毎PATCH動く4 instance・計46 child commandについて、旧実装の
92回のtemplate decode、138回のchild change、4回のgroup更新が、変更後はdecode 0回、
child change 92回、group更新0回になる。実機で確認したのはこの構造的削減と、全体の非劣化・
小幅な`turn_ms`短縮である。

通常版の`render_ms`はLV1約21.2 ms、LV2約21.0 msで、`send_ms`約4.1 msは別に加わる。この全体を無駄なFW
オーバーヘッドとは呼ばない。別の計数ON診断imageで、初回全画面更新を除く30描画窓を
調べると、LV1の平均で画素合成bracket約17.7 ms、group tile約3.3 ms、text span約0.8 ms、
command view取得約0.9 msだった。bracketは入れ子で、割込みも含み、合計や通常版との差分には
使えない。約3,100回/frameのview取得bracketも実core decode回数を意味しない。現状の主な
負荷は半透明・重なりの画素処理であり、command capをハードウェア限界とする証拠はない。
ログは `.cache/kasane-stress-{baseline,preopt,postopt-repeat,profile}-20260926.log`。

## 縦グラデーションのPIE描画（2026-09-26）

空と海の縦グラデーションは静的でも、STRESSが汚す帯では毎回描き直される。
LV1の既存ログで30描画窓の末尾17フレームは平均26,052転送バイト、すなわち
約13,026画素（画面の40.2%）。両グラデーションは上下で全画面を覆うため、
この画素はグラデーションの対象でもある。色補間は既に行単位だが、従来は
端点が異なるというだけでPIE合成を使わず、行内で色が一定の縦グラデーションも
画素ごとのscalar合成を通っていた。新経路は既存の8画素PIE kernelへ行ごとの
色を渡す。LUTの選択条件は変更しない。

同一診断バイナリで `KASANE_STRESS_GRAD_AB=1` とし、30描画ごとに新経路を
ON/OFFしてSTRESS各段階20秒を測った。`render_ms` は送信を除く30描画平均の
窓中央値で、`bytes_avg` は窓内の転送量平均。切替以外は同じ75コマンド。

| 段階 | 旧経路OFF | 新経路ON | ON/OFF窓数 | 平均転送量 OFF / ON |
| --- | ---: | ---: | ---: | ---: |
| LV1 | 20.99 ms | 6.94 ms | 9 / 9 | 26,126 / 26,581 B |
| LV2 | 20.53 ms | 6.94 ms | 9 / 10 | 26,213 / 26,967 B |
| LV3 | 23.09 ms | 7.81 ms | 8 / 7 | 28,449 / 27,701 B |

LV1で旧窓と両隣の新窓との差の中央値は14.51 ms（8組）、LV2は13.45 ms
（9組）。`send_ms` は約4 ms、`turn_ms` は約8.6 msのまま。LV3はOOMの
周期が変わるため、速度の因果評価には使わない。ホストでは縦グラデーションの
不透明・半透明・角丸・ディザを含む120フレームの4経路比較で全画素一致、
STRESSの900フレームの画面digestも新旧 `fdca4e79` で一致した。
ホストでは `KSN_VERTICAL_GRAD_PIE=0 /tmp/test-stress-app` と
`KSN_VERTICAL_GRAD_PIE=1 /tmp/test-stress-app` で同じ900フレームのdigestを比較できる。

診断切替を外した通常ファームでもSTRESS全段階PASS。LV1/LV2は29.7 fps、
`render_ms` 中央値は6.93/7.14 ms、LV3はOOM14回から復帰した。
証跡は `.cache/kasane-grad-pie-{ab,final}-20260926.log`。現在の40%という値は
30描画窓の**末尾フレーム**の転送量から得た標本で、全フレームの平均ではない。

## 群描画の到達表と子命令スキップ（2026-09-26）

縦グラデーション改善後に計数ONのSTRESSを測ると、群描画の入れ子bracketは
30描画窓あたり約17〜29百万cycle（240 MHzで約2.4〜4.0 ms/描画）、
text spanは約0.7〜0.9 ms/描画だった。計器自体の負荷と割込みを含むので
通常ビルドの時間と加算しない。魚群の1インスタンスは18子命令だが、従来の
到達表は16件までで、群全体の空タイル判定が無効だった。

到達表を18件（144 Bのスタック領域）にし、表が全子命令を収容できる場合は
空タイルだけでなく、そのタイルに届かない子命令の再読出しも省く。
表に収まらない群は従来経路へフォールバックする。これはアプリ種別で分岐する
仕組みではなく、任意の群に使う一時的な幾何情報である。
18子命令fixtureを追加したホストスイートでは、到達表ON/OFFと64/16画素tileの
計4,212,000画素が一致し、fixtureは独立した合成参照とも一致した。
計数ビルドでは子命令のスキップが
実行されたことを確認した。STRESSの900フレーム画面digestも従来と同じ
`fdca4e79`。

同一診断バイナリで `KASANE_STRESS_REACH_AB=1` とし、30描画ごとに
到達表をON/OFFした。表を18件へ拡張しただけの試験と、子命令スキップを
加えた試験は別runである。下表は旧経路OFF窓と両隣のON窓平均との差の中央値。
単位ms/描画で、正値がONの短縮。LV3はOOMにより参考値。

| 段階 | 18件化のみ | 子命令スキップ込み | ペア数（後者） |
| --- | ---: | ---: | ---: |
| LV1 | 0.27 | 0.67 | 8 |
| LV2 | 0.11 | 0.44 | 8 |
| LV3 | 0.36 | 0.63 | 6 |

両runとも `STRESS_APP_PASS`、75コマンド、LV1/2約29.7 fps。
