# M1: Hello World

状態: 計画。以下の検証は未実施。

## ユーザー体験

電源ON → ホームのApps / Hello World → Enter → JSがHello, Cardputer!を表示 → 決定キーでカウンター更新 → 戻るで同じホーム位置へ。

## 実装順序

1. IDF・依存バージョンを固定し、ADV用の最小ビルドを成立させる。
2. LCDとキーボード、単調時刻、USBログを確認する。Wi-Fi/BLEはまだ起動しない。
3. QuickJSのみを起動し、評価・中断・破棄とメモリ回収を確認する。
4. PocketJSの最小UIと英数フォントを追加し、strip描画で液晶へ送る。
5. AppManagerと静止ホームを実装し、Hello Worldの起動・終了を接続する。
6. 初期化失敗、無限ループ、ログ過多への対処を確認する。
7. 波背景とメニューの補間を追加し、応答時間と転送負荷を再計測する。

M1ではSD、音声、IMU、エディタ、ネットワーク、アプリのインストールは実装範囲に含めない。
左右・上下の複数項目選択は、製品にダミーアプリを残さず、テスト用リストで検証する。

## 測定記録

起動直後、HAL初期化後、guest生成後、core/binding生成後、JS評価のピーク、最初の描画後、終了後で記録する。

- 内部RAMの空き量、最小空き量、最大連続空きブロック。
- QuickJSの使用量と設定上限。Rust/native側の確保量は別に観測する。
- 各タスクのスタック余裕。QuickJS stack limitと実タスク領域の整合。
- JSフレーム時間、描画時間、SPI転送時間、入力から画面更新までの時間。
- 終了理由、起動回数、破棄ログ数、watchdogの有無。

記録にはファームウェアcommit、IDFとPocketJSのバージョン、ビルド設定、対象機種を添える。
認証情報や個人データを含まない検証結果だけをリポジトリに保存する。

## 完了条件

| 検証 | 合格条件 |
| --- | --- |
| 通常操作 | Hello WorldがJSで描画され、決定キーの押下単位でカウンター更新 |
| 再起動 | アプリの終了・再起動でカウンターが初期化され、ホームの選択位置が復元 |
| 起動終了100回 | クラッシュなし。ウォームアップ後の空きRAMが減少し続けず、最大空きブロックも悪化し続けない |
| JS構文・実行エラー | ネイティブエラー画面へ戻り、次の起動が成功 |
| JS無限ループ | 起動評価中・フレーム中の両方で戻る要求により中断。目標1秒以内に復帰 |
| JS heap上限 | 制限を超えるスクリプトが通常のエラーとして終了し、再起動可能 |
| 部分初期化失敗 | 生成済み資源のみが解放され、二重解放や使用中の解放がない |
| 入力 | 長押し・連打で多重起動せず、アプリに渡したEnterがホームを再操作しない |
| 表示 | strip境界に欠けがなく、横長240×135で正しい向きと色。部分更新後も残像なし |
| 演出 | 入力から可視反応まで目標100ms以内。背景で入力処理が止まらない |

数値は受け入れ目標で、達成済みの性能ではない。測定後に必要なら理由を記して見直す。
RustのOOM復帰はM1で保証できない。固定アプリでも十分な余裕が確保できなければ、UIリソースや実装を縮小して再評価する。

## 次段階へ進む判断

M1合格後にEditor / Run / Console / Docsの切り替えを設計する。
RAM不足の場合は、まずフォント、UIノード、バンドル、バッファを削減する。
QuickJSを別エンジンに替えたり、実行をPCへ移したりする変更は、本体実行という目的に影響するため別の設計判断として扱う。
