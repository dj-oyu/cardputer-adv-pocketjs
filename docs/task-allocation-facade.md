# タスク割り当てファサード仕様

2026-09-09。FP・非FPのFreeRTOSタスクを、自己申告したCPU負荷とコア制約に従って配置する。
管理部を常駐タスクにせず、呼び出し時だけ固定長の構成情報を操作する。

## 実装範囲

配置・チケット管理は [standalone/fp_ticket](../standalone/fp_ticket/README.md) に実装済み。
名称は `fp_ticket` だが非FPタスクも対象とする。既存ファームとビルド設定には接続していない。
FreeRTOSのタスク作成・登録・終了をまとめる接続層は未実装で、本書のライフサイクル契約に従って追加する。
本書の「接続層が行う」は今後の実装要件を示す。

## 入力と配置規則

管理部は2コア・最大16予約。コアごとの `capacity_ppm` は0〜1,000,000で指定し、
1,000,000を1コアの100%とする。0は配置禁止、両コア0は初期化エラー。
未登録のシステムタスクや割り込みに必要な余裕を差し引いて設定する。

| 要求フィールド | 契約 |
| --- | --- |
| `runtime_us` | 1回の処理で使うCPU時間。変換・付随処理を含み、I/O待機時間を除く。1以上 |
| `period_us` | 処理周期。`runtime_us` 以上 |
| `allowed_cores` | Core 0は1、Core 1は2、どちらでもよければ3。0や未知ビットは禁止 |
| `flags` | 非FPは0、FPは `FP_TICKET_USES_FP`（bit 0）。未知ビットは禁止 |
| `priority` | 将来のタスク作成に渡す情報。配置順序・枠の横取りには使わない |

FPの申告はタスクから呼ぶライブラリも含めて行う。実行中に非FPからFPへ変更するAPIは設けない。
負荷は `ceil(runtime_us × 1,000,000 / period_us)` ppm。計算は整数で行い、微小な負荷も最低1ppmを予約する。

1. 許可コアからcapacityが0のコアを除く。
2. FP要求なら、既にFP予約があるコアを除く。**FPは各コア1タスクまで**。
3. 追加するとcapacityを超えるコアを除く。
4. 残りから、追加後の全予約負荷/capacityが最小のコアを選ぶ。
5. 同率の非FP要求は非FP予約数の少ないコアを選ぶ。それも同じならCore 0。FP要求の同率もCore 0。

非FPの「均等」は申告負荷を優先する意味であり、タスク数が常に同数になる意味ではない。
配置は登録時に決定して固定する。スリープやI/O待機でも予約は保持し、動的な移動・負荷更新・追い出しは行わない。
3個目のFPタスクはCPUに余裕があっても拒否する。この1個制限は配置方針であり、ハードウェア上の上限ではない。

例として、両コアのcapacityが100%、各要求が10%なら、FPを2個登録すると各コアに1個ずつ配置される。
続く非FPを2個登録すると各コアの合計は20%ずつとなる。ここでFPを追加しても枠不足で失敗する。
数値は配置規則の例であり、音楽再生やflowerの実測値ではない。

## ビットマスクと保存領域

各マスクのbit 0〜15は同じ予約スロットを指す。

| マスク | 1の意味 |
| --- | --- |
| `live_mask` | 登録中 |
| `core1_mask` | Core 1所属。登録中で0ならCore 0所属 |
| `fp_mask` | FP利用 |

常に `core1_mask` と `fp_mask` は `live_mask` の部分集合となる。
Core 0のFP枠使用は `live_mask & fp_mask & ~core1_mask`、Core 1は
`live_mask & fp_mask & core1_mask` が非0かで分かる。それぞれの立つビットは最大1個。
解放時は該当スロットの3ビットをすべて落とす。

マスクは合計6バイト。これは管理部全体のRAM量ではない。
別途capacity 2個、次の32ビットID、16枠分の定義ポインターと32ビットIDを保持する。
全体のサイズはポインター幅とアラインメントに依存する。タスクのスタック・TCB・接続層の同期情報も別枠となる。
負荷・予約数・コア別FP占有は最大16枠から呼び出し時に集計し、重複したカウンターを常駐させない。

要求定義はコピーせず参照する。**解放まで有効かつ変更禁止**で、`static const` によるFlash配置を想定する。
可変の予約状態はRAMに置く。予約・解放ごとのFlash書き込みや永続化は行わない。
管理部はヒープ確保・待ち行列・タイマー・管理用タスクを持たず、計算にもFPを使わない。

## チケットAPI（実装済み）

公開型とシグネチャは [fp_ticket.h](../standalone/fp_ticket/fp_ticket.h) を参照。

| API | 動作 |
| --- | --- |
| `fp_ticket_init` | capacityを検証して初期化。寿命の開始時に1回だけ呼ぶ |
| `fp_ticket_acquire` | 配置を決めて枠を予約し、所有管理部とIDからなるチケットを返す |
| `fp_ticket_get` | 有効なチケットから所属コア・負荷・要求のコピーを取得する |
| `fp_ticket_release` | 有効なチケットの予約を解放する |
| `fp_ticket_snapshot` | capacity・負荷・全予約数・非FP予約数・FP占有コアを取得する |

取得失敗では管理状態と出力チケットを変更しない。エラーは以下の通り。

| 結果 | 意味 |
| --- | --- |
| `FP_TICKET_INVALID` | 不正な引数・要求 |
| `FP_TICKET_ID_EXHAUSTED` | 32ビットの予約IDを使い切った |
| `FP_TICKET_NO_SLOT` | 16枠がすべて登録中 |
| `FP_TICKET_NO_CAPACITY` | 許可された有効コアがない、または空きCPU予算が不足 |
| `FP_TICKET_FP_BUSY` | 許可された有効コアのFP枠がすべて使用中 |
| `FP_TICKET_STALE` | 別管理部・解放済み・無効なIDのチケット |

取得は引数、ID枯渇、スロット不足、有効コア、FP枠、CPU予算の順に検査する。
複数の条件が成立した場合は最初のエラーを返す。IDは1から発行し、再利用しない。
最終IDの発行後は解放・照会を継続できるが、新規取得は拒否する。
二重解放や再利用されたスロットへの古いチケットを拒否するため、単なるスロット番号をチケットにしない。

## FreeRTOS接続層の契約（未実装）

ファサードは配置要求に加えて、タスク名・入口・引数・スタック設定・優先度を受け取り、
割り当てたコアに固定してタスクを作成する。具体的な公開関数名と型は接続層の実装時に定める。
配置要求とFreeRTOS固有の作成情報を分け、上記管理部のOS非依存を保つ。

作成順序は「予約取得 → 割当コア取得 → そのコアに固定してタスク作成 → ハンドルとチケットの対応確定」。
作成直後に別コアで実行が始まる場合を考慮し、所有情報が確定するまで利用者のタスク入口を走らせない。
作成に失敗した場合は予約を返却し、作成失敗を呼び出し元へ返す。
予約成功はタスク作成成功を意味しない。

終了時は接続層の所有者が実行終了を保証してから予約を解放する。
終了要求の送信や終了通知の受信だけで、まだ実行できるタスクのFP枠を解放してはならない。
自己終了・外部削除・作成直後の終了を含め、タスクが実行不能になったことと二重解放防止を
接続層で保証する。実装時には終了手順と同期方式を具体化し、競合を検証する。

既存タスクを登録する場合は実際の固定コアに一致する要求を使う。登録失敗を無視して管理済みとして扱わない。
既にFPを使うタスクをこの登録によって移動させることはしない。
チケットはタスク寿命に対する配置予約であり、FP演算ごとに取得・返却する実行許可ではない。

## 同期・寿命・検証

管理部自体はスレッドセーフではない。接続層は同じ管理部の全API呼び出しを、照会も含めてmutex等で直列化する。
複数マスクの更新を単独のビット演算で原子的に扱えるとは仮定しない。ISRからは呼ばない。
管理用mutexを保持したままタスク終了を待たず、終了側が同じmutexを必要とするデッドロックを避ける。
常駐管理タスクを置かず、呼び出し元のコンテキストで処理する。

管理部は全チケットより長く同じアドレスで生存する。コピー・移動、古いチケットが残る状態での再初期化は禁止。
登録情報の実行時間は自己申告なので、CPU時間の強制割当・締切保証・性能改善の保証にはならない。
未登録タスク、割り込み、SD待ち、メモリ競合は自動計測しない。

管理部のホストテストはFPと非FPの混在、FP枠不足、capacity不足、配置制約、枠再利用、
古いチケット、ID枯渇を検査する。実行手順はstandaloneのREADMEに記載する。
接続層を組み込む際は作成失敗時の巻き戻し、同時登録、作成直後の終了、終了と再予約の競合を追加検証する。
音楽とflower併用時の改善は、接続後にCPU実行時間と待ち時間を分けて実機測定する。
