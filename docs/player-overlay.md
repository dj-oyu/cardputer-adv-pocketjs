# ホーム画面のプレイヤー — 何ができて、何が残っているか

2026-09-09。`docs/common-api.md` 3.1 の改訂に合わせて `apps/player` を
**overlayアプリとして作り直した**。この文書は「移すために足りないもの」の一覧だったが、
5点のうち4点が実装されたので、いまは**残りの一覧**である。

## 済んだもの

| | 実装 |
| --- | --- |
| overlayセッションに `fs` / `av` が無い | `app_session.c` が両方をinstallする。無線・マイク・バスは依然として無い |
| ポンプが回っていない | `app_overlay_tick()` が `pocket_overlay_pump()` / `pocket_fs_pump()` / `pocket_av_pump()` を `app_tick()` と同じ順で回す |
| モーダルがホームループで配送されない | 3つのピッカーを `ui_task` が配送する。**モーダルがoverlayに勝つ**ための必要条件で、選択肢ではなくなった |
| overlayが1個固定、Settingsがトグル | `REGISTERED[]` は2行（DESK CLOCK / MUSIC）、Settingsは3択 |
| 描画順とXMBの終了 | `shell_draw()` はoverlayが立っているとき `menu_layout()` を呼ばず、ラベルも描かない |
| 予約キー | ESCがシェルのもの。**配送ループの先頭で `break` する**ので、ゲストへ渡す呼び出しに到達しない |

**予約キーは一度間違えた場所に置いた。** 最初はforce stop（Ctrl+Alt+Del）の分岐に
書いてしまい、通常のBackは配送経路をそのまま通っていた——**つまり実装したつもりの
不変条件が、1ビルドのあいだ成立していなかった**。動いて見えたのは、ESCが
`action_of()` で名前を持たず落ちていたからで、それは偶然である。

## 残っているもの

### 1. 合成が毎フレーム全部描き直している

`ovl=3.44ms/frame`（XMBは0.9ms）。帯の外の項目を飛ばして5.33→3.4msまで下げたが、
表示リスト自体に差分は無く、`pocket_overlay_paint()` は毎フレーム残りを全部塗る。

### 2. ホーム画面が再生中に26fpsへ落ちる

30 → 26。**overlayのせいではない**（`ovl` はむしろ下がった）。増えているのは
`send` 7.08→8.8ms と `prep` で、パネル転送とシーンが復号器・カード読み出しと
CPUを取り合っている。直すならDMAの非同期化か、復号タスクの優先度である。

### 3. ターンの計測が実時間である

`overlay_budget` もゲストの割り込み期限も実時間を測るので、uiタスクが
復号器（優先度6）・オーディオ（7）・カード読み出しに横取りされている時間が
ターンの費用として計上される。`worst=188607us` はそれで、
**ゲストが188ms動いたという意味ではない**。この文書は同じ数字を
「曲送りのopen」と書き、次に「フォントアトラス構築」と書いた——
どちらも当て推量で外している。中身は特定していない。

**この測り方は実害を出した。** FLOWER背景（`draw=71ms`、`kernel=53ms`）で
再生すると、文字を数えるだけの5行のループが `InternalError: interrupted` で
落ちた。50msの割り込み期限が混雑を測っていたためで、前景と同じ250msにした。
費用の制御は `budget_us` の連続超過という別機構が持っている。
**暴走検知と費用制御を1つの数で兼ねてはいけない。**

**そして予算の側も同じ理由で止めた。** 割り込み期限を直した次の走行は
`OVER BUDGET worst=187781us turns=101` で落ちた——前段落で「残る懸念」として
書いたそのものである。FLOWERは `draw=79ms` `kernel=60ms` で、overlay自身の合成は
そのうち3〜5msなのに、ターンは12msを60回連続で越えた。

**そして止めても直っていない**（停止後も14fps）。予算の目的は3.1の一文
「overlayがホーム画面を使えなくしてはならない、止める行がそこにあるから」で、
既に使えない機械でoverlayを止めることは目的を果たしていない。**規則が自分の
理由で発火したかどうかの試験は、止めて何が良くなったかである。**

だから課金は**割合**にした。ターンがフレームの4分の1を超えないなら、
そのフレームが遅かったのはoverlayのせいではない——連続カウントは加算せず
リセットする。60回の証拠はシーンについての証拠であってoverlayについてではない。
比率にしたのはシーンごとに数字を調整し直さないためである。

### 4. 測っていないもの

- **カードの読み出しの計時。** 25 MHzで足りてはいるが、余裕がどれだけあるかは不明。
  `sd_media.h` の `SD_MAX_OPEN_FILES` の判断も同じ測定待ち。
- **数十分の連続再生。** 2曲・数曲の走行では抜けた後の `free` が 273,068 と 273,892、
  `largest` はどちらも 102,400 で、**リークは見えない**。これは「短い走行で見えない」
  であって「無い」ではない。
- **偽UIに対する予約キーの発見可能性。** 3.1はESCを「人が知っている」ことを
  信頼の錨にしているが、いまそれを言っているのはこのアプリの画面の1行だけである。

## 済んだもの（続き）

**音量。** Settingsに VOLUME 行（QUIET / LOW / MID / HIGH / LOUD）と、
ホーム画面でどこでも効く `-` / `=` キー。キーは**シェルが取る**ので、
プレイヤーを見ながら押せるがプレイヤーは所有していない。変更は右上に1.5秒出て、
NVSへ保存される。予約キーはESCと合わせて3つになり、そのぶんoverlayへ渡る残余が減る
——3.1が言っている実際の代金である。
ES8311のレジスタ `0x32` を書く。**機器のプロパティであってアプリのものではない**ので
`pocket.audio` には出していない——自分で音量を上げられるアプリは、
誰も見ていないあいだに上げられるアプリである。5段が上寄りなのは、
0x60より下はこの基板のスピーカーでは部屋の雑音に埋もれるからで、
下に刻んでも「無音の別名」が増えるだけだった。0xbf が段の1つとして残っているのは、
これまでの音の測定が全部その値で行われているためである。

**曲の長さ。** Xing/Info/VBRIタグから総フレーム数を読む（`pocket_mp3_total_frames`）。
無ければ `durationMs` は null のままで、**推測しない**。アプリは長さが分かるときだけ
バーを描き、分からないときは位置を主張しない光の演出に切り替える。
実機のアルバムは20曲すべてタグ無しだったので、タグがある側は
`tools/test_mp3_duration.c` がホストで検査している。

## 変わっていない制約

**前景アプリでの再生は依然としてセッションと一緒に死ぬ。** JSセッションは同時に1つ、
供給はそのセッションのタスク、MP3は `seekable:false`。だからプレイヤーは
overlayに居る——移したのは好みではなく、他に置ける場所が無いからである。
