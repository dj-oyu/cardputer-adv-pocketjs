# ホーム画面で鳴らし続けるために足りないもの

2026-09-09。`apps/player` は前景アプリで、ESCで抜けると再生が止まる。
プレイヤーをoverlayセッション（`docs/common-api.md` 3.1）へ移すと止まらなくなるが、
そこに至るまでにネイティブ側で**5つ**足りない。この文書はその一覧で、
どれも「やれば動く」ではなく**未検証**であることを先に書いておく。

## なぜ前景アプリでは無理なのか（3つの独立した理由）

1. **JSセッションは同時に1つ。** 前景アプリが上がる前に `overlay_release()` が走り、
   ホームへ戻るときも前景セッションは破棄される。
2. **供給がセッションのタスクに載っている。** `pocket_av_pump()` → `pocket_fs` の
   読み出しはJS/uiタスクのもので、`pocket_av_reset()` がセッション終了でリングも
   デコーダーも落とす（`pocket_av.c:1611`）。
3. **MP3は位置を持って引き継げない。** `seekable:false` で `seek()` は
   `NOT_AVAILABLE`。仮に1と2を回避しても、セッションをまたぐ引き継ぎは
   **必ず頭からの鳴り直し**になる。

3つのうち1つでも残ると「抜けても鳴り続ける」は成立しない。だから移すなら
**再生が最初からoverlayセッションの中に居る**形しかない。

## 足りない5つ

### 1. overlayセッションに `av` と `fs` が入っていない

`app_session.c:281` は overlay に console / jsfont / pocket / storage / app / overlay
の6面しか入れない。これは3.1の「overlayの能力集合は狭い」という**意図的な**設計で、
広げるなら理由を3.1に書くこと。`pocket.audio.player` には `av` が、
カードを読むには `fs` が要る。

### 2. `app_overlay_tick()` がポンプを回していない

`app_session.c:408` は `pocket_app_pump()` と `pocket_api_pump()` だけ。
`pocket_fs_pump()` と `pocket_av_pump()` を足す必要がある。ホームフレームは30fpsなので
供給レートは前景と同じ（2,048Bを毎秒約23回）。**この順序は `app_tick()` の
コメントが理由込みで書いているので、そこから写すこと。**

### 3. 許可がセッション限りなので、overlayセッションにはカードの許可が無い

`sd:` の許可はセッションと一緒に死ぬ（`docs/filesystem-api.md` 2）。
overlayセッションは自前で `requestFolder` を通す必要があるが、そのモーダルを
**ホーム画面のループが誰も回していない**（`tick_run()` にしかディスパッチが無い）。
選択肢は2つで、どちらも決めていない:

- **(a) ホーム画面にもモーダルのディスパッチを足す。** 人がホームに居るのだから
  そこに画面が出るのは自然で、`overlay_tick()` の隣に3つのピッカーの
  `_modal()/_key()/_dirty()/_draw()` を並べる。overlayが自分でピッカーを開けるので、
  前景の選曲アプリは不要になる。
- **(b) 許可をセッションをまたいで残す。** これは認可の仕様変更で、
  `sd_path.h` が2つの不変条件で守っている領域に触る。**安易にやらないこと。**

(a) が筋に見えるが、**「overlayがユーザーの操作なしに全画面を取れてはいけない」**
という制約とどう両立させるかは決めていない（人がキーを押した結果なら良い、
という線引きになるはず）。

### 4. overlayは1つしか登録できず、Settings行はトグルである

`overlay.c:45` の `REGISTERED[]` は `_Static_assert` で1個に固定されていて、
Settings行は OFF/ON の2択（`overlay_toggle_names[2]`）。時計とプレイヤーを
選べるようにするなら、行は3択以上のリストになる。**`tools/test_settings.py` と
`tools/capture_home.py` は押下回数を数えるので、同じ変更の中で直すこと。**

### 5. メモリの余裕が測られていない

これが一番大きい。現在のoverlay起動条件は
`OVERLAY_EXPECTED_COST`（96KiB、**推定**）+ `OVERLAY_FREE_FLOOR`（56KiB、実測）で、
起動後に `overlay_room_left()` が実測で検証する。そこへMP3再生が
**約50KiBを追加で**要求する（`docs/mp3-implementation.md`。うちスタック24KiBは
連続領域が要る）。ホーム画面のシーンが描いている最中に、である。

**足りるかどうかは推定してはいけない。** このプロジェクトには推定1.2msが実測25.6msだった例があり、
`OVERLAY_EXPECTED_COST` 自身が「次に起動が成功したら実測で置き換えよ」と書かれた推定である。
順序としては、**先に `tools/memlog.py --port --check` でoverlay起動後の実測を取り、
そこから50KiBを引いて `OVERLAY_FREE_FLOOR` を割らないかを見る**。
割るなら `overlay_room_left()` が正しく降りるので機体は壊れないが、
「プレイヤーoverlayは起動できない」が答えになる。

## SDカードの供給（2026-09-09に解決済み）

**これは「先に測るべき」項目として書かれていたが、実機で答えが出た。**
400 kHzのままでは2,048バイトの補充1回が約41 msかかり、33 msのフレームに
収まらないので、SDからの再生はぶつ切りになった。

転送クロックは固定値をやめ、マウント時に探索するようにした（`sd_path.h` の梯子を
降り、Default Speed上限の25 MHzまで1段上げ直してセクタ読みで検証する）。
この機体のこのカードでは**25 MHz**に落ち着き、`faults=0` で再生できている。

したがって「カードが間に合わないからoverlay化しても無駄」という懸念は消えた。
ただし**カードの読み出しを計時したわけではない**ので、余裕がどれだけあるかは
まだ分からない。`SD_MAX_OPEN_FILES` の判断もその測定待ちのままである。
