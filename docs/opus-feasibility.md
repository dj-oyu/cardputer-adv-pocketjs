# Opus復号の実現性 — Cardputer ADV（ESP32-S3、PSRAMなし）

作成日: 2026-09-09。実装ではなく調査の記録である。ファームは一行も書いておらず、コンポーネントもvendorしていない。S3 PIEについての前提知識は [pie-simd.md](pie-simd.md) から借りている（特に §3.6〜3.8、§5）。Opusの採否そのものの議論の出発点は [common-api.md](common-api.md) §9.1。

数値には **実測 / 導出 / 仮定** のどれかを必ず付ける。この機体では、自信のある数字が別のものを測っていた例が繰り返し出ている（PIE索引ロードで3体が同じ誤り、推定1.2msが実測25.6ms、`--gc-sections` 済みモジュールのサイズ測定、未配線ピンのDCオフセットを8回掃引）。出所の言えない数字は載せない。

## 0. 結論

**成立する。ただし条件付きで、PIEはその条件に入らない。** 2026-09-07に測られた「20msフレームあたり3.2ms、realtimeの16%」（§2）は、この石の上でのスカラー固定小数点ビルドの実測であり、私はその計測ハーネスそのものをディスク上で確認した。したがってPIE化は前提条件ではなく最適化で、しかも期待できる利得は計測ノイズより小さい（§4）。

**採否を決めるのは速度ではなくメモリの形である。** 復号には10,420バイト以上のstack（実測、§2）が要り、既存の音声タスク `sfx` のstackは4,096バイト（`main/hal/sound.c:1042`）。載せるなら、(a) 再生中だけ生成する復号専用タスク（再生中のheap約36KiB＝復号状態18,436＋stack 16KiB、連続ブロック2本）か、(b) `ui` タスクの32KiB stackで復号し、33.3ms予算に対して39.9ms使っているレンダラーのフレームに約5.3msを上乗せするか、のどちらかを選ぶ。それと、ライセンスとvendoringの判断（§7）。決めるのはオーナーで、この文書は決めていない。

## 1. P4のコンポーネントについて、先にはっきり書く

オーナーは `C:\devs\m5stack\esp32p4-mqjs\components\opus_p4_kernels`（デコーダー本体は隣の `esp_opus_float`）にOpus加速コンポーネントを持っている。

**アセンブリは一切移らない。** `.S` は7本すべてRISC-Vで、`#if defined(__riscv) && CONFIG_IDF_TARGET_ESP32P4` で自分を囲っているので、S3では空にアセンブルされる。P4のPIEとS3のPIEは名前が同じだけで命令セットが違う。「RISC-V対Xtensa」は易しいほうの半分で、機械的な書き直しだと思われると困るので、命令レベルの違いを書く（TRMからの導出。実機では試していない）:

| P4カーネルが頼っているもの | S3 PIEにあるか |
| --- | --- |
| `vmul.s32.s16xs16`（16×32のレーン乗算） | **無い。** S3の乗算は8/16bitレーンのみで、積は40bitのQACCへ累積する。このプロジェクトがQACCから値を取り出すのに使ってきた唯一の命令 `EE.SRCMB.S16.QACC` は **16bitに縮める**（pie-simd.md §8） |
| int32の `celt_sig` を直接扱う（comb、denorm、bfly3の3本） | 上の理由で、hi/lo分割と32bit再構成が要る。S3にそれを1命令でやるものは無い |
| `src.q` による未整列ロード、未整列ならCへフォールバック | S3は **未整列128bitアクセスで例外を出さず、下位4bitを黙って0にする**（pie-simd.md §5）。だからS3版は整列ガードとCフォールバックを必ず持つ（P4版がその形をしているのは正しい） |

つまり **rewrite であって port ではない。**

**移るもの。** `include/opus_p4_kernels.h` の契約（6つの境界のうち、bit-exact必須＝normres、bfly3、anti-collapseのseed進行／`opus_compare` 許容内で緩めてよい＝comb、denorm、inner product）、各カーネルの `_c` 参照実装（中身はupstreamのループの切り出しで、価値は境界が切ってあること）、917行の `opus_p4_kernels.c` にあるdispatch・最初N回のC照合・不一致で恒久Cフォールバックに落とす足場。そしていちばん役に立つのが **P4側の実測結果**（§4）。

**適用範囲の確認。** P4のプロファイルはCELT経路のものである。S3の計測ベクタがSILKモードだったら、この地図は隣接しているだけで当てはまらない。§2のベクタのTOCバイトを復号して確認した: **50パケット全部がCELT・WB・20ms・mono**（実測）。だからP4のホットスポット地図はS3の負荷をそのまま記述している。

## 2. 「3.2ms」の出所

`docs/common-api.md` §9.1 の「実機実測（2026-09-08）」はセッション `845f52f4`（2026-09-07 23:30〜23:50Z）のもので、ハーネスはいまも `C:\devs\m5stack\ble-wt\` に残っている: `components/opus/CMakeLists.txt`、`main/opus_probe.c`、`main/opus_test_data.h`、`build_opus/cardputer_pocketjs.elf` と `.map`。ソースとELFから読めるもの（特記なければ実測）:

- **ライブラリ**: `.cache/codecs/opus`（gitignore下）のxiph/opus master `a6128f4`（1.5系の後。DREDのソースは在るがコンパイルされていない）。`-DFIXED_POINT -DVAR_ARRAYS=1`、**`-Os`**（イメージ中969 TUのうち960が-Os。プロジェクト既定 `CONFIG_COMPILER_OPTIMIZATION_SIZE=y`）。celt/silk/silk-fixedを全部globしてリンクし、`--gc-sections` でデコーダーだけが残った。`nm` で `opus_decode` / `celt_decode_with_ec` / `silk_Decode` とベクタがイメージに在ることは当時確認されている。
- **ベクタ**: 24kHz・mono・24kbps VBR・`OPUS_APPLICATION_AUDIO`、和音＋雑音＋包絡、50パケット＝3,050バイト（⇒3,050 B/s）、パケット長52〜91バイト。エンコーダーは50個全部にCELT WB 20msを選んだ（TOC復号、実測）。
- **プローブ**: 専用タスク、core 0固定、優先度7、stack 24,576バイト、`esp_timer` で `opus_decode()` だけを囲む、`OPUS_RESET_STATE` を挟んで20周×50＝1,000回復号。**他には何も動いていない**（レンダラーもJSゲストも無し）。
- **ボードのログ（原文）**: `get_size=18340 heap_used=18436` / `frames=1000 bad=0 mean_us=3208 worst_us=3713 stack_used=10420 of 24576` / `realtime_pct=16`。
- **Flash**: 当時のイメージ差分で+80,376。私がmapの生き残った入力セクションを数え直すと79,576（text 54,827＋literal 824＋rodata 23,925）で整合する。`.bss` の960はプローブ自身のPCMバッファで、libopus自体の静的DIRAMは **0**。

240MHzで3,208µs＝約770kサイクル／480サンプル＝**約1,600サイクル/サンプル、realtimeの6.2倍速**（導出）。

**この数字が覆っていないもの**（それぞれ§6の走行に対応する）:

- `-O2`。ハーネスは-Osである。
- **生きているレンダラーとの命令キャッシュの取り合い。** CLAUDE.mdの±15%はビルド間の値で、40ms/フレームのレンダラーの横で走ればもっと悪くなる。未計測。
- 他のビットレート。CELTのコストはパルス数で弱く増える（仮定）。
- SILK／hybrid／PLC（NULLパケット）。別のコードが走り、stackの最高水位も別。
- **`stack_used=10420` はこのCELT一経路の値で、デコーダー全体の上限ではなく下限である。**

規模感のためだけに（比較にはならない: 内容・48kHzステレオ・360MHz・-O2が全部違う）: P4の固定小数点Cは729.9サイクル/ステレオサンプルフレーム（P4側の実測）。S3の約1,600/monoサンプルはサンプルあたり2〜4倍のサイクルで、その差の一部は-Osと、半分の長さのフレームで償却が効かないぶん（導出）。

## 4. CPUと、PIEを書かないという勧め

**置き場所。** この石は2コアで（`CONFIG_FREERTOS_UNICORE` 未設定）、タスクは固定なしで作られている。16%がどこに落ちるかは設計の選択である: `ui` と別のコアに固定すればレンダラーは無傷、固定なしで優先度7ならレンダラーを1ビデオフレームあたり約5.3ms止め、`ui` のpumpで復号すれば既に予算超過のフレームに5.3msが乗る（導出）。「1コアの16%」がレンダラーに何か払わせるかはR5（§6）で、誰も測っていない。

**PIEは勧めない。** 根拠は3つ。

1. **P4側の実測結果**（`esp32p4-mqjs/docs/history/opus-decoder-plan.md`、COM8、5周、同一fixture）: float→固定小数点で−13.5%。その後PIE comb −3.85%、PIE denorm 増分−0.73%、PIE normres ≈0（不採用）。**完成したPIEカーネル3本でend-to-end −4.95%。** 唯一2桁の見積もり（約18%）だったFFTバタフライは「最難」として着手されず、landしていない。S3で同じ相対利得が出ても3.2msの5%＝**約0.16ms/フレーム**で、ビルド間±15%の命令キャッシュ変動の中に沈む。同一バイナリ・スイッチ1個の規律（pie-simd.md §3.8）なしには効果の証明すらできない。
2. **`tools/pie/piesim.py` はこれらのカーネルを検査できない。** 16bitを超える符号付きQACC取り出し、`EE.CMUL.S16`、`EE.FFT.*`、32bitレーン加算のどれも模擬していない。S3のPIEカーネルは焼く前に `stalls.py` / `test_kernels.py` / `run_models.py` の3層を通す決まりなので、**最初の1本のコストにシミュレータの拡張が含まれる。** 再訪する人はこれを始める前に済ませること。
3. 速度が要るなら先にスカラーの梃子がある: R1の `-O2`（define 1個）、次にCELTデコーダーのテキストに183本ある整数除算（`quos`/`rem`。ハードウェア除算器で1本16〜18サイクル、pie-simd.md §3.7の逆算値）。ベクタ化の話ではない。

## 5. 帯域 — 算術であって計測ではない（カードの読みは誰も測っていない）

SDのSPIクロック400kHz、理想400kbit/s に対して: PCM16 384kbit/s（96%、維持できない）、ADPCM 96kbit/s（24%）、**Opus 24.4kbit/s（6%）**。Opusは `pocket_av.c` が書いている `sd:` ストリーミングの問題を解かない——2,048バイトのスロット1本は依然として、それを要求したフレームの中の約41msのバス時間である。変わるのは頻度で、PCM16の16分の1、ADPCMの4分の1（スロット1本≈Opus 0.67秒、PCM16 43ms）。出口は変わらず供給タスクかクロックで、変わらず「まずカードの読みを測る」。

Opusが席を得るのは置き場のほうである: `app:/` の24,576バイトで8.06秒（符号化して計数、実測）対ADPCM 2.05秒。供給がタスクに移れば、バスの6%占有はEXT SPIをほぼ空けたままにする。

## 7. ライセンス — オーナーがまだ決めていない判断として

libopusはBSD-3-Clause（`COPYING`）で、Xiph・Microsoft・Skype・BroadcomからIETF IPR声明経由の royalty-free 特許許諾が付く（defensive termination条項あり）。この木に入れるとは: 約100本のCファイルを `components/` にvendorする（またはレジストリの `78/esp-opus` 1.0.5——固定小数点を強制するが、ここではそれが望みの形——をPocketJSと同様に固定revisionで）、BSDの表示を `licenses/` と第三者通知に足す、エンコーダーを持ち込まないデコーダー限定のソースリストを持つ。`.cache/codecs/opus` にあるcloneはリリースタグでなくmasterなので、実装するならリリース（1.5.2以降）にpinする。私は何もvendorしていない。

## 8. 一行で

成立する。スカラー固定小数点のlibopusがこの石の上で6倍速のrealtimeで走ることは、いまも残っているハーネスで実機計測されている。決めるべきは (a) 再生中約36KiBの復号専用タスクか `ui` タスク上の復号か、(b) 1コアの16%をレンダラーから固定で遠ざけるか（R5）、(c) BSD-3のvendoring。R1を最初に走らせ、統合の寸法を切る前にR2/R3を走らせること。

### 9.1 R1が実際に返したもの（2026-09-09、実測）

同一ツリー・2つのビルドディレクトリ・変数1個（`ble-wt` の `build_opus_os` / `build_opus_o2`）。

```
-Os   mean 3,208 us   worst 3,670   stack 10,420
-O2   mean 3,089 us   worst 3,491   stack 10,484
```

**−3.7%。** §6は10〜30%を仮定し、実装側は走行前に「−10〜−25%、5%未満なら棄却」と書いた。
**両方外れた。** 棄却条件のほうは事前に書いてあったので、そのまま適用して
`components/opus/CMakeLists.txt` は `-Os` のまま、Flashの11,920バイトは払わない。

この走行が、フラグの選択以外に確定させたことが2つある。

- **`-Os` 側が2026-09-07の3,208µsを1桁も違わずに再現した。** 木はその後動いているのに再現した
  ということは、§2のハーネスとあの数字が健全だということで、**この設計の寸法は全部そこから
  出ている**。数字が別のものを測っていた例がこのプロジェクトには何度もあるので、
  再現したことのほうを記録しておく価値がある。
- **2.5msには届かなかったので、§6が言っていた「PIEの問いが恒久的に閉じる」は起きていない。**
  問いは**開いたまま、かつ不利**である。閉じたのとは違う状態で、丸めないこと。
  §4の「書くな」は依然としてP4の実測（3本でend-to-end −4.95%）と
  `piesim.py` が検査できないことに乗っていて、R1に乗ってはいない。
