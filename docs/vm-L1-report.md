# VM L1 報告: ジョブ境界の実行制御と起床（`vm/l1-host-sched`）

対象: [quickjs-freertos-vm-spec.md](quickjs-freertos-vm-spec.md) §6。設計は [vm-L1-design.md](vm-L1-design.md)、基準値は [vm-L0-report.md](vm-L0-report.md) §2.1/§2.2、1 ティックの実際の順序は [vm-ledger/03-jobs-interrupts.md](vm-ledger/03-jobs-interrupts.md)。2026-09-12 時点。

本書は**ユーザーが「L1 を完了と認めるか」「`vm/main` へマージするか」「L2 に進むか」を判断するための報告**で、設計判断の理由は設計書側にある。数値は **実測(device) / 実測(build) / 実測(host) / 推定** を毎回書く。実機の数値は 2026-09-12 に揃った（§2）。

**先に結論を。**

1. **仕様 §6 の完了条件 4 つは、これで全部満たした。** 残っていた条件 4（RAM 増分と応答遅延の実測）は
   2026-09-12 に実機で埋まった（§2）。ホスト側の 3 条件は以前から満たしている。
2. **ただし、その実測が 1 件の回帰を出した — 同じ日に直し、実機で確かめた（§2.8）。** F 型（`async_generator`）で **ゲストの `frame()` が
   28.20 → 7.72 fps に落ちる**（実測(device)、base。audio 26.74 → 7.57、wifi 26.85 → 7.65）。
   完了遅延も同じ理由で 3〜8 倍に伸びる（audio 中央値 9.22 → 69.13 ms）。
   原因は §2.4 に特定してある — **継続ターンが 33 ms の表示フレーム周期で律速されている**（`main.c` の
   `cap = running ? 33 : …` が継続ターンにもかかる）。スケジューラの論理ではなく、待ち方の問題。
3. **回帰は直った（§2.8）。** 継続ターンには表示周期を課金せず、周期は `frame()` 1 回につき
   1 回だけその周期の開始時刻から課金する、という規則にした。**F の `frame()` は
   7.49 → 22.80 fps（legacy 28.20 の 81%）**、完了遅延は wifi / all で legacy と同じところまで戻る。
   D と他の 5 型は動いていない。**したがって §6-1 の (a) は実施済みで、マージを妨げるものは
   もう無い**（§6-11 も決着済み）。
4. 他の 5 ワークロード（A/B/C/D/E）は `frame()` 到達率・turn・メモリのいずれも legacy と区別できない。
   L1 は**壊していない**。壊れているのは、L1 が助けるために作られた唯一の型である。

## 1. L1 で何が変わったか

### 1.1 利用者（JS アプリ）から見た挙動

| 変わるもの | 変わる内容 | どのアプリで見えるか |
| --- | --- | --- |
| 1 ターンの長さ | Promise ジョブの drain が **8 ms（`VM_TURN_BUDGET_US`）でジョブとジョブの間で中断**し、残りは次ターンの冒頭で続く。ターンが長いアプリほど画面・音・OS の応答が戻る | drain が長いアプリ（L0 のワークロード F: drain 30.27 ms、実測(device)）。drain が 0.01 ms のアプリ（A/B/C）は**何も変わらない** |
| `frame()` の呼ばれ方 | ジョブが残っているターンでは `frame()` を**呼ばない**。キューが空になったターンだけが pump → `frame()` → drain の通常経路に進む | F 型のアプリは `frame()` が約 4 ターンに 1 回になる（**実測(device) で 4.0 ターン**。継続ターンが 33 ms ずつ待っていた頃は `frame()` の到達率が 28.20 → 7.72 fps まで落ちた — §2.4。**§2.8 で直り、22.80 fps = legacy の 81%**） |
| 完了（`await` の解決）の届き方 | resolve / reject の配送も継続ターン中は**保留**される（§6 が求める互換モード）。したがって **F 型アプリの JS 完了遅延は縮まない。むしろ `frame()` と同じく約 4 ターンに 1 回にまとまる**（実測(device): F の完了遅延中央値は audio で 9.22 → 69.13 ms、§2.4） | 設計 §1.2 が明記している L1 の限界。縮むのは「ターン長」であって「JS ハンドラ到達時刻」ではない |
| フレーム周期 | 他タスク・ISR からの完了で `vTaskDelay` を早く抜ける（`vm_wake_*`、FreeRTOS 直接タスク通知）。ただし下限 `VM_MIN_PERIOD_MS=8` ms | UART / ネット / 音声の完了を待つアプリ。`frame()` の回数を時計代わりにするアプリは速くなりうる |
| キー入力 | 継続ターン中の押下は落とさず `deferred_buttons` に保持し、最初の通常ターンで配る。**ただし 2 つの打鍵が 1 マスクに融合しうる**（§5 の残存危険 2） | 継続ターンが続く忙しいアプリのみ |
| `pocket.input.text` の打鍵 | ホスト側（IME・バッファ・キャレット・再描画）は従来どおり即座。**ゲストの onEdit/onSubmit/onCancel は `app_tick()` の pump 段に遅延**（同じフレーム内） | 観測差は通常無し。1 本の論理 drain の途中に JS が割り込まなくなる |
| 暴走 | 「1 本の論理 drain が `vm_sched_drain` の中で使った時間」が 250 ms（`VM_RUNAWAY_US`）を超えるとセッション終了。例外は投げない（`finally` を飛ばさない、`await` を永久 pending にしない）。時計が死んだときの受け皿が 10 万件（`VM_RUNAWAY_JOBS`） | `function f(){Promise.resolve().then(f)} f()` のような「空にならないキュー」。**旧 250 ms 壁時計ガードより必ず緩い**（`frame()`・pump・描画・転送を数えないため） |
| 離脱（Back） | 離脱ターンは広い予算（`VM_LEAVE_BUDGET_US=50000` / backstop 256）で継続を走らせ、**空にならなくても** `frame(0x2000)` へ抜ける。ゲストの最後の保存機会を保つ | 忙しいアプリ（= 保存が最も要る側） |

**変えていないもの**: ログ標識（`PERF` / `PAINT` / `MEM` / `HOME_READY` / `APP %u` …）の書式は 1 バイトも変えていない。`MEM` は `tools/memlog.py` が `js=` を正規表現で拾うので特に触っていない。追加した行は 2 本だけ — `W app: jobs dropped at stop: queue was not empty (yields=%u continuations=%u)` と `E app: RUNAWAY one drain spent %lld us over %llu jobs in %u turns`（後者は `jsconsole` に `JOB QUEUE RUNAWAY`）。

## 2. 実機の結果（2026-09-12、すべて実測(device)）

### 2.1 何をどう測ったか

Cardputer ADV / COM3、ブランチ `vm/l1-host-sched`、ワークツリー `…-vm`。**L1-new と L1-legacy は
同じツリー・同じコンパイラ・同じ日のセッションで作り直した 2 本**で、違いは `CONFIG_POCKET_VM_SCHED`
の y/n だけ（`build_l1_dev_probe_on` / `build_l1_dev_probe_legacy`、どちらも §8 の決定どおり
core 1 pin・`VM_JOB_STRIDE=1`・esp_timer）。6 ワークロード × base/all × 3 反復、加えて
ジョブの重い D/F × ui/audio/wifi × 3 反復。生データは `.cache/vm/l1-new.jsonl` /
`.cache/vm/l1-legacy.jsonl`（git 管理外）。

**L0（[vm-L0-report.md](vm-L0-report.md) §2.1）は取り込み前のバイナリ**なので、§2.3 の比較は
L1-legacy との対で読む。L0 の列は桁の確認にしか使わない（CLAUDE.md: 命令キャッシュの
アラインメントで同じカーネルがビルド間で 15% 動く。実際 `closures` は L0 50.11 → legacy 41.94 ms と
8 ms 違い、これは L1 の効果ではない）。

`all` 条件では 3 反復すべてで `VMCOND wifi connected 192.168.1.42` が出て実際にリンクし HTTP まで
通っている（L0 採取時にあった「資格情報が無い」制約は解消済み）。

### 2.2 `turn` と `drain` の列が何を指しているか（**先に読むこと**）

`vmprobe_frame_sample()` は**通常ターンの末尾でしか呼ばれない** — 継続ターンはその手前の
`return present_frame(&cont)` で抜ける（`main/app_session.c:710` と `:770`）。したがって
**L1-new の `turn` / `drain` / `heap_free_min` / `js_used_max` の列には、継続ターンが 1 標本も
入っていない。** `drain` は論理 drain の**最初の一切れ**であって全体ではない。

窓ヘッダの `frames` と `ms` だけが継続ターンの影響を受ける — これが**ゲストの `frame()` が
実際に何回呼ばれたか**であり、L1 の費用はここにしか現れない。以下の表で `frame()/s` を
turn/drain と並べているのはそのためで、**この 3 列を別々に読むと必ず誤読する。**

この読み違いには実害があった: 「同じ 62 ジョブの drain が 31.29 ms から 4.08 ms になった」は
**JS が 7 倍速くなったのではない。** 62 ジョブのうち通常ターンで走るのが約 12 件に減り、
残りが標本に入らない継続ターンへ移っただけである（`vm_sched_drain()` は両ビルドで
同一コードで、legacy は `limit_ticks=0` で判定を飛ばすだけ。`vm_sched.c:62`）。

### 2.4 なぜ F だけ `frame()` が 1/4 になるのか（原因は特定済み、コード上の 1 箇所）

D と F は「1 ターンのジョブ数が予算で切られる」点では同じなのに、D は 29.9 fps のまま、
F だけ 7.7 fps に落ちる。差は**論理 drain が継続ターンを何回必要とするか**で決まる。

`app_tick()` は継続の**後ろに落ちてこられる**: 継続 drain でキューが空になれば、同じターンの
うちに pump → `frame()` → 次の drain まで進む（`app_session.c:702` の
`if(!leaving && …jobs_pending)` が偽になる経路）。空にならなかったときだけ
`present_frame(&cont)` で早期に返り、**そのターンに `frame()` は無い**。

- **D (`promise_chain`)**: `frame()` が 8.63 ms で 8 ms 予算を先に使い切るため、通常ターンの
  drain は floor の 8 件（0.73 ms）で止まる。残り 33 件は**次のターンの継続 drain 1 回で
  片付き**（0.073 ms/件 × 33 ≒ 2.4 ms、8 ms 予算の内側）、そのまま同じターンの `frame()` へ
  落ちてくる。**早期に返る継続ターンは 0 回。`frame()` は毎ターン走る → 29.9 fps を維持。**
- **F (`async_generator`)**: 1 件 0.49 ms × 62 件 ≒ 30 ms。1 ターンの予算 8 ms では
  12〜16 件しか進まないので、**早期に返る継続ターンが 3〜4 回必要**になる。その各回が
  `present_frame()` で返り、`main.c` のフレーム律速に入る。

律速はここ（`main/main.c`、`ui_task` の末尾）:

```c
unsigned cap = running ? 33 : SCREENS[screen].frame_ms;
unsigned rest = (unsigned)held<cap?cap-held:1;
… if(rest) vm_wake_wait(pdMS_TO_TICKS(rest));
```

**`cap` は継続ターンにも 33 ms でかかる。** 継続ターンは「まだ仕事が残っている」ターンなので
待つ理由が無いのに、表示のフレーム周期ぶん待つ。`vm_wake_wait` は完了通知で早く抜けられるが、
継続ターンに未処理の完了は無い（ジョブは既にゲストのキューの中にある）ので、**丸ごと待ち切る**。

算数が実測と合う: F は継続 3 回 + 通常 1 回 = 4 ターン × 33 ms ≒ **132 ms/`frame()`**。
実測は **129.56 ms**（base）/ 133.20 ms（all）。legacy は 35.47 ms。**JS の仕事量は変わって
いない**（62 ジョブ × 0.49 ms ≒ 30 ms のまま）。伸びたのは**待ち時間だけ**である。

完了遅延の悪化も同じ 1 個の原因から出る。F の audio 条件で 9.22 → 69.13 ms なのは、
完了が `pocket_api_pump()` に届くのが「キューが空になったターン」＝ 133 ms に 1 回だから。
§5.1 が「互換モードなので F 型の遅延は縮まない」と予告していたのは**方向としては当たったが、
量の原因は互換モードではなく待ち方**である。

**直し方は実装して実測した — §2.8。** 上の見立て（`jobs_pending` のターンで `cap` を下げる）は
方向として正しかったが、**それだけでは足りない**。継続ターンの待ちを消しても、その継続に使った時間が
次の通常ターンの表示周期に二重計上されるので、F は 17 fps 止まりになる（実測(device)）。
採った規則と実測は §2.8。

### 2.5 四つの問いへの答え

1. **最悪のターンは短くなったか — なった。** F の turn は all 条件で p95 45.77 → 14.37 ms、
   最大 78.72 → 38.46 ms。D は p95 17.54 → 15.34、最大 33.39 → 31.87 ms。drain がほぼ 0 の
   A/B/C/E は動かない（設計どおり）。**L1 の唯一の目的は達成されている。**
2. **完了遅延は改善したか — 型で割れる。** D は改善（audio 22.91 → 3.52 ms、wifi 19.45 → 5.38 ms、
   いずれも中央値）。**F は 3〜8 倍の悪化**（audio 9.22 → 69.13、wifi 32.83 → 106.16、
   all 30.41 → 74.77 ms）。原因は §2.4 の待ち方であり、互換モードそのものではない。
3. **スループットの代償は何か — F の `frame()` 到達率が 28.20 → 7.72 fps（base、−73%）。**
   ジョブ/ターンは両ビルドとも 41（D）/ 62（F）で変わらず、JS が処理したジョブの総量は
   `frame()` 到達率と同じ比で落ちる（F: 約 1,750 → 478 jobs/s、実測値からの計算）。
   他の 5 ワークロードは 2% 以内（= 反復間ばらつきの内側）。**「L1 が JS を速くした」とは
   言えない**（§2.2）し、「遅くした」とも言えない — **待たせた**のである。
4. **メモリはどうか — 静的は問題なし、実行中は今の器械では比較できない。**
   静的 DIRAM は L1 前 115,372 → L1 後 115,468 B（**+96 B**、上限 +8 KiB の 1.2%）で、
   §8 の pin/stride を足しても **+0 B**。`stack_hw` は全ワークロードで legacy と一致
   （追加タスクを作っていないので当然）。
   **実行中の空きヒープは比較にならない。** D の base で legacy 106,544 → new 83,760 B、
   `js_used_max` が 86,320 → 103,032 B（3 反復 42 窓すべてで完全に平坦、ばらつき 0）。
   これは漏れではなく**測る場所が動いた**結果である: heap / `js_used` の標本は
   `vmprobe_frame_sample()` の中でしか採られない（`main/pocket/vmprobe.c:181`）ので、
   legacy では「41 段の連鎖を drain し終えた後」、new では「8 件だけ流して 33 段が生きて
   いる最中」を見ている。差の 16,712 B は**生きている連鎖そのもの**で、legacy でも同じものが
   同じ瞬間に存在していた — 標本がその瞬間を一度も踏まなかっただけである（42 窓すべてが
   同一値という平坦さが、偶然踏んだ窓が 1 つも無いことの証拠）。
   **つまり L0 §2.2 が RAM 上限の根拠にした「実行中の空きヒープ最小 14,768 B」自体が、
   drain 中の山を外して測った値である。**

### 2.8 §2.4 の回帰を直した（2026-09-12、実測(device)）

#### 診断の実機確認

直す前に、§2.4 の診断（「待ち方の問題であって JS の問題ではない」）を実機で確かめた。
`ui_task` の待ちの直前と直後に時刻を取り、継続ターンと通常ターンに分けて 120 ターンごとに
平均を出す一時プローブ（`VMWAIT`、コミットしていない）を入れ、F/base を走らせた:

```
I (5542) app: VMWAIT cont n=89 held=8 cap=33 wait=23 | norm n=31 held=15 cap=33 wait=19
I (9572) app: VMWAIT cont n=90 held=8 cap=33 wait=23 | norm n=30 held=12 cap=33 wait=19
I (13578) app: VMWAIT cont n=90 held=8 cap=33 wait=23 | norm n=30 held=13 cap=33 wait=19
```

**診断は正しい。** 120 ターンのうち 90 が継続ターン（= 論理 drain あたり継続 3 回、§2.4 の
「3〜4 回」と一致）。継続ターンは仕事を 8 ms しかしていないのに **23 ms 待っている** —
`vm_wake_wait` は未処理の完了が無いので短縮されない。1 枚の `frame()` に
3×(8+23) + (13+19) = **125 ms** かかっており、実測の 129.56 ms と桁も内訳も合う。
待ちの合計 69 ms が、そのまま失われた fps である。

#### 採った規則

> **表示周期は「絵」を律速するためにある。したがって 1 回の `frame()` につき 1 回だけ、
> その `frame()` の周期の開始時刻から課金する。ターンごとには課金しない。**
> 継続ターンは誰も待っていない絵を描かないので、表示周期ではなく**ジョブ予算の下限
> （`VM_MIN_PERIOD_MS`、ただし 0 にはしない）**だけ待ち、そこで使った時間は
> 向かっている先の `frame()` の周期の一部として数える。

実装は 3 箇所（`main/app_session.h` の `VM_DISPLAY_PERIOD_MS` と `app_turn_continued()`、
`main/app_session.c` の `turn_continued` と提示の間引き、`main/main.c` の `period_began`）。
静的 DIRAM は **115,468 → 115,484 B（+16 B）**、実測(build)。

**退けた案と、その理由**:

| 案 | 退けた理由 |
| --- | --- |
| (a) 継続ターンにも表示周期をかける（現状維持） | 上の実測の回帰そのもの |
| (b) 継続ターンは一切待たない | `ui` タスクは優先度 5 で、長い drain の間じゅうコアを握る。優先度がこれ未満のものが飢える。暴走ガードも助けにならない — あのガードが数えるのは drain 時間で、ここではそれは正直な仕事である。**だから下限は決して 0 にしない** |
| (c) 表示周期をやめ `frame()` を 8 ms 下限で回す | 1 周期に 4 回転送することになる（1 転送 7.7 ms、実測(device)）。加えて `frame()` の回数を時計にしているアプリの速度が変わる（§5.2-6） |
| (d) 周期を**このターンの開始**から課金する（一行で済む素直な案） | その周期の中で既に使われた継続ターンが二重に課金される。**実測で 17 fps**（採用案は 23 fps） |

**提示（LCD 転送）は表示周期で間引いたまま**にした。継続ターンは約 9 ms ごとに来るように
なったので、毎回提示すればバスが持たない。飛ばしても描画は失われない — damage plan は
最後に **commit した** target との差分なので、継続ターンが描いたものは次の提示に全部入る
（フレームを落とすのであって、画素を落とすのではない）。長い drain の間も絵が動くという
「継続ターンが提示する」本来の目的は、周期ごとに 1 回残ることで保たれる。

### 5.2 設計として残した危険（修正していない）

1. **`deferred_buttons` は 2 つの打鍵を 1 フレームに融合する。** `main.c` は `app_tick(buttons)` の直後に `app_tick(0)` を呼び「連続した打鍵が別物として届く」ことを離鍵フレームで保証しているが、継続ターンが続く間に別々のキーが届くと `deferred_buttons |= buttons` が 1 マスク（例: UP|RIGHT）にまとめる。**予算導入前には起こり得ない入力**。設計 §2.2 が `|=` を指定しているので設計側の判断として残してある。キューにするなら離鍵フレームの対も作り直しが要る。

2. **予算は壁時計なので、プリエンプトされた時間も drain に課金される。** 暴走ガードの許容量を旧ガードと同じ桁（250 ms）に置き、かつ合算対象を drain の中だけに絞ることで「旧ファームが完走させた drain をこれが殺すことはない」を構造的に保証した。しかし**混んだ機械では 8 ms 予算が他タスクの時間で尽きる**ので、1 ターンあたりのジョブ数は負荷に依存する。ホスト側の機構でこの時間を JS 時間と区別する手段は無い（`esp_timer` も CCOUNT もタスクの実行時間ではない）。

3. **【解決済み・2026-09-12】継続ターンが表示のフレーム周期（33 ms）で律速される。** 実測で
   見つかった、この節で唯一の「設計判断ではなく穴」だったもの。**§2.8 で直した** —
   継続ターンは表示周期ではなくジョブ予算の下限だけ待ち、周期は `frame()` 1 回につき
   1 回だけ課金する。F の `frame()` は 7.49 → 22.80 fps（legacy の 81%）、実測(device)。
   残る 19% は待ちではなく、1 論理 drain が 4 ターンに割れること自体の費用である。

4. **互換モード（継続 drain より前に resolve を配らない）は F 型アプリの完了遅延を縮めない。**
   §6 が既定に求めたものなので L1 の欠陥ではない。**ただし実測が出た今、F 型の遅延悪化の
   主因は互換モードではなく上の 3 である** — 互換モードが効くのは「継続が 1 回で済む」
   D 型で、その D 型では遅延はむしろ改善している（22.91 → 3.52 ms）。互換モードの代償は
   予想より小さく、待ち方の代償が予想より大きかった。公平モード（§6-6）の必要性は
   §2.4 を直した後に測り直して判断すること。

5. **`frame()` は分割できない。** A（117.56 ms）・C（49.75 ms）の `frame()` はそのまま（いずれも実測(device) base 中央値）。これらのアプリでは 8 ms 予算は守れず、drain が floor（8 件）まで縮むだけ。**L1 の限界であって欠陥ではない**が、「応答性が改善する」とユーザーに説明するときこの 2 型は例外である。

6. **`VM_MIN_PERIOD_MS=8` により `frame()` が 30 fps より速く呼ばれうる。** `onFrame` の `dt` は実測時刻から計算されるので正しいが、**`frame()` の回数を時計代わりにするアプリは速くなる**。

### 5.3 clockbench の結論（解決済み）

CCOUNT は不採用。いずれも実測(device)。`vm/l1-clockbench` が「pin ビルドの実行時コストが
未測定」として残していた穴も §8.1 で埋まっている。この節はもう危険ではない。

core 1 pin）が載ってホーム画面（背景モード 3）で待っている。

### 5.5 測定器そのものの限界（新規、実測で判明）

1. **`vmprobe_frame_sample()` は通常ターンでしか呼ばれない。** `turn` / `drain` / `heap_free_min` /

## 6. L2 に進む前に決めること

（形式は [vm-L0-report.md](vm-L0-report.md) §6 に合わせた。番号ごとに「決めること」と
「決めないとどうなるか」を書く。**1 と 11 が今回の実測で新しく決定事項になったもの**、
4 と 6 は「実測後に改めて問う」と約束していた 2 つの設計上の危険である。）

1. **L1 の完了と、マージするかどうか。** §3 のとおり **§6 の完了条件は 4 つとも満たした**ので、
   「完了と認めるか」は形式上は済んでいる。決めるのは**マージの形**:
   - (a) **§2.4 を直してから `vm/main` へ**（勧める案。**2026-09-12 に実施済み — §2.8**）。継続ターンの待ち方 1 箇所 +
     F/D の再測定で済む見込み（推定）。直したうえで `frame()` 到達率が legacy 並みに戻れば、
     L1 は「ターンを短くし、何も遅くしない」と言い切れる。
   - (b) **今マージし、既定を `CONFIG_POCKET_VM_SCHED=n` にする。** 仕様 §12（既定挙動を
     変えない）には従うが、L1 は誰も使わない状態で `main` に入る。
   - (c) **今マージし、既定 `y` のまま。** F 型アプリの `frame()` が 1/4 になる状態が
     既定になる。今日そういうアプリはプローブしか無いが、`await` の多いアプリを書けば
     誰でも踏む。**これは勧めない。**
   決めないと L2 の着手時期が決まらない。

2. **出荷時定数の承認。** `VM_TURN_BUDGET_US=8000` / **`VM_JOB_STRIDE=1`**（§8.3 で 4 から変更）/
   `VM_JOB_FLOOR=8` / `VM_JOB_BACKSTOP=64` / `VM_LEAVE_BUDGET_US=50000` / `VM_LEAVE_BACKSTOP=256` /
   `VM_RUNAWAY_US=250000` / `VM_RUNAWAY_JOBS=100000` / `VM_MIN_PERIOD_MS=8`。
   L0 §2.2 が提案した遅延上限（p95 8 ms / 最大 20 ms）は、**D 型では実測で満たしている**
   （audio の lat 中央値 3.52 / p95 16.60 ms）が、**F 型では満たしていない**（中央値 69.13 ms）。
   1-(a) を選ぶならこの提案値は F 型に対しても再挑戦できる目標になり、選ばないなら
   L2 以降へ送る値になる。

3. **時計とコアの決定。決定済み — §8。** pin 採用（core 1）、`VM_JOB_STRIDE=1` 採用、
   CCOUNT 不採用（実装は `CONFIG_POCKET_VM_CCOUNT` 既定 `n` として残置）。決めることは無い。

4. **`deferred_buttons` の融合（§5.2-1）を受け入れるか。**
   (a) 受け入れて文書化、(b) キュー化（離鍵フレームの対を作り直す）、(c) 継続ターン中は
   最初の 1 つだけ保持して残りを捨てる。
   **実測後の追加情報**: 融合が起こるのは「早期に返る継続ターンが連続する」間だけで、
   実測でそうなったのは **F 型のみ**（D 型は継続 0 回、§2.4）。しかも F 型では継続ターンが
   33 ms ずつ続くので、**融合の窓は 1 フレームではなく約 100 ms ある** — 人が 100 ms 以内に
   2 キー押すのは普通なので、**この危険は焼く前の見積もりより大きい**。ただし 1-(a) で
   継続ターンを 8 ms 周期にすれば窓は約 24 ms に縮み、元の見積もりに戻る。
   **推奨: 1-(a) を先に決め、その後で (a) 受け入れを選ぶ。** 融合を根絶する (b) は
   離鍵フレームの対の作り直しを含むので L1 の範囲を超える。

5. **§6 の「未処理ジョブもイベントも無い場合だけ待機する」の解釈。** L1 は `ui_task` を

   フレーム待ちを完了通知で早く抜ける形に留めた。これを充足と認めるか、専用タスクを
   別段階（L1b）として立てるか。**認めない場合、L2 の前に RAM の作り直しが要る。**

6. **「公平モード」をビルド時選択にするか。** 継続 drain より前に `pocket_api_pump()` の
   resolve だけを許す形（FIFO は壊れないが、旧 drain 完了前に resolve が起きる順序になる）。
   **実測後の追加情報: 優先度は下がった。** F 型の遅延悪化の主因は互換モードではなく
   §2.4 の待ち方で、D 型では互換モードのままでも遅延は改善している（22.91 → 3.52 ms）。
   **推奨: 1-(a) を実施して測り直してから、まだ必要かを判断する（＝今は決めない）。**

7. **L0 で見つかった既存不具合の扱い**（L0 §6-6 から持ち越し。いずれも `main` にも効き、

8. **マージとタグ。** `vm/l1-host-sched` は 12 コミットで push していない。`vm-branching.md` は

## 8. 時計とコアの決定（2026-09-12、実機で決着）

§5.3 と §6-3 が残した「clockbench の 3 結論を取り込むか」を実機で測って決めた。
[vm-l1-clock.md](vm-l1-clock.md) §2 の「pin したビルドの実行時コストは未測定」も
ここで埋まっている。測定はすべて `CONFIG_POCKET_VM_PROBE=y` + `tools/vm_l0_capture.py`
（配置の比較はワークロード A/D/F × 条件 base/audio/all、時計と stride の比較は
ジョブの重い D/F × base/all、いずれも反復 2 × 15 秒）と、ホーム画面の
`PERF` 行を 12 秒のウォームアップ後 60 秒プールしたもの。**決定の結果は

### 8.3 決定

1. **`ui_task` を core 1 に pin する（採用）。** `CONFIG_POCKET_UI_TASK_CORE` の既定を
   `1` にした。実測で core 1 は無 pin と区別できない（sync_loop と promise_chain の
   ターン中央値は 0.1% 以内、async_generator は 1.5〜2% で反復間ばらつきと同程度、
   転送 0.04% 以内、DIRAM 0 B）、core 0 は 5.6〜15.6% 高い。無 pin は「OS が選ぶ」
   ＝将来の負荷次第で core 0 に載りうる側なので、測って安い方を固定する。
   これは**時計とは独立に成り立つ判断**で、CCOUNT を採らなくても残る。

2. **CCOUNT は採用しない。** 測定が利益を示さないため（§8.2）。代わりに払う代償は
   小さくない — CCOUNT はコアごとのレジスタなので `ui_task` の pin と**永久に結び付く**し、
   `CONFIG_PM_ENABLE`（DFS）を入れた日に**黙って**間違える（CCOUNT は CPU サイクルを
   数えるので、周波数が動けばレートが動く）。**測って差が出ないものに、静かに壊れる
   結合を足さない。** clockbench の「無料だからやる」は読み取りコストの比（33 倍）を
   根拠にしていたが、その比が drain に現れないことがここでの実測。

3. **`VM_JOB_STRIDE` を 1 にする（採用）。** clockbench の 3 結論のうち
   「毎ジョブ読む」だけは実測が支持した — ただし clockbench の理由（読み取りが安いから）
   ではなく、**予算の超過が実際に縮むから**である。

   | ワークロード / 条件 | stride 4（drain 中央値 / p95 / 最大 µs） | stride 1 | 差 |
   | --- | --- | --- | --- |
   | promise_chain / base | 730 / 897 / 1,053 | 731 / 858 / 1,035 | 変化なし |
   | promise_chain / all | 730 / 1,104 / 13,210 | 728 / 1,170 / 13,115 | 変化なし |
   | async_generator / base | 4,138 / 6,720 / 7,144 | 3,862 / **4,184** / **4,877** | **p95 −38%、最大 −32%** |
   | async_generator / all | 4,424 / 10,964 / 32,982 | 4,429 / 12,377 / 34,610 | 差なし（後述） |

   async_generator の p95 が 2.5 ms 縮むのは、このワークロードの高いジョブが
   中央値のジョブではないからで、stride 4 の 1 区間に高いジョブが 3 つ入りうるという
   clockbench の (N−1)×0.49 ms がそのまま出ている。**同じ差が CCOUNT 側の 2 本でも
   再現する**（6,551 → 4,432 µs、−32%）ので、ビルド間ばらつきではない。

   **`all` 条件では効果が消える。** 音・UI・Wi-Fi が載ると drain の尾を決めるのは
   予算検査の粒度ではなく**プリエンプション**で（p95 11〜12 ms、最大 33 ms はどちらの
   stride でも同じ）、細かく測っても縮まない。**改善するのは「他に誰も走っていない
   ときの超過」だけ**であって、混んだ機械の応答性ではない。

   費用は測定に出ない: promise_chain は 1 ターン 41 ジョブで、stride 4→1 の drain は
   730 → 731 µs（同じ器械が CCOUNT との 8 µs 差は分離している）。

4. **実装は残す。** `CONFIG_POCKET_VM_CCOUNT`（既定 `n`）として入っており、
   `CONFIG_POCKET_UI_TASK_CORE < 0` では**コンパイルを拒否する**（`vm_clock.c` の
   `#error`）。採らない判断を、次に誰かが測り直せる形で残すため。

### 8.4 単位と折り返し（採否に関わらず正しくした）

CCOUNT は 32 bit で、240 MHz では 2^32/240e6 ≒ **17.9 秒で一周する**。したがって:

- **時計の型を `vm_tick_t = uint32_t` にした。** 差分は `(vm_tick_t)(now - start)` と
  **符号なし 32 bit** で取る。C の mod-2^32 規則により、真の経過が周期未満である限り
  折り返しをまたいでも差は正しい。8 ms のターンに対して周期は 3 桁上なので、
  **折り返しは分岐ではなく型で処理されている**。esp_timer 経路も同じ型に落とし込んで
  あり（µs を 32 bit に切る）、こちらの周期は 4,295 秒。
- **µs ↔ tick の変換場所は 2 箇所だけで、どちらもジョブごとではない。**
  (a) 予算を張るとき（`vm_budget_begin_full`）に `limit_us × vm_clock_ticks_per_us()`
  で tick へ — **1 ターンに 1 回の掛け算**。(b) drain が返るときに
  `(vm_tick_t)(now - start) / ticks_per_us` で µs へ — **1 drain に 1 回の割り算**
  （小さな定数で割る 32 bit 除算、数十サイクル。drain は ms 単位）。
  **ジョブごとの検査は tick のままの引き算と比較**で、掛け算も割り算も入らない。
- `limit_ticks` は 2^31 tick で飽和させてある。符号なし差分は周期未満の間隔しか
  区別できないので、周期以上の予算は「期限切れになったことが観測できない」予算に
  なるため。240 MHz で 8.9 秒であり、このファームが張る最長の予算（離脱ターンの
  50 ms = 12e6 tick）から 2 桁離れている — 到達しないことを保つための飽和。
- 予算の**外向きの単位は µs のまま**（`VM_TURN_BUDGET_US` / `VM_RUNAWAY_US` /
  `RUNAWAY` のログ行 / `budget.elapsed` を足し込む暴走ガード）。単位が変わったのは
  `vm_sched.c` の内側だけで、`guest.c` も `app_session.c` も 1 行も変わっていない。

### 8.6 開いたまま残る問い

- **`VM_JOB_FLOOR=8` と、現れない読み取りコスト。** promise_chain は 1 ターン 41 ジョブで、
  stride 1 なら時計は 33 回読まれるはずで、esp_timer の 833 ns（実測、vm-l1-clock.md §1）
  なら +27 µs 出るはずである。**出ない**（730 → 731 µs、同じ器械が 8 µs 差は分離している）。
  floor が効いて「1 回の drain 呼び出しが 8 件に届いていない」のではないかと疑い、
  **floor を 0 にしたビルドを焼いて確かめた**（§8.2 の最終行）。結果は promise_chain
  729 µs で、やはり変わらない — floor は理由ではなかった。残る可能性は 2 つで、
  どちらも未確認（推定）: (a) この文脈での `esp_timer_get_time()` は clockbench が
  孤立して測った 833 ns よりずっと安い、(b) 41 ジョブが drain の外でも数えられている。
  **決定には影響しない** — 高い方の時計で測っても費用が出ない、という向きの疑問だから。
- **floor 0 は async_generator の尾を広げた**（p95 4,184 → 6,736 µs、stride 1 同士の比較）。
  予算を早く効かせるはずの変更が逆に働いており、floor は「前進保証」以上の役割を
  持っている可能性がある。スケジューラ定数の問題で、時計とは別に測るべき。
- **ホーム画面 mode 3 の fps は boot ごとに 27% 動く。** 背景が毎 boot 違う庭を生成する
  ため。ホームの描画に関する主張をするなら、この器械では**同一 boot 内の比較**か、
  庭を固定する手段が要る。

## 9. 公平モード（`CONFIG_POCKET_VM_FAIR`、既定 off、2026-09-12）

### 9.1 何のためにあるか

§6-6 が「実測後に判断する」として残していたもの。出荷時の既定は**互換順序**（§2.1、
設計 §2.1）— キューを残して戻ったターンの次のターンは、キューが空になるまで
JavaScript へ一切のホストイベントを届けない — で、その代償は「継続を要するアプリの
完了遅延」だった（音声競合下で legacy の 1.9 倍、実測(device)）。

公平モードはその代償を**測れるようにするため**に入れた build 時スイッチである。
既定は `n` で、off のときこのモードのコードは 1 バイトも生成されない：直前のビルドと
焼き込み像がバイト一致し、違うのは app descriptor の `elf_sha256`（オフセット 0xb0 から
32 B）とそれを含んで計算される末尾の像チェックサム 32 B だけ、残り 2,541,920 B 中の
全バイトが一致する（実測）。**既定の挙動は変えていない**（仕様 §12）。

### 9.2 実装した順序規則

継続ターンは**まず継続 drain から始まる**。これは互換モードと同一で、予算も同じ。

- その drain がキューを空にしたら、ターンはそのまま互換モードと**同じ経路**へ進む
  （exit の判定 → pump 群 → `frame()`）。つまり 1 ターンが 2 回 pump することは無い。
- ジョブが残ったら — 互換モードが「何も届けない」と決めている、まさにその境界で —
  通常ターンと**同じ pump 群を同じ順序で**走らせる（`frame()` と exit の判定は除く）。

pump が完了を settle する手段は resolve 関数の `JS_Call` で、resolve 関数は reaction を
**キューの末尾に積む**（台帳 03 事実 53）。したがって reaction は未完了の drain の
全ジョブの**後ろ**に入る。**キュー内の FIFO は互換モードとバイト単位で同一**であり、
変わるのは「ホストイベントが 1 本の論理 drain の 2 つのジョブの間で JavaScript に
届きうる」ことだけである。

`tools/vmtest/corpus/fair_fifo_tail.js` がこの末尾性そのものを固定している：完了が
記録された時点で `b1` `b2` は既にキューにあり `b3` `b4` はまだ無い。公平モードの出力は
`b2` の後・`b3` の前に完了が入り、それより前に現れたら「ホストの仕事がキューの
**先頭**に入った」ことの証拠になる。

**drain を先に、pump を後に**したのは意図的である。継続ターンが継続から始まらないと、
高頻度の購読が drain の前に仕事を積み続け、drain が自分の予算に到達しない形を作れる。

### 9.3 公平にしなかったもの（拒否した 2 件）

| 項目 | 公平モードでどうするか | 理由 |
| --- | --- | --- |
| `exit()` の判定 | **しない。** 両モードとも「キューが空で始まったターン」でのみ読む | `app_request_stop()` はゲストに**捕捉不能な割り込み**として届く。ジョブ境界で honour すると、そこに着地した drain が切られ、`.finally` が走るか否かが「予算がどこに落ちたか」で決まる。設計 §11.2 が互換モードで拒否したのと同じ理由が、公平モードでも消えない |
| `frame()` | **しない。** 継続ターンは両モードとも `frame()` を呼ばない | `frame()` はホストイベントではなくゲストの絵である。継続ターンで呼ぶと連鎖の**中**にフレームが入り、`corpus/budget_frame_boundary.js` が禁じている状態そのものになる。`app_turn_continued()` は継続ターンで真のままなので、`main.c` の表示周期の規則（3298d0f、§2.8）は**一切変更していない** |

触っていないもの: **未処理 rejection の報告時点**（ゲストは `vm_sched_drain()` が
`VM_DRAIN_EMPTY` を返した地点でのみ報告し、公平モードが足した境界はそれではない。
`corpus/fair_reject_point.js` が両モードで「報告は誰も捕まえない 1 件だけ」を固定する）と
**暴走ガードの集計**（`vm_sched_drain()` が消費した時間だけを足す規則は同じ）。

`deferred_buttons` は公平モードでは使われない。`pocket_ui_pump()` が継続ターンで走るので
押下はその場で届き、§5.2-1 の「2 打鍵が 1 マスクに融合する」危険は公平モードでは
発生しない。

**書き留めておく非対称（未計測）**: 公平モードでは pump が積んだ reaction が進行中の
論理 drain の一部になり、その drain に課金される。予算で切られ続ける drain の中で
毎ターン発火する購読があると、互換モードより早く `VM_RUNAWAY_US` に近づきうる。
実測していない。

### 9.4 実機の結果（2026-09-12、すべて実測(device)）

同一ツリー・同一日・`CONFIG_POCKET_VM_FAIR` の y/n だけが違う 2 本のプローブビルド
（`build_fair_on_probe` / `build_fair_off_probe`、どちらも core 1 pin・`VM_JOB_STRIDE=1`・
esp_timer）。ワークロードは **D promise_chain** と **F async_generator** の 2 本のみ、
条件 base / audio / wifi / all、各 3 反復、1 反復 15 s。生データは
`.cache/vm/fair-off.jsonl` / `.cache/vm/fair-on.jsonl`（git 管理外）。

### 9.5 誰が on にするか

**`await` の多いアプリ、すなわち 1 論理 drain が 1 ターンの予算に収まらないアプリで、
ネイティブ完了（音・無線・バス）の遅延が体感に効く場合。** それが F 型であり、そこでは
中央値で 3〜7 倍の改善が測れている。逆に D 型（drain が予算に収まる）では公平モードの
コードは到達不能で、on にする理由も害も無い。

on にしないのは、**順序の互換が仕様 §12 の要求だから**である。公平モードは JS から
観測できる順序を変える — 1 本の論理 drain の途中で `.then` の相手が増える — ので、
L1 の完了条件（旧来と同じ drain 順序）を満たすのは互換モードだけである。L2 が
この数字を根拠に既定を問い直すことはできる。
