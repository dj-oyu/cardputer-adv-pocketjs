# VM L2 設計: 移動しない VM スタックと中断・再開

対象: [quickjs-freertos-vm-spec.md](quickjs-freertos-vm-spec.md) §7（L2）。
方式は仕様どおり **L2a（非移動セグメント）→ L2b（明示フレームと単一実行ループ）→ L2c（セーフポイント・保存・再開）** の3段。
根拠は [vm-ledger/](vm-ledger/) の 01〜06（quickjs.c の事実）、[vm-L0-report.md](vm-L0-report.md)（実機の基準値）、
[vm-L1-report.md](vm-L1-report.md)（ジョブ境界までで到達した範囲）。2026-09-12 起案。

この文書は**決定**を書く。事実は台帳に、測定値はレポートにある。ここで新しく事実を主張しない。

## 1. 何をもって L2 が終わったとするか

仕様 §7 の完了条件は7項目ある。**そのうち3項目は、判定する仕組みがこのリポジトリに存在しない。**
実装より先にそれを作る。理由は L1 が実証している — 計測点が経路の一部しか通らなかったせいで、
「7倍速くなった」「16.7 KB 余分に保持している」という結論が2回とも誤りだった
（[vm-L1-report.md](vm-L1-report.md)、仕様 §14.4）。**判定できない条件は、満たしたかどうかを言えない。**

### 1.1 現状の対応表

`tools/vmtest/` の実走で確認した現状（2026-09-12、コーパス36件 × 6モード、Test262 4モード、
すべて pass。Test262 は 7,501 pass / 194 fail / regressions 0 で README の基準値と一致）。

| # | 完了条件（§7） | 判定手段 | 現状 |
| --- | --- | --- | --- |
| 1 | 純粋な JS の深い呼び出しで C スタック使用量が深さに比例しない | **無い。G1 を作る** | vmtest に C スタック使用量の計測が無い。`deep_recursion.js` の `max_depth` は「何段で溢れるか」であって「1段あたりの消費」ではない |
| 2 | 監査済みセーフポイントで停止し、再開後の値・副作用・例外が非中断実行と一致する | `--force-yield` + バイト比較 | **枠組みは動く**（実走で確認）。ただし後述のとおり今は**ジョブ粒度止まり** |
| 3 | 同期 JS の途中に別 JS を挟まない。中断で共有オブジェクトの状態が不意に変化しない | 同上 | 同上。ジョブ粒度のうちは「同期 JS の途中」をそもそも試せていない |
| 4 | 中断状態での GC・OOM・終了・例外・finally・クロージャ保持 | 同上 + コーパス | ジョブ境界での該当ケースは既にコーパスが固定している（`gc_threshold_device.js`、`try_finally.js`、`closures.js`、`stop_with_queue.js` 等）。opcode 粒度の中断状態では未 |
| 5 | 正確な最大中断遅延を主張するなら、最長の中断禁止区間も測定する | **無い。G5 を作る** | `timing.py` は eval+drain+frame の合計の中央値/p95/最大のみ。区間長を出さない |
| 6 | セグメント追加・境界越え・返却で値とクロージャの参照が壊れない | **無い。G6 を作る** | `vmrun.c` のアロケータはヘッダ付き malloc/realloc の写しで、セグメントの概念を持たない |
| 7 | 各確認地点の直前・直後に中断要求を発生させ、命令や副作用の重複・欠落がない／通知なし通常経路の性能低下も測る | 前半: `--force-yield`／後半: `timing.py` | 後半は現インフラで足りる。前半は #2 と同じ前提 |

### 1.2 いちばん安い関所が、まだ開いていない

`tools/vmtest/vmrun.c:540` が弱シンボルで宣言している

```c
void vmtest_vm_set_force_yield(JSRuntime *rt, int on);
```

を、**リポジトリの誰も定義していない**（`vmrun.c` の宣言と `vmrun.c:749` の呼び出し以外にヒットが無い）。
そのため `if (vmtest_vm_set_force_yield)` は常に偽で、`--force-yield` は `--budget-jobs 1`
と同義、つまり L1 のジョブ境界でしか中断していない。

これは壊れているのではなく、L1 が L2 のために先に用意した受け口が、まだ埋まっていないだけである。
ただし**結果として、L2 の完了条件 #2 #3 #4 #7前半 を検査するはずの関所は、今どんな実装に対しても緑になる。**
誰も走らせていない検査が「失敗しないという意味で通っているように見える」のと同じ形で、
**走ってはいるが何も検査していない検査**がここにある。

この1つの定義を埋めるだけで4項目が開く。**L2a の実装より前にこれを埋める。**
埋める先は L2 で新設する VM 側の1ファイルとし、`tools/vmtest/build.sh`（52-54 行でリンク対象を
列挙している）に追加する。`quickjs.c` 自体に置けば build.sh の変更は要らないが、上流との差分を
小さく保つため置かない。

**流用してはいけないもの:** `vmrun.c:226-230` / `:724` の `JS_SetInterruptHandler(G.runtime, vm_interrupt, &G)`
は `host_stopping`（セッション終了検知）専用である。ここに相乗りすると終了と中断が同じ経路で混線する。
これは仕様 §3-6「中断は例外ではない」と、台帳03 が記録する「割り込みが捕捉できない例外として
実装されている」という現状との衝突そのもので、§2 で正面から決める。

### 1.3 作る3つの判定機構

| 記号 | 何を判定するか | 作り方 | どこで動くか |
| --- | --- | --- | --- |
| G1 | 1段あたりの C スタック消費が深さに依存しないこと | 再帰の各段でスタックポインタ相当（ローカルのアドレス）を記録し、段差の系列を出す。判定は「深さ N と 2N で消費が2倍にならない」であって「溢れない」ではない | ホスト（vmrun）。実機は `uxTaskGetStackHighWaterMark` で追認 |
| G5 | 最長の中断禁止区間 | 中断を要求した時点から実際に停止した時点までを VM 側でカウントし、その**最大値**を出す。平均や中央値では完了条件を満たさない | ホスト（force-yield 中に常時記録）＋実機 |
| G6 | セグメント追加・境界越え・返却で参照が壊れないこと | `tools/vmalloc/` は既にアロケータ比較の器がある（台帳06）。ここにセグメント方式を足し、確保履歴の再生と、境界を跨いだ値・クロージャの生存検査を行う | ホスト。ASan/UBSan 付き |

G1・G5・G6 は L2a/L2b/L2c のどれとも独立に着手できる。**実装の前に用意する。**

### 1.4 L2 の終わり方

上の7項目すべてが機械で緑になり、かつ

- ホスト: `run.sh` を通常 / `--force-yield` / `--fair` / `--budget-jobs` の各モードで、コーパスがバイト一致
- ホスト: `test262.py` の合格集合が縮まない（現在 7,501 pass / 194 fail が基準）
- 実機: 恒久ハーネス（`CONFIG_POCKET_VM_PROBE`、`tools/vm_l0_capture.py`）で退行が無い
- 実機: `tools/memlog.py --port --check` が予算内

を満たしたときに L2 は終わる。**ビルド時スイッチで旧経路へ戻せること**（仕様 §12）は各段の必須要件で、
これも関所に含める。

## 2. opcode チェックポイントが届かない場所

**先にここを書く。** §7 の方式は「選んだ opcode の入口または処理完了後に固定の中断確認を置く」だが、
**バイトコードのディスパッチループに戻ってこない区間には、opcode に確認を何個置いても届かない。**
仕様 §7 は「未対応経路は従来の同期呼び出しとして囲い、中断禁止を明示する。黙って仕様を変更しない」
と書いている。そのためにはまず**どこが届かないのかの一覧**が要る。これが完了条件 #5
（最長の中断禁止区間の測定）の対象そのものになる。

以下は本日 quickjs.c を読んで確認した4種類。行番号は現行ワークツリー。

| # | 区間 | 上限 | 事実 |
| --- | --- | --- | --- |
| N1 | 正規表現マッチ | 無し（入力とパターン次第） | `lre_check_timeout`（`quickjs.c:50400-50406`）は `interrupt_counter` を経由せず `rt->interrupt_handler` を**無条件に直接**呼ぶ。真を返すと `js_regexp_exec` が `JS_ThrowInterrupted` する箇所が2つ（`:50531-50532`、`:50745-50746`）。**opcode 確認の完全な外側にある、既存の唯一の別系統**（台帳03 fact 36、台帳04） |
| N2 | ネイティブ関数だけで完結する処理 | 無し | `js_call_c_function` 系の呼び出し経路に `js_poll_interrupts` が**1つも無い**（grep 確認）。JS コールバックを介さない大きな `JSON.stringify` などはここに入る |
| N3 | `for-in` の1ステップ | オブジェクトの `prop_count` / 配列の `array_length` | `js_for_in_next`（`quickjs.c:17054-17118`）の内部に `for (;;)`（`:17073-17108`）があり、非 enumerable なプロパティと `JS_ATOM_NULL` を**中断確認なしに読み飛ばし続ける**（`:17089`）。削除済みプロパティ（`JS_HasProperty` が 0）でも継続する。**上限は有限だが、1回の `OP_for_in_next` が全プロパティ数に比例して長くなりうる** |
| N4 | パース | ソース長 | direct eval（`JS_EvalObject` → `__JS_EvalInternal` → `js_parse_program`、`quickjs.c:38358`）のパース段。実行段は `JS_CallFree`（`:38242`）で通常の `JS_CallInternal` に戻るので既存機構に乗る。起動時パースと同種 |

**届く経路として決着したもの:**

- **`for-of` はそのまま乗る。** `js_for_of_next`（`quickjs.c:17317-17343`）は内部でループせず、
  `JS_IteratorNext` を1回呼んで返る（`:17322-17339`）。反復はバイトコードの後方分岐が回すので、
  毎イテレーションでディスパッチループに戻る。JS で書かれた `next()` は `JS_Call`（`:17200`）
  経由でバイトコード実行に入る。**N3 と対照的で、for-in と for-of を同じ扱いにしてはならない。**
- **`apply` は有界。** `js_function_apply`（`:42943-42970`）と `build_arg_list`（`:42895-42939`）に
  中断確認は無いが、`len > JS_MAX_LOCAL_VARS`（65535、`quickjs.c:222`）を弾く（`:42909-42914`）ので
  内部の作業量に定数上限がある。引数を組んだ後は `JS_Call` でバイトコード実行に戻る。
  N3 より優先度は低い。
