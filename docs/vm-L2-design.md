# VM L2 設計: 移動しない VM スタックと中断・再開

対象: [quickjs-freertos-vm-spec.md](quickjs-freertos-vm-spec.md) §7（L2）。
方式は仕様どおり **L2a（非移動セグメント）→ L2b（明示フレームと単一実行ループ）→ L2c（セーフポイント・保存・再開）** の3段。
根拠は [vm-ledger/](vm-ledger/) の 01〜06（quickjs.c の事実）、[vm-L0-report.md](vm-L0-report.md)（実機の基準値）、
[vm-L1-report.md](vm-L1-report.md)（ジョブ境界までで到達した範囲）。2026-09-12 起案。

この文書は**決定**を書く。事実は台帳に、測定値はレポートにある。ここで新しく事実を主張しない。

## 1. 何をもって L2 が終わったとするか

仕様 §7 の完了条件は7項目ある。**そのうち3項目は、判定する仕組みがこのリポジトリに存在しない。**
実装より先にそれを作る。理由は L1 が実証している — 計測点が経路の一部しか通らなかったせいで、
「7倍速くなった」「16.7 KB 余分に保持している」という結論が2回とも誤りだった
（[vm-L1-report.md](vm-L1-report.md)、仕様 §14.4）。**判定できない条件は、満たしたかどうかを言えない。**

### 1.1 現状の対応表

`tools/vmtest/` の実走で確認した現状（2026-09-12、コーパス36件 × 6モード、Test262 4モード、
すべて pass。Test262 は 7,501 pass / 194 fail / regressions 0 で README の基準値と一致）。

| # | 完了条件（§7） | 判定手段 | 現状 |
| --- | --- | --- | --- |
| 1 | 純粋な JS の深い呼び出しで C スタック使用量が深さに比例しない | **無い。G1 を作る** | vmtest に C スタック使用量の計測が無い。`deep_recursion.js` の `max_depth` は「何段で溢れるか」であって「1段あたりの消費」ではない |

### 1.2 いちばん安い関所が、まだ開いていない

`tools/vmtest/vmrun.c:540` が弱シンボルで宣言している

```c
void vmtest_vm_set_force_yield(JSRuntime *rt, int on);
```

を、**リポジトリの誰も定義していない**（`vmrun.c` の宣言と `vmrun.c:749` の呼び出し以外にヒットが無い）。
そのため `if (vmtest_vm_set_force_yield)` は常に偽で、`--force-yield` は `--budget-jobs 1`
と同義、つまり L1 のジョブ境界でしか中断していない。

これは壊れているのではなく、L1 が L2 のために先に用意した受け口が、まだ埋まっていないだけである。
ただし**結果として、L2 の完了条件 #2 #3 #4 #7前半 を検査するはずの関所は、今どんな実装に対しても緑になる。**
誰も走らせていない検査が「失敗しないという意味で通っているように見える」のと同じ形で、
**走ってはいるが何も検査していない検査**がここにある。

この1つの定義を埋めるだけで4項目が開く。**L2a の実装より前にこれを埋める。**

**状態（2026-09-13）: 埋めた。** `components/quickjs-ng/quickjs-ng/quickjs-vm.c` が定義し、`tools/vmtest/build.sh` がリンクする。
止まる地点は §7.2 の分類 A の 7 地点だけで、「止まる」は §4.1 の捕捉不能な `interrupted` のまま（L2c が置き換える）。
したがって **`run.sh --force-yield` は今、赤い**: 37 件中 3 件（分岐を 1 つも実行しないファイル）だけ通り、34 件が最初の後方分岐でジョブを失って落ちる（実測(host)、asan）。
赤いことが、この関所が何かを検査している証拠になる。通常走行は 37/37、Test262 は 7,501 / 194 / regressions 0 で変わらない。
詳細と「通ってしまったときに疑う手順」は [tools/vmtest/README.md](../tools/vmtest/README.md) の FORCED-YIELD の節。
埋める先は L2 で新設する VM 側の1ファイルとし、`tools/vmtest/build.sh`（52-54 行でリンク対象を
列挙している）に追加する。`quickjs.c` 自体に置けば build.sh の変更は要らないが、上流との差分を
小さく保つため置かない。

**流用してはいけないもの:** `vmrun.c:226-230` / `:724` の `JS_SetInterruptHandler(G.runtime, vm_interrupt, &G)`
は `host_stopping`（セッション終了検知）専用である。ここに相乗りすると終了と中断が同じ経路で混線する。
これは仕様 §3-6「中断は例外ではない」と、台帳03 が記録する「割り込みが捕捉できない例外として
実装されている」という現状との衝突そのもので、§2 で正面から決める。

### 1.4 L2 の終わり方

上の7項目すべてが機械で緑になり、かつ

- ホスト: `run.sh` を通常 / `--force-yield` / `--fair` / `--budget-jobs` の各モードで、コーパスがバイト一致
- ホスト: `test262.py` の合格集合が縮まない（現在 7,501 pass / 194 fail が基準）
- 実機: 恒久ハーネス（`CONFIG_POCKET_VM_PROBE`、`tools/vm_l0_capture.py`）で退行が無い
- 実機: `tools/memlog.py --port --check` が予算内

を満たしたときに L2 は終わる。**ビルド時スイッチで旧経路へ戻せること**（仕様 §12）は各段の必須要件で、
これも関所に含める。

## 2. opcode チェックポイントが届かない場所

**先にここを書く。** §7 の方式は「選んだ opcode の入口または処理完了後に固定の中断確認を置く」だが、
**バイトコードのディスパッチループに戻ってこない区間には、opcode に確認を何個置いても届かない。**
仕様 §7 は「未対応経路は従来の同期呼び出しとして囲い、中断禁止を明示する。黙って仕様を変更しない」
と書いている。そのためにはまず**どこが届かないのかの一覧**が要る。これが完了条件 #5
（最長の中断禁止区間の測定）の対象そのものになる。

以下は本日 quickjs.c を読んで確認した4種類。行番号は現行ワークツリー。

| # | 区間 | 上限 | 事実 |
| --- | --- | --- | --- |
| N1 | 正規表現マッチ | 無し（入力とパターン次第） | `lre_check_timeout`（`quickjs.c:50400-50406`）は `interrupt_counter` を経由せず `rt->interrupt_handler` を**無条件に直接**呼ぶ。真を返すと `js_regexp_exec` が `JS_ThrowInterrupted` する箇所が2つ（`:50531-50532`、`:50745-50746`）。**opcode 確認の完全な外側にある、既存の唯一の別系統**（台帳03 fact 36、台帳04） |
| N2 | ネイティブ関数だけで完結する処理 | 無し | `js_call_c_function` 系の呼び出し経路に `js_poll_interrupts` が**1つも無い**（grep 確認）。JS コールバックを介さない大きな `JSON.stringify` などはここに入る |
| N3 | `for-in` の1ステップ | オブジェクトの `prop_count` / 配列の `array_length` | `js_for_in_next`（`quickjs.c:17054-17118`）の内部に `for (;;)`（`:17073-17108`）があり、非 enumerable なプロパティと `JS_ATOM_NULL` を**中断確認なしに読み飛ばし続ける**（`:17089`）。削除済みプロパティ（`JS_HasProperty` が 0）でも継続する。**上限は有限だが、1回の `OP_for_in_next` が全プロパティ数に比例して長くなりうる** |
| N4 | パース | ソース長 | direct eval（`JS_EvalObject` → `__JS_EvalInternal` → `js_parse_program`、`quickjs.c:38358`）のパース段。実行段は `JS_CallFree`（`:38242`）で通常の `JS_CallInternal` に戻るので既存機構に乗る。起動時パースと同種 |
| N5 | 関数プロローグ（`new_target` をローカルへ写すまで） | 固定長・短い | §5.2 の条件。ここで中断しないなら `new_target` を保存しなくてよい。§5.3-3 |

**届く経路として決着したもの:**

- **`for-of` はそのまま乗る。** `js_for_of_next`（`quickjs.c:17317-17343`）は内部でループせず、
  `JS_IteratorNext` を1回呼んで返る（`:17322-17339`）。反復はバイトコードの後方分岐が回すので、
  毎イテレーションでディスパッチループに戻る。JS で書かれた `next()` は `JS_Call`（`:17200`）
  経由でバイトコード実行に入る。**N3 と対照的で、for-in と for-of を同じ扱いにしてはならない。**
- **`apply` は有界。** `js_function_apply`（`:42943-42970`）と `build_arg_list`（`:42895-42939`）に
  中断確認は無いが、`len > JS_MAX_LOCAL_VARS`（65535、`quickjs.c:222`）を弾く（`:42909-42914`）ので
  内部の作業量に定数上限がある。引数を組んだ後は `JS_Call` でバイトコード実行に戻る。
  N3 より優先度は低い。

| 32 | 25.60% | 不明 | — |
| 96 | 17.34% | 初期 shape | **80** |
| 64 | 9.66% | `JSShape` 本体と一致（断定はしない） | **48** |

すべて16の倍数である。**（32 と 24 と 8 のクラスは正体が不明なので、この観察を全体へ広げない。）

**未取得:** 実機での確保サイズ分布そのもの。ホストの分布は形の参考にはなるが、
ブロックが総じて小さくなる分、同じ刻みでも相対的な内部断片化は実機の方が悪くなる側にずれる。
恒久ハーネス（`CONFIG_POCKET_VM_PROBE`）にサイズヒストグラムを足せば取れる。L2a の
セグメントサイズを最終決定する前に取ること。

（`-DJS_NAN_BOXING=1` を付けた64bitホストビルドで実機と同じ `JSValue` 幅にする案は成立しない。
NaN boxing はポインタを下位32bitに入れる設計なので、64bit ホストではヒープポインタが切り詰められ、
ランタイム初期化中に必ず落ちる。実装の不具合ではなく32bit専用の設計。）

### 3.3 整列（D7 の決着）

実機コンパイラでの測定:

- `_Alignof(uint64_t)` = `_Alignof(double)` = 8、`_Alignof(void*)` = 4、`sizeof(max_align_t)` = 16。
- **しかし Xtensa LX7 に64bitのロード命令は無い。** `uint64_t` の読み出しは `l32i.n` **2命令**に
  展開される（`load64` を逆アセンブルして確認）。それぞれは4バイト整列のアクセスなので、
  4バイト境界に置かれた `JSValue` をスカラーで触っても落ちない。

**決定: 個々の確保に8バイト境界を強制しない。4バイトで足りる。**

**ただしセグメントの先頭は16バイト境界に取る。** 理由は PIE の一括転送で、`ee.vld.128.ip` /
`ee.vst.128.ip` が16バイト／命令を動かせる（`JSValue` 2個ぶんを1命令、スカラーの `l32i.n`×2 に対して4倍）。
L2 は生存セグメントを移動しないのでここでは効かないが、**L4 のコンパクションはコピー速度が
そのまま停止時間になる**（仕様 §9）。16バイト境界はセグメント単位（数 KB に1回）の要求で
個々の確保の余白を増やさないので、いま揃えておく費用はほぼゼロで、L4 に速いコンパクタの
選択肢を残せる。§3.1 のとおり、正体の割れた主要クラスは実機で 48・80・48・32 と
すべて16の倍数でもある。

**この整列は守らないと静かに壊れる。** 128bitアクセスはアドレスの下位4bitを0に強制し、
**例外は上がらない**（[pie-simd.md](pie-simd.md) §5）。`board.c` の共有ストリップバッファが
`__attribute__((aligned(16)))` を付けているのはこのため。

**未確認:** S3 の PIE には非整列ストリーム用の命令（`EE.LD.128.USAR.IP` + `EE.SRC.Q`）が
ISA にあるはずだが、このリポジトリでは使っておらず、TRM でも確認していない。
整列を諦める設計を採るなら先に裏を取ること。

### 3.4 JSValue の表現は L2 で触らない（既決）

実機コンパイラでの測定: `sizeof(JSValue)` は既定（NAN boxing 有効）で **8**、
`-DJS_NAN_BOXING=0` で **16**。**8 はこのチップでの小さい方**で、切れば全スタックスロット・
全配列要素・全プロパティ値が倍になる。

4バイトにはできない。NaN boxing は IEEE754 の double を64bitの中に**そのまま**格納している
（`__JS_NewFloat64`、`quickjs.h:266-281`。ビットパターンをオフセットするだけで確保は発生しない）。
4バイト値にはタグ付きポインタか小整数しか入らないので、そこへ行く処理系は非整数の数値を
すべてヒープに箱詰めする。4バイト/スロットの節約と引き換えに float 1個ごとに確保・参照カウント・
GC 圧を払う取引で、算術をする JS には損。短い BigInt も同じ枠を使っている（`JS_TAG_SHORT_BIG_INT`）。

払っている代金は Xtensa 側の命令数（読み出し1回が `l32i.n`×2）で、これは §3.3 で測ったとおり。

**値表現の変更は上流の値モデルそのものの変更であって、呼び出しとフレーム管理の話ではない。
L2 の範囲外とする。** 蒸し返さないためにここへ記録する。

## 4. 中断を例外にしない（D1 の決定）

### 4.1 いま「中断」が通っている道

`JS_ThrowInterrupted`（`quickjs.c:8450` 付近）は `InternalError: interrupted` を
**uncatchable フラグ付きで投げる**。インタプリタはそれを `exception:`（`quickjs.c:20875`）で受け、
こうなる。

```text
exception:                       quickjs.c:20875
  build_backtrace(...)           :20876-20881  ← uncatchable かどうかを見る前に走る
  if (!IsUncatchableError) {     :20882        ← uncatchable なら catch/finally 探索を丸ごと飛ばす
      ... CATCH_OFFSET を探して restart ...
  }
  ret_val = JS_EXCEPTION;        :20904        ← フレームは失われる
  if (func_kind != NORMAL) {
done_generator:                  :20909
      sf->cur_pc = pc;                         ← 保存して返る。ローカルは解放しない
      sf->cur_sp = sp;
  } else {
done:                            :20913
      close_var_refs(rt, sf);
      for (pval = local_buf; pval < sp; pval++) JS_FreeValue(ctx, *pval);   ← 全部解放
  }
  rt->current_stack_frame = sf->prev_frame;    :20923
```

この道を yield に使えない理由は4つあり、いずれも構造的である。

1. **`done:` がローカルとオペランドスタックを全部解放する**（`:20913-20921`）。再開する気なら
   これは通れない。
2. **`ret_val = JS_EXCEPTION`（`:20904`）でフレームが失われる。** 呼び出し元に返るのは値であって、
   中断状態ではない。
3. **`try`/`catch`/`finally` が素通りする**（`:20882` の条件）。仕様 §3-6 の「中断時に finally の
   実行やフレーム解放を開始しない」は満たすが、**それは中断が終了と同じ扱いだからで、
   再開できないことの裏返し**である。台帳03 の事実39-41 のとおり、`await` 再開中に起きると
   その async 関数の Promise は resolve も reject もされず永久に pending で残る。
4. **中断の道が確保をする。** `build_backtrace`（`:20876-20881`）は uncatchable かどうかを
   **判定する前に**走る。つまり今は割り込みのたびにバックトレースを組んでいる。仕様 §14.6 が
   記録している上流の use-after-free は、まさにこの「バックトレースを組む途中で確保に失敗する」
   経路である。**メモリが苦しいときこそ止まりたいのに、止まる道が確保を要求する。**

### 4.2 中断の原語はすでに VM の中にある

`done_generator`（`:20909-20912`）が `sf->cur_pc = pc; sf->cur_sp = sp;` を書いて、
**ローカルを解放せずに返る**。これは async / generator の suspend が使っている道で、
L2 が必要とする「保存して戻る」そのものである。

仕様 §14.5 が「async/generator の機構は、フレームの表現と再開の入口の雛形にはなるが、
呼び出し構造の雛形にはならない」と言っているのはこの区別で、**保存と復帰の形は流用でき、
C 再帰を消す部分は流用できない**。L2b で作るのは後者だけでよい。

### 4.3 決定

**D1: 中断を3つに分ける。yield は返り値であって、投げられる値ではない。**

| 種別 | 意味 | 通る道 | finally | 確保 |
| --- | --- | --- | --- | --- |
| **YIELD** | 予算切れ・プリエンプト。**同じジョブを後で続ける** | `done_generator` 形（`cur_pc`/`cur_sp` を保存して返る）。`exception:` を通らない | 走らせない（走らせてはいけない。まだ抜けていない） | **してはならない** |
| **TERMINATE** | セッション終了・ウォッチドッグ。**もう続けない** | 現行の uncatchable 例外のまま | 走らない（現状どおり。§4.1-3 の性質は終了なら許容できる） | 現状どおり（backtrace は組まれる） |
| **WAIT** | `await` など言語上の中断 | 既存の Promise 機構のまま。L2 は触らない | — | — |

仕様 §7 の `VMRunStatus` に写すと、YIELD が `VM_YIELDED`、TERMINATE が `VM_FAILED`、
WAIT が `VM_WAITING` に対応する。

**この分割の帰結:**

- **述語の返り値の型が変わる。** 今のウォッチドッグ述語は `int (*)(void *)` の真偽値で、
  「止めるか否か」しか言えない（`pocketjs_guest_set_watchdog`、`guest.h:93`）。L2 では
  「どの種別で止めるか」を返す必要がある。ここは L1 が既に1本化してある
  （`guest.c:359` が唯一の `JS_SetInterruptHandler` 呼び出し口で、ホストは述語だけ差し替える。
  **台帳03 の事実46-47「app_session.c が guest.c の機構を上書きして殺している」は L1 以前の記述で、
  現状とは違う**）ので、変えるのは述語の型と、それを読む1箇所だけで済む。
- **YIELD は確保をしてはならない。** メモリが苦しいときに止まれないと、L2 が何のためにあるのか
  分からなくなる。`build_backtrace` を通らないことが要件で、これは §4.1-4 の上流 UAF を
  yield 経路については構造的に避けることにもなる。
- **YIELD で `finally` を走らせない**のは仕様 §3-6 そのものだが、TERMINATE との違いは
  「後で走る」か「二度と走らない」かである。**TERMINATE が finally を飛ばす現状は L2 では直らない。**
  直すなら別の段の仕事で、L2 の完了条件には入っていない。ここを黙って広げない。
- **`await` 中断で Promise が pending のまま固まる問題（台帳03 事実39-41）は、YIELD については
  起きなくなる**（そもそも例外にならないので `js_async_function_resume` の uncatchable 分岐に
  入らない）。**TERMINATE では残る。** これも L2 の範囲外として明示する。

**未決（D8 へ送る）:** YIELD がどの地点で許されるか、その地点ごとに `cur_pc` を命令の先頭に
戻すのかデコード後の状態を保存するのか（仕様 §7「再開 PC の契約を地点ごとに記録する」）。

## 5. フレームが運んでいないもの（D2 の決定）

### 5.1 `JSStackFrame` の実レイアウト（実測）

§3.1 と同じ方法（ファームと同じコンパイル行、`.rodata` から読み出し）で `offsetof` を取った。

| フィールド | offset | サイズ |
| --- | --- | --- |
| `prev_frame` | 0 | 4 |
| *(隙間)* | **4-7** | **4** |
| `cur_func` | 8 | 8（`JSValue`、8バイト境界を要求） |
| `arg_buf` | 16 | 4 |
| `var_buf` | 20 | 4 |
| `var_refs` | 24 | 4 |
| `cur_pc` | 28 | 4 |
| `var_ref_count` | 32 | 2 |
| `arg_count` | 34 | 2 |
| `is_strict_mode` | 36 | 1 |
| *(隙間)* | **37-39** | **3** |
| `cur_sp` | 40 | 4 |
| *(末尾隙間)* | **44-47** | **4** |
| 合計 | | **48**（`_Alignof` = 8） |

**11 バイトが隙間である。** つまり **4バイト幅のフィールドを2つと、1バイト幅を3つまで、
構造体を1バイトも太らせずに足せる。** 一方 `JSValue`（8バイト、8バイト境界）は隙間に入らず、
足せば 48 → 56 になる。

`JSAsyncFunctionState` は 64 バイトで、`frame` は offset 16。
つまり `this_val`(8) + `argc`(4) + `throw_flag`(1) + 詰め物(3) + `frame`(48)。
**フレームを太らせるのではなく、フレームを包む構造体に持たせている。**

### 5.2 3つのうち2つは保存が要らない

- **`flags`（`JS_CALL_FLAG_*`）は保存不要。** `JS_CallInternal` 本体での参照は
  `quickjs.c:18227`・`:18262`・`:18266` の3箇所だけで、**すべて `restart:`（ディスパッチループの
  入口）より手前**にある。フレームの形を決めたら用済みで、実行中は二度と読まれない。
  それ以降に出てくる `flags` は opcode オペランド由来の同名ローカルで別物。
  再開側は `async_func_resume`（`:21211`）と同じく、**定数として渡し直せばよい**。
- **`new_target` も保存不要 — ただし条件付き。** 本体での参照は4箇所（`:18484` の
  `OP_special_object NEW_TARGET`、`:18794` の `OP_check_ctor`、`:18803`/`:18810` の
  `OP_init_ctor`）で、**この3つの opcode はいずれも関数バイトコードのプロローグにしか
  現れない**。ユーザーが書いた `super()` は `OP_init_ctor` ではなく
  `OP_scope_get_var new_target` → `OP_call_constructor` にコンパイルされ、
  **プロローグで既にローカル変数へ写された値**を読む。だから関数の途中で `new_target` の
  生の引数が要ることはない。
  → **条件は「プロローグの中で中断しないこと」。** これは安いので採る（§5.3）。
- **`this_obj` だけは保存が要る。** これは `JSAsyncFunctionState.this_val`
  （`async_func_init` の `:21134` で1回だけ書かれ、`async_func_resume` の `:21207-21209` で
  再開のたびに読まれる）として、上流が既に「C スタックに置けないので逃がしている」唯一のもの。

- **`caller_ctx` は保存が要る。ただし費用はゼロ。** `JS_CallInternal` の第1引数で、
  総参照10箇所のうち**4箇所がディスパッチループの中**にある（`:18784`・`:19211`・`:19224`・
  `:19237`、いずれも `JS_Throw*` によるエラー生成）。callee 側の `ctx` は `b->realm`
  （`:18234`）から復元できるが、**`caller_ctx` は復元できない** — 呼び出し元の realm であって、
  実行中の関数からは辿れない。4箇所を `ctx` で代用するとエラーオブジェクトが作られる realm が
  変わるので、仕様 §7 の「黙って仕様を変更しない」に反する。
  **`JSContext *` は4バイトで、§5.1 の offset 4-7 の隙間にそのまま入る。構造体は 48 バイトのまま。**

### 5.3 決定

**D2: フレームを太らせず、`JSAsyncFunctionState` に倣って包む。**

1. **中断フレームは `JSStackFrame` を内包する構造体に持たせ、`this_val` はそこに置く。**
   `JSStackFrame` に `JSValue` を1つ足すと 48 → 56 になるが、**その代償は L2 が触らない経路にも
   かかる**。`JSStackFrame sf_s` は `alloca` ではなく素の C 自動変数で、`JS_CallInternal`
   （`:18191`）だけでなく `js_call_c_function`（`:17984`）、`js_call_c_function_data`（`:6479`）、
   `js_call_c_closure`（`:6612`）の**4つの呼び出し規約それぞれ**が1段につき1個持つ。
   L2b が C 再帰を消すのはバイトコード関数の分だけなので、残り3つは太ったまま残る。
   しかも `js_check_stack_overflow` の閾値計算は `alloca_size`（`arg_buf`/`var_buf`/`stack_buf`/
   `var_refs` の合計）しか見ておらず、**`sf_s` 自身はその計測の外にある**（`:18262-18264`）。
   つまり太らせた分はスタックガードから見えないところで効く。
2. **`flags` と `new_target` は保存しない。** 再開側が定数を渡す（`flags`）、プロローグで
   ローカルに写った値を使う（`new_target`）。
3. **プロローグを中断禁止区間に加える。** §2 の N1〜N4 に **N5: 関数プロローグ**（`new_target` を
   ローカルへ写すまで）を足す。長さは固定で短く、証明も容易なので、これで `new_target` の
   永続化を丸ごと回避できる。
4. **`caller_ctx` は `JSStackFrame` の offset 4-7 の隙間に置く。** 全フレームが必要とし、
   4バイトで、そこがちょうど空いている。構造体は 48 バイトのまま。
5. **残る隙間の使い道。** 37-39 の3バイトは中断状態の目印（§6.2-2）へ。44-47 の4バイトは復帰の形（§7.3-2）へ。
   **隙間は「全フレームが常に必要とするもの」にだけ使う** — 中断フレームだけが必要とするものは
   包む側（1 の構造体）へ置く。そうしないと、中断しない大多数のフレームが費用を払うことになる。

**この結果、L2 が `JSStackFrame` を太らせる必要は無くなった。** 48 バイトのまま、
`caller_ctx` と中断の目印が入る。`this_val` だけが包む側に出る。

## 6. 中断フレームと GC（D4 の決定）

### 6.1 何が問題なのか

QuickJS は参照カウントが主、循環参照 GC が従。循環 GC は「各 GC オブジェクトが申告した子への
参照を辿ってカウントを引き、0 になったものは輪の中からしか参照されていない」と判定する。

**GC が辿らない場所からの参照は減算されないので、カウントが残り、対象は生き残る。**
だから実行中の関数のローカル（C スタック上）を GC が walk しなくても壊れない。安全側に倒れている。

`async_func_mark`（`quickjs.c:21155-21173`）がこの境界をそのまま書いている。

```c
    if (sf->cur_sp) {
        /* if the function is running, cur_sp is not known so we
           cannot mark the stack. Marking the variables is not needed
           because a running function cannot be part of a removable
           cycle */
        for (sp = sf->arg_buf; sp < sf->cur_sp; sp++)
            JS_MarkValue(rt, *sp, mark_func);
    }
```

`cur_sp` が非 NULL = 中断中のときだけ mark する。**この1つの分岐が「実行中」と「中断中」を
分ける唯一の目印**である。失敗の仕方は非対称:

- **mark しない → 漏れる。** その中断フレームを通る循環が回収されない。落ちはしない。
- **間違って mark する（実行中を古い `cur_sp` で walk するなど）→ 早すぎる解放 = use-after-free。**

L2 が作るのは**普通の関数の中断フレーム**で、これはセグメントの中にいて、
**GC オブジェクトの誰も所有していない**。今「中断できるフレーム」は async / generator だけで、
それらは `JSAsyncFunctionState` の中にあり、持ち主が GC オブジェクトなので辿れている。

### 6.2 決定

**D4: 中断フレームは、GC が辿れるものから所有される。目印は明示的に持つ。**

1. **所有者を作る。** 中断フレームを、mark 関数を持つ GC オブジェクト（または runtime が持つ
   中断フレーム一覧で、`gc_mark` から辿るもの）にぶら下げる。`JSAsyncFunctionState` が
   `async_func_mark` から辿られているのと同じ形にする。
2. **「実行中／中断中」の目印を `cur_sp` の再利用に頼らない。** L2 のフレームは `cur_sp` が
   NULL でない状態で実行中になりうるので、`cur_sp` を判別に使うと §6.1 の UAF 側に落ちる。
   §5.3-4 の隙間に専用のビットを置く。
3. **フレームを汎用的に歩く仕組みを足すときは、`class_id` のガードを外さない。**
   台帳02 が記録しているとおり、ガード無しに `JSFunctionBytecode*` 等を読むと未初期化の
   C スタックメモリを読む。今そういうコードは無いが、L2 が最初に作るものがそれになる。

### 6.3 §14.6 の GC 閾値修正とは独立ではない

仕様 §14.6 は「循環参照のゴミが一度も回収されない。GC の自動閾値の初期値（256 KiB）が
ゲストのヒープ上限（160 KiB）より大きく、firmware はどこからも `JS_SetGCThreshold` /
`JS_RunGC` を呼ばない」と記録している。**つまり実機では循環 GC が事実上一度も走っていない。**

だから §6.1 の漏れは今は表面化しない。逆に言えば:

- **閾値を直して GC が走り始めたとき、中断フレームが未対応なら漏れる。**
- **対応が間違っていれば落ちる。**

「1行呼べば済む」と書かれている修正は、L2 と順序の依存がある。**閾値の修正は L2c（中断・再開の
統合）より後に入れる。** 先に入れるなら、その時点では中断フレームがまだ存在しないので安全だが、
L2c を入れた瞬間に上の2つが同時に有効になる。どちらの順でも、**L2c の関所に「GC を強制的に
回した状態で中断・再開してもコーパスがバイト一致する」を入れる**（完了条件 #4 の
「中断状態での GC」はこれを指している）。

## 7. 再開 PC の契約（D8 の決定）

仕様 §7 は「再開 PC の契約を地点ごとに記録する。opcode を読み取って PC が進んだだけの地点なら、
命令先頭に戻して保存するか、デコード済みの状態を保存する。実行済みの分岐を再実行したり、
未実行の call を飛ばしたりしない」と要求している。

### 7.1 原則: 命令が完全に退役した地点にしか置かない

**デコード済み状態の保存はしない。命令の途中では止まらない。** そう決めれば「命令先頭に戻すか
デコード済みを保存するか」という選択自体が消える。セーフポイントに許されるのは、

- `cur_pc` = **次に実行する命令の先頭**
- `cur_sp` = **その命令の副作用を全部反映した後**のスタック
- 半分消費したオペランドも、解放済みなのに残っている参照も無い

という地点だけ。再開はディスパッチループに入り直すだけで済み、保存すべき「途中の状態」が存在しない。

### 7.2 分類 A: 既存の7地点はそのまま契約を満たしている

`goto` / `goto16` / `goto8` / `if_true` / `if_false` / `if_true8` / `if_false8`。
**上流がこの位置に置いた理由がコードの形に出ている。**

```c
CASE(OP_goto):
    pc += (int32_t)get_u32(pc);              // 分岐先が確定してから
    if (unlikely(js_poll_interrupts(ctx)))   // ← 確認
        goto exception;
BREAK;                                        // quickjs.c:19298-19303
```

```c
CASE(OP_if_true): {
    op1 = sp[-1];
    pc += 4;                                  // オペランド消費
    res = ...JS_ToBoolFree(ctx, op1);         // op1 を解放
    sp--;                                     // ポップ
    if (res) pc += (int32_t)get_u32(pc - 4) - 4;   // 分岐先確定
    if (unlikely(js_poll_interrupts(ctx)))    // ← 確認
        goto exception;
}                                             // quickjs.c:19315-19333
```

確認地点では `pc` は分岐先（または次命令）、`sp` はポップ済み、`op1` は解放済み。
**命令は完全に退役している。** 契約は「`cur_pc` と `cur_sp` をそのまま保存する」で足り、
分岐の再実行も起きない。仕様が言う「分岐先 PC を確定してから確認」はこの形を指している。

### 7.3 分類 B: 呼び出し地点は種類が違う

呼び出しは「退役して止まる」ではなく「呼び先のフレームを積んで、呼び元は待つ」である。
ここで確認したことが2つある。

**(1) 呼び元の再開 PC は上流が既に書いている。**

```c
call_argc = get_u16(pc);
pc += 2;
call_argv = sp - call_argc;
sf->cur_pc = pc;                              // ← 呼び出しの直前に保存済み
ret_val = JS_CallInternal(ctx, call_argv[-1], ...);   // quickjs.c:18684-18689
```

`sf->cur_pc` は**呼び出し命令の次**を指す。今はバックトレース用だが、これがそのまま
呼び元の再開 PC になる。**この点は変更が要らない。**

**(2) 復帰後の後始末は `cur_pc` から復元できない。** 呼び出しが戻ってからやることは

```c
for (i = -1; i < call_argc; i++) JS_FreeValue(ctx, call_argv[i]);
sp -= call_argc + 1;                          // call_constructor は +2
*sp++ = ret_val;
```

で、**`call_argc` と「どの呼び出し命令だったか」に依存する**。ところが `cur_pc` は既に
オペランドを通り過ぎており、しかも `OP_call0`〜`OP_call3` はオペランドを持たない
（`call_argc = opcode - OP_call0`）ので命令長すら一定でない。**`cur_pc` から逆算できない。**

呼び先の `sf->arg_count` で代用することもできない。`quickjs.c:18281` は `sf->arg_count = argc`
を書くが、**`:18295` が `sf->arg_count = b->arg_count` で上書きする** — 宣言された引数より
少なく渡されたとき（または `JS_CALL_FLAG_COPY_ARGV`）に、実際の `call_argc` ではなく
宣言側の個数になる。**呼び元が捨てるべきスロット数は、呼び先の `arg_count` とは別物である。**

→ **決定: 復帰の形（捨てるスロット数と tail かどうか）をフレームに明示的に持たせる。**
これは仕様 §7 の「フレームの保持内容」が挙げている**「復帰先」**そのもの。
`call_argc` は `get_u16` なので16ビット、形の区別に2ビットあれば足りるので、
§5.1 の **offset 44-47 の隙間（4バイト）に入る**。L2b では呼び出しごとに必ず要るので、
「全フレームが常に必要とするもの」の条件（§5.3-5）を満たす。

**(3) 「call を飛ばさない」を何が保証するか。** 呼び元の `cur_pc` は呼び出しの**次**を指すので、
`cur_pc` だけを見ると「呼び出しは済んだ」と「これから呼ぶ」が区別できない。
**区別するのはフレーム鎖であって PC ではない** — 呼び先のフレームが存在すれば呼び出しは実行中、
存在しなければ `cur_pc` は素直に「次を実行せよ」を意味する。**セーフポイントを
「呼び先フレームを積んだ後」にだけ置き、「積む前」には置かない。** これで仕様の
「未実行の call を飛ばさない」が構造的に保証される。

### 7.4 分類 C: 置かない場所

§2 の N1〜N5（正規表現、ネイティブ完結、`for-in` の1ステップ、パース、関数プロローグ）。
中断禁止区間として明示し、G5 がその最長を測る。

### 7.5 分類 D: 既に離脱経路を持つもの

`return` 系と `await` / `yield` / `yield_star` 系は `done` / `done_generator` を通って
フレームを離れる。§4.2 のとおり `done_generator` が L2 の YIELD と同じ形なので、
ここは新しい契約を作らず既存に合わせる。

### 7.6 まとめ

| 分類 | 地点 | `cur_pc` の意味 | 追加で保存するもの |
| --- | --- | --- | --- |
| A | `goto`×3、`if_*`×4（既存の7地点） | 次に実行する命令 | 無し |
| B | 呼び出し（呼び先フレームを積んだ後） | 呼び出し命令の次 | 復帰の形（捨てるスロット数・tail 種別）。§5.1 の 44-47 へ |
| C | N1〜N5 | — | 置かない |
| D | `return` / `await` / `yield` 系 | 既存の `done` / `done_generator` に従う | 無し |

起案時はこう書いていた — 「ループは必ず後方分岐を通るので、A の7地点だけで L2 の目的は
達成される。B は L2b が C 再帰を消すために必要で、中断のためではない。L2c で新しく置く
セーフポイントは 0 個になる可能性がある」。**測ったら違った。**

**A の7地点だけでは足りない（実測(host)、2026-09-13）。** G5（`vmrun --profile host --gaps`、
`corpus/g5_gaps.js`）で連続する停止機会の間隔を測ると、**JS を走らせ続けているのに7地点を
一度も通らない区間が実在する**:

| 始点 | 区間長（o2、実測） | 何が起きているか |
| --- | --- | --- |
| `n4_direct_eval` | 15.5 ms | N4。パースと直線実行 |
| `n2_native_sort_callback` | **10.3 ms** | **JS 比較関数付きの `sort`。比較関数は毎回呼ばれるが分岐を持たないので、7地点を1つも通らない** |
| `n2_native_json` | 9.9 ms | N2。`JSON.stringify` |

`sort` の行が答えになっている。呼び出しのプロローグは中断**確認**の地点だが**停止機会ではない**
（`JS_CallInternal` 入口の `js_poll_interrupts` は A の7地点に含まれない）。つまり **分類 B
（呼び出し地点）は、C 再帰の解消のためだけでなく、中断のためにも要る。**

この訂正は「7地点で足りるかは測って決める」と書いておいたから出てきたもので、
書かずに進んでいれば L2c で「なぜか止まらない場合がある」として現れていた。

## 8. L2a の着地（2026-09-13）

実装は `components/quickjs-ng/quickjs-ng/quickjs-vmstack.h`（ヘッダオンリー）と `quickjs.c` の
差分。`CONFIG_POCKET_VM_SEGFRAMES`（実機）/ `-alloca` バリアント（ホスト）で旧経路へ戻せる。

### 8.1 何が動いたか（実測(host)、統合後に再走）

| 関所 | 新経路（segframes） | 旧経路（alloca） |
| --- | --- | --- |
| `run.sh` asan / o2 | 43/43 / 43/43 | 43/43 / 43/43 |
| G1 `bytes_per_call` | **528.000** | **672.000** |
| `run.sh --force-yield` | 3 pass / 40 fail | 3 pass / 40 fail |
| Test262 | 7,501 / 194 / regressions 0 | 同左 |
| G6 `verify_all.sh` | exit 0 | — |
| ファーム DIRAM / flash | **115,468**（不変）/ 1,554,032 | 115,468 / 1,553,648 |

**旧経路が 672.000 を正確に再現することが、仕様 §12 の「戻せる」の実証になっている。**
差 144 B/段が C スタックから出た分（ホストの `sizeof(JSStackFrame)` 72 + alloca 64 を
16 に丸めた値と一致）。`verdict` は両方 PROPORTIONAL で、これは L2a では正しい
（C 再帰が消えるのは L2b）。

`--force-yield` が 3/34 → 3/40 になったのは、新しく入れたコーパス6件がすべて後方分岐を
持つため。旧経路でも同じ 3/40 なので、L2a が変えたものではない。

### 8.2 メモリは純増する

仕様 §7 は「固定プール化だけで省メモリになるとは主張しない」「固定プールの予約量、プール管理領域、
セグメント内の未使用量を RAM 使用量へ含める」と要求している。**増えた:**

- **常駐セグメント1本**（ホスト実測 4,143 B = 4096 + ヘッダ32 + 整列15。実機は計算値 4,127 B）。
  最初の呼び出しから `JS_FreeRuntime` まで居座る。深さが境界を跨げば +1 本キャッシュ。
- `JSRuntime` に `JSVMStack` が +20 B（実機、計算値）。
- 内部余白は `resident_max − live_max` で、浅いファイルでは常駐1本のほぼ全部（3.5〜4.0 KiB）。
- **減ったのは C スタックだけ**（144 B/段）。ui タスクのスタックは静的確保なので、
  **この減少が RAM として戻るのは L2b で C 再帰が消えてから。**
- 静的 DIRAM は不変、flash +360 B。

### 8.3 直したもの、残した退行

**直した実バグ（Test262 が発見）:** pop の判定に `b->func_kind == JS_FUNC_NORMAL` を使っていたが、
`JS_FUNC_ASYNC` で組まれたバイトコード関数が通常経路で呼ばれて `done_generator:` に抜ける経路がある。
フレームが積まれたまま残り、`JS_FreeRuntime` の表明で abort していた
（`language/eval-code/direct/export.js` / `import.js`、regressions 2）。`flags` も opcode が
スクラッチに再代入するので鍵にできない。セグメントの生存範囲で判定する形に変えて解決。

**訂正（2026-09-13、H7 の実験。§10.1）:** 起案時は「モジュール内の直接 `eval`」と書いたが、**誤り**。
その経路は**モジュール本体の関数**である — `__JS_EvalInternal` がモジュールを `JS_FUNC_ASYNC` で組み
（`quickjs.c:38608-38611`、`m != NULL`）、`js_create_module_bytecode_function` が
`JS_CLASS_BYTECODE_FUNCTION` のオブジェクトにし、**`js_inner_module_linking` が hoisting 済み宣言の
初期化のために `JS_Call(ctx, m->func_obj, JS_TRUE, 0, NULL)`（`:31791`）で通常呼び出しする**。
評価本体は `js_async_function_call`（`:32360`）経由でヒープフレームなので通常経路を通らない。
直接 `eval` は `m == NULL` なので `JS_FUNC_NORMAL` で組まれ、この経路には乗らない。
2 件だけが落ちたのは、Test262 部分集合で `module` フラグを持つのがその 2 件だったからで、
`eval` は無関係。モジュール本体も `eval` も関数名アトムが `<eval>`（`JS_ATOM__eval_`）なので読み違えた。

**残した退行（承知のうえで入れた）:** `run.sh --trace`（asan）と `--vm-seg-size 2048`（o2）で
`gc_threshold_device.js` が落ちる。常駐セグメントがジワジワ型 OOM の「残り」を動かし、
catch した後の `print` 自体が OOM する。**期待値は書き換えていない**（仕様 §12「新たな失敗を
期待値の書き換えだけで処理しない」）。通常の `run.sh` 4 バリアントでは通る。詳細は
[tools/vmtest/README.md](../tools/vmtest/README.md) の既知の脆さの節。

### 8.4 満たしていない項目

- **完了条件6の後半「アロケータ比較で内部余白・外部断片化を分ける」は未実施。** 台帳07 の比較は
  汎用アロケータの確保履歴に対するもので、フレームセグメントについては内部余白しか出していない。
  外部断片化は測っていない。
- **標準セグメントサイズ 4096 はフレームの分布から決めたものではない**（台帳07 のオブジェクト
  分布由来）。仕様 §7 は「L0 の使用量分布から決める」と要求している。コーパス43件中37件は
  深さ38以下でセグメント1本に収まる、という観察はあるが、根拠としては弱い。
- **実機で1度も走らせていない。** D7 の「4バイト整列の `uint64_t` スロット」はコンパイルが
  通っただけで、実行は未確認。

## 9. L2b に入る前に決めたこと（2026-09-13）

L2b の実装前に、生徒役（sonnet）が L2b の実装手順を説明し、教師役（fable）が問い詰める
往復を3回行って、仕様と設計が決めていない箇所を洗い出した。13件のうち「実装を止める」が4件。
うち1件（G1 の判定）はその場で直した（[commit 3c5ea59](../tools/vmtest/stack_probe.sh)）。
残り3件をここで決める。

**この作業で確認できたこと**: 疑われた11項目は仕様・設計が既に決めていた（復帰の形の 44-47、
`caller_ctx` の 4-7、`new_target` を保存しない根拠、セーフポイントをフレーム鎖で保証すること、
`JSValue` を触らないこと等）。穴は13件で、半分ではない。

### D10: 無限再帰を止めるのは、フレーム数ではなくセグメントのバイト予算

L2b の後、`js_check_stack_overflow`（`quickjs.c:2874-2885`）が見ている C スタック残量は
深さに応じて減らなくなる。**無限再帰を止めるものが無くなる。** 仕様はこの資源について何も
言っていないので、ここで決める。

**決定: VM セグメントスタックの総バイト数で切る。フレーム数では切らない。**

- フレーム 1 個の大きさは `sizeof(JSStackFrame) + alloca_size` で、関数のローカル数と
  オペランドスタック深さによって桁で変わる。**フレーム数はメモリを少しも束縛しない。**
  仕様 §7 が「固定プールの予約量、プール管理領域、セグメント内の未使用量を RAM 使用量へ含める」
  と要求している以上、束縛すべき量はバイトである。
- この機体の制約は深さではなくメモリ（DRAM 約 334 KiB、ゲスト上限 160 KiB）。

**エラーの種別は2つを分ける。** 既存の期待値がその両方を固定しているため:

| 起きたこと | 報告 | 固定している期待値 |
| --- | --- | --- |
| **予算**を使い切った（深い再帰） | `RangeError: Maximum call stack size exceeded` | `expected/deep_recursion.txt`、`expected/deep_recursion_device.txt` |
| **ヒープ**がセグメントを渡せなかった | `InternalError: out of memory` | `expected/seg_oom_boundary.txt` |

→ **予算はヒープが尽きるより先に当たらなければならない。** そうでないと2つが区別できなくなる。
これは機構だけでなく**値に対する制約**である。値は測ってから決める（`deep_recursion.txt` は
ホストで深さ 1000 超を要求し、device 版は「どこかで overflow すること」しか要求していない）。

**knob は既存の `JS_SetMaxStackSize` / `rt->stack_size` を読み替える。** 単位（バイト）も API も
変えず、対象だけが C スタックから VM セグメントに変わる。L2b 後、この knob が C スタックを
指したままでは意味を持たないため。**帰結として、ホストの `--stack-limit` と実機の
`app_session.c` の `stack_limit=20*1024` の値は選び直しになり、実機側はメモリ予算の決定になる。**

**順序:** ガードはフラット化より**前**に入れる。後回しにすると最初のフラット化コミットで
`deep_recursion.txt` が `InternalError` に変わり、仕様 §12「新たな失敗を期待値の書き換えだけで
処理しない」と衝突する。

**なぜビット数（占有ビットマップの popcount）で数えないのか。** 検討したが採らない。
次に見た人が同じ発想をするはずなので理由を残す。

- **セグメントスタックはバンプアロケータで、ビットマップを持たない。** `quickjs-vmstack.h:22`
  のとおり push は `top += size`、pop は `top = block`（`:251`、`:277`）。使用量は各セグメントの
  `top - base` の和で、**O(1) かつ正確**。数えるべき値が既にタダで手に入っている。
- **QuickJS も既にバイトを正確に持っている。** `JSMallocState.malloc_size` / `malloc_limit` /
  `malloc_count`（`quickjs.h:596-597`）。ゲストは `heap_used = usage.malloc_size`
  （`guest.c:620`）として読んでおり、`VMPROBE` の `js_used_max` はこれ。
- **TLSF のビットマップは占有マップではない。** ESP-IDF の `tlsf.c:69-71` で `fl_bitmap` /
  `sl_bitmap` は**サイズクラスごとに1ビット**（`sizeof(*sl_bitmap) * fl_index_count`）で、
  「どの空きリストが空でないか」を表す。ブロック1個に1ビットではないので、popcount しても
  出るのは「空でないサイズクラスの数」であって使用バイト数ではない。
- **決め手はホットパスであること。** 予算の判定は呼び出しのたびに走る。`top - base` は減算1回。
  ビットマップの走査はどれだけ速くてもワード単位のループになる。

ただし仕様 §7 がアロケータ候補に挙げている **estalloc は「サイズ別リストとビットマップ」方式**で、
そちらは占有ビットマップを持つ。将来セグメント**内部**の詰め方をそれにするなら、その層では
ビット数が自然な数え方になる。**予算（この呼び出し連鎖が何バイト積んだか）とは別の層である。**

### D11: 呼び出し元へ戻った後の `argc` は、フレームに既にある場所へ真の値を置く

フラット化すると、呼び出し元のディスパッチループの C ローカル `argc` / `argv` を復元する必要が
ある（`OP_rest` が本文中で読む。`function f(a = g(), ...r){}` は `g()` から戻った後に読む）。
`argv` は `sf->arg_buf` から取れる。問題は `argc` で、`sf->arg_count` は `quickjs.c:18492` で
真の `argc` を書いた後、**`:18508` が `b->arg_count` で上書きする**（引数が宣言より少ないとき）。

**確認した事実: `JSStackFrame.arg_count` は vendored ツリー全体で一度も読まれていない**
（書き手は `:6644`・`:6775`・`:18187`・`:18199`・`:18492`・`:18508`・`:21369` の7箇所、読み手は 0。
`b->arg_count` / `fd->arg_count` / `bc.arg_count` はいずれも別の構造体）。

**決定: `:18508` の上書きをやめ、`sf->arg_count` に真の `argc` を残す。** 詰められた個数が要る
箇所は `b->arg_count` を `cur_func` 経由で引けばよい。**新しい記憶域は要らず、`JSStackFrame` は
48 バイトのまま。** D2 が隙間を使い切っていることは制約にならなかった。

### D12: L2b がフレームごとに要るものは、セグメントのブロックに置く

呼び出し元の `sp`（子が走る間の退避先）は復元できない — 実行によって決まる量で、
`prev_frame` からも `arg_buf` からも引けない。`JSStackFrame` の隙間は D2 と D8 で使い切っている。

**決定: セグメントの push が確保するブロック（今は `sizeof(JSStackFrame) + alloca_size`）を
広げ、そこに置く。`JSStackFrame` の定義は変えない。**

§5.3-5 が定めた規則そのままである — **隙間は「全フレームが常に必要とするもの」、
それ以外は包む側へ**。`sp` の退避が要るのはセグメントに積まれたフレームだけで、
`js_call_c_function` 系の4つの呼び出し規約が持つ `sf_s`（素の C 自動変数）は払わなくてよい。
`JSStackFrame` を太らせると、L2b が触らない3つの規約にも代金がかかる（§5.3-1）。

**`cur_sp` を呼び出し元の `sp` の退避先に流用しない。** `async_func_mark`（`:21396-21403`）と
`async_func_free`（`:21421`）が `cur_sp != NULL` を「中断中」の証明に使っており、流用すると
generator の床が子を呼んでいる間に GC が回ったとき、実行中のフレームを中断中と誤認して
子のオペランドスタックの途中までを mark する（§6.1 の UAF 側）。D4 が決めた専用ビット
（offset 37-39）への差し替えは L2b が負う。

### 9.1 まだ決めていないこと（起案時。**すべて §10 で決着**）

- **予算の値**（ホスト・実機）。**窓が存在することは確認した**（下記 §9.2）。具体値は
  ガードの実装時に、その実装自身で測って決める。→ §9.3（出荷値を据え置き）。
- L2b のビルド時スイッチと、`alloca / segframes+再帰 / segframes+フラット` の3経路の検証行列（H5）。→ §10.2。
- 床（1回の C 活性で最初に積んだフレーム）の判定方法と、`done`/`done_generator` の鍵を
  `func_kind` から実行時フラグへ置き換える時期（H6）。→ §10.3。
- legacy constructor の一時 `obj` の置き場、または `OP_call_constructor` を L2b 対象外とする明示（H8）。→ §10.4。
- ネイティブ再入深さを runtime のフィールドにするのは L2b か L2c か（H9）。→ §10.3。
- §8.3 に記録した「BYTECODE_FUNCTION で非 NORMAL が通常経路で push された」経路は、
  コードからの再現ができていない（H7）。記録が正しいかを確かめる実験が要る。→ §10.1。

### 9.2 予算の窓は存在する（実測(host)、2026-09-13）

D10 を実装する前に確かめるべきだったのは「3つの期待値を1バイトも変えずに通る予算値が
そもそも在るか」。**在る。しかも狭くない。**

フレーム1個の大きさは、式が実測と一致する:

```
alloca_size = sizeof(JSValue) * (arg_allocated_size + var_count + stack_size)
            + sizeof(JSVarRef *) * var_ref_count
frame_total = round_up(sizeof(JSStackFrame) + alloca_size, JS_VM_FRAME_ALIGN)
```

`sizeof(JSStackFrame)` はホスト 72 / 実機 48（実機側はクロスコンパイルで確認。§3.1 の
実測と一致する）。`arg_allocated_size` は**宣言どおりの数で呼べば 0** で、引数が足りない
呼び出しのときだけ `b->arg_count` になる。つまり同じ関数でも呼び方でフレームの大きさが変わる。
**フレーム数で予算を切れない理由（D10）が、ここでも数字として出ている。**

| | 下限（これより大きくないと期待値が壊れる） | 上限 | 窓 |
| --- | --- | --- | --- |
| host | 約 0.1 MB（`deep_recursion.txt` の `depth>1000`） | 64 MiB のヒープ | **3桁の余裕** |
| 実機 | 約 480 B（`seg_oom_boundary` の大確保の時点） | ゲスト上限 160 KiB より小さいこと | **2桁以上の余裕** |

実機側は、既存の `stack_limit = 20 * 1024`（`app_session.c:391`）をそのまま予算に読み替えても
成立する見込み — `dive()` 型のフレーム（実機 72 B）なら 20 KiB は約 284 段で、
160 KiB の 1/8 で当たる。**予算がヒープより先に当たる**という D10 の要求を満たす。

**この表の下限は桁の目安であって、確定値ではない。** 1フレームあたりのバイト数は走行条件で
104 〜 120 B の幅があり（`--stack-limit` を変えた2回の走行で一致しなかった）、報告が主張する
「1バイト単位で一致」の精度は出ていない。**窓が3桁あるので判断は変わらないが、値を決めるときは
ガードの実装自身で測り直すこと。**

**未計測（実機）:** アプリ起動後に 160 KiB のうちどれだけ既に使われているか。ここでの数字は
`vmrun` の最小ハーネス基準で、実機の実効ヘッドルームは `tools/memlog.py --port --check` が要る。
実機の TLSF がセグメント1本に付けるブロックヘッダと断片化の分も未検証。

### 9.3 D10 の着地（2026-09-13、`vm/l2b`）

実装は `quickjs-vmstack.h` の `JSVMStack.used` / `budget` と `js_vm_stack_over_budget()`、
`quickjs.c` の push 直前の判定、`JS_SetMaxStackSize` での `rt->vm_stack.budget = rt->stack_size`
（`CONFIG_POCKET_VM_SEGFRAMES` のときだけ）。ホストの `vmrun` に `--vm-budget` を足し、
C スタックのガードと予算を**別々に**動かせるようにした。

**出荷値は変えていない。** host 7 MiB（`--profile host`）、実機 `stack_limit = 20 * 1024`
（`app_session.c`）。どちらも §9.2 の窓の中にある。

**run.sh だけでは検証にならない。** C 再帰が残っている間は、同じ値を持つ C スタックのガードが
先に答える（`budget_hits=0`）。**何もしない予算でも run.sh は通る。** そのまま L2b で C 再帰を
消せば、コーパスの `RangeError` がすべて `InternalError` に変わっていたはず。

そこで `tools/vmtest/budget_probe.sh` が、`--stack-limit 512M` で C スタックのガードを退け
`--vm-budget` だけを残した走行（= L2b 後の状況）で、期待値3本を検査する。
**陰性対照を4つ持つ** — 予算 off（ヒープが答え `seg_refused=1`）、小さすぎる予算（host 100K で
`depth>1000` を満たせない）、ヒープより先に当たりすぎる予算（480 B で `seg_oom_boundary` の
`InternalError` が `RangeError` に化ける）、ヒープを超える予算（200K でヒープが先に尽きる）。
**窓の外の値ではちゃんと壊れる**ことが、ガードが本物である証拠。

実測（o2）: 10 項目すべて OK。予算だけを残した走行で host は深さ 70,575、実機プロファイルは
深さ 195 で `RangeError`、`seg_oom_boundary` は `InternalError` のまま。
asan でも 10 項目すべて OK（asan は ulimit を上げないので host の予算を 512K にして深さ 5,039 で
`RangeError`。`depth>1000` は満たす）。

関所: コーパス 43/43（asan・o2・asan-alloca・o2-alloca）、Test262 7,501 / 194 / regressions 0、
G1 は 528.000（segframes）/ 672.000（alloca）でともに PROPORTIONAL（C 再帰は残っているので正しい）、
selftest ok、`--force-yield` 3/40 不変、期待値ファイル無変更。

**未計測:** 呼び出しごとに加算1回と比較1回が増えた分の速度（`timing.py` は未実行。
L2b のフラット化で経路自体が変わるので、そちらと合わせて測る）。ファームのビルドは本線への統合時。

## 10. L2b の着地（2026-09-13、`vm/l2b`）

実装は `quickjs.c` の `JS_CallInternal`（`flat_call:` ブロック、`frame_pushed:` 共有プロローグ、
末尾の `JS_SF_FLAT` 復帰）と `quickjs-vmstack.h`（`JSVMLink`、`JS_SF_*`、`JS_RET_*`）。
スイッチは `CONFIG_POCKET_VM_FLATCALLS`（`depends on POCKET_VM_SEGFRAMES`）。
**対象は `OP_call` / `OP_call0`〜`3` / `OP_call_method` / `OP_tail_call` / `OP_tail_call_method` で、
呼び先が `JS_CLASS_BYTECODE_FUNCTION` かつ `func_kind == JS_FUNC_NORMAL` のとき**（`js_vm_flat_callable`）。
それ以外はすべて従来の C 呼び出しのまま（§10.4）。

呼び出し: 中断ポーリング → D10 の予算判定 → `[JSVMLink][JSStackFrame][slots][var_refs]` を push →
呼び出し元の `sp` を link に、復帰の形を `ret_shape` に、`ctx` を `caller_ctx` に書く → ループの
C ローカルを呼び先のものに差し替えて `frame_pushed:` へ。**押せなかった場合（予算・ヒープ）は
何も積まずに呼び出し元へ throw** — 上流の `if (JS_IsException(ret_val)) goto exception` と同じ場所に落ちる。
復帰: `done:`（または捕捉されなかった `exception:`）の後、`sf->l2_flags & JS_SF_FLAT` なら
link を読んでからブロックを pop し、`sf->prev_frame` から呼び出し元のローカルを組み直して、
例外なら `goto exception`、tail なら `goto done`、それ以外は上流と同じスロット整理をして `goto restart`。

### 10.1 H7: 記録は「機構は正しく、主語が誤り」

`sf->prev_frame` 設定直後に `b->func_kind != JS_FUNC_NORMAL` で abort する実験を置き（コードは戻した）、
4 入力を走らせた（実測(host)、`-O1`、segframes）:

| 入力 | 結果 |
| --- | --- |
| 通常スクリプト内の直接 `eval` | 発火せず |
| generator / async を含むスクリプト | 発火せず（別クラスの class call 経由） |
| モジュール `export const x = 1` | **発火**: `func=<eval> kind=2(ASYNC) this_tag=1(BOOL) flags=2(COPY_ARGV) prev_frame=no` |
| 直接 `eval` を含むモジュール | 同上、**リンク時点**で発火（`eval` に到達する前） |

`this = true`・`flags = COPY_ARGV`・最外フレームは `js_inner_module_linking` の
`JS_Call(ctx, m->func_obj, JS_TRUE, 0, NULL)` と一致する。§8.3 の訂正参照。

**床の判定を `func_kind` に頼れるか**: 頼らない。フラットで積むフレームは `js_vm_flat_callable` が
`JS_FUNC_NORMAL` を要求するので、**フラットフレームが `done_generator:` に入ることは構造的に無い**。
非 NORMAL がセグメントに積まれるのはこのモジュール本体（床）だけで、その場合の pop は
L2a と同じ `js_vm_stack_holds()` が担う。`done`/`done_generator` の鍵は上流のまま `b->func_kind`。

### 10.2 H5: 3 経路の行列

| 経路 | `build.sh` | Kconfig | 何が違うか |
| --- | --- | --- | --- |
| alloca | `asan-alloca` / `o2-alloca` | `SEGFRAMES=n` | L2a 以前。C スタックにフレーム |
| segframes 再帰 | `asan-recur` / `o2-recur` | `SEGFRAMES=y, FLATCALLS=n` | L2a。C 再帰は残る |
| segframes フラット | `asan-flat` / `o2-flat` | `SEGFRAMES=y, FLATCALLS=y` | L2b |
| **無印 `asan` / `o2`** | | **Kconfig の既定を写す**（今は = フラット、§10.5） | 無印の関所 = 出荷経路の関所 |

`run.sh --variant` / `test262.py --variant` / `stack_probe.sh N V` / `budget_probe.sh V` は
6 つの名前をそのまま受ける。`budget_probe.sh` は最初の 3 項目の期待（どちらのガードが答えるか）を
バイナリの `#info vmstack flat=` から決める — 名前ではなく実体で。

### 10.3 H6・H9: 床の判定と、ネイティブ再入の床

**H6 — 床は `JSStackFrame.l2_flags` の 1 ビットで判定する（offset 37、D2 の隙間）。**
`JS_SF_SEG`（セグメントに積んだ）と `JS_SF_FLAT`（フラット呼び出しで積んだ）の 2 ビット。
C から入った床は `SEG` のみ、generator/async の床は両方 0（`js_mallocz` 由来）、フラットフレームは両方。
復帰は `FLAT` の 1 ビット比較で「C へ return か、呼び出し元を再開か」を分ける。
`local_buf` の復元は `SEG` で分ける（generator の床は `local_buf == arg_buf`、再開入口と同じ）。
セグメント範囲検査（L2a の `js_vm_stack_holds`）は残してある: 床の pop はそれで決まる。

**H9 — ネイティブ再入は新しい C 活性 = 新しい床。** 組み込みが `JS_Call` で JS に戻るたびに
`JS_CallInternal` の新しい活性が始まり、その最初のフレームが床になる。**深さを数える runtime
フィールドは L2b では足さない**: 床の入口には L2a と同じ `js_check_stack_overflow(rt, 0)` が残っており、
これが「ネイティブ再入の深さ」を C スタック残量として直接測っている
（`deep_recursion_device.js` の `through-map` が `RangeError` のまま通ることがその検査）。
L2c が「ネイティブが同期の戻り値を待つ区間ではホストに戻らない」を実装するとき、床の持ち主
（どの C 活性が中断を許すか）はこの活性ごとの C ローカル（`floor_argc` / `floor_argv` / `floor_this` /
`floor_new_target`）と同じ場所に置くのが自然で、そこで数える。

**床の持ち物（C 活性ごとに 4 スロット、JS の深さには比例しない）:** 入口引数の `argc` / `argv` /
`this` / `new.target`。フラットフレームには要らない — `argc` は D11 どおり `arg_count`、`argv` は
自分の link の `caller_sp - arg_count`、`this` は `ret_shape` が method なら func スロットの下、
`new.target` は常に undefined。

**訂正（L2b の敵対的レビューで発見）:** 最初の版は床の持ち物を 3 つとし、床へ戻るときの `argc` を
`sf->arg_count` から組み直していた。**C から入った床ならそれで正しい**（D11 で真の `argc` を残して
いる）が、**generator / async の床のフレームは `JSAsyncFunctionState.frame` で、その `arg_count` は
`async_func_init` が書く `arg_buf_len = max(宣言数, 渡した数)`** であり、`async_func_resume` が
入口で渡す `s->argc` とは違う。デフォルト引数の初期化子でフラット呼び出しをした後に `OP_rest` が
`argc` を読むので、`function* g(a = h(), ...r)` を引数なしで呼ぶと、フラット経路だけ `r` が
`[undefined]` になっていた（再帰・alloca は `[]`）。`floor_argc` を 4 つ目として退避して直し、
`corpus/l2b_floor_argc.js`（generator / async / async generator × 引数の過不足）で固定した。
**L2c が床の状態を保存するときも、この 4 つが床の持ち物である。**
D11 の「`argv` は `sf->arg_buf`」「`argc` は `sf->arg_count`」は、**フラットフレームについてだけ**成り立つ。

### 10.4 H8 と、囲った経路（従来の同期呼び出し・中断禁止）

- **`OP_call_constructor` は対象外**（H8）。legacy constructor は `JS_CallConstructorInternal` が
  `js_create_from_ctor` で作った `obj` を呼び出しの外で保持し、戻り値がオブジェクトでなければ
  それを返す。その `obj` の置き場を L2b では作らない。派生クラスも同じ入口なので同様。
- `OP_apply` / `OP_apply_eval` / `OP_eval`（間接・直接とも）/ `OP_init_ctor`（`super()` の暗黙形）。
- 呼び先が非バイトコード（native / bound / Proxy / Promise の resolve 関数）と、
  generator / async / async generator（別クラス）、モジュール本体（§10.1）。
- ネイティブから JS への再入すべて（getter / setter / Proxy trap / `sort` の比較関数 / …）。
  台帳01 §10.1 のとおり列挙可能ではないので、「新しい C 活性 = 床」で機械的に扱う（§10.3）。

これらは仕様 §7 の「未対応経路は従来の同期呼び出しとして囲い、中断禁止を明示」に当たる。
中断禁止は今のところ暗黙（L2c まで中断そのものが無い）で、L2c は床ごとに明示する。

### 10.5 D11 の補足、費用、既定 on の理由

**D11 の「`argv` は `sf->arg_buf`」は床では成り立たない。** `JS_Call`（`COPY_ARGV`）で宣言より多い引数を
渡された床は `arg_buf` が `b->arg_count` 個しか無く、`OP_rest` / `arguments` は `argv` の
`argc` 個を読む（`corpus/l2b_flat_calls.js` の `from-native-more-args` がこれを固定する）。
だから床の `argv` は C ローカルに退避し（§10.3）、フラットフレームだけが link から引く。
`sf->arg_count` に真の `argc` を残す決定はそのまま（FLATCALLS ビルドのみ。他は上流の行を残して
バイト一致を保つ）。

**費用（計算値、実機）:** フレームごとに link 4 B（ホスト 8 B）。`JSStackFrame` は **48 B のまま** —
`caller_ctx`(4-7)・`l2_flags`(37)・`ret_shape`(44-47) は隙間に入った。**実機コンパイラで確認**
（`xtensa-esp-elf-gcc 15.2.0`、`quickjs.c` を include した TU の `_Static_assert` が通り、
`FLATCALLS` を外すと同じ TU が 9 件失敗する = 表明が生きている）。C 活性ごとに 3 スロット。
フラットビルドの C フレーム自体の大きさは未計測（G1 は段あたりの差分しか出さない）。

**実測(host)、`8833514`〜:**

| 関所 | フラット | segframes 再帰 | alloca |
| --- | --- | --- | --- |
| G1 `bytes_per_call`（2000 / 4000） | **0.000 / 0.000 NOT_PROPORTIONAL**、selftest ok | 528.000 PROPORTIONAL | 672.000 PROPORTIONAL |
| `budget_probe.sh`（o2・asan） | 10/10、**出荷値で `budget_hits=1〜2`**（host depth 57,342、device 158） | 10/10、`budget_hits=0` | 予算なし |
| コーパス（asan・o2） | 44/44 | 44/44 | 44/44 |
| Test262 | 7,501 / 194 / regressions 0 | 同左 | 同左 |
| `--force-yield` | 3 / 41（`l2b_flat_calls.js` の +1 は後方分岐を持つため） | 同左、**出力 43 件バイト一致・safepoint 数一致** | — |
| G6 `verify_all.sh` | exit 0 | | |

「出荷値で `budget_hits` が 0 でなくなる」が、ガードを先に入れた意味の実証（§9.3 の予告どおり）。
`seg_oom_boundary` は `InternalError` のまま。

**既定 on にした。** 理由: (1) 上の関所がすべて通り、3 経路とも期待値無変更。(2) `stack_limit = 20 KiB`
（`app_session.c`）が L2a では「C スタックの残量」と「予算」の二重の意味だったのが、フラットでは
JS の深さに対して予算だけが答える — §9.2 の窓の中で、ヒープより先に当たる。(3) 戻す手段は
`CONFIG_POCKET_VM_FLATCALLS=n` の 1 行（`-recur` 変種が同じものを検査している）。
**実機では走らせていない**（L2a と同じく §8.4）。

**未計測:** 速度（`timing.py` 未実行。呼び出しごとの経路が変わったので L2a 分と合わせて要計測）、
フラットビルドの `JS_CallInternal` の C フレーム絶対値、実機の段数と DIRAM。

### 10.6 L2c への引き継ぎ

- セーフポイント B（呼び出し地点）は `frame_pushed:` の**後**に置く。`flat_call:` のポーリングから
  `frame_pushed:` までに止まれる地点は無い（D8 §7.3-3 の保証はコードの順序として実装済み）。
- 中断中の目印（D4）は `l2_flags` の空きビット（offset 37 の残り 6 ビット）へ。
- 床の `floor_*` ローカルは C 活性に属する。中断・再開でその活性が消えるなら、床ごとに
  保存が要るのは**床の持ち物 4 つ（`floor_argc` / `floor_argv` / `floor_this` / `floor_new_target`、§10.3）**と
  `caller_ctx`（既にフレームにある）。最初は「3 つ」と書いていたが、`argc` が抜けていた（§10.3 の訂正）。
- `JS_SF_FLAT` の復帰は `ret_val` を C の変数で運ぶ。再開側が同じ場所に値を置けば、
  「子から戻ったところから再開」はこのブロックをそのまま通る。

## 11. L2c に入る前の穴（2026-09-13）

L2b と同じく、実装前に生徒役（sonnet）が L2c の実装手順を説明し、教師役（fable）が問い詰める往復を
3回行った。**結論: 今の仕様と設計では着手できない。** ただし設計のやり直しではなく決定の不足。

**核心:** 設計が決めたのは中断の**形**（D1 返り値で戻る・確保しない、D4 所有者と専用ビット、D8 B 地点は
push の後）で、**誰が中断を受け取り、誰が再開を呼ぶか**が1か所も決まっていない。`JS_CallInternal` の
返り値を受ける C 関数（`JS_CallFree`、`JS_ExecutePendingJob`、`promise_reaction_job`、
`pocketjs_guest_frame`、`js_async_function_resume`、`js_generator_next`、`js_async_generator_resume_next`）は
どれも `JS_IsException` の2値で後始末を続ける。

| # | 穴 | 重さ | 決める人 |

**対照:** 疑われた13項目は既に決まっていた（D1・D3・D4・D8・D9、GC 閾値修正の順序 §6.3、
破棄の慣習、床の持ち物の**個数**、TERMINATE が finally を飛ばすのは L2 で直さないこと 等）。
依頼者が渡した既知の穴3つのうち、GC 閾値の順序は §6.3 で決まっていて穴ではなかった。

**教師が推奨した順序（L2b と同じ「関所 → ガード → 本体」、今回は関所が最も重い）:**

1. **決定**: H1/H2/H3/K1 を1つの決定として、止まってよい床の集合を列挙する。最小集合は
   「`JS_Eval` のトップレベル script、ホストの `JS_Call(frame)`、`promise_reaction_job` の handler 呼び出し」。
   generator/async 床・class call・ネイティブ再入は囲った経路（止まらない）。**この最小集合だと
   `async function frame()` の本体は止められない**（ユーザー判断）。
2. **関所（H9）**: `vmrun` の4つの受け口に「YIELDED なら同じ単位を呼び直す」ループを入れ、
   正の証拠（`safepoints>0` のファイルは `stops>0` かつ `resumes == stops`）を契約にする。VM を触る前に、
   赤い理由が「止まって死ぬ」から「止まって再開できない」に変わることを確認する。
3. **ガード**: 中断状態で GC を強制する変種、中断中の `JS_FreeRuntime`、中断鎖の上に別の `JS_Call` を
   積むケース。G5 の定義（H10）もここで決める。
4. **本体**: A 地点の `yield:` と再開入口 → B 地点（フラット push 直後のみ）→ GC 所有者と床の持ち物
   ブロック → 破棄（H12）→ TERMINATE（H13）。
5. **実機統合は別の段**: 要求の口と保持（H5）、3層の第3状態（H6）、累積時間ガード（H7）、FAIR（H8）、
   中断中の予算計測（H14）。

生徒が答えられなかった問いは13件（問答の記録は workflow `wf_4994cc8d-57d` の journal）。

### 12.2 L2b の拡張（D31）: JS から呼ぶ async 関数をフラットにする

初版 12.2 の末尾が認めていた欠け — 「JS から呼ばれた async 関数の最初の同期区間は止まらない」— を、L2b の対象を広げて埋める。**この節は L2c の yield と独立で、先に入れて先に検証する**（12.15 の段 A）。

**今の経路（事実）。** `OP_call` 系は `js_vm_flat_callable`（`:18384-18392`）が `class_id == JS_CLASS_BYTECODE_FUNCTION && func_kind == NORMAL` だけを通す。async 関数オブジェクトは `class_id == JS_CLASS_ASYNC_FUNCTION`（`:205` `/* u.func */`、`func_kind_to_class_id[JS_FUNC_ASYNC]` `:17984`）なので弾かれ、`JS_CallInternal(ctx, call_argv[-1], …)`（`:19045`）→ `:18520` の class 分岐 → `rt->class_array[JS_CLASS_ASYNC_FUNCTION].call = js_async_function_call`（`:57949`）。`js_async_function_call:22104-22141` は `js_mallocz(JSAsyncFunctionData)`（`:22111`、失敗なら `JS_EXCEPTION` `:22112-22114`、GC オブジェクト `:22116`）→ `JS_NewPromiseCapability`（`:22121`）→ `async_func_init`（`:22126`、ヒープ上に `arg_buf` `:21667`、`cur_func` を dup `:21671`、`this_val` `:21672`）→ `js_async_function_resume`（`:22134`）→ `async_func_resume`（`:21736`、C スタック検査 `:21740`）→ `JS_CallInternal(GENERATOR)`（`:21746`、**C 再帰**）。本体は最初の `OP_await`（`:21175-21177`）か `OP_return_async`（`:21185-21188`）で `done_generator:`（`:21350-21352`）を通って戻り、`js_async_function_resume` の後半（`:22029-22071`）が return なら `resolving_funcs[0]` を呼び、await なら `js_promise_resolve` + `perform_promise_then` で継続を登録する。最後に生成者の参照を落とし（`:22138`）、promise を返す（`:22140`）。

#### D32: 対象と判定

**決定: `js_vm_flat_callable` を「`JS_CLASS_BYTECODE_FUNCTION` かつ NORMAL」または「`JS_CLASS_ASYNC_FUNCTION`」に広げ、`flat_call:` の先頭で `np->class_id == JS_CLASS_ASYNC_FUNCTION` なら `flat_async_call:` へ分岐する。** 対象 opcode は L2b と同じ（`OP_call` / `call0`〜`3` / `call_method` / `tail_call` / `tail_call_method`、判定は `:19041` と `:19089`）。§10.1 の「モジュール本体は ASYNC にコンパイルされるが class は BYTECODE_FUNCTION」は、BYTECODE_FUNCTION 側の NORMAL 要求を残すので引き続き弾かれる。`OP_apply` / `.call` / `Reflect.apply` / `OP_call_constructor`（`:19061-`、flat 判定なし）/ bound / Proxy 経由の async 呼び出しは §10.4 の囲った経路のまま（C 再帰、保持）。`OP_tail_call` は `resolve_labels:36419-36431` が `OP_call` + `OP_return` の並びだけを変換するので async 本体（`OP_return_async`）には現れず、tail の分岐は呼び出し元が通常関数のときだけ。

#### D33: 押し方 — `flat_async_call:`（呼び出し元の状態で、確保はここで起きる）

- **(1) promise の置き場。** 上流は `js_async_function_call` の C ローカルに持つ（`:22108`）。フラットではその C フレームが無い。呼び出し元の func スロット（`call_argv[-1]`）は、`async_func_init` が `cur_func` を dup した（`:21671`）瞬間から呼び先には要らず、上流もそのスロットを戻り値の後に解放するだけ（`:19054-19055`）。だから**スロットの参照を promise に差し替える**。読み手の確認: 復帰の組み立て（`:21396-21405`）が読むのは `av[-2]`（`this`）で `av[-1]` ではない。バックトレースは `sf->cur_func`。GC は呼び出し元が SEG フレームなら D21r の walk で `local_buf..sp` を mark するので promise も 1 回 mark される（resolving 関数からの参照は別の実参照で、二重ではない）。**新しいフィールドは要らず、D9 にも触れない。**
- **(2) 呼び出し元の `sp`。** フラット SEG フレームは link（D12）に持つが、async フレームはセグメントに無く link が無い。`JSAsyncFunctionData` に `JSValue *flat_caller_sp` を足す。置き場は `is_active`（`:939`）の後ろ: 実機では `header` 16 B（`:438-446`、`int` + ビット列 4 B + `list_head` 8 B）+ `resolving_funcs[2]` 16 B + `is_active` 1 B で 33 B、`func_state` は先頭が `JSValue` なので 40 B 境界 — **33〜39 の 7 B の詰め物に 4 B ポインタが入る（計算値、実機 +0 B。`_Static_assert(sizeof(JSAsyncFunctionData) == 104)` で固定する）**。ホストは 8 B ポインタが詰め物に入らず +8 B（計算値）。generator / async generator の `JSAsyncFunctionState` は触らない。D2 の規則「中断フレームだけが要るものは包む側へ」そのもの。
- **(3) 費用。** 呼び出し 1 回あたり: 上流と同じ確保（`JSAsyncFunctionData`、promise + resolve 関数 2 つ、`arg_buf`）だけ。D35 を廃止したので予算の比較も加算も無い。**yield 時の確保はゼロのまま**（確保は呼び出し時であって D1 の道ではない。yield は 12.4 のとおり dup と store だけ）。
- **(4) `func_obj` の読み手（レビューで訂正）。** ディスパッチループ（`:18670-21240`）で C ローカル `func_obj` を読むのは `OP_init_ctor` の `super = JS_GetPrototype(ctx, func_obj)`（`:19166-19172`）の 1 箇所だけ（初版の「`OP_get_super`」は誤り）。`OP_init_ctor` は派生クラスのコンストラクタのプロローグにしか出ず、async 関数は `new` できないので到達しない。`nsf->cur_func` を入れておくのは backtrace と念のため。結論（スロットを promise に差し替えてよい）は変わらない。
- 呼び先の `sf->arg_count` は `arg_buf_len = max(宣言, 渡した数)`（`:21674`）で真の argc ではない — §10.3 の訂正と同じ。フラット async フレームの真の argc は `s->argc`（`:21673`）で、12.4 の再開もそれを読む。D11 は SEG フレームについての決定なので触れない。

#### D34: 戻り方 — 最初の await / return / 例外で呼び出し元へ promise を渡す

**決定: `done_generator:`（`:21350-21352`）の直後、`:21365` の `if (sf->l2_flags & JS_SF_FLAT)` の前に `if ((sf->l2_flags & (JS_SF_FLAT|JS_SF_SEG)) == JS_SF_FLAT) goto async_flat_return;` を置く。** 到達の仕方は 3 つで、上流の `js_async_function_resume` が受けていたのと同じ値が `ret_val` に入っている: `OP_await` → `js_int32(FUNC_RET_AWAIT)`、`OP_return_async` → `JS_UNDEFINED`、捕捉されなかった例外 → `JS_EXCEPTION`（`:21345`、`func_kind != NORMAL` `:21349` で `done_generator:` に落ちる）。

```
async_flat_return: {

    shape = sf->ret_shape;  csf = sf->prev_frame;  caller_sp = s->flat_caller_sp;
```

`resume_caller:` の後（上流の `:21414-21430` に当たる場所）で、呼び出し元が「async の戻り」を待っていたかを `shape` のビットではなく**戻ってきた側の種類**で分ける必要がある。そこで `resume_caller:` の直前に C ローカル `settle_s`（`JSAsyncFunctionData *`、通常は NULL）を置き、`async_flat_return:` だけがそれを立てる:

**settle は 2 段（レビューで境界を訂正）:**

1. **`js_async_function_settle_core(ctx, s, func_ret) -> bool`** = `js_async_function_resume:22008-22071` の後半そのもの（例外なら uncatchable を見て reject `:22010-22026` → `js_async_function_terminate` `:22027`; `JS_UNDEFINED` なら `cur_sp[-1]` の値で `resolving_funcs[0]` `:22030-22037`; `FUNC_RET_AWAIT` なら `js_promise_resolve` + `js_async_function_resolve_create` + `perform_promise_then` `:22042-22069`）。**生成者参照には触らず、promise も知らない。** `js_async_function_resume` は `async_func_resume` の後にこれを呼ぶ形に書き直す（段 A1、挙動不変）。await 復帰 `js_async_function_resolve_call:22098` からの呼び出しでも二重解放にならない（生成者参照は `:22138` で既に落ちている）。
2. **`js_async_flat_settle(ctx, s, func_ret, promise)`** = core を呼び、`js_async_function_free(rt, s)`（生成者参照、上流の `:22138` / `:22129` のどちらか一方と同じで、必ず 1 回）、成功なら `promise` を返し、uncatchable（TERMINATE）なら `JS_FreeValue(promise)` して `JS_EXCEPTION`（`:22135` → `fail:` と同じ）。**呼び出し元から見える形は上流と同一**: 同期区間の catchable な例外は投げられず**拒否済み promise が返る**（上流も `resume` が reject して `true` を返し promise を返す）。

- **C 再帰は消える。** core の中の `JS_Call(resolving_funcs[..])` は promise の resolve 関数（`js_promise_resolve_function_call:56796`、値が object なら `then` の getter で JS に再入しうる `:56833` — それは今もあるネイティブ再入で、新しい床）で、深さに比例しない 1 回の C 呼び出し。G1 は async 再帰で NOT_PROPORTIONAL になる（12.2 末尾）。
- **`js_vm_pop_frame` の LEAVE フック（`:6565`）は通らない**（`prev_frame != NULL`）。フラット SEG フレームと同じ。
- **例外の backtrace**（`:21317-21321`）は `rt->current_stack_frame` から `prev_frame` を辿るので、フラット async フレーム → 呼び出し元 SEG フレーム → 床 と続く。generator 床の上にフラット子が居る今の形と同じで、`class_id` のガード（D4-3）は既存のまま。`Error().stack`（`build_backtrace:8296-8330`）は上流の C 呼び出しでも `:18501` で同じ鎖になるので差は出ない。
- **tail call**（呼び出し元が通常関数で `return asyncFn()`）: `JS_RET_TAIL` で `goto done` — 呼び出し元の `done:` が `local_buf..sp` を解放するが、(1) のスロットは既に `JS_UNDEFINED` に戻してある。
- **中断中の `JS_FreeRuntime` / TERMINATE / GC** でこのフレームがどう扱われるかは 12.8 / 12.12。

#### D38: 予算はセグメントのバイト数だけ — フラット async フレームは数えない（D35 の廃止）

**決定（依頼者）: D10 の `rt->vm_stack.used` は文字どおり「セグメントの `top - base` の和」のまま。フラット async フレームの bytes（`sizeof(JSAsyncFunctionData) + alloc_size`）は乗せない。`flat_async_call:` に予算検査は無い。**

**帰結（コードから読める範囲。実測ではない）:**

- **深い async 同期再帰はヒープ枯渇で終わる。** `async function f(){ f(); }` はフラット化後 C を 1 段も積まず（`js_check_stack_overflow` は `async_func_resume:21740` と、class 分岐 `:18520-18528` の**後**にある `:18577` の 2 つで、どちらもこの経路を通らない）、セグメントも使わないので、`js_mallocz`（`:22111`）か `JS_NewPromiseCapability` か `async_func_init` の確保が `JS_SetMemoryLimit`（実機 160 KiB `guest.c:356`、vmrun `--profile device` `vmrun.c:742/:762`）に当たって **`InternalError: out of memory`** になる。投げられる場所は確保に失敗した呼び出し元（深さ N-1 のフラット async フレーム）で、その promise が拒否され、`await` していた各段に N 個のジョブを経て伝わる。同期 `try` には捕まらず `.catch` に届く形は RangeError のときと同じで、**違うのはクラスだけ**。`-recur` 変種（上流経路）では `:21740` の C スタック検査が RangeError を先に出す**可能性が高い**が、ヒープ 160 KiB と C スタック上限のどちらが先かは深さあたりの確保量に依り、**測るまで断言しない**。
- **D10 の「予算はヒープより先に当たる」は async の同期再帰にだけ成り立たない。** これは D10 の対象を広げない代償で、衝突ではなく限界として記録する（12.16）。
- **上流の `build_backtrace` UAF に到達しやすくなる。** ヒープが尽きた瞬間の `exception:` は `build_backtrace:21317-21321` を通り、DynBuf の realloc が `JS_ThrowOutOfMemory` を呼んで組み立て中の例外を解放する上流不具合（§14.6、`tools/vmtest/known/oom_backtrace_uaf.js`、README.md:206）に入りうる。じわじわ型 OOM で踏む不具合で、async の同期再帰はまさにその形。**ASan で緑を要求する関所にこのプローブは置けない**（12.2 末尾の表と 12.9）。
- **仕様 §12「新たな失敗を期待値の書き換えだけで処理しない」（spec:348）に照らして:** 既存の期待値ファイルに async の深い再帰で RangeError を固定しているものは**無い**（`tools/vmtest/corpus/deep_recursion.js` / `deep_recursion_device.js` / `seg_oom_boundary.js` に `async` は現れず、`expected/*.txt` で RangeError を含むのは `deep_recursion.txt:4` と `deep_recursion_device.txt:2` の通常関数だけ。`l2b_flat_calls.txt:24-25` / `l2b_floor_argc.txt:4-7` / `seg_generator_frames.txt:3` の async 行は再帰ではない）。したがって D38 は既存の期待値を書き換えない。新設のプローブ `deep_async_recursion` は最初から「ヒープで InternalError になる」ことを固定する（下表）。

#### D37: generator / async generator の呼び出しは分けて、どちらも囲った経路のまま

- **同期 generator の呼び出し** `g()`（`js_call_generator_function:21895`）は `OP_initial_yield` まで走って即戻る（`:21913-21918`）。C 再帰は 1 段で深さに比例せず、本体は `.next()` まで動かない。**本体（`js_generator_next:21807` → `async_func_resume:21846`）は `.next()` の呼び手が C スタック上で同期的に待つので止まらない — D8 を変えない限り（受け入れ済み、§11.2）。** フラット化しない。
- **async generator の呼び出し** `ag()`（`js_async_generator_function_call:22560`）も同じく `initial_yield` まで（`:22580-22586`）。本体は `.next()`（`js_async_generator_next:22515`）が **`state != EXECUTING` ならその場で `js_async_generator_resume_next`（`:22549-22551`）→ `async_func_resume:22428` を C 再帰で走らせる** — つまり **async generator 本体の最初の yield / await までの同期区間は、`.next()` の C 呼び出しの下で走り、止まらない**（`.next()` は C 関数メソッドで、D32 の対象外）。止まるのは await 復帰のジョブから再開されたとき（初版 12.3 の ASYNC_GENERATOR 床）だけ。**D13 の「async generator の本体」はこの範囲で満たす**。`.next()` を再帰的に呼ぶ JS は C 再帰のまま（G1 の対象外、`deep_recursion_device.js` の `through-map` と同じ「ネイティブ再入の深さ」で `:21740` が答える）。

### 12.3 D17r: 止まってよい床は `l2_flags` の 1 ビットで、活性の入口で決まる（H2, H4）

### 12.6 D36: 通常関数の Promise handler を止める — ジョブの保留と tail

### 12.7 D20: 床の持ち物 4 つの所有（K1）— 初版のまま

### 12.8 D21r: 鎖の GC と表明（H11）— 非 SEG フレームが鎖の途中にも居る

**決定: 鎖の所有者は初版どおり `JS_MarkContext` に足す 1 行（`mark_children` の `JS_GC_OBJ_TYPE_JS_CONTEXT` `:7373-7377`）。walk は top から床まで、`JS_SF_SEG` のフレームだけ `local_buf..sp`（top は `cur_sp`、それ以外は子の `js_vm_flat_caller_sp`）を mark し、SEG 床の spill 5 種を `taken` のとき mark する。フラット SEG 子の `cur_func` は mark しない（借用、初版のとおり）。**

**改訂点:**

- **ヒープに居るフレーム（generator 系床、フラット async フレーム）は walk が触らない。** それぞれの持ち主が mark する: `JSAsyncFunctionData` は GC オブジェクトで `mark_children:7357-7364` → `async_func_mark:21692`、generator は `js_generator_mark:21790`、async generator は `js_async_generator_mark:22201`。`async_func_mark:21701` は `cur_sp != NULL` のときだけ `arg_buf..cur_sp` を mark する — **12.4 の `vm_yield:` が鎖の全ヒープフレームの `cur_sp` を埋めるのはこのため**（top は自分の `sp`、途中と床は子の caller_sp = 呼び出し命令が退役した時点のオペランドスタック、すべてそのフレームが所有）。フラット async フレームの `cur_func` は `async_func_init:21671` が dup した所有参照なので、`async_func_mark:21699` の mark は正しい。**実行中に古い `cur_sp` で歩く D4 の UAF 側にはならない**: 書くのは中断の瞬間で、`vm_resume:` が NULL に戻す。フラット SEG 子の `arg_buf` はヒープ親のオペランドスロットを alias するが、walk は SEG の `local_buf..sp`（alias を含まない）、持ち主は `arg_buf..cur_sp` を mark するので二重にならない。

- §6.3 の GC 閾値修正はこの後（既決）。関所は 12.9 の `--gc-on-yield`。

### 12.12 D25 / D26r: TERMINATE と破棄、計測の口（H13, H12, H14）

**D25（初版のまま）:** `JS_VMTerminate` は `vm_susp.throw = 1` で `vm_resume:` から `goto exception`（uncatchable）。`JS_VMDiscard` は内側から畳む。使い分け（セッションが続く終了は Terminate、終わる破棄は Discard）も同じ。12.11 の leave ターンは「Terminate + Resume で畳んでから Discard」の順。
