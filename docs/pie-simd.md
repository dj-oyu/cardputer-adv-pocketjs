# ESP32-S3 PIE（SIMD）で描画カーネルを書く

確認日: 2026-09-07。このプロジェクトで実際に書いた4つのPIEカーネル（バイトスワップ、海面、波、blend）から得た知見をまとめます。

数値はすべてCardputer ADV実機（ESP32-S3FN8、240MHz、PSRAMなし）の実測です。推測はその旨を明記します。命令の節番号は[ESP32-S3 Technical Reference Manual](https://documentation.espressif.com/esp32-s3_technical_reference_manual_en.pdf)第1章のものです。

## 1. PIEとは何か、何が無いか

PIE（Processor Instruction Extensions）はESP32-S3のXtensaコアに載る128bit SIMDです。**コプロセッサ3**として実装されており、FPUと同じくタスク切り替え時に退避・復元されます。したがって**タスク内では安全、割り込みハンドラ内では使えません**。

前提として押さえておくべき制約:

| 項目 | 内容 |
| --- | --- |
| intrinsics | **存在しない**。すべてインラインアセンブリで書く |
| ベクタレジスタ | q0〜q7 の8本のみ。16bitレーンなら8要素 |
| アキュムレータ | QACC（8レーン×40bit）が1本 |
| 16bitレーンのシフト命令 | **存在しない**（§2で回避法） |
| ギャザー（索引ロード） | `EE.LDXQ.32` のみ、**1命令で1レーン**（§3） |
| レーン選択・ブロードキャスト | `EE.VLDBC.*`（メモリから）のみ。**QR内の1要素を全レーンへ配る命令は無い** |
| 128bitアクセスのアラインメント | 16バイト。**違反しても例外にならず、下位4bitが黙って0にされる**（§5） |

参考資料として[esp-dlのPIEスキル](https://github.com/espressif/esp-dl/tree/master/tools/agents/skills/esp32s3-pie-simd)がありますが、**不完全かつ一部不正確**です。`EE.LDXQ.32` の記載が無く、パイプライン段の記述（§4）も誤っています。TRMの表1.7-2が一次情報です。

## 2. シフトはすべて「定数との乗算」で表現する

16bitレーンを直接シフトする命令が無いため、`EE.VMUL.S16` / `EE.VMUL.U16`（§1.8.122 / §1.8.128）を使います。この命令は32bit積の**下位16bitをSARだけ右シフトした値**を返すので、SARを固定しておけば乗数の選び方で左右どちらのシフトにもなります。

SAR=11 に固定した場合:

```
x << 3   →  EE.VMUL.U16 with 16384    (x * 2^14 >> 11)
x >> 2   →  EE.VMUL.U16 with 512      (x * 2^9  >> 11)
x << 4   →  EE.VMUL.U16 with 32768    (上限。x << 8 は2回に分ける)
x >> 3   →  EE.VMUL.U16 with 256
```

`wsr.sar` は**関数の先頭で1回だけ**実行します。途中でSARを切り替えると往復2命令が増え、多くの場合それだけで利得が消えます。

左シフトの上限が ×16 である点に注意してください。RGB565のパッキングで赤を8bit左へ寄せるには `×32768` を2回適用します。これは無駄に見えますが、SARを切り替えるより安いことを確認済みです。

## 3. テーブル参照が高いのは「命令が遅いから」ではなく「本数が要るから」

索引ロードは `EE.LDXQ.32`（§1.8.37）だけで、**1命令につき32bitレーン1本**しか読めません。8要素を引くには8命令、2つの表を引けば16命令かかります。

命令そのものは1サイクルで、他のどのPIE命令とも変わりません（§3.5で本数を振って確認済み）。**高いのは、8要素を集めるのに8命令使うという構造のほうです。**

**設計上の含意**: PIEカーネルで正弦表などを引く設計は、スカラーコードほど有利ではありません。海面カーネルでは、2つの正弦表を放物線近似（`u(128-|u|)` と補正項1つ）で置き換えて **16本の `ldxq` と2本の `vunzip`、2本のマスクが丸ごと消え**、命令数が62から40へ、時間が1.06msから0.89msになりました。§8の但し書きどおり、これはビット一致を捨てる判断です。

## 3.5 「説明のつかないサイクル」は存在しなかった

この節は失敗の記録です。**カーネルが遅いという前提そのものが、計測の読み違いでした。**

海面カーネルは64命令で123サイクル/ブロック（1.9サイクル/命令）に見え、ストールを全部取り除いても、`ldxq` を全廃しても「残差」が消えませんでした。3つのエージェントが独立に「`ldxq` の部分書き込みがread-modify-writeになっている」と推測し、その前提で近似化まで実施しました。

### 機械の下限を測ったら、答えが出た

推測をやめて**PIEそのものの素の速度**を測りました。30ブロックのループを回し、本体だけを差し替えます。

まず命令の種類を変えて（40命令、依存なし）:

| ループ本体 | サイクル/ブロック |
| --- | --- |
| `EE.VADDS.S16` を40命令 | **40.9** |
| `EE.VMUL.S16` を40命令 | 40.9 |
| `EE.VPRELU`/`EE.VRELU` を12本混ぜて40命令 | 40.9 |
| 40命令のうち1本を `EE.VST.128.IP` に | 41.5 |
| ループ1回に1命令だけ | 1.7 |

次に、**本体を41命令に固定して融合ロードの本数だけ動かします**:

| `.LD.INCP` の本数（41命令中） | 0 | 8 | 16 | 24 | 32 | 16（1命令おきに分散） |
| --- | --- | --- | --- | --- | --- | --- |
| サイクル/ブロック | 41.9 | 42.0 | 42.0 | 42.1 | 42.2 | 41.9 |

**融合ロードは無料です。** 42命令に固定して `EE.LDXQ.32` の本数を動かしても同じでした:

| `EE.LDXQ.32` の本数（42命令中） | 0 | 8 | 16 | 24 | 24（4KB表に散在） | 24（全部同じレジスタへ） | 24（2本を交互） |
| --- | --- | --- | --- | --- | --- | --- | --- |
| サイクル/ブロック | 43.3 | 43.2 | 42.9 | 42.9 | 42.9 | 42.9 | 44.0 |

**索引ロードも無料**で、アドレスが散っていても、同じレジスタの別レーンに連続で書いても変わりません。長らく疑っていた「1レーン書き込みがread-modify-writeになっている」説は、ここで完全に否定されました。

### 結論: PIEは1命令1サイクル

**唯一の例外は128bitストアで、+0.6サイクル。** それ以外は種類を問わず1サイクルです。したがって理論値は:

```
サイクル/ブロック = 命令数 + 0.6 × ストア数 + ストール数
```

実カーネル `ocean_row_pie`（40命令、ストア1本）は下限40.6に対し**単独実測45.5**。差の約4は行あたりの前処理（定数21個の構築とブロードキャスト）を30ブロックで割ったぶんです。**カーネル本体に無駄はありません。**

### 何が起きていたか

`loop` という計測値に**カーネル以外のものが入っていました**。海面は水平線より上の37行を1ピクセルずつ塗っており（2.2サイクル/ピクセル、80µs）、そこに毎ストリップ2回の `esp_timer_get_time()`（1回0.90µs、フレームあたり30µs）とループの足場が乗ります。

| 内訳（OCEAN、1フレーム） | |
| --- | --- |
| 海面カーネル 98行 | 0.69ms |
| 空の塗りつぶし 37行（スカラー） | 0.08ms |
| タイマ呼び出し34回 | 0.03ms |
| ループの足場・プリエンプション | 約0.09ms |
| **`loop` 合計** | **0.89ms** |

これを30ブロック×98行で割ってカーネルのせいにしたのが「残差33サイクル」の正体でした。**割り算の分母が間違っていただけです。**

### 単独計測と実動作では3〜4割違う

もう一つ、下限表では説明できない差が残ります。海面カーネルを単独で回すと1行1365サイクル（98行で0.557ms）ですが、実際のフレームの中では `kernel=0.69〜0.74ms` と**2〜3割高く**出ます。行あたりの前処理を足すと、下限に対しては3〜4割増しです。波も同じ比率でした。

これは描画タスクが他のタスク（5msごとのキー走査、音、USB）に割り込まれるためで、PIEはコプロセッサ3なので切り替えのたびに8本のQRを含む状態の退避と復元が起きます。**カーネルの問題ではないので、カーネル側で対処できることはありません。**

実測を下限と比べると、海面 v3 は 40.6 → 単独45.5 → 実動作56、波 v2 は 69.6 → 実動作95。どちらも **下限の3〜4割増し**に収まります（行あたり前処理で約1割、プリエンプションで約2割）。新しいカーネルがこの範囲に入っていれば正常で、それ以上外れているときだけ疑ってください。

### 教訓

- **推測が3人一致しても、それは証拠ではありません。** `ldxq` 犯人説は全員が同意し、誰も測っていませんでした。実際には無料でした。
- **機械の下限を先に測ること。** 「40命令のループは何サイクルか」は10分で測れて、数時間の推測を不要にしました。この表があれば、新しいカーネルが理論値に届いているかは引き算で分かります。
- **係数は本数を振って決めること。** 最初に「融合ロード1本0.37サイクル」という係数を出しましたが、これは1点だけを測って命令数を数え違えた結果でした。0本から32本まで振ったら、正しい答えは0でした。
- **合成された計測値を、その一部の指標として使わないこと。** `loop` は「1行あたりの描画」であってカーネルではありません。いまは `PERF` に `kernel=` を分けて出しています。

なお、この経緯で入れた放物線近似（`d266ecf`）は**残差を消す目的では不要でした**。命令数を62から40へ減らしたこと自体は正しく効いており（1.06→0.89ms）、そちらは有効なので残しています。

なお、表引きが避けられない場合でも**表そのものに定数を畳み込む**ことで命令を減らせます。海面カーネルでは正弦表を `(sine[i]/6)*16 - 180*16` として持ち、除算・スケーリング・オフセット加算をすべて表の初期化に押し込んでいます。同様に波のカーネルでは、明度とその重み付き値（/4, /3, /2）を `lo | (hi << 16)` の形で1つの32bitエントリに詰め、1回の索引ロードで両方を取得して `EE.VUNZIP.16` で分離しています。

## 3.6 「下限」はループ本体の下限であって、1行の下限ではない

この節も失敗の記録です。§3.5 の式は正しいのに、それを使った予測が 2 割外れました。

庭（`main/scene/garden.c`）の画素ループを PIE 化したとき、`kernel=` を 38〜44 ms と予測して**実測 48.9 ms** でした。ストールはゼロ、命令数も設計どおり、`test_kernels.py` は全画素一致。式は合っていて、**式に入れなかったものが足りませんでした**。

### 何を数え落としたか

予測は「1 ブロック 180.8 サイクル × 30 ブロック ＋ 行あたりの前処理**約 1600 サイクル**」でした。この 1600 は見積もりで、数えていません。`objdump` で数えると:

| 1 行の内訳 | サイクル | |
| --- | --- | --- |
| ベクタ本体 3 ループ（30 ブロック × 180.8） | 5,424 | §3.5 の式が当てる部分 |
| run ごとの足場（13.25 run × 174） | 2,306 | 見積もりは 1,170。**2 倍の数え落とし** |
| 画素パスの前後（k[40] の構築 95 ＋ ブロードキャスト 109） | 204 | |
| 行のセットアップ（corner 12 回、逆数 3 本、motion 1 回） | 1,447 | ほぼ丸ごと勘定に入れていなかった |
| **合計** | **9,381** | 予測は 7,024 |

**ベクタ本体は 1 行の 58% しかありません。** 残り 42% はアセンブリの外側です。9,381 × 135 行 = 1.27M サイクル = **5.28 ms**（予測は 3.95 ms）。ここに §3.5 の実動作係数 1.3〜1.4 を掛けて 6.9〜7.4 ms。

### なぜ海面と波では起きなかったか

**`ocean_row_pie` と `wave_row_pie` は 1 行 = 1 ループです。** 行あたりの足場は「定数 21 個のブロードキャスト」だけで、§3.5 が単独実測 45.5 に対して「差の約 4」と書いているのがそれです。第 2 項が第 1 項の 1 割しかないので、下限に係数を掛ければ当たります。

庭のカーネルは**行を run に切ります**（格子セルの境界でコーナー値が変わるため）。すると 1 行に 13 回の関数呼び出し、13 回の定数ブロードキャスト、13 回の `loopgtz` 立ち上げが入り、**第 2 項が第 1 項と同じ桁になります**。§3.5 の「下限の 3〜4 割増し」は前者で較正された数字で、後者には効きません。

### 数え方

見積もらずに `objdump -d` で数えます。**`loopgtz` / `bnez` の外側にある静的命令数が、そのまま 1 回の呼び出しあたりのコスト**です。

```
garden_broadcast    static   7   ループ本体 2   ループ外  5
garden_coarse_pie   static  57   ループ本体 22  ループ外 32   （+ 8 反復の rcv 充填）
garden_pixels_pie   static 230   ループ本体 135 ループ外 95
```

`ee.vst.128.ip` の 0.6 を忘れないこと。ブロードキャストは nk 本のストアなので、40 定数なら +24 サイクルです。

もう一つ、スカラー側で見落としやすいもの: **このコアのハードウェア除算は 1 命令ですが約 32 サイクルです。** 庭は画素ループから除算を全廃したのに、行の足場に 28 本（`garden_corner` 12、逆数 3、run ドライバ 13）残っていました。1 行 900 サイクル、1 フレーム 0.5 ms です。ループから追い出した除算が、ループの外に溜まっていないか見ること。

### 補正した形

```
サイクル/行 = ブロック数 × (命令数 + 0.6×ストア数 + ストール数)      §3.5 が当てる部分
            + run 数     × (ドライバ + カーネルのループ外 + 呼び出し)   objdump で数える
            + 行のセットアップ（除算は 1 本 32 サイクルで数える）
```

そのうえで実動作は 1.3〜1.4 倍。**掛ける前の中身を数え落としていると、係数をいくら正確にしても当たりません。**

## 3.7 このコアでは C の `/` は関数呼び出しで、逆アセンブルからは見えない

**浮動小数のコードをプロファイルする前に、この節を読んでください。** 私と team lead は同じ数え間違いを 2 回、独立にしました。

ESP32-S3 の FPU には**除算命令も平方根命令もありません**。GCC は seed 命令（`div0.s` / `recip0.s` / `sqrt0.s`）を**一度も出しません**（`-fno-math-errno` を付けても変わりません。イメージ全体で 14 本見つかりますが、全て Wi-Fi と ROM のコードです）。したがって:

```c
float dx = (x + .5f - 180) / SCALE - p->c.x;   // SCALE は定数。これが呼び出し 1 本
float d  = dot(a, p->axis[j]) / p->radius[j];  // これも
float m  = fmaxf(0, x);                        // これも
float r  = sqrtf(v);                           // これも
```

`SCALE` がコンパイル時定数でも畳まれません。`1/37.0f` が正確に表現できないため、GCC は `-freciprocal-math` なしでは逆数乗算に置き換えないからです。

### なぜ grep で見つからないか

`-mlongcalls` が呼び出しを 2 命令に割ります:

```
l32r    a8, 4207f298 <...>  (42096134 <__divsf3>)
callx8  a8
```

**`div` を mnemonic 検索しても、`call8 <symbol>` を検索しても出ません。** `__divsf3` は `40002274 A`、つまり ROM の絶対アドレスで、`nm` の T にも W にも並びません。私は最初「`ray_row` に除算は無い」と報告しました。実際には **16 本**ありました。

**見つけ方**: `callx8 aN` の直前の `l32r aN` を辿ってリテラルを解決します。`objdump -d` はリテラルの値と記号を括弧で注記するので、レジスタごとに最後の `l32r` を覚えながら 1 パスすれば全部名前が付きます。

**もっと安い見つけ方: `.s` を出すと名前で数えられます。** `l32r`+`callx8` への分割はアセンブラの仕事で、**コンパイラの出力にはまだ `call8 __divsf3` と書いてあります**。`build_*/compile_commands.json` からそのファイルのコマンドを取り、`-c <file> -o <obj>` を `-S <file> -o <file>.s` に替えて回すだけです（インクルードパスと `-D` が本物と同じでないと意味がないので、コマンドは手で書かずにここから取ること）。関数ごとに数えられます:

```
flower_draw   sqrtf x2  __divsf3 x2   (ray_row と bell_hit を inline したもの)
shade         sqrtf x1  __divsf3 x1  floorf x2
flower_prepare __divsf3 x19  sqrtf x4  floorf x2  ceilf x2  sinf x3  cosf x1
```

この 3 行は 5 秒で出ます。リテラルを辿る 1 パスは、それが要る場面（最終バイナリしか無いとき）に取っておけます。

**同じ出力で契約が確認できます。** 最適化の前後で `.s` を 2 本出して `call8` を数えれば、「呼び出しを何本消したか」は測定ではなく**数え上げ**になります。これが本数の話であって時間の話でないことは §3.8 のとおりで、時間は実機で聞くしかありません。

**そして `-ffp-contract=fast` が既定です。** `flower.c` 1 ファイルで `madd.s` 104 本 `msub.s` 22 本。**浮動小数の式を並べ替えてビット一致を主張するときは、両方の綴りが同じように融合されるかを見ること** — `x*x+y*y-z*z` は `madd`+`msub` の 2 命令で、丸めは 2 回しか起きません。ホスト側でこれを再現するには `gcc -mfma -mavx2 -ffp-contract=fast` で焼き直して比べます（`-ffp-contract=off` と両方通れば、その並べ替えは融合に依存していません）。

### 呼び出しは自分のサイクルより高い

soft-float ABI は引数を**整数レジスタ**で渡します。だから 1 回の呼び出しごとに `rfr`（float→AR）と `wfr`（AR→float）が要り、さらに**生きている float が全部スピル**します。ループ本体の中に `/` が 1 本あるだけで、そのループの作業集合が毎周メモリを往復します。

`main/scene/flower.c` の実測（`objdump`、同一ビルド）:

| | 命令 | float st | float ld | `rfr`/`wfr` | 呼び出し |
| --- | --- | --- | --- | --- | --- |
| `ray_row` 前 | 637 | 61 | 97 | 37 | `__divsf3` ×12, `sqrtf` ×2 |
| `ray_row` 後 | 586 | 49 | 80 | 27 | `__divsf3` ×4, `sqrtf` ×2 |
| `shade` 前 | 544 | 20 | 50 | **116** | `fmaxf` ×6, `__divsf3` ×4, `sqrtf` ×1 |
| `shade` 後 | 467 | **6** | **24** | 98 | `__divsf3` ×2, `sqrtf` ×1 |

`shade` は**演算（110）より register-file 間の移動（116）のほうが多い**状態でした。

### 値段（2026-09-09 実測。ここにあった 150〜250 は推定で、4 倍外していました）

| `sqrtf` | **174〜188** | 実機で単体計測 |
| `__divsf3` | **55〜67**（観測の幅から 43〜91） | 下記、スイッチ 1 個の 2 本焼き |
| `floorf` / `ceilf` | **約 78** | 下記、スイッチ 1 個の 2 本焼き |

**`__divsf3`。** `FLOWER_NO_BAND_INVA` を切った 2 本を、静止させたツリーから焼きました（`esptool` で既存のバイナリを直接。あいだにビルドを走らせないため）。calla（species 6）で:

```
bell:sqrt calls        A 4,765-4,774   B 4,766-4,774   （不変＝二本は比較可能）
```

**消えた除算の本数は推定ではありません。** 除算は `disc >= 0` の帯でだけ走り、平方根も同じ条件なので、**`bell:sqrt` の calls がそのまま除算の本数**です（§3.11）。1.33 ms × 240,000 ÷ 4,770 = **67 サイクル/本**。同じスイッチが帯あたり 3 演算（`dr` と `a` の再計算）も一緒に消しているので、これは**上限**で、そのぶんを戻すと 55〜65。観測された幅の両端で割ると 43〜91。

**注意: `bell` の cy/visit は棄却された visit も分母に入っています**（`prof_belln++` は `bell_reject` の前）。§3.11 の 4.5〜5.4 は**生き延びた visit あたり**なので、この二つを直接割ってはいけません。上の計算がそれを避けているのは、`bell:sqrt` の calls という**フレームあたりの絶対本数**を使っているからです。二つの計器の分母が違うときは、率ではなく本数で割ること。

**`floorf` / `ceilf`。** `FLOWER_NO_IFLOOR` を切った 2 本、species 13（25 部品）の `prep: petals=`:

```
B  2,679-2,741 cy/part
D  2,379-2,411 cy/part     差 約 310、部品あたり 4 本 → 約 78 サイクル/本
```

**整数の除算のほうは呼び出しではなく、ハードウェア除算器で約 16 サイクル**です。これは直接の計測ではなく、`0ecf16e` からの逆算です: あのコミットは 2 つの厳密な置き換えだけを含み、消えた除算の本数が両方とも数えてあります（林冠 10,454 + `garden_corner` 1,620 = 12,074 本/フレーム）。実測の節約 0.82 ms = 196,800 サイクルを割って 16.3、置き換えた乗算とシフトのぶんを戻して約 18。

整数側のこの数字が要ったのは、**私が 32 と仮定して 2 倍外した**からです。浮動小数側は長らく誰も測っておらず（`div=` を名乗ったカウンタは乗算を囲っていました）、上の表がその最初の実測です。

### なぜ 150〜250 になったのか

古い推論はこうでした: `sqrtf` は約 95 命令で 188 サイクル、ゆえに**このクラスのソフトルーチンは 2.0 サイクル/命令**、`__divsf3` も同規模だから 150〜250。

**間違っていたのは 2.0 のほうではなく「同規模だから」のほうです。** 単精度のソフト除算は本来短く、あの 95 命令は `sqrtf` に固有の長さでした。**命令数を数えずに「同じクラス」で括ったのが誤りで、比例定数のほうは疑われてすらいませんでした。** 命令数なら `.s` を出して数えられます（この節の「もっと安い見つけ方」）。

そして**この 150〜250 は一度も測られないまま、少なくとも 3 つの判断の土台になっていました。** 推定と実測の差が 4 倍あるので、**この数字を使った過去の見積もりは、符号は合っていても倍率は当てになりません。**

### 予測が当たるかどうかは、定数だけで決まっていた

この巻き上げのフレーム効果を、私は 150〜250 を使って −2.3〜−8.7 ms と予測し、実測は **−1.33 ms** でした。同じ式に実測の 67 を入れると 4,770 × 67 = 320k サイクル = **1.33 ms** です。**モデルは合っていて、定数だけが 4 倍でした。** §3.8 は「命令数はサイクルを予測しない」ですが、ここは逆の形で、**本数は完全に予測できていて、1 本の値段だけが推定**でした。数える対象が正しいなら、残る誤差は全部その定数にあります。

### スイッチは変更の全部を戻すこと

`FLOWER_NO_BAND_INVA` は最初、`bell_hit` から 6 本の除算を外しながら、それを肩代わりする `petal_reciprocals` の 6 本を**両方のビルドに残していました**。画素はどちらでも一致するので絵の証明は何も言わず、**`petals=` がスイッチをまたいで動かない**という形でだけ出ます。私はその不動を「予測が外れた」として報告される側に置きました。

**半分だけ戻すスイッチは、スイッチが無いより悪い。** 無ければ数字は出ませんが、半分なら数字は出て、しかも正しく見えます。§3.8 の「スイッチは存在するだけでなくコンパイルが通ることを確認すること」に、もう一項: **切ったビルドで、そのスイッチが変更の全部を戻すことを確認すること。** 確認の仕方は、そのスイッチが動かすはずの計器を 1 つ名指ししておいて、動かなければスイッチを疑うことです。

### 直し方（どれも算術ではなく呼び出しの本数を減らす）

- **逆数をフレームに 1 回**。`p->radius[j]` は部品ごとに固定なので `inv_radius[j]` を持たせる。bell の visit ごとに 6 本消える。
- **除数を共有する**。`(-b+sd)/a` と `(-b-sd)/a` は `1/a` を 1 回。
- **定数除算は明示的に逆数乗算へ**。`x/SCALE` → `x*(1.0f/SCALE)`。
- **`fmaxf(0,x)` は三項演算子へ**。NaN 意味論が要らないなら完全に等価で、呼び出しが丸ごと消える。

### 精度は掃引すること

どれも恒等式ではありません。`a/b` と `a*(1/b)` は 1 ulp 違い、判別式の 1 ulp は `d<0` の反対側に落ちるシルエット画素です。`tools/test_flower_div.c` が両方の形をビルドして全画素比較します（8 種 × 8 位相 = 207 万画素で **1 画素**、緑 1 段）。`garden_model.c` が lobe の逆数を掃引するのと同じ形で、「たぶん動かない」ではなく**動く量の上限をテストにする**こと。

## 3.8 棄却テストの経済学と、命令数がサイクルを予測しない領域

2026-09-08 の丸一日、`ray_row` を 31.7 ms から 15.2 ms にする過程で、**予測した倍率が実測と合わなかったのが 5 回**ありました。誰も推論を間違えていません。間違えたのは毎回、倍率のほうです。その 5 回から取り出せる規則が 2 つあります。

### 「visit の N% を落とす」は「時間の N% を落とす」ではない

```
節約 = 棄却率 x 棄却された visit のコスト
                 ^ 「安かったから棄却できた」もので、平均ではない
```

安い保守的テストは安い仕事を落とします。ある画素が早く抜けるのは、たいてい**遠く外れているから**で、それはまさにテストが捕まえやすい画素です。

このリポジトリの 3 例:

| テスト | 棄却率 | 実測の時間効果 | なぜ |
| --- | --- | --- | --- |
| `tools/flower-rejection/`（楕円体の span 狭め） | visit の 27〜50% | **0.2 ms / 30 ms** | 落とすのは `d<0` で即抜ける最安の画素。関数の時間は残る画素にある |
| 鐘の外接円筒、半径だけ | 21.8% | **2.7%**（2,045→1,989 cy/visit） | 円筒の外の光線は、既に 6 バンド全部を `disc<0` で抜けていた |
| 同、高さ上限つき | 40.8% | **20.6%**（1,989→1,580 cy/visit、ただし下記の注） | 6 バンドを `disc>=0` で歩き切っていた光線を落とす |

**棄却率は 1.9 倍にしかなっていません。効果が変わったのは、落とす対象が変わったからです。**

3 行目の 20.6% には注が要ります。それを出したコミット（`714f712`）には高さ上限と**バンド境界のホイストの両方**が入っており、409 cy/visit はその合計です。どちらが何を出したかは分かりません — `FLOWER_NO_BAND_HOIST` を切って焼けば今からでも分けられますが、まだ誰も分けていません。**表に載せる数字が 3 つあって、そのうち「その変更だけ」と言えるのは 2 行目だけ**です。

だから設計の順序は決まっています。**テストを選ぶ前に、生き残った visit が「どこで」落ちているかを数えること。** 鐘では、円筒を通り抜けてなお外れた visit の 38〜48% が「円錐には当たったが、そのバンドの高さの外だった」でした。高さ上限はそこを狙って書いたもので、思いついた順ではありません。

私（このカーネルを書いたエージェント）の誤りは、棄却率 × **平均** visit コストで 590 cy/visit と予測したことです。実測 56。要るのは条件付き平均です。

### 同じ規則の裏側 — 判定が、判定している仕事より高いとき

上の規則は「落とす仕事は平均より安い」でした。裏返すと「**残す仕事を選ぶ判定は、選ばれた仕事より高いことがある**」になります。同じ日の夕方、庭の光柱に入れた 14 個の羽虫がそれでした。

見積もりは触れる画素で立てました。14 個 × 3 画素 × 2 行 = 84 画素、1 画素あたり約 30 演算で **4.6 us**。「実測」は **1.0 ms**（`pixels` 5.94 → 6.94 ms）。200 倍 —— **ただしこの 1.0 ms 自体が後で崩れます。下の節まで読んでください。**

外したのは画素の数ではありません。画素の数は合っていました。抜けていたのは、その 84 画素を**見つけるための** 14 × 135 = **1,890 回の行×粒子テスト**です。ヒットは 27〜28 個。描くより、描くかどうかを決めるほうが 2 桁高い。

```
sparse な仕事のコスト = 描画 + 「どれを描くか」の探索
                                  ^ 疎であるほど、こちらが支配する
```

直し方は判定を行から frame へ動かすことだ、と書きました。`garden_prepare` が 135 語のビットマスクを 1 回書き、行はそれを 1 語読んで立っているビットだけを回る。1,890 回のテストが 135 回のロードと 27 回の描画になります（`GARDEN_MOTE_INDEX`、`main/scene/garden.h`）。

### そして、それも間違いでした

スイッチで測ると:

```
GARDEN_MOTE_INDEX=1   pixels 6.80 ms
GARDEN_MOTE_INDEX=0   pixels 6.86 ms   （11 サンプルの平均）
```

**1,863 回のテストを消して 60 us。** 1 回あたり 8 サイクルで、上で計算した 127 の 1/16 です。索引は正しく、ゼロコストで、そして**今日の粒子数では何も買っていません**。

さらに悪いのは、それを作らせた 1.0 ms のほうです。あれは**群れの無いビルドと有るビルドを比べた値**でした。CLAUDE.md が言うとおり同じカーネルは i-cache のアラインメントでビルド間 15% 動き、6 ms の 15% は 0.9 ms。**1.0 ms は自分のノイズの中に入っていた**のです。

だからこの節の教訓は 2 つに増えます。

1. **棄却率でも命令数でもなく、「その仕事は本当に高いのか」を先に測る。** 8 サイクルの判定を 1,890 回やっても 15 us です。判定が支配するのは、判定が高いときだけでした。
2. **2 つのビルドを比べるのは測定ではない。** 1 本のツリー、1 個の define、他は完全に同じ — それだけが差を出せます。`GARDEN_NO_MOTES` / `GARDEN_MOTE_INDEX` / `GARDEN_PIE_FUSE` はそのために在り、**機能を書くのと同じコミットでスイッチを書く**のが唯一の防ぎ方です。索引はこの規律で測れたから間違いが 1 日で分かりました。1.0 ms のほうはスイッチが無かったので、誰も気づけませんでした。

ホスト側の注意も、結果として正しい読みでした。x86 で同じ 1,890 回を回しても 0.29 ms/frame から動かず差はノイズに沈みます（`tools/garden_bench.c`）。当時これを「ホストは実機を再現できていない」と読みましたが、**ホストは本当のことを言っていた**のです。数えられる量（1,890 → 27）だけを契約にしたのは正しく（`tools/test_garden.c` の `INDEX_OK`）、それを時間の主張に翻訳したのが誤りでした。

### 命令数はサイクルを予測しない — レジスタが溢れている領域では

同じ日、逆向きの誤りもありました。`bell_hit` の setup を

```
o[j] = dot(origin, axis[j]) * inv_radius[j]     9 乗算 + 6 加算
o[j] = dx * oax[j] + ob[j]                      3 乗算 + 3 加算
```

に書き換えたとき、**命令数から 0.2〜0.4 ms と予測して、実測は約 2.4 ms**（1,580 → 1,163 cy/visit）でした。14 倍の過小評価です。

理由は逆アセンブルに出ています。`ray_row` は浮動小数演算 134 に対して **float ストア 45・ロード 89**。バンドループの生存集合が 16 本の float レジスタを超えていて、常に溢れています。**そこで演算を 1 つ減らすと、その演算とスピル/フィルの往復が一緒に消えます。** 命令数の比ではなく、圧力の比で効きます。

`shade` も同じでした: 呼び出しを 10 本消して**命令数 14% 減、時間 39% 減**。§3.7 の soft-float ABI の話と同じ機構です。

**見分け方**: `objdump` で `ssi`/`lsi`（float のストア・ロード）を数え、`.s` で終わる演算命令と比べます。1:1 に近ければその関数は溢れていて、命令数からの見積もりは下限にしかなりません。

### 最適化とその計測を同じコミットに入れない

上の表の 3 行のうち、**クリーンな前後があるのは 1 行だけ**です。

- `bell_reject`（円筒）は、それを測るはずのカウンタと同じコミットで出ました。実機の効果は復元不能になり、あとから `FLOWER_NO_BELL_REJECT` を足して測り直すしかありませんでした。
- 次のコミットは高さ上限と**バンド境界のホイストの 2 つ**を含み、1,989 → 1,580 はその合計です。どちらが何を出したかは分かりません。
- その次のコミットのメッセージは、**前のコミットに入っていた変更を credit しています**。

円筒の 21.8%→2.7% がクリーンなのは、たまたまカウンタの改名がその境界になったからで、設計の結果ではありません。

対策は 1 つだけです。**すべての最適化に、それを切るコンパイル時スイッチを付ける。** 両方焼いて引き算できます。

```
FLOWER_DIV_EXACT   FLOWER_NO_BAND_HOIST   FLOWER_NO_SPAN_AFFINE
FLOWER_NO_BELL_REJECT   FLOWER_BELL_CHECK   GARDEN_NO_CANOPY_RECIP
```

そして**存在するだけでなく、コンパイルが通ることを確認すること。** 4 つ作って 3 つしか通らず、通らなかったのは、いちばん必要だった 1 つでした（棄却が無効だと `bell_reject` が未使用になり `-Werror` が止める）。

## 3.9 オーバーレイの二つの罠 — ストリップごとの全走査と、重なる走査の非線形性

背景に飾りを1つ足して、それが **3.3〜4.0 ms**（`hud` 1.6→5.5、`fps` 23.7→19.9）かかったので取り外しました。飾り自体はもう居ませんが、そこで見つかった二つは次に `overlay` を書く人が同じだけ払うものなので、ここに残します。

### 罠1: `overlay` は1フレームに17回呼ばれる

`shell_draw` はストリップループの中で `sc->overlay(strip,strip_y,strip_h)` を呼びます。**17回です。** 描画対象が画面の一部にしかなくても、呼ばれる回数は変わりません。

飾りは56列 × 4掃引のループで、各列で格子読み2回と混色4回をして色を作り、最後に行でクリップしていました。帯は17本のうち**5本**にしかかからないので:

```
色の生成回数/フレーム   813  →  201     （行が届かない掃引を飛ばす1行を足して）
合成回数               2369  →  2369    （画素は元から一度しか書いていない）
```

**612回、つまり3/4が捨てられていました。** そして**画素数からは見えません** — 画素数は「塗った画素」であって「した仕事」ではないからです。飾りは画素1153に対して合成2369、色生成813でした。

包絡線のように列から列へ状態を持ち越すものはストリップをまたいで省略できません。**省略できるのは、その行がこのストリップに届かないと分かった後の仕事だけ**で、そこが偶然いちばん高い部分でした。

    if(bot<y0||top>=y0+height)continue;   /* 状態の更新の後、色の生成の前 */

### 罠2: 重なる走査は本数に比例しない

同じ領域を複数回走査する描画は、走査本数に線形では増えません。飾りは掃引を重ねる方式で、基線の近くで重なります:

| 掃引 | 合成/フレーム | 点灯画素 | 画素あたり合成 |
| --- | --- | --- | --- |
| 1 | 690 | 690 | 1.00 |
| 2 | 1197 | 897 | 1.33 |
| 3 | 1751 | 1084 | 1.62 |
| 4 | 2369 | 1153 | **2.06** |

画素は4倍、時間は**6〜7倍**。差は全部この列にあります。**「N回描く」は「N倍」ではなく、重なりの分だけ超えます。**

### そして、いちばん重要なこと

この飾りは、外すと決まるまでに5往復して良くなり、最後に**測って落ちました**。3.3 ms は林冠を丸ごとベクトル化して得た 0.5 ms の7倍で、朝に HUD のホイストで取り戻した 4.4 ms とほぼ同額です。**装飾ひとつが、その日の最適化の全部を使い切っていた。**

見た目の良し悪しでは決まりませんでした。カウンタが1つあっただけです。

## 3.10 半径は歩幅で買う、区間は形ではない、そして「計器が黙る」四つの形

FLOWER に被写界深度を入れて、丸ごと取りやめになりました。機能は残っていませんが、作って測った三つは次の効果が同じ道を通るので残します。

### 半径は極ではなく歩幅で買う

一極 IIR の到達距離は **時定数 × タップ間隔** です。係数（極）を上げて半径を買うと、`avg565` の入れ子が増えて**画素あたりの命令が増えます**。同じ極のまま歩幅を2や4にすると、半径は歩幅倍になり、**触る画素はその分の一**になります。

| 買い方 | 極 | 最大半径 | px/frame |
| --- | --- | --- | --- |
| 入れ子 | 7/8 | 13.0 px | 16,262 |
| 歩幅 | 3/4 | **19.7 px** | **6,541** |

**画素2.5分の1で半径1.5倍。** しかも極 7/8 が不要になったことで、5bit パネルでは尾が短いという性質（極1/2で赤青5・緑6タップ、3/4で8・10、7/8で11・16）から、**FIR 化＝PIE 化の道が開き直します**。極を上げると閉じ、歩幅を使うと開く——二つの目標が同じ方向を向くかどうかは、この選択で決まります。

**そして外挿の罠。** 画素数だけから費用を外挿して外しました。実測は `px` 16,419 に対し予測 16,262 とほぼ完璧でしたが、**動いたのは `cy/px` のほう**で、22 → 34。極を上げると1画素あたりの演算が増えるのだから当然で、外挿は**実際に動く項を固定していた**わけです。§3.8 の「命令数はサイクルを予測しない」の、もう一つの現れ方です。

### 区間は形ではない

行の最左・最右（`tlo`/`thi`）は**一区間**です。それを外へ D 画素広げると、斜めや曲がった縁では**実際の境界から遠く離れた背景**に届き、しかもどの行も同じ端点から同じ量だけ伸びるので、**垂直な柱＝階段状の矩形**になります。ガラスの上では「葉から四角い切れ端が生えている」「鐘が黒い箱に入っている」でした。

画素ごとの答えは **`depth[]` に最初からありました**——`ray_row` が毎行書き、行頭でリセットされ、花弁が書かれた画素を持っています。そこから「覆われている、かつ隣が覆われていない」で真の輪郭が取れ、走査カウンタ2本で余白を形の上に育てられます。1行240演算、追加記憶ゼロ。

**この描画器には「行の中の花の縁」が三つあります** — `depth[]` の画素単位、`tlo..thi` の区間、それを広げたもの。効果ごとにどれを指すかを言わないと、輪郭を扱う次の効果が同じ矩形を作ります。

### 計器が黙るのは、精度ではなく「別の性質を測っている」から

同じ日に三度ありました。

- **`bell:sqrt` は `bell` の内側**で計られているのに、行はそう言っていなかった。七つの数を素直に足すと 1.8 ms の穴が開き、**計器が壊れたように見えた**。実際には合っていて、入れ子が読めなかっただけ。
- **書式と引数のずれ。** `ESP_LOGI` に format 属性が効かず、`#ifdef ESP_PLATFORM` でホストは見もしないので、**コンパイラは検出しない**。varargs で昇格した float の bit が整数枠から 1072049757 として六行続けて出た。`tools/test_flower.c` の `LOGFMT_OK` は `flower.c` を読んで変換指定と引数を数えます——粗いが、これが唯一available な検査です。
- **「N視点ある」と「サイズの階段がある」は、ほぼ同一の四枚が満たす主張です。** `VIEWS_OK` は画素差を見るので、同じ大きさを別角度で撮った四枚は堂々と通ります。捕まえるには**差ではなく性質**を読む assert が要りました（隣接ショットのサイズ比、巻き戻り込み）。

そして四つ目が、この組でいちばん強い例でした。**カメラの `zoom` と `aim` は一度もガラスに届いていなかった** — `view_pending` を一人目の読み手が消し、二人目（構図）が常に0を見て素通しの枝を取っていた。四時間ぶんのカメラ作業が「一つの引きの絵を四つのピッチで撮ったもの」として再生され、`VIEWS_OK` は**その間ずっと通っていました**。

通ってしまう理由が、サイズ梯子と同じです。ショットは数秒離れて採取されるので、株の揺れと姿勢が違い、**カメラがバイト単位で同一でも画素は違う**。「四つの視点がある」の証拠として画素差を使うのは、**主張が入力についてなのに出力を比べている**ということでした。今は投影に届いた `cam_s` そのものを検査しています。

共通するのは**不正確だったのではなく、別のものを測っていた**ことです。「この assert は何を数えているか」を「この assert は厳しいか」より先に問うこと。今日、機能が動いたせいで落ちた assert が五つありましたが、それらは正しく壊れました。危ないのは、**動いていないのに通り続けるもの**です。

## 3.11 ピクセルに見えて、フレームに 1 回でよかった除算

`main/scene/flower.c` の `bell_hit` は、鐘の 6 つの緯度帯それぞれについて二次方程式を解きます。その先頭の係数は

```c
float dr = slope*d[1];
float a  = d[0]*d[0] + d[2]*d[2] - dr*dr;   /* d = p->bd, slope = bell_slopes[band] */
```

で、`d[]` は**部品の**光線方向、`slope` は**帯の**プロファイルです。**ピクセルは一つも出てきません。** `a` も、`fabsf(a)<1e-7f` の分岐も、そして `1.0f/a` も、フレームのあいだ (部品, 帯) ごとに定数でした。それが visit ごとに、帯ごとに、毎フレーム計算されていました。

`bell_lo` / `bell_hi` / `bell_slopes` を `flower_prepare` へ巻き上げた作業はこの同じループに対して既に行われていて、**`a` はその一段内側で見落とされていました**。理由ははっきりしています: 巻き上げられた 2 本は `2.0f*band/LAT` と**書いてあった**除算で、`1.0f/a` は §3.7 のとおり逆アセンブルにも mnemonic 検索にも出ない呼び出しだからです。**書いてある除算は見つかり、書いていない除算は残った。**

### 何本だったのか

「visit あたり最大 6 本、ただし全部走る visit は多くない」というのが唯一あった見積もりでした。数えたら:

| 種 | 棄却を生き延びた visit あたりの `disc >= 0` |
| --- | --- |
| valley | 4.51 |
| daffodil | 5.35 |
| calla | 4.50 |
| fritillaria | 5.18 |

**6 本中 4.5〜5.4 本**です（`tools/test_bell_reject.c`、14 種 × 24 位相）。`disc >= 0` の回数は `sqrtf` の回数でもあり、巻き上げる前は `__divsf3` の回数でもありました。つまり**平方根と除算は同数**で、`SPLIT` 行が既に印字している `bell:sqrt` の calls がそのまま除算の本数です。

数えるときの罠が 1 つ: `FLOWER_BELL_CHECK` は棄却を**計算するが従わない**ビルドなので、その中でただ数えると棄却済み visit の帯まで数えます（4.5 のはずが 11.5 になります）。出荷ビルドが歩かない visit は分子からも分母からも外すこと。

### 副産物として、これは `__divsf3` の値段を測る実験になっています

§3.7 は長らく「浮動小数の除算は誰も測っていません」と書いていました。この変更は**消えた本数が正確に分かっている**（`bell:sqrt` の calls に等しい）唯一のもので、`FLOWER_NO_BAND_INVA` を切って両方焼けば商が値段です。**だからこの巻き上げと、同じ visit にあった 30 個の積和の巻き上げは別スイッチにしてあります**（`FLOWER_NO_BAND_DOTS`）。1 つのバイナリに 2 つ入れると、商が除算の値段ではなくなります。

**焼きました。答えは 55〜67 サイクルで、§3.7 にあった推定 150〜250 の 4 分の 1 です**（calla、1.33 ms/frame ÷ 4,770 本）。表と経緯は §3.7 の「値段」。

### ビット一致であること

`p->ba0` は `bd[0]*bd[0]+bd[2]*bd[2]` そのもので、巻き上げ先は `p->ba0 - dr*dr` と綴ってあります。元の式と語順が同じなので、融合の有無にかかわらず同じ値になります。`tools/test_flower_div.c` の枠組みで HEAD と突き合わせて 14 種 × 8 位相 × 32,400 画素 = **362 万画素が完全一致**、`-ffp-contract=fast -mfma` と `-ffp-contract=off` の両方で一致します。

### 教訓

**「ピクセルごとに変わるもの」を式の見た目で判断しないこと。** `a` は `d[]` と `slope` しか含まないのに、6 個の局所変数と 2 つのループの内側にいたので、ピクセルの式に見えました。ループから追い出した除算がループの外に溜まっていないかを見よ、と §3.6 は言いますが、**追い出されなかった除算がループの中に残っていないか**も同じだけ見る価値があります。見分ける機械的な方法は `.s` の `call8` を関数ごとに数えることで、上の 3 行がそれです。

## 3.12 `floorf` は 1 命令に置き換わるが、「引数は非負だから」で置き換えないこと

`floorf` / `ceilf` も §3.7 の呼び出しです。C の `(int)` キャストは `trunc.s` 1 命令で、負の側の丸め方だけが違います。

`main/scene/flower.c` には 6 本ありました — `shade` の市松模様に 2 本（fritillaria の鐘の画素ごと）、`flower_prepare` の画面ボックスに `floorf` 2 本と `ceilf` 2 本（部品ごと、最大の種で 224 本/フレーム）。`.s` で数えて、置換後は**全部 0 本**です。

自然な書き方は「引数は構造上非負だからキャストでよい」ですが、それは**値についての主張**で、標本でしか確かめられません。`longitudinal` が丸め誤差でわずかに負に振れると `floorf` は `-1`、キャストは `0` を返し、市松の偶奇が 1 画素だけ反転します。代わりに**表現についての恒等式**を使えば前提が要りません:

```c
static inline int ifloor(float x) { int t=(int)x;return t-(x<0.0f&&(float)t!=x); }
static inline int iceil (float x) { int t=(int)x;return t+(x>0.0f&&(float)t!=x); }
```

`(float)t != x` は「小数部があった」そのもので、符号がキャストの間違えた向きを選びます。**主張が表現についてなら、総当たりで決着します** — `tools/test_flower_floor.c` が 2^32 個の float ビットパターン全部をライブラリと突き合わせ、NaN・無限大・int に入らない大きさ（どちらも未定義）だけを外して **26.5 億通り一致**します。10 秒です。

条件が無いことが利点です。あとから負を渡す呼び出しが増えても、証明し直すものがありません。

## 3.13 FPU の除算・平方根の種命令は、この石に載っている（GCC が出さないだけ）

§3.7 は「GCC は seed 命令を一度も出しません」と書いていて、それは正しいのですが、**命令が無いとは書いていない**のに無いように読めます。確認しました:

```
sqrt0.s  rsqrt0.s  recip0.s  div0.s  divn.s  maddn.s
nexp01.s  addexp.s  addexpm.s  mksadj.s  const.s
```

**11 個すべて `xtensa-esp32s3-elf-gcc` のインラインアセンブリで組み立てが通ります**（esp-15.2.0_20251204）。§3.7 がイメージ中に 14 本見つけたのは、それらが実行される石だからです。

一方で **`-mhard-float-div` / `-mhard-float-sqrt` / `-mhard-float-recip` / `-mhard-float-rsqrt` はこのツールチェインに存在しません**（`unrecognized command-line option`）。`--help=target` に浮動小数関係で出てくるのは `-mfused-madd` だけです。**つまりフラグ 1 つで手に入る話ではなく、Newton-Raphson の列を手で書く話です。**

値段の目安: `sqrtf` は実測 174〜188 サイクル（§3.7）。種＋2 回の反復は 10 命令台のはずなので、当たれば 1 桁です。`bell_hit` は棄却を生き延びた visit あたり 4.5〜5.4 回の `sqrtf` を呼んでいるので（§3.11）、そこだけで visit あたり 780〜940 サイクルが対象になります。

**まだ誰も書いていませんし、いま書く価値は下がりました。** `__divsf3` が実測 55〜67 だった（§3.7）ということは、**ソフト浮動小数の話全体が、この日まで思われていたより小さい**ということです。`sqrtf` は依然としてこの中で最大の項ですが、除算が 4 分の 1 だったのと同じ理由 —「同じクラスのルーチンだから同じ値段だろう」— で `sqrtf` の 188 だけは**単体計測なので信用できます**。それでも、手書きの Newton-Raphson が買うのは 1 種のシーンの 1 関数であって、根拠のある見積もりが取れるまで着手しない、というのが現在の判断です。書くなら ISA が定める列をそのまま使うこと — 種の精度は実装定義なので、反復回数を勘で減らすとビット一致が黙って壊れます。

## 4. パイプライン: ロードの直後に使ってはいけない

**これが最も効いた知見です。**

TRM表1.7-2が各命令の use / def ステージを定めています。関係する値:

| 命令 | use | def |
| --- | --- | --- |
| `EE.VLD.128.IP` / `EE.VLDBC.16.IP` / `EE.LDXQ.32` / `EE.VLD.L.64.IP` | 1 | **2** |
| `EE.VMUL.S16` / `EE.VMUL.U16` | 1 | **2** |
| `EE.VRELU.S16` | 1 | **2** |
| `EE.VADDS` / `EE.VSUBS` / `EE.ANDQ` / `EE.ORQ` / `EE.VUNZIP` / `EE.VMIN` / `EE.VMAX` | 1 | 1 |
| `EE.VST.128.IP` | 1 | — |

必要間隔は §1.7.1 の `D = max(SA - SB + 1, 0)`。def 2 の命令の結果を use 1 の命令が読む場合 D=2 となり、**直後に置くと1サイクル止まります**。間に独立した命令を1本挟めば止まりません。

ロードだけでなく **`EE.VMUL` と `EE.VRELU` も def 2** である点が見落とされがちです（esp-dlの資料は「0-1 cycle」と記載していますが不正確）。

### 実際に何が起きたか

海面カーネルv1（64命令）は、17本の定数ブロードキャストすべて、2本のunzip、2か所の乗算チェーンが「直後に使用」パターンでした。**約21ストール/ブロック**です。

対策は3つとも機械的です:

1. **定数を複数レジスタでダブルバッファする**。q2/q6/q7 の3本を回し、使用の2〜3命令前にロードする。
2. **索引ロードの書き込み先を交互にする**。2つの表を A→B→A→B と交互に発行すれば、最後のロードとunzipの間が自然に空く。
3. **乗算の結果をすぐ足さない**。独立した別チャネルの計算を挟む。

結果（海面、出力はビット一致のまま）:

| | 命令数 | loop | サイクル/ブロック | サイクル/命令 |
| --- | --- | --- | --- | --- |
| v1 | 64 | 1.43ms | 123 | 1.90 |
| v2 | 62 | **1.06ms** | **86** | 1.39 |

**26%の短縮が、演算を1つも変えずに得られました。** 新しくカーネルを書くときは最初からこの順序で書くべきです。

## 5. アラインメントは黙って壊れる

128bitアクセスはアドレスの**下位4bitを0に強制**します。例外は上がりません。アラインメントされていないバッファを渡すと、**意図しない場所を読み書きして静かに壊れます**。

対策として、カーネルに渡すバッファには必ず `__attribute__((aligned(16)))` を付けます。`board.c` の共有ストリップバッファがその例です。行の途中から処理を始める場合（blendの矩形が奇数x始まりの場合など）は、**行頭を16バイト境界までスカラーで進めてから**ブロック処理に入り、末尾も同様にスカラーで処理します。

行の長さが16の倍数であれば、基底さえ揃っていれば各行の先頭は自動的に揃います。240ピクセル×2バイト = 480バイトはその条件を満たします。

## 6. GCCのレジスタ共有に注意

定数表を歩くポインタには **early-clobber 制約 `"=&a"` が必須**です。

```c
const int16_t *kp;
__asm__ volatile(
    "2:\n"
    "  mov %[kp], %[k]\n"      /* ブロックごとに巻き戻す */
    ...
    : [kp] "=&a"(kp)
    : [k] "a"(k), ...);
```

`"+a"(kp)` と書くと、GCCは `kp` と `k` に**同じレジスタを割り当てることがあります**。そうなると `mov` が無効化され、巻き戻しが単なるインクリメントになり、2ブロック目以降が表の範囲外を読みます。コンパイルは通り、テストによっては通ってしまいます。

同様に、`loopgtz` はハードウェアループレジスタを操作するため、**コンパイラが駆動するループの内側に置いてはいけません**。カーネルは `__attribute__((noinline))` で切り出します。

## 7. loopgtz の256バイト制限

`loopgtz` のループ本体は**256バイト以内**でなければなりません。PIE命令はおおむね3〜4バイトなので、実質70命令程度が上限です。

超える場合は `addi` / `bnez` の通常ループにします。blendカーネル（本体292B）はこちらです。1ブロックあたり2命令の追加コストで済むので、無理にアンロールを減らすより素直です。

逆に、**アンロールで本体を256B超にしてしまうと `loopgtz` が使えなくなる**ため、命令数が減っても損をすることがあります。海面カーネルの2倍アンロールは、得られるのが `mov` 1本/2ブロックだけなのに対して制限ぎりぎりになるため見送りました。

## 8. ビット一致を保ったまま最適化する

カーネルは原則として**ビット一致**で書き、近似はそれ以外に手がなくなってから、絵を見比べて判断します。海面カーネルだけが近似で（`d266ecf`、RGB565が変わる画素10.1%、段差はR/B最大1・G最大2）、これは表引きを消すのに他の方法が無かったためです。ビット一致を原則とする理由は2つあります。

- **blend**: 条件を満たせない入力（グローバルα<255、マスク非整列）ではソフト経路にフォールバックするため、1でもずれると同じ画面上で段差が見えます。
- **海面・波**: スカラー参照実装をソースに残しておけるため、「アセンブリが何をしているか」の唯一の説明になります。近似を入れた瞬間、この関係が崩れます。

### 16bitレーンに収まらない式を書き換える

blendの合成式 `s*a + d*(255-a)` は最大65025で、signed 16bitレーンに入りません。恒等式で書き換えます:

```
c = min(s,d) + floor(|s-d| * a' / 255)      a' = (s<d) ? 255-a : a
```

`|s-d|` は `VMIN`/`VMAX`/`VSUBS`、`a'` は `EE.VCMP.LT.S16` の結果を `0x00FF` でマスクして `a` とXOR。分岐は要りません。

### /255 を厳密に計算する

`floor(x/255)`（x ≤ 65152）は `(x + (x>>8) + 1) >> 8` と厳密に一致します（総当たりで確認）。ただし x が16bitに収まらないので、**QACC（8レーン×40bit）**で計算します:

```
EE.ZERO.QACC
EE.VMULAS.U16.QACC diff, a'      ; QACC = x
EE.VMULAS.U16.QACC k127, k1      ; QACC = x + 127
EE.SRCMB.S16.QACC  q, sh8, 0     ; QACC = x >> 8 = t
EE.VMULAS.U16.QACC diff, a'      ; QACC = t + x
EE.VMULAS.U16.QACC k128, k1      ; QACC = t + x + 1
EE.SRCMB.S16.QACC  q, sh8, 0     ; q = (x + t + 1) >> 8
```

`EE.SRCMB.S16.QACC`（§1.8.54）のシフト量は**SARではなくARレジスタ**から来ます。定数1との乗算加算は、QACCへ定数を足すための常套手段です。

### 検証の手順

書いたカーネルは実機に載せる前にホストで検証します。実際に使った3段階:

1. **チャネル単位の総当たり**: 合成式やビット複製の展開を、入力の全域で参照実装と突き合わせる（blendでは s 256通り × dst 5/6bit全値 × a 256通り）。
2. **関数丸ごとのランダムテスト**: `-DRENDER_ACCEL_HOST_MODEL` のようなフラグでアセンブリを「同じレーン演算のC」に差し替え、ランダムな矩形・マスク・色で参照実装と `memcmp`。**先頭/末尾のスカラー処理とポインタ計算はここでしか担保できません**。
3. **起動時の自己検査**（採用は場合による）: バイトスワップでは `board_init` が両実装を同じバイト列に対して走らせ、一致した場合のみPIE版を有効にしています。

海面カーネルでは、スカラー版との10.3億通りの総当たりを書き換えのたびに再実行しました。

庭の行は 3 つのループ（粗い格子 22 命令、細かい格子 22、画素 135 → 融合後 114）で、ストールはゼロです。画素ループの 40 個の定数のうち 21 個が `.LD.INCP` に乗りました（`GARDEN_PIE_FUSE`、生成は `tools/pie/fuse_pixels.py`）。融合できる上限は「ホストが空いていること」ではなく**歩く順序**で決まります — 定数の walk は load の**プログラム順**そのものなので、load が別の load を追い越すと 2 つの定数が静かに入れ替わり、組み立ても実行も通ってどこかの色だけが狂います。加えて、消す 1 命令が stage-2 の producer と consumer の間の唯一の隔てだった場合、スロットを 1 つ節約してストールを 1 つ買うことになるので、候補は `stalls.py` のモデルで**両方の綴り**（融合版と対照版）を検査してから採用しています。**`kernel=` は画素ループだけの値ではありません**（幹・林冠・草はまだスカラーで、同じ `garden_row` の中にいます）。その内訳は `flower.c` の `SPLIT` 行が `pixels=` / `decor=` として出します。予測を 2 割外した理由は §3.6。

海面はスカラー版14.2msから通算で**16倍**になりました。

ホーム画面の内訳（現在）:

```
LEVEL WAVE     mode=0 fps=30.3 draw=21.11 | prep=0.99 loop=1.75 (kernel=1.67) hud=2.63 send=15.68
OCEAN + STARS  mode=1 fps=30.3 draw=19.93 | prep=1.06 loop=0.89 (kernel=0.69) hud=2.44 send=15.47
```

`kernel` はベクトル行だけの時間です。波は全135行を描くので `loop` とほぼ一致し、海面は水平線より上の37行をスカラーで塗るぶんだけ差が出ます（§3.5）。

JSアプリ（組み込みHello World）の内訳。`kernel_ms` はPIEカーネルが自分で数えたサイクルです:

```
PAINT render_ms=9.52 kernel_ms=3.74 send_ms=21.9 accel=53 software=2
```

> **この行の数値は過大です。** 計測に使った `jsperf.py` は0.2秒ごとにEnterを押して再描画を促すので、**その間ずっと効果音が鳴っていました**。
>
> 原因は判明しています。効果音1回の合成に **25.6msのCPU** を使っていました（音の長さ59.4msの43%）。`audio_task` は優先度7で、しかもIDFが「FPUを最初に使ったコア」にタスクを自動ピン留めするため、描画タスクと同じcore 0に張り付いてCPUを時分割していました。波形を起動時に一度だけ生成する方式（`bf82769`）で解消しています。
>
> **v1とv2の比較は同じ条件で取ったので方向は保たれます**が、絶対値は数割高いものとして読んでください。修正後・80MHzでの実測は `turn 1.62 / render 7.92 / send 7.67` です。

**render_ms のうちPIEカーネルは4割弱で、残りはRust側のマスク生成**（`composite_mask` のper-pixelループ）です。アクセラレータの差し込み口の外なので、PIEでJSアプリをこれ以上速くする余地は小さいという結論になります。この比率自体は音の有無で変わりません（9.52/3.74 と 8.1/3.2 はどちらも約4割）。

### 計測についての教訓

最初に得た「pixels 18.6ms」という数字は、**ループ(14.2)・HUD(3.9)・準備(0.9)を混ぜたもの**でした。分割した瞬間に優先順位が変わりました。カーネルを書く前に、まず**削ろうとしている部分だけを切り出して測る**べきです。

**計測スクリプト自身が測定対象を変えていないか**も確認してください。上のJSアプリの数値は、再描画を促すために押していたEnterが効果音を鳴らし、それが3〜4割の水増しになっていました。**キー入力で画面を動かす計測は、その入力の副作用ごと測っています。**

**ビルドが変われば同じコードの実測も変わります。** 波のカーネルは、他の場所にコードを足しただけのビルドで 1.30ms と 1.54ms を行き来しました（15%）。関数の配置がずれて命令キャッシュ（16KB、両コア共有）の当たり方が変わるためです。**数%の差を主張するには、同じバイナリ内での比較にするか、この揺れを超える必要があります。**

**共有ツリーでは、比較する複数のビルドが同じソースから出たことを確認してください。** これは疑いではなく検査で、1 コマンドです — 4 本のビルドを連続で回し、その窓の中でソースが触られていないかを後から聞きます:

```
find main components apps -type f \( -name '*.c' -o -name '*.h' -o -name CMakeLists.txt \) -newermt "<開始時刻>"
```

2026-09-09、A/B/C/D の 4 本を作っている 30 分のあいだに別セッションが `main/main.c` と `main/ui/shell.c` と `main/CMakeLists.txt` を書き替えていました。**4 本のうち D だけが旧ソース、A と C が新ソース**で、気づいたのは A のサイズが 2,324,480 から 2,329,616 へ動いたからです。**変更を入れていないビルドのサイズが動いたら、それは自分のツリーではありません。** 4 本まとめて焼き直して、上の `find` が空を返してから渡すこと。窓は 4 分で済みます。

**共有ツリーでは「自分が変えたつもりのない変数」を疑ってください。** 複数のセッションが同じ作業ツリーを使っていた日、他人の未コミット変更を拾ったビルドで3回誤った結論を出しました。うち1回は「命令キャッシュを32KBにしたら転送が40%速くなった」という物理的にありえない数字で、正体は別セッションが入れたSPIクロックの変更でした。**測定対象の設定値を起動時にログへ出す**のが安い対策です（`board.c` が `LCD SPI %d Hz` を出しているのはこのため）。

同じ理由で、**描画カーネルの高速化がフレームレートに効くとは限りません**。ホーム画面では `send=15.4ms` が支配的で、海面の `loop` を1.43msから1.06msにしてもfpsは30.3のまま動きません。効いたのはJSアプリのblendだけです（`render_ms` がフレーム時間の主要項だったため）。

### 最適化のつもりで遅くした例

バイトスワップを16bitずつではなく32bitずつ処理する版を書いたところ、転送が**16.5ms → 24.2ms に悪化**しました。`board.c` はプロジェクト既定の `-Os` でビルドされており、4バイトの `memcpy` が関数呼び出しのまま残っていたためです。

最適化の前後は必ず実測してください。「明らかに速いはず」の変更が逆効果になることは実際に起きます。同様に、除算をビットシフトや逆数乗算に置き換える試みも**測定可能な差が出ませんでした**。このコアにはハードウェア除算器があるためで、これは元に戻しています。

## 10. 新しいカーネルを書くときのチェックリスト

0. **機械の下限と引き算する**。§3.5のとおり `命令数 + 0.6×ストア数 + ストール数` が下限で、実動作ではそこに3〜4割乗る。`python tools/pie/stalls.py <file> <kernel>` が出してくれる。届いているなら、そこから先は命令を減らすしかない。
1. 削ろうとしている処理を**単独で計測**する。フレーム全体のどれだけを占めるか、そして**その計測値に他のものが混ざっていないか**を確認する（§3.5）。
2. スカラー参照実装を先に書き、`__attribute__((unused))` で**ソースに残す**。
3. バッファに `__attribute__((aligned(16)))` を付ける。行の途中から始まる場合はスカラーの頭・尾を用意する。
4. SARを1つ決めて先頭で `wsr.sar`、以降のシフトはすべて定数乗算で表現する。
5. **ロード・`VMUL`・`VRELU` の結果を直後に使わない**。定数は複数レジスタでダブルバッファし、2〜3命令前にロードする。
6. 定数表を歩くポインタは `"=&a"` で宣言する。
7. 本体が256Bを超えるなら `loopgtz` ではなく `addi`/`bnez` を使う。
8. ホストで検証してから実機に載せる。手順は [tools/pie/README.md](../tools/pie/README.md)：`run_models.py`（式の総当たり）→ `test_kernels.py`（アセンブリを命令レベルで実行してスカラー参照と比較）→ `stalls.py`（§4 のストールを静的に列挙）。
9. 実機で計測し、**キャプチャで見た目も確認する**。数値が良くても絵が壊れていることがある。
