# ESP32-S3のHTTPSハードウェアアクセラレーション設計

ESP-IDF 6.0.1とmbedTLS 4.0.0を対象とする。最初にSHA-256のDMA完了待ちを割り込み化する。HTTPSで利用できる回路全体は末尾の表で管理する。

## 現在のSHA経路

ファームは `CONFIG_MBEDTLS_HARDWARE_SHA=y` でビルドされている。ESP-TLSからmbedTLSのPSA Cryptoを経由し、EspressifのSHAドライバがハードウェアを呼ぶ。SHA-256の更新処理は、SHA/AES共有ロックを取得し、ハッシュ状態を復元し、処理後の状態を読み出してからロックを解放する。

ESP32-S3では、64バイトに切り下げた入力長が256バイトを超えるとPSAのSHA-256更新処理がDMAを選ぶ。DMA非対応の入力はIDFがブロック処理へ戻す。DMAではIDFが入力を最大3,968バイトずつに分け、必要なら未処理の先頭ブロックを別の記述子につなぐ。共有GDMAを起動した後、`sha_hal_hash_dma()` でSHAを始動し、`sha_hal_wait_idle()` で完了をポーリングする。

参照箇所はESP-IDFの `components/mbedtls/port/psa_driver/esp_sha/core/psa_crypto_driver_esp_sha256.c` 84–118行、`components/mbedtls/port/sha/core/include/esp_sha_internal.h` 34、49–56行、`components/mbedtls/port/sha/core/sha.c` 301–308、316–374行。

## 割り込み待ちの仕様

- **差し込み位置**は `esp_sha_dma_process()` のGDMA設定成功後、`sha_hal_hash_dma()` の前後とする。始動直前に割り込みを準備し、始動後の完了待ちを切り替える。PSAとmbedTLSの公開APIは同期のまま。パディング、途中状態の保存、ダイジェストの読出し、記述子、DMA可否判定、キャッシュ処理はIDFに委ねる。
- **対象**はESP32-S3の検証用オプションと、Core 0に固定した既存HTTPS計測タスクの両方で許可されたSHA-256 DMAチャンク。組み込み直後は、実測済みのDMA合計3,968バイトを既知値試験で再現し、差し込み位置と完了処理を照合する。実HTTPSで使うサイズ範囲は次節の比較で決める。複数チャンクはチャンクごとに判定する。通常ビルドのオプションは初期値で無効。
- **資源**はCore 0の専用割り込み1本と静的な完了セマフォ1個。最初のHTTPS試験の前に、既存の検証タスクが同じコア上で `ESP_INTR_FLAG_LOWMED` を使って一度確保する。通常のアプリタスク、記述子、入力バッファをそのまま使う。割り込み枠が確保できない場合は、その起動中はポーリングを使う。
- **順序**は共有ロックを保持した状態で、割り込み元をマスク、古い通知を捨てる、完了フラグをクリア、待機状態を設定、割り込み元を有効化、SHAを始動の順。ISRは完了フラグを消し、待機中の転送へセマフォを返す。タスクは通知後もハードの完了を確認してから結果を読み出す。完了後は割り込み元をマスクして待機状態を解除し、IDFが元の手順で共有ロックを返す。ISRと待機タスクを同じCore 0に置く前提で検証する。通知が待ちに入る前に届いてもセマフォに残る。転送中にタスクを外部から削除せず、HTTPSの呼び出しが戻ってから試験対象の登録を解除する。タスク優先度は現行のまま比較する。
- **通知の期限**は初期値を2 RTOS tickとする。現行の1 kHz設定では約2 msの設定値であり、実際の起床時間はスケジューリングにも依存する。期限切れでは、割り込み元をマスクしてフラグを消し、その起動中は割り込み経路を停止する。進行中の転送は既存のポーリングで完了まで待つ。入力、記述子、SHA/AES共有ロックはその間保持する。待ち通知の期限はDMAのキャンセルやハード障害の復旧期限を意味しない。真にハードが停止した場合の挙動は既存IDFと同じ。
- **実装の置き場所**はバージョンを固定したESP-IDFパッチ。実験で使ったグローバルな `--wrap=sha_hal_wait_idle` は比較用として残し、統合コードはDMAを始動する1か所に置く。brokerのビルド入力として適用先のIDF版とパッチを照合する。SHAとAESの排他はIDFのロックで行い、追加のジョブキュー、DMAチャネル、暗号ワーカー、スケジューラは設けない。

SHA回路の動作と割り込み割り当ては、[ESP32-S3 TRM 18章](https://documentation.espressif.com/esp32-s3_technical_reference_manual_en.pdf)と[ESP-IDFの割り込み割り当て](https://docs.espressif.com/projects/esp-idf/en/stable/esp32s3/api-reference/system/intr_alloc.html)を参照。

## 実機での判断基準

1. まず同じ証明書検証付きHTTPSで、SHAの方式、DMAサイズの区分、IRQ対象件数、ハンドシェイクと応答取得それぞれの時間を記録する。記録するのは集計値と交渉結果。SHAやTLSの入力内容、秘密鍵やセッション鍵は記録しない。今回の既知値試験と同じサイズの転送が実通信でどの程度あるかを確認する。
2. IDFのPSA API経由で既知値と分割更新を照合する。DMAの境界、複数チャンク、DMA非対応メモリ、AESと別SHAコンテキストの同時利用、割り込み枠不足、通知を意図的に抑止した経路も確認する。証明書検証の成功ケースと、無効な証明書の拒否を比較する。
3. 同じモデル入りファームをbrokerで実機へ書き込み、ポーリングと割り込みを交互に繰り返す。同量の通信を処理して、SHAおよびHTTPSタスクのCPU時間、両コアのアイドル率、SHA/AESロックの保持時間、HTTPSの所要時間、LCDのFPSと最長間隔、内部RAM低水位と最大連続空きブロックを比較する。使用する暗号方式と証明書検証条件は両試験でそろえる。
4. 実HTTPSで観測した「SHA方式 × DMAチャンク長」ごとに、発生件数に1件あたりのCPU削減時間を掛け、接続全体への寄与を見積もる。3,968バイトが少なければ、よく出る短いDMAチャンクから比較する。ポーリング同士の反復で測ったばらつきを上回るCPU削減が同量の通信で繰り返し出て、SHA/AESロックの保持時間、HTTPSの所要時間、LCDの最長間隔、内部RAMに再現する悪化がなければ、その範囲でIRQ待ちを使う。サイズによる損益の境界が安定していれば、そこを方式ごとの閾値とする。効果が薄い範囲はポーリングで動作させる。
5. 3,968バイトの合成試験ではCPU時間が1件あたり57.17 µsから41.18 µsに減った。Core 0のアイドル率は73.33%から75.80%、LCDは19.97 fpsと19.91 fpsだった。この値は組み込み時の照合に使う。SHAの採否で他の回路の着手順や採否は決めず、それぞれ実際のHTTPSの呼び出し頻度、CPU削減量、共有資源の待ち時間で判断する。

## 開発ループ

1. **対照を取る。** 同じCardputerとモデルで、現行ファームのWi-Fi接続・再接続、証明書検証付きHTTPS、LCD描画をbroker MCPで測る。新規TLS接続と再利用する接続を分け、同じ要求・応答量・交渉結果で比較する。SHAの方式とチャンク長、AES・RSA/MPIの経路、GDMAのコピーと競合を集計し、現行設定同士の反復で計測のばらつきを取る。3,968バイトの合成試験は実装照合用の参照として扱う。
2. **回路ごとに単独で試す。** 負荷の頻度とCPU時間から、効果の大きそうな変更を一つ選ぶ。対象経路、予想する効果、比較指標を試験前に記録する。Astraが高難度の実装と性能評価を担当し、同一モデル入りのビルド・書き込み・実機計測はbroker MCPを使う。SHAの採否をAES、RSA/MPI、eFuse鍵用HMAC、DS、GDMAの着手条件にしない。
3. **採否を決める。** 暗号の結果と証明書検証を先に照合する。適格なA/Bペアについて同量通信あたりのCPU時間を比較し、削減量が現行設定同士のばらつきを上回って複数ペアで再現するかを見る。HTTPS所要時間、共有ロックの保持・待ち時間、LCDの平均FPSと最長間隔、最低空き内部RAMと最大連続空きブロックも同じペアで見る。効果が再現し、悪化も再現しなければ観測した条件で「採用」。対象経路が使われないか効果が薄ければ「現行維持」。不足している証拠や試験環境があれば、担当と再開条件を付けて「保留」。例えばeFuse鍵用HMACとDSの相互TLSは、対応する資格情報を持つ試験環境が整った時点で回す。
4. **差が曖昧なら仮説を変える。** 対象が少なければ頻出経路へ、CPU差が小さければ測定区間やサイズ範囲へ、待ちが悪化すれば共有ロックの保持区間へ戻る。次に何を変えれば違いが出るか書いてから再試験する。
5. **採用分を組み合わせて確認する。** モデル入りの統合イメージをbroker MCPでビルドし、同じイメージを書き込んで通信と描画の回帰を確認する。単独で合格した回路を組み合わせて回帰が出た場合は、競合する組み合わせを切り分けて採否を見直す。20 fpsは独立した達成指標として実測値を記録する。

非公開のproblem-loop-harnessケースは `.cache/ap4/https-hw-loop/` に置く。 `plan.json` が工程、`state.json` が進行状態。ハーネスはローカルの証拠を照合する。broker操作とAstraへの依頼は各工程が始まった時点の担当が行う。ジョブIDとイメージ識別子を保存し、読み取りが途切れたときは既存ジョブの状態を照合してから次に進む。

ケースの `profile.json`、`decisions/<回路名>.json`、`combined.json` には `outcome`、`reason`、ケース内の証拠ファイルの `path` と `sha256` を記録する。実機合格を示す記録にはビルドID、書き込みID、ELF SHA-256を添える。保留には `owner` と `resume_when` を添える。六回路それぞれの判断がそろい、採用分の統合検証が通れば、この周回を閉じる。

## HTTPSで扱う回路

| 回路 | HTTPSでの役割と設計対象 |
|---|---|
| **SHA** | ハンドシェイクのトランスクリプト、証明書関連のハッシュ、HMACの基礎演算。現行ビルドで有効。最初にDMA SHA-256のIRQ待ちを試し、SHA-384/512も実際の使用量を見て対象を広げる。 |
| **AES / GDMA** | 交渉でAES系を選んだ場合のレコード処理。AESハードウェアと長いAES転送の完了割り込みは現行ビルドで有効。AES演算とGCMの認証計算は別々に計測し、入力コピーとSHA/AES共用GDMAの待ちも調べる。GDMAは転送資源として両ドライバで管理する。 |
| **RSA / MPI** | RSA証明書やRSA署名の検証に使う多倍長演算。ハードウェアMPIと対応する完了割り込みは現行ビルドで有効。方式別に呼び出し、CPU時間、排他時間を確認する。S3のECDHE／ECDSAには専用ECC回路がなく、点演算は別の計測対象。 |
| **eFuse鍵用HMAC** | 端末にプロビジョニングされた鍵による認証や、DSの鍵導出に使える。TLSが接続ごとに導出する鍵のHMACは、既存のPSA経路でSHA回路の恩恵を測る。eFuseを使う認証は、その用途と対応する接続先が決まった段階で試験する。 |
| **RSA電子署名（DS）** | 対応する資格情報を供給する相互TLSのクライアント署名で使える。サーバー証明書の検証はMPI側。DSはHMAC、SHA/AES、MPIにもまたがって排他を取るため、相互TLSの試験で保持時間を確認する。 |

回路の利用条件は[ESP32-S3 TRM 18〜22章](https://documentation.espressif.com/esp32-s3_technical_reference_manual_en.pdf)と[ESP-IDFのDS・相互TLSの仕様](https://docs.espressif.com/projects/esp-idf/en/v6.0/esp32s3/api-reference/peripherals/ds.html)を参照。
