## 1. 目的

Cardputer ADV の quickjs-ng を対象に、デバイス完了通知と JS 実行を FreeRTOS に統合し、必要に応じて VM の中断・再開、共有スタック領域、コンパクションへ拡張する。

優先する成果は、画面・音声・I/O への応答性、実行状態の保持に必要な RAM の削減、負荷の観測可能性である。JavaScript の計算速度向上やハードリアルタイム性は保証しない。

対象ハードウェアは ESP32-S3FN8、PSRAM なし。QuickJS 本家ではなく、このプロジェクトが取り込む quickjs-ng を実装基準とする。

## 2. 現状と用語

調査したローカル実装では、以下の構造になっている。実装着手時には依存 revision とビルド設定を固定して再確認する。

- `main/app_session.c`: 各 pump で完了を取り込み、JS のフレーム処理を経て描画する。
- `main/pocket/pocket_api.c`: 完了済み要求の resolve / reject を JS 所有側で呼ぶ。
- `.cache/components/pocketjs_guest/src/guest.c`: `drain_jobs()` が `JS_ExecutePendingJob()` をキューが空になるまで呼ぶ。
- `managed_components/espressif__quickjs-ng/quickjs-ng/quickjs.c`: runtime ごとの FIFO ジョブキュー、C 再帰による通常の JS 呼び出し、`alloca()` による通常フレームの値領域、ヒープ上の async/generator 保存状態を持つ。
- `JSVarRef` は生存フレーム内の値を生ポインタで参照し、変数の寿命がフレームから分離すると自身の保持領域へ切り替える。

| 用語 | 本書での意味 |
| --- | --- |
| FreeRTOS タスク | C スタックを持つ OS の実行単位 |
| VM タスク | 提案する JS 実行状態の保持単位。FreeRTOS タスクと一対一にしない |
| ジョブ | Promise reaction や async 再開など、QuickJS がキューに登録する処理 |
| VM フレーム | JS 関数一回分の引数、変数、オペランド、復帰情報 |
| トランポリン | 次のフレーム・保存状態を選び、VM の共通実行ループへ戻す処理。スタック内に実行コードを生成しない |
| セーフポイント | 生ポインタや一時状態を整理し、中断・必要なら移動できると定義した地点 |
| コンパクション | 生存領域を移動して空き領域をまとめる処理 |

未解決 Promise は実行待ちジョブではない。FIFO が空なら未解決 Promise が残っていてもホストに戻れる。一方、ジョブが次のジョブを追加し続けると drain は終わらない。

FreeRTOS は別タスクへプリエンプトできるが、同じタスクの後続処理へ進むことは保証しない。標準的な FreeRTOS のタスク切り替えはスタック領域を移動しない。

## 3. 全レベル共通の制約

1. 同一 `JSRuntime` の操作主体は一つとする。別タスク・ISR はネイティブな完了情報だけを送る。JSValue の作成・参照カウント変更・resolve・GC は所有側で行う。
2. Promise の状態遷移、thenable の取り込み、例外の伝播は既存実装を維持する。Promise ごとに OS タスクを生成しない。
3. runtime 全体の FIFO 順序を維持する。ジョブ追加と、外部イベントの JS への配送順序を区別する。
4. 完了通知を黙って落とさない。容量不足は要求受付時の拒否、予約済み完了スロット、または再取得可能な完了記録で処理する。所有タスクが自分の満杯キューを待つ構造は禁止する。
5. タスク ID・要求 ID・フレーム ID の再利用には世代管理を設け、終了済みセッションへの遅延通知を無効化する。
6. 中断は例外ではない。中断時に finally の実行やフレーム解放を開始しない。失敗・キャンセル・正常完了を別の状態として扱う。
7. 解放時には保持中の JSValue、クロージャ、Promise、ネイティブ資源をそれぞれの所有規則に従って処理する。
8. 保守する改変は追跡可能なソースまたは再適用可能なパッチに置く。生成・取得済みの managed_components / .cache の直接編集だけを成果物にしない。

| L3 | 相対参照による移動可能スタック | フレーム、クロージャ、再開処理 | 非常に高い | 生ポインタ補正への依存を減らす |

### GMP から取り入れる設計

Go の G（保存する処理）、M（OS スレッド）、P（実行権と管理資源）の分離を参考にする。本仕様では VM タスク、実行用 FreeRTOS タスク、runtime の実行権を分ける。JSRuntime は共有ヒープ等も含むため Go の P と同一視しない。[Go runtime の設計説明](https://go.dev/src/runtime/HACKING)

- 初期構成は runtime 一つにつき所有 FreeRTOS タスク一つ。VM タスクごとに C スタックを予約しない。
- VM の保存領域は可動化の対象、スケジューラとアロケータを動かす C スタックは固定とする。
- 待機・起床・実行可能への遷移を明示し、待機中の継続のために OS タスクを占有しない。
- 中断中に別の同期 JS を動かせるとは仮定しない。予算による中断と await による待機を区別する。
- 複数 P、work stealing、ネイティブ呼び出しでブロックした所有タスクの他タスクによる代行は初期範囲に含めない。

## 6. L1: FreeRTOS ネイティブなホスト実行基盤

### 機能

- runtime の所有タスクを明示する。専用タスク化する場合は、UI が直接 JS や可変の描画状態に触れないよう受け渡しを設計する。
- ネイティブ完了記録のキューと、起床用通知を設ける。タイマーと ISR は JS を直接呼ばない。
- 未処理ジョブもイベントもない場合だけ待機する。待機に入る直前の通知との競合で起床を失わない。
- 件数・時間によってジョブ間でホストへ戻る。新しい JS ジョブの最中には割り込まない。
- キューを残したまま戻る場合は、次回実行を保証する。継続処理は新しい外部イベントより優先する互換モードを既定とする。

### 意味論

未完了の drain の間にネイティブな描画・I/O 処理を許すが、新しい JS コールバックや resolve の配送は保留し、従来の順序を保つ。通知の取り込みと JS への配送は分離する。

既存 `drain_jobs()` の未処理 rejection 判定は、予算切れごとに確定しない。従来相当のジョブ処理完了地点まで遅らせ、同じ連鎖内の catch を誤って未処理と報告しない。

ジョブ一件が無限ループなら L1 だけではホストに戻れない。既存の暴走停止ガードを維持する。単なる taskYIELD は低優先度タスクへの実行保証にならないため、優先度と待機方針を別途設定する。

### 完了条件

- VM 本体の変更なしで動作する。
- FIFO、then/catch/finally の観測順序が基準と一致する。
- 完了通知の集中、満杯、停止直後の通知、通知と待機の競合で取りこぼし・永久待機がない。
- 追加タスクのスタックを含む RAM 増分と応答遅延の変化を実測する。

## 7. L2: 移動しない VM スタックと中断・再開

### 内部段階

| 段階 | 変更 | まだできないこと |
| --- | --- | --- |
| L2a | フレーム・値領域を移動しない VM 管理領域へ確保 | C 再帰が残る間の一般的な中断 |
| L2b | JS 同士の call / return を明示フレームと単一実行ループへ変更 | ネイティブ呼び出しをまたぐ自由な中断 |
| L2c | セーフポイント、状態保存、再開、例外・GC・破棄を統合 | 同一 runtime の別 JS ジョブへの切り替え |

### L2a のメモリ確保: 非移動セグメント方式

初期方式は「汎用プールからセグメントを確保し、セグメント内に VM フレームを積む」の二層構成とする。JS の call / return ごとに汎用 malloc / free を呼ぶことを既定にしない。

```text
runtime 所有のメモリプール
    └─ セグメントの確保・返却
         └─ VM タスクがフレームを push / pop
```

- フレームは原則として一つのセグメント内に収める。必要量が残量を超えた場合、新しいセグメントを追加する。
- 大きいフレームには要求量を満たす専用サイズを使う。標準セグメントサイズは L0 の使用量分布から決める。
- L2 では生存セグメントを移動しない。容量不足時は追加セグメントで対応し、生ポインタを無効化する realloc を呼ばない。
- pop 時には値を解放し、クロージャが保持する変数を切り離してから領域を再利用する。async/generator などが独立して保持する状態は、元のセグメントへの隠れた参照を残さないよう寿命を管理する。
- 空になったセグメントは共有プールに返すか、上限付きで再利用用に保持する。長寿命の保存状態が領域を保持する場合は、その予約量も計測する。
- 固定プールの予約量、プール管理領域、セグメント内の未使用量を RAM 使用量へ含める。固定プール化だけで省メモリになるとは主張しない。

estalloc は、mruby/c 由来のプール型アロケータであり、この層の実装候補・比較対象とする。サイズ別リストとビットマップ、分割、隣接空きブロックの結合を参考にする。[estalloc README](https://github.com/picoruby/estalloc)

```text
空きの結合: [ 使用中 A ][ 空き ][ 空き ][ 使用中 B ]
                         ↓
             [ 使用中 A ][ 大きな空き   ][ 使用中 B ]
```

この操作は A/B を動かさず、参照補正も不要である。L4 の生存領域を移動するコンパクションとは区別する。

確認した estalloc 実装には First-Fit の走査経路がある。README の O(1) 表記だけで最悪割り当て時間を保証しない。realloc のコピー、デバッグ処理、統計走査も別に測定する。[estalloc 実装](https://github.com/picoruby/estalloc/blob/master/estalloc.c)

採用前に revision・ライセンス・設定を固定し、対象のアラインメント、要求サイズの加算・乗算オーバーフロー、容量上限、OOM 後の整合性を検証する。既存アロケータと同じ確保履歴で比較し、コード量・管理 RAM・最大空きブロック・最悪待ち時間で選ぶ。

プールの操作は runtime 所有側に集約する。通知を送る ISR からプールを操作しない。排他コールバックを使う場合も、探索・コピー・統計処理による割り込み禁止時間を監査する。アロケータの排他だけで QuickJS の並行操作が安全になるとは扱わない。

### フレームの保持内容

関数・this・必要な new.target、引数、ローカル変数、オペランド、PC、SP、呼び出し元、復帰先、例外処理に必要な状態、クロージャ参照を保持する。列挙した内容は設計要件であり、現在の構造体の単純置換とはしない。実装時に各 opcode と呼び出し種別を監査する。

通常呼び出し、constructor、可変引数、getter/setter、Proxy、eval、組み込み関数からの JS 呼び出しを分類する。未対応経路は従来の同期呼び出しとして囲い、中断禁止を明示する。黙って仕様を変更しない。

### 実行契約

提案内部 API は次の状態を返す。既存公開 API への追加を確定するものではない。

```c
typedef enum {
    VM_DONE,
    VM_YIELDED,
    VM_WAITING,
    VM_FAILED
} VMRunStatus;

VMRunStatus vm_run(VMTask *task, const VMRunBudget *budget);
```

- `VM_YIELDED`: 現在のジョブを継続する必要がある。runtime 内の他の JS は実行しない。ネイティブな別処理には制御を渡せる。
- `VM_WAITING`: await など言語上の中断を表す。既存 Promise 機構に従い他のジョブを処理できる。
- `VM_DONE`: 対象の実行単位が完了した。
- `VM_FAILED`: 例外または定義済みの失敗。yield と区別して処理する。

### opcode による中断確認

初期方式は、選択した opcode の処理入口または処理完了後に固定の中断確認を置く。直接ジャンプ方式では選択したエントリからチェック付き処理へ飛び、switch 方式でも同じ地点に確認を置く。通知によるジャンプテーブルの書き換え・切り替えは採用しない。

通常の算術・ロード命令すべてには確認を追加しない。要求フラグと予算を確認する頻度を絞り、状態保存は実際に中断するときだけ行う。時刻取得も確認地点で間引く。命令カウンタを使っても実行時間の上限保証とはしない。

| 命令群 | 初期の監査対象 |
| --- | --- |
| `goto`, `goto8`, `goto16` | 後方分岐を中心に、分岐先 PC を確定してから確認 |
| `if_true`, `if_false`, `if_true8`, `if_false8` | 条件値を処理し、次の PC を確定してから確認。短縮形も漏らさない |
| `call`, `call0`～`call3`, `call_method`, `tail_call`, `tail_call_method` | 呼び出し準備状態の所有権が確定する地点 |
| constructor / apply / eval の各経路 | C コールバックとの境界を個別に監査し、未対応経路は中断禁止 |
| return 系 | 結果を呼び出し元へ渡し、フレーム寿命を整理した地点 |

現行定義に後方分岐専用の opcode はない。命令処理内で分岐方向を判定する。専用 CHECKPOINT 命令の追加は、既存 opcode への確認で不足することが測定された場合の拡張候補とする。

中断要否と中断可能性を分ける。ネイティブ実行深さなどの理由で停止できない場合は要求を保持して通常処理を続け、次の安全な地点で応答する。確認ルーチン自身を再実行するループには入らない。

再開 PC の契約を地点ごとに記録する。opcode を読み取って PC が進んだだけの地点なら、命令先頭に戻して保存するか、デコード済みの状態を保存する。実行済みの分岐を再実行したり、未実行の call を飛ばしたりしない。

既存の割り込み確認位置を調査し、重複を減らす。ただし例外停止用の確認位置を無条件に再開可能と判断しない。対応ビルドの全ループ経路が確認地点を通ることをバイトコードと実行の両方で検証する。

### セーフポイントとネイティブ境界

- 初期実装は監査済みの命令境界・後方分岐などに限定する。「すべての命令境界が安全」とは仮定しない。
- 中断時に C ローカルの一時 JSValue の所有権と PC/SP を既知の保存領域へ退避する。
- ネイティブ実行深さを追跡し、C が同期的な JS 戻り値を待つ区間ではホストまで戻らない。
- 非同期 I/O は Promise を返して C の呼び出しを終了する。長時間ブロックする C 関数は分割または別ネイティブタスクへ移す。
- GC から中断中の値を到達可能にする。既存の「実行中なら回収対象にならない」という仮定を監査する。
- finally を含む例外巻き戻し、async/generator の状態遷移、スタックトレースを維持する。

通知側は完了記録を公開した後に起床・中断要求を送る。要求の公開と消費には適切な atomic / FreeRTOS プリミティブを使い、通知と消去の競合で要求を失わない。VM 側が停止位置を決定する。

```text
ネイティブ完了 → 記録・中断要求
    → 選択した opcode のセーフポイント
    → 状態保存 → vm_run() がホストに戻る
    → 通知取り込み・ネイティブ処理
    → 同じジョブを再開
```

同期ジョブが予算中断中の場合、resolve と別の JS ハンドラ実行は保留する。通知取り込みの遅延改善と JS ハンドラ実行の遅延改善を別々に報告する。

### 完了条件

- 純粋な JS の深い呼び出しで C スタック使用量が深さに比例しない。
- 監査済みセーフポイントで停止し、再開後の値・副作用・例外が非中断実行と一致する。
- 同期 JS の途中に別 JS を挟まない。中断によって共有オブジェクトの状態が不意に変化しない。
- 中断状態での GC、OOM、終了、例外、finally、クロージャ保持を検証する。
- 正確な最大中断遅延を主張する場合は、最長の中断禁止区間も測定する。
- セグメント追加・境界越え・返却で値とクロージャの参照が壊れない。アロケータ比較で内部余白・外部断片化を分ける。
- 各確認地点の直前・直後に中断要求を発生させ、命令や副作用の重複・欠落がない。通知なし通常経路の性能低下も測る。

## 8. L3: 相対参照と移動可能スタック

### 参照方式

固定位置のタスク記述子を「根元」とし、現在の配置を保持する。色はタスク ID / 世代 ID で表す。

- 一括で移動する連続領域: TaskId + offset。
- 独立に移動する分割領域: TaskId + SegmentId + offset、または FrameId + slot。
- 断片ごとに異なる移動量を、根元の一つの加算値で表現しない。

`JSVarRef.pvalue`、フレーム間リンク、runtime の現在フレーム参照、async/generator 保存状態など、移動領域を指すすべての入口を台帳化する。単純に全 JSContext を走査するだけでは不十分である。

### 実行中のアドレス

実行中は `var_buf` などを生ポインタとしてキャッシュしてよい。中断・移動後は必ず再取得する。領域拡張時の移動も同じ規則に従う。

外部へ生ポインタを渡す区間は pin を取得する。pin がある領域は移動しない。初期実装ではネイティブ呼び出し中の移動を全面禁止する。ヒープ上の JS オブジェクト本体は本仕様の移動対象ではない。

estalloc などの realloc を利用する場合も、返った新しいアドレスだけを保存して完了とはしない。移動条件、全参照の再解決、失敗時の旧領域保持を VM 側で保証する。L2 の追加セグメント方式からの変更は L3 の移動検証を通してから有効化する。

### 完了条件

- テスト用の明示移動 API で、セーフポイントにある領域を移動・再開できる。
- 複数クロージャが同じ変数を共有し続ける。
- 移動後に旧領域を毒化し、旧ポインタへのアクセスを検出する。
- ID 世代不一致、pin 中の移動要求、OOM が安全に失敗する。
- C レジスタ・スタックの任意の数値をポインタと推測して補正する方式は採用しない。

## 9. L4: コンパクション

### 方針

- まず解放領域を再利用し、毎回の解放では詰め直さない。
- 空き総量は足りるが要求を満たす領域がない場合、または明示した閾値で実行する。
- runtime の所有側が、VM をセーフポイントで止め、移動可能性を確認する。
- 移動計画、コピー、対応表更新を外部から中途半端に観測できない形で行う。
- 重なる移動は memmove 相当の安全性を持たせる。対象を指す根はすべて更新するか間接参照で維持する。
- 非移動領域・pin により空きがまとまらない場合は、移動量を増やして無制限に再試行しない。
- 分割実行する場合は、各移動単位を完了してからホストへ戻る。未完了のコピー先から VM を再開しない。
- コンパクションを GC と混同しない。生存スタックの移動だけで、JS オブジェクトの総生存量は減らない。

汎用アロケータから得た領域を、VM が勝手に隣のアドレスへ移動してはならない。ブロックヘッダ・空きリスト・境界情報も整合する必要がある。L4 では移動専用 arena を用意するか、アロケータと協調する移動 API を設計する。estalloc をそのまま使うだけで L4 が成立するとは扱わない。別ブロックへの確保・コピー・解放では移動先の空きが必要なので、空き不足時にも可能なインプレース圧縮と区別する。

### 完了条件

- 複数領域の解放・移動・再確保をランダムに繰り返して参照が破損しない。
- 最大連続空き領域、コピー量、停止時間、失敗回数を測定する。
- 同一負荷で L3 の移動なし方式より回収できる容量を示す。
- 停止時間と追加管理領域が許容できない場合は無効化できる。

## 10. L5: 複数 VM タスクの協調実行（研究分岐）

L2 のホストへの yield と、同一 runtime の別 JS への切り替えは別機能である。通常の同期 JS の途中へ別 JS を挟むと、getter、Proxy、組み込み関数、ユーザーコードが期待する順序を変えうる。

初期方針は、既存コードにはジョブの run-to-completion を維持し、明示的に参加するタスク API のみで切り替えを許す。API 名と公開時期は未定。

必要な仕様:

- タスクごとの実行フレーム、例外状態、結果、キャンセル、待機・準備完了状態。
- 共有 heap・global・Promise キューの順序と、タスク間での変数共有規則。
- ネイティブ関数・組み込み関数の再入可能性の監査。
- 優先度、公平性、飢餓、親子タスク終了時の資源寿命。

独立 runtime 間のメッセージ通信を比較対象にする。同一 runtime の実際のマルチコア並列実行、任意の C スタックの移動、JS のハードリアルタイム保証は本書の対象外。

## 11. オーバーヘッドと計測仕様

以下は設計用の仮定であり、現在の構造体サイズや実測性能ではない。

| 項目 | 仮の設計予算 |
| --- | --- |
| JSValue | 8 B と仮定。L0 で確認 |
| フレーム管理 | 32～64 B / frame を初期仮置き。実際には例外等の追加状態を算入 |
| ID 対応表 | 4～8 B / entry を初期仮置き。世代・空き管理で増加しうる |
| タスク管理 | 64～128 B / task を初期仮置き。スケジューラ等は別途算入 |

```text
新方式の保持量 = 値スロット総数 × sizeof(JSValue)
               + フレーム管理 + 対応表 + タスク管理
               + アロケータ管理 + 予約余白 + 残存 C スタック

純増減 = 新方式の保持量 − 同じ負荷における旧方式の保持量

移動停止時間 ≈ コピー量 / 実効帯域 + 走査・管理更新時間
```

例: 10 タスク × 10 フレーム × 16 スロット、48 B/frame、96 B/task なら約 18 KiB。ただし対応表・アロケータ・余白・C スタック・JS オブジェクトは含まない。現在の単一アプリとの直接比較値ではない。

64 KiB のコピーは、仮に 20 MB/s なら約 3.28 ms、100 MB/s なら約 0.66 ms。Cardputer の実測帯域ではなく、走査時間も含まない。

CPU の一律な低下率は設定しない。通常変数、クロージャ、call/return、例外、Promise、I/O、GC を分けて測る。件数予算と時間予算は構成可能にし、数値は L0 の UI・音声要件から決定する。L0 完了時に RAM 上限、遅延上限、許容スループット低下を記録し、それ以後のレベルの判定基準とする。

追加の比較項目:

- 選択 opcode の確認有無による通常実行時間、中断要求からホスト復帰までの遅延、確認頻度と時刻取得回数。
- 汎用割り当ての回数、セグメントサイズ別の使用分布、ピーク予約量、セグメント内未使用量。
- 空き総量、最大連続空き、結合回数、探索長、割り当て失敗数、最悪割り当て・解放時間。
- debug / 統計有無の違い。測定用の走査時間を通常経路の性能と混同しない。
- L4 の利益は、L2 の非移動・空き結合・再利用を行った方式と比較する。

## 12. 検証と移行

### 共通検証項目

- 値と副作用: 引数、this、new.target、arguments、let/const の初期化、クロージャ共有、再帰。
- 言語の特殊経路: constructor、eval、getter/setter、Proxy、組み込みコールバック。
- 非同期: resolve の一回性、thenable、throw/catch/finally、async/generator、未処理 rejection の報告時点。
- 寿命: 中断中 GC、循環参照、OOM、タスク終了、遅延通知、世代再利用。
- 移動: セグメント境界、異なる移動量、重複コピー、pin、旧領域毒化。
- デバイス: UI 更新、音声、通信の同時負荷、起動・停止の反復。

ホスト上の差分実行・sanitizer・対象機能の Test262 を使い、各レベルで既存の合格項目を維持する。実機では性能・メモリ・停止時間を確認する。新たな失敗を期待値の書き換えだけで処理しない。

### 段階移行

1. L0 と L1 を先に完成させる。応答性の目的を達成したならここで終了できる。
2. 長い単一ジョブの中断が必要な場合だけ L2 へ進む。L2a だけで任意中断を提供しない。
3. estalloc 等を比較対象に、移動しないセグメントの分割・空き結合・再利用を先に測る。それでメモリが足りるなら L3/L4 を実装しない。
4. L3 を手動移動で検証してから L4 の自動移動を有効化する。
5. L5 は別の互換性仕様と検証計画を成立させてから着手する。

各段階はビルド時選択で従来経路へ戻せるようにする。可変レイアウトを持つ生存タスクを実行途中で旧方式に戻さない。バイトコードや公開 C API への影響は各段階で記録し、互換性が失われる場合はキャッシュ形式を識別・無効化する。

## 14. 実装で分かったこと（L0・L1 完了時点、2026-09-12）

本節は実測と実装の結果であり、§1〜§13 の設計案より優先する。詳細は [vm-L0-report.md](vm-L0-report.md)、[vm-L1-design.md](vm-L1-design.md)、[vm-L1-report.md](vm-L1-report.md)、[vm-l1-tuning.md](vm-l1-tuning.md)、台帳 [vm-ledger/](vm-ledger/)。

### 14.1 いま実在するもの

- **上流は取り込み済み。** quickjs-ng 0.14.0、pocketjs_guest、pocketjs_ui_qjs を `components/` に取り込んだ。**改変はすべて取り込みコミット以降の差分**なので、`git diff <取り込みコミット>..` が改変の全体になる。`.cache/` の共有チェックアウトを直接編集しない（§3-8）。
- **ビルド時スイッチ。** `CONFIG_POCKET_VM_SCHED`（既定 y、L1 の実行制御。n で旧経路）、`CONFIG_POCKET_UI_TASK_CORE`（既定 1）、`CONFIG_POCKET_VM_CCOUNT`（既定 n）、`CONFIG_POCKET_VM_PROBE`（既定 n、計測）。
- **L0 のワークロードと採取スクリプトは tag `vm-L0` にある。** 計測し直すときは `git checkout vm-L0 -- apps/vmprobe tools/vm_l0_capture.py` で戻し、配線を足してから測り、**コミットせずに捨てる**。
- **ホスト側の判定基盤は `tools/vmtest/`。** コーパスはバイト比較で、`--budget-jobs` で予算を小さく強制できる。Test262 の基準は `test262-baseline.txt`。L1 以降の意味論はここで守られている。

### 14.2 確定した設計判断

| 判断 | 理由（実測） |
| --- | --- |
| 予算は**時間が主、件数が従** | 1 ジョブの費用が種類で 7 倍違う（0.072 ms / 0.49 ms）。件数だけでは軽いジョブを無駄に切り、重いジョブを止め損ねる |
| `VM_JOB_FLOOR`（8）は必須 | `frame()` だけで予算を使い切るワークロードがあり、床が無いと進捗ゼロで飢餓する（床 0・予算 1 µs で再現した） |
| 暴走検知は**drain が消費した時間**で見る（250 ms） | ターン数で数える方式は、正常な長い連鎖を旧ガードの半分以下（134 ms 相当）で殺した |
| 時計は `esp_timer_get_time()` | `CCOUNT` は読み取りが 33 倍安い（25 ns 対 833 ns）が、drain の実測差は測定ノイズ以下。採用するとコア固定に永久に縛られ、`CONFIG_PM_ENABLE` を入れた日に黙って壊れる |
| `ui_task` はコア 1 に固定 | コア 0 は ESP-IDF が Wi-Fi ドライバを固定する側で、LCD 転送 +0.6 ms、JS 実行 5.6〜12.6%、JS 実行中の HTTP +15.6% 悪化する |
| 表示周期は **`frame()` 1 回につき 1 回だけ**課金する | 継続ターンにも 33 ms を課金すると、継続を要するアプリの `frame()` が 28.2 → 7.7 fps に落ちる。JS の仕事量は変わらず、増えるのは待ち時間だけ |
| 未処理 rejection はキューが空になる境界でのみ報告する | 予算の切れ目で判定すると、同じ連鎖の後ろにある `catch` を見ずに未処理と報告する |
| 継続は新しい外部イベントより優先（互換モード） | 順序の互換を保つため。**代償として、継続を要するアプリの完了遅延は残る**（音声競合下で legacy の 1.9 倍）。順序互換を捨てる「公平モード」は L1 の範囲外 |

### 14.3 数値の扱い

構造体の大きさは仕様 §11 の仮置きと合った（`JSValue` 8 B、`JSStackFrame` 48 B、`JSVarRef` 32 B、実測）。**それ以外の数値をここに正確な値として書かない。** capability とアプリを足すたびに動き、書いた瞬間から古くなる。桁の目安と測り直しの手順だけを残す:

- 1 ジョブの費用は種類で 0.07〜0.5 ms の幅。drain 1 回は数十件。
- 無線を上げて音声と UI を同時に動かすと、**最大空きブロックは一桁 KiB まで落ちる**。taffy の段（§CLAUDE.md）に届かなくなる領域がある。
- 20 KiB の C スタックに収まる JS の再帰はおよそ 50 段（推定）。実測はまだ無い。
- 測り直しは probe ビルド（`sdkconfig.vmprobe.defaults`）と `vm_l0_capture.py`。**`-D SDKCONFIG=<dir>/sdkconfig` を省くと共有の `sdkconfig` に計測設定が入り、他のビルドも巻き込む。**

### 14.4 この機体で数字が嘘をつく条件

- **計測点が経路の一部しか通らないと、静かに嘘になる。** L1 の計測点は通常ターンにしか無く、継続ターンを通らなかった。そのため drain の「1 回目の切れ端」を drain 全体と読み、「7 倍速くなった」「16.7 KB 余分に保持している」と 2 回とも誤った結論が出た。**経路を足したら計測点も足す。**
- **ビルドが違えば命令キャッシュの配置差が効果を飲み込む。** ビルド時スイッチで新旧を分けた比較は、この意味で構造的に交絡する。性能差を主張するなら同一バイナリで切り替えるか、差が配置差より大きいことを示す。
- **実機が応答しない前に、`usbipd` が WSL に奪っていないか確認する。**（`usbipd list` の busid が `Attached`。故障と区別がつかない）
- **ホスト側の検査は `main/` のパスを直書きする。** `main/vm/` を足したとき、ホストのテストが 1 本リンクできなくなった（CLAUDE.md が警告しているのと同じ再発）。
- **`tools/vmtest/expected/*.txt` は LF に固定してある。** `text=auto` に任せると Windows チェックアウトで全件が改行だけで失敗する。

### 14.5 L2 に着手する人が前提にすべきこと

- **async/generator の機構は、フレームの表現と再開の入口の雛形にはなるが、呼び出し構造の雛形にはならない。** C の再帰は残り、解放経路はコンパイル時に決まり、`this`/`new_target` は保存されない。「C スタックが深さに比例しない」には call 系 opcode と `done:` を作り直す必要がある（L2b）。
- **GC はフレームを走査しない。** 値は参照カウントだけで生きている。フレームを動かす方式は自前の生存走査が要る。
- **`JS_CallInternal` の C ローカル変数が、フレームを指す 2 組目の生ポインタになっている。** L2a で移すのは alloca のブロックだけではなく `JSStackFrame` 本体も含む。
- **割り込みは捕捉できない例外として実装されている。** §3-6 の「中断は例外ではない」とは相容れない。中断された `await` の Promise は永久に pending のまま残る（台帳 03）。
- **L1 は 1 ジョブの途中では止まれない。** 同期ループ 118 ms は L1 では 1 ms も縮まない。そこが L2 の担当範囲との境目である。

### 14.6 VM とは独立に見つかった、まだ直していない不具合

- **循環参照のゴミが一度も回収されない。** GC の自動閾値の初期値（256 KiB）がゲストのヒープ上限（160 KiB）より大きく、firmware はどこからも `JS_SetGCThreshold` / `JS_RunGC` を呼ばない。
- **上流 quickjs-ng の use-after-free。** バックトレースを組み立てる途中で確保に失敗する経路。再現は `tools/vmtest/known/oom_backtrace_uaf.js`。
