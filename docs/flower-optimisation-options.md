# flower のフレームをどう縮めるか — 残っている手の検討（2026-09-15）

**これは検討であり、実測ではない。** 数字は「実機 / [obj]（クロスコンパイラの静的カウント）/
推定」を明記する。§0 と §1 は実機と [obj] の実測、§2 の各候補の「上限」は実測からの引き算、
実装難度と検証手順は設計判断。

## 1. 候補を測る方法（先に決めておく）

- **ビルド間比較は使えない。** このボードは同一カーネルがビルド間で最大 15% 動く（命令キャッシュの
  配置、`docs/pie-simd.md` §3.13）。10% 級の変更を「前のビルドと比べる」のは測定ではない。
- **同一バイナリ内で切り替える。** 60 フレーム窓ごとにスイッチを反転し、隣接窓のペアで差分を取る
  （SPLIT3 の `gate=` がその実装）。**触っていない項目を同時に出す**とノイズ床が分かる。
- **ホストは可視性だけを証明できる。** 画素一致（`tools/flower_decor_identity.c` の型のハーネス）は
  ホスト、速度は実機。ホストの時間は主張に使わない。
- **[obj] の命令数は設計に使える。** ループ本体の命令数と内訳は `objdump` から出せる（下記）。

## 2. 残っている手（価値 × 実現難度の順）

### A. LCD 転送の非同期化 — 上限 ~7.5 ms(実機)、シーンに一切触らない【実装・計測済み 2026-09-15】

**結果: `send` 7.77 → 1.46 ms、`draw` 50.54 → 44.70 ms、fps 19.5 → 22.3（+14%）。**
同一バイナリ（`async=` を PERF 窓ごとに反転）・30窓ずつ・59ペアで、
`send` の差は mean −6.31 / median −6.33 / min −6.51 / max −6.06 ms（±0.2 ms に収まる）、
対照の `loop` +0.31 / `kernel` +0.33 / `prep` +0.02 / `hud` +0.01 ms。コミット `e282c8e`。
**画面（ガラス）側は未確認** — MISO 未配線でソフトからは見えないため、物理確認が要る項目として残る。

`board.c:39` は `spi_device_polling_transmit` で、**CPU が転送完了まで回り続ける**。
1 フレーム 17 ストリップ × 240×8×2 B、80 MHz で 1 ストリップ ~0.4 ms → 実測 `send` 7.4–7.8 ms と一致。
ストリップの描画は 1 枚 ~2.2 ms（45.6 / 17 と draw から）なので、**転送中に次のストリップを描けば
送信はほぼ全部隠れる**: 45.6 → 38〜39 ms（fps 21.7 → 25 前後）が上限の見積り（推定）。

やることは `board.c` の中だけ:

1. ストリップを 2 本にする（`static uint16_t shared[LCD_W*STRIP_H]` を 2 面、各 3.84 KB、DRAM は足りる）。
   1 本で成立していた理由（同期転送だから同時に 2 人が触らない）は `board.c:20-25` に書いてある。
2. `spi_device_polling_transmit` を `spi_device_queue_trans` にし、**前のストリップの結果を次の
   `board_present` の先頭で `spi_device_get_trans_result` で回収**する（1 枚遅れのパイプライン）。
3. `pet_hub_overlay` / `pocket_capture_overlay` は転送前に面へ書いているので、**キューに積む前に
   呼ぶ**（いまの順序のまま、転送だけ後ろにずらす）。
4. `next_row` の連続 RAMWR 判定はそのまま使える（積む順は変わらない）。
5. `board_capture`（PIX 行）は `pixels` を読むので、**面を再利用する前に**読む（1 枚遅れに合わせる）。

検証: 画素は変わらないので `tools/capture_home.py` 相当の実画素取得で一致を見る。速度は
PERF の `draw` と `send` を同一バイナリ A/B で。**ティアリングは MISO 未配線でソフトからは見えない**
（`hardware-constraints.md`）ので、物理確認を依頼する項目として残す。

リスク: SPI ドライバのキューを LCD と他デバイス（SD は別ホスト）で共有しないこと、DMA 記述子の
アラインメント、CS の扱い。ここは board.c の唯一の転送口なので変更点は閉じている。

### B. 装飾光線パイプラインの PIE 化 — 上限 ~10 ms(実機)、難度 高

`rays` はフレーム内で最大のスカラー項。143 命令/訪問画素（[obj]: `garden_atmosphere_row` の
内側ループ本体 143 命令で、ループ制御も込み）で、内訳は mix+pack ≈45、profile 2 本 ≈40、門番+protect ≈35、
dither ≈10、残りがループ制御。**算術を削る方向は実測でノーゲイン**（§2-E の 35.6% 削減がノイズ）だが、
8 レーンにすれば命令数が ~1/8 になり、同時にストールの共有も減る。

設計上の壁（この順に潰す）:
1. **profile の `smooth(q)=q*q*(768-2q)/65536` は 16bit レーンに収まらない**（q² ≤ 65025 は u16 だが
   ×(768-2q) で 32bit が要る）。PIE の 40bit アキュムレータ（`VMULAS.S16.QACC`）と
   `SRCMB.S16.QACC`（シフト + 16bit 飽和）で**同じ丸め**を作れるかを、まず単命令で確かめる。
2. **mix の 3 チャンネルは RGB565 のパック/アンパックを 8 レーンで**やる（`VMUL.16` + SAR、
   `VADDS`/`VMIN` のクランプ、最後に `slli`/`or` で再パック）。16bit レーンを 2 本使って
   r/g/b を分けるのが素直。
3. **dither は x 依存のハッシュ**（[obj] 10 命令）なので、レーンごとの値はスカラで表を作って
   `VLD` するか、x の線形性を使って行内で 8 レーン分を先に計算する。
4. 被覆の外は「書かない」ではなく「0 を足す」に変える必要がある（現行の `if(!light&&!shadow)continue`）。
   `mix(row,0,0,d)` は `row + (d>>8)` なので**恒等ではない** → マスクして書く（`VST` の前に
   レーン単位で選択する）か、0 のときの加算項を 0 にする。ここが一番の落とし穴。

検証: `tools/pie/` の 3 層（`stalls.py` / `test_kernels.py` の命令レベル模擬 + 全画素比較 /
`run_models.py`）→ ホスト画素一致 → 実機 A/B。**既存の `garden_pixels_row` が同じ形の手本**。

### C. 林冠ブレンドの PIE 化 — 上限 ~4.8 ms(実機)、難度 中〜高

`veg` 5.0–5.9 ms のうち林冠が大半（命令数の床 2.0 ms × 実測係数 ~2.4）。コード自身が
`garden.c` の林冠ループに "Secondary PIE candidate: contiguous ellipse coverage + RGB565 blend.
Clip once, process aligned 8-pixel interiors, retain scalar tails" と書いている。

形は B より簡単: 楕円 1 つ 1 つが連続区間で、被覆は `dx²·mrr>>18` の 1 つの積和、ブレンドは 3 チャンネル。
B の 2〜4 の知見がそのまま使える（レーン並び、パック、端のスカラー尾）。**B の副産物として
先に「8 レーンの RGB565 ブレンド部品」を作り、C から使う**のが順序として良い。

### D. スカラーの残り玉（合計 ~0.3–0.8 ms 推定、難度 低、ただし測ってから）

**結果（2026-09-15、実装・計測済み）**: 門番の **unsigned 1 比較**化だけで `rays` が
**mean −1.46 / median −1.02 ms**（予測 0.4 ms より大きい。[obj] の 20 命令 ≈ レイ本体 143 命令の
14% と整合する）。canopy の `f==0` 短絡は `veg` のノイズ（min −4.3 / max +4.9）に埋もれて**未解決**で、
1 比較の価値しか主張しない（コミット `1ec48bd`）。4 アーム（両方 ON / GATE0 / TWEAK0 / OLD）が
すべて変更前リビジョンとバイト一致。

- **門番のコストが節約とほぼ同じ**（[obj] で判明）: いまの support 門番はコンパイラが
  `salt/neg/and/extui` の連鎖 ~20 命令に展開していて、節約する profile 1 本（~20 命令）と相殺している。
  これは §2.2 の「実測でノーゲイン」の説明そのもの。**符号なし 1 比較**
  （`(unsigned)(d + radius) < 2*radius`）に書き換えれば ~4 命令になり、門番が正味の得になる。
  ただし予測は「モデルでは ~0.4 ms」なので、**また実測で確かめる**（前回それをしなかったら嘘を書いていた）。
- **行ループ内のリテラル再ロード**: `garden_vegetation_row` の内側ループは [obj] 199 命令中
  `l32r` 13、`shade` は 205 命令中 `l32r` **45**（+ `wfr` 45）。定数はループ外に出す／
  レジスタに載せ直せば数 % だが、**コンパイラが既にやっている分との差**しか出ないので、
  変更前に [obj] で「ループ内に何個残っているか」を数える。
- **dissolve の二重走査**: フェード中の行は vegetation を 2 回走る（実測 veg 9.61 ms / 240 passes、
  rest 3.37 ms）。`FLOWER_GARDEN_FADE_S=3 s` / `hold=40 s` なので**フレームの平均では ~0.3 ms**。
  得は小さいが、`bloom_garden_mix` を 8 行単位でキャッシュする手はある。

### E. 検討したが採らない／保留

- **ray パスの算術 micro-opt**: 実測でノーゲイン（profile 評価 35.6% 減 → rays 平均 −0.19 ms、
  ノイズ床 −0.09 ms）。理由も [obj] で説明済み（門番が節約分を食う）。**この線は終了。**
- **ホスト時間での比較**: このボードの変更はホストでは測れない（§1）。
- **species 依存の重さ**: fps 19.5–30.3 は種で決まる（`bell` 0–9.9 ms）。重い種を出さないのは
  最適化ではなく製品判断なので、ここでは扱わない。
- **`pixels`（既存 PIE 3 パス）**: 6.0–6.8 ms は既にベクタ。さらに縮めるにはパスを減らすしかなく、
  それは絵が変わる。
- **DRAM/ゲスト側**: このフレームの話ではない（別項）。

## 3. 推奨順序

1. ~~**A（転送の非同期化）**~~ — **実装・計測済み（−6.31 ms / +2.8 fps、`e282c8e`）**。
   残るのは物理確認（ガラス）と、`send` に残った 1.46 ms（最終ストリップ + memcpy + queue/reap）。
2. ~~**D の門番 1 行**~~ — **実装・計測済み（rays −1.46 ms、`1ec48bd`）**。canopy の `f==0` は未解決。
3. **B/C の共有部品（8 レーンの RGB565 ブレンド）** を作り、**C（林冠）**から適用 →
   既存 `garden_pixels_row` と同じ形に落ちる。**ここから先が残っている本体**。
4. **B（装飾光線）** — 最後。profile の 32bit 中間と、被覆の外を「書かない」から
   「マスクして書く」への変更が要る。
5. 横道で見えた候補（未検討の深掘り）: `shade` の [obj] 205 命令ループに `l32r` 45 + `wfr` 45 が
   あり、float のソフトウェア演算が濃い（実機 `shade=4.03 ms` / ~1,869 hits ≈ 517 cy/hit）。
   **絵の代償は測った（2026-09-15）**: 最大の単発コストである `sqrtf`（実測 154 cy/call、
   4,010 calls/フレーム = 2.1 ms = フレームの 6%）を整数平方根（16 段のシフト/比較、float なし）に
   置き換え、ホストで 14 種 × 2 時刻 = 28 フレームを画素比較した（`tools/flower_frame_dump.c`、
   `docs/flower-decor-cost.md`）。**B=14（出力の小数部 14 bit）で 32,400 画素のうち 1 画素が
   ≤4/255 違うだけ**＝目視では同一。B=8 では 0.022% の画素が違い、金色の花冠に白い点が 1〜3 個出る
   （深度テストの反転）。ループ段数は B によらず同じなので、**B=14 は絵を無料で取り戻す**。
   実機での速度確定は次の段（同一バイナリ A/B の型は既にある）。


## 結果: canopy の PIE 化もノーゲインだった（2026-09-15、実機 154 ペア）

`garden_canopy_row` の PIE カーネル（`main/scene/canopy_pie.c`、8画素/パス、除算なし、
分岐なし、ブロック内 51 PIE 命令）は**画素一致を証明済み**（120 フレーム 7,776,000 バイト、
5 アーム同一 md5）で、実機でも **155 窓・パニック 0** で動きます。しかし速度は:

    field    mean   median     （canopy=1 − canopy=0、ms/フレーム）
    total   -0.357  -0.535
    decor   -0.424  -0.610
    veg     -0.684  -0.750   ← 対照。canopy スイッチでは動かないはずの欄
    rays    +0.166  +0.075
    rest    +0.093   0.000

つまり decor の差（中央値 −0.61）は **対照である veg の揺れ（中央値 −0.75）より小さい**。
内訳の会計（veg + rays + rest = −0.42）が decor の差（−0.42）と一致してしまうので、
この差は canopy の仕事量ではなく窓間のシーン位相のドリフトで説明できます。判定は
**「ノイズ内＝差なし」**です（canopy=1 で 35.00 ms / 28.6 fps、canopy=0 で 35.39 ms / 28.3 fps）。

これで装飾側の命令数削減は 3 連続のゼロ結果になりました（profile 門番、固定小数点 sqrt、
canopy PIE）。一方で効いたのは構造の変更 2 つ（LCD 転送の非同期化 −6.3 ms、unsigned 比較
−1.5 ms）です。命令数の床（rays 3.9 / canopy 2.0 / veg 2.4 ms）に対して実測が約 2.4 倍ある
という以前の観察と合わせると、**装飾の残り時間は命令数ではなくメモリ／パイプライン側に
ある**という読みになります。カーネルは厳密で無害なので残してありますが、装飾の
命令レベル最適化はここで打ち切り、次の対象は装飾光線（約 10 ms、アルゴリズム側）か
フレーム構造そのもの（転送とループの重なり）に移すべきです。
