# R3 設計: 小さいブロックの再利用（2026-09-27、設計・未実装）

出典: [allocator-cost.md](allocator-cost.md)（実機: malloc 1 回 約 1,270 サイクル、free 約 620、ブロック長の読み戻し
約 110、STRESS の JS のターンの 20.6%）。道具は `tools/vmtest/prof/`（`alloc_sim.py`・`vmtrace2alloc.py`、
`test_stress_app.c` の `STRESS_ALLOC_TRACE`）。

## 1. 前提の事実

- **解放はほぼ全部が参照カウントでその場で起きる**（`js_free_value_rt` → `free_zero_refcount`、GC は循環だけ）。
  STRESS の LV1/LV2 で GC は 599 フレームに 5 回、free は 1 フレーム約 165 回。つまり確保と同じ大きさの解放が
  毎フレーム同じくらい起きていて、捨てたブロックを次の確保に回す余地がある。
- **大きさが偏っている**（ホスト `-m32`、実機の tlsf の丸め。STRESS の LV1、フレーム 30〜299）:

| usable | 割合 | 累積 |
| --- | --- | --- |
| 48 B | 22.8% | 22.8% |
| 32 B | 21.9% | 44.7% |
| 16 B | 18.0% | 62.7% |
| 12 B | 13.7% | 76.3% |
| 80 B | 8.9% | 85.3% |
| 36 B | 6.5% | 91.8% |

  64 B 以下が 88.5%、128 B 以下が 98.7%。コーパスの `bench_*` 8 本でも上位は 48・16・80・12・32・36・72・88 B で、
  QuickJS の 32 bit の構造体の大きさ（`JSObject` など）で決まっている（アプリに依らない）。

| 全クラス、合計の上限だけ | 0〜10% | — | — | — | — | — | — |

（値は malloc のうちキャッシュから出せた割合。）

- **フレームで回るアプリ（作ってすぐ捨てる）には 60〜100% 効く。** 解析・コンパイルのように溜めてから
  まとめて捨てる走り方には効きが薄い（2〜25%）が、それは起動時の一度きりで、毎フレームのターンではない。
- **合計の上限だけでクラスを選ばないと効かない**: まれな大きさのブロックが枠を埋めて使われずに残り、よく使う
  大きさを締め出す。クラスごとの上限が要る。

## 3. 設計

### 3.1 どこに置くか: ゲストのアロケータ（`guest.c`）の下、QuickJS の計上の外

- QuickJS の `js_malloc_rt`/`js_free_rt` はそのまま。キャッシュは `GUEST_ALLOCATOR` の関数の中に置く。
  QuickJS から見ると「free したブロック」なので、`malloc_size`（160 KiB の上限の計上）はキャッシュの分を含まない。
  → **キャッシュが持つ分だけ、上限の外でシステムのヒープを使う**。上限はクラスごとの個数で決まる（§3.3、最大約 3 KB）。
- 代わりに QuickJS の中（`js_malloc_rt`）に置けば計上に含められるが、上流のコードへの変更が大きく、ホストの
  `vmrun`（独自のアロケータ）でもコーパスの確保番号がすべて動く。まず外に置く。

### 3.2 ブロック長の読み戻しを直読みにする

キャッシュのクラスはブロックの**実際の**長さで決める必要がある（tlsf は分けられない余りを最大 15 B 付けて返す）。
`heap_caps_get_allocated_size`（flash 上、ヒープ一覧の線形探索、約 110 サイクル）の代わりに、tlsf のブロック
ヘッダの長さの語（利用者ポインタの 4 B 前、下位 2 bit はフラグ）を読む。QuickJS が確保・解放のたびに呼ぶ
`js_malloc_usable_size` もこれにする（1 フレーム約 390 回）。

**取り違えを防ぐ**: ゲスト作成時に試しのブロックを数個確保し、直読みと `heap_caps_get_allocated_size` が一致する
ことを確かめる。一致しなければ直読みもキャッシュも使わない（ESP-IDF の tlsf や `MULTI_HEAP_BLOCK_OWNER` の
形が変わったときの安全側）。

### 3.3 クラスと個数

- クラスは実際の長さ 12・16・32・36・48・72・80・88 B（§1 の上位）。それ以外の長さはキャッシュしない。
- クラスごとに最大 8 個（単方向リスト、次のポインタはブロックの先頭 4 B に置く）。最大で
  8 ×（12+16+32+36+48+72+80+88）= **3,072 B** を上限の外で持つ。
- malloc(n): 要求を tlsf と同じ丸め（4 B、最小 12 B）にしてクラスを引き、あれば取り出す。無ければ今までどおり
  `heap_caps_malloc`。free(p): 直読みの長さがクラスにあり、そのクラスが 8 個未満なら積む。それ以外は `heap_caps_free`。
- realloc はキャッシュを通さない（取り出したブロックも普通の tlsf のブロックなので、そのまま渡せる）。

### 3.4 手放すとき

- **ゲストを壊すとき**: `JS_FreeRuntime` の後で全部 `heap_caps_free`。
- **確保に失敗したとき**: `heap_caps_malloc` が NULL を返したらキャッシュを全部返してから一度だけやり直す
  （抱えた小ブロックが隣と合体できずに大きな確保を落とす、を避ける）。
- **メモリ逼迫のとき**: `pocket_memory` の逼迫の通知と同じ時点でも返す（候補。§5）。

### 3.5 タスク

ゲストの JS は `ui_task` だけで動く。念のため、ゲスト作成時のタスク以外から来た呼び出しはキャッシュを通さず
`heap_caps` に直接流す（`xTaskGetCurrentTaskHandle()` との比較、数サイクル）。

## 4. 見込み（推定）

STRESS の LV1: malloc 166 回・free 165 回のうち 6 割がキャッシュから出入りすると、1 回あたり
（1,270 → 数十）と（620 → 数十）の差で約 18 万サイクル、読み戻しの直読みで約 4 万サイクル、合わせて
**約 0.9 ms / フレーム（ターン 7.6 ms の 1 割強）**。実機で測って確かめる（`CONFIG_POCKET_VM_ALLOCPROBE` の同じ窓）。

## 5. 関所と未決

- **ホストで試せる形にする**: キャッシュは `guest.c` の中ではなく小さな独立したモジュール（後ろのアロケータを
  関数で受け取る）にして、(1) ASan の下で乱数の確保・解放列を旧実装と突き合わせる単体試験、(2) `vmrun` の
  アロケータにも同じモジュールを挟んでコーパス・Test262・確保失敗の総当たりを通す、の両方で検査する。
- 負の対照: 積むときの個数上限を外す・直読みの一致確認を外す・失敗時に返さない、をそれぞれ壊して検出されること。
- 実機: `ALLOCPROBE` でアロケータの時間とターン、`app_free`・最大空きブロック（上限の外の 3 KB と断片化の影響）、
  smoke・settings・STRESS。
- 未決: 逼迫の通知で返すか（返すと直後の確保でまた積み直すだけの可能性）。クラスの一覧を固定にするか、
  実測から選ぶか（固定で始め、`bench_*` と STRESS で外れていないことを見る）。
