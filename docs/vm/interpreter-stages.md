# インタプリタの段階分割（素案、2026-10-23）

**状態: 素案。§4.1・§4.3・§4.5 は試作をブランチ `vm/tiered-interp-20261023` にマージ済み（host 検査済み、実機は未測定）。** 数字の区分は、実測（実機または host で測った値）、推定、コード（ソースや逆アセンブルを読んで確かめた事実）の3つ。

## 0. 何のための分割か

STRESS の JS のターンでは、サイクルの 57% が命令キャッシュのミス待ちになっている（実測、[turn-cpi.md](turn-cpi.md)）。1ターンに触るコードは 45.5 KiB で、キャッシュの 32 KiB に入らない（推定、[r5-icache.md](r5-icache.md) §2）。データの読み書きで待つのは 4〜5% にとどまる（実測）。

遅い原因は、どれか1つの関数が重いことではない。**熱いループ（オペコードの dispatch）から、どの関数でも呼べてしまう**ことにある。そこで、インタプリタの1回の実行を段階に分ける。各段階が呼ぶ関数を閉じた小さな集合に絞り、答えが変わらない処理は前の段階へ、後片付けは後の段階へ移す。

機械語は生成しない（JIT ではない）。バイトコードを読み込み時に特殊化し、後片付けをまとめる。

## 0.1 方針：段階実行（tiered interpreter）

**ここでは2種類の段を使う。** S0〜S4 は時間の流れの段（§1）、T0〜T2 は最適化の段を表す。文字で区別する。

V8 と同じく、熱いコードほど上の段で走らせる。ただし機械語は作らない。機械語を置く DRAM が無いので、3つの段とも、バイトコードをインタプリタが解釈する。

**原則：どの段でも、1ターンに触るコードを予算の中に収め、その中で速くする。** T0 も例外にしない。予算の叩き台（推定、内訳の実測待ち）は次のとおり。

| 枠 | 予算 |
|---|---|
| インタプリタの実行パス | 約14 KiB |
| native の境界（Kasane の提出、`pocket.*`、アロケータ） | 約12 KiB |
| 衝突と出入りの余裕 | 約6 KiB |

**原則：外れのコストは外れたときだけ払う（ヒーリング）。** 外れを想定した防衛（カウンタ、epoch、アサーション）は持たない。それ自体が毎ターン作業集合を増やすからである。guard の失敗だけを信号にして、少ない手間で直す。

- quickening は、命令ごとにジャンプテーブルの添字（opcode のバイト）をキャッシュする操作で、型が外れるとはその選択を誤ること。ヒーリングは添字を書き直すことなので、1 バイトの store で済む。外れのコストの正体は、guard（飛んだ先でのタグや shape の比較）と汎用経路の両方の行が icache に入ること。Xtensa LX7 は分岐予測を持たないので、間接ジャンプの値段は飛び先によらない。
- **T1 の guard に失敗したら**、その実行は汎用経路で済ませ、命令を retry-T0 に戻すだけにする。次の実行で、見えた型でもう一度 T1 に書き直す。多相の箇所は書き換えを繰り返すが、1 回あたりの追加は汎用経路と 1 バイトの書き込みだけで、T0 に置いたままとほぼ同じコスト。止める仕組み（確定 T0、試行回数）は要らない。
- **ずれの許容はフォールスルーの鎖で行う**（算術と比較の op）。quickjs の汎用ハンドラはもともと鎖になっている（`OP_add`：int 同士 → float 同士 → `js_add_slow`）。特殊化は鎖の途中に入口を作ることで、外れたらそのまま鎖の先へ落ちる。本体は op ごとに 1 つで入口だけが複数あり、専用ハンドラのコードを複製しないので作業集合が増えない。許容は int → float → slow の一方向で、戻る方向（float の入口に int が来る）は slow へ落ち、入口を戻すヒーリングで扱う。入口ごとに opcode 番号が要る点は変わらない。
- **superinstruction** は先頭の opcode だけを書き換え、後ろのバイト列は残す（CPython 方式）。融合するのは、範囲の中にラベルも park/yield の検査点も無い区間だけ。
- **残す防衛は正しさの条件だけ**：guard そのものと、T2 の書き換えを論理ターンの終わりに限ることの 2 つ。
- 受け入れ基準には、速さに加えてメモリの指標（評価の余裕、ゲストの最大ヒープ、`tools/memlog.py` の DRAM の静的値）を置く。

段を上げる判定には、ものさしを2本使う。1ターンのサイクル数が下がり、かつ触るコードが増えないこと。

| 段 | 中身 | 入り方 | 外れたとき |
|---|---|---|---|
| **T0** | 汎用の dispatch。まれな命令と slow 経路は cold の関数へ追い出し、普段呼ぶ下請けの関数は閉じた一覧にする | 読み込み直後 | — |
| **T1** | quickening。観測した型と呼び先に合わせて、命令をその場で同じ長さの専用命令に書き換える | 型と呼び先が安定したコード | despecialize。その命令だけ T0 の処理を使い、命令を元に戻す |
| **T2** | superinstruction。よく続く命令の組をまとめ、小さく連続した専用のループで走らせる | すべての命令が T1 になった関数 | T0 へ戻る |

T1 の命令は、T0 の命令を置き換えるものであって、足すものではない。関数が上がると、その関数については T0 の汎用の処理を触らなくなる。そのため、flash 上のコードの総量は増えても、1ターンに触る量は減る。

### 事前計算と観測

| 種類 | 答えが決まる時点 | 例 | 置き場所 |
|---|---|---|---|
| 証明できる | コンパイル時 | TDZ（§4.3、試作済み）、トップレベルの `const` のスロット | T0（S0 で計算する）。ガードは要らない |
| 観測して決める | 実行して数ターン後 | 値の型（int か double か）、`Math.sin` の呼び先 | T1。安いガードが要る |

証明できるものは、できるだけ T0 に寄せる。T0 が軽くなるほど、T1 に要る仕組みが減る。

### 用語

| 用語 | 意味 | 出どころ |
|---|---|---|
| tier-up | 上の段へ上げる | V8 |
| despecialize | 特殊化を戻す | CPython 3.11 |
| quickening | バイトコードをその場で書き換える | CPython 3.11、JVM |
| superinstruction | よく続く命令の組を1つにまとめた命令 | インタプリタ研究の一般用語 |

deopt は使わない。V8 では、フレームを作り直す重い処理を指すからである。

### 段に置く基準（素案）

命令ごとに、次の3つを順に問う。

| 問い | はい | いいえ |
|---|---|---|
| ① 答えはコードの形だけで決まるか（証明できるか） | T0。S0 で計算し、ガードも要らない | ②へ |
| ② 実行すると答えが安定するか（型・呼び先） | T1。ガード付きの専用命令にする | T0 の汎用の処理のまま |
| ③ T1 の命令が決まった並びで続くか | T2。superinstruction にまとめる | T1 のまま |

段に入れる条件がもう1つある。専用の命令とその下請けの関数を合わせて、置き換える汎用の経路より、1ターンに触る行が少ないこと。速くなっても、触るコードが増えるものは入れない。

### tier-up の条件（素案。閾値は叩き台）

**T0 → T1（命令単位）**
- 対象は、観測で答えが決まる命令の族（`add`/`mul`/`lt` などの型、`get_var` の組み込み、Math の呼び出し）。
- 命令を実行したとき、オペランドの型や呼び先を見て、その場で専用の命令に書き換える。
- 助走のカウンタは置かない。ゲームループでは型が最初から安定するはずで、カウンタを置く場所も無い。
- 予想が外れたときは despecialize で戻す。外れたときの値段は、命令1つを汎用の処理で実行することだけである。

**T1 → T2（関数単位）**
- 次の3つをすべて満たした関数を上げる。
  - 関数の熱い命令が、すべて T1 になっている。
  - 直前のターンで、その関数に guard の失敗が無い（N ターン数えるカウンタは持たない）。
  - 毎ターン実行されている。
- 判定と書き換えは論理ターンの終わりに限り、その関数の park 中のフレームが無いときだけ行う（S4 が論理ターンの終わりとは限らない。§8）。書き換えのコードは cold に置き、予算の外にする。
- superinstruction の種類は、プロファイルからビルド時に決める。実行時には作らない。

### despecialize の条件（素案）

| 起きたこと | 行き先 |
|---|---|
| T1 の命令でガードが外れた | その1回は汎用の処理で実行し、命令を「再挑戦できる T0」に戻す。次の実行で見えた型に書き直す（ヒーリング） |
| T2 の関数の中で、どれかの命令が外れた | 関数ごとの 1 ビットを立て、論理ターンの終わりに関数を T1 に戻す |

「確定 T0」（何度も外れたら特殊化をやめる）は廃止した（2026-10-24）。止めなくてもコストは T0 とほぼ同じだからである。

**ガードは、その命令の中で確かめられるものに限る。** 依存している箇所を全体に知らせて無効にする仕組みは作らない。依存の表は DRAM を食い、壊れやすい。§4.5 の Math の試作は「呼んだ時点での呼び先の値そのもの」でガードしていて、この原則に合っている。

フレームの形は段で共通なので、戻るときに作り直すものは無い。命令の長さも変えないので、park 中のフレームがあっても安全である。

### 状態の持ち方と、命令番号の制約

状態は命令の番号そのもので表す。1つの族を「再挑戦できる T0」と「T1」の番号で持てば、ゲストのヒープに状態を足さずに済む。関数単位の情報（T2 から戻す印）だけは、関数ごとに 1 ビット要る。確定 T0 を廃止したので、その分の番号は要らない。

**命令番号の空きはほとんど無い。** 実行時の命令は 246種類で、1バイトの 256 までの残りは約10枠しかない（`quickjs-opcode.h` の `DEF` を数えた。正確な空きは要確認）。対策の候補は次の3つ。T1 の設計で最初に決める。
- T1 の族を絞る（数値の演算と比較、グローバルのスロット、Math の呼び出しなど）。
- めったに使われない命令を、2バイトの拡張命令へ移して枠を空ける。

### 決めるのにデータが要るもの

- 型が混ざる箇所の数（DERBY と STRESS）。ヒーリングの書き換えが毎ターン起きる箇所がどれだけあるかを見る。
- T1 に入れる族の優先順位。1ターンに触るコードの内訳（集計中）と、host の opprof で数える命令ごとの回数で決める。

## 1. 段階の定義

| 段階 | 中身 | 頻度 | 実装の場所 |
|---|---|---|---|
| **S0 読み込み** | 解析・コンパイル・トップレベルの評価、`frame` の取得 | アプリにつき1回（2 s の期限、予算は無制限） | `app_session.c:1503-1983`、`guest.c:637-789` |
| **S1 ターン入口** | メモリの標本、pump 12本、`arm_turn`、FRAME_WRAP | 毎フレーム | `app_session.c:2266-2458` |
| **S2 実行** | オペコードの dispatch と速い経路 | 毎フレーム約3.8万命令（DERBY、実測 host） | `quickjs.c` の `JS_CallInternal` |
| **S3 境界** | ネイティブ呼び出しと引数の変換（Math、`pocket.*`） | 毎フレーム数百回 | `js_call_c_function`（`quickjs.c:19542`）、`pocket_derby.c`、`pocket_kasane.c` |
| **S4 ターン出口** | ジョブの消化、`JS_VMStackTrim`、`pocket_kasane_end_turn`、OOM canary の回収 | 毎フレーム | `guest.c:576-621`、`app_session.c:2466-2486` |
| （描画） | `present_frame` → 帯ごとに描画 → `board_present_sync` | 毎フレーム | ゲストの外 |

境界はコード上ほぼできている。S1 から S4 は `app_tick` 1本が順番に呼んでいる。ただし次の2つは、S4 ではなく S2 の確保の中で動いている（コード）。

- GC の判定。`js_trigger_gc` が確保のたびに閾値を見る。
- R3 ブロックキャッシュの出し入れ。

### 共通の呼び先と分類

**a** は S2 に残すもの、**b** は S0 へ移せるもの、**c** は S4 へ移せるもの、**d** は冷たい処理（熱いループのコード配置から外すもの）。

| 呼び先 | 分類 | 根拠 |
|---|---|---|
| **ENABLE_DUMPS の後処理（オペコードごと）** | **d** | コード（下の §4.1） |
| `get_u16` / `get_u32`、`set_value`、`JS_FreeValue` が別関数のまま呼ばれている（`-Os` のため） | a（inline 化すべきもの） | ELF で確認 |
| 参照カウントが 0 になった後の解放の連鎖（`free_gc_object` → `js_free_rt`×3 → … → `tlsf_free`） | c | コード |
| double を含む比較と、int・float 混在の算術 | a（今は slow 関数の中にある） | コード。DERBY での型の混ざり方は推定 |
| `get_var` のハッシュ検索 | b | コード。ロード後に答えが変わらない、は推定 |
| TDZ 検査（get_loc_check と set_loc_uninitialized を合わせて21%） | b | 推定。コンパイル時に証明できるかどうか次第 |
| ネイティブ呼び出しの prologue と `js_call_c_function` | a。Math のように呼び先が固定のものは b | コード、推定 |
| GC の判定、R3 の出し入れ | c | コード |
| `JS_Throw*`、typed array の分岐、lazy の初回の実体化 | d | コード |

## 4. 候補（強い順。数字は推定）

### 4.1 本番ビルドで ENABLE_DUMPS が有効になっている（d）

`quickjs.c:114` は `#ifndef NDEBUG` のときに `ENABLE_DUMPS` を定義する。このファームは `CONFIG_COMPILER_OPTIMIZATION_ASSERTIONS_ENABLE=y` でビルドしていて、`NDEBUG` をどこでも定義していない（コード）。

その結果、`SWITCH(pc)` に `DUMP_BYTECODE_OR_DONT` が付き（`quickjs.c:19841-19860`）、オペコード1個ごとに次の処理が走っている。

- `ctx->rt` と `rt->dump_flags` を順に読む（ロード2段）。
- 分岐する。
- その先に `dump_single_byte_code` の呼び出しがある。`-Os` はこれを別の場所へ追い出さず、各ハンドラの末尾に約23 B ずつそのまま置いている（逆アセンブル）。

**実測（オブジェクト単位、2026-10-23、ブランチ `worktree-agent-a5d13a17c3d64bbbb` の `53af3d2`）:** `QJS_DISABLE_DUMPS` を定義すると、`JS_CallInternal` が 26,602 → 21,742 B（−4,860 B、−18.3%）、命令数が 10,377 → 8,366 になった。検査 211 箇所はすべて消えた。assertion は残る。host の vmtest 80/80（asan・o2・force-yield・budget-jobs 3）と test262 で、退行は 0。**実機のターン時間はまだ測っていない。**

### 4.2 get_var をスロットにする（S0）

アプリは `JS_EVAL_TYPE_GLOBAL` で評価される（`app_session.c:844`）。そのため、トップレベルの `let` / `const` はグローバル変数表に入り、毎回 atom でハッシュ検索される。DERBY では2,981回/フレーム（全命令の7.8%）。ただし、その単価はまだ測っていない（仮定値 1.28 µs）。

### 4.3 TDZ 検査を消す（S0）

**更新（2026-10-23、host 実測）:** コンパイル時の前向きデータフロー解析で、TDZ 命令が 1フレーム 2,323 → 11 になり、全命令は 12,375 → 11,506（−7.0%）になった。評価のピークは −2.6 KB で、ReferenceError を投げるべき場面はすべて今も投げる。試作はブランチ `worktree-agent-a07f1203eefcaae28` の `40b300d`、詳細はそのブランチの `docs/vm/tdz-elision.md`。

以下は ser native 前の数字。get_loc_check と set_loc_uninitialized を合わせて、8,208回/フレーム（21%）。初期化前に読まれないことをコンパイル時に証明できれば、ただの get_loc に置き換えるか、省略できる。省略できる側では、`set_value` の3段の呼び出しも消える。

### 4.4 double を S2 の中で扱う（a）

DERBY は浮動小数点が中心で、比較と除算のほとんどが「slow」の関数を通っている。「slow」の経路が、実際には普段の経路になっている。あわせて、`-Os` で別関数になった小さな関数（`get_u16` / `get_u32` / `set_value` / `JS_FreeValue`）を inline 化する。この一覧は R5 の IRAM 候補（`tools/r5sim/candidates/r5_iram8.lf`）と一致する。

### 4.5 Math の呼び先を固定する（S0、ガード付き）

## 8. メモリ最適化の観点からの照合所見（2026-10-23）

本節は、共有実験ノートと TODO を本計画・関連コードに照合したレビューである。§0〜7 の段階分割を維持し、採否のものさしと確認事項を補う。以下の「推奨」「確認事項」は、実装済みの機能や確認済みの不具合を意味しない。

### 8.1 速度とメモリの予算を分ける（推奨）

目的は JS 実行の消費メモリを減らし、現在のメモリ不足を悪化させずに段階導入すること。§0.1 のサイクル数と触るコード量の2本に、次の資源の判定を加えたい。命令キャッシュの working set が減っても、DRAM やゲストヒープが空くとは限らない。§1 の S0「予算は無制限」は実行予算の扱いであり、解析・評価に使えるメモリが無制限という意味にはしない。

| 分けて記録する資源 | 見たいもの |
|---|---|
| 静的 DRAM / flash / 実行コードの working set | 常駐データ、コード総量、1ターンに触るコード量を別々に記録 |
| 保持 heap / 常駐 bytecode | 読み込み直後と GC 後の生存量。bytecode 本体・定数・atom・付帯情報、関数ごとの状態を含める |
| compile peak / S0 評価 peak | 解析・変換中の入力、出力、解析表などの同時生存量。トップレベル評価の peak とも区別 |
| 実行 peak / 一時 alloc | 最悪の論理ターンでの同時占有量、alloc/free 回数、累積要求 bytes、allocator の実占有 bytes、copy/write 量を区別 |
| stack | C / FreeRTOS タスクの stack と、ゲスト heap 上の VM frame・segment・cache を区別。二重計上しない |
| 空き領域 | 総空き量に加え largest free block。空きが同じでも次の確保が通るとは限らない |

T0/T1/T2 の採用判定では、読み込み peak・定常保持・最悪 turn peak・stack 余裕・largest free block を同じ条件で比較し、必要な余裕を満たすことを先に確認する。許容する増分と上限は実測から決め、サイクル削減だけで相殺したことにしない。task peak、非 yield の最長区間、固定仕事量の性能も別の評価軸である。

### 8.3 段階導入の成立条件（推奨・確認事項）

1. **まず、既存 T0 試作を同じ条件で比べる。** §4.3 の評価 peak −2,632 B は [TDZ の host 模型](tdz-elision.md) の実測であり、実機の削減量は未確認。出力 bytecode が短くなる利点と、kill を落とした値が次の書き込みまで生存する影響を両方見る。§4.5 は [Math fastpath](math-call-fast.md) の追加 DRAM 0 B の試作として比較する。コード上も関数・引数の解放は汎用経路と共通なので、native frame を省いたことから guest alloc の減少は推論しない。
2. **T1/T2 の状態の実費を設計時に出す。** 関数ごと1〜2 B は論理的な情報量であり、構造体の alignment、allocator の丸め、保持 bytecode の付帯情報、変換中の一時 peak を含めた実占有量とは限らない。インプレースの同長書き換えであっても、観測・失敗履歴・T2 判定に費用が無いとは言えない。同じ命令の3回失敗を、関数単位の情報だけで他の命令の失敗とどう区別するかも決めたい。
3. **同長命令と共通 frame は安全性の必要条件として扱う。** park 中 frame の再開 PC が融合命令の途中を指し得るか、T2 が外れてから S4 で T1 に戻すまでをどの命令表で走るか、途中で例外・park・budget yield が起きても再実行や飛ばしが無いかを確認する。T2 の途中 PC、ジャンプ先、例外位置、命令予算の対応を明示してから導入する。これは現時点の確認事項であり、既知の不具合という指摘ではない。
4. **S4 は毎回「論理ターン終了」とは限らない。** `guest.c` の `drain_jobs` は suspended / yielded では segment を保持して戻り、論理 drain 完了時などに `JS_VMStackTrim` する。§2 の寿命区分どおり、ホストの出口に移す仕事が、park 中の値・所有権・GC root に触れない条件を定める。§4.6 の解放延期は peak を押し上げるため、今は採らない方針が Space と整合する。
5. **S0 が実制約なら、bytecode の flash 保存の順位を見直せる。** 定常 DRAM を減らす約束ではなく、解析・評価中の同時生存を減らす候補である。S0 peak が支配的と測れた場合は、実行パスの速度最適化完了を待たずに検討する余地がある。deserialize 時の一時領域や残るトップレベル評価も含めた内訳を先に測り、採用はその結果で決める。

### 8.4 比較と受入の記録（推奨）

比較元と候補の commit、compiler、ABI、allocator、heap 上限、診断設定、app と入力台本を固定する。§3 と §4.5 のように ser native 化の前後の命令頻度を混ぜない。時間と alloc 計測は別 pass にし、JS、owner タスク、描画、全体のどの範囲を測ったかを明記する。

読み込み、定常、最悪の論理ターン、停止後を分ける。実機では交互 A/B と独立 boot の反復を行い、同じ boot 内の連続 frame を独立した試行として扱わない。保持量や peak の差が診断自身の割当・配置の差でないことも確認する。

例外・評価順・副作用、OOM/GC、所有権、park/resume、budget yield の契約を維持し、固定台本で状態と最終描画を比較する。host の意味論検査、同じ head の CI、実機のメモリ・時間の受入は別工程として記録する。本節の追記自体では新しい実機計測を行っていない。

| prototype 1 段 | 9 |
| 遅い経路（exotic 5、lazy 2） | 7（1.3%） |

今のハンドラは IC が無くても自分のプロパティを inline のハッシュ検索で読むので、IC が省けるのはその検索（推定 15〜25 cycle）と shape 比較（推定 5〜8）の差だけになる。約 540 × 10〜15 cycle ≒ 5〜8 k cycle/ターンで、DERBY の JS ターン（横見 WIDE 14.5〜15.7 ms、首振り WIDE 21.6 ms、実機。`docs/apps/derby-pan-memory.md`）の 0.1〜0.2%（推定）。shape と添字の置き場（命令には atom の 4 B しか無い）に DRAM も要る。**T1 の IC は DERBY を理由には入れない。** STRESS では `get_field_slow_path` が 204 回/ターン（`turn-working-set.md` §4）で事情が違うので、入れるなら STRESS の内訳（exotic と lazy のどちらか）を数えてからにする。

**STRESS でも割に合わない（2026-10-26、host の数え上げ）。** `tools/test_stress_app.c` の 900 フレームを、opprof の写し（`patch_quickjs.py`）と端末と同じ 8 バイトの JSValue（`m32_sysroot.sh`）で走らせ、1 ターンを 1 窓に数えた（`main` の `467562d2`、T0 入り）:

| 命令 | 回数/ターン | 内訳 |
| --- | --- | --- |
| `get_field` | 51.1 | 自分 99.0%、遅い経路（lazy、1 段上）1.0% |
| `get_field2` | 56.6 | 自分 39.9%、prototype 1 段 36.8%、**遅い経路（exotic、受け手そのもの）22.6%** |
| `put_field` | 8.5 | 自分 95.3%、遅い経路（lazy）4.7% |

- 遅い経路は 1 ターンの中央値 5 回・平均 13.7 回・最大 35 回で、100 フレームごとに見ても変わらない。94% が `get_field2` の exotic（12.8 回/ターン）。exotic な受け手（配列など）にメソッドを引く `obj.m()` の形と読める（推定。どの式かは数えていない）。
- `turn-working-set.md` §4 の `get_field_slow_path` 204 回/ターンとは桁が違う。あちらは QEMU の命令の記録で関数の入り口を数えた値で、数え方もビルド（T0 の前）も違う。どちらが差を作ったかは確かめていない。
- **T1 の IC は STRESS を理由にも入れない。** 自分のプロパティは既にハンドラ内で読めている。残る exotic の 12.8 回に専用の道を作っても、1 回 100 cycle と置いて 1.3 k cycle/ターンで、STRESS の 1 ターン（約 1.7 M cycle、`turn-cpi.md`）の 0.1% 未満（推定）。

ここまでで、DERBY の命令の数から見える guard 無しの取り分（P0）はおおむね取った。残る大きな手は配置（P1: T1 ループを IRAM、ジャンプテーブルを DRAM）で、これは実機の I_STALL でしか判断できない。
