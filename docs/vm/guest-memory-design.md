## 1. 現状の仕組み

### 1.1 確保の経路

ゲスト（QuickJS）の確保は 1 ブロックずつ `guest_malloc`（`components/pocketjs_guest/src/guest.c:448`）へ来る。
QuickJS は「大きな塊を取って中で管理する」ことをしない。オブジェクト 1 個、文字列 1 本が、それぞれ 1 回の確保である。

| 段 | 何か | 場所 |
| --- | --- | --- |
| 1 | ブロックキャッシュ: 解放された小さなブロック（8 階級、252 B まで、階級ごとに 16 本、圧迫時 4 本）を同じ長さの次の確保へ返す | `block_cache.h:27,34`、[r3-small-block-cache.md](r3-small-block-cache.md) |
| 2 | アリーナ: ゲスト生成時に取る 1 つの領域。ロック無しの専用 TLSF（`multi_heap_register`） | `guest.c:798`、[qjs-observe.md](qjs-observe.md) §20 |
| 3 | 共有ヒープ: `heap_caps_malloc`。Kasane・Shiki・無線・表示・ソケットと同じプール | `guest.c:460` |

- アリーナの大きさは設定 64 KiB から 8 KiB ずつ下げて試す。条件は「空きの合計 ≥ アリーナ ＋ 56 KiB」と
  「取ったあとに 24 KiB の塊が残る」（`guest.c:360-363`）。実機の STRESS では 24 KiB になる（実測(device)、`GUEST_ARENA bytes=24576`）。
  Shiki の heap が先に取られるため（[qjs-observe.md](qjs-observe.md) §23.3）。
- アリーナは伸びない。満ちたら、以後の確保はすべて 3 段目へ 1 ブロックずつ溢れる。
- 解放はアドレスで振り分ける。別タスクからのアリーナの解放は、ロック無しのスタックに積んで所有タスクが返す（`guest.c:381`）。

### 1.2 上限

- `JSRuntime.malloc_limit`。既定 160 KiB（`main/app_session.c` の `heap_limit`）。`js_malloc_rt`（`quickjs.c:2132`）が、
  確保の前に使用量と比べて断る（上限の拒否）。上限の中でも、アロケータが NULL を返せば断る（アロケータの拒否）。
- OOM カナリアが 2 種類を別々に数える（`quota_count` / `allocator_count`）。

### 1.3 GC の起動条件

QuickJS のメモリ回収は 2 層ある。

1. **参照カウント。** 参照が 0 になった瞬間に解放する。循環していないごみは、すべてここで即座に戻る。
2. **循環回収（以下「GC」）。** 参照カウントでは戻らない循環だけを探す。全 GC オブジェクトを歩く（停止型、増分でない、移動しない）。

GC が走るのは、オブジェクト生成時に `malloc_size` が閾値を超えたとき（`js_trigger_gc`、`quickjs.c:2005`）。

- 閾値は最初が上限の半分（80 KiB、`guest.c:845`）、以後は GC 後の生存量の 1.5 倍。
- 天井: 上限 − 上限/32（160 KiB なら約 158.7 KB、`quickjs.c:1993`）。
- 天井が起こした GC の後は、ヒープが予算 `min(上限/32, (上限 − 床)/2)` だけ伸びるまで待つ（`gc_cap_floor`、[gc-cap-backoff.md](gc-cap-backoff.md)）。
- **アロケータが断っても GC は走らない**（`js_malloc_rt` は回収しない）。

## 2. 何が起きていたか

### 2.1 事実

| 事実 | 出所 |
| --- | --- |
| 起動: アリーナ 24,576 B、評価後 `free=90932 js=44828` | 実測(device) |
| LV3: 使用量 約 130〜141 KB でアロケータが 1,059 B の要求を断る。システムの空き 4〜5 KB、最大ブロック 224〜400 B | 実測(device) |
| 刈り込み後のゲストの使用量（床）が 95 → 138 KB と上がる。STRESS の `pool` は約 3 個 | 実測(device) |
| `InternalError: out of memory at wrap.js:1:114` で EXECUTION FAILED | 実測(device) |
| A（アリーナ 24 KiB）: アロケータの拒否 14 ターン、上限の拒否 0。空きの最小 1.7 KB、そのとき最大ブロック 416 B。床 42 → 59 KB。OOM の間隔 27 → 18 フレーム。GC は 400 フレームで 2 回（LV3 に入ってから 1 回）。ゲストの最大 140.8 KB | 実測(QEMU) |
| B（アリーナ 64 KiB）: アロケータの拒否 0、上限の拒否 10。床 約 41 KB で一定。GC 102 回。最大 162.6 KB。刈り込み後の最大ブロック 25 → 8 KB | 実測(QEMU) |
| A ＋ 拒否の後に GC: 1 回 2〜3.5 KB を回収、床 41〜44 KB で一定、間隔 約 27 | 実測(QEMU) |
| 1,059 B は VM の 2 本目のスタック片（1,024 ＋ 35 B） | コードと [vm-L2-results.md](vm-L2-results.md) §5.6 の表 |

**A と B の比較の注意:** B はアリーナ 64 KiB をバラスト（空きを 91 KB に合わせる詰め物）より前に取ったので、
A より約 40 KB 多くメモリを持っていた。この A/B は「溢れによる断片化」と「上限の超過」を分けていない。

### 2.2 原因（確かな順）

**(a) 上限が、実際に取れる量より大きい（主因。算術は実測値から、確定）。**
評価後のゲストは 44.8 KB、システムの空きは 90.9 KB。160 KiB に届くにはあと約 119 KB 要るが、無い。
ゲストは 135〜140 KB で物理的に尽きる。実機が 130〜141 KB で断られ、空きが 4〜5 KB なのはこれである。
空きの合計が 4〜5 KB のときに最大ブロックが 224〜400 B なのは、満杯のヒープの残りかすで、それだけでは断片化の証拠にならない。

**(b) GC の起動点に届かない（QEMU で確定、実機は推定）。**
天井は約 158.7 KB、物理的な行き止まりは約 140 KB。生存量が約 92 KB を超えると 1.5 倍の閾値も 138 KB を超える。
以後 GC は一度も走らない（A: LV3 に入ってから 1 回）。STRESS は 5 回に 1 回循環を作る（`apps/stress/stress.js:102`）ので、
循環ごみが溜まり続け、床が上がる。拒否の後に GC させると床は上がらなくなった（§2.1）。
実機の床 95 → 138 KB が同じ仕組みかは、実機の `CONFIG_POCKET_OOM_GC_PROBE` の `guest=..->..` で確かめる（未測定）。

**(c) 入口の OOM（コードから確定、実機の行との対応は推定）。**
`frame()` が 2 本目のスタック片まで潜るアプリは、ターンの終わりにその片を返し（D43）、次のフレームの入口で取り直す。
ヒープが尽きていると、ラッパーの `f.apply(` で失敗する（`FRAME_WRAP`、`main/app_session.c:832`。114 桁目は `f.apply` の `(`）。
アプリの `try` は呼ばれる側にあるので捕まえられない。ラッパーが投げ直し、`main/main.c:801` が EXECUTION FAILED にする。
**QEMU では一度も再現していない**（どの run も `frame_errors=0`）。

**(d) 溢れによる共有ヒープの断片化（二次的、QEMU で観測）。**
B でも刈り込み後の最大ブロックは 25 → 8 KB と縮む。ゲストの小さなブロックが共有ヒープに 1 個ずつ混ざり、
長生きの 1 個が周りの空きを分断する。クラッシュの主因ではないが、ネイティブ（Kasane の arena、ソケット）の
連続領域を時間とともに削る。A/B が (a) と分かれていないので、**寄与の大きさは未確定**。

## 3. 方針

1. **空いているメモリは使う。** 「念のため」の予約はしない。小さなアプリがアリーナの残りを抱えたままにしない。
2. **上限は、実際に取れる量にする。** 固定の 160 KiB は「取れるかもしれない量」であって、約束ではない。
3. **尽きるときは、アプリが捕まえられる OOM で尽きる。** 共有ヒープの底ではなく、ゲストの上限で断る。
   ネイティブの作業場所が残っているので、OOM の後の `patch` や回復処理が動く。
4. **共有ヒープを細切れにしない。** ゲストの小さなブロックは、ゲストの領域の中に置く。共有ヒープから見えるゲストは、少数の大きな塊だけにする。
5. **速い道を遅くしない。** 確保は JS のターンの約 35〜38%（[qjs-observe.md](qjs-observe.md) §7）。ブロックキャッシュの当たりと、今の塊での確保は、命令列を変えない。
6. **GC は強くしない。起動を正しくする**（§7）。

「床」（ネイティブに残す量）は 1 の例外に見えるが、遊んでいるメモリではない。Kasane の `replace`、
ファイルの 1 ブロック、ソケット、VM のスタック片が毎フレーム出入りする作業場所である。
床が無かったときの値は「空き 1.7〜5 KB」で、そこでは `V.patch` も失敗していた（[lv3-heap-exhaustion.md](lv3-heap-exhaustion.md) §3）。

## 4. 実装済み（`7b0c2a0`）

### 4.1 D44: フレームの入口のスタック片を残す

`js_vm_stack_trim`（`quickjs-vmstack.h:662`）は、ターンの終わりに `JS_VM_SEG_KEEP`（1,024 B、`:660`）以下の
キャッシュを 1 本だけ残す。常駐 約 1 KB。入口での確保が無くなるので、(c) の失敗点が消える。
**どこでも検証できていない**（QEMU で (c) が再現しないため）。実機の LV3 で確かめる。

### 4.2 アロケータが断ったターンの後の GC

`report_oom_if_any`（`main/app_session.c:227`）が、`allocator_count > 0` のターンの後で `JS_RunGC` を呼ぶ。
ターンの間なので安全。4.3 が効いていれば、ここはほぼ通らない保険になる。

### 4.3 上限の追従

`pocketjs_guest_fit_limit`（`guest.c:1507`）。ネイティブの標本（100 ms ごと、`sample_memory_pressure`、`main/app_session.c:270`）で:

```
上限 = min(160 KiB, 使用量 ＋ アリーナの空き ＋ ブロックキャッシュの保持分 ＋ max(0, システムの空き − 床))
```

床は `CONFIG_POCKET_GUEST_NATIVE_FLOOR_KB`（既定 16、0 で固定の上限に戻る）。
GC の天井と後退の予算は上限からの割合なので、上限が下がれば GC の起動点も一緒に下がる。VM の変更は無い。

### 4.4 結果（実測(QEMU)、アリーナ 24 KiB）

| | 対策なし | 4.2 のみ | 4.2 ＋ 4.3（床 16 KiB） |
| --- | ---: | ---: | ---: |
| アロケータが断ったターン | 14 | 11 | 0 |
| 上限が断ったターン | 0 | 0 | 14 |
| 空きの最小 | 1.7 KB | — | 15.6 KB |
| 最大ブロックの最小 | 416 B | 384 B | 7.7 KB |
| OOM のときの床 | 42 → 59 KB | 41〜44 KB | 41〜43 KB |
| GC の回数 | 2 | — | 128 |
| ゲストの最大 | 140.8 KB | — | 125.7 KB |

- 合わせた上限は約 120 KB。ターンあたりの命令数（ターン 61〜400）は 177,072、B は 176,928（+0.08%）。
- **代償:** ゲストの最大が 140.8 → 125.7 KB に下がる。床 16 KiB を、ゲストからネイティブへ渡した分である。
  以前の 140.8 KB は「ネイティブが動けない状態で持っていた量」なので、使える量としては比べられない。

### 4.5 4.3 の残りの穴（未対処）

- **標本は 100 ms ごと。** その間にネイティブが大きく取ると、次の標本までは古い上限で走る。4.2 が受ける。
- **評価中は追従しない（推定）。** 標本はターンの始めにしか採られないので、ソースの評価は 160 KiB のまま走るはず。
  DERBY の評価のピークには影響しないと見ているが、コードの経路を確かめていない。
- **アリーナの空きは、断片化していれば全部は使えない。** 上限より先にアロケータが断ることは残りうる（4.2 が受ける）。
- **上限が毎標本わずかに動く。** 天井も動くので、天井の近くで使用量が出入りし、余分な GC を起こしうる（§7.3 の G2）。

## 5. 伸びるアリーナ（塊）— 試して、設計のままでは不採用

> **結果（§5.7）:** 実装して（`7767f64`、`CONFIG_POCKET_VM_GUEST_CHUNK_KB`、既定 0）QEMU と実機で測った。
> QEMU では良く見え、実機では悪かった。§5.1〜§5.6 は当初の設計の記録として残す。コードは残すが、既定は固定のアリーナ。

4.3 で「尽き方」は直る。残るのは方針 1 と 4: 小さなアプリが 24〜64 KiB のアリーナを抱える件と、
アリーナより大きいアプリの小さなブロックが共有ヒープに混ざる件（(d)）。

### 5.1 形

アリーナを、必要になったら取り、空になったら返す **塊の列** にする。塊の中は今と同じ TLSF（`multi_heap_register`）。
共有ヒープから見えるゲストは、同じ大きさの少数のブロックになる。同じ大きさなので、返した穴は次の塊がそのまま使える。

```c
/* pocketjs_guest の中。静的 DRAM は増えない。 */
struct guest_chunk { multi_heap_handle_t heap; uint8_t *lo, *hi; uint32_t empty_free; };
struct guest_chunk chunk[GUEST_CHUNKS];   /* 12 */
uint8_t chunk_n, chunk_cur;
/* guest->arena は chunk[chunk_cur].heap を指し続ける: 速い道は今と同じ 1 回の呼び出し */
```

### 5.2 大きさ

| 項目 | 値 | 理由 |
| --- | --- | --- |
| 塊 | 16 KiB。取れなければ 8 KiB | 実機は連続領域が乏しい（評価後の最大 31,744 B、実測(device)）。小さいほど空になりやすく、取りやすい。小さすぎると TLSF の管理領域の割合が増える |
| TLSF の管理領域 | 1 塊 約 0.5〜1 KB（**推定**） | r5sim で、登録直後の `multi_heap_free_size` を読んで確かめる。16 KiB で 6% を超えるなら塊を 24 KiB にする |
| 最初の塊 | 16 KiB を生成時に 1 本 | 今の「64 KiB から下げて試す」をやめる。小さなアプリの持ち分が 24 KiB → 16 KiB、評価が伸びれば自然に増える |
| 塊を通さない確保 | 2 KiB を超える要求は `heap_caps` へ直接 | 数が少なく、解放されれば共有ヒープで隣とつながる。塊に入れると 1 個で塊を留める |
| 最大の本数 | 12（16 KiB × 12 = 192 KiB、上限 160 KiB を覆う） | 固定の表。解放時の走査の上限になる |

2 KiB の境目と 16 KiB は出発点で、割り当てトレース（`tools/vmtest` の割り当て記録）の大きさの分布で決め直す。

### 5.3 時機

**取る（確保の遅い道だけ）。** 今の塊が NULL を返したら:

1. 古い塊から順に、空きの合計（O(1)）が要求より大きいものを試し、取れたらそれを今の塊にする。
   古い塊を優先するのは、長生きのオブジェクトを古い塊に詰め、新しい塊が空になりやすくするため。
2. 無ければ新しい塊を取る。条件は「システムの空き − 塊 ≥ 床」。満たさなければ取らず、`heap_caps` へも溢れさせない（NULL を返す）。
   ただし 2 KiB を超える要求は、床を残せる限り `heap_caps` へ通す。
3. 表が満杯、または登録に失敗したら、今と同じ（`heap_caps` へ溢れる）。

**返す（ターンの終わり、所有タスク）。** 12 本の空きを読み、`multi_heap_free_size == empty_free` の塊を返す。

- ふだんは空の塊を 1 本だけ予備に残す（上限の近くで取って返してを繰り返さないため）。
- ネイティブの圧迫（FREE・LARGEST のビット、`main/pocket/pocket_memory.c:19-22`）のときは、ブロックキャッシュを流してから、空の塊を全部返す。
- 予備の 1 本は方針 1 に反するので、N ターン（出発点 30）使われなければ返す。

**上限。** 4.3 の式の「アリーナの空き」を「全部の塊の空き ＋ 床の上で取れる塊の分」に置き換える。

### 5.4 解放と別タスク

- 解放はブロックキャッシュへ入るのが大半で、そこは塊を知らなくてよい（長さは TLSF のヘッダから読む、`guest.c:316-346`）。
- キャッシュから溢れた解放と `realloc` は、12 本の範囲を走査して塊を見つける（遅い道、1 ターン数十回）。
- 別タスクからの解放は今と同じ積み置き。範囲の表は、塊を公開してからブロックを出し、空になってから消すので、
  生きたブロックの解放と表の書き換えが競合しない（空の塊に生きたブロックは無い）。

### 5.5 失敗時の振る舞い

| 場面 | 振る舞い |
| --- | --- |
| 床を割るので塊を取れない | NULL。上限が先に下がっているので、ふつうは上限の拒否が先に来る。来なければ 4.2 |
| 連続 16 KiB が無い | 8 KiB を試す。それも無ければ上と同じ |
| 塊が 1 個の長生きのブロックで留まる | 留まる。QuickJS は移動しないので直せない。害は最大 16 KiB で、今（共有ヒープのあちこち）より限られる |
| 表の満杯・登録の失敗 | 今の経路（溢れる）へ戻る。ログに 1 行 |

### 5.6 採らない案

- **固定のアリーナに上限を合わせ、溢れを禁じる。** 小さなアプリでメモリが遊び、大きなアプリの予算が減る。方針 1 に反する。
- **大きさ別のスラブ。** 小さなブロックには最良だが、`usable_size` の仕組み（TLSF のヘッダを読む）を作り直すことになる。
  塊の TLSF は今あるコードで足りる。塊で (d) が残ったときの次の手。
- **ゲストをアドレスの端から伸ばす。** `heap_caps`/TLSF にアドレスを指定する確保は無い。領域を予約することになり、方針 1 に反する。

| LV3 のゲストの上限 | 約 124 KB | 約 100 KB | 実測(device) |
| STRESS のプールの最大 | 53 | 38 | 実測(device) |
| LV3 のシステムの空き / 最大ブロック | 17〜79 KB / 15〜22 KB | 33.2 KB / 7.4 KB で固定 | 実測(device) |
| OOM の回数（90 秒） | 26 | 86 | 実測(device) |
| `err` / EXECUTION FAILED | 0 / なし | 0 / なし | 実測(device) |

QEMU の表は、評価の **後** にバラストで空きを 91 KB に合わせた比較である。評価のピークの影響は、作りの上で見えない。

外れた前提は 3 つある。

1. **「空になった塊は返る」（§5.3）は成り立たない。** STRESS がプールを捨てた後（使用量 約 41 KB）、9 本の塊のどれも空にならない
   （実測(QEMU)）。どの塊にも 600〜2,300 B が残り、半分前後はブロックキャッシュの保持分、残りは数百 B の長生きのブロックである。
   §5.5 は「1 個で留まる害は最大 16 KiB」と書いたが、実際は **全部の塊** が留まった。固定のアリーナでは、同じ場面で
   溢れていた約 110 KB が共有ヒープへ戻る（実測(QEMU)）。使用量が上下するアプリでは、ピークの後のネイティブの空きは塊の方が少ない。
2. **評価のピークが塊を取り、評価の後も留める。** 実機の評価直後の空きは 28.3 KB 少なく、最大ブロックは半分（実測(device)）。
   評価のピークは定常の約 2 倍で、ピークで取った塊に、評価の後も要るブロックが散らばって残る（§9）。
3. **塊の単位で取れない空きは、ゲストから使えなくなる。** 実機の共有ヒープは、走るうちに連続 16 KiB も 8 KiB も無くなる
   （実測(device)、最大ブロック 7.4 KB）。固定のアリーナの溢れは 1 ブロックずつなので、どんな小さな穴も使える。
   塊は、塊より小さい空きを数えられない（数えると上限より先にアロケータが断る。lv3-heap-exhaustion.md §6.3 で直した 1 点目）。
   その結果、上限が約 124 → 約 100 KB に下がった。方針 1（空いているメモリは使う）に、塊の方が反した。

QEMU で良く見えた 3 点（上限 +5 KiB、GC −40 回、命令数 −8.6%）の出所は分けていない。命令数の差は、確保が
`heap_caps`（ロックと領域の探索）ではなく専用の TLSF で済む割合が増えたためと見ている（**推定**）。

**塊の変形も、この実機では採らない。**

| 変形 | 判断 | 根拠 |
| --- | --- | --- |
| 評価が終わってから塊を取る | 採らない | QEMU の比較（§6.3）がまさにこの条件で、そこで「塊は返らない」が出た。実機では評価直後の最大ブロックが 31.7 KB（実測(device)）なので、16 KiB の塊は確実には 1 本しか取れない。2 本目以降が取れるかは未測定。前提 1 と 3 は残る |
| 長生きのブロックを別の塊に寄せる | 採らない | 確保の時点で寿命がわからない。評価の時の残るもの（§9.2）は呼び出し元で分けられるが、QEMU で塊を留めたのは **評価の後** に作られた数百 B のブロック（形、atom、表の伸長など。中身は未特定）で、こちらは分けられない |
| 返す前にブロックキャッシュを流す | 効果は半分まで | 留めている量の半分前後がキャッシュ（実測(QEMU)）。残りの長生きのブロックが 1 個でもあれば塊は返らない |
| 評価の後に固定の領域をもう 1 本取る | 採らない | アリーナの生成の条件「取ったあとに 24 KiB の塊が残る」（§1.1）を保つと、31.7 KB から取れるのは約 7 KB（計算） |

**再開する条件:** 共有ヒープの連続領域の事情が変わったとき（例: Shiki の heap より先にゲストの領域を取れる、
ネイティブの常駐が減って評価直後の最大ブロックが 64 KiB を超える）。そのときも、まず「プールを捨てた後に何本返るか」を r5sim で、
評価のピークを含む形（バラストを評価の前に置く）で測る。

## 6. これから: 返却の入口と、床の決め方

### 6.1 返却の入口

「ブロックキャッシュを流し、空の塊を返す」1 つの関数（所有タスク、ターンの間）を、次の 3 か所から呼ぶ。
**改訂:** 関数は入った（`pocketjs_guest_release_memory`、`7767f64`）。塊が既定で無いので、今はブロックキャッシュを流すだけである。
ネイティブの圧迫に入ったときと休止のときに呼んでいる。無線の起動の前に呼ぶ件は未実装（§10 の 5）。
表の「空の塊を返す」は、塊を使わない限り効果が無い。

| 入口 | 今 | 加えること |
| --- | --- | --- |
| ネイティブの圧迫 | キャッシュの深さを 4 にする（`sample_memory_pressure`） | 空の塊を全部返す |
| 休止（Back でアプリを残す） | GC ＋ キャッシュを流す（`guest.c:1152-1171`） | GC の後で空の塊を返す。今のアリーナは休止中も丸ごと持つ |
| 無線の起動 | 空きが 56 KiB 未満なら `LOW_MEMORY`（`main/pocket/pocket_net.c:1438`） | 判定の前に返却を 1 回。ゲストから呼ばれる経路なので、返却はターンの間に限る（要設計） |

無線の 56 KiB は予約しない。今も、アリーナの生成時に見るだけで、その後の溢れが食う（`guest.c:800`）。同じ扱いを保つ。

### 6.2 床の決め方と DERBY

床は、ネイティブが 1 フレームに出し入れする量の最大より上で、できるだけ小さくする。今の 16 KiB は
圧迫の閾値（`LARGEST_ENTER_BYTES`）に合わせた出発点で、**測って決めた値ではない**。

- DERBY のレース中のシステムの空きの最小は 21 KB（実測(device)、ただし別の計測用ビルド）。
  床 16 KiB なら、ゲストが伸びられる余地は約 5 KB（**推定**）。DERBY のゲストの最大は 134.1〜134.8 KB（実測(device)、CLAUDE.md）。
- 上限は「使用量 ＋ 余地」なので、空きが床を下回らない限り、今の使用量が断られることは無い。
  危ないのは、DERBY が一時的に 5 KB より多く伸びる場面（レース開始の構築、FINISH の演出）と、
  空きが床を割る場面（余地 0 になり、次の確保が上限の拒否になる）。
- DERBY と MEGADEMO は `internalFreeBytes` の 18 KB の門を持つ。塊の中の空きは、今のアリーナと同じく、この値に入らない。
  最初の塊が 24 → 16 KiB に減る分、門は通りやすくなる（推定）。

**床の決め方:** 出荷ビルドで、DERBY（レース全体）・MEGADEMO・STRESS LV3 の「システムの空きの最小」と
「上限の拒否の回数」を、床 8・12・16 KiB で取る。DERBY と MEGADEMO で上限の拒否が 0、かつ STRESS LV3 で
アロケータの拒否が 0 になる最小の床を採る。どの床でも DERBY が断られるなら、床ではなく DERBY の予算の問題として扱う。

## 7. GC の役割

問い: 「GC が 1 回 0〜3 KB しか解放しないのは問題ではないか」。

### 7.1 結論

**解放量が少ないのは、欠陥ではなく、この VM の作りからの当然である。欠陥だったのは「いつ走るか」で、そこは直した。**

- QuickJS のごみの大半は、参照カウントが即座に戻す。STRESS が `pool` を捨てると 163 → 41 KB が GC 無しで戻る（実測(QEMU)）。
  「GC の解放量」は、回収された量の全体ではなく、**循環だけ** の量である。
- STRESS の LV3 のメモリは生きている（`pool` が参照している）。どんな回収器でも解放できない。
- STRESS の循環ごみは、27 フレームで 2〜3.5 KB（実測(QEMU)）。GC が 1 回に見つけるのは、これで全部である。
- GC は移動しないので、断片化は直せない。断片化を決めるのは配置（§5）である。

### 7.2 GC にできること・できないこと

| | できる | できない |
| --- | --- | --- |
| 循環ごみの回収 | できる。これが唯一の仕事 | — |
| 生きたデータの解放 | — | できない。アプリが参照を捨てる（圧迫の通知、`pocket.memory.onPressure`）しかない |
| 断片化の解消 | — | できない（移動しない） |
| 小分けの実行 | — | できない。停止型で、全 GC オブジェクトを歩く。増分にするのは VM の大きな改造で、採らない |

### 7.3 それでも変えること

**G1: GC の時間（測定済み）。** 実機、`CONFIG_POCKET_GC_STATS`（[lv3-heap-exhaustion.md](lv3-heap-exhaustion.md) §6.2）。

- 1 回 1.3〜1.8 ms（生存 約 120 KB、LV3）。最大は LV2 の 3.3 ms（20 KB の循環を回収した 1 回）。実測(device)。
  設計時の推定（約 150 KB で 2.5〜5 ms）より短い。
- LV3 では 1 秒に 5〜18 回、合計 8〜29 ms/秒、最大 2.9%。受け入れ条件（5% 以下）は満たす。実測(device)。
- **LV3 の GC の大半は何も回収しない**（`last=124904->124904`）。実測(device)。
- QEMU の命令数では 1 回 2.5〜3.6 万で、実機の約 36 万サイクルの約 1/10。QEMU では GC の時間を測れない。

1 秒の平均では小さいが、フレームで見ると違う。上限に当たるたびに GC は 3〜8 回続く（実測(QEMU)）。
これが 1 フレームに入れば 3.9〜14.4 ms になる（**計算**: 1.3〜1.8 ms × 3〜8 回。1 フレームに何回入るかは未測定）。
30 fps のアプリではフレーム落ちの大きさである。DERBY はゲストの最大が約 134 KB で、合わせた上限の近くを走りうる。

**G2: 上限を 1 KiB 単位にする（実装済み、`3d24656`）。** 上限を 1 KiB に丸め、下げるのは余地が今の上限より
1 KiB 以上下回ったときだけにした。GC 128 → 105 回、上限が変わったターン 398 → 129、拒否は変わらず（実測(QEMU)）。VM の変更は無い。

**G3: 空振りの GC を続けない（実装済み、`0825262`。結果は下の「結果」と [lv3-heap-exhaustion.md](lv3-heap-exhaustion.md) §6.8）。** 塊を採らないので、残る改善のうち実機のデータが直接指すのはここである。

なぜ続くか（コードから。実機の `124904->124904` と合うが、**どの条件で起きているかは未確認**）:

- 天井は「上限 − 上限/32」（124 KB なら約 120.1 KB）。合わせた上限は「使用量 ＋ 余地」なので、システムの空きが床に近いと
  上限が使用量に張り付き、使用量は **ずっと天井の上** にいる。
- 天井の上では、後退の予算 `min(上限/32, (上限 − 床)/2)` だけ伸びるたびに GC が走る（`js_trigger_gc`）。
  `(上限 − 床)/2` は、生存量が上限に近づくほど半分ずつ小さくなる。上限まで 2 KB なら 1 KB、次は 0.5 KB と、
  上限に届くまでに何度も走る。生きているデータが伸びているだけなので、どれも回収しない。
- 4.2（アロケータが断ったターンの後の GC）と上限の拒否の後の回復も、同じ時期に重なる。

変えること（`js_trigger_gc` と `report_oom_if_any`。VM の変更は GC の起動条件だけ）:

1. 天井が起こした GC の回収量を記録する。回収が予算の 1/4 未満なら「空振り」とする。
2. 空振りの後は、半分ずつ詰める規則をやめる。次の天井の GC は「使用量が床より下がった後」（参照カウントが返した = 状況が変わった）か、
   「床から 上限/32 伸びた後」だけにする。上限までの残りが 上限/32 より少なければ、天井の GC はもう走らない。
3. その代わり、**上限が断ったターンの後** に 1 回 GC する（今はアロケータの拒否だけ。4.2 を上限の拒否にも広げる）。
   循環ごみが残りの 上限/32（約 3.9 KB）に溜まっていても、OOM 1 回につき 1 回の GC で回収される。床が上がらないことは保たれる。
4. 回収があった GC（空振りでない）の後は、今の規則のまま。

失うもの: 残りが 上限/32 を切ってから上限に当たるまでに溜まった循環ごみは、OOM を 1 回出してからでないと戻らない。
今は、その手前の GC が拾うことがある。アプリが受ける OOM が増えるかは測る（受け入れ条件 §8.2）。

見込み（**推定**）: LV3 の GC は「OOM の回数 ＋ 伸びた量 / 予算」程度になる。実機の LV3 は 90 秒で OOM 26 回なので、
GC は 1 秒に 5〜18 回から 1〜2 回へ下がる見込み。r5sim の 105 回がいくつになるかで先に確かめる。

実装（下の 2 は設計より単純にした）: 天井が起こした GC の回収が「上限/32 の 1/4」未満なら空振りとし（`g_gc_cap_dry`）、
次の予算を半分に詰めず 上限/32 のままにする。回収があれば今の規則に戻る。ランタイムを作るときに戻す。
3 は `app_session.c` で、アロケータの拒否だけでなく上限の拒否（`quota_count`）の後にも 1 回 GC する。
空振りの印は、ヒープが床より下がった時点で消す（設計の 2 の「床より下がった後」。最初の版はこれが抜けていて、vmtest の
`gc_threshold_near_limit` の strip 版が OOM になった。[lv3-heap-exhaustion.md](lv3-heap-exhaustion.md) §6.8）。

結果:

| | G3 の前 | G3 の後 |
| --- | ---: | ---: |
| r5sim、STRESS LV3、400 フレーム: GC の回数 | 105 | **25** |
| 同: GC のサイクル | 3.58 M | 0.52 M |
| 同: ターンあたりの命令数 | 174,814 | 163,330 |
| 同: 上限が断ったターン / OOM のときの床 | 14 / 41〜43 KB | 14 / 41.2〜43.3 KB |
| 実機、STRESS LV3、約 10 秒の窓: GC の回数 | 約 10 回/秒（4〜15） | **約 3.3 回/秒**（1〜6） |
| 同: GC の時間 | 約 16.6 ms/秒 | **約 4.2 ms/秒** |
| 同: OOM | 約 1.3 回/秒 | 約 1.2 回/秒 |

（実測。前は `378aad2`、後は `0825262` の計測ビルド。どちらも `CONFIG_POCKET_GC_STATS=y`。）受け入れ条件（§8.2）の「1 秒に 3 回以下」は、
平均ではわずかに超える（3.3 回）。1 秒で 5〜6 回の窓が残り、そこは OOM の後の GC と天井の GC が重なっている。OOM は増えていない。

元の G3（閾値を「合わせた上限」に対して決める、循環の多いアプリで後退を一般化する）は、この後に回す。
DERBY と MEGADEMO の循環ごみの量（`POCKET_GC_STATS` の回数と回収量）を測ってから決めることは変わらない。

**G4: 空き時間の GC（採らない。条件が揃えば再検討）。** P2a（[two-core-pipeline.md](../perf/two-core-pipeline.md) §7.3）で
UI のコアに 1 フレーム 6〜8 ms の空きがある。そこで GC を回す案には、次の問題がある。

- GC は小分けにできない。1 回が空きに収まる保証が無い（G1 の値しだい）。
- 遅らせた present が別のコアで走っている間に GC が走ると、ファイナライザがネイティブの資源を解放しうる。
  表示中のフレームが読んでいるものが含まれるかは、§1.3 の条件と同じ検討が要る（未検討）。
- 得るものは「循環ごみを圧迫の前に戻す」ことで、G3 の計測で循環が少なければ、得るものが無い。

休止に入るときの GC は、すでにある（`guest.c:1169`）。フレーム時間を使わない GC の機会は、まずここである。

## 9. 評価の後に何が残るか

問い: 「QuickJS の解析で生存期間の長いオブジェクトが残る。それはパージしてよいものか、高速化のためにつかんでいるものか」。

### 9.1 結論

**残っているのは、解析のごみでも、速さのための取り置きでもなく、ほぼ全部が「プログラムそのものと、その初期状態」である。
パージできるのは行番号表（STRESS で 677 B）くらいで、すでにアプリごとに落とせる。**

根拠（実測(QEMU)、`tools/r5sim` の `memusage()`、`-DR5SIM_MEMUSAGE=1`、`JS_ComputeMemoryUsage`、実機と同じ評価の経路）:

- 評価の直後に `JS_RunGC` を走らせても、内訳は 1 バイトも変わらない。**評価の後にごみは無い。** 定常の約 2 倍あったピークは、
  評価が終わった時点で全部返っている。
- 残るのは、到達できる（生きている）ものだけである。

| | アプリの前（`stub.js`） | STRESS の評価の後 | 差 |
| --- | ---: | ---: | ---: |
| 確保の合計（ブロック / B） | 102 / 18,276 | 484 / 40,120 | +382 / +21,844 |
| atom（個 / B） | 43 / 5,104 | 138 / 7,926 | +95 / +2,822 |
| オブジェクト（個 / B） | 19 / 912 | 89 / 4,272 | +70 / +3,360 |
| プロパティ（B） | 1,104 | 2,448 | +1,344 |
| 形（個 / B） | 17 / 2,776 | 27 / 3,688 | +10 / +912 |
| JS 関数（個 / B） | 3 / 275 | 17 / 2,389 | +14 / +2,114 |
| バイトコード（B） | 74 | 2,743 | +2,669 |
| 行番号表（個 / B） | — | 15 / 677 | +677 |

内訳に出た差の合計は 13,898 B で、残りの約 7.9 KB（計算）は `JS_ComputeMemoryUsage` が分類しない分である
（文字列 4 本 137 B、配列 7、C 関数 17、ブロックごとの課金、atom と形のハッシュ表、ネイティブの面が持つ構造体など。**配分は推定**）。

つまり、塊を留めていたのは「評価の時に、解析の一時領域と **時間的に交互に** 確保された、動かすのに要るデータ」である。
解析器は一時領域を自分で全部返している（`js_create_function` が `JSFunctionDef`・pass-1 のバイトコード・ラベル・変数表を解放する）。
一時領域が返った後に、要るデータが点々と残る。**保持の問題ではなく、配置の問題** である。QuickJS は動かさないので、後から詰め直せない。

### 9.2 分類

| 残るもの | 分類 | 落とせるか、落とす代償 |
| --- | --- | --- |
| バイトコード（関数ごとに 1 ブロック: ヘッダ・定数表・クロージャ変数・命令列） | 動かすのに要る | 落とせない。一番外側のスクリプトの関数は、実行が終わると参照カウントで解放される。残るのは、アプリが参照している関数だけ。初期化で 1 回しか呼ばない関数も、名前が生きていれば残る（VM には「もう呼ばれない」がわからない。アプリが `null` を入れれば解放される） |
| 関数オブジェクト、アプリの初期状態（オブジェクト・プロパティ・配列・文字列） | 動かすのに要る | アプリのデータ。アプリが参照を捨てるしかない |
| atom（プロパティ名、文字列定数、グローバルの名前） | 動かすのに要る。速さのための形でもある | 参照カウントで、使うものが無くなれば解放される。バイトコードと形が指している間は落とせない。名前を 1 か所に集めるのは、比較をポインタで済ませるためと、同じ名前を 1 本にするため（メモリも減らす） |
| 形（shape）と形のハッシュ表 | 動かすのに要る。共有でメモリを減らす | 同じ並びのオブジェクトが 1 つの形を共有する。参照カウント。途中の形は、使うオブジェクトが無ければ残らない |
| ローカル変数の名前（vardefs） | すでに落としてある | harden の後にコンパイルした関数は、名前を捨てて 2 B の表にしている（`js_create_function` の `compact`、[compact-vars.md](compact-vars.md)）。代償は TDZ のエラーの名前と `eval` |
| 関数のソースの文字列 | すでに持たない | `fd->source` を設定する所が無い（[strip-debug.md](strip-debug.md)）。代償は `Function.prototype.toString` |
| 行番号表（pc2line） | **パージ可能**（デバッグ用） | `JS_PocketSetStripDebug`（アプリのチャンクごとの設定）と `CONFIG_POCKET_VM_STRIP_DEBUG`。代償は実行時エラーの位置が関数の先頭行になること。STRESS で 677 B（実測(QEMU)）、DERBY で 2.7〜3.2 KB（実測(device)、[strip-debug.md](strip-debug.md)） |
| atom の配列・atom のハッシュ表・形のハッシュ表 | 速さのため。**伸びるだけで縮まない** | `JS_ResizeAtomHash`・`resize_shape_hash` は新しい表を取って移す。縮める道は無い。ただし評価の後に atom も形も減らないので、縮めても戻るのは余りの分だけ。atom の配列は最小 711 個 × 4 B（コード）。量は未測定、小さいと見る（**推定**） |
| 1.5 倍で伸びる配列の余り（プロパティ、形、配列の要素） | 速さのため（伸長の償却） | 詰める `realloc` を足せば戻るが、次の追加でまた伸びる。量は未測定（§8.3 の 17） |
| ブロックキャッシュ（階級ごとに 16 本、252 B まで） | 速さのため | いつでも流せる（`pocketjs_guest_release_memory`）。止めると JS のターンが 7〜13% 遅くなる（実測(device)、[frame-breakdown.md](../perf/frame-breakdown.md) §7）。圧迫時は深さ 4。`JS_ComputeMemoryUsage` には出ない（ゲストの会計の外） |
| VM のスタック片 1 本（D44、1,024 B） | 動かすのに要る | 落とすと、フレームの入口の OOM（§2.2 (c)）が戻る |
| ランタイム・コンテキスト・組み込み（18,276 B、アプリの前） | 動かすのに要る | アプリより前に確保されるので、まとまって置かれる。塊を留めた原因ではない |

### 9.3 ここから言えること

- **パージで評価の後の空きを増やす道は、ほとんど無い。** STRESS で確実に落とせるのは 677 B。
- 評価のピークそのもの（解析の一時領域）は、評価が終わればすでに返っている。問題になるのは「返った後の空きが、
  残ったブロックで切られること」だけで、固定のアリーナでは、それでも評価直後に 91.0 KB / 最大 31.7 KB が残る（実測(device)）。
- 配置を良くする手はある（§10 の 4）。ただし得るものは **連続領域** で、空きの合計ではない。連続領域が実際に足りていないかを先に測る。

## 10. 改訂した方針と順序

方針（§3）は変えない。変えるのは手段である。**共有ヒープへ 1 ブロックずつ溢れる今の作りは、方針 4（細切れにしない）には反するが、
方針 1（空いているメモリは使う）を、連続領域の乏しいこの実機で満たせる唯一の作りだった。** 方針 4 は、
「尽きる前に上限で断る」（4.3）と床で、害を限る形で受け入れる。

1. **固定のアリーナ ＋ 上限の追従（§4）を、このまま採る。** 残りの検証: 実機の STRESS LV3 を 10 分以上
   （90 秒では `err=0`、空き 17〜79 KB、最大ブロック 15〜22 KB。実測(device)）。D44 は実機でしか確かめられない。
2. ~~**G3: 空振りの GC を続けない**~~（実装済み、`0825262`。GC 約 10 → 3.3 回/秒、実機）（§7.3）。r5sim で回数を見てから実機の `GC_STATS`。実機のデータが直接指している唯一の無駄で、
   変更は GC の起動条件だけである。
3. **評価直後の共有ヒープの地図を測る。** 実機で評価の直後に、空きブロックの大きさの分布と、ゲストの溢れたブロックが
   共有ヒープのどこに何個あるかを出す（`heap_caps_walk` か `heap_caps_print_heap_info`、ゲストのブロックはアドレスで見分ける）。
   あわせて DERBY と MEGADEMO の §9.1 の表を取る。「連続領域を切っているのがゲストの残ったブロックか、ネイティブの常駐か」が決まる。
4. **条件付き: 評価の時の配置を良くする。** 3 で「ゲストの残ったブロックが切っている」かつ「連続領域が足りない場面がある」
   （無線の起動、Kasane の `replace`、休止からの復帰）と出たときだけ行う。候補は 2 つ。
   - **解析の一時領域を、残るものと別の場所に取る。** 必ず死ぬのは一時領域の側で、呼び出し元が少ない（`JSFunctionDef`、
     pass-1 のバイトコードの DynBuf、ラベル、変数表。DERBY のコンパイルのピークの約 8 割。実測(host)、[eval-peak.md](eval-peak.md) §2）。
     残るもの（atom は字句の文字列をそのまま使う）を分けるより確かである。一時領域は共有ヒープへ直接取り、残るものはアリーナから詰める。
     評価が終われば一時領域は全部返る。VM の変更（解析器の確保の経路に印を付ける）が要る。効果は **推定のみ** で、3 の後に r5sim で測る。
   - **事前コンパイル。** 埋め込みのアプリは host でバイトコードにし、実機では読むだけにする。解析の一時領域が最初から無い。
     DERBY で評価の余裕 +26 KB、評価 170 → 49 ms（実測(device)、[eval-peak.md](eval-peak.md) §3.5）。ビルドの手順が要り、
     エディタで書いたプログラムには効かない。
5. **床の掃引（§6.2）と、無線の起動の前の返却（§6.1）。** 塊が無いので、返却はブロックキャッシュを流すことだけである。
6. **元の G3**（循環の多いアプリの閾値）。DERBY と MEGADEMO の循環ごみを測ってから。

**採らないもの:** 塊とその変形（§5.7）。空き時間の GC（G4）。パージのための VM の変更（§9.3。得るものが数百 B）。

**受け入れの目安は §8.2。** この実機の現実は「アプリの起動直後で空き約 91 KB、走るうちに連続 16 KiB が無くなる」なので、
どの変更も「評価直後の空きと最大ブロックを悪くしない」「連続領域を前提にしない」を条件にする。
