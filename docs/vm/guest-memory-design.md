# ゲストのメモリ管理の設計（2026-11-12）

[VMの文書](README.md)

状態: §4 は実装済み（`7b0c2a0`、QEMU で確認、**実機は未測定**）。§5〜§6 は設計のみで未実装。
数値は「実測(device)」「実測(QEMU)」「推定」を必ず付ける。QEMU は `tools/r5sim`（実機のゲスト部品、
Shiki 版 STRESS、LV3 はフレーム 80 から、400 フレーム、評価後のシステムの空きを実機の約 91 KB に合わせた）。
QEMU の値は命令列で、時間を含まない。もとの記録は [lv3-heap-exhaustion.md](lv3-heap-exhaustion.md)。

## 1. 現状の仕組み

### 1.1 確保の経路

ゲスト（QuickJS）の確保は 1 ブロックずつ `guest_malloc`（`components/pocketjs_guest/src/guest.c:448`）へ来る。
QuickJS は「大きな塊を取って中で管理する」ことをしない。オブジェクト 1 個、文字列 1 本が、それぞれ 1 回の確保である。

| 段 | 何か | 場所 |
| --- | --- | --- |
| 1 | ブロックキャッシュ: 解放された小さなブロック（8 階級、252 B まで、階級ごとに 16 本、圧迫時 4 本）を同じ長さの次の確保へ返す | `block_cache.h:27,34`、[r3-small-block-cache.md](r3-small-block-cache.md) |
| 2 | アリーナ: ゲスト生成時に取る 1 つの領域。ロック無しの専用 TLSF（`multi_heap_register`） | `guest.c:798`、[qjs-observe.md](qjs-observe.md) §20 |
| 3 | 共有ヒープ: `heap_caps_malloc`。Kasane・Shiki・無線・表示・ソケットと同じプール | `guest.c:460` |

- アリーナの大きさは設定 64 KiB から 8 KiB ずつ下げて試す。条件は「空きの合計 ≥ アリーナ ＋ 56 KiB」と
  「取ったあとに 24 KiB の塊が残る」（`guest.c:360-363`）。実機の STRESS では 24 KiB になる（実測(device)、`GUEST_ARENA bytes=24576`）。
  Shiki の heap が先に取られるため（[qjs-observe.md](qjs-observe.md) §23.3）。
- アリーナは伸びない。満ちたら、以後の確保はすべて 3 段目へ 1 ブロックずつ溢れる。
- 解放はアドレスで振り分ける。別タスクからのアリーナの解放は、ロック無しのスタックに積んで所有タスクが返す（`guest.c:381`）。

### 1.2 上限

- `JSRuntime.malloc_limit`。既定 160 KiB（`main/app_session.c` の `heap_limit`）。`js_malloc_rt`（`quickjs.c:2132`）が、
  確保の前に使用量と比べて断る（上限の拒否）。上限の中でも、アロケータが NULL を返せば断る（アロケータの拒否）。
- OOM カナリアが 2 種類を別々に数える（`quota_count` / `allocator_count`）。

### 1.3 GC の起動条件

QuickJS のメモリ回収は 2 層ある。

1. **参照カウント。** 参照が 0 になった瞬間に解放する。循環していないごみは、すべてここで即座に戻る。
2. **循環回収（以下「GC」）。** 参照カウントでは戻らない循環だけを探す。全 GC オブジェクトを歩く（停止型、増分でない、移動しない）。

GC が走るのは、オブジェクト生成時に `malloc_size` が閾値を超えたとき（`js_trigger_gc`、`quickjs.c:2005`）。

- 閾値は最初が上限の半分（80 KiB、`guest.c:845`）、以後は GC 後の生存量の 1.5 倍。
- 天井: 上限 − 上限/32（160 KiB なら約 158.7 KB、`quickjs.c:1993`）。
- 天井が起こした GC の後は、ヒープが予算 `min(上限/32, (上限 − 床)/2)` だけ伸びるまで待つ（`gc_cap_floor`、[gc-cap-backoff.md](gc-cap-backoff.md)）。
- **アロケータが断っても GC は走らない**（`js_malloc_rt` は回収しない）。

## 2. 何が起きていたか

### 2.1 事実

| 事実 | 出所 |
| --- | --- |
| 起動: アリーナ 24,576 B、評価後 `free=90932 js=44828` | 実測(device) |
| LV3: 使用量 約 130〜141 KB でアロケータが 1,059 B の要求を断る。システムの空き 4〜5 KB、最大ブロック 224〜400 B | 実測(device) |
| 刈り込み後のゲストの使用量（床）が 95 → 138 KB と上がる。STRESS の `pool` は約 3 個 | 実測(device) |
| `InternalError: out of memory at wrap.js:1:114` で EXECUTION FAILED | 実測(device) |
| A（アリーナ 24 KiB）: アロケータの拒否 14 ターン、上限の拒否 0。空きの最小 1.7 KB、そのとき最大ブロック 416 B。床 42 → 59 KB。OOM の間隔 27 → 18 フレーム。GC は 400 フレームで 2 回（LV3 に入ってから 1 回）。ゲストの最大 140.8 KB | 実測(QEMU) |
| B（アリーナ 64 KiB）: アロケータの拒否 0、上限の拒否 10。床 約 41 KB で一定。GC 102 回。最大 162.6 KB。刈り込み後の最大ブロック 25 → 8 KB | 実測(QEMU) |
| A ＋ 拒否の後に GC: 1 回 2〜3.5 KB を回収、床 41〜44 KB で一定、間隔 約 27 | 実測(QEMU) |
| 1,059 B は VM の 2 本目のスタック片（1,024 ＋ 35 B） | コードと [vm-L2-results.md](vm-L2-results.md) §5.6 の表 |

**A と B の比較の注意:** B はアリーナ 64 KiB をバラスト（空きを 91 KB に合わせる詰め物）より前に取ったので、
A より約 40 KB 多くメモリを持っていた。この A/B は「溢れによる断片化」と「上限の超過」を分けていない。

### 2.2 原因（確かな順）

**(a) 上限が、実際に取れる量より大きい（主因。算術は実測値から、確定）。**
評価後のゲストは 44.8 KB、システムの空きは 90.9 KB。160 KiB に届くにはあと約 119 KB 要るが、無い。
ゲストは 135〜140 KB で物理的に尽きる。実機が 130〜141 KB で断られ、空きが 4〜5 KB なのはこれである。
空きの合計が 4〜5 KB のときに最大ブロックが 224〜400 B なのは、満杯のヒープの残りかすで、それだけでは断片化の証拠にならない。

**(b) GC の起動点に届かない（QEMU で確定、実機は推定）。**
天井は約 158.7 KB、物理的な行き止まりは約 140 KB。生存量が約 92 KB を超えると 1.5 倍の閾値も 138 KB を超える。
以後 GC は一度も走らない（A: LV3 に入ってから 1 回）。STRESS は 5 回に 1 回循環を作る（`apps/stress/stress.js:102`）ので、
循環ごみが溜まり続け、床が上がる。拒否の後に GC させると床は上がらなくなった（§2.1）。
実機の床 95 → 138 KB が同じ仕組みかは、実機の `CONFIG_POCKET_OOM_GC_PROBE` の `guest=..->..` で確かめる（未測定）。

**(c) 入口の OOM（コードから確定、実機の行との対応は推定）。**
`frame()` が 2 本目のスタック片まで潜るアプリは、ターンの終わりにその片を返し（D43）、次のフレームの入口で取り直す。
ヒープが尽きていると、ラッパーの `f.apply(` で失敗する（`FRAME_WRAP`、`main/app_session.c:832`。114 桁目は `f.apply` の `(`）。
アプリの `try` は呼ばれる側にあるので捕まえられない。ラッパーが投げ直し、`main/main.c:801` が EXECUTION FAILED にする。
**QEMU では一度も再現していない**（どの run も `frame_errors=0`）。

**(d) 溢れによる共有ヒープの断片化（二次的、QEMU で観測）。**
B でも刈り込み後の最大ブロックは 25 → 8 KB と縮む。ゲストの小さなブロックが共有ヒープに 1 個ずつ混ざり、
長生きの 1 個が周りの空きを分断する。クラッシュの主因ではないが、ネイティブ（Kasane の arena、ソケット）の
連続領域を時間とともに削る。A/B が (a) と分かれていないので、**寄与の大きさは未確定**。

## 3. 方針

1. **空いているメモリは使う。** 「念のため」の予約はしない。小さなアプリがアリーナの残りを抱えたままにしない。
2. **上限は、実際に取れる量にする。** 固定の 160 KiB は「取れるかもしれない量」であって、約束ではない。
3. **尽きるときは、アプリが捕まえられる OOM で尽きる。** 共有ヒープの底ではなく、ゲストの上限で断る。
   ネイティブの作業場所が残っているので、OOM の後の `patch` や回復処理が動く。
4. **共有ヒープを細切れにしない。** ゲストの小さなブロックは、ゲストの領域の中に置く。共有ヒープから見えるゲストは、少数の大きな塊だけにする。
5. **速い道を遅くしない。** 確保は JS のターンの約 35〜38%（[qjs-observe.md](qjs-observe.md) §7）。ブロックキャッシュの当たりと、今の塊での確保は、命令列を変えない。
6. **GC は強くしない。起動を正しくする**（§7）。

「床」（ネイティブに残す量）は 1 の例外に見えるが、遊んでいるメモリではない。Kasane の `replace`、
ファイルの 1 ブロック、ソケット、VM のスタック片が毎フレーム出入りする作業場所である。
床が無かったときの値は「空き 1.7〜5 KB」で、そこでは `V.patch` も失敗していた（[lv3-heap-exhaustion.md](lv3-heap-exhaustion.md) §3）。

## 4. 実装済み（`7b0c2a0`）

### 4.1 D44: フレームの入口のスタック片を残す

`js_vm_stack_trim`（`quickjs-vmstack.h:662`）は、ターンの終わりに `JS_VM_SEG_KEEP`（1,024 B、`:660`）以下の
キャッシュを 1 本だけ残す。常駐 約 1 KB。入口での確保が無くなるので、(c) の失敗点が消える。
**どこでも検証できていない**（QEMU で (c) が再現しないため）。実機の LV3 で確かめる。

### 4.2 アロケータが断ったターンの後の GC

`report_oom_if_any`（`main/app_session.c:227`）が、`allocator_count > 0` のターンの後で `JS_RunGC` を呼ぶ。
ターンの間なので安全。4.3 が効いていれば、ここはほぼ通らない保険になる。

### 4.3 上限の追従

`pocketjs_guest_fit_limit`（`guest.c:1507`）。ネイティブの標本（100 ms ごと、`sample_memory_pressure`、`main/app_session.c:270`）で:

```
上限 = min(160 KiB, 使用量 ＋ アリーナの空き ＋ ブロックキャッシュの保持分 ＋ max(0, システムの空き − 床))
```

床は `CONFIG_POCKET_GUEST_NATIVE_FLOOR_KB`（既定 16、0 で固定の上限に戻る）。
GC の天井と後退の予算は上限からの割合なので、上限が下がれば GC の起動点も一緒に下がる。VM の変更は無い。

### 4.4 結果（実測(QEMU)、アリーナ 24 KiB）

| | 対策なし | 4.2 のみ | 4.2 ＋ 4.3（床 16 KiB） |
| --- | ---: | ---: | ---: |
| アロケータが断ったターン | 14 | 11 | 0 |
| 上限が断ったターン | 0 | 0 | 14 |
| 空きの最小 | 1.7 KB | — | 15.6 KB |
| 最大ブロックの最小 | 416 B | 384 B | 7.7 KB |
| OOM のときの床 | 42 → 59 KB | 41〜44 KB | 41〜43 KB |
| GC の回数 | 2 | — | 128 |
| ゲストの最大 | 140.8 KB | — | 125.7 KB |

- 合わせた上限は約 120 KB。ターンあたりの命令数（ターン 61〜400）は 177,072、B は 176,928（+0.08%）。
- **代償:** ゲストの最大が 140.8 → 125.7 KB に下がる。床 16 KiB を、ゲストからネイティブへ渡した分である。
  以前の 140.8 KB は「ネイティブが動けない状態で持っていた量」なので、使える量としては比べられない。

### 4.5 4.3 の残りの穴（未対処）

- **標本は 100 ms ごと。** その間にネイティブが大きく取ると、次の標本までは古い上限で走る。4.2 が受ける。
- **評価中は追従しない（推定）。** 標本はターンの始めにしか採られないので、ソースの評価は 160 KiB のまま走るはず。
  DERBY の評価のピークには影響しないと見ているが、コードの経路を確かめていない。
- **アリーナの空きは、断片化していれば全部は使えない。** 上限より先にアロケータが断ることは残りうる（4.2 が受ける）。
- **上限が毎標本わずかに動く。** 天井も動くので、天井の近くで使用量が出入りし、余分な GC を起こしうる（§7.3 の G2）。

## 5. これから: 伸びるアリーナ（塊）

4.3 で「尽き方」は直る。残るのは方針 1 と 4: 小さなアプリが 24〜64 KiB のアリーナを抱える件と、
アリーナより大きいアプリの小さなブロックが共有ヒープに混ざる件（(d)）。

### 5.1 形

アリーナを、必要になったら取り、空になったら返す **塊の列** にする。塊の中は今と同じ TLSF（`multi_heap_register`）。
共有ヒープから見えるゲストは、同じ大きさの少数のブロックになる。同じ大きさなので、返した穴は次の塊がそのまま使える。

```c
/* pocketjs_guest の中。静的 DRAM は増えない。 */
struct guest_chunk { multi_heap_handle_t heap; uint8_t *lo, *hi; uint32_t empty_free; };
struct guest_chunk chunk[GUEST_CHUNKS];   /* 12 */
uint8_t chunk_n, chunk_cur;
/* guest->arena は chunk[chunk_cur].heap を指し続ける: 速い道は今と同じ 1 回の呼び出し */
```

### 5.2 大きさ

| 項目 | 値 | 理由 |
| --- | --- | --- |
| 塊 | 16 KiB。取れなければ 8 KiB | 実機は連続領域が乏しい（評価後の最大 31,744 B、実測(device)）。小さいほど空になりやすく、取りやすい。小さすぎると TLSF の管理領域の割合が増える |
| TLSF の管理領域 | 1 塊 約 0.5〜1 KB（**推定**） | r5sim で、登録直後の `multi_heap_free_size` を読んで確かめる。16 KiB で 6% を超えるなら塊を 24 KiB にする |
| 最初の塊 | 16 KiB を生成時に 1 本 | 今の「64 KiB から下げて試す」をやめる。小さなアプリの持ち分が 24 KiB → 16 KiB、評価が伸びれば自然に増える |
| 塊を通さない確保 | 2 KiB を超える要求は `heap_caps` へ直接 | 数が少なく、解放されれば共有ヒープで隣とつながる。塊に入れると 1 個で塊を留める |
| 最大の本数 | 12（16 KiB × 12 = 192 KiB、上限 160 KiB を覆う） | 固定の表。解放時の走査の上限になる |

2 KiB の境目と 16 KiB は出発点で、割り当てトレース（`tools/vmtest` の割り当て記録）の大きさの分布で決め直す。

### 5.3 時機

**取る（確保の遅い道だけ）。** 今の塊が NULL を返したら:

1. 古い塊から順に、空きの合計（O(1)）が要求より大きいものを試し、取れたらそれを今の塊にする。
   古い塊を優先するのは、長生きのオブジェクトを古い塊に詰め、新しい塊が空になりやすくするため。
2. 無ければ新しい塊を取る。条件は「システムの空き − 塊 ≥ 床」。満たさなければ取らず、`heap_caps` へも溢れさせない（NULL を返す）。
   ただし 2 KiB を超える要求は、床を残せる限り `heap_caps` へ通す。
3. 表が満杯、または登録に失敗したら、今と同じ（`heap_caps` へ溢れる）。

**返す（ターンの終わり、所有タスク）。** 12 本の空きを読み、`multi_heap_free_size == empty_free` の塊を返す。

- ふだんは空の塊を 1 本だけ予備に残す（上限の近くで取って返してを繰り返さないため）。
- ネイティブの圧迫（FREE・LARGEST のビット、`main/pocket/pocket_memory.c:19-22`）のときは、ブロックキャッシュを流してから、空の塊を全部返す。
- 予備の 1 本は方針 1 に反するので、N ターン（出発点 30）使われなければ返す。

**上限。** 4.3 の式の「アリーナの空き」を「全部の塊の空き ＋ 床の上で取れる塊の分」に置き換える。

### 5.4 解放と別タスク

- 解放はブロックキャッシュへ入るのが大半で、そこは塊を知らなくてよい（長さは TLSF のヘッダから読む、`guest.c:316-346`）。
- キャッシュから溢れた解放と `realloc` は、12 本の範囲を走査して塊を見つける（遅い道、1 ターン数十回）。
- 別タスクからの解放は今と同じ積み置き。範囲の表は、塊を公開してからブロックを出し、空になってから消すので、
  生きたブロックの解放と表の書き換えが競合しない（空の塊に生きたブロックは無い）。

### 5.5 失敗時の振る舞い

| 場面 | 振る舞い |
| --- | --- |
| 床を割るので塊を取れない | NULL。上限が先に下がっているので、ふつうは上限の拒否が先に来る。来なければ 4.2 |
| 連続 16 KiB が無い | 8 KiB を試す。それも無ければ上と同じ |
| 塊が 1 個の長生きのブロックで留まる | 留まる。QuickJS は移動しないので直せない。害は最大 16 KiB で、今（共有ヒープのあちこち）より限られる |
| 表の満杯・登録の失敗 | 今の経路（溢れる）へ戻る。ログに 1 行 |

### 5.6 採らない案

- **固定のアリーナに上限を合わせ、溢れを禁じる。** 小さなアプリでメモリが遊び、大きなアプリの予算が減る。方針 1 に反する。
- **大きさ別のスラブ。** 小さなブロックには最良だが、`usable_size` の仕組み（TLSF のヘッダを読む）を作り直すことになる。
  塊の TLSF は今あるコードで足りる。塊で (d) が残ったときの次の手。
- **ゲストをアドレスの端から伸ばす。** `heap_caps`/TLSF にアドレスを指定する確保は無い。領域を予約することになり、方針 1 に反する。

## 6. これから: 返却の入口と、床の決め方

### 6.1 返却の入口

「ブロックキャッシュを流し、空の塊を返す」1 つの関数（所有タスク、ターンの間）を、次の 3 か所から呼ぶ。

| 入口 | 今 | 加えること |
| --- | --- | --- |
| ネイティブの圧迫 | キャッシュの深さを 4 にする（`sample_memory_pressure`） | 空の塊を全部返す |
| 休止（Back でアプリを残す） | GC ＋ キャッシュを流す（`guest.c:1152-1171`） | GC の後で空の塊を返す。今のアリーナは休止中も丸ごと持つ |
| 無線の起動 | 空きが 56 KiB 未満なら `LOW_MEMORY`（`main/pocket/pocket_net.c:1438`） | 判定の前に返却を 1 回。ゲストから呼ばれる経路なので、返却はターンの間に限る（要設計） |

無線の 56 KiB は予約しない。今も、アリーナの生成時に見るだけで、その後の溢れが食う（`guest.c:800`）。同じ扱いを保つ。

### 6.2 床の決め方と DERBY

床は、ネイティブが 1 フレームに出し入れする量の最大より上で、できるだけ小さくする。今の 16 KiB は
圧迫の閾値（`LARGEST_ENTER_BYTES`）に合わせた出発点で、**測って決めた値ではない**。

- DERBY のレース中のシステムの空きの最小は 21 KB（実測(device)、ただし別の計測用ビルド）。
  床 16 KiB なら、ゲストが伸びられる余地は約 5 KB（**推定**）。DERBY のゲストの最大は 134.1〜134.8 KB（実測(device)、CLAUDE.md）。
- 上限は「使用量 ＋ 余地」なので、空きが床を下回らない限り、今の使用量が断られることは無い。
  危ないのは、DERBY が一時的に 5 KB より多く伸びる場面（レース開始の構築、FINISH の演出）と、
  空きが床を割る場面（余地 0 になり、次の確保が上限の拒否になる）。
- DERBY と MEGADEMO は `internalFreeBytes` の 18 KB の門を持つ。塊の中の空きは、今のアリーナと同じく、この値に入らない。
  最初の塊が 24 → 16 KiB に減る分、門は通りやすくなる（推定）。

**床の決め方:** 出荷ビルドで、DERBY（レース全体）・MEGADEMO・STRESS LV3 の「システムの空きの最小」と
「上限の拒否の回数」を、床 8・12・16 KiB で取る。DERBY と MEGADEMO で上限の拒否が 0、かつ STRESS LV3 で
アロケータの拒否が 0 になる最小の床を採る。どの床でも DERBY が断られるなら、床ではなく DERBY の予算の問題として扱う。

## 7. GC の役割

問い: 「GC が 1 回 0〜3 KB しか解放しないのは問題ではないか」。

### 7.1 結論

**解放量が少ないのは、欠陥ではなく、この VM の作りからの当然である。欠陥だったのは「いつ走るか」で、そこは直した。**

- QuickJS のごみの大半は、参照カウントが即座に戻す。STRESS が `pool` を捨てると 163 → 41 KB が GC 無しで戻る（実測(QEMU)）。
  「GC の解放量」は、回収された量の全体ではなく、**循環だけ** の量である。
- STRESS の LV3 のメモリは生きている（`pool` が参照している）。どんな回収器でも解放できない。
- STRESS の循環ごみは、27 フレームで 2〜3.5 KB（実測(QEMU)）。GC が 1 回に見つけるのは、これで全部である。
- GC は移動しないので、断片化は直せない。断片化を決めるのは配置（§5）である。

### 7.2 GC にできること・できないこと

| | できる | できない |
| --- | --- | --- |
| 循環ごみの回収 | できる。これが唯一の仕事 | — |
| 生きたデータの解放 | — | できない。アプリが参照を捨てる（圧迫の通知、`pocket.memory.onPressure`）しかない |
| 断片化の解消 | — | できない（移動しない） |
| 小分けの実行 | — | できない。停止型で、全 GC オブジェクトを歩く。増分にするのは VM の大きな改造で、採らない |

### 7.3 それでも変えること

**G1: GC の時間を測る（最優先、未測定）。** 4.3 の後は上限の近くで GC が増える（QEMU で 400 フレームに 128 回、
B は 102 回）。1 回は全ヒープを歩く。命令数では +0.08% だが、時間は測っていない。実機の
`CONFIG_POCKET_OOM_GC_PROBE` の `gc_us` と、LV3 の 1 秒あたりの GC の回数を取る。
受け入れ: LV3 で GC の時間がフレーム時間の 5% 以下。目安として、約 150 KB の生存量で 1 回 2.5〜5 ms（**推定**、
[gc-cap-backoff.md](gc-cap-backoff.md) の 1 回 約 26 万命令から）。

**G2: 動く上限でも後退が効くようにする（設計、未実装）。** 後退の予算は `min(上限/32, (上限 − 床)/2)` で、
上限に近いほど小さくなる。固定の上限では、上限に当たるたび GC は 3〜8 回で収まる（実測(QEMU)、
[lv3-heap-exhaustion.md](lv3-heap-exhaustion.md) §2）。上限が標本ごとに数百 B 動くと、天井が使用量をまたいで往復し、
この「3〜8 回」が標本のたびに起きうる（推定、未観測。128 回がそれかは分けていない）。対策は追従の側で行う:
上限を 1 KiB 単位に丸め、下げるのは 1 KiB 以上動いたときだけにする。VM の変更は無い。

**G3: 閾値を「合わせた上限」に対して決めるか（測ってから）。** 上流の閾値（生存量の 1.5 倍、最初は 80 KiB）は、
循環ごみを生存量の半分まで溜めることを許す。循環を多く作るアプリでは、死んだメモリが数十 KB 残りうる。
これは方針 1（使えるメモリを使う）に反する。ただし、**実際のアプリが循環をどれだけ作るかを測っていない**。
DERBY と MEGADEMO を `POCKET_GC_STATS` 付きで回し、GC の回数と解放量を取る。循環がほぼ無ければ、何も変えない。
多ければ、後退を一般化する: 前回の GC が伸びた分のうち少ししか解放しなければ次の予算を倍に、多く解放したら半分に
（STRESS LV3 のように「伸びているが生きている」負荷で、無駄な GC が増えないための条件）。

**G4: 空き時間の GC（採らない。条件が揃えば再検討）。** P2a（[two-core-pipeline.md](../perf/two-core-pipeline.md) §7.3）で
UI のコアに 1 フレーム 6〜8 ms の空きがある。そこで GC を回す案には、次の問題がある。

- GC は小分けにできない。1 回が空きに収まる保証が無い（G1 の値しだい）。
- 遅らせた present が別のコアで走っている間に GC が走ると、ファイナライザがネイティブの資源を解放しうる。
  表示中のフレームが読んでいるものが含まれるかは、§1.3 の条件と同じ検討が要る（未検討）。
- 得るものは「循環ごみを圧迫の前に戻す」ことで、G3 の計測で循環が少なければ、得るものが無い。

休止に入るときの GC は、すでにある（`guest.c:1169`）。フレーム時間を使わない GC の機会は、まずここである。
