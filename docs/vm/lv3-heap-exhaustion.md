# STRESS LV3 のヒープ枯渇を QEMU で追う（2026-11-12）

[VMの文書](README.md)

実機で STRESS TEST を LV3 にすると、約 30 秒で EXECUTION FAILED になった。ログの最後は `InternalError: out of memory at wrap.js:1:114`（`frame()` を呼ぶラッパーの中で、STRESS の `try` に入る前の OOM）。ゲストは 160 KiB の上限の手前（約 130〜140 KB）で、システムヒープの空きは約 4〜5 KB、最大ブロック 224〜400 B だった（実測、実機のログ）。

問い: このメモリ不足は、実際に使われている（生きている）メモリか、回収されないごみ（GC が追いつかないスラッシング）か、断片化か。

## 1. 道具

`tools/r5sim`（QEMU の ESP32-S3 像。STRESS のターンを実機と同じゲスト部品で回す）に、測定用の選択肢を足した。

- `-DR5SIM_GC_TRACE=1`: ターンごとの行 `R5SIM GC t= used= thr= gc=(+) freed= last= oom= q= a= req= sys_free= sys_largest= pend= needs= sub=`。GC の回数と解放量は quickjs.c の `POCKET_GC_STATS`（測定用、ファームでは無効）。`q`/`a` は OOM の内訳（ゲストの上限で断った数／アロケータが断った数）。`pend` は Shiki のフレームが提示待ちか、`needs`/`sub` は Kasane が提示を要るか・提出があるか。
- `-DR5SIM_FREE_KIB=89`: 評価の後のシステムヒープの空きを実機と同じ約 91 KB にする（QEMU には無線もパネルも無いので、そのままでは空きがずっと多い）。4 KB の塊で埋める。
- `-DR5SIM_GC_ON_OOM=1`: アロケータが断ったターンの後で GC する実験（今回は使わなかった。アロケータの拒否が起きなかったため）。
- 実行: `FAST_WAIT_TICKS=2400 tools/r5sim/fast.sh .cache/r5gc -DR5SIM_DEVICE=1 -DR5SIM_APP=shiki -DR5SIM_LEVEL_UP=1 -DR5SIM_FRAMES=400 -DR5SIM_GC_TRACE=1 -DR5SIM_FREE_KIB=89`（LV3 はフレーム 80 から）。

## 2. わかったこと（QEMU、命令列。時間は含まない）

- **GC はほとんど何も解放しない。** 1 回あたり 0〜3 KB。LV3 のメモリは生きたデータ（STRESS の `pool`）で、STRESS が `pool` を捨てると参照カウントで即座に戻る（163 KB → 41 KB）。循環ごみの取り残しではない。
- 上限の手前では GC の回数は増える（上限に当たるたび 3〜8 回）が、そのたびに解放はほぼ 0。`gc-cap-backoff.md` の天井の後退が効いていて、毎オブジェクトの GC にはなっていない。
- **断片化が周回ごとに進む。** `pool` を捨てた直後の空きは毎回 87〜89 KB に戻るのに、最大ブロックは 25 KB → 13 KB → 11.5 KB → 8 KB と縮む。
- QEMU では断るのはいつもゲストの上限（`q`）で、アロケータは断らなかった（`a=0`）。実機ではアロケータが 1,059 B の要求を断っている（最大ブロックが 224〜400 B）。実機のほうが断片化がずっと進んでいる（無線・表示・入力のタスクが同じヒープから確保するため、と推定。未確認）。

## 3. 見つけた不具合（修正済み）

QEMU の 1 回目は、フレーム 295 から毎フレーム `STRESS_FAIL frame Error: previous frame awaits presentation or repair` になり、二度と描かなかった。

- その直前のターンは OOM で、HUD の `V.patch` も失敗した。そのターンで commit した Shiki のフレームは前と同じで、損傷が空だった。
- Shiki の `commit` は、image モードでは変わったバンドだけを無効化する（`pocket_kasane_proc_publish_at`）。損傷が空なら何も無効化しない。ふだんは HUD の提出があるので提示が走り、そこで `pending` が下りる。HUD も失敗したターンでは提示が走らず、`pending` が立ったまま残った（トレース: `pend=1 needs=0 sub=0`）。以後の `beginFrame` はすべて BUSY。
- 修正: `commit` の後で Kasane に提示するものが無ければ、そのフレームはその場で提示済みにする（`pocket_shiki_frame.c`、`pocket_proc_present_result(KSN_OK)`）。見せるものが無いので、見せたことにしてよい。
- 修正後: 400 フレームで `fail=0`。フレーム 295 は `pend=0`。

## 3.1 アリーナの大きさの A/B と、拒否の後の GC（QEMU、400 フレーム、空き約 91 KB）

| | A: アリーナ 24 KiB（実機と同じ） | B: 64 KiB | A ＋ 拒否の後に GC（`-DR5SIM_GC_ON_OOM=1`） |
| --- | ---: | ---: | ---: |
| システムヒープが断ったターン | 14 | 0 | 11 |
| ゲストの上限が断ったターン | 0 | 10 | 0 |
| 最大ブロックの最小 | 416 B | 1,152 B | 384 B |
| OOM のときの最大ブロック | 7.2 → 2.6 KB と下がって止まる | 8〜25 KB で上下 | 4.6〜11 KB で上下 |
| OOM のときのゲストの使用量（床） | 42 → 59 KB と上がる | 約 41 KB で一定 | 41〜44 KB で一定 |
| OOM の間隔 | 27 → 18 フレームと縮む | 約 32 | 約 27 |

- **アリーナを実機と同じ 24 KiB にすると、実機の症状（アロケータの拒否、最大ブロックが数百 B、床の上昇）が無線も表示も無しに再現する。** 64 KiB なら上限で止まり、床は上がらない。
- **床が上がるのは、循環ごみが回収されないから。** GC はゲストの使用量が上限の手前（約 158.7 KB）を超えたときにしか走らず、システムヒープが先に尽きるとその点に届かない（Fable のレビュー）。STRESS は 5 回に 1 回循環を作る（`apps/stress/stress.js`）。拒否の後に GC すると、1 回 2〜3.5 KB の循環を回収し、床は上がらなくなった。
- `frame()` の入口で断られる 1,059 B は、VM の 2 本目のスタック片（1,024 ＋ 35 B）。ターンの終わりに毎回返すので、毎フレーム取り直す（Fable のレビュー、`quickjs-vmstack.h`）。

## 4. 実機の EXECUTION FAILED について（未解決）

- 実機では、ゲストが上限に届く前にシステムヒープ（最大ブロック）が尽き、`frame()` の呼び出しそのものが OOM になる。STRESS は自分の `try` の中の OOM は捕まえて回復するが、`frame()` に入る前の OOM は捕まえられない。ラッパーはそれを投げ直し、セッションが終わる。
- 本質は「ゲストの上限 160 KiB が、実機のシステムヒープの実際の余裕より大きい」こと。LV3 は上限まで積むアプリなので、上限より先にシステムヒープが尽きる。
- 次の候補（未実施）: (1) ゲストの上限を、起動時のシステムヒープの空きに合わせて下げる、(2) 断片化を減らす（ゲストのアリーナを大きくする、大きめの確保をアリーナに寄せる）、(3) `frame()` の入口で OOM になったターンはセッションを終わらせずに次のフレームへ進む。

## 5. 対策（2026-11-12、Fable の設計レビューの D と 4 節）

1. **フレームの入口でスタック片を取り直さない（D44）。** `JS_VMStackTrim` はターンの終わりに、`JS_VM_SEG_KEEP`（1,024 B）以下のキャッシュを 1 本だけ残す。約 1 KB 常駐。`frame()` に入るときの確保が無くなる。
2. **システムヒープが断ったターンの後で GC する**（`app_session.c` `report_oom_if_any`）。
3. **ゲストの上限を、実際に取れる量に合わせる**（`pocketjs_guest_fit_limit`、`CONFIG_POCKET_GUEST_NATIVE_FLOOR_KB` 既定 16）。100 ms ごとの標本で、上限 = min(160 KiB, 使用量 ＋ アリーナとブロックキャッシュの空き ＋ システムの空きのうち床より上)。尽きるときは捕まえられる上限の OOM になり、GC の天井（上限の割合）にも届く。床は「遊ばせるメモリ」ではなく、Kasane・無線・表示の作業場所。

QEMU（アリーナ 24 KiB、空き約 91 KB、LV3、400 フレーム）:

| | 対策なし | 2 のみ | 2 ＋ 3（床 16 KiB） |
| --- | ---: | ---: | ---: |
| システムヒープが断ったターン | 14 | 11 | 0 |
| 上限が断ったターン | 0 | 0 | 14 |
| LV3 中の空きの最小 | 1.7 KB | — | 15.6 KB |
| 最大ブロックの最小 | 416 B | 384 B | 7.7 KB |
| OOM のときの床 | 42 → 59 KB | 41〜44 KB | 41〜43 KB |

合わせた上限は約 120 KB（STRESS のとき）。残り: アリーナを必要に応じて 16 KiB の塊で伸ばし、空いた塊を返す（設計 A）、圧力・休止・無線の起動で空いた塊を返す（設計 E）。

## 6. 上限の丸め（G2）、GC の時間（G1）、伸びるアリーナ（2026-11-12）

設計は [guest-memory-design.md](guest-memory-design.md) §5・§7.3。

### 6.1 G2: 上限を 1 KiB 単位にする

`pocketjs_guest_fit_limit` は、上限を 1 KiB に丸め、下げるのは余地が今の上限より 1 KiB 以上下回ったときだけにする。

QEMU（アリーナ 24 KiB、床 16 KiB、LV3、400 フレーム）:

| | 丸めなし | 丸めあり |
| --- | ---: | ---: |
| GC の回数 | 128 | 105 |
| 上限が変わったターン | 398 | 129 |
| 上限が断ったターン | 14 | 14 |
| アロケータが断ったターン | 0 | 0 |

### 6.2 G1: GC の 1 回の時間（実機、`CONFIG_POCKET_GC_STATS`）

`JS_RunGC` の前後の CPU サイクルを数え、1 秒に 1 行 `GC_STATS` を出す（計測専用、既定 n）。

- **1 回 1.3〜1.8 ms**（生存 約 120 KB、LV3）。最大は LV2 の 3.3 ms（20 KB の循環を回収した 1 回）。評価直後の 1 回は 1.5 ms（28 → 10.9 KB）。
- LV3 では 1 秒に 5〜18 回、合計 8〜29 ms/秒。**時間の最大 2.9%**。設計の受け入れ条件（フレーム時間の 5% 以下）は満たす。
- ただし LV3 の GC の大半は何も回収しない（`last=124904->124904`）。上限に当たるたびの「3〜8 回」が、1 秒の中で繰り返されている。後退の一般化（設計 G3）で減らせる。
- QEMU の `gc_cc`（命令数に近い）は 1 回 2.5〜3.6 万で、実機の 1.5 ms（約 36 万サイクル）の約 1/10。GC は全オブジェクトを歩くので、キャッシュミスが支配的と見られる（推定）。QEMU で GC の時間は測れない。

### 6.3 伸びるアリーナ（`CONFIG_POCKET_VM_GUEST_CHUNK_KB`、既定 0）

16 KiB の塊を必要に応じて取り、空になったら返す。2 KiB を超える要求と、どの塊にも入らない要求は共有ヒープへ。

QEMU（同じ条件）:

| | 固定 24 KiB ＋ 上限の追従 | 16 KiB の塊 |
| --- | ---: | ---: |
| アロケータが断ったターン | 0 | 0 |
| 上限（ゲストが使える量） | 約 123 KiB | 128 KiB |
| LV3 のシステムの空きの最小 | 15.6 KB | 23.8 KB |
| GC の回数 | 105 | 65 |
| ターンあたりの命令数 | 174,814 | 159,697 |

- 途中で見つけて直した 2 点: (1) 上限が、塊として取れない細切れの空きまで数えていた（最大ブロックが 8 KiB 未満なら、システムの分は数えない）。(2) 塊の中の穴に入らない 1〜1.3 KB の要求を断っていた（共有ヒープへ回す）。どちらも直す前はアロケータの拒否が 7〜10 ターンあった。
- **塊は返らない。** STRESS がプールを捨てた後（使用量 約 41 KB）、9 本の塊のどれも空にならない。`-DR5SIM_CHUNK_TRACE=1` で見ると、新しい塊も 600〜2,300 B を持ち、その半分前後はブロックキャッシュの中、残りは数百 B の長生きのブロック。移動しない GC では直せない（設計 §5.5 の想定より広い）。
- 固定のアリーナでは、プールを捨てると溢れていた約 110 KB が共有ヒープへ戻った。塊では戻らない。ゲストの使用量が大きく上下するアプリでは、ピークの後のネイティブの空きは塊の方が少ない。

### 6.4 伸びるアリーナの実機（STRESS LV3、90 秒、計測ビルド）

| | 固定 24 KiB（c376d20） | 16 KiB の塊（8e6c7c6） |
| --- | ---: | ---: |
| 評価直後のシステムの空き / 最大ブロック | 91.0 KB / 31.7 KB | 62.7 KB / 15.4 KB |
| LV3 のゲストの上限 | 約 124 KB | 約 100 KB |
| STRESS のプールの最大 | 53 | 38 |
| LV3 のシステムの空き / 最大ブロック | 17〜79 KB / 15〜22 KB | 33.2 KB / 7.4 KB で固定 |
| OOM の回数（同程度の時間） | 26 | 86 |
| GC の 1 回 | 1.3〜1.8 ms | 1.3〜1.4 ms |
| `err` / EXECUTION FAILED | 0 / なし | 0 / なし |

- **実機では塊のほうが悪い。** 評価のピーク（定常の約 2 倍）で取った塊が、長生きのブロックに留められて返らない。評価直後の空きが 28 KB 少なく、最大ブロックも半分になる。
- その後、実機のヒープには連続 16 KiB（8 KiB も）が無く、新しい塊を取れない。上限は「取れない空きは数えない」ので約 100 KB に下がり、ゲストが使える量も減った。
- QEMU では評価の後にバラストでヒープを埋めるので、評価のピークで塊が留まることが見えなかった（§6.3 の表は評価の後の比較）。
- **既定は 0（固定のアリーナ）のまま。** 塊のコードは残す。直すなら、評価中は塊を使わない（評価が終わってから最初の塊を取る）、または長生きのブロックを別の塊に寄せる手が要る（未検討）。

### 6.5 評価直後のヒープの地図（実機、DERBY、`CONFIG_POCKET_HEAP_MAP`）

`heap_caps_walk` で内部ヒープを、ゲストを作る前（Shiki のヒープ 48 KiB は取った後）・評価の直後・ゲストを壊した後の 3 回、歩いた（計測ビルド a90567a）。256 B 以上の空きを位置つきで出す。

| 時点 | 空きの合計 / 最大ブロック | 主領域（0x3fcb5f40、約 206 KB）の空き |
| --- | ---: | --- |
| ゲストの前 | 147,044 / 31,744 | 13 個: 8,808・21,808・2,380・1,808・2,144・948・2,560・11,792・26,780・368・1,960・1,936・25,852 |
| 評価の直後（js=95,304） | 37,496 / 31,744 | 4 個: 324・308・2,052・384（ほぼ満杯） |
| ゲストを壊した後 | 146,396 / 26,624 | ゲストの前と**同じ並び** |

- **主領域は、ゲストを作る前からネイティブに 13 個に切られている。** 大きな穴の間に、小さなネイティブのブロックが 1 個だけ挟まる所がある（例: 11,792 と 26,780 の間に 3,584 B が 1 個、21,808 と 2,380 の間に 84 B が 1 個）。
- **ゲストを壊すと、主領域は「前」と同じ並びに戻る。** ゲストは持続する断片化を残していない。
- **評価の直後、ゲストは主領域をほぼ埋めている。** 解析の一時領域が返った穴も、トップレベルの実行がもう使っている。残る空きは 2 KB 以下の 4 個。
- **「最大ブロック 31,744 B」は別の領域（0x3fcf0000、32 KiB）で、評価の前後で手つかず。** STRESS の評価直後の 31.7 KB（§6.4）も同じ領域と見られる（推定）。この領域は評価中にゲストに使われていない（理由は未確認）。
- 計測ビルドの DERBY は、レース中（96.6 秒）に上限の OOM（`used=110564`）で止まった。出荷版（7b0c2a0）では一周した。差は計測用の 6 KB の静的バッファと見ている（推定、未確認）。

**含意:** 評価中の配置を良くしても（解析の一時領域を別の場所に取る）、DERBY の評価直後の連続領域はほとんど増えない（主領域は満杯で、一時領域の穴は既に埋まっている）。連続領域を決めているのは、ゲストより前にあるネイティブの小さなブロックの位置。

### 6.6 大きな穴を分けているネイティブのブロック（実機、`CONFIG_POCKET_HEAP_ORIGIN`）

ヒープトレース（`HEAP_TRACING_STANDALONE`、leaks モード、300 件、深さ 4）を `app_main` の頭から回し、DERBY を起動する直前の地図（§6.5 の「前」と同じ並び）で、2 KiB 以上の空き 2 つに挟まれた 8 KiB 以下の使用中ブロックの確保元を出した（計測ビルド 97309ae）。トレースの 17 KB が加わるので DERBY 自体は評価中に OOM で起動しなかったが、地図は評価の前に取っている。

| ブロック | 大きさ | 左の空き / 右の空き | 確保元（addr2line） |
| --- | ---: | ---: | --- |
| 0x3fcd3080 | 3,584 | 11,792 / 26,780 | `sys_thread_new`（lwIP、`sys_arch.c:390`）→ `xTaskCreatePinnedToCore`。tcpip スレッドのスタック（`CONFIG_LWIP_TCPIP_TASK_STACK_SIZE=3072`） |
| 0x3fccd6ec | 84 | 21,808 / 2,380 | `sys_sem_new`（lwIP、`sys_arch.c:111`） |
| 0x3fcd0214 | 84 | 2,560 / 11,792 | `xQueueCreateCountingSemaphore` |
| 0x3fcd0154 ほか 2 個 | 12 × 3 | 2,560 / 11,792 | `pthread_key_create` / `pthread_setspecific`（スレッド局所の領域） |

- 6 個すべてが、ネットワークの起動（`main/pocket/wifi_time.c:273` の `esp_netif_init()`、自動時刻同期で起動のたびに走る）で作られるものと見られる。セマフォ・カウンティングセマフォ・pthread のキーの呼び出し元は、深さ 4 が確保の関数の入れ子で尽きて見えていない（lwIP の netconn のスレッド別セマフォと推定）。
- **tcpip スレッドのスタック 3,584 B が 1 個だけ、11,792 B と 26,780 B の穴を分けている。** これが無ければ約 42 KB の連続領域になる（計算）。
- 起動の途中（ホーム画面を作った後）で無線が上がるので、その時点の空きの真ん中に恒久のブロックが置かれる。

### 6.7 lwIP の核を起動の早い時期に作る（`bf6d547`、実機）

AUTO TIME SYNC が ON のとき、`shell_init()` の直後に `esp_netif_init()` を呼ぶ（`wifi_time_stack_early`）。同じ地図の計測ビルド（9fd2654）で DERBY を一周させた。

| | 修正前（a90567a） | 修正後（9fd2654） |
| --- | ---: | ---: |
| DERBY を作る前の最大ブロック | 31,744（別の 32 KiB 領域） | **43,008**（主領域） |
| 主領域の大きな穴 | 21,808・26,780・11,792・25,852 | **24,700・44,296**・25,868 |
| ゲストのアリーナ | 24 KiB | **40 KiB**（連続領域の規則を満たす大きさが増えた） |
| 評価直後の主領域の使用中ブロックの並び | 645 個 + 128 個に分断 | 544 個が 1 続き |
| 同じ計測ビルドの DERBY | レース 96 秒で上限の OOM | **一周（写真・結果まで）** |

- HELLO（Shiki のヒープなし）でも、11,792＋3,584＋26,780 が **44,296 B の 1 つの穴**になった。
- 主領域にはまだ 12 B のブロックが 2 個、穴を分けている（24,700 | 1,456、2,356 | 44,296）。Fable のレビュー（[lwip-resource-review.md](../platform/lwip-resource-review.md)）では、Wi-Fi のタスク別セマフォ（`esp_adapter.c` の `wifi_thread_semphr_get_wrapper`）。`esp_netif_init` を早めても動かない。
- アリーナが 40 KiB になったのは、`GUEST_ARENA_KEEP_PIECE`（24 KiB の連続領域を残す）を満たせる大きさが増えたため。ゲストの使用量の内訳は変わらない。

### 6.8 G3: 空振りの GC を続けない（`0825262`、r5sim と実機）

天井の GC が「上限/32 の 1/4」未満しか回収しなかったら、次の予算を半分に詰めない（`quickjs.c` の `g_gc_cap_dry`）。上限が断ったターンの後にも 1 回 GC する（`app_session.c`）。設計は [guest-memory-design.md](guest-memory-design.md) の G3。

- r5sim（STRESS LV3、400 フレーム）: GC 105 → 25 回、GC のサイクル 3.58 M → 0.52 M、ターンあたり 174,814 → 163,330 命令。上限が断ったターン 14 → 14、OOM のときの床 41.2〜43.3 KB。host のコーパス 88 件すべて通過。
- 実機（STRESS LV3、計測ビルド、約 10 秒の窓、`GC_STATS`）: GC **約 10 → 3.3 回/秒**、GC の時間 **約 16.6 → 4.2 ms/秒**、OOM 約 1.3 → 1.2 回/秒（実測）。GC 1 回は 0.7〜1.8 ms のまま。
- 1 秒に 5〜6 回の窓が残る。OOM の後の GC と、回収があった後の天井の GC が重なっている。
- ほとんど回収しない GC はまだ続くことがある（1 秒に 6 回で計 3,672 B、最後の 1 回は `121996->121996`）。空振りの判定は 1 回ごとなので、上限の直下で回収が少しだけある GC が続くと、半分に詰める規則に戻る。次に詰めるならここ。
