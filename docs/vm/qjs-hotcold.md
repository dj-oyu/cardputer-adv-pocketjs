## 0. 結論

- **実機（§7.1、TURNPERF、同じ固定の種）: 退役命令は同じまま、1 ターンの命令キャッシュ待ち（`I_STALL`）が STRESS −18%、DERBY のレース −20〜−23%。JS のターンのサイクルは STRESS −7.3%（1.320 → 1.223 M）、DERBY のレース −8.8%（1.472 → 1.347 M、6.29 → 5.77 ms）。熱い領域を 20 B ずらした像（B''）も B と 0.1% 以内で同じ**なので、配置の偶然ではない。これを受けて既定を ON にした。

- **やり方: QuickJS のソースは 1 行も変えない。** コンパイラの前に立つスクリプト（`tools/qjs_hotcold/hc_cc.py`）が `quickjs.c` だけを一度アセンブリに落とし、プロファイル（どの基本ブロックをターンが走るか）に従ってブロックを並べ替えてからアセンブルする。熱いブロックは**全関数ぶんを 1 か所に背中合わせで**置き、走らないブロックはその後ろへ出す。変わるのはブロックの順番と、動かしたブロックをつなぐ分岐・ジャンプだけ（§3）。
- **手で `likely`/`cold`/外出しを書く案は採らなかった。** この GCC は `-Os` では分岐の予測を配置に使わない（§2.2、実測（コンパイラ））。効かせるには関数ごとに速度優先（`-O2`）にするしかなく、コードが 28〜67% 膨らむ（§2.3）。外出しは 1 つ 20〜30 B の呼び出しが熱い行に残り、200 関数に手で入れる上流差分になる（§8）。

- **正しさ**: 並べ替えのたびに、出力を元のアセンブリと突き合わせる検査がビルドの中で走る（全ブロックが同じ命令列・同じ行き先か）。さらに、約 900 関数の全ブロックに乱数で階級を振った像を r5sim で走らせ、STRESS・DERBY のデモレース全体・LCD CATCH が通常の像と同じ結果になることを確かめた（§6）。**ホストの試験（x86）はこの変換を通らない**ので、根拠は Xtensa の像を QEMU で走らせた結果と、実機（§7.1: DERBY のデモレースの着順・タイムが A と同じ）。
- **見込みの大きさで実機に出た。** 模型の見込みは JS のターンで数 %〜10%（推定、§5.4）、実機は −7〜−9%。ビルド間の配置の揺れ（最大 15%、CLAUDE.md）より小さいので、`turn_ms` だけでは判定せず、退役命令が同じで `I_STALL` が減ったこと、熱い領域をずらした B'' も同じだったことで判定した（§7）。PGO は模型 −4.9% が実機で見えなかった（[qjs-pgo.md](qjs-pgo.md) §5）。
- **道具の誤りを 1 つ直した**: `icache.py extract` は `-icount` の記録で、熱いブロックの後半を落とすことがあった。これまでの「行の使用率」は低く出ていた（同じ記録で 59.8% → 66.2%、§1.2）。触る行の数はほぼ変わらない。

### 1.2 `icache.py extract` の誤り（直した）

`-icount` の QEMU は、命令数の予算がブロックの途中で尽きると、そのブロックを「尽きた命令まで」の短い形でもう一度翻訳し、`in_asm` に同じ先頭番地で短い一覧を出す。`extract` は先頭番地ごとに**最後の一覧**を使っていたので、熱いブロックほど後半を失った。同じ STRESS の記録で:

| | 直す前 | 直した後 |
| --- | ---: | ---: |
| flash の実行命令/ターン | 483,484 | 755,411 |
| 実行したバイト/ターン | 24,140 B | 26,952 B |
| 行の使用率 | 59.8% | 66.2% |
| 触る行 | 1,266（39.6 KiB） | 1,275（39.9 KiB） |

触る行とミスはほとんど動かない（切れた後半は次のブロックとして別に記録されるため）。**[turn-icache.md](turn-icache.md) §3 の使用率 57.5% と [qjs-pgo.md](qjs-pgo.md) §3 の実行命令数は `-icount` の記録で、同じ理由で低く出ている可能性が高い**（当時の記録は取り直していない）。直し方は、先頭番地ごとに一番長い一覧を残す。プロファイルを取る `hc_profile.py` も同じ規則。

## 2. 調べたこと

### 2.1 無駄はどこにあるか（模型、`tools/r5sim/coldmap.py`）

STRESS と DERBY の記録を合わせ、`quickjs.c` の関数ごとに「どちらのターンも走らないのに、触る行に乗っているバイト」を出した。

- 走った関数は 208、無駄は合計 9.8 KiB。`JS_CallInternal` が 2.3 KiB、残りは 1 関数 50〜400 B の長い裾（`JS_SetPropertyInternal2` 387、`JS_DefineProperty` 304、`JS_SetPropertyValue` 242、`JS_GetPropertyInternal` 186 …）。
- `JS_CallInternal` の無駄は切れ目の数で決まる。8 B 以上の走らない区間が 81 か所あり、うち 30 か所は 100 B 以上（走らない命令ハンドラ。最大 1,100 B 台）で熱いハンドラの間に挟まる。区間が大きくても、捨てるのは切れ目ごとに行の端の約 30 B。残りはハンドラの中の 9〜60 B の遅い経路。
- **helper は 1 関数あたりの熱い部分が小さい**（STRESS で 4.6 KiB を約 150 関数で分ける。平均 30 B 前後）。関数の中で熱い部分を前に寄せるだけでは、関数の境目ごとに行の端が余る。**熱い部分を関数をまたいで続けて置く**必要がある。これが設計（§3）を決めた。

### 2.2 この GCC は `-Os` で配置を変えない（実測（コンパイラ））

`xtensa-esp32s3-elf-gcc` esp-15.2.0 に小さな関数を通し、呼び出しの順で配置を読んだ。

| 指定 | 結果 |
| --- | --- |
| `-freorder-blocks` | Xtensa の GCC は既定で**切っている**（`-Q --help=optimizers` が `-O2` でも `[disabled]`）。ただし **ESP-IDF が自分で付けている**（`CMakeLists.txt`）ので、ファームではすでに有効 |
| `-Os -freorder-blocks` ＋ `__builtin_expect` ＋ 呼び先に `__attribute__((cold))` | **ソースの順のまま。** `unlikely` を付けた大きな塊も、cold な関数を呼ぶ塊も、熱い経路の途中に残る。`-freorder-blocks-algorithm=stc` を足しても同じ |
| `-O2 -freorder-blocks` ＋ 同じ注釈 | 熱い経路が先頭に並び、cold の塊と `unlikely` の塊が関数の末尾へ行く（大きさ +5%） |
| `-freorder-blocks-and-partition` | back end が `-freorder-blocks` に読み替える。別の節には分かれない |
| ラベルの `__attribute__((cold))`（computed goto の入口） | `-Os` では動かない。`-O2` では末尾へ行く |

理由: GCC の並べ替えは「速度優先の関数」でだけ熱さを使い、`-Os` の関数は全部「大きさ優先」。**`-Os` のままでは `likely`/`unlikely`/`cold` をいくら書いても配置は変わらない。** PGO（[qjs-pgo.md](qjs-pgo.md)）が少しだけ効いたのは、プロファイルが熱い関数を速度優先に切り替えたから。

ついでに分かったこと: `quickjs.c` 全体で `jx` は 1 個。`-Os` では命令の振り分け（computed goto）が複製されず、各ハンドラは共通の振り分けへ `j` で飛ぶ（今回は触っていない）。

## 3. 設計: アセンブリの上で並べ替える

GCC が配置を決められないなら、GCC の出力を並べ替える。`-Os` の GCC はブロックをソースの順に置くだけなので、後から動かしても何とも競合しない。

### 3.1 流れ

| 段 | 何をするか | 場所 |
| --- | --- | --- |
| 仲立ち | CMake の `C_COMPILER_LAUNCHER` で quickjs-ng 部品のコンパイラの前に立つ。`quickjs.c` 以外は素通し | `components/quickjs-ng/CMakeLists.txt`、`tools/qjs_hotcold/hc_cc.py` |
| 分解 | `-S` でアセンブリにし、関数を基本ブロックに切る（コードのラベルと、分岐・ジャンプ・戻りの直後で切る） | `tools/qjs_hotcold/hc_asm.py` |
| 学習（`gen`） | 各ブロックの先頭にローカルシンボルを足した像を r5sim で走らせ、ブロックごとに「何ターンで走ったか」を数える | `hc_profile.py`、`train.sh` |
| 配置（`use`） | プロファイルの階級の順にブロックを書き出す | `hc_asm.py` |
| 検査（`verify`） | 書き出したものを元と突き合わせる。合わなければビルドを止める | `hc_asm.py` |
| アセンブル | 同じコンパイラのドライバに `.s` を渡す（アセンブラへの指定がコンパイル時と同じになる） | `hc_cc.py` |

中間ファイルは目的ファイルの隣に残る（`quickjs.c.obj.hc0.s` が GCC の出力、`.hc.s` がアセンブルしたもの）。

### 3.2 階級と置き場所

ブロックの階級はプロファイルが決める。

| 階級 | 条件 |
| --- | --- |
| hot | どれかの負荷で、連続 60 ターンの区間のうち 50% 以上のターンで走った |
| warm | どこかのターンか、最初のターンより前（評価・起動）で走った |
| cold | 学習で一度も走らなかった |

- **hot なブロックを 1 つでも持つ関数だけ**を動かす（188 関数）。それらを 1 つの節 `.text.qjshc0` に移し、**全関数の hot → 全関数の warm → 全関数の cold** の順に書く。hot の領域では関数の境目に冷たいコードが挟まらない。
- **hot は、どの負荷が使うかの組で分ける**（3 負荷なら 7 組）。全負荷が使うブロックが先頭、次に 2 負荷、最後に 1 負荷だけのもの。同じ関数でも、STRESS だけが使うブロックと DERBY だけが使うブロックは別の場所に集まる。1 つの hot にまとめた場合と比べて、インタプリタの取り分は STRESS 14.69 → 13.20 KiB、DERBY 14.57 → 13.70 KiB（模型）。代わりに成立するジャンプが少し増える（DERBY で +3.1% → +5.9%、§5.3）。`hc_profile.py merge --single` で 1 つにまとめられる。
- hot を持たない関数（評価でしか走らないものを含む）は GCC の出力のまま、元の節に残す。
- 元の関数のシンボルは入口のブロックに付いたまま。入口と別の場所へ行った部分には `関数名.hot1`〜`.hot6`・`.warm`・`.cold` のローカルシンボルと大きさを付ける（`nm` で読む道具がバイトを取り違えない）。

### 3.3 つなぎ直し

ブロック k が次のブロック k+1 へ落ちる形で終わっていて、k+1 が別の階級へ行くとき:

- k の最後が条件分岐で、その行き先が「新しい配置で k の直後に来るブロック」のとき（冷たい塊を飛び越える形）は、**条件を反転して** k+1 へ飛ばす。熱い経路は飛ばずに落ちるようになる（成立分岐が 1 回減る）。
- それ以外は k の後ろに `j k+1` を足す。

届かなくなった条件分岐は、アセンブラが自分で「反転した分岐＋`j`」に広げる（Xtensa の gas の既定の動作）。熱い側から冷たい側への分岐が遠くなると、熱い経路で成立分岐が 1 回増える。§5.3 の「成立した分岐・ジャンプ」がその合計。

動かさないもの: ゼロオーバーヘッドループ（`loop` から `_LEND` のラベルまで。全体を 1 ブロックとして扱う）、ブロックの中に挟まるジャンプ表などのデータ（そのブロックと一緒に動き、戻り先の節を書き換える）。

### 3.4 1 つの節にする理由（リテラルとジャンプの届く範囲）

- Xtensa の `j` は ±131 KiB、条件分岐は ±128 B〜±2 KiB。別の節に分けると、節の間の距離はリンクするまで分からず、リンカは `j` も条件分岐も広げない。**同じ節なら全部アセンブラが解決する**ので、リンカ断片も要らない。GCC が Xtensa で分割を切っているのと同じ壁（リテラルと分岐の届く範囲）を、節を分けないことで避けた。
- 節の大きさが `j` の届く範囲を超えないよう、見積もり（1 命令 3 B）で 110 KiB を超える前に次の節（`.text.qjshc1`）を始める。今のプロファイルでは 1 つで 60,152 B（実測（静的））。
- リテラルは `.literal.qjshc0` にまとまり、節の直前に置かれる（`l32r` の届く範囲 256 KiB の内側）。届かなければリンクが止まる（黙っては壊れない）。
- アセンブラの subsection は使えなかった: text の節に 2 つめの subsection があると、この gas は longcall のリテラルで内部エラーになる（`subseg_set_rest`）。階級ごとのバッファを自分で持ち、順に書き出している。

### 3.5 プロファイルが古いとき

プロファイルは関数ごとに「命令列のハッシュ（ラベルの番号を振り直したもの）」と、ブロックごとの階級を持つ（`tools/qjs_hotcold/profile.json`、15.8 KB、git 管理）。ビルド時にハッシュが合わない関数は**動かさない**。`hc_cc.py` は「何関数を並べ替え、何関数が合わなかったか」を毎回ビルドのログに出し、半分以上が合わなければ警告する。古いプロファイルで起きるのは「効かなくなる」であって「壊れる」ではない。

ハッシュは命令の文字列だけから作るので、木の場所（絶対パス）には依らない（PGO の `.gcda` が Windows のビルドで当たらなかった問題、[qjs-pgo.md](qjs-pgo.md) §1.1、は起きない作り。Windows の broker のビルドでは未確認）。

### 3.6 IRAM の helper

`main/vm/helper_iram8.lf` は関数を `.text.<名前>` の節の名前で IRAM へ写す。関数を `.text.qjshc0` へ移すと断片が黙って外れるので、`hc_cc.py` は断片に名前のある関数を動かさない（`--keep-out`）。学習も実機と同じ IRAM 化で走らせるので、IRAM の関数は flash の記録に現れず、もともと候補にならない（今のプロファイルとの重なりは 0）。

IRAM の関数の中を hot/cold に分けて「IRAM には熱いブロックだけ置く」ことは、IRAM と flash の間を `j` が越えられないので、この方式ではできない。

### 3.7 デバッグ情報

行の表（`.loc`）とシンボルは正しい（アドレス → 行・関数名は引ける）。動かした関数の中の、スコープや変数の位置の範囲（ラベルの差で書かれる）は正しくない。`quickjs.c` を `-gno-variable-location-views` で組む（view の番号はアドレス順に数えるので、動かすとアセンブラが止まる）。`-fno-var-tracking` は使わない: この GCC では生成コードが変わる（8 関数、実測（コンパイラ））。

## 4. プロファイルの学習


r5sim を `-DPOCKET_QJS_HOTCOLD=gen` で 3 つの負荷（`shiki`＝STRESS 120 ターン、`derby`＝デモレース全体 1,773 ターン、`hud`＝LCD CATCH 240 ターン）について組み、QEMU の記録を FIFO で `hc_profile.py run` に流す。`gen` はブロックの先頭にシンボルを足すだけで、命令は変わらない（`selftest.py` が全節の逆アセンブルを突き合わせる。アセンブラが自分で決める「狭い命令か広い命令か」と詰め物だけは、ラベルの有無で 2 関数が変わる）。

## 6. 正しさの確かめ方

| 層 | 内容 | 結果 |
| --- | --- | --- |
| 構造の検査（毎ビルド） | `hc_asm.verify`: 動かした関数ごとに、全ブロックが 1 回ずつ出ていること、命令列が同じこと（許すのは末尾の `j` の追加と、条件分岐の反転だけ）、落ちる先が元と同じブロックであること、反転した分岐の落ちる先が元の行き先であること、ラベルが元のブロックに残っていること。動かしていない行は 1 行も違わないこと | 188 関数、毎回通る。合わなければビルドが止まる |
| 道具の自己検査 | `tools/qjs_hotcold/selftest.py <build dir>`: `gen` が命令を変えないこと。乱数の階級（5 階級、約 950 関数）で `use`＋`verify`＋アセンブルが通ること | 通る |
| 動かして確かめる | `tools/qjs_hotcold/torture.sh`: 乱数の階級を振った `quickjs.c`（875〜904 関数、熱いブロックもばらばらに動く）を r5sim に入れ、STRESS・DERBY のデモレース全体（1,773 ターン）・LCD CATCH を走らせる。フレーム数・失敗 0・1 ターンの確保数・使用中のヒープ・DERBY のイベントの行（ターン番号込み）が通常の像と一致すること | 種 2 つ × 3 負荷で一致 |
| 本番のプロファイル | STRESS・DERBY・LCD CATCH が ON の像で `oom=0 fail=0 bad_present=0`、確保数とヒープが OFF と同じ | 一致 |
| ファーム | ON でビルドが通り、`check_flash.py` が通ること | 通る（焼いていない） |

乱数の試験が要る理由: 本番のプロファイルが動かすのは「走らないブロック」なので、反転した分岐や足した `j` は、試験が通らない経路にしか現れない。乱数の階級なら、走る経路の上でつなぎ直しが働く。

**確かめていないもの**: 実機。ホストの試験（`tools/kasane_contract/run.sh`、STRESS のホスト試験、`run_derby.py`）は x86 のコードを走らせるので、このフラグの影響を受けない（フラグを立ててもホストのビルドは同じ）。QuickJS のコーパス・Test262 の部分集合（`tools/vmtest/`）を Xtensa の ON の像で走らせることはしていない。r5sim の 3 負荷が通らない経路（正規表現、JSON、例外の巻き戻しなど）の、つなぎ直した後のコードは、構造の検査だけが根拠。

## 7. 実機の A/B 手順

実行時には切り替えられない（配置そのものの変更）。**ビルド 2 つの比較になる。**

1. **計数を入れる（A・B 共通の `measure:` コミット）**: `main/app_session.c` の 1 行目に `#define CONFIG_POCKET_VM_TURNPERF 1` を足す（[turn-cpi.md](turn-cpi.md) §1 の計装。Kconfig を通さずに有効にする。30 ターンごとに `TURNPERF <事象> cy= ev= n= us=` を出す）。DERBY は種を固定する 1 行（[p1-iram-placement.md](p1-iram-placement.md) §9 の手順）も同じコミットに入れる。
2. **A**: 1 だけの像。
3. **B**: `components/quickjs-ng/CMakeLists.txt` の `set(_qjs_hc "")` を `set(_qjs_hc "use")` に変える（1 行）。ビルドのログに `hc_cc: quickjs.c: 188 functions laid out hot/cold (0 of the profile's did not match ...)` が出ることを確かめる。**0 でなければ、その木の `quickjs.c` の目的コードが学習時と違う**（Windows のコンパイラの出力が違う場合を含む）ので、測る前に知らせてほしい。
4. **B'・B''**: 同じファイルの `set(_qjs_hc_pad 0)` を `12`、`20` にした像。熱い領域を 32 B の行に対してずらす（配置の当たり外れを分けるため）。
5. 焼く順は A → B → A → B' → B''。各脚で STRESS 60 秒（`tools/stress_app.py`）と DERBY のデモレース。焼くのはビルド済みのイメージを直接（[turn-icache.md](turn-icache.md) §1.3.4 の注意）。
6. **読む値**（主 → 従）:
   - `TURNPERF istall` の `ev/n`（1 ターンの `I_STALL_BUSY`）。模型どおりなら STRESS で −19〜−37%、DERBY で −15〜−19%（cold と warm のミスの減り方の幅。待ちがミスの回数に比例すると仮定した推定）。
   - `TURNPERF insn` の `ev/n`（退役命令）。A と B でほぼ同じはず（模型で +0.01〜+0.15%）。大きく違えば別の原因。
   - `cy/n`（1 ターンのサイクル）と、`KASANE_PAINT` の `turn_ms`、DERBY のレース区間の turn ms。
7. **判定**: `turn_ms` の差が 15% 未満なら、1 組の A/B だけでは配置の揺れと区別できない（CLAUDE.md）。**B・B'・B'' の 3 つとも `istall` が 2 つの A より低く、退役命令が同じ**なら、配置の偶然ではなく行が詰まった効果と読める。3 つがばらつくなら、効果は揺れの大きさ以下。見込み（§5.4）は turn で数 %〜10% なので、`turn_ms` だけでは見えない可能性が高い。
8. 終わったら `measure:` のコミットを revert する。空きヒープは変わらないはず（`memlog.py --port --check` で確かめる。DIRAM の差は 0）。

## 8. 採らなかった案と理由

| 案 | 理由 |
| --- | --- |
| `likely`/`unlikely`、エラー関数への `cold` | `-Os` では配置が変わらない（§2.2、実測（コンパイラ））。書いても何も起きない |
| `quickjs.c`（または熱い関数だけ）を `-O2`/`-O1` にして GCC に並べ替えさせる | コードが 28〜67% 増える（§2.3）。熱いハンドラが大きくなり、触る行が増える方向 |
| 冷たい経路を `noinline`,`cold` の関数に手で出す | 出した跡に 20〜30 B の呼び出しが残り、切れ目は消えない（切れ目 1 つで捨てるのは約 30 B）。関数の境目の余りも残る。効かせるには約 200 関数に手を入れる上流差分になり、rebase のたびに保守が要る。Kconfig で OFF の像を変えないには、元の形と分けた形を両方ソースに持つことになる |
| 稀な命令ハンドラを computed goto の外の関数へ（共通の入口 1 つ） | ハンドラの本文を別の関数へ移すので、同じく上流差分。ローカル変数・`goto exception`・generator の再入を持つ 3,500 行の関数で、試作の最初の一歩としては危険が大きい。アセンブリの並べ替えは同じ効果（走らないハンドラが熱い領域から出る）を、ソースを変えずに得る |
| 関数単位の並べ替え（`gen_hot_lf.py`） | 実リンクで cold −0.6%（[turn-icache.md](turn-icache.md) §1.3.1）。関数の中の冷たいバイトが一緒に付いてくる |
| PGO（`-fprofile-use`） | Xtensa では分割できず、並べ替えは速度優先に切り替わった関数だけ。模型 −4.9%、実機 0（[qjs-pgo.md](qjs-pgo.md)） |
| 冷たい部分を別の節（`.text.unlikely.*`）へ | 節の間の `j`・条件分岐はリンカが広げない。距離が ±131 KiB を超えるとリンクできない（§3.4） |
| アセンブラの `.subsection` | この gas が内部エラーで止まる（§3.4） |
| 学習・配置を 1 つの hot にまとめる | 負荷ごとの組で分けたほうが、インタプリタの取り分が 1.0〜1.5 KiB 小さい（§3.2）。`--single` で残してある |

## 9. リスクと限界

- **実機で未確認**（正しさも速さも）。模型は描画を見ない。実機ではターンの間に描画がキャッシュを入れ替える。
- **学習に無い経路は遅くなりうる。** cold に分類されたブロックを通る経路は、ジャンプが増え、cold の領域（約 27 KB）に散る。学習の 3 負荷に無いアプリ（BIG WAVE、MEGADEMO、エディタの JS など）での効きは測っていない（§5.2 の 2 例は悪化なし）。評価（起動時の解析）は warm に入れてあるが、解析器の関数の多くは hot を持たないので動かしていない。
- **成立する分岐が増える**（STRESS +1.2%、DERBY +5.9%、模型）。ミスの減少で取り返す前提（§5.4）。flash の待ちが小さい条件（IRAM を増やした、flash が速い）では差し引きが逆になりうる。
- **プロファイルの保守。** `quickjs.c` を変えるたびに、変えた関数は照合から外れて元の配置に戻る（ビルドのログに数が出る）。効果を保つには学習し直す（約 20 分、QEMU と Node が要る）。
- **ビルドの経路が増える。** `quickjs.c` だけ「C → アセンブリ → 変換 → アセンブル」になる。コンパイル時に Python が要る（ESP-IDF のもの）。ccache はこの部品では使われない。
- **デバッグ情報**: 動かした関数の中の変数・スコープの範囲は正しくない（§3.7）。パニックのバックトレース（番地 → 行）は引ける。冷たい部分の番地は `関数名.cold` と出る。
- **`JS_CallInternal` の大きさを `nm` で読む道具**は、入口の部分だけを見る（`tools/r5sim/case_sizes.py` など）。`turnset.py` は `JS_CallInternal.*` を core に数えるが、helper の `.hotN` は名前の規則で部品が変わることがある（合計は変わらない）。
- **`gen` の像は命令が同じだが、アセンブラの詰め物が 2 関数で違う**（§4）。階級はシンボルの番地で読むので影響しない。
- **PGO とは併用しない**（Kconfig で排他）。PGO の像は目的コードが違うので、プロファイルが当たらない。

## 10. 上流（quickjs-ng）との対応

**QuickJS のソースへの差分は無い。** rebase で持ち越すものは `components/quickjs-ng/CMakeLists.txt` の 1 ブロック（仲立ちの設定）だけ。上流の更新を取り込んだ後は:

1. フラグ OFF で普通にビルドできることを確かめる（この変更は関係しない）。
2. `tools/qjs_hotcold/train.sh` で学習し直し、`profile.json` をコミットする。
3. `tools/qjs_hotcold/selftest.py <build dir>` と `tools/qjs_hotcold/torture.sh` を通す。GCC の出すアセンブリの形（ラベルの名前、`loop`、節の切り替え）が変わっていれば、ここで止まる。

`hc_asm.py` が GCC の出力について仮定していること: コードのラベルは `.L<数字>`、関数は `.section .text.<名前>` で始まり `.size <名前>, .-<名前>` で終わる、ループの終わりは `.L<数字>_LEND`、関数の中の他の節（ジャンプ表）は `.section .text.<名前>` で戻る。コンパイラを上げたら `selftest.py` で確かめる。

## 11. 再現

```bash
# 学習（profile.json を書く）
tools/qjs_hotcold/train.sh
# ファーム（既定で ON。OFF は menuconfig で POCKET_VM_QJS_HOTCOLD を外すか -DPOCKET_QJS_HOTCOLD=off）
idf.py -B build_api build
# r5sim（模型）。OFF は -DPOCKET_QJS_HOTCOLD を外す
tools/r5sim/fast.sh <dir> -DR5SIM_DEVICE=1 -DR5SIM_APP=shiki -DPOCKET_QJS_HOTCOLD=use
#   記録 → turns.pkl.gz（turn-icache.md §2.5。-icount shift=2,sleep=off、flash だけ）
python tools/r5sim/turnset.py <dir>/turns.pkl.gz <dir>/r5sim.elf <dir>/r5sim.map --nm ... --addr2line ...
python tools/r5sim/lineuse.py <dir>/turns.pkl.gz <dir>/r5sim.elf <dir>/r5sim.map --nm ... --objdump ...
python tools/r5sim/jumps.py   <dir>/turns.pkl.gz <dir>/r5sim.elf --objdump ...     # 成立した分岐
python tools/r5sim/coldmap.py <dirA>,<dirB> --nm ... --objdump ... --addr2line ...  # 無駄の場所（§2.1）
# 検査
python tools/qjs_hotcold/selftest.py <build dir>
tools/qjs_hotcold/torture.sh
```

別のプロファイルで組む: `-DPOCKET_QJS_HOTCOLD_PROFILE=<絶対パス>`。学習から負荷を抜く: `WORKLOADS="shiki hud" tools/qjs_hotcold/train.sh`。
