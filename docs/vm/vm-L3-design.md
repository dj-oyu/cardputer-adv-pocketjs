# L3 設計: 相対参照と移動可能スタック

仕様は [quickjs-freertos-vm-spec.md](quickjs-freertos-vm-spec.md) §8。入口の台帳は
[vm-ledger/09-relocation-entries.md](vm-ledger/09-relocation-entries.md)。決定表は §9（D44 から。
D1〜D43 は L2 が使い切っている）。開発は `vm/l3a-refs`、基点は `953c627`（tag `vm-L2`）。

| 段階 | 変更 | 状態 |
| --- | --- | --- |
| L3a | 明示移動 API、差分表による型付き補正、旧領域の毒化、世代 | **実装・検証済み**（ホスト全関所、実機で移動 235 µs）。既定 n |
| L3b | 移動の自動化（誰がいつ動かすと決めるか） | 閾値つきの寄せ方をホストで測り、**動かさないのが最良**（§10） |
| L4a | 駐機中に鎖を1ブロックへ寄せる | 実装・検証済み、**不採用**（§10、D57） |
| D6 | セグメントを専用の領域から取る | ホストで模擬、**不採用**（§11、D59） |

**L3a の完成は「動かせること」であって「動かすこと」ではない。** 動かす理由（断片化の回収）は
L4 の担当で、L3a が出荷ビルドの挙動を変えることは無い（仕様 §12 の既定挙動維持）。

---

## 1. この段が解く問題と、解かない問題

L2a はフレームを C スタックから **動かないセグメント** へ移した。動かないので、
`JSVarRef.pvalue` のような生ポインタがそのまま通用する。L3 はそのセグメントを別の番地へ
写せるようにする。

**解く問題**: セグメント payload を新しい番地へ写し、そこを指していた 14 種の入口
（台帳 §8）をすべて正しい新番地へ向け直し、再開したら中断前と同じ実行が続く。

**解かない問題**:

- *いつ* 動かすか。L3a の移動は外から明示的に呼ばれたときだけ起きる。
- 断片化がどれだけ回収できるか。これは L4 の主張で、L3a は測らない。
- JS オブジェクト本体の移動。仕様 §8 が明示的に対象外としている。

### 1.1 着手の条件 — まだ開いていない関所

仕様 §12.2-3 は「estalloc 等を比較対象に、移動しないセグメントの分割・空き結合・再利用を先に
測る。**それでメモリが足りるなら L3/L4 を実装しない**」と書いている。この判定は
**まだ実機で済んでいない**: ホストの4方式比較は台帳 07 §7 にあるが、その文書自身が
「実機の断片化や最適セグメントサイズの検証を代替しない」と断っている。

したがって L3a は**関所が開く前に始まっている**。この文書はその事実を隠さない。L3a が
関所より先に進んでよい理由は2つで、どちらも「実装を進める」理由であって「関所を飛ばす」
理由ではない:

1. **台帳（§0 の 14 種）は関所の結果に関わらず要る。** 関所が「L3 不要」と答えても、
   入口の一覧は L4 のコンパクション設計がそのまま使う。
2. **移動できる VM は、断片化を測る道具でもある。** 「動かしたらどれだけ詰まるか」は
   動かせるようになって初めて実測できる。関所を「推定で閉じる」より確実である。

**L3a の成果を `vm/main` へ戻す条件に、関所の実機計測を入れる**（§8 の関所表 G12）。

## 2. 中心の決定 — 動かすのは中断中だけ

**D45: 移動は `rt->vm_susp.top != NULL`（L2c の駐機状態）の間にのみ許す。走っている VM は
動かさない。**

台帳 §7 の通り、`JS_CallInternal` が走っている間はブロック内を指す値が C の自動変数と
レジスタに散っている。これを補正する方法は仕様 §8 が禁じた「C スタックの任意の数値を
ポインタと推測する」しか無い。中断中はその活性が呼び出し元へ戻り切っているので、
**ブロックを指す値は台帳の 14 種だけになる**。

この決定の効果は大きい:

- **pin が要らない。** 仕様 §8 の「外部へ生ポインタを渡す区間は pin を取得する」は、
  ネイティブ呼び出し中に中断点が存在しないことで構造的に満たされる。pin は API として
  置くが、L3a では**常に 0 であることを表明する assert** として働く（D51）。
- **移動の停止時間は中断の停止時間に含まれる。** 新しい「止まる理由」を作らない。
- **L2c が無ければ L3 は成立しない**という依存が明示される。`CONFIG_POCKET_VM_RELOC` は
  `CONFIG_POCKET_VM_YIELD` に依存する（D52）。

### 2.1 中断していても、動かせないことがある

**D55: 移動は `rt->current_stack_frame == NULL`（駐機中の鎖が生きているフレームの全部）の
ときに限る。床の下に外側の JS 活性が残っていたら移動を拒む。**

D45 だけでは足りない。中断した鎖の**下**にもフレームが在りうる: 外側の JS がネイティブ関数を
呼び、そのネイティブが JS を呼んで、内側が中断した場合である。このとき外側の
`JS_CallInternal` の C 活性は**まだ走っている**（C スタック上で内側の戻りを待っている）ので、
その C ローカルはブロックを指したままで、D45 が避けたかった状況がそのまま残っている。

しかもセグメントはバンプアロケータなので、**床のフレームと外側のフレームが同じセグメントに
同居しうる**。「床より上のセグメントだけ動かす」では切れない。

判定は 1 行で済む。L2c は中断時に `rt->current_stack_frame = floor->prev_frame` と書く
（`quickjs.c:22305`）ので、**外側が無ければ中断中の `current_stack_frame` は `NULL`**
になる（ホストのターンから入った床は `prev_frame == NULL`、`quickjs.c:19372`）。

代償は小さい: ホストのターンから始まる通常の実行はこの条件を満たす。満たさないのは
「JS → ネイティブ → JS」の入れ子が中断した場合だけで、**その形は次の中断まで動かせない**。
L2c の `JS_SF_MAY_YIELD` が同じ入れ子を別の理由で扱っているので、条件を緩める余地は
L3b で改めて見る。

代償: **動かせる瞬間が中断点にしか無い。** 中断しないアプリのセグメントは永久に動かない。
L4 が「断片化したから今すぐ詰めたい」と言ったとき、L3a の答えは「次の中断まで待つ」である。
これで足りるかは L4 が決めることで、L3a はこの制限を**明示的な設計の選択**として記録する。

## 3. 移動の単位と、差分の表し方

**D44: 動かすのは `js_malloc_rt` ブロック全体（`JSVMSeg` ヘッダ + payload）。**

ヘッダは payload と同じブロックの先頭に在る（`quickjs-vmstack.h:394-399`）。ヘッダを
指しているのは `JSVMStack.cur` / `.cache` と `JSVMSeg.prev` だけで、すべて `JSVMStack` の
内部にある（台帳 E4/E5）。分けて動かす利益が無く、分けると `js_free_rt` の呼び先が
2つになる。

**D46: 差分は根元の 1 個の加算値ではなく、移動したセグメントごとの表で表す。**

仕様 §8 の「断片ごとに異なる移動量を、根元の一つの加算値で表現しない」の実装形。
1回の移動が作る表は

```c
typedef struct JSVMReloc {
    uint8_t *old_base;     // 旧 payload の先頭
    uint8_t *old_end;      // 旧 payload の終端
    ptrdiff_t delta;       // new_base - old_base
    JSVMSeg *old_seg;      // 段5 で返す旧ブロック
} JSVMReloc;
```

の配列で、補正は「ポインタ `p` が `[old_base, old_end)` に入る行を引き、`p + delta` にする」。
行数は生きているセグメント数で、`JS_VM_SEG_MAX` が小さく保つので（512 B 基点・4096 B 上限で、
実機の 20 KiB 予算でも数十本、`quickjs-vmstack.h:437-438` の同じ理由）、線形探索で足りる。

**表の引き方が「入っているか」の判定を兼ねるのが要点**で、これが仕様 §8 の禁じた
「ポインタと推測する」との違いを作る: 補正する場所は台帳が型で列挙したフィールドだけ、
その値がどのセグメントに属するかだけを表が答える。**任意の数値を引かない。** 引くのは
`sf->prev_frame` のような、型が `JSStackFrame *` だと宣言しているものだけである。

### 3.1 全部動かすとは限らない

表は「今回動かしたセグメント」だけを持つ。動かさなかったセグメントを指すポインタは
表に当たらず、そのまま残る。**当たらないことが正常**なので、補正は「見つからなければ
何もしない」で正しい。これはセグメント単位の部分移動（L4 が使う形）を最初から許す。

ただし **`arg_buf` の例外**（台帳 §0）に注意が要る: `arg_allocated_size == 0` のとき
`sf->arg_buf` は呼び出し元のブロック内を指す。呼び出し元が別のセグメントに在り、そちらだけを
動かした場合、`arg_buf` は「自分のセグメントは動いていないのに補正が要る」。**表を引くのは
フィールドの値であって、フレームの所属ではない** — この設計は最初からそうなっている。

## 4. 手順 — 失敗しても旧領域を壊さない

仕様 §8 は「失敗時の旧領域保持を VM 側で保証する」と書いている。確保と書き換えを分ける:

```text
  段1  新しいブロックを必要な数だけ確保する（旧は触らない）
       1本でも失敗したら、取った新ブロックを全部返して -1。VM は無傷。
  段2  payload を写す（旧も生きている）
  段3  差分表を作る
  段4  型付き補正の一巡（台帳 E1〜E14）
  段5  旧 payload を毒で埋め、ASan 毒を付け、js_free_rt で返す
```

**段4 までは旧領域が読める状態で進む**ので、段1〜3 のどこで止めても巻き戻せる。段4 は
確保をしない（表は段1で一緒に取る）ので失敗しない。**段4 に入ったら最後まで行く**のが
この設計の不可分点で、そこから先に失敗要因を置かない。

**D47: 段1は 1 回の `js_malloc_rt` で表と全ブロックをまとめて取るのではなく、ブロックごとに
取る。** まとめると「移動でメモリを詰めたいのに、その瞬間に最大の連続ブロックを要求する」
という自己矛盾になる。表だけは別に 1 本取る（生きているセグメント数 × 12 B 程度）。

### 4.1 補正の一巡（段4）

台帳 §6 の `js_vm_mark_suspended` と**同じ鎖を歩き、排他のフィールドを触る**:

```text
 根     E1 rt->current_stack_frame     表を引いて補正（セグメント外なら当たらない）
        E2 rt->vm_susp.top             補正
        E3 rt->vm_susp.floor           補正
        E4 JSVMStack.cur               移動の結果として書く
        E5 JSVMStack.cache             同上（中身は空なので補正不要）

 鎖     for (sf = vm_susp.top; ; sf = sf->prev_frame) {
            sf が JS_SF_SEG なら:
                E7  arg_buf     E8 var_buf   E9 var_refs   E10 cur_sp
                E11 ((JSVMLink *)sf - 1)->caller_sp
                E13/E14 var_refs[0..var_ref_count) の開いた var_ref
            sf が非 SEG なら:
                E12 container_of(...)->flat_caller_sp
            E6  sf->prev_frame                （歩く前に退避して補正）
            sf == floor で終わり
        }
```

**`prev_frame` を補正する順序が唯一の罠**である。補正してから辿ると新番地（まだ内容が
無い可能性はないが、旧 `sf` から読んだ値）と混ざる。**旧番地の鎖を歩き切ってから書くのでは
なく、1フレームごとに「次を読む → 現在のフィールドを全部補正する」の順にする**。段2 で
payload は写し終わっているので、旧と新の両方に同じ内容がある — 歩くのは**新側**にして、
読む値は旧番地を指しているものを補正して書く。これで一巡で済む。

**D48: 歩くのは新しい payload 側。** 旧側を歩くと、段5 の毒化で「今歩いた場所」を
毒にすることになり、ASan の下で自分の足跡を踏む。

### 4.2 開いた var_ref だけを触る

台帳 §4 の通り `sf->var_refs[i]` に登録されているものが開いた var_ref の全数で、
**`is_detached` が true のものは触ってはならない**（`pvalue` が自己参照で、差分を足すと壊れる）。

**D49: 判定は `is_detached` を読む。** `pvalue == &var_ref->value` という等価な判定も
コードにある（`quickjs.c:8057`）が、こちらは「自己参照かどうか」を番地の比較で見ており、
L3 の文脈では「表を引くべきか」の判定と紛らわしい。意図を読める側を使う。

## 5. 旧領域の毒化 — 抜けを捕まえるのはここ

仕様 §8 の完了条件「移動後に旧領域を毒化し、旧ポインタへのアクセスを検出する」。
台帳 §9 が書いた通り、**14 種が網羅であることの証明はこの毒化であって、文書ではない。**

**D50: 3層で毒にする。**

| 層 | 手段 | 捕まえるもの | 効く環境 |
| --- | --- | --- | --- |
| 1 | 旧 payload を `0xD3` で埋めてから解放 | 補正漏れの読み出しが即座に異常値になる（`JSValue` のタグが不正になり、既存の assert に当たる） | 全部 |
| 2 | `__asan_poison_memory_region` を解放前に | 旧番地への touch が use-after-poison として行番号つきで出る | ホストの asan 変種 |
| 3 | 解放しないで保持する診断モード | 解放後に別の確保が同じ番地を取って「たまたま動く」のを防ぐ | ホストの診断ビルドのみ |

層3（`--reloc-keep-old`）が要るのは、層1・層2 の両方が「解放された番地」に依存していて、
tlsf がすぐ再利用すると毒が上書きされうるから。**保持は当然リークなので診断専用**で、
実機ビルドには入れない。

層1 の `0xD3` は既存の毒と衝突しない値を選ぶこと（`quickjs.c` の既存パターンを確認して
から確定する。未確定）。

## 6. 世代と、失敗の作り方

**D51: `JSVMStack.generation`（`uint32_t`）を移動のたびに 1 増やす。** L3a では VM の
内部で使わない — 相対参照をまだ導入していないので、照合する相手がいない。置く理由は
**テストが「本当に動いたか」を確かめる手段**と、L3b が使う場所を先に決めておくこと。

pin は D45 により常に 0 である。API（`js_vm_pin` / `js_vm_unpin`）は置くが、L3a での
実装は**カウンタと、移動時に 0 でなければ拒む assert** だけ。仕様 §8 の完了条件
「pin 中の移動要求が安全に失敗する」は、テストがカウンタを立てて移動を要求し、`-1` が
返ることで満たす。**pin を立てる本物の経路はまだ無い**ことを、ここに明記しておく。

失敗の3種（仕様 §8 の完了条件）と、その作り方:

| 失敗 | 返り値 | テストでの作り方 |
| --- | --- | --- |
| 中断していない | `-1` | 走っていない状態（`vm_susp.top == NULL`）で移動を要求 |
| 床の下に外側の活性（D55） | `-1` | JS → ネイティブ → JS の入れ子で中断させて要求 |
| pin 中 | `-1` | `js_vm_pin` を呼んでから要求 |
| OOM | `-1`、VM 無傷 | `--fail-alloc` で段1の n 本目を落とす |
| 世代不一致 | `-1` | 古い世代を持って移動 API を呼ぶ |

## 7. API

```c
/* quickjs.h */
typedef struct JSVMRelocStats {
    uint32_t segments;       /* 動かしたセグメント数 */
    uint32_t frames;         /* 補正したフレーム数 */
    uint32_t var_refs;       /* 補正した開いた var_ref 数 */
    uint32_t generation;     /* 移動後の世代 */
    size_t   bytes;          /* 写した payload の合計 */
} JSVMRelocStats;

/* 中断中のセグメントを新しい番地へ写す。テスト用の明示移動 API（仕様 sec.8）。
 * 0 で成功、-1 で失敗（失敗時 VM は移動前と同一）。out は NULL 可。
 * CONFIG_POCKET_VM_RELOC が無効なビルドでは常に -1。 */
JS_EXTERN int JS_VMStackRelocate(JSRuntime *rt, JSVMRelocStats *out);
```

**D52: `CONFIG_POCKET_VM_RELOC`、既定 n、`CONFIG_POCKET_VM_YIELD` に依存する。**
出荷ビルドは L3a を持たない。仕様 §12 の「新しい経路はビルド時選択で既定を従来経路に」。

`JS_VMStackTrim` と同じ置き場（`quickjs.h:541` の隣）に並べる。ホストの受け口は
`tools/vmtest/vmrun.c` に `--force-reloc`（中断のたびに移動する）として足す — L2c の
`--force-yield` と同じ形にすると、**既存のコーパス全部がそのまま移動の検査になる**。

### 8.1 実機で達成すべきこと

すべて `tools/vmtest/device_reloc.py` と既存の実機スクリプトで取る。**順番に意味がある** —
D1 が取れなければ以降はすべて無意味で、「落ちなかった」は「試されていない」と区別が
つかない。

| # | 目標 | 判定 | 根拠となる値 |
| --- | --- | --- | --- |
| **D1** | **実機で1回でも移動する** | `VM_RELOC_ARMED` が出て、`VM_RELOC` の `moves>0` | 未取得。**これが無い限り他は何も言えない** |
| **D2** | 実アプリで移動が拒否され切らない | `refused / (moves+refused)` を記録。大半が拒否なら D3 以降は「出荷アプリでは検証されていない」 | D55（床の下の外側活性）。ホストでは `bench_promise` が常に拒否 |
| **D3** | 観測できる挙動が変わらない | 契約マーカー（`APP_ID` / `LOADED` / `APP_STOPPED`）が移動あり/なしで一致 | `device_reloc.py` が自動判定 |
| **D4** | 壊れない | `Guru Meditation` / `assert failed` / `CORRUPT HEAP` が0件。`smoke_device.py --cycles 20` が通る | 毒（`0xD3`）は実機でも効くが、ASan は無い |
| **D5** | メモリ予算を割らない | `memlog.py --port --check` が通る | 移動中は新旧が同時に生きる |
| **D6** | **1回の移動の停止時間が、フレームを壊さない** | `max_us` **< 5,000 µs** を目標、**絶対上限 33,000 µs**（`VM_DISPLAY_PERIOD_MS`=33） | 33 ms を超える移動は1フレームを丸ごと落とす。250 ms（`VM_FRAME_RUNAWAY_US`）に触れたらアプリが停止させられる |
| **D7** | 移動の総コストがフレーム時間を実用外にしない | `total_us / セッション時間`。既存の最悪フレームは実測 47.4 ms（出荷5アプリ） | 参考値、合否は置かない |
| **D8** | 実機の飛地がホストと同じ傾向か | `gap_max` / `gap_segments` をホスト（深さ9で 23〜49 KB）と比較 | **仮説の検証点**。同じ深さで実機が大きければ「駐機中のネイティブ確保が飛地を増やす」が確定 |
| **D9** | 移動がヒープを悪化させない | `largest_first` / `largest_last` / `largest_min` | **観測のみ。** L3a は詰めないので、合否を置く根拠が無い |

**D6 の閾値の意味**: 移動は `guest_continue_impl()` の中、つまり**ターンの中**で起きる。
`max_us` はそのターンに丸ごと乗る。33 ms がフレーム1枚、250 ms で暴走ガードが
アプリを止める。ホストの単価（浅い鎖で 82 ns/移動）から実機を推定してはいけない —
S3 は遅く、写すバイト数も違う。**D6 は推定ではなく実測で埋める欄である。**

**この表に G12（断片化の関所）は無い。** L3a は詰めないので、`device_reloc.py` では
答えられない（results §3.1）。D8 と D9 が**その関所への入力**になるだけである。

## 10. L4a: 鎖を1ブロックに寄せる — 実装し、採らないと決めた

### 10.1 何を作ったか

`JS_VMStackCompact()`（`CONFIG_POCKET_VM_RELOC` の下、既定 n）。駐機中の鎖を、セグメントごとの
同サイズのブロックではなく**1つのブロック**へ、下のセグメントから順に生きている部分だけ写す。
fix-up は L3a と同じ関数で、変わるのは表の差分だけ（各旧セグメントが新ブロックの自分の区間を指す）。
D46 の「差分はセグメントごと」は最初からこの形を許していた。新ブロックは位置による大きさの系列に
属さない（`standard = 0`）ので、キャッシュされず、巻き戻れば解放される。

ホストの `vmrun --force-compact`、方針の実験用に `--compact-min-segs K`（K 本以上のときだけ寄せる）、
`JS_VMStackSegments()`（生きているセグメント数の問い合わせ）を足した。

### 10.2 採らない理由（実測(host)、tlsf モデル）

正しさは L3a と同じ関所で確かめた（results §13）。問題は**効き目**で、トレースを tlsf モデルの
アロケータで再生し（`tools/vmalloc/replay`、プール 163,840 B）、実行中の最大空きブロックの最小値を
比べた。深い鎖で完走する 2 ファイルで、**寄せるとどの頻度でも、動かさない場合より悪い**:

- 毎回寄せても、1回だけ寄せても（K=9）、最大空きブロックの最小値は 26 KB → 7〜9 KB に落ち、
  ピーク使用量は約 17 KB 増える。**頻度ではなく1回の移動そのものが高い。**
- 仕組み: 寄せるのは鎖が一番深いとき — まさに寄せたいとき — で、その瞬間に**生きている鎖の大きさの
  連続ブロック**（約 23 KB）を新しく要求する。旧セグメントと同時に持つのでピークが上がり、しかも
  **大きな空きを1つ使い切って、512〜4,096 B の小さな穴をオブジェクトの間に散らばらせて返す**。
  §4.1 の「隙間」は他人の確保が挟まったもので、スタックを退かしても他人は動かないので空きは繋がらない。

つまり**スタックは断片化の原因ではなく、被害者**だった。コピーで寄せても、ヒープ全体の断片化は
良くならない。仕様 §12.2-3 の「移動しないセグメントで足りるなら L3/L4 を実装しない」に対し、
ホストの答えは「**このやり方の L4 は実装しても逆効果**」である。

例外は `tco_guards` の1件で、どの方式でも 160 KiB に収まらず失敗するが、最大空きブロックの最小値は
寄せると 40 → 14,848 B に上がった。「もう入らない」状況で1つの大きな確保を通すには効く可能性があるが、
それは完走できない負荷での話である。

### 10.3 残る方向

スタックを使うなら**退避**の向きしか無い: 大きな空きを分断している生きたセグメントを見つけ、
別の場所へ動かして空き同士を合体させる。L3a の「動かせる」はそのまま使えるが、「どれを動かせば
空きが繋がるか」はアロケータ（tlsf の隣接ブロック）の情報が要り、スタック側だけでは決まらない。
**着手するかは実機の G12（実際に断片化で大きな確保が失敗しているか）を見てから決める。**

## 11. セグメント専用の領域（D6）— 試して、採らないと決めた

§10 の結論（寄せると逆効果）は「散らばってから動かす」より「最初から散らばらせない」方が筋が
良いことを示唆した。L2 の設計が未決のまま残した D6 — セグメントをオブジェクトとは別の領域から
取る — をそのまま試した。

**方法**: vmrun のトレースに、セグメントの確保の直前だけ `# seg` を書く（ホストのみ、
`vmtest_seg_alloc_hint`）。`tools/vmalloc/replay --seg-arena A` はその確保をアロケータに渡さず
A バイトの専用領域から取った扱いにし、アロケータには残りの `プール − A` を渡す。**総メモリは同じ**で、
問いは「オブジェクトの側の最大空きブロックが大きく保たれるか」。専用領域は LIFO の確保解放なので
断片化しない理想の形でモデル化した（実装すればこれより悪くしかならない）。

**結果**（results §14）: 専用領域をピークちょうど — 事前にピークを知っている、実装では不可能な
最良の場合 — にしても、オブジェクトの側の最大空きブロックの最小値は共有ヒープと**同じか 1〜2 KB
小さい**。固定の大きさ（8 / 16 / 24 KiB）を確保すると、スタックの浅いプログラム（ほとんどのアプリ）では
確保した分がそのまま死んで大きく負け、generators は 24 KiB で 160 KiB に収まらなくなる。

**読み取り**: tlsf の共有ヒープで、セグメントは**オブジェクトの側を意味のある形では断片化させていない**。
§4 で測った「鎖の中の他人の確保」は鎖が散らばっていることを示すが、それがオブジェクトの大きな確保を
妨げているわけではない。

## 12. L3/L4 の結論（ホスト）

ホストで試せる方式をすべて比べた — 動かさない（出荷中）、同サイズで動かす（L3a）、寄せる（L4a、
毎回・閾値つき）、専用領域（D6、ピークちょうど・固定）。**tlsf モデルで、動かさない共有ヒープの
現行設計に勝つものは無かった。** 仕様 §12.2-3 の「移動しないセグメントで足りるなら L3/L4 を
実装しない」に対し、ホストの証拠は「足りている — そして動かすと悪くなる」を指している。

L3a（動かせること）と L4a（寄せること）のコードは既定 n のまま残す。測る道具としては役に立ち、
§10.3 の退避を試すことになればそのまま使える。**次に何かを決めるのは実機の G12**: 実機の
tlsf とネイティブの確保が混ざった状態で、断片化が原因で大きな確保が失敗しているかどうか。
失敗していなければ、この段はここで閉じてよい。
