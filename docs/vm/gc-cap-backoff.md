# 上限の手前での GC の空回りを止める（2026-09-27、`vm/runtime-speed`）

`components/quickjs-ng/quickjs-ng/quickjs.c` の `js_trigger_gc`・`js_gc_effective_threshold`。
計測の道具は `tools/vmtest/prof/stress_prof.sh`、負の対照は `tools/vmtest/gc_faults.sh`。

## 1. 何が起きていたか

循環回収（GC）の起動条件は、上流では「`malloc_size` が閾値を超えたら。閾値は GC 後の生存量の 1.5 倍」。
ゲストには 160 KiB の上限があるので、PocketJS は閾値に**上限の手前 1/32（5 KiB）という天井**を足している
（backlog #5。天井が無いと、生存量が上限の 2/3 を超えた時点で閾値が上限の外に出て、循環ごみが OOM になる）。

天井には代償がコメントに書いてあった: **生存量が天井を超えると、オブジェクトを 1 つ作るたびに GC が走る**。
「上限の 1〜2 確保手前でしか起きない」とされていたが、STRESS TEST の LV3（生きたデータを上限近くまで積む
アプリ）で測ると常態だった。

| 計測（ホスト、実機レイアウト `-m32`、ファームの既定の VM 設定、上限 160 KiB・初回閾値 80 KiB、callgrind） | 値 |
| --- | --- |
| LV1〜LV2 の 599 フレームで走った GC | 5 回 |
| LV3 の 301 フレームで走った GC | 1,080 回（1 フレーム 3.6 回） |
| LV3 の JS のターン（命令数/フレーム） | 約 1.32M、うち GC 約 0.93M（70%） |

GC の後も天井を超えている = その GC は解放できるものをほぼ見つけられなかった。次の GC が解放できるのは、
その後に**増えた分**だけである。

## 2. 何をしたか

天井が起こした GC の後もヒープが天井を超えていたら、そのときの `malloc_size` を床として覚える
（`JSRuntime.gc_cap_floor`、64 B 単位の 16 bit。`gc_phase` の後ろの詰め物に入るので `JSRuntime` の大きさは変わらず、
コーパスが固定している確保のバイト位置も動かない）。次に天井が GC を起こそうとしたとき:

- ヒープが床より**下**なら（参照カウントで解放が起きた後）、床は古いので今までどおり GC する。
- 床から伸びた量が **予算未満**なら GC しない。予算 = `min(上限 >> 5, (上限 − 床) / 2)`。
  上限に近い床ほど予算が小さくなり、残りの半分を使い切る前に必ず GC する。
- 天井より下の閾値で起きる GC は一切変えない。4 MiB を超えるヒープ（16 bit に入らない）は上流のまま。

最初は「オブジェクトを 32 個作るまで待つ」という個数の後退で作った。個数はオブジェクトの大きさを
見ないので、`gc_threshold_near_limit.js` で測った余裕は 2〜4 倍しかなかった（64 個で通り、128 個で OOM）。
伸びた量で見れば、循環ごみが何個のオブジェクトでできていても同じ尺度になる。
