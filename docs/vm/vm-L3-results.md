# L3 の実測と関所の結果

設計は [vm-L3-design.md](vm-L3-design.md)、入口の台帳は
[vm-ledger/09-relocation-entries.md](vm-ledger/09-relocation-entries.md)。
ブランチ `vm/l3a-refs`、基点 `953c627`（tag `vm-L2`）。

**実機で走らせてはいない。** 実機ビルドは通り、サイズも測れた（§2）が、書き込みも
実行もしていないので、停止時間・空きヒープ・移動の実機単価は主張しない。実機の呼び出し元
（§3）は**一度も動いていない**。それ以外はすべてホストの実測。

## 1. L3a の着地（2026-09-23、実測(host)）

`CONFIG_POCKET_VM_RELOC`、既定 n。移動は駐機のたびに、再開の直前に、生きている
セグメント鎖を丸ごと新しい番地へ写す。受け口は2つ:

- **ホスト**: `tools/vmtest/build.sh asan-reloc` / `o2-reloc`、`vmrun --force-reloc`。
- **実機**: `guest_continue_impl()` の1箇所、USB `&` で武装（§3）。**未実行**（§3.2）。

## 2. 実機のサイズ — と、呼び出し元が無いと測れないという話

```powershell
idf.py -B build_l3a_reloc -D SDKCONFIG="build_l3a_reloc/sdkconfig" `
       -D SDKCONFIG_DEFAULTS="sdkconfig.defaults;sdkconfig.reloc" build
```

`sdkconfig.reloc` は `CONFIG_POCKET_VM_RELOC=y` の1行だけ。**`-D SDKCONFIG` でビルド
ディレクトリごとに分けるのが必須**で、既定の `sdkconfig` はツリーで1本しか無いため、
片方のビルドが立てた `RELOC=y` をもう片方が黙って拾う（この節を書く途中で実際に踏んだ）。

| ビルド | DIRAM | Flash |
| --- | --- | --- |
| 既定（RELOC=n） | 159,676 | 1,402,876 |
| RELOC=y、呼び出し元あり | 159,692（**+16**） | 1,404,176（**+1,300**） |

既定ビルドは L3a 着手前と**バイト一致**（仕様 §12 の既定挙動維持）。

### 2.1 呼び出し元が無かった間、この表は嘘だった

最初にこの表を取ったとき、**2行が完全に同じ**だった。読み方を間違えかけたところを
`nm` が止めた:

```text
quickjs.c.obj              T JS_VMStackRelocate …   在る
cardputer_pocketjs.elf     （1つも無い）            無い
```

ファームに呼び出し元が1つも無いので `--gc-sections` が丸ごと落としていた。
**増減ゼロは「機能が軽い」ではなく「機能がそこに無い」だった。** CLAUDE.md が
名指ししている罠（「`--gc-sections` で削除済みのモジュールを測っていた例」）を、
警告を読んだ上で1回踏んだ。

§3 の呼び出し元（`guest_continue_impl`）を入れて初めて上の表が測定になった。
`JS_VMStackPin` は**今も ELF に無い** — ホストの関所専用で、ファームに呼び出し元が
無いため。これは正しい状態であり、同時に**「シンボルが在るか」を毎回 `nm` で見るべき
理由の実例**でもある。

## 3. 実機の呼び出し元（2026-09-23）

**1箇所だけ。** `components/pocketjs_guest/src/guest.c` の `guest_continue_impl()`、
`JS_VMResume()` の直前。ここはファームが**これから走らせ続けるつもりの鎖**を再開する
唯一の場所で、vmrun の `resume_until_done` に対応する。

`pocketjs_guest_prepare_stop()` にも駐機中の再開が在るが、**そちらには入れない** —
終了させるための再開なので、解放される途中のバイトを写すことになる。
`vm_sched_drain()` は再開しない（`VM_DRAIN_SUSPENDED` を返すだけ）。

| 口 | 形 |
| --- | --- |
| 武装 | ホーム画面の USB `&` → `VM_RELOC_ARMED` を出す。粘着（set のみ、toggle ではない） |
| 適用 | `app_start_test()` のゲスト生成直後。**評価より前**（トップレベル await の駐機を逃さないため） |
| 報告 | アプリ停止時に `VM_RELOC moves=… refused=… frames=… var_refs=… bytes=… max_us=… total_us=… largest_first=… largest_last=… largest_min=… gap_max=… gap_segments=…` |

`&` を選んだのは、既存の USB キー（`1`-`6` `8` `9` `A`-`F` `G`-`K` `L` `M` `N` `O` `P`-`W`
`U` `X` `Y` `Z` `[` `\` `]` `<` `>` `~` `s` `c` `-` `=` `?` と小文字の nav）と
**1つも重ならないため**。置き場は FPU プローブより後 — `F` を先に取ったせいで
プローブの第6ワークロードが黙って到達不能になった件（`c073f8a`）と同じ失敗を避けるため。

**ホーム画面でしか取らない**理由: アプリ実行中のバイトは `pocket_bridge_usb()` と
`pet_hub_usb()` に先に渡されるので、`&` を要求するアプリがあれば黙って奪われる。

**既定 `n` なので、出荷ビルドにこの経路は1バイトも入らない。**

### 3.1 この検査が見るもの / 見ないもの

| 問い | 見えるか | 何で |
| --- | --- | --- |
| 移動して壊れないか | **見える** | 契約マーカーの一致 + `moves>0` の要求 |
| 移動が何度起き、何を補正したか | **見える** | `moves` `refused` `frames` `var_refs` |
| 1回の移動の最悪停止時間 | **見える** | `max_us`（`heap_caps_*` の外で計測） |
| 移動がヒープをどう動かすか | **見える（観測のみ）** | `largest_first` / `largest_last` / `largest_min` |
| 鎖がどれだけ飛地か | **見える** | `gap_max` / `gap_segments`（§4） |
| **断片化が回収できるか** | **見えない** | L3a に詰める機能が無い（下記） |

**L3a はコンパクションをしていない。** 移動は「**同じ大きさ**の新しいブロックを取り、写し、
古いのを解放する」なので、

- 移動の最中は**新旧が同時に生きている**。一時的に要る追加は、その鎖自身の大きさ
  （`bytes`）ちょうど。**ヒープの山は下がるのではなく上がる。**
- 返す量と取る量が同じなので、**原理的に詰まらない。** 配置が変わるだけで、それが
  結果的に良くなるか悪くなるかは誰も設計していない。

だから `largest_*` は**関所ではなく観測**として出している。合格条件を置いていないのは、
「どうあるべきか」を決めるのが L4 だからで、L4 はまだ無い。**「移動したらヒープが悪化した」が
起きていたら見えるようにしてある**、それだけである。

仕様 §12.2-3 の関所（G12、断片化を測って L3/L4 の要否を決める）は、**この検査では
答えられない**。必要なのは「詰めたらどれだけ回収できるか」で、詰める実装はまだ無い。

## 4. セグメント鎖は本当に飛地なのか（実測(host)）

移動の前に、**そもそも断片化しているのか**を測った。`JSVMRelocStats` に 2 つ足した:

- `resident` — 生きているセグメントのブロックの合計。
- `span` — 一番低いブロックの先頭から、一番高いブロックの終端まで。

**`span - resident` が、その鎖の番地範囲の中に挟まっている「他人の確保」のバイト数**である。
セグメントが隙間なく並んでいれば 0 になる。

| コーパス | 移動 | セグメント | resident | span | **他人の確保** | 鎖の密度 |
| --- | --- | --- | --- | --- | --- | --- |
| `tco_guards` | 298 | 8 | 18,816 | 68,000 | **49,184** | 28% |
| `deep_recursion` | 253 | 9 | 22,960 | 52,704 | **29,744** | 44% |
| `seg_closure_survives` | 252 | 9 | 22,960 | 46,464 | **23,504** | 49% |
| `closures` | 60 | 2 | 1,632 | 20,592 | **18,960** | 8% |
| `yield_async_in_chain` | 5,807 | 2 | 1,632 | 3,680 | **2,048** | 44% |

**飛地は実在する。** 22,960 B のスタックが 52,704 B に散らばり、間に 29,744 B の他人が
座っている。`closures` に至っては鎖の番地範囲の 92% が他人である。

### 4.1 ただし、原因は中断の回数ではない

「中断と復帰を繰り返すと飛地になる」という読みは、**この計測では支持されなかった**。

決め手は `yield_async_in_chain` で、**5,807 回**駐機しているのに他人は 2,048 B しかない。
逆に `closures` は **60 回**しか駐機していないのに 18,960 B ある。回数と隙間に関係が無い。

移動ごとの推移（`#info reloc_gap_trend`）も同じことを言う。`deep_recursion` は
最初の移動が `0/1`（セグメント1本、隙間0）で最後が `25,888/9` — **隙間が増えたのは
鎖が深くなったからで、時間が経ったからではない**。`tco_guards` は最初も最後も `0/1` で、
49,184 B は途中の深い瞬間に出ている。

効いているのは**鎖が深くなる過程で他の確保が挟まること**である。セグメントは深さが増える
たびに別々の `js_malloc_rt` で取られるので、その合間に確保されたものが物理的に間に入る。
駐機はその鎖を保持するだけで、保持している間にホスト側が何も確保しなければ隙間は増えない。

**ホストの結論を実機へそのまま持ち越してはいけない。** vmrun の駐機中は何も走らないが、
**実機の駐機中はファームのネイティブ work（Kasane、音、pump）が同じプールで確保と解放を
する**（ゲストの `js_malloc_rt` は `heap_caps_malloc(MALLOC_CAP_INTERNAL|MALLOC_CAP_8BIT)`、
ネイティブと同一プール）。**中断が飛地を作るという仮説が一番効きそうなのは実機で、
そこはまだ測っていない。** `VM_RELOC` の `gap_max` / `gap_segments` がその口である。

### 4.2 QuickJS の GC はこの話にどう効くか

3つの事実で、効き方が決まる。

**1. GC はオブジェクトを動かさない。** `free_gc_object`（`quickjs.c:7639`）は
`js_free_rt` で返すだけで、生きている物を寄せる経路がどこにも無い。参照カウント＋
循環回収で、**non-moving**。だから **GC がいくら回っても隙間は閉じない** — 隙間の中身が
「生きたオブジェクト」から「空きブロック」に変わるだけである。上の表の
「他人の確保」は、GC の後には「他人の空き」になる。**これが L4 が要る理由そのもので、
L3a の移動だけでは足りない理由でもある。**

**2. セグメントの確保は GC を起こさない。** `js_trigger_gc` の呼び出しは全 66,955 行で
**1 箇所だけ**、`JS_NewObjectFromShape`（`quickjs.c:6305`）である。`js_malloc_rt` は
呼ばない。**深い再帰でセグメントを何本取っても、それ自体では GC は1回も走らない。**

**3. それでもセグメントは GC の閾値を押し上げる。** 閾値の判定は
`rt->malloc_state.malloc_size + size > js_gc_effective_threshold(rt)`（`quickjs.c:1770`）で、
`malloc_size` は `js_malloc_rt` を通る**すべて**を数える — セグメントも含む。しかも
GC 後の再設定は `malloc_size + malloc_size/2` なので、**深い鎖が生きている間は閾値が
その分だけ浮く**。

つまり GC とこの断片化の関係は:

- **隙間を作る側ではない。** 隙間を作るのは「深くなる過程で挟まる確保」であって GC ではない。
- **隙間を直せる側でもない。** non-moving なので、回収しても配置は変わらない。しかも
  このコーパスではセグメント自体が一度も解放されない（§4.4）ので、回収の対象ですらない。
- **隙間の中身を変える側ではある。** 生きたオブジェクト → 空きブロック。tlsf が隣接する
  空きを結合できれば、次のセグメントがそこに入る余地はできる。**ただし L3a は同じ大きさの
  ブロックを取り直すだけなので、その余地を使って詰めることはしない。**
- **間接的に頻度へ効く。** 深い鎖は `malloc_size` を押し上げ、次のオブジェクト確保で
  GC が早く走るようにする。backlog #5 が直した「閾値がゲスト上限より大きくて回収されない」
  も同じ量の話で、`gc_threshold_{device,near_limit}.js` が回帰になっている。

### 4.3 検算: 毎中断 GC を足しても、隙間は1バイトも動かない（実測(host)）

上の読みを `--gc-on-yield`（駐機のたびに `JS_RunGC`）で検算した。

| コーパス | GC なし | **毎中断 GC** |
| --- | --- | --- |
| `deep_recursion` | max=29,744 span=52,704 resident=22,960 seg=9 | **完全に同一** |
| `tco_guards` | max=49,184 span=68,000 resident=18,816 seg=8 | **完全に同一** |
| `closures` | max=18,960 span=20,592 resident=1,632 seg=2 | **完全に同一** |

3 件とも 4 つの数値すべてがビット単位で一致した。

**この検査は、当初書いたほど強い証拠ではない。** §4.4 を測って分かったが、これらの
コーパスでは**セグメントが最初に確保されたきり一度も解放されない**（`seg_frees=0`）。
番地が変わる機会がそもそも無いのだから、GC を何回走らせようと一致するのは当たり前で、
**この実験は失敗しようがなかった**。

構造的な事実（§4.2 の 1: non-moving なので回収は配置を変えない）は依然として正しい。
正しくなかったのは「毎中断 GC で一致したから証明された」という**証拠の格付け**である。
鎖が解放と再確保を繰り返す負荷でなければ、この比較に意味は無い。

### 4.4 スラッシングはしていない（実測(host)）

「隙間が再利用されず、セグメントが取っては捨てられ続けるのか」を測った。
**`--force-reloc` を付けずに**、つまり素のセグメント挙動で:

| コーパス | pushes | seg_live_max | **seg_mallocs** | seg_frees | **seg_reuses** | trims |
| --- | --- | --- | --- | --- | --- | --- |
| `deep_recursion` | 127 | 9 | **9** | 0 | 0 | 0 |
| `tco_guards` | 411 | 9 | **9** | 0 | **37** | 0 |
| `closures` | 55 | 2 | **2** | 1 | **12** | 1 |

**churn は無い。** 127 回の push に対してセグメントの確保は 9 本、解放は 0。
`tco_guards` は 411 回の push で確保 9 本・**再利用 37 回** — D43 のキャッシュが
効いていて、浅くなって深くなり直すたびに**同じセグメントを取り戻している**
（`js_vm_stack_pop` がキャッシュへ返し、`push_slow` がそこから取る）。

**比較のため**: 同じ負荷に `--force-reloc` を付けると `seg_mallocs` は 9 → **1,570** に跳ねる。
その 1,561 本は**移動が自分で作った churn** であって、通常のセグメント挙動ではない。
`--stats` の `seg_mallocs` を読むときは、移動の分が混ざることに注意する。

つまり現状は:

- **隙間は「再利用されない」わけではない。** 隙間は普通のヒープで、tlsf の空きブロックは
  誰でも取れる。ただし**そこを取るのは主に後続のオブジェクトで、セグメントではない** —
  セグメントはそもそも取り直さないから。
- **スラッシングもしていない。** 鎖は一度組んだら保持され、浅くなってもキャッシュに残る。
- **問題は「隙間が埋まらない」ことではなく、「鎖が散らばったまま固定される」こと**である。
  一度この配置で確保されたら、解放されるまで動かない。**動かす手段が無いことが問題**で、
  それを作るのが L3a、詰めるのが L4 という切り分けになる。

## 5. G7: 移動しても観測できる挙動が変わらない（実測(host)）

コーパス 75 件を `--force-yield --budget-jobs 1` の有無で 2 回ずつ走らせ、**stdout を
バイト比較**した。

| 変種 | 一致 | 差分 | タイムアウト |
| --- | --- | --- | --- |
| asan-reloc | 74 | **0** | 1 |

タイムアウトの 1 件は `runaway_jobs` で、**移動しない側も同じく 120 秒で切れる**

`closures.js` は asan-reloc / o2-reloc の両方で、それぞれの非移動実行と一致した

## 6. どの枝が実際に踏まれたか（実測(host)）

「通った」と「踏まれていない」は区別が要る。`JSVMRelocStats` に枝ごとの計数を置き、
コーパス 74 件で集計した。

| 枝 | 台帳 | 踏んだファイル | 最大値（1 実行） |
| --- | --- | --- | --- |
| 非 SEG フレーム（コルーチンの所有者記録） | E12 | 15 | `yield_async_generator` 9,003 |
| 開いた var_ref | E13/E14 | 9 | `tco_guards` 420 |
| 複数セグメントを跨ぐ鎖 | E6/D46 | — | `deep_recursion` で `seg_live_max=9` |

E12 が 15 ファイルで踏まれていることが重要で、**これは「セグメントの中を歩くだけでは
届かない入口」**（台帳 §3）。`seg_live_max=9` は、**セグメントごとに違う差分**（D46）が
実際に必要になる状況が走っていることの証拠 — 1 本しか生きていなければ根元の1加算値でも
たまたま通ってしまう。

## 7. G9: 毒が本当に鳴るか（実測(host)）

**毒化の価値は、鳴らないことではなく鳴ることでしか示せない。** `--reloc-fault` で
補正を1本だけ故意に抜き、3種すべてで検出されることを確かめた。

| 抜いた補正 | asan-reloc | o2-reloc |
| --- | --- | --- |
| `varref`（開いたクロージャ変数が旧スロットを指したまま） | `heap-use-after-free` | abort |
| `link`（フラットフレームが呼び出し元の旧 sp を持ったまま） | `heap-use-after-free` | segfault |
| `varbuf`（フレームが旧ローカル基底を持ったまま） | `heap-use-after-free` | abort |

ASan 側は 3 種とも**即座に**報告し、出力も一致しなくなる。ASan を持たない o2 側は
`0xD3` 充填（層1）だけで abort / segfault になり、**黙って動き続けることは無かった**。

つまり §5 の「差分 0」は、検出できない検査が通っただけではない。

`--reloc-keep-old`（層3、旧ブロックを毒のまま解放しない）は `--heap-limit 0` で
60 回移動・出力一致・報告なし。**既定のヒープ上限では使えない**: 意図的な漏れが
163,812 B を食って `#info oom count=10` になり、実行そのものが変わる（移動 51 / 拒否 6）。
診断専用という位置づけどおりだが、**出力一致の関所には使えない**ことを記録しておく。

## 8. G10: 失敗が安全か（実測(host)）

| 失敗 | 結果 |
| --- | --- |
| 駐機していない | `vmrun` が起動直後（JS 実行前）に呼んで `-1` を確認。0 が返ったら異常終了する検査を常設した |
| pin 中（D51） | `--reloc-pin` で `moves=0 refused=60`、**出力は非移動実行とバイト一致** |
| 床の下に外側の JS 活性（D55） | `bench_promise` で `refused=2` を**自然に**観測。仮定の制約ではなかった |
| 段1の確保失敗（OOM） | `--fail-alloc 2500` で `moves=59 refused=1`、VM は無傷で完走 |

D55 の拒否が実コーパスから出たのは、この決定を**実装中に足した**ことの裏付けになる
（当初の D45 だけでは足りなかった）。

## 9. G11: Test262（実測(host)、o2-reloc、固定 `72faf8ec1445`）

`--force-yield` に `--force-reloc` を足した実行と、**同じバイナリ・同じ範囲で足さない実行**を
対にして取った。退行の有無だけでなく、pass/fail の数そのものを突き合わせている
（「退行 0」は基準ファイルとの比較なので、基準に無い項目を見逃しうる）。

| 範囲 | ファイル | 移動あり | 移動なし（対照） |
| --- | --- | --- | --- |
| `async-function` / `await` / `for-of` | 847 | 1,612 pass / 7 fail | **同一** |
| `Promise` / `generators` / `async-generator` / `class` / `try` | 6,189 | 12,018 pass / 210 fail / 1 skip | **同一** |

合計 7,036 ファイル、退行 0。**210 件の失敗は移動の有無で1件も動かない**ので、
移動が原因ではない（基準の既知の失敗）。

固定 Test262 全体 53,582 本との対照は未実施（§12）。

## 10. 移動の費用（実測(host)、o2-reloc）

**短いコーパスでは測れない。** `deep_recursion`（253 移動）や `yield_async_frame`
（8,004 移動）では、同じ設定の反復が 19〜41 ms にばらつき、移動の有無の差は
その中に埋まる。プロセス起動が支配的で、この計器の分解能を下回る。**ここで数字を
作らない。**

差が出るのは移動を百万回させたときだけ:

| `bench_closure` | 実測（2回ずつ） |
| --- | --- |
| `--force-yield` のみ | 214 / 223 ms |
| `+ --force-reloc` | 327 / 320 ms |

移動は 1,280,002 回、補正したフレームは 1,700,002。差は約 105 ms なので
**1 移動あたり約 82 ns（ホスト x86、計算値）**。ただしこの負荷は
`seg_live_max=1`・`live_max=344 B` で、**1 移動が写すのは 1 セグメントの数百バイトだけ**。
セグメントが 9 本生きている `deep_recursion` の形での単価は測っていない。

**この 47% という比は最悪条件の上限であって、費用の見積もりではない。**
`--force-reloc` は安全地点のたびに駐機し、そのたびに必ず移動する。実際に L4 が
移動を要求する頻度は「断片化したとき」であって「毎安全地点」ではない。
**実機の単価は未測定。**

## 11. 見つけた、L3 とは無関係の不具合

`--fail-alloc` の掃引（15 点）で `N=1500` が `heap-buffer-overflow` を起こす。
場所は `resolve_variables`（`quickjs.c:37723`）の `dbuf_put` で、**パース中**
（`JS_Eval` → `js_create_function`）。フレームもセグメントも関与しない。

**RELOC を1行もコンパイルしない素の `asan` ビルドで、`--force-reloc` 無しに同一アドレスで
再現する。** L3 以前から在る。backlog の L3 #6 に送った。

掃引の残り 14 点は crash 無し。

## 12. まだ測っていないこと

- **実機で走らせていない。** サイズは測れた（§2）が、書き込みも実行もしていないので
  停止時間・空きヒープ・実機の移動単価は未測定で、`VM_RELOC` の行を一度も見ていない。
  呼び出し元・武装キー・`device_reloc.py` はすべて**未検証**である（§3.1）。
- **Test262 は 7,036 ファイルの部分集合まで**（§9）。固定 Test262 全体 53,582 本との
  対照は未実施。
- **移動の単価はホストの1形だけ**（§10）。`seg_live_max=1` の浅い鎖での 82 ns で、
  セグメントが複数生きている形も、実機も測っていない。L3a の主張は「動く」であって
  「速い」でも「安い」でもない。
- **断片化がどれだけ回収できるか（G12）は未実施。** これは L3 着手の関所そのもので、
  実機計測が要る（design §1.1、backlog の L3 #1）。
