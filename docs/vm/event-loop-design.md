# イベントループ設計: 非同期の合流点を表示ループから外す

状態: **設計・素案（2026-10-27）。** 実装は無い。SLOW（Fable）の独立レビュー前。
発端は issue #98（`frame()` の無いプログラムが評価直後に終わり、Promise のジョブを捨てる）と、
そこから辿った「`pocket.*` は非同期 API なのに、合流点が同期的」という指摘。

この文書は、なぜそうなっているのかを根拠つきで掘り（§2）、既にある決定とどこで衝突するかを確かめ（§3）、
ui_task のままで成立する形を示し（§4〜§7）、段階と決めることを並べる（§8・§9）。
事実には file:line か文書の節を付け、推測・推定はそう書く。

---

## 0. 要約

- **同期的なのは合流点だけではなく、3 層ある**（§1）。実行そのものが同期（`pocket.fs` は SD でも
  JS の呼び出しの中で `fread` まで済ませ、解決済みの Promise を返す）、合流が同期（完了を拾うのは
  `app_tick()` の決まった pump 段だけ）、ループの中心が `frame()`（表示の周期が合流を回す）。
- **根本原因は「ターン」の過積載**（§2、R1）。1 つのターンが JS 実行・資源の会計・入力の配送・描画の
  4 役を兼ねている。DIRAM の制約（R3、変えられない）が強いるのは「JS の所有タスクは 1 つ」までで、
  「ループの中心が `frame()`」ではない。後者は歴史の順番（frame ループが先、`pocket.*` の非同期と L1 が後）。
- **目標の形**（§4）: ui_task のまま、ループの中心をイベントループにする。1 周 = 待つ → マクロタスク 1 つ →
  マイクロタスクの checkpoint →（予算の範囲で繰り返す）→ 描画の機会。`frame()` は requestAnimationFrame と
  同じく描画の機会の 1 つに降格する。セッションの生存は参照カウント（Node と同じ）で決める。
- **L1 §4.2 が「`frame()` を飛ばした完了専用ターンは作らない」と決めている**（§3.2）。理由は
  「`.then` が次の `frame()` より前に走る」という観測可能な順序の変化。したがって段階を分ける:
  **E1 は `frame()` の無いセッションだけ**（比べる旧挙動が「すぐ終わる」なので互換の問題が無い）、
  `frame()` のあるアプリへ広げる E4 は互換の判断を経る。
- **生産者の多くは ui_task 自身が拾っている**（§6）。sleep の期限、UART の受信、ネットの状態は
  pump の中でポーリングして完了に転記している。タスク通知が縮めるのは別タスク・ISR の完了だけなので、
  イベントループにしても、この種の生産者は「期限」としてループに登録し直す必要がある。

## 1. 問題: 3 つの層

### 1.1 実行そのものが同期

`pocket_api_promise_open()`（完了テーブルの枠を取る、本当に非同期な経路）の呼び出しは 14 箇所
（file_picker・pocket_app の sleep・pocket_av ×2・pocket_bridge・pocket_capture・pocket_io ×2・
pocket_net ×4・pocket_workspace・sd_picker）。一方 `pocket_api_settled()`（C で処理を済ませてから
解決済みの Promise を返す）は `pocket_fs.c` だけで 32 箇所ある（`grep -c`、2026-10-27）。

例: `sd_read_text`（`main/pocket/pocket_fs.c:3762`）は `stat` → `malloc` → `fopen` → `fread` →
`fclose` → UTF-8 検査を JS の呼び出しの中で行う。その間 ui_task は止まり、ゲスト・描画・キー入力・
オーバーレイがすべて待つ。

仕様はこれを禁じている: 「入力応答を維持するため大きなコピー／一覧走査を native worker で分割する。
…同期的な長時間 SD 待ちを JS タスクへ持ち込まない」（`docs/api/filesystem-api.md:210`）。
**実装が仕様から外れている。** 止まる時間は §8 の E0 で測る。

### 1.2 合流が同期

本当に非同期な操作でも、完了が JS に入るのは `pocket_api_pump()`（`pocket_api.c:501`）だけで、
これは `run_pumps()`（`app_session.c:2055`）の決まった位置から、通常ターンでだけ呼ばれる。

- 同じターンに複数の完了が揃っていると、settle は**枠の番号順**（`for i<POCKET_MAX_PROMISES`）で、
  届いた順ではない。面をまたぐと pump の並び順が順序を決める。
- 継続ターン（キューが残っているターン）では pump が呼ばれないので、完了は「キューが空になったターン」まで
  待つ（L1 の互換モード、`vm-L1-design.md` §2.1）。

### 1.3 ループの中心が `frame()`

1 ターンは「停止要求 → 入力・I/O の完了 → 上限付き Promise job → frame → 描画」（`common-api.md:266`）。
`app_tick()`（`app_session.c:2117`）はこの順を 1 本で実装し、`main.c` の ui_task は 33 ms
（`VM_DISPLAY_PERIOD_MS`、`app_session.h:103`）の周期でそれを呼ぶ。完了の通知（`vm_wake_post()`）は
フレーム末尾の待ちを早く抜けさせるだけで、抜けた後に走るのは同じターン全体（`main.c:1341` 付近）。

`frame()` が無いと、このターン自体が始まらない: `bind-frame.js` が `ESP_ERR_NOT_FOUND` を返し
（`app_session.c:816`）、`main.c:635` が `EVALUATED (NO frame)` として終える。評価中に積まれた
Promise のジョブは「jobs dropped at stop」で捨てられる（#98、実機で確認 2026-10-27）。

## 2. なぜなぜ分析

### 2.1 鎖 1: 完了が表示ループの決まった段でしか JS に合流しない

| なぜ | 答え | 根拠 |
| --- | --- | --- |
| 1. なぜ合流点が pump 段だけか | JS の context に触れるのは ui_task だけで、ui_task が JS に入る入口が `app_tick()` / `app_overlay_tick()` の「ターン」しか無いから | `app_session.c:2117`、`:1921` |
| 2. なぜ入口がターンしか無いか | 仕様が 1 ターンを 1 本の順序で定義し、多くの規則がこの単位に結び付いているから: 予算と暴走ガード（`arm_turn`）、ネイティブ heap の標本（ターンの始めだけ、`sample_memory_pressure`）、`exit()` の処理（空のキューで始まるターンだけ）、Kasane の提出チケット（1 ターン 1 枚）、`deferred_buttons`、離脱ターン | `common-api.md:266`、`app_session.c:2117-2330` |
| 3. なぜターンと描画が一体か | JS と描画が受け渡しの境界なしに状態を共有しているから（Kasane のシーン、ストリップバッファ 1 本）。同じタスクで決まった順に回せば、ロック無しで一貫する | `quickjs-freertos-vm-spec.md:106`「専用タスク化する場合は…受け渡しを設計する」 |
| 4. なぜ受け渡しを作らず同じタスクのままか | 専用タスクはスタックで静的 DIRAM +24〜32 KiB（推定）、L0 の上限 +8 KiB を超えるから。PSRAM が無く、ゲストの heap と食い合う | `vm-L1-design.md` §4.1、仕様 `:144` |
| 5. なぜその妥協が構造として残ったか | 順番の問題。`frame()` のゲームループが先にあり（画面ループの統一 `f17c8d54` 2026-09-06）、`pocket.*` の非同期（`c4b61710` 2026-09-07）と L1（2026-09-12）は pump として後から乗った。「イベントが無いときだけ待つ」は設計ではなく「充足と認めるか」の判断として backlog に置かれた | git log、`backlog.md` 表の 2 |

**なぜ今まで表に出なかったか**: 出荷アプリはすべて `frame()` を持つ常時描画の型で、`frame()` の無い
経路は PLAYGROUND の実機試験くらいでしか通らない。L1 の測定ワークロード（A〜F）もすべて `frame()` を持つ。

### 2.2 鎖 2: 非同期 API なのに実行が同期

| なぜ | 答え | 根拠 |
| --- | --- | --- |
| 1. なぜ SD の読み込みが ui_task を止めるか | `sd_read_text` などが呼び出しの中で I/O を済ませ、`pocket_api_settled()` で返すから | `pocket_fs.c:3762` |
| 2. なぜその形か | `app:` 側のストア（索引とブロック走査）がスレッド安全でなく ui_task 専用だから。SD 側も同じ形に揃えたと見られる（**推測**） | `common-api.md:607` |
| 3. なぜ仕様どおり worker に出していないか | 理由は記録に無い。完了テーブルの枠（4）、worker のスタック（DIRAM）、実装の手間のどれか（**推測**） | `filesystem-api.md:210` と実装の差 |
| 4. なぜずれに気づかないか | SD の読み込みが ui_task を止める時間を誰も測っていないから。試験で読むのは小さなファイル | 測定記録が無い |

### 2.3 根本原因

| 原因 | 変えられるか | この設計での扱い |
| --- | --- | --- |
| **R1** 1 つのターンが 4 役（JS 実行・資源の会計・入力の配送・描画）を兼ねる | 変えられる | ターンを「マクロタスク + checkpoint」と「描画の機会」に分け、会計をマクロタスクの単位へ付け替える（§4、§7） |
| **R2** JS と描画に受け渡しの境界が無い | 変えなくてよい | 同じタスクのままなら、描画の機会をループの 1 段にするだけでロックは要らない |
| **R3** DIRAM が無く専用タスクを持てない | 変えられない | 解を ui_task の上に置く |
| **R4** 出荷アプリが全部ゲーム型で、検証が偏っている | 変えられる | `frame()` の無いワークロードと大きな I/O を測定と vmtest のコーパスに足す（§10） |
| **R5** 仕様と実装のずれを捕まえる仕組みが無い | 変えられる | SD の停止時間を測り（E0）、fs を仕様に合わせる（E3） |

## 3. 既にある決定との関係

### 3.1 専用タスクを作らない（L1 §4.1）— 維持する

この設計は専用タスクを作らない。R3 の範囲に収まる。

### 3.2 「完了専用ターン」を作らない（L1 §4.2）— 段階を分けて扱う

L1 §4.2 の決定: 「早く起きたターンは `app_tick()` を普通に回す。`frame()` を飛ばした完了専用ターンは
作らない。作ると resolve → drain → `frame()` の順になり、`.then` が次の `frame()` より前に走るという
観測可能な変化がアプリに入る」。

今の順序と、イベントループでの順序:

| | 今（1 ターン） | イベントループ |
| --- | --- | --- |
| 完了が届いたターン | pump（resolve、reaction を積む）→ `frame()` → drain（`.then` が走る） | resolve → checkpoint（`.then` が走る）→ …描画の機会が来たら `frame()` |
| `frame()` が見る状態 | `.then` の**前** | `.then` の**後** |

後者はブラウザの順序（タスク → マイクロタスク → rAF）と同じで、`frame()` が最新の状態を描くという意味では
むしろ自然だが、**変化であることに変わりはない**。仕様 §12.1「新たな失敗を期待値の書き換えだけで処理しない」に従い、

- **E1（§8）は `frame()` の無いセッションに限る。** 旧挙動は「評価後に終了してジョブを捨てる」なので、
  比べるべき順序が存在しない。互換の問題が起きない。
- **E4 で `frame()` のあるアプリに広げるかは、出荷アプリの監査と実機の比較を経て決める**（§9 の決定 D-E4）。

### 3.3 互換モード（キューが空のときだけ完了を配る）— 意味はそのまま

「継続中は pump を呼ばない」は、HTML の「マクロタスク 1 つ → マイクロタスクの checkpoint → 次のマクロタスク」と
同じ規則で、イベントループでも保たれる。L1 の測定で F 型（`async_generator`）に残る完了遅延
（中央値 18〜36 ms、`vm-L1-report.md` §2.8）は、アプリ自身のマイクロタスクの連鎖（0.49 ms × 62 件）が
原因で、この設計でも縮まない。縮めるなら L2c の opcode 中断で checkpoint の途中にマクロタスクを挟む形になり、
それは削除済みの公平モード（`backlog.md` 表の 3、2026-09-23 に n で確定・削除）の再検討になる。**この設計の範囲外。**

### 3.4 backlog 表の 2（「イベントが無いときだけ待つ」を充足と認めるか）

この設計は、専用タスクなしで文字どおり満たす答えになりうる。ただし ui_task にはホーム・ペット・オーバーレイ・
キーボードの読み取りが乗っているので、「眠れる」のは前面に `frame()` の無いセッションだけが走っている間に限る
（§6.3）。

## 4. 目標の形

### 4.1 ui_task の 1 周（ゲスト実行中）

1. **待つ**: `vm_wake_wait(min(次の表示, 次の期限, 次のキー読み取り, 次の定期処理))`。
2. **マクロタスクを 1 つ取る**: 完了・キー入力・期限（sleep など）・購読の配送のうち、届いた順で最も古いもの。
3. **checkpoint**: マイクロタスクを空にする。8 ms の予算・暴走ガード・L2c の中断は今の `vm_sched_drain` をそのまま使う。
   空にならなければ継続（今の継続ターンと同じ）で、次のマクロタスクは取らない。
4. **予算が残っていれば 2 へ。**
5. **描画の機会**: 表示の周期が来ていて、かつ「`frame()` がある」「Kasane のアニメ中」「提出済みのチケットがある」の
   どれかなら、`frame()`（あれば）→ present。

ゲストが居ないとき（ホーム画面など）の周は今と同じ。

### 4.2 セッションの生存: 参照カウント

セッションは次のどれかが残っている間は生きる（Node の ref と同じ考え方）:

- QuickJS のジョブキュー（`pocketjs_guest_work_pending`）
- 完了待ちの枠（`pocket_api_open_count()`）
- 購読（面ごとの購読テーブル。**全体の数を返す API は今は無い** — 足す）
- sleep・再生中の音・録音・ネットの lease など、期限や完了を後で出す資源
- `frame()` の定義、または `pocket.app` の hook の保留

すべて 0 になったら正常終了（`EVALUATED (NO frame)` と同じ終わり方）。Back（Esc）は今と同じく止める。
上限は今の暴走ガードとセッションの資源上限で足りるかを §9 の D-E1b で決める。

### 4.3 届いた順の保存

`pocket_api_complete()` で atomic の通し番号を振り（`atomic_fetch_add`、ISR 安全）、settle を番号順にする。
追加は枠ごとに 4 B 程度（推定）。面をまたいだ順序（UART の受信と sleep の完了など）もこれで揃う。
ui_task 自身が転記する完了（§6.1 の (b)）は転記した順になる。

## 5. 何がマクロタスクになるか

| 種類 | 今の入口 | イベントループでの扱い |
| --- | --- | --- |
| Promise の完了（別タスク・ISR） | `pocket_api_complete()` → `vm_wake_post()` → 次の通常ターンの `pocket_api_pump()` | 通知で起き、通し番号の順に 1 件ずつ settle |
| Promise の完了（ui_task が転記） | pump の中で期限・リング・状態を見て `pocket_api_complete()`（§6.1 (b)） | 期限を「次の期限」に登録し、来たら転記して 1 件 |
| 購読の配送 | 各 pump の `pocket_api_sub_deliver()` | 1 配送 = 1 マクロタスク（今は 1 pump の中でまとめて呼ぶ。分けるかは D-E2b） |
| キー入力 | `pocket_input_pump(buttons)`、`deferred_buttons`、`pocket_text_pump()` | 1 打鍵 = 1 マクロタスク。融合問題（`backlog.md` 表の 1）が解ける可能性がある |
| `frame()` | ターンの中心 | 描画の機会（§4.1 の 5） |
| hook（start / suspend / resume / stop） | `pocket_app_pump()`、`pocket_app_run_suspend()` | 今と同じ場所に残す（セッションの状態遷移なので） |

## 6. 生産者: 通知で起こせるもの・起こせないもの

### 6.1 3 つの型

- **(a) 別タスク・ISR が完了を書く**（音声、録音、ネットの一部、ブリッジ）: `vm_wake_post()` が既にある。
  イベントループでそのまま起きる。
- **(b) ui_task が pump の中で拾って転記する**（sleep の期限 `pocket_app.c:723`、UART の受信 `pocket_io_pump`、
  ネットのリンク・スキャン `pocket_net_pump`、ピッカーの結果）: L1 §4.2 のとおり、自タスクの投稿は起床を出さない。
  これらは**期限**（sleep の `due_us`）か**定期の見回り**（UART のリング）としてループの待ち時間に入れる。
  UART・ネットを別タスクからの投稿に変えられるかは個別に調べる（**未調査**）。
- **(c) 呼び出しの中で同期に済ませる**（`pocket.fs` の大半、`pocket_storage`）: 合流の問題ではなく実行の問題。
  E3 で SD を worker へ出す。`app:` ストアは ui_task 専用のまま（スレッド安全でない、`common-api.md:607`）で、
  1 回の読み出しが短いことを測って確かめる。

### 6.2 SD を worker へ出す（E3）

`sd_media.c` には既に worker と lease の仕組みがある（`sd_media.c:89`「An acknowledged worker is necessary…」）。
これを使えるか、新しいタスクが要るかで DIRAM の費用が変わる（**未調査**）。ui_task に残すのは JS の値を作る
`settle`（文字列・ArrayBuffer の生成）だけ。完了テーブルが 4 枠なので、fs の同時操作 2 件
（`filesystem-api.md:210`）と他の面の合計が 4 を超えないかを確かめる。

### 6.3 消せないポーリング

- **キーボード**: TCA8418 を I2C で毎周読む（`board_key_event()`、`main/hal/board.c`）。CFG に 0x01
  （KE_IEN）を書いているが、INT ピンが GPIO に配線されているかは**未確認**。配線されていればキー入力も通知にできる。
- **ホーム・ペット・オーバーレイの描画**: ゲストが居ない周、およびオーバーレイを出している周は今と同じく
  フレームで回る。眠れるのは「前面に `frame()` の無いセッションだけ」の間。
- **定期処理**: `net_service_pump()`、`net_autosync_poll()`、通知（`sys_notify_active`）、メモリの標本。
  これらは「次の定期処理」として待ち時間の上限に入る。

## 7. ターンに結び付いていた規則の付け替え

| 規則 | 今の単位 | イベントループでの単位 | 注意 |
| --- | --- | --- | --- |
| 予算 8 ms（`VM_TURN_BUDGET_US`） | ターン | 1 周（§4.1 の 2〜4 の合計） | 周の中で複数のマクロタスクを取るので、予算は周全体にかける |
| 暴走ガード 250 ms（`VM_RUNAWAY_US`） | 1 本の論理 drain | 同じ | 変更なし |
| ネイティブ heap の標本 | ターンの始め | 周の始め | 評価中は `null` のまま（CLAUDE.md の制約） |
| `exit()` | 空のキューで始まるターン | 空のキューで始まるマクロタスク | L1 §2.2 の理由（停止は割り込みとして届く）はそのまま |
| Kasane の提出チケット | 1 ターン 1 枚、未消費なら次の `frame()` で BUSY | 描画の機会で消費。**マクロタスクの中の `.then` が提出したら、次の提出の前に present が要る** | `app_session.c:2262` 付近の BUSY 対策と同じ問題が、`frame()` の外でも起きる。「提出済み」を描画の機会の条件に入れる（§4.1 の 5） |
| `deferred_buttons` | 継続ターン中のキーを OR で保持 | 打鍵ごとのマクロタスクにすれば不要（D-E2c） | `backlog.md` 表の 1 と同時に決める |
| 離脱ターン（Back、`0x2000`） | 広い予算で `frame(0x2000)` まで | 同じ。`frame()` の無いセッションは stop hook だけ | |
| 中断（suspend） | `pocket_api_cancel_all()`、`APP_SUSPEND_REFUSED work pending` | 同じ。参照カウント（§4.2）が「仕事が残っている」の定義を兼ねる | |
| オーバーレイ | `app_overlay_tick()`、`budget_us` と `over_limit` | 前面と同じループ関数。描画の機会は `shell_draw()` が出す | 2 系統の骨格を 1 つにまとめる |

### 8.1 E0 の結果

**未測定。** E3 の根拠は数値ではなく仕様違反に置く: `filesystem-api.md:210` は「同期的な長時間SD待ちを
JSタスクへ持ち込まない」と定めるが、`sd_read_text`（`pocket_fs.c:3762`）は ui_task の上で stat・fopen・fread を
済ませる。止まる時間の大小にかかわらず直す対象なので、数値が決めるのは E3 を他の段より先にやるかの優先順位だけ。
その数値は E3 の実機確認で、修正前後を同じ手順で測って得る（ピッカーでのフォルダー選択に人の操作が要る:
`requestFolder('sd')` の許可は人の選択で、USB からはピッカーのカーソルを動かせない）。

## 9. 決めること

- **D-E1a**（決定 2026-10-28）: `frame()` の無いセッションは、評価の出力（`EVALUATED` 画面）を出したまま待ち、
  後から出た `print` もそこへ足す。
- **D-E1b**（決定 2026-10-28）: 時間の上限は付けない。止める手段は Back。待つものが無くなった時点で自動で終わる
  （§4.2）。sleep の長い待ちやピッカー（120 秒）のような正当な待ちを切らないため。
- **D-E2b**: 購読の配送を 1 件ずつのマクロタスクにするか、pump ごとにまとめたままにするか。
- **D-E2c**: キー入力を打鍵ごとのマクロタスクにして `deferred_buttons` をやめるか（`backlog.md` 表の 1 を同時に決める）。
- **D-E3**: SD の worker に既存の仕組みを使うか、新しいタスクを足すか（DIRAM の費用で決める）。
- **D-E4**: `frame()` のあるアプリに広げるか。広げるなら、apiVersion で切り替えるか一斉に変えるか。

## 10. 検証

- **host**: `tools/vmtest` の `--host-events` に「`frame()` 無し」「完了の到着順」を足す。コーパスに
  `frame()` 無しで `await` の連鎖と sleep を使うプログラムを足す（R4）。
- **実機**: L1 のワークロード A〜F を、E1 の前後で同一条件で取り直す（周期・完了遅延・空き heap）。
  `frame()` の無いワークロード（sleep の連鎖、SD の読み込みの連鎖）を足す。
- **出荷アプリ**: E1 は `frame()` の無いセッションだけを変えるので、出荷アプリの通常の実機検査
  （`launch_rows.py`、`stress_app.py`、`test_app_resume.py`）が全部通ることで「変えていない」ことを確かめる。
