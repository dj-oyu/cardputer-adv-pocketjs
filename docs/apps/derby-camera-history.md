## 1. 計算コストの見積もり（旧 derby-pan-camera-cost.md、2026-09-30）

実装前に、首振りカメラ（WIDE を場内の固定カメラにして首を振る。広角 f≈200、遠い区間は先頭馬を約 14 px に保つ自動ズームで f ≤ 1,500）と楕円コースの費用を、実機の単価から見積もった。

### 結論

- **点ごとの JS 投影は成り立たない。** 1 点（回転・近クリップ・除算・格納）が **41.8 µs/点**（実測）。1 フレームの余力 5.7 ms で約 130 点。首振り WIDE（100〜250 点）は中央値 13〜25 ms（推定、20 fps 前後）。型付き点列を毎フレーム登録し直す案はさらに遅い（**74 µs/点**＋固定 0.54 ms、実測）。
- **VM の中で投影すれば成り立つ。** 直線上の点（柱・縞の端・観客の区画）の奥行きは番号の一次式なので、逆数を「前の点の逆数から Newton 法 2〜3 回」（`r ← r(2 − zr)`、MUL と ADD だけ）で出す。柱 1 本 **9.5 µs**、刈り目の縞 1 本 **14.9 µs**、観客の区画の縮尺 **16.4 µs**（いずれも実測）。誤差は f=200 で Newton 2 回なら最大 0.07 px（計算）、3 回で 0.0001 px。
- VM 方式＋観客 LOD＋柱の LOD 4 px＋先頭の 150 m 奥で打ち切りなら、MID・HEAVY とも 30 fps に収まる見込み（推定。HEAVY の 2 台だけ 75 m）。対策なしは最悪フレームで 24〜29 fps。**時間より先に 1 フレームの線分上限 1,024 に当たる**（対策なしの最悪 976〜1,937 本、対策後 524〜700 本）。
- 台数はフレーム費用に効かない（同時に描くのは 1 台）。最悪の首振り角と f を通して点数に効く（2 台で最大 83°・f 1,468、6 台で 71°・f 515）。カットの追加費用は無い（推定）。望遠でも投影の単価は変わらず、視線がコースに沿う（75° 以上）と f=1,500 でも柱 135 本と広角より多い（計算）。
- 楕円は見えるコーナー 1 つあたり VM 方式で +1.1／1.5／2.0 ms（10／16／24 分割）、JS 方式で +2.1／3.1／4.6 ms（推定）。大型画面が映るフレームは JS が約 2.5 ms 重い（実測、derby-background-cost）。

### 整数と倍精度（実測、2026-09-30）

整数の加算 1.59、整数の乗算とマスク 2.08、Q16 の乗算（`(s*b)>>15`）2.24、`Math.imul` 4.79（関数呼び出しで 2 倍遅い）、倍精度の加算 2.25・乗算 2.49・除算 4.86、整数×倍精度 3.46 µs。**整数は倍精度の 2 倍速くない**（加算 1.4 倍、比較 1.8 倍、乗算 1.2 倍）。型付き配列は読むのが速くならず（2.64〜2.92 µs）書き込みは遅い（3.7〜4.3）。当時は「固定小数点化の価値は低い（削れるのは 1 ms 前後）」と判断した。のちの整数化は [derby-integer.md](derby-integer.md)。

### 確信の低い点（当時）

VM 方式の単価は測定用の plan での値。JS の単価は小さなクロージャの中の測定で、実際の `course()` はもっと重くなりうる。LOD・奥の打ち切りの値は見積もりのための仮の値。

## 2. 首振りカメラ（段階 3）のゲストヒープ（旧 derby-pan-memory.md §1〜§7、host m32 の実測）

段階 3（首振り WIDE）は実機の DRAM に収まらなかった。ユーザーの問い「大規模なコードになるのか、事前コンパイルでなんとかなるか」への材料。

- **段階 3 のコードは約 3 KB（コメント抜き）だが、常駐は約 9.4 KB（コンパイル済み）、実行後は +11.1 KB**（host、評価後）。内訳はコンパイル済み 53,496（基準）→ 63,796 B、atom +35 個・+2,259 B、関数 +9 個・+2,849 B、バイトコード +3,617 B、行番号表 +624 B。大きい関数は `pan()` 1,988 B、`ser()` 1,700 B。
- **関数の固定費は小さな関数 1 つで約 200 B**（名前の atom 込み）。単発の関数を畳む得は 1 つ 150〜220 B（実測）。2 回以上呼ぶ関数は畳むと 0〜170 B の得か損。7 つ畳んで −692 B。
- **事前コンパイルは定常ヒープを減らさない**（`JS_WriteObject` → `JS_ReadObject` の常駐は 63,796 B で同一）。減るのは評価のピークだけ。**行番号表を落とすと（`STRIP_DEBUG`）アプリ全体で −3.7 KB**（段階 3 の分 −0.6 KB）。
- **plan の常駐メモリは命令数によらない**（`code[64]` 固定）。メモリに効くのは plan の本数と JS のコード。Newton を 3 → 2 回にすると最大誤差 3.8 px（LIGHT）、1 回で 40 px。
- **統合（横見も首振りの系で描く、段階 3b）**: ゲスト増 +11.1 → +6.9 KB、plan 30 → 27 本だが、実機 MID の横見 WIDE が 29.7 → 25.7 fps（JS 14.2 → 20.3 ms）に遅くなった。メモリの条件に届く道は行番号表を落とす VM の変更を足す場合だけ、と整理した。
- 受け入れ条件（`LOADSTALL` なし、ターン内の空き最小 ≥ 11,208 B、評価の余裕 ≥ 20 KB、ゲスト最大 ≤ 140 KB）は §3 以降の各表の判定に使った。

## 3. 段階 3 の外で空けた分（旧 §8、`vm/derby-trim`、2026-09-30、実機）

単発の関数を畳み（−444 B）、plan を 4 bit に詰めた文字列で持ち（−1,704 B）、描画の `[plan, 入力]` 配列をやめ、**計 −2,116 B・評価のピーク −4,896 B**。実機の前後: 評価の余裕 28,814 → 34,071 B（+5,257）、ゲスト最大 130,856 → 126,456 B（−4,400）、ターン内のネイティブ空き最小 23.3 → 30.3 KB、fps は −0.1〜−0.2。

**退行の教訓**: 詰めた plan の復号器が負号を自分の再帰（`-v()`）で読み、自己参照クロージャの循環が登録のたびに残った。実機のコレクタはゲストの上限近くまで走らないので 1 レース約 4 KB ずつ増え、2 レース目から `LOADSTALL`。host の検査はフレームごとに GC を回していて通っていた。以後、`test_derby_host` は「循環コレクタだけが解放したバイト数」を出し 0 を合格にした。

フレームごとの配列確保を減らす追加の試み（HUD の patch・`pose()` 定数化）は、ゲスト最大が増えるか基準の揺れ（±100 B）に届かないため入れなかった。2026-10-01 に plan を flash の表へ（[../kasane/flash-plan.md](../kasane/flash-plan.md) §10）置いたところ、ターン内のネイティブ空き最小 +18 KB（30.0 → 48.0 KB）、評価の余裕 +4.8 KB、レース中のゲスト最大 −6.5 KB。

## 5. 楕円コース（段階 4、旧 §12、`vm/oval`、2026-10-01）

**結論: (a)(b)(c)(d)(f) は満たした。首振り WIDE は直線 24.8〜24.9 fps（MID）、楕円の曲線区間 15.1 fps、楕円のホームストレート側（WIDE 3）18.5〜20.1 fps。** 最初の版（e574c73）は曲線区間 8.9 fps だった。補正とオッズは [derby-watch.md](derby-watch.md) の「楕円コースのカーブ補正とオッズ」。

- **区分（w=−100、推定 ms、括弧は実機の尺度）**: ネイティブへ移せる分（`ser()` 全部と `pan()` の弦の端 `VE`・選び出し `VC`）22.02（27.6）、`pan()` に残る分 4.88（6.1。走者 `rin` 1.74、距離標と走者の `pose` 14 回 1.63、`pj` 0.79）、`pan()` の外 5.02（6.3。`step` 1.75、`order` 0.81）、frame() の外の固定分 4.2。P5（ネイティブ系列ウォーカー）の設計値は移す分は当たり、残る分を低く見積もっていた（ターン 設計 14.3〜16.9 ms に対し計数から 17.8〜18.4 ms、27 fps の線は 19.1 ms で余裕は小さい）。
- 実機で測るべきとして残った項目（未測定）: `get_var` の単価、`Math.min/max/round/floor/abs/imul` の単価、配列リテラルの要素数ごとの単価、倍精度の比較と `ToInt32`、関数ごとの実時間（1.25 倍が関数ごとに同じか）、GC の頻度、固定分 4.2 ms の中身、`TURNPERF` の `I_STALL_BUSY`。

## 7. 三角関数・pose・弦の culling（旧 derby-trig-cull.md、derby-trig-cull-device.md、2026-10-01）

楕円の首振り WIDE の JS を軽くする案を host で数えて比べ（`tools/games/ovalcost/`）、一部を実機で測った。

- **三角関数より pose() の呼び出しが重い。** 実機の pose 1 回は曲線上 135 µs（sin+cos 37.4 µs）、直線の近道 26 µs、楕円の直線区間 約 70 µs（推定）。コーナーの監督で 1 フレーム pose 68〜77 回・sin+cos 111〜128 回（host 実測）、うち pose 19 回・sin+cos 32 回はレース中に変わらない弦の端（`VE`）。曲線上の pose 1 回は sin+cos 2 回、直線区間は 0 回。
- **採用した変更（B）**: 弦の端をレースごとに sin 9 個（`CH.P`）から対称性で作る＋`wide()` の先頭の pose を 1 回に。pose 68 → 49（w=−100）、sin+cos 111 → 75、画素の差 0、結果の行 479 行・画素ハッシュ 11 個が vm/main と全一致（host）。m32 のゲストは評価後 +788 B、生存ピーク +820 B、評価のピーク +572 B。**ただし 2026-10-01 時点で vm/main には入れていない**（ゲスト最大の余裕約 1 KB を食い、ネイティブ `ser()` で不要になる見込みだったため）。コードは tag `archive/trig-cull-B`（`vm/trig-cull` 15d26ed）。`tools/games/ovalcost/` の一部のツールはこの変更を前提にする。
- **不採用**: cos/sin の表（LUT）は速くならない（1 回の引き 39〜80 µs で `Math.cos`+`Math.sin` 41.8 µs とほぼ同じか遅い。誤差 0.05 px 以内の表は普通の配列で 9 KB、対称性で 440〜664 B）。型付き配列は 1 本に 0.5〜0.75 KB の固定費。g ごとのキャッシュ（`Map` の get/set が引くより高い）。弦の端の漸化式（得 0.37 ms）。「固定点を全部表に」（得 3.08 ms だがゲスト +2.9 KB、直線で 0.18 ms 遅い）。弦の端の表を double の配列で持つ形はゲスト +1.4〜2.0 KB で余裕を超えた。新しいトップレベルの名前を 1 つ足すだけで評価のピークが約 +1.5 KB 跳ねる（原因は切り分けず）。
- **画面上で小さい弦はほとんど無い**（箱が 4 px 未満の本体は 1 フレーム 0.2 本以下）ので、大きさで飛ばす・隠れる弦を飛ばす・LOD を弦に効かせる案は省けるものが無い。隣の弦の結合は T=2 で本体 15.9 → 9.9（w=−100）だが画素が 1〜7% 変わり、ゲスト +1.9 KB で入れなかった。画像: [derby-trig-cull-camera.png](derby-trig-cull-camera.png)、[derby-trig-cull-w100.png](derby-trig-cull-w100.png)・[derby-trig-cull-w14.png](derby-trig-cull-w14.png)・[derby-trig-cull-u14.png](derby-trig-cull-u14.png)（と各 gif）。
- **ネイティブ固定小数点（実装せず、誤差は host で実測・時間は推定）**: 1/4 周期の int32 Q30 の表 256 区間（flash 1,032 B、ゲスト 0 B）＋角度 Q28 で最大誤差 0.033 px。角度を Q16 rad にすると 2.3 mm の床（0.13 px から下がらない）。pose 1 回は JS 135 µs → 推定 15〜25 µs（費用の大半は JS とネイティブの境目）。より効くのは `ser()` 本体のネイティブ化（S1b）。

## 9. 登録済みコースのキャッシュと一括投影の実験（旧 derby-projection-experiment.md、2026-10-19、既定 OFF）

PR8 の normal-OFF を基準にした実験で、ここでは**実機の受入・採用は一度も主張されていない**。`main/CMakeLists.txt` の 2 つの option は現在も存在し既定 OFF。

| スイッチ | 境界 |
| --- | --- |
| `POCKET_DERBY_COURSE_CACHE` | コース登録時に固定の弦の端の world x/z と w=0 での接線を前計算し、view はカメラ変換だけにする（曲線 1 端点あたり double 4 個＝32 B。ゲームの 19 端点で +608 B、最大 32 端点で +1,024 B、直線はゼロ。既存の確保の中に置く） |
| `POCKET_DERBY_PROJECT_BATCH` | PAN の 2 回の呼び出しで終点の標と距離標 6 点＋走者 8 頭を投影し、点ごとの JS の pose/pj を置き換える。`project(progress[], depths[], subtract, Float64Array output)` が 1..32 組を読み、1 点あたり double 4 個（分子・Z・画面 x・1/Z）を書く。倍精度・式の順序は不変（FMA・逆数近似・丸めなし） |

どちらもレースの状態・乱数・カメラ選択・除算・sqrt・LOD・クリップ・並べ替え方針・手続き plan を変えない。入力の検証（getter による差し替え、detach、読み取り専用 buffer、非有限値、後ろの無効入力で途中書き込みなし）を事前に行う。

- **A/B の方法**: `python -B tools/games/run_derby_projection.py --all-tiers --out artifacts/projection`（`--tier N` で絞れる。every-call の oracle は tier 1 に付く）、`--benchmark-only` で境界のコストだけ。4 通りのスイッチ組み合わせを実際の QuickJS・実アダプタ・レンダラで ASan/UBSan 下に走らせ、全 tier で handle/入力/surface/draw 順の raw ストリームをバイト比較、フレームごとの画素・仕事量の CSV の一致、着順・時刻の一致を確かめる。MID は再生も確認し、ネイティブの各点を元の JS の pose/pj の式（符号つきゼロ含む）と直接比較する。事前検査は 19,200 点（直線・曲線・区間境界、Z=.02 の両側、0・負の深度、非有限・不正入力）。
- 最適化・非サニタイズのコストは直列に別計測（JS/native の引数と戻り値の境界込み）。サニタイズ下のヒープ観測は host モデルでの機能計測で、**S3 の CPU サイクル比・実機ヒープ・fps・採用は何も立証しない**。旧 WIDE2 の JS バイトコード割合は現在の投影割合として再利用できない。実機比較と、その前提（メタデータ・承認・キャッシュ）は保留のまま。
- 2026-10-19 の通常 main（5455a59）への統合は OFF のみで、実験スイッチ（COURSE_CACHE・PROJECT_BATCH と、現在は存在しない runner affine）は OFF、PIE の閾値 0。affine と projection を同時に有効にするのは未受入。JS の投影は整数化・Shiki への移行で不要になった（[derby-integer.md](derby-integer.md)）。
