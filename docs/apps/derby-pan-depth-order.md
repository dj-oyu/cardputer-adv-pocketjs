自然レースの再現条件（馬番号は0始まり）:

1. 実 `field(2)`・`race(F)` を使用し、楕円を指定（この seed は元から楕円）。
2. gate と同様に `rs.l = DL.slice()` と `F.k` を初期化する。
3. 実 `step(F, rs, .05)` と `at(1)` を391回呼ぶ。t=19.550000000000143。

従来の `zo` は `[6,4,7,5,2,3,1,0]`（lz 降順）。

## 最小修正と制約

`pan()` の馬のループの直前で、8頭の投影結果を配列 `ps` に保持し、
`zo` をその深度の降順へ並べ直す。描画も同じ `ps` を再利用する。
投影を比較関数の中で再計算しない。guest の pan ソース差分は +76 bytes。

中継 feed は横見カメラなので、従来の `lz` 順が必要。
**feed を描き終わってから**首振り用に並べる。
次の gate/race フレームでは既存の `at()` が `zo` を `lz` 順へ戻す。
写真は `photo(u)` が `zo.slice()` を保存し、写真場面はその保存順を復元して
`shot(4)`（pc=null）を使うため、首振りの sort は写真の保存配列を変更しない。

増えるのは投影を保持する配列1個、map/sort の callback と sort 処理。
投影計算の回数は8頭分のままだが、投影結果の配列8個が馬のループの最後まで生存する。
追加グローバル・plan・乱数・レースモデル変更は無い。
QuickJS の評価ピーク・生存 heap・fps は未測定で、余裕があるとは断定しない。
馬単位の投影基準点による描画順を直す変更であり、線分単位の隠面処理を追加するものではない。

## 公開された回帰テスト

`tools/games/test_derby_pan_order.mjs` は実ソースの model / at / photo / pose /
shot / pj / pan / course / feed を読み込む。
native の `S.view/ser` と線描画 `dr` は stub、馬の `rin` は提出記録として捕捉する。
KN はテスト用の間隔値を与える。実レンダラの画素やnative投影を検査するテストではない。

確認する契約:

- 上記 seed2/391 step の重なる馬7/5がカメラ深度の順で提出されること。
- 直線/楕円、seed 2/7/19、WIDE 1/2/3、LIGHT/MID/HEAVY、
  9個のステップ位置と補間 u=0/.5/1、中継あり/なしで提出順が投影深度の降順であること。
- 投影 X・縮尺・地面位置・可視条件が変わらず、投影再計算を sort 比較のたびに増やさないこと。
- 実 `course/feed` が提出した中継の馬は、元の横位置順を保つこと。
- 首振りの sort が写真の保存順を変更せず、同じ seed の再走で同じ提出順になること。

cloud のツール内 V8 に同じテスト本体と実ソースを渡して実行した結果:

- 修正前: `pan must draw far to near in camera depth` で失敗。
  実際 `[6,4,7,5,2,3,1,0]`、期待 `[4,2,6,1,0,3,5,7]`。
- 修正後: 2,923 フレーム、23,384 頭の提出、1,465 件の馬のある中継で PASS。
- PR5 の sway 修正と組み合わせても同じ件数で PASS。
- sort を feed より前へ移す誤修正をテスト内で一時適用すると、
  `side-view feed retains lateral-depth order` で失敗することも確認した（製品コードには未適用）。
