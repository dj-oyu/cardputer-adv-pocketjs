# DERBY WATCH: JS から double を無くす（整数化の設計）

2026-11-01、ブランチ `claude/epic-ptolemy-wyvhym`。**設計（実装前）。数値は断りのない限り推定。** SLOW のレビュー（§8）を受けて改訂済み。

## 0. 動機と決定

- DERBY の走者は Shiki の式になった（[README](../../apps/derby/README.md)「走者と正面の馬を Shiki で」）。表示側の `sin` も `shiki.sin/cos/sinMany` に移したが、JS の値が double なので、渡す前に `r * TQ | 0` のような double→int の変換が JS に残った。
- 利用者の決定（2026-11-01）: **double の値は伝播するので、データの持ち方を根本から整数にする。範囲は「すべて」** ── レースのモデル、カメラ、投影、背景の旧 API（`@plan`）の入力、走者（Shiki）まで。同じ seed でもレースの結果が変わること、オッズの再較正と host の記録の作り直しを受け入れる。

## 1. 受け入れ条件

1. **frame() の float の演算は、列挙した境目だけ。** host の bytecode 計装（`tools/vmtest/opprof`、`float_count.py`）で、DERBY の全チャンクの `frame()` の窓の float の (op, 型) の組が、§4.2 の表の境目の分だけ。前（§2）と後の表を残す。
2. **静的検査が 0。** `tools/games/derby_int_lint.mjs --strict`（`@plan`/`@shiki` の本体とコメントの外の `/`・小数の定数・`Math` の小数を返す関数・`Float64Array`）が 0 件。opprof は call を呼ばれる側の種類で分類し、引数の型を持たないので、`Math` の関数はこの検査が受け持つ。
3. **ネイティブの境目に double を渡さない。** `H.draw`・`SK.drawMany`・`pocket.derby.*`・`setRect` などに渡る数値がすべて `JS_TAG_INT`（host の harness で数える）。`drawMany` の入力は `Int32Array` だけ。
4. **起動・レースの準備（`field`・`odds`・`race`・`step`）も整数**（1〜3 を評価中・`enter()` を含む全区間で）。
5. **レースのモデルの性質を保つ。** 整数モデルで tune（`tools/games/tune_derby.mjs`）を回し、勝率・オッズの較正・払い戻し率・入れ替わりの指標が旧モデルの記録（[derby-watch.md](derby-watch.md)、[derby-corner-model.md](derby-corner-model.md)）と同じ範囲に入る。範囲は段階 4 の前に数値で決める。大穴のオッズは Q16 の量子化で約 3% 動き得る（§5.4）。
6. **画素。** 表示の段階（1〜3）はレースを変えないので、旧版と同じレースで画素を比べ、差の分布を記録する（丸めの 1 px 程度のはず）。モデルの段階（4）から新しい基準。
7. **メモリと速さ（実機）。** 評価の余裕・ゲストの最大が今（[README](../../apps/derby/README.md) の実機の記録）より悪くならない（許容 −2 KB）。各カメラの JS ターンが今以下。

## 4. QuickJS で整数のままでいる規則

### 4.1 演算

`JS_TAG_INT`（int32）の値は、次の演算でだけ int のまま残る（quickjs-ng の `OP_*` の速い道、`quickjs.c` 22320 行付近）。

| 演算 | int のまま | double になる |
| --- | --- | --- |
| `+` `-` | 結果が int32 に収まる | あふれ |
| `*` | 結果が int32 に収まり、**-0 でない** | あふれ、`0 * 負` |
| 単項 `-` | `x ≠ 0` | `x = 0`（−0） |
| `/` | — | **常に double の割り算**（割り切れれば int に戻すが、計算は double） |
| `%` | 左が 0 以上、右が正 | 左が負は遅い道（結果は −0 以外 int） |
| `>>` `<<` `&` `\|` `^` `Math.imul` | 常に int32 | — |
| `>>>` | 結果が 2^31 未満 | 2^31 以上（double で持つ） |
| `Math.floor/ceil/round` | 引数が int | 引数が double（整数値なら int に戻るが、計算は double） |

規則:
- **`/` を使わない。** 割り算は §5.2 の行き先へ。
- **積は `|a·b| < 2^31` を表（§5.1）で示せるものだけ `*` で書く。** `Math.imul` は下位 32 bit なので、あふれる積の `>> 16` にはならない（QuickJS に 64 bit 整数の道は無い）。示せない積は差分（1 に近い係数は `v + ((v * (m − 65536)) >> 16)`）か、16 bit への分割で書く。分割を関数にすると呼び出しが約 4.4 µs（[derby-pan-camera-cost.md](derby-pan-camera-cost.md) §1 の実測）で double の乗算（約 2.5 µs）より高いので、**毎フレームの経路では、分割が要る積を作らない単位を選ぶ。** 範囲は段階ごとに host で全レースの最大値を記録して検める。
- 0 になり得る値に単項 `-` を付けない。剰余は 2 の冪なら `&`、それ以外は左を 0 以上にしてから `%`。
- 小数の定数を書かない。乱数は `>>> 2` で 2^30 未満に収める。

### 4.2 許す境目（ネイティブが double を返す値）

| 値 | 所 | 扱い |
| --- | --- | --- |
| `pocket.time.now()`（ms、double） | `attract()`（幕・デモの時計） | 1 フレーム 1 回 `\| 0`（起動からの差だけを使う） |
| `pocket.random.seed()` | 起動時 1 回 | `\| 0` |
| モデルの出力（段階 1〜3 の間だけ） | `at()` の入口、1 ステップ 8 回 | 位置を Q16 m の int に。段階 4 で消える |

opprof の float の組は、この表の分だけ残る。

## 5. 単位と割り算の行き先

### 5.1 単位（2 進の固定小数点）

**長さは 2 進の固定小数の m** にする（mm だと m への変換が 1000 の割り算になる。下流の `pose`・`CAMS`・`pocket.derby`・`run` の `sin(d * 1.93328)` は m）。

| 量 | 単位 | 範囲 | 備考 |
| --- | --- | --- | --- |
| 位置（モデル・表示） | Q16 m | 0〜約 1,100 m（7.2×10^7） | 分解能 15 µm |
| 速さ（モデル） | 1 ステップあたり Q16 m（`DT` を畳む） | 0〜約 0.9 m（5.9×10^4） | `x += v` |
| 楕円の乗数 `m` | 1 との差 `δ`、Q16 | ±1,500 | `x += v + ((v * δ) >> 16)`、積は 9×10^7 |
| 体力 `e`・係数 | Q16 | — | 消耗は `(v − vth) · k`（`vth`・`k` は馬ごとに準備で 1 回、§5.4） |
| 時刻 | ステップ数（int）、着の時刻は Q16 ステップ | — | |
| 乱数 | `rng()` は 0〜2^30−1 | — | `r() < .0006` は `r() < 644245` |
| 角 | Q16 の回転数 | — | `shiki.sin/cos/sinMany` と同じ |
| 画面の座標（旧 API の入力） | Q4 px | ±32,768 px | plan の側で `>> 4` 相当 |
| 焦点距離 `f` | px（int） | 3〜1,500 | |

背景の投影（JS、定数の奥行き）は、`(w − x0)` を Q8 m に落とし、`f · (1/d0)` を Q8 の整数の定数との積にして、積が 2^31 未満の範囲を表で示す（段階 3）。

### 5.2 割り算の行き先

| 割り算 | 頻度 | 行き先 |
| --- | --- | --- |
| 定数の奥行き（40 m、`DFR`、`DNR`、`VS[1]`）での投影 `f / d0` | 毎フレーム数回 | 定数の逆数（整数）との積 |
| 走者の投影 `f / lz[l]`（横）、`pj()` の `Z`・`1/Z`（首振り）、HEAD ON の `400 / (D + 12 − x)` | 毎フレーム 8 | **`pocket.derby` の C**（整数で入れ、`Int32Array` に Q4 px・Q16 の縮尺で返す。C の中は int64 と整数除算が使える） |
| 首振りの距離標・大型画面の 4 隅 | 毎フレーム 5 + 2 | 同上 |
| カメラ `f` の逆数・首振りの単位ベクトル（`sqrt` と割り算） | 毎フレーム 1 | 同上（`view` の中） |
| モデル: `v / h.top`、`(D − x) / (y − x)`、オッズの `z / p[i]` | 準備・着ごと | JS の整数の長除法（§5.4）。準備で馬ごとに 1 回、着で 8 回、オッズで 8 回 |
| 時間の割合（幕の `fa`、PHOTO の拡大、パドックの棒） | 毎フレーム 1〜3 | 分母が定数なので逆数の積 |

**Shiki に除算は足さない。** 当初の案（`DIV` を v1.5 に足し、投影だけの式 `proj` がデータ領域に書いて `run`・`legs` が読む）は、(1) `FETCH`/`PUT` は `EACH` のカーソルのレコードしか触れず、レーンごとの draw がレーン `l` のレコードを読み書きできない（[shiki-spec.md](../kasane/shiki-spec.md) §5.2〜§5.4、`ksn_shiki.c` の登録時の検査）、(2) 64 bit の中間を持つ割り算は「実行時の割り算は 32 bit ÷ 32 bit」の決定（同 §2.2）と衝突し、`b = 0` の `INVALID` はフレーム全体を捨てる、ので取り下げた。投影は `pocket.derby`（DERBY だけの面）の C で行い、Shiki の v1.5 は変えない。

`pocket.derby` の今の C は、JS の倍精度の演算の順をビット単位で再現する契約（`pocket_derby.c` の冒頭、oracle は `derby_ser_oracle.js`・`derby_project_oracle.js`・`run_derby_projection.py`）。整数の入出力にした所は、この oracle を整数の参照に作り直す（段階 2）。`ser` の内部の倍精度（soft-float）を整数にするかは、段階 3 の後に費用を測って決める（目標は「JS から double を無くす」。C の中の double は別の課題）。

### 5.3 旧 API の `@plan`（背景）

入力を Q4 の整数で受け、式の中で `>> 4` 相当に直す（plan ごとに入力の単位を書き換える。18 本）。投影の割り算が要る plan は無い（JS が定数の逆数で済ませる、§5.2）。ダストの位相は Q16 の回転数で渡す。

### 5.4 JS の整数の除算・平方根・指数

レースの準備と着の判定に、変数での除算が残る。**シフトと減算の長除法 `idiv(a, b)`**（int だけ、24 回程度のループ）、整数の Newton の `isqrt`、`exp2`（2 の冪と小さな表、Q16）を持つ。毎フレームの経路では使わない。準備（`enter('pad')`）と `settle()` でだけ使うので、**別のチャンクに置き、評価のピークに乗せない。**

オッズ（Luce）は `exp(a_i − a_max)` に書き直す（今の `M.exp(≈298)` は Q16 で表せない）。最小の重み e^−7.6 は Q16 で 33 なので、大穴のオッズは約 3% 動き得る（受け入れ条件 5）。

## 7. 危うい所

- **ヒープ。** CLAUDE.md の記録でゲスト最大 134.1〜134.8 KB（140,000 B まで約 5.2 KB）。整数の書き方はソースが長くなる。`idiv` 系は別チャンク。段階ごとに `APP_LOAD` の `used` と host の評価のピークを記録する。
- **速さ。** 整数の演算は QuickJS で double より安いが、分割の乗算や長除法を毎フレームに置けば逆になる（§4.1）。段階ごとに opprof の全命令数も見る。
- **モデルの性質。** 量子化で接戦の判定（`DEAD HEAT` の 0.02 m）や `sb` の減速の発生率が変わり得る。tune の指標で確かめる。
- **旧 API の plan の入力の単位の書き換え**は plan ごとに画素の確認が要る（18 本）。
- 段階 4 でレースが変わるので、host の記録（着順・時計・seed の表、`tools/games` の期待値）を作り直す。
