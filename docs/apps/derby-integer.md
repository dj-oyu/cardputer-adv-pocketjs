# DERBY WATCH: JS から double を無くす（整数化の設計）

2026-11-01、ブランチ `claude/epic-ptolemy-wyvhym`。**設計（実装前）。数値は断りのない限り推定。**

## 0. 動機と決定

- DERBY の走者は Shiki の式になった（[README](../../apps/derby/README.md)「走者と正面の馬を Shiki で」）。表示側の `sin` も `shiki.sin/cos/sinMany` に移したが、JS の値が double なので、渡す前に `r * TQ | 0` のような double→int の変換が JS に残った。
- 利用者の決定（2026-11-01）: **double の値は伝播するので、データの持ち方を根本から整数にする。範囲は「すべて」** ── レースのモデル、カメラ、投影、背景の旧 API（`@plan`）の入力、走者（Shiki）まで。同じ seed でもレースの結果が変わること、オッズの再較正と host の記録の作り直しを受け入れる。

## 1. 受け入れ条件

1. **frame() の中で float の演算が 0。** host の bytecode 計装（`tools/vmtest/opprof`、`opprof_ty.py` の (op, 型) の組）で、DERBY の全チャンクの `frame()` の窓に `float` の型の算術・比較、float の配列要素、`Math` の浮動小数点の関数（`sin` `cos` `sqrt` `pow` `exp` `floor` `ceil` `round` の float 引数）が 1 件も無い。前（§2）と後の表を残す。
2. **ネイティブの境目に double が来ない。** `H.draw`・`SK.drawMany`・`pocket.derby.*`・`setRect` などに渡る数値がすべて `JS_TAG_INT`（host の harness で数える）。`drawMany` の入力は `Int32Array` だけ。
3. **起動・レースの準備（`field`・`odds`・`race`・`step`）も整数。** 評価中と `enter()` を含む全区間で 1. と同じ計数を取り、0 件。
4. **レースのモデルの性質を保つ。** 新しい整数モデルで tune（`tools/games/tune_derby.mjs`）を回し、勝率・オッズの較正・払い戻し率・入れ替わりの指標が旧モデルの記録（[derby-watch.md](derby-watch.md)、[derby-corner-model.md](derby-corner-model.md)）と同じ範囲に入る。範囲は §6 の段階 2 で数値で決める。
5. **画素は新しい基準。** 旧版との全画素一致は求めない。host の画像（各カメラ・楕円・HEAD ON・PHOTO）を旧版と並べ、目で差を確かめる。
6. **メモリと速さ（実機）。** 評価の余裕・ゲストの最大が今（[README](../../apps/derby/README.md) の実機の記録）より悪くならない（許容 −2 KB）。各カメラの JS ターンが今以下。

## 4. QuickJS で整数のままでいる規則

`JS_TAG_INT`（int32）の値は、次の演算でだけ int のまま残る（quickjs-ng の `OP_*` の速い道、`quickjs.c`）。

| 演算 | int のまま | double になる |
| --- | --- | --- |
| `+` `-` | 結果が int32 に収まる | あふれ |
| `*` | 結果が int32 に収まり、**-0 でない** | あふれ、`0 * 負` |
| `/` | — | **常に double の割り算**（割り切れれば int に戻すが、計算は double） |
| `%` | 左が 0 以上、右が正 | 左が負（-0 の扱いで遅い道へ） |
| `>>` `<<` `&` `\|` `^` `Math.imul` | 常に int32 | — |
| `>>>` | 結果が 2^31 未満 | 2^31 以上（double で持つ） |
| `Math.floor/ceil/round/abs/min/max` | 引数が int | 引数が double |

規則:
- **`/` を使わない。** 割り算は §5 の行き先へ。
- 積は範囲を確かめた `*`、あふれ得るものは `Math.imul` と `>>`。`0 * 負` を避ける（符号付きの積が 0 になり得る所は `Math.imul`）。
- 剰余は 2 の冪なら `&`、それ以外は左を 0 以上にしてから `%`。
- 小数の定数を書かない（`.5` `1.085` など）。固定小数点の整数の定数にする。
- 文字列への変換（HUD）は整数から（`'' + (n / 10 | 0)` のような書き方もしない。§5.4 の整数の除算か、表示用の桁分け）。

## 5. 単位と割り算の行き先

### 5.1 単位（固定小数点）

| 量 | 単位 | 範囲 | 備考 |
| --- | --- | --- | --- |
| モデルの位置 `x` | 1/256 mm（Q8 mm） | 0〜約 1.1×10^6 mm（2.8×10^8） | int32 の上限 8,388 m |
| モデルの速さ `v` | 1 ステップあたり Q8 mm（`DT` を畳む） | 0〜約 0.9 m/ステップ（2.3×10^5） | `x += v` |
| 時刻 | ステップ数（int）、着の時刻は Q16 ステップ | — | `tc` |
| 体力 `e`・係数 | Q16 | — | |
| 乱数 | `rng()` は 0〜2^30−1 の int（SMI に収める） | — | `r() < .0006` は `r() < 644245` |
| 表示の位置 | mm | — | モデルの `x >> 8` |
| 角 | Q16 の回転数 | — | `shiki.sin/cos/sinMany` と同じ |
| 画面の座標（旧 API の入力） | 1/16 px（Q4） | ±32,768 px | plan の側で `>> 4` 相当（§5.3） |
| 焦点距離 `f` | px（int） | 3〜1,500 | |

各式の値の範囲（積のあふれ）は実装で表にし、host で全レースの最大値を記録して検める。

### 5.2 割り算の行き先

| 割り算 | 頻度 | 行き先 |
| --- | --- | --- |
| 定数の奥行き（40 m、`DFR`、`DNR`、`VS[1]`）での投影 `f / d0` | 毎フレーム数回 | **定数の逆数（Q16 の整数）との積**。 |
| 走者の投影 `f / lz[l]`（レーンごと、揺れで連続に変わる） | 毎フレーム 8 | **Shiki の式の中**（§5.3）。 |
| HEAD ON の `400 / (D + 12 - x)` | 毎フレーム 8 | 同上（`frl`・`frb` の中）。 |
| 首振りの `pj()`（`Z` と `1 / Z`）: 走者・距離標・大型画面 | 毎フレーム 8 + 5 + 2 | **`pocket.derby` の C**（すでに `project` の原型がある）。整数で入れ、整数（Q4 px）で返す。 |
| カメラ `f` の逆数・首振りの単位ベクトル（`sqrt` と割り算） | カットごと〜毎フレーム 1 | **`pocket.derby` の C**、または JS の整数の除算（§5.4）。 |
| モデル: `v / h.top`、`(D - x) / (y - x)`、オッズの `z / p[i]` | レースの準備・着ごと | `h.top` の逆数をレースの準備で 1 回（§5.4）、着の時刻は 8 回、オッズは 8 回。 |
| 時間の割合（幕の `fa`、PHOTO の拡大、パドックの棒） | 毎フレーム 1〜3 | 分母が定数なので逆数の積。 |

### 5.3 Shiki に割り算を足す（v1.5 の追加）

Shiki にも旧 API の VM にも除算命令が無い（[shiki-spec.md](../kasane/shiki-spec.md) §3、`ksn_procedural.h`）。走者の投影を式に入れるには次のどちらか。

- **案 A（推奨）: `DIV dst, a, b, aux=s` を v1.5 に足す。** `r[dst] = (r[a] << s) / r[b]`（0 へ切り捨て、64 bit の中間、`b = 0` は `INVALID`、結果が int32 の外は飽和）。ESP32-S3 の整数除算命令（`QUOS`）で数十 cycle。参照実装（`shiki_ref.mjs`）・コンパイラ（`/` を `DIV` に）・host の比較・実機の検査を足す。**v1.5 は未凍結なので、ここに入れる。**
- 案 B: 逆数を `LOOKUP` の表（奥行きの刻み）から引き、Newton 1 回（`MUL` 2・`SUB` 1）。命令は増えないが、表のデータ領域と奥行きの範囲の前提が要る。

走者の式（`run` 42 命令・`legs` 59 命令、上限 64）に投影を足すと `legs` があふれる。**投影だけの式 `proj` を 1 本作り、レーンごとの `X`・`S`・`Y`（と可視の旗）をデータ領域に `PUT`、`run`・`legs` は `FETCH` で読む。** `drawMany` の順は `proj`×8 → 走者。首振りのとき（§5.2 の `pocket.derby`）は C が同じ領域の形で書く案と、`proj` の首振り版を作る案を段階 4 で比べる。

旧 API の `@plan`（背景）は入力を Q4 の整数で受け、式の中で `>> 4` 相当に直す（plan ごとに入力の単位を書き換える）。投影の割り算が要る plan は無い（JS が定数の逆数で済ませる、§5.2）。

### 5.4 JS の整数の除算

レースの準備と表示の一部に、変数での除算が残る（`h.top` の逆数、着の時刻、オッズ、HUD の桁）。JS の `/` は double なので、**シフトと減算の長除法 `idiv(a, b)`**（int だけ、24 回程度のループ）を 1 本持つ。毎フレームの経路では使わない（使う所は表にして opprof で回数を数える）。`sqrt` は整数の Newton（`isqrt`）、`exp` は 2 の冪と小さな表（`exp2` の Q16）。

## 7. 危うい所

- **ヒープ。** 整数の書き方（`Math.imul(a, b) >> 16`）はソースが長くなり、評価のピークを押し上げる（DERBY は余裕が約 22〜28 KB）。段階ごとに `APP_LOAD` の `used` を見て、増えた分を記録する。
- **モデルの性質。** 量子化（1/256 mm、Q16）で、接戦の判定（`DEAD HEAT` の 0.02 m）や `sb` の減速の発生率が変わり得る。tune の指標で確かめる。
- **`pocket.derby` の C** は内部が倍精度（soft-float）のまま。入出力を整数にした後、内部の整数化は別の段階として残すか、ここで行うかを段階 4 で決める。
- **旧 API の plan の入力の単位の書き換え**は plan ごとに画素の確認が要る（18 本）。
- 段階 2 でレースが変わるので、host の記録（着順・時計・seed の表、`tools/games` の期待値）を作り直す。
