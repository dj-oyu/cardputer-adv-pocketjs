# Experimental PAN runner submission batch

The normal build and shipping JS are unchanged. The host command
`python tools/games/run_derby.py --runner-batch --heap-limit 524288` enables
`POCKET_DERBY_RUNNER_BATCH` and generates an alternative PAN chunk. This is a
bridge experiment, not a claim of faster device rendering.

Scope: actual JS `at`, sway, pose, projection, stable camera-depth sorting,
screen feed, photo copies, racecore, seed, clock and finish remain in place.
Only the PAN visible-runner loop packs submissions instead of calling `rin`
separately. Feed/side/closeup/HEADON and the existing native series are unchanged.
The same procedural runner IR/VM receives the same eight numeric inputs.

`pocket.derby.runners(buffer, count)` accepts an ordinary ArrayBuffer of exactly
320 bytes and an integer count 0..8. The buffer has eight native-endian float64
records `[planHandle, X, scale, groundY, phase]`. JS uses one reusable
Float64Array(40), passing its whole `.buffer`; typed-array views, shared buffers
and offsets are not accepted. A subview's `.buffer` still denotes its whole
buffer, never its offset. Both supported host and ESP32-S3 use little endian.

The API copies the full 320 bytes to bounded stack storage before any draw or
guest call. Alignment is immaterial to memcpy. It retains no guest pointer or
handle, reads current buffer length on each invocation, and rejects detached or
wrong-size resized buffers. Count and used input fields must be finite; handles
are integers 0..INT32_MAX (0 skips the draw). Unused tail rows are ignored.
All layout/number checks happen before drawing. Stale/foreign handle validation,
frame ownership, derived overflow and VM errors use the existing procedural draw
path without interception. An error in a later draw can follow earlier submitted
draws, and stops the batch with the original exception. This is sequential
submission, not an atomic frame transaction.

`rin`'s exact expression and double operation order are preserved, with no
float32 geometry change, SIMD, fixed point or hidden error tolerance. The
existing final double-to-float procedural conversion is unchanged. The native
source retains `-ffp-contract=off`; 64-bit QuickJS/native tests compare double
inputs bit for bit. m32 x87 is useful for object-size/heap checks, not a bitwise
double arithmetic oracle.

At N visible horses this replaces N H.draw crossings (9 numeric arguments per
horse) and five JS Math.sin calls per horse with one ArrayBuffer/count crossing.
The JS writes 5N doubles and C snapshots 40 doubles, then performs the same 5N
sin computations and N procedural draws. Pose/projection/sort and their existing
temporary arrays are deliberately still JS. There is a persistent 320-byte data
buffer plus typed-array/ArrayBuffer objects and generated bytecode; report actual
heap deltas rather than assuming batching is free. Native adds a 320-byte local
snapshot and the existing eight-double draw array. Neither device speedup nor an
adoption threshold has been established.

Validation:

- `python tools/games/test_derby_runner_batch.py` runs the actual transformed PAN
  through all 2,923 camera/feed/order/photo cases; generation fails on source drift.
- `run_derby.py --runner-batch --heap-limit 524288` runs real QuickJS/native and
  renderer with ASan/UBSan, compares actual app rin expressions bit for bit,
  exercises 2,000 randomized batches and boundary/error cases. Oracle allocation
  is test-only, so its heap is not an experiment footprint measurement.
- `python tools/games/compare_derby_runner_batch.py` builds OFF/ON, runs the same
  scripted MID game without oracle instrumentation, requires identical complete
  pixel hash, captured panel bytes and finish result, and reports both guest heap
  summaries. Host execution time is not device throughput.

No USB, flash, device input or remote job is part of these tests. A device
candidate needs same-head CI/build provenance and a reserved formal comparison;
successive experiments must not flash another version into an active trial.

Initial local host evidence (64-bit MID, ASan, oracle disabled): all-frame
pixel hash `4f063ab172c34803`, all 40 captured panels and race finish agree.
Reported eval peak/after-eval grow by 2,704 bytes; reported live peak grows
by 2,220 bytes and whole-run peak by 2,028 bytes. These are the harness TLSF
model, not device heap readings. The complete opt-in footprint is therefore
larger than the 320-byte payload. Device speed and the adoption decision remain
open pending separate instrumentation/comparison.

Device opt-in: `POCKET_DERBY_RUNNER_BATCH=ON` generates only the PAN alternative,
adds the native method and runs a mandatory ALL proof on every successful
build, including incremental builds. The proof checks actual ELF symbols and
embedded PAN bytes plus the IDF BIN's embedded ELF hash; no `.git` is required.
Configuration and proof imports use Python `-B`, preserving source snapshots.
It composes with telemetry by preserving that generated play chunk. Both
options default OFF; alternative bgcost/heapprobe chunks are refused. The
separate target workflow checks OFF/ON firmware and host equivalence; ordinary
shipping chunk bytes remain unchanged.
