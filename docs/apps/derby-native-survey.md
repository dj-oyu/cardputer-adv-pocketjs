# DERBY WATCH: ネイティブ（C）に下ろす候補の洗い出し（設計・調査）

2026-10-01、ブランチ `vm/native-survey`（`vm/main` cb83ebc から）。**設計と調査だけで、アプリ（`apps/`）と `main/` は変えていない。実機（COM3）は使っていない。ビルドも新しい測定もしていない。** 対象は楕円コーナーの首振り WIDE 2（実機 MID 16.1 fps・JS 44.25 ms）。何をどの順で native にするかをユーザーが決めるための材料を並べる。

数値の種類は 3 つに分ける。

- **実測（実機）**: 既存の文書の値。出典を付ける。
- **計数（host）**: [derby-wide2-profile.md](derby-wide2-profile.md)（以下「計数」）と `vm/trig-cull` の derby-trig-cull.md（`git show vm/trig-cull:docs/apps/derby-trig-cull.md`、以下「trig-cull」）が数えた回数。
- **推定**: 計数 × 単価、較正式「実機 = 1.253 × 推定 + 4.22 ms」（計数 §4）での換算、まだ無いコードの見積もり。**この文書の ms・fps・KB・人日は、出典を付けた実測以外はすべて推定。**

この文書で「実機の尺度」と書く ms は、ベンチの単価での推定に 1.253 を掛けた値。較正式は 4 構成（実質 3 点）の合計への当てはめで、関数ごとに同じ倍率とは限らない（`pose` 1.15 倍、`Math.sin` 1.55 倍。計数 §4・§7）。

## 1. 結論

1. **候補は 30 個**（§3）。native の API として採る価値があるのは 6 個: 系列のウォーカー（N1）、道の登録と `pose`／一括投影（N4・N5）、`draw` の数値引数（N12）、走者の脚を plan へ（N6）、および N1 の代わりか前段になる `ser()` の C 直訳（N2）。残りは「N1 で消える」「JS だけで足りる」「得が小さい」「決定論を壊す」のどれか。
2. **利得の大きい順**（w=−100、実機の尺度、推定）: N1 ウォーカー −25.8〜−26.4 ms、N2 `ser()` の直訳 −19〜−23 ms、N3 弦の端と選び出しだけ 約 −6 ms、N4 `pose` 単発 −3.9〜−7.3 ms、N5 一括投影 −2.6〜−2.8 ms（N1 の後に残る分に対して）、N10 `step()` −1.8〜−2.0 ms（**不採用**: 決定論）、N6 走者の脚 −0.7〜−0.9 ms、N12 数値引数の `draw` −0.8 ms（N1 の後は −0.25 ms）。
3. **`ser()` に触らない限り 20 fps に届かない。** `pose`・投影・配列を全部 native にしても 17.9〜19.0 fps（シナリオ S1a）。20 fps 台の最小は `ser()` の C 直訳（S1b、23〜26 fps、4〜6 人日）。
4. **27 fps は、ウォーカーだけだと境目**（27.5〜28.0 fps。フレームの非 JS 分が 19.2 ms なら届かない）。走者の脚（N6）を足すと 28.3〜29.0 fps、残りの投影（N5）まで入れると表示の上限（33 ms 周期、約 30 fps）に当たる見込み。w=−3（u=14）でも、ウォーカーの後は差が 1 ms 以内になる。
5. **API は「道（path）を登録し、それを 3 つの入口が共有する」形を勧める**（§5 の案 B＋C の小さい部品）: `H.path()`（登録）、`H.pose()`／`H.project()`（点の投影、倍精度で画素を変えない）、`H.walk()`（系列、float32）。DERBY 専用の native（案 A）は最終形にしない。ただし N2 は、画素を変えずに 20 fps 台へ上げる中間段として成り立つ。
6. ゲストのヒープは、N1・N2 のどちらでも −3〜−6 KB（推定。現在の最大は実測 138.9 KB で、140,000 B まで約 1.0 KB）。それ以外の候補は ±0.5 KB 以内。

### 3.3 採らない・後回しの候補

| # | 内容 | 理由 |
| --- | --- | --- |
| N10 | `step()`（レースのモデル、2.2 ms）を native に | **決定論を壊す危険に対して得が小さい。** 着順・時計は倍精度の演算順で全桁が決まり、種・デモ・R 再生・保存がそれに依る。C に写すと、コンパイラの定数の畳み込みや host（i386）の中間精度で 1 bit ずれうる。状態（`rs.x`・`rs.v` など）を JS が読むので境目の費用も残る。DERBY 専用で再利用も無い |
| N13 | `draw` ごとの plan の写しと検証（native 約 12 µs）を登録時だけに | 今 −0.25 ms、N1 の後 −0.09 ms。「検証したものだけを実行する」という今の保証を崩す割に小さい |

命令の種類の側: 基本の命令 42% と並べ替え 18% は関数に付いて動く（上の対応のとおり）。倍精度の算術 19% は N1・N2 で大半が移り、残りは N17。`get_var` 8.1% は N16、配列の読み 8.1% と配列リテラルは N18・N12・N5、`Math` 466 回は N1・N6・N4・N15。

## 4. 組み合わせと順序

### 4.1 依存関係

- **共通の基盤は「道の登録」**（区間の表を native が持つ）。N1・N4・N5 が同じ表を使う。N4 を先に入れても、N1 のときに捨てる部分が無い。
- **N1 と N2 は排他**（同じ JS を移す）。N2 を先に入れて後で N1 に替えると、N2 の C（2〜3 KB）は捨てることになる。plan の書き直し（「1 点ぶんの絵」）は N1 だけに要る。
- N1 を入れると不要になるもの: N3、N19、N20、N29、trig-cull の `CH.P`。N12 と N13 の得は 3 分の 1 になる。
- N6 は誰にも依らない。ただし走者の画素を変えるので、基準の作り直しを N1 と同じ回にまとめる。
- N5 は N4 の上に載る（同じ計算を n 点ぶん回すだけ）。

### 4.3 27 fps に届くかの感度

ウォーカーだけ（N1 単独）は 17.8〜18.4 ms で、線（19.1 ms）まで 0.7〜1.3 ms しかない。外れると届かなくなる条件:

| 何が外れるか | 届かなくなる境目 | 見立て |
| --- | --- | --- |
| フレームの非 JS 分 | 17.9 ms → 18.6〜19.2 ms 以上 | 17.9 は P24 の実測 1 回からの逆算、19.2 は以前の 2 点。**どちらかは実機でしか決まらない** |
| 残る JS の倍率（較正の 1.253） | 1.33〜1.39 以上 | `Math.sin` は 1.55 倍、`pose` は 1.15 倍（計数 §4）。残る JS は `rin`（`sin` 40 回）と `step` が主なので、高い側に寄る恐れがある |
| ウォーカーの native（0.7〜1.3 ms の見積もり） | 2.0 ms 以上 | 1 点の本体を 8〜12 ステップと置いた値。plan の書き直しは未試作 |
| 命令キャッシュ | — | 同じカーネルがビルド間で 15% 動く（CLAUDE.md）。JS のターンへの効きは未測定だが、18 ms の数 % で余裕が消える |
| 監督のカメラ | `wide()` の `pose` 6 回で +0.9 ms | 計数は WIDE 2 を手動で保った。N9（JS のキャッシュ）で消せる |

別の向きからの確かめ: 直線の横見 WIDE（MID）の実測は 14.51 ms で、中身は `step`・`order`・走者 8 頭・HUD・横見の背景。ウォーカーの後の首振りは「これ − 横見の背景の JS ＋ 距離標と走者の投影 3.0 ＋ ウォーカー 1.2〜1.75」に当たり、16〜17 ms 前後になる（推定）。17.8〜18.4 ms はこれより少し重い側で、桁は合っている。

**S2（N1＋N6）は線まで 1.7〜2.5 ms、S3 は 4.8〜5.8 ms の余裕**がある。S3 は残る JS の倍率が 2.0 になっても線の内側。27 fps を「確実に」と言えるのは S3 だけで、S2 は非 JS 分が 19.2 ms なら 27.3〜27.9 fps と境目に残る。

w=−3: 今は +8.8 ms（53.0 ms、推定）だが、増える分はほぼ全部が系列（36.3 ms）なので、N1 の後は native の点が増える分（+0.3〜0.6 ms）だけになる。**w=−3 にするかどうかは、N1 を入れるなら fps では決まらない**（見た目で決められる）。N1 を入れない S1a では 15.6〜16.4 fps、S1b では 22.0〜24.9 fps で、w=−100 より 1.5〜2.5 fps 低い。

## 5. API の形の比較

### 5.1 3 つの案

| | A: DERBY 専用の native | B: 道に沿って plan の本体を繰り返す汎用部品 | C: 低いレベルの部品の組み合わせ |
| --- | --- | --- | --- |
| 中身 | N2。`ser()` を C に写し、DERBY の plan の入力の並びを知っている | N1。`H.path()` と `H.walk(plan, path, camera, options)` | N4・N5・N12。`H.pose()`・`H.project()`・数値引数の `draw`。切り出しと LOD は JS に残る |
| 1 フレームの境目の呼び出し | 5 回（引数 8 個ずつ） | 5〜6 回（カメラ 6 個＋オプション 7 個） | 投影 5〜10 回＋ draw 31.6 回 |
| 単独で届く fps（w=−100） | 23〜26 | 27.5〜28.0 | 17.9〜19.0 |
| ゲスト | −3〜−6 KB | −3〜−6 KB | ±0.5 KB |
| 画素 | 変えない見込み | 変わる | 変えない見込み |
| 再利用 | 無い。DERBY の plan と入力の並びに固定 | 奥行きのある道を描くアプリ（下） | 点を投影するアプリ一般。数値引数の `draw` は全アプリ |
| 保守 | JS と C の 2 か所に同じ規則（plan の入力の並び、LOD の式）。片方だけ変えると壊れる | 規則は native に 1 か所。plan は「1 点ぶんの絵」で短くなる | 小さい。関数ごとに閉じている |
| 複数コース・複数カメラ | コースの形（楕円の区間の表）も C に入れるか、引数で渡す | 道は登録で何本でも、カメラは呼び出しごとの引数 | 同じ |
| 契約の置き場所 | 共通 API には入れられない（[common-api.md](../api/common-api.md) §2「アプリ固有の面は共通APIに含めない」）。`pocket.pet`（capability `pet.companion`）と同じく、DERBY のセッションにだけ注入する面にする。前例はもう 1 つある: flash の plan の表（`derby.*`）は DERBY 専用の内容が firmware に入っている | `pocket.kasane.procedural` に足す | 同じ |
| リスク | 低〜中 | 中（plan の書き直し、円弧の切り出しの境目） | 低 |

### 5.2 推奨: B を系列に、C の小さい部品を点に、同じ「道」の上で

- **系列（柵・芝・スタンド・観客）は B。** 27 fps に届くのはこれだけで、ゲストも一番空く。
- **点（走者・距離標・大型画面・台）は C の `pose`／`project`。** 同じ道の表を使うので、native の追加は小さい。**倍精度で計算する**（1 フレーム 20 点前後で、費用は 0.5 ms 以下）。走者と距離標の位置が JS と全桁で一致し、host の oracle がそのまま使える。
- **数値引数の `draw`（N12）は先に入れる。** 0.5 人日で、どのシナリオにも、ほかのアプリにも効く。
- **A（N2）は最終形にしない。** ただし「B の plan の書き直しが止まったとき」「先に 20 fps 台を見たいとき」の中間段として成り立つ。その場合は DERBY のセッションにだけ注入する面にして、B が入ったら消す。

理由: (1) 規則が 1 か所になる（A は JS の plan と C の両方に入力の並びを持つ）。(2) CUBIC（曲線 1 本を native のループで標本化）や LINE_PATTERN（遠近の弦を native が切る）と同じ「繰り返しを native に、絵は plan に」という今の手続き面の作り方の延長になる。(3) C だけでは `ser()` の本体（自己 9,707 命令）が JS に残り、20 fps に届かない。

### 5.3 入口の案（B＋C）

```ts
// 道: 始点と区間の列。コースが決まったときに 1 回。
H.path(sections: number[]): number        // [x0, z0, heading, len0, curv0, len1, curv1, ...]
H.unpath(path: number): void
// 点: 倍精度。pose は [x, z, 接線 x, 接線 z]。
H.pose(path, g, w): number[]
// n 点を camera で投影する。gw = [g0, w0, g1, w1, ...]、out に [画面 x, 1/Z'] を書く。戻り値は点の数。
H.project(path, camera: number[], gw: number[], out: number[]): number
// 系列: 道の上の等間隔の点ごとに plan の本体を 1 回。beginFrame の中で呼ぶ。
H.walk(plan, path, camera: number[], options: number[]): void
// camera = [x, z, 向き x, 向き z, f, 奥の限界]
// options = [w, 間隔, 格子の原点, 最小の px 間隔, 2 つ目の w, 値 a, 値 b]
```

- **置き方**: `pocket_proc.c` の関数の表に足す（`pocket_proc_install()`、`build_kasane()` から呼ばれる）。`pocket_api.c` は編集しない。名前空間 `pocket.kasane` は遅延で、アプリが最初に読んだときに作られる。関数の実体は QuickJS が最初に読まれたときに作る（今の `register`・`draw` と同じ）ので、使わないアプリのゲストは増えない。使うアプリは関数 1 つぶん増える（バイト数は未測定）。
- **capability**: 新しい名前 `display.kasane.path` を、**実装が入った firmware でだけ** `supported: true` で登録する（`pocket_api_register()`）。入口を段階的に入れるなら、`pose`／`project` が入った段で登録し、`walk` は `limits.walk`（FLAG）で示す。実装の無い入口を持つ段で true にしない。
- **limits**: コードで強制している値だけを出す。候補は `paths`（同時に登録できる道）、`sections`（道 1 本の区間、8）、`projectPoints`（1 回の投影の点）。ステップ 10,000・線分 1,024・座標 −480〜720 は今の `draw` と同じ値を点をまたいで数えるが、今は `display.kasane` の limits に出ていない（出ているのは `commands`・`references`・`cacheTemplates`・`cacheInstances`）。出すなら既存の値と一緒に出す。
- **リソース**: 道の表は登録時に heap から取り、`pocket_proc_reset()`（`app_stop()` から呼ばれる）で解放する。静的な `.bss` は増やさない（増やすとゲストの部屋が減る。CLAUDE.md）。ゲストのコールバックは持たないので、reset の順序の条件は増えない。同期の呼び出しだけなので cancel トークンは要らない。
- **誤り**: 今の手続き面と同じ `PocketError`。古いハンドルは `CLOSED`、範囲外・非有限は `INVALID_ARGUMENT`、上限は `LIMIT_EXCEEDED`、`beginFrame` の外の `walk` は `BUSY`、確保の失敗は `OUT_OF_MEMORY`。`walk` が失敗したら、`draw` と同じくそのフレームを捨てる。配列の要素の読み取りはゲストのコードを呼びうるので、今の再入の検査（`js_call_active`）の内側に置く。
- **既存との整合**: `draw(handle, array)` は残す（数値引数は 2 つ目の引数が数のときだけ）。既存の命令・plan・flash の表の番号は動かさない。使わないアプリの経路は変わらない。

### 5.4 ほかのアプリで使えるか

| アプリ | 今の描き方（ソースの読み） | 使える部品 |
| --- | --- | --- |
| BIG WAVE | 世界に固定した断面の列。VM に除算が無いので、`1/d` を級数で進めている（誤差 最大 3.1 px、[big-wave.md](big-wave.md)）。draw は 16 回/フレーム | **`walk`**（直線の道 1 本で、断面ごとの `1/d` を native が出す。級数と誤差が無くなる）、数値引数の `draw` |

## 6. 勧める順序

1. **N12（数値引数の `draw`）。** 0.5 人日。画素は変わらない。
2. **道の登録＋ N4・N5（`pose`／`project`、倍精度）。** 2〜4 人日。画素は変わらない見込み。ここまでが S1a（17.9〜19.0 fps）。境目の費用（§2.3 の測られていない単価）がここで分かるので、N1 の見積もりの確かさも上がる。
3. **N1（ウォーカー）＋ N6（走者の脚）。** 7〜11 人日。基準の作り直しを 1 回にまとめる。ここで S3 に届く（上限の約 30 fps、推定）。
4. 並行して、JS だけの N11（`order` を 1 回に）と N9（台の `pose` をレースごとに 1 回）。

先に 20 fps 台を見たいなら、2 の代わりに N2（S1b）を入れる道がある。その場合、後で N1 に替えるときに N2 の C を捨てる。

## 7. 実機で確かめる最小の項目（測定を再開するとき）

今回は測っていない。順序は、結論を動かす大きさの順。

1. **JS から native の関数 1 回の費用**（引数 2 個で 4 つの数を配列で返す形、数値引数 8 個の `draw`、配列 2 つを受ける形）。N4・N5・N12 の得と、N1 の呼び出し 0.45 ms を決める。pancost のベンチに 3 ケース足せば足りる。
2. **首振りのフレームの非 JS 分の内訳**（帯描画・転送・その他）。17.9 ms か 19.2 ms かで、27 fps の線が 1.3 ms 動く。
3. **残る JS の実時間**（`rin`・`step`・`order`・距離標と走者の `pose`）。較正の 1.253 倍が残りにも当てはまるか。
4. **w=−3 の JS のターン**（今は推定 53.0 ms だけ）。
5. N1・N2 を入れた後: ゲストの最大（`gu`）、評価の余裕（heapprobe）、`LOADSTALL` の有無、ほかのアプリの画素ハッシュと `draw_us`（±15% の中か）。
6. `get_var` の単価（計数 §6 の 1）。VM 側の改良（N16）を考えるときだけ。

## 8. ユーザーが決めること

- **どこまで行くか**: S1a（画素を変えない、19 fps まで）、S1b（DERBY 専用の C で 23〜26 fps）、S2・S3（汎用の入口、27〜30 fps、画素が変わる）。
- **汎用の入口を firmware に足してよいか。** flash +4〜6 KB、新しい入口 4〜5 個と capability、host の試験と文書。今使うのは DERBY だけ。
- **WIDE 2 の台を w=−3 にするか。** N1 を入れるなら fps の差はほぼ無くなる（推定）ので、見た目で決められる。入れないなら 1.5〜2.5 fps 低い。
- **N6 で走者の脚が 1 px 動きうること**、N1 で柵・芝・観客の LOD の境目が動くこと。見た目の判断はユーザー。

## 9. 確信の低い点

- **ms と fps はすべて推定。** 計数の較正式は合計への当てはめで、関数ごとの倍率は 1.15〜1.55 と幅がある。区分ごとの ms は ±30% 動きうる。
- **境目の費用（15〜35 µs／30〜60 µs）は測られていない。** N4・N5・N12 の得はこれで決まる。`H.draw` の固定費（29.3 µs、うち native 12.1 µs）からの類推。
- **N2 の native の費用（4〜8 ms）は幅が広い。** 倍精度の soft-float の 1 演算を、JS のベンチの上乗せ分（乗算 1.27 µs、加算 1.04 µs、除算 3.64 µs）を上限に置いた。実際はそれより安いはずだが、測っていない。
- **N2 が画素を変えないという見込み**は、C の倍精度（soft-float）と `sin`・`cos`・`sqrt` が QuickJS と同じ関数を通ることに依る。host の i386 のビルドで中間精度が違うと、host の照合だけが外れる恐れがある。試していない。
- **N1 の native（0.7〜1.3 ms）、ゲストの −3〜−6 KB、工数**は oval-pie-design の見積もりをそのまま使った。plan を「1 点ぶんの絵」に書き直す試作は無い。スタンドの段と観客（今は弦ごとの `hl`・`crowd`）を点ごとの本体にしたときの線分の数と帯描画の増減は見積もっていない。
- **N6 の `runner` が 64 命令に収まるか**は未試作。収まらなければ、命令数の上限を上げる（VM の構造体が大きくなり、全アプリに効く）か、N6 を見送る。
- **非 JS 分 17.9 ms** は実測 1 回からの逆算で、N1 の後も同じと仮定した。観客を点ごとの模様線にすると帯描画が増えうる。
- **表示の上限 約 30 fps** は、横見のカメラの実測（29〜30 fps）と 33 ms 周期からの読み。S3 の「上限に当たる」は、ターンが 15.4 ms を下回るという推定に依る。
- 関数オブジェクト 1 つがゲストに載せるバイト数、`cosf`・`acosf` が今の image に入っているか（`sinf` は VM の `SIN` が使っている）は確かめていない。
- 監督のカメラが曲線で常に WIDE 2 を選ぶかは確かめられていない（計数 §7）。違えば `wide()` の分が全シナリオに乗る。
- ほかのアプリでの使い道（§5.4）は、ソースを読んだ見立て。
