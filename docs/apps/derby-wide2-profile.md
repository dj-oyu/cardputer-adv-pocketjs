# DERBY WATCH: 楕円コーナーの首振り WIDE 2 の 1 フレームを、バイトコード単位で数える（host）

2026-10-01、ブランチ `vm/wide2-prof`（`vm/main` 44fce25 から）。**アプリ（`apps/derby/`）と `main/` は変えていない。実機（COM3）は使っていない。** 楕円コースのコーナー（先頭 273〜650 m）の首振り WIDE 2 は実機 MID で 16.1 fps・JS 44.25 ms（[derby-pan-memory.md](derby-pan-memory.md) §13、P24 の版）で、どの場面より重い。今の JS のまま、このフレームで QuickJS が何をどれだけ実行しているかを、host の QuickJS に計装を入れて命令単位で数えた。

数値の種類: **計数（host）** は計装が数えた回数（命令・関数の入口・ネイティブの呼び出し・配列リテラル・確保）とハーネスの draw・VM ステップ。**実測（実機）** は既存の文書の値（出典を書く）。**推定** は計数 × 実機の単価、またはそこからの換算。

## 結論

1. **1 フレームの JS は 38,246 命令**（w=−100、先頭 273〜650 m の 449 フレームの平均、計数）。先頭 300 / 400 / 500 / 600 m の 1 フレームは 38,322 / 38,025 / 37,431 / 39,289。WIDE 2 の台を内側（w=−3）に寄せると **46,449 命令**（+21%）。draw は 31.6 回（w=−3 で 38.9）、VM のステップは 2,079（2,728）。
2. **`pan()` が 82%（31,362 命令）、そのうち `ser()` が 52%（19,839）。** 関数の包括の上位は `pan` 82%・`ser` 52%・`pose` 24%（61.6 回）・`ou` 15%（44.5 回）・レースのモデル `step` 7.7%・`lim` 3.5%（78.5 回）・`order` 3.1%・`inr` 3.0%。
3. **命令の種類は「軽い命令の数」が支配する。** 種別は、変数・引数・分岐などの基本の命令 42%、スタックの並べ替えと定数 18%、算術と比較 19%（うち倍精度の被演算子 約 5,700 回）、グローバル変数の読み書き（`get_var`）8.1%、配列の読み（`get_array_el`）8.1%、呼び出し 2.3%、プロパティ 2.0%、配列リテラル 0.4%（140 個）。命令の 1 位は `get_loc_check`（16.4%、TDZ の検査つきのローカルの読み）、5 位は `set_loc_uninitialized`（5.0%、ループの中の `const` が周回ごとに TDZ に戻す）。
4. **単価を掛けた推定は 31.9 ms で、実機の 44.25 ms とは合わない（実測 / 推定 = 1.39）が、「実機 = 1.253 × 推定 + 4.22 ms」の一次式で、実機を測った 4 構成すべてが ±0.06 ms に乗る**（楕円 MID・HEAVY、直線の首振り HEAVY、直線の横見 MID）。1.25 倍は、詰めたループで測った単価と、アプリの中の実際の単価の差（命令キャッシュ。DERBY の中の `Math.sin` は 18.7 µs、ベンチでは 12.1 µs）、4.2 ms は frame() のバイトコードの外の毎ターンの固定分（`end_guest_turn`・ジョブの消化・`commit` など）と読める（読みは推定）。
5. **推定の内訳（w=−100、ベンチの単価、ms）**: 倍精度の算術と比較 7.0、基本の命令 5.8、`get_var` 4.0（単価は仮定）、配列の読み書き 3.4、`Math` 3.2（466 回）、draw（固定費・VM ステップ・線分）2.5、配列リテラル 2.5（140 個、確保 497 回）、プロパティ 1.0、呼び出し 0.9、並べ替え 0.8。**GC は計測した窓で 0 回**（host。実機の頻度は未確認）。
6. **P5（ネイティブの系列ウォーカー）の見積もりは、移す分は当たり、残る分を低く見ている。** 移せる分（`ser()` の全部と、`pan()` の弦の端・弦の選び出し）は推定 27.6 ms（実機の尺度。フレームの JS の 62%）で、設計の想定どおり。`pan()` に残る分は **6.1 ms**（走者 `rin` 2.2、距離標と走者の `pose` 14 回 2.0、`pj` 1.0 ほか）。設計の「残りの JS 約 2.2 ms」は P0 と固定の点の使い回しの後の値で、`rin` は設計では「首振りの外 11.0 ms」の側に入っている。ターンの合計で比べると、P5 の後は設計の 14.3〜16.9 ms に対して **17.8〜18.4 ms**、fps は 27.6〜29.2 に対して **27.5〜28.0**（すべて推定）。P24 の非 JS 分 17.9 ms（実測から逆算）なら 27 fps の線（ターン 19.1 ms）に 0.7〜1.3 ms 残るが、設計の非 JS 分 19.2 ms なら線は 17.8 ms で、届かない。距離標と走者の `pose`（14 回、2.0 ms）を表やウォーカー側へ移す、走者の脚を plan に移す（設計の M4）と余裕ができる。
7. 依頼の前提「首振りの JS 約 20 ms」は、計数からは `ser()` だけの値（推定 21.3 ms）に当たる。`pan()` 全体は推定 33.7 ms。

## 1. 方法

### 1.1 計装の場所

QuickJS（`components/quickjs-ng/quickjs-ng/quickjs.c`）は**変えていない**。[`tools/vmtest/opprof/patch_quickjs.py`](../../tools/vmtest/opprof/patch_quickjs.py) が `.cache/opprof/obj/quickjs.c` に写しを作り、5 か所にフックを入れて、末尾で [`opprof_impl.c`](../../tools/vmtest/opprof/opprof_impl.c) を `#include` する（内部の構造体 `JSStackFrame`・`JSFunctionBytecode`・`JSObject` を読むので、同じ翻訳単位に入れる）。照合する文字列が期待どおりの回数だけ見つからなければ、写しを作らずに止まる。

| 場所 | 数えるもの |
| --- | --- |
| `SWITCH(pc)` のマクロ（`DIRECT_DISPATCH`、gcc の計算型 goto。`BREAK` もここを通る） | 命令ごと: 自己（実行中の関数）と包括（フレームの鎖の上の関数、再帰は 1 回）、算術・比較で被演算子が倍精度か、`array_from` の要素数、関数の入口（`pc` が先頭）と呼び出し元、バイトコードの位置ごとの自己の回数（出力時に行番号へ） |
| `js_call_c_function`・`js_call_c_function_data` の入口 | C の関数の呼び出し（名前ごと、呼び出し元の関数ごと、自己と包括） |
| `js_malloc_rt`・`js_calloc_rt`・`js_free_rt`・`js_realloc_rt` | ゲストのヒープの確保・解放（そのときの関数へ） |
| `js_trigger_gc` の `force_gc` の枝 | 閾値で起きた GC |

`DUMP_BYTECODE_OR_DONT` ではなく `SWITCH` に入れたのは、前者の定義が `NDEBUG` の有無（`ENABLE_DUMPS`）で入れ替わるため（最初の版はこれで 1 命令も数えなかった）。ゲストからは `__opprof(1)` で開始、`__opprof(0, tag)` で停止して窓の値を `$OPPROF_OUT` に追記する。`__opprof` は `-Wl,--wrap=JS_NewContext` で足すので、ハーネス（`tools/games/test_derby_host.c`）も変えていない。

**ハーネスの包みを除く**: ハーネスの prelude（`prelude.js`）は `H.draw`・`commit`・`register` などを JS の関数で包み、検査用の `__draw` を呼ぶ。実機には無い命令なので、`OPPROF_HIDE=prelude.js,frame.js,env.js` の関数は「見えない関数」にして、その命令・確保・C の呼び出しを数えない（別に `HIDDEN` として数える。w=−100 で 1 フレーム 2,398 命令）。ただし包みの中から呼ぶ実機の API（`OPPROF_KEEP`: `draw`・`commit`・`beginFrame`・`patch` など）は、アプリの呼び出しとして、包みの外の一番近い関数に付ける。

### 1.2 場面と回し方

```bash
# WSL（node が PATH にある bash -lc）。m32 の sysroot は tools/vmtest/m32_sysroot.sh が .cache/m32/debs から作る
python3 tools/vmtest/opprof/run_derby_prof.py          # ビルド + ベンチ + 5 構成（約 2 分）。--only NAME で 1 構成
python3 tools/vmtest/opprof/analyze.py > report.md     # 表（Windows の python でも動く）
```

- ビルドは `run_derby.py --m32` と同じ: i386、`-malign-double`、`-O1`、実機と同じ 8 B の JSValue（NaN boxing）と 4 B のポインタ。アプリは `run_derby.py` と同じく `lower_plans.mjs` で下ろした写しを走らせ、コースは写しの `OV[0]` で固定する（`force_course()`）。
- カメラは `DERBY_NOCAM=1`（台本のカメラキーなし）と `DERBY_EACH="cam=8;man=9;"`（毎フレーム、手動の WIDE 2 を保つ）。w=−3 は `DERBY_JS` で `CAMS[8][5]=-3`（楕円での WIDE 2 の w）。直線の横見は `wide=()=>0` と `cam=0`。
- 窓: `DERBY_JS` で `globalThis.frame` を包み、**プレイヤーの最初のレース**（デモでも R 再生でもない）で、先頭がその構成の帯（楕円 273〜650 m、直線 300〜620 m）にいるフレームだけ計装を入れる。印 300・400・500・600 m を最初に越えたフレームは `at<m>` とし、帯の全フレームの平均も出す。窓の中の `cm` は 8、`pc` は首振りであることを、全フレームのタグで確かめた。
- ハーネスの判定は `DERBY_HOST FAIL` になる（直線の横見を除く）。理由は「大型画面が一度も映らない」検査だけで（WIDE 2 に固定すると画面が視野に入らない）、例外・`FRAMEFAIL`・Newton の誤差は 0 / 0 / 0.0004 px。
- 描画の回数・VM のステップ・線分は、ハーネスの `DERBY_CSV` の行（`tick` が窓のタグと一致）から取る。

### 1.3 m32 のバイトコードは実機と同じか

- バイトコードを作るのは同じ `quickjs.c` のコンパイラで、アプリは同じ下ろし方の同じソースを評価する。コンパイラの範囲（26,419〜41,200 行）の条件コンパイルは、`ENABLE_DUMPS`（ダンプだけ）・`QJS_DISABLE_PARSER`・`CONFIG_POCKET_VM_STRIP_DEBUG`（行番号表を作らないだけ。既定 OFF で、DERBY の実機の値も OFF）だけで、命令の列を変える分岐は無い（ソースを読んで確認）。ポインタや JSValue の大きさで命令を変える箇所も無い。
- 実行時の型（整数か倍精度か）は値の表現で決まり、m32 は実機と同じ NaN boxing。「倍精度の被演算子」の計数はこれに依る。
- 確かめていないこと: 実機のバイトコードを取り出して、命令の列をバイト単位で比べてはいない。

### 3.4 配列・確保・`dr()`・`Math`

- **配列リテラル 139.9 個 / フレーム**: 4 要素 62.6（`pose` の戻り値 61.6）、2 要素 36.6（`ser` の `q` 19.6、`pj` の戻り値 16）、8 要素 33.6（`dr` の入力: `ser` 22.3、`rin` 8、`order` 2 …）、その他 7。**確保（malloc）は 496.5 回 / フレーム**で、配列 1 個につき 3 回（オブジェクト・要素の表・形）の 420 回が大半。推定 2.8 ms（実機の尺度 3.5 ms、JS の 9%）。
- **GC**: 計測した窓では、閾値で起きた GC は 0 回（全構成）。ただしハーネスは毎フレームの後に `JS_RunGC` を呼ぶので、実機の閾値の状態とは違う（§6）。循環の無いゲストは参照カウントで解放されるので、窓の中で GC が要らないのは実機でも同じ見込み（推定）。
- **`dr()` は 31.6 回**（`ser` 22.3、`rin` 8、距離標・`paint` の地図 1.3）、`H.draw` も 31.6 回。入力の配列は 8 要素（`ser` の系列は `[X'', dX'', −Z', −dZ', 本数, 1/Z', a, b]`、スタンドの段 `hl` と観客 `crowd` も 8）。w=−3 で 38.9 回。
- **`Math` は 466 回 / フレーム**: `sin` 91.2（`pose` 51.2、`rin` 40）、`cos` 51.2（`pose`）、`sqrt` 67.8（`ou` 44.5、`ser` 22.3、`shot` 1）、`min` 71.2・`max` 47.3（うち `lim` 39.3 ずつ）、`round` 57.2（`ser` 55.2）、`abs`・`floor`・`ceil` 15.9 ずつ（`ser`）、`imul` 32（レースの乱数）。推定 3.2 ms（実機の尺度 4.1 ms）。

  - 4.2 ms: `MDT` の `js=` は `dispatch_guest()`（frame() とジョブの消化）と `end_guest_turn()` の時間（`main/app_session.c`）。frame() のバイトコードに入らない固定分と、推定を低めに置いたネイティブ（`commit`・`patch` など）がここに入る（推定）。
- **確かさ**: 点は 4 つで、うち楕円の MID と HEAVY はほぼ同じ点なので、実質 3 点に 2 個の係数（自由度 1）。`get_var` の単価（仮定）を 0.33〜2.5 µs に振っても、残差は ±0.1 ms 以内のまま、傾きが 1.11〜1.40、切片が 4.7〜3.8 ms に動く。つまり**合計は合うが、`get_var` の単価はこの照合からは決まらない**。
- w=−3 は実機の値が無い。一次式では 53.0 ms（実機の非 JS 分 17.9 ms を足して 14.1 fps、推定）。

### 5.2 P5 の見積もりの検算

[oval-pie-design.md](../kasane/oval-pie-design.md) §6.1 の P5 の費用は「系列 6 本の呼び出し 0.45 ms ＋ 首振りの残りの JS 約 2.2 ms ＋ ネイティブ 0.7〜1.3 ms = 首振り 3.3〜3.9 ms、ターン 14.3〜16.9 ms、27.6〜29.2 fps」。計数からは:

| 項 | 設計（推定） | 計数から（推定） |
| --- | ---: | ---: |
| 系列の呼び出し（JS） | 0.45 | 0.45（設計の値をそのまま） |
| 首振りの残りの JS | 約 2.2（P0 と固定の点の使い回しの後） | **6.1**（今の JS のまま） |
| ネイティブのウォーカー | 0.7〜1.3 | 0.7〜1.3（設計の値をそのまま） |
| **首振りの合計** | **3.3〜3.9** | **7.3〜7.9** |
| 首振りの外 | 11.0 | 10.5（6.3 ＋ 固定分 4.2） |
| **ターン** | **14.3〜16.9** | **17.8〜18.4** |
| fps（非 JS 分は P24 の実測 1000/16.1 − 44.25 = 17.9 ms） | 27.6〜29.2 | **27.5〜28.0** |

- **移せる分の大きさ（27.6 ms）は設計の想定どおり**で、P5 の効果そのもの（44 → 18 ms 前後）は大きい。
- 首振りの行だけを比べると 3.3〜3.9 と 7.3〜7.9 で倍違うが、これは区分の違いを含む。設計の「首振りの外 11.0 ms」は直線コースの実測から首振りのモデルを引いた値なので、走者の `rin`（`sin` 5 回 × 8 頭、8 要素の配列、draw。直線の横見でも同じ費用）がそちらに入っている。計数の区分では `rin` は `pan()` の中。**比べられるのはターンの合計で、差は 0.9〜4.1 ms（計数の方が重い）。** 差の中身は、`rin` を除いた残り（`pose` 14 回 2.0 ms と `pj` 1.0 ms ほか、計 3.9 ms）が設計の 2.2 ms より 1.7 ms 重いことと、ネイティブ・系列の呼び出しの幅。
- 27 fps はフレーム間隔 37.0 ms。非 JS 分を P24 の実測からの逆算 17.9 ms とすると、ターンの線は 19.1 ms で、P5 の後の 17.8〜18.4 ms は 0.7〜1.3 ms 下。設計の非 JS 分 19.2 ms を使うと線は 17.8 ms で、届かない。どちらにしても余裕は小さい。距離標と走者の `pose`（14 回、2.0 ms）を表やウォーカー側へ移す、走者の脚を plan に移す（設計の M4）、`rin` の `sin` 5 回を減らす、で余裕ができる（推定）。
- w=−3 では、今の推定 53.0 ms から P5 の後 約 18 ms（移せる分が増えるだけで、残りは同じ）。台を内側に寄せる費用は、P5 の後はほぼ消える（推定）。
- 移せない分のうち、`step`（レースのモデル）・`order`・`hud` などはどの場面にもある（直線の横見 MID の JS 8,399 命令のうち `step`＋`order` で 4,034）。

## 6. 実機で測るべき項目（今回はしていない）

1. **`get_var`（トップレベルの `let`/`const` の読み）の単価。** 1 フレーム 2,981 回で、推定の 12% を占めるが仮定値（プロパティと同じ 1.28 µs）。§4 の傾きがこれで 1.11〜1.40 動く。pancost のベンチに、トップレベルの名前を読むループを足す。
2. **`Math.min`/`max`/`round`/`floor`/`ceil`/`abs`/`imul` の単価**（1 フレーム約 255 回、推定 5.0 µs）。
3. **配列リテラルの要素数ごとの単価**（2・4 要素。1 フレーム 99 個）と、確保と解放 1 回の単価。
4. **倍精度の比較と ToInt32 の単価**（`lt`・`gt` など 685 回、推定 0.55 µs）と、倍精度の補助関数（`__adddf3`・`__muldf3`・`__divdf3`・比較）の 1 フレームの回数と時間。P5 の試作では、ネイティブ側の `__divsf3`（単精度の除算）の回数。
5. **関数ごとの実時間**（計時を入れた一時ビルドで `pan`・`ser`・`pose`・`ou`・`rin`・`step`）。§4 の 1.25 倍が関数ごとに同じか（命令キャッシュの外れ方は関数で違いうる）。
6. **GC**: このシーンで `js_trigger_gc` が走る頻度と 1 回の時間。
7. **固定分 4.2 ms の中身**: `end_guest_turn()`・ジョブの消化・`commit`／`patch` の時間を分けて測る。
8. このシーンの `TURNPERF`（`I_STALL_BUSY` の割合）。1.25 倍が命令キャッシュかを確かめる。

## 7. 確信の低い点

- **µs はすべて推定。** 単価の多くは詰めたループのベンチで、アプリの中では §4 の一次式で 1.25 倍と見なしている。この倍率が関数・命令の種類によらず同じという仮定は確かめていない（`pose` 1.15 倍、`Math.sin` 1.55 倍と幅がある）。
- `get_var`・`Math` の小さな関数・配列の要素ごとの傾き・倍精度の比較の単価は推定で、ベンチが無い。一次式の残差はこれらに敏感でない（§4）ので、照合が合ったことは、これらの単価が正しいことを意味しない。
- 実機の値は P24 の測定（各 1 回、デモで決まるレース、中央値）。照合した 4 構成のうち 2 つ（楕円の MID と HEAVY）はほぼ同じ点。
- 実機の「楕円の首振り WIDE 2」は監督のカメラの値（曲線区間で一番近い台）。host は WIDE 2 を手動で保った。曲線区間での監督の台が常に WIDE 2 かは確かめていない（違えば `wide()` の `pose` 6 回、約 0.9 ms が実機側に乗る）。
- P5 の区分は、`pose` の 1 回の費用が呼び出し元によらないと仮定して、呼び出しの回数で割り振った（曲線上と直線上で `pose` の費用は 135 µs と約 70 µs で違う）。走者と距離標の `pose` は曲線上が多いので、残りの 1.63 ms はやや多めの可能性がある。
- P5 のネイティブ側（0.7〜1.3 ms）と系列の呼び出し（0.45 ms）は設計の推定をそのまま使った。
- 先頭 300・400・500・600 m の値は各 1 フレーム。表は帯の全フレームの平均を使った。
- 実機のバイトコードを取り出して比べてはいない（§1.3 はソースの条件コンパイルを読んだ確認）。
