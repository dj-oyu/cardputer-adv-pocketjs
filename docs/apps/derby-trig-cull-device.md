# DERBY WATCH: trig-cull と WIDE 2 の u=14 を実機で測る

2026-10-01、ブランチ `vm/trig-device`（`vm/trig-cull` 48e9cde から）。[derby-trig-cull.md](derby-trig-cull.md) の変更（`wide()` の pose を 1 回に、弦の端を `CH.P` の sin 9 個から対称性で作る）を、実機（COM3）で fps とゲストのメモリについて測った。あわせて、WIDE 2 の台を u=14（`CAMS` の行 8 の楕円用 w を −100 → −3。u = 11 − w）にした場合も測った。**表の数値はとくに断りがなければ実機の実測。** host の数値は「host」と書く。

## 結論

- **trig-cull（B）は (c)(d) を割らない。** ゲストの最大は 139,364〜139,624 B で、140,000 B まで残り 376〜636 B。評価の余裕は 21,985 B（20 KB の線まで 1,985 B）。基準（A）からの増分は、同じレース同士でゲストの最大 +868〜+928 B、評価のピーク +428〜+557 B。m32 の予測（+824 B、+576 B）と合う。
- **trig-cull の効き**: 楕円のコーナーの首振り WIDE 2 で、JS が 44.43 → 42.72 ms（−1.71 ms、MID）、fps は 15.8 → 16.2。HEAVY は 43.69 → 42.71 ms（−0.98 ms、1 回ずつ）、15.9 → 16.2 fps。楕円の WIDE 3 は 19.4 → 20.1 fps（JS −1.54 ms）。直線の首振りと横見は変わらない（差は 0.1 fps・0.15 ms 以内）。推定（1.8〜2.1 ms）の下側に近い。
- **u=14（w=−3）は、コーナーの WIDE 2 で約 2.6 fps 遅い。** MID で B 16.2 → C 13.6 fps（JS +11.6 ms、VM の draw 31 → 40 本）、基準のまま w だけ変えた D は 13.3 fps。trig-cull が戻す分は 0.3 fps 程度。さらに **楕円の WIDE 3 が 20.1 → 16.4 fps** に下がる。WIDE 2 の台がホームストレッチから遠くなり、WIDE 3 への切り替えが先頭 690 m → 655 m に早まって、まだ曲線の弦が多く写る区間（弦の本体 17〜22 本、host）を WIDE 3 が受け持つため。
- **u=14 で壊れるものは見つからなかった**（host の本物の harness: 例外・描画の失敗 0、線分 583/1024、コマンド 32/80、Newton の誤差は画面上の点で 0.028 px）。`wide()` はコーナー全域（273〜650 m）で WIDE 2 を選ぶ。**先頭 440〜480 m では台からの距離が 19.8〜27.6 m で、f が最小値 200 に張り付く。** その区間では、先頭から 10.5 m 後ろの走者が画面の左端の外に出る（470 m で x = −20、host）。見た目の評価は書かない（下の画像）。

## 1. 構成と手順

| 構成 | JS | WIDE 2 の楕円用 w |
| --- | --- | ---: |
| A 基準 | `vm/main` 44fce25 の apps/derby | −100 |
| B trig-cull | `vm/trig-cull` 48e9cde の apps/derby | −100 |
| C trig-cull + u=14 | B の `CAMS` の行 8 だけ変更 | −3 |
| D 基準 + u=14 | A の `CAMS` の行 8 だけ変更 | −3 |

- C のコードは同じ。4 構成とも同じビルドディレクトリ・同じ設定で、JS だけ差し替えて作った（診断 image `-DKASANE_MEGADEMO_TRACE=ON -DKASANE_BGCOST_TRACE=ON -DPOCKET_KEYTEST=ON`、heapprobe image `-DPOCKET_HEAPPROBE=ON`、いずれも `-DSDKCONFIG=<dir>/sdkconfig`）。bin に入った JS（`CH.P`・w の値）を確かめた。
- **デモの種を固定した。** デモの種は `HW = pocket.random.seed()`（実機では `esp_random()`）で起動ごとに変わり、最初の 3 回（固定前）は回ごとにレースが違った。fps を同じレースで比べるため、診断 image の 4 構成すべてで `HW = 0x2545f492` に置き換えた（保存の race=18 で、デモ 5 本が直線 1・楕円 4 になる値。tools/games/derby_seeds.py の式で選び、実機の `SCENE` の種が予測と一致した）。このため、固定種の image は出荷の JS と 10 バイト違う。ゲストの最大は、固定前の 3 回（出荷の JS そのもの、種は乱数）も表に載せた。
- 実機の手順（[`tools/games/ovalcost/trig_device.py`](../../tools/games/ovalcost/trig_device.py)）: 書き込み → 6 秒後に DERBY を開く → キーを押さずにデモを流す（MID 420 秒）。HEAVY は書き込み直後のパドックで tab を 1 回（USB のキー注入）押して 330 秒。MID は A→B→C→D を 3 巡、HEAVY は A・B・C を 1 回ずつ。全 run で `LOADSTALL`・`FRAMEFAIL`・`LOADFAIL`・`DEMOFAIL`・OOM なし。
- 集計: レースのターン（`SCENE race`）を、コース（`ODDS ... OVAL`）・`CAM`・tier ごとに分け、切り替わりの後 3 ターンを捨てた中央値。fps は 1 / ターン間隔の中央値。**「楕円 WIDE 2」は、コーナーに入って（273 m）から WIDE 3 に切り替わるまで**（w=−100 は約 690 m、w=−3 は約 655 m。host）の首振りの全フレームで、300〜620 m だけを切り出してはいない（ログに先頭の位置が無い）。リードの交代で CLOSE に切れた区間は含まない。
- 楕円の結果（`FINISH` の全桁）は A〜D で同じ（C・D は 5 本目が 420 秒の打ち切りで終わっていない）。

## 5. 採否の材料

- **trig-cull（B）**: (c)(d) を割らず、結果・画素は変わらず、楕円のコーナーで 1.0〜1.7 ms・0.3〜0.4 fps 速い。入れられる。ただし (d) の残りは 0.4〜0.6 KB になり、楕円にこれ以上の描写を足すには、どこかを削る必要がある。
- **u=14（w=−3）**: 壊れはしないが、コーナーの首振りが 16.2 → 13.6 fps、楕円の WIDE 3 が 20.1 → 16.4 fps。f が 200 に張り付く区間（440〜480 m）で後ろの走者が画面外に出る。採るかどうかは見た目との引き換えで、ユーザーが実機とシミュレータで判断する。

## 確信の低い点

- HEAVY は各 1 回。B − A の差が MID（−1.71 ms）と HEAVY（−0.98 ms）で違う理由は調べていない。
- 「楕円 WIDE 2」は 273 m から切り替えまでの全フレームで、依頼の 300〜620 m とは区間が少し違う（ログに先頭の位置が無い）。w=−3 では区間の終わりが 655 m で、w=−100 の 690 m より短い。
- ゲストの最大は種で 300 B ほど動く（A: 138,492 と 138,812）。固定種の 4 本の楕円より重いレースがあれば、残りはもっと小さい。
- 固定種の image は `HW` の行だけ出荷の JS と違う（全構成で同じ置き換え）。
