# DERBY WATCH: `ser()` の除算と倍精度をやめる設計（固定小数、PIE の扱い）

2026-11-13、設計（SLOW）。**同日、S0・S1 と S2 の `view()` を実装した（§10、STEADY）: r5sim の重い WIDE 2 は 229,120 → 145,550 カウント/ターン（−36.5%、実測）、実機は未測定。** **§12: 実機で差が見えなかった件の診断（直線のコースでは r5sim −9.0%、計装 `DERBY_SER`）。**[derby-ser-cost.md](derby-ser-cost.md) の続きで、重い CAM WIDE 2 の `pocket.derby.ser()`（`main/pocket/pocket_derby.c`）の倍精度の計算（r5sim で 1 ターン約 76k カウント、実機換算の推定で約 3.7 ms）を減らす方法を比べ、推奨と段階を決める。

利用者の方針（2026-11-13）: 有望さは (c) 固定小数・整数 ＞ (b) float32 ＞ (d) 構造の変更 ＞ (a) ビット一致のまま。**精度にはこだわらない**（画素と oracle のビット一致は必須ではない）。(c) で作れるなら PIE も一緒に考える。PIE の実証は実機で行い、asm を書くときは esp32s3-hw MCP を使う。

**結論**

- **重いのは除算だけではない。** 除算は `ser()` の倍精度の計算の約 4 割（推定）、残りの大半はソフトウェアの倍精度の乗算と加減算。除算だけを減らす案の上限は小さく、**数の表現を変える案だけが全部を消す**。
- **(c) 整数（Q16 の位置、Q30 の向き、64 ビットの積）を推奨する。** host の試作（この設計のために書いた。§4.3）で、アプリのカメラの範囲では画面上の点 1,360 万個のうち 4 個を除いて倍精度と 0.01 px 以内、ランダムなカメラ 32 万呼び出しでも 1,613 万点のうち 3 点を除いて 0.1 px 以内だった（実測）。外れた点は LOD の境目などが同値のときに柱 1 本・縞 1 本が入れ替わるもので、25 万呼び出しに 2 回。
- **見込み（推定）:** 重い WIDE 2 の r5sim 229k → 約 150k カウント/ターン（−33〜35%）、実機 11.6 ms → 約 8 ms。段 S1（`ser()` だけ）で −65〜69k、段 S2（`view()`・`aim()` と境目）で −10k 前後。
- **PIE は、この仕事には大きくは効かない見込み（推定）。** 整数にした後に残る `ser()` の計算は 7〜11k カウント（約 0.3〜0.5 ms）で、その中身は 32×32→64 ビットの乗算と、弦ごとに回数の違う LOD のループと除算。PIE には 32 ビットの乗算が無く（TRM、アセンブラで確認。§6.1）、16 ビットのレーンに入るのは弦の除外（`ou()`）だけ。**「整数にする → 実機で残りを測る → PIE の試作（弦の除外の核、asm）を実機の同一バイナリ A/B で測る」の順に分け、PIE の利得は実機の数字だけで主張する。**
- **oracle の契約は「JS と C の draw の入力がビット単位で一致」から、「画面上の点が 1 px 以内・描画が壊れない不変条件・整数の C どうし（スカラーと PIE）のビット一致」に改める**（§5）。
- **追記（2026-11-13）: PIE の試作 P1 の核を書いた（§10）。** 端の回転と弦の除外の asm、スカラーの整数の参照、host の 3 層の検査（安全側でない判定 0、asm と参照の不一致 0）、既定 OFF の `CONFIG_POCKET_DERBY_SER_PIE` と実機の自己検査 `SERPIE`。`ser()` にはまだ組み込んでいない。実機の数字はまだ無い。

### 1.3 除算の割合（推定）

host の試作に数える印を付けて、アプリのカメラ（首振りの 3 台、先頭を −20〜1,010 m に置く。§4.3）で楕円を回すと、`ou()` を通った弦 1 本あたり除算 13.8 回（うち `lim()` 4.0）、`sqrt` 1.0 回、draw 1.05 本（実測、合成したカメラの分布。`pose()` の中の `1/曲率` は数えていないので、足して 15 前後）。

- 弦 1 本の倍精度の計算は 76.0k ÷ 28.2 ≒ 2.7k カウント。除算 15 回 × 71 ≒ 1.07k（**約 40%**）、`sqrt` 約 0.11k（4%）。**残りの約 55% は乗算・加減算・比較・`ceil`/`floor`/丸め**（1 回は安いが、弦 1 本に 100 回を超える）。
- この割合は推定（回数は合成した分布、値段は逆算）。重い窓そのものの回数は r5sim の計装で数えられる（段 S0）。
- したがって「除算を減らす」だけでは、全部消しても −30k カウント前後が上限。**ソフトウェアの倍精度そのものをやめる案（b・c）は 76k のほぼ全部が対象になる。**

- アプリは `L` に 4 か 8 しか渡さない（`apps/derby/derby_pan.js`）。`L = 0` の分岐（`fmod` と `t` の偶奇）は fuzz しか通らない。整数の経路は `L ≥ 1` だけを扱い、それ以外は倍精度の経路に残す。

## 3. (b) float32 を本命にしない理由

- 精度の評価は (c) と同じ道具（§5.1 の点の照合）でできる。アプリのカメラでは倍精度との差は (c) と同じで、同値のときの入れ替わりも同じ 2 回だった（実測）。
- ランダムなカメラ（`f` 50〜3,050、カメラの `w` −150〜41、`zf` の余り 0〜500 m）では、draw の本数が違う呼び出しが 197 回、2 px を超える点が 1,608 個（0.01%）、最大 147 px（実測）。整数は同じ入力で 3 回・3 点。float32 は 24 ビットで、±10,000 m の弦の端からの外挿と、カメラ位置の引き算の桁落ちに余裕が無い（推測。原因は調べていない）。
- 実機の値段も整数より良くない: 除算は `__divsf3` の呼び出し（55〜67 サイクル、実測）で、整数の `quos`（2〜12）より高く、`sqrtf`（174〜188）・`floorf`（約 78）も呼び出し。soft-float ABI で生きている float が呼び出しのたびに退避される（pie-simd.md §3.1・§3.5）。
- 採るなら: 入力の範囲（`f`・コースの座標）を `course()`・`aim()` で検査し、外なら倍精度の経路へ戻す。受け入れ基準は §5 と同じ。

## 4. (c) 整数の `ser()` の設計

### 4.1 数の型

| 値 | 型 | 範囲と根拠 |
| --- | --- | --- |
| 世界の座標、コース上の距離 `g`、奥行き `Z`、横 `X` | Q16 m、int32 | ±32,767 m。コースの端は ±10,000 m（`CH` の ±655,360,000）、カメラからの差は ±21,000 m 以内。分解能 1.5 × 10⁻⁵ m は、手前の面（`Z = f/50`）で 0.0008 px |
| 向き（カメラ `d`、弦の単位長あたりの進み `t`、弦の法線 `n`） | Q30、int32 | 絶対値 1 以下。20,000 m 外挿しても 10⁻⁵ m |
| `f` | Q16 px | 32〜4,096 px（アプリは 200〜1,500） |
| `1/f` | Q32 | `aim()` で 1 回。`f ≥ 32` で int32 に入る |
| 積 | int64（`mull`＋`muluh`） | Q16 × Q30 → 丸めて Q16。2 項の和までは 2⁶³ に入る（§4.4 の範囲の検査） |
| plan の入力 | 各入力の Q 形式の int32（`prail`・`pt` は x・dx が Q16、z・dz・farZ が Q24、r が Q16） | `pocket_proc_draw_fixed()`（走者の draw と同じ入口）にそのまま渡す。double → 固定小数の変換（[shiki-spec.md](../kasane/shiki-spec.md) §2.4）が消える |

カメラ（`aim()`）は S1 では倍精度のまま計算し（1 フレーム 1 回、1.3k カウント）、その結果を固定小数に丸めて持つ。

### 4.2 手順（弦 1 本）

記号は [oval-pie-design.md](../kasane/oval-pie-design.md) §3 と同じ素の形（`f` を畳まない）。

1. **表（フレームに依らない。系列 `(w, s, g0)` ごと、最初の呼び出しで作る）**: 弦 j の `ga`・`gb`（Q16 の整数どうしの丸めなので正確）、`A = pose(ga, w)`（Q16）、`t = (B − A)/(gb − ga)`（Q30）、単位の法線 `n`（Q30、芝の幅に使う）。作るときは今の倍精度の `pose()` を使う（1 レースに 1 回）。8 個 × int32 × 弦 18 本 × 系列 5 = 2,880 B。系列は 8 個まで持ち、それを超える呼び出しは倍精度の経路へ。
2. **カメラ座標の直線**: `rel = A − E`、`Za = rel·d`、`Xa = rel·d⊥`、`uz = t·d`、`ux = t·d⊥`（積 8 回）。`g0` を原点にして `Z(G) = Zq + G·uz`、`X(G) = Xq + G·ux`。
3. **切り出し（`lim()` の 4 面）**: 手前 `Z − f/50`、奥 `zf − Z`、左 `f·X + 160·Z`、右 `160·Z − f·X` を、区間の両端で計算する。両端とも負なら弦を捨て、両端とも非負なら除算しない。符号が違う面だけ、交点を `lo + (hi − lo)·A/(A − B)` で求める（`A`・`B` は `nsau` で 31 ビットに正規化してから。除算 1 回）。
4. **LOD**: `W = |ux·Zq − Xq·uz|`（カメラから弦の直線までの距離 × `|t|`。倍精度の `|v·q1 − q0·u|` と同じ量）、`Z0 = isqrt(f·W·s/L)`（`L` が 4・8 ならシフト）。段の境目は `Z0·2^(n/2)`（`√2` は Q30 の定数の乗算。倍精度の `Z /= √2` の除算が消える）。格子への切り上げ・切り下げは `quos` と整数の補正。`inr()` は `Z > f/50`、`f·X + 520·Z > 0`、`520·Z − f·X > 0` の符号で判定し、除算しない。
5. **段ごとの draw**: 段の手前の端 `hh` は `(Zt − Zq)/U`（除算 1 回、飽和つき。`U` が小さければ今と同じく −∞ 扱い）、本数は `(e − hh)/k`（`quos`、割り切れる）。入力は `z' = Z·(1/f)`（Q24）、`x'' = X + 120·z'`（Q16）、1 歩の `dz'`・`dx''`、`r = f/Z`（除算 1 回）。
6. **スタンド（`b < 0`）**: 両端の `r = f/Z` と `x = 120 + f·X/Z`（除算 4 回）、あとは乗算。

試作の回数（実測、host。`ou()` を通った弦 1 本あたり、アプリのカメラ・楕円）: 64 ビットの積 49.9、`quos` 相当 2.29、64 ビットの除算 2.37、`isqrt` 0.72。今の倍精度は除算 約 15・`sqrt` 1.0。

### 4.3 host の試作の結果（実測）

試作は、今の C の `ser()` の写し（倍精度）と §4.2 の整数版を同じカメラで回し、両方の draw の入力を plan の Q 形式に丸めてから、plan が画面に置く点（柱の足元と上端、芝の縞の両端、スタンドの段の両端）に直して照合する。点は画面内（x 0〜240）のものだけを数え、相手側のいちばん近い点との距離（x・y の大きい方）を取る。両方向。`ou()` の判定は両方とも倍精度のまま。

| 入力 | 呼び出し | draw（倍精度 / 整数） | 画面内の点 | 0.01 px 以内 | 0.01〜0.1 px | 2 px 超 |
| --- | ---: | --- | ---: | ---: | ---: | ---: |
| アプリのカメラ、直線（3 台 × 3 段階 × 先頭 2,784 か所 × 5 系列） | 125,280 | 386,577 / 386,578 | 8,304,496 | 8,304,494 | 0 | 2（6.7 px） |
| アプリのカメラ、楕円 | 125,280 | 431,756 / 431,757 | 5,291,709 | 5,291,707 | 0 | 2（6.7 px） |
| ランダムなカメラ（`__serfuzz` と同じ分布、`L` は 4・8、4 万ケース × 8 系列） | 320,000 | 1,262,267 / 1,262,268 | 16,135,073 | 16,134,830 | 240 | 3（24.7 px） |

- 入力の飽和（int32 に入らない値）は 0 回。
- 2 px を超えた点の中身: (1) LOD の `while` の条件が数学的に等しいとき、整数は 1 段粗い段から始め、いちばん奥の柱が 1 本（4〜8 px 間隔の 1 px の線）足りない。(2) 弦が視線にちょうど直交する（`u = 0`）とき、歩く向きの符号が逆になり、端の縞が 1 本入れ替わる。どちらも「同値のときにどちらへ倒すか」の違いで、誤差が積もったものではない。アプリのカメラでは 250,560 呼び出しに 2 回（約 5 万フレームに 1 回、1 フレームだけ）。
- 同じ道具で float32 版も測った（§3）。
- **試作はこの設計のための一時ファイルで、リポジトリに入っていない。** 段 S0 で `tools/games/` に入れ、数字を再現できるようにする。
- 現在の木の基準（実測、この設計の作業中に実行）: `python3 tools/games/run_derby.py` は 19 回 PASS、ser の oracle は不一致 0（ゲーム 19,325 呼び出し、fuzz 32,000 × 3）。

### 4.4 範囲の検査と倍精度への戻り道

整数の経路は、検査した範囲の中だけで使う。外なら今の倍精度の経路で描く（絵は出る。遅いだけ）。

- `course()`: 弦の端と区間の座標が ±16,000 m 以内。
- `aim()`: `f` が 32〜4,096 px、カメラの位置が ±16,000 m 以内。
- `ser()`: `L` が 1 以上の整数、`s` が 0.25 m 以上、系列の表に空きがある。
- 弦ごと: `W` は 1,024 m で頭打ち（LOD の境目にしか効かない）、`(Zt − Zq)/U` は ±2²⁴ m で飽和。

倍精度の経路は、A/B と戻り道のために当面残す（flash 約 5 KB、`js_ser` は今 5,027 B）。消すかどうかは利用者の判断（§8）。

### 4.5 見込み（推定）

- 試作を `xtensa-esp32s3-elf-gcc -O2` で組むと、整数の `ser()` は 2,164 命令・5.3 KB（実測。host 用の変換と数える印の残りを含む、全部の分岐の合計）。弦 1 本で通るのは 1,500〜2,500 命令と見る（推定。面のループ 4 周と LOD の段を含め、64 ビットの除算 2.4 回 × 約 100 命令を足した）。
- `ou()` を通る弦 28.2 本 × 1,500〜2,500 命令 ＝ 6.5〜10.8k カウント。整数の `ou()`（40.7 回 × 約 60 命令）0.4k。**倍精度の 76.0k が 7〜11k になる（−65〜69k）。**
- draw の境目（3.3k）のうち double → 固定小数の変換と有限の検査が消える（−2k 前後）。
- S2: `view()` 10.1k → 約 1k（弦の端を表にし、回転と `ou()` を整数に）。`aim()`・走者の `lane()`・距離標は 1 フレームの回数が少ないので小さい。
- 合計で 229k → 約 150k カウント/ターン（−33〜35%）、実機 11.6 ms → 約 8 ms。**実機の数字は S1 の A/B で確かめる。** r5sim は Shiki を C のモデルで回し flash の待ちも無いので、比はそのまま実機に移らない。

## 5. oracle の契約をどう改めるか

今の契約は「JS の `ser()`（`tools/games/derby_ser_oracle.js`）と C の draw の入力が、全部の呼び出しでビット単位で一致」。これを 3 つに分ける。

### 5.1 幾何の許容差（JS の倍精度 ↔ 整数の C）

`derby_ser_oracle.js` はそのまま参照として残し、`__sercmp`（ビットの比較）を、§4.3 と同じ「点の照合」に替える（`__sertol`）。

| 検査 | 基準（案） | 根拠 |
| --- | --- | --- |
| 画面内の点の距離 | **1.0 px 以内**（両方向、x・y の大きい方）。超えた点は「入れ替わり」に数える | 試作は 0.1 px 以内。利用者の「±1 px」に合わせ、余裕を持たせる |
| 入れ替わり（1 px を超えた点） | 1 呼び出しに 4 点以下（柱 1 本 ＝ 足元と上端で 2 点、両方向で 4）、かつ呼び出しの 0.01% 以下 | 試作は 25 万呼び出しに 2 回（0.0008%） |
| draw の本数 | 呼び出しごとに差が 1 本以下 | 試作は差 1 本が 3 回 |

fuzz は今と同じ分布で回す。`L = 0` の呼び出しは倍精度の経路に行くので、そこは今のビットの比較のまま。

### 5.2 描画が壊れない不変条件（整数の C だけで検査する）

参照と比べずに、整数の経路が出す draw そのものを検査する。「見た目の破綻・欠けが無い」をここで保証する。

- 入力は全部 int32 に入っている（飽和 0 回）。
- 本数は 1〜255、`r > 0`、`z'` は手前の面より奥。
- `r` は `1/z'` と相対 2⁻¹² 以内（plan の Newton が正しい値から始まる）。
- 1 歩の奥行きの比 `|dz'| / z'(手前の端)` が 0.31 以下（plan の Newton が収束する条件。倍精度の 0.3 に丸めの余裕）。
- 弦のつなぎ目: 隣り合う弦の同じ系列の端の点が 1 px 以内でつながる（スタンドの段・観客の帯が切れない）。
- 画面を横切る弦が 1 本も描かれないフレームが無い（倍精度が描いた呼び出しで、整数が 0 本ではない）。

### 5.3 画素とビット一致

- **画素の基準は作り直す。** `run_derby.py` の全画素ハッシュは、整数の経路で 1 回取り直して新しい基準にする。整数の C は host（64 bit・`--m32`）と実機で同じ結果になるので、以後は今と同じくハッシュの一致で回帰を見る。作り直すときに、古い基準との画素の差（フレームごとの違う画素の数）を記録する。
- **`--m32` でも oracle を回せるようになる。** 今は x87 の 80 ビットのために 64 bit でしか判定できない（derby-ser-native.md §9）。許容差の照合は 1〜2 ulp の違いに影響されない。
- **ビット一致の契約は「整数の C ↔ PIE の核」に移る**（§6.4）。
- 着順・時計・種・保存の行（`FINISH` ほか）は今と同じく全桁一致。`ser()` はレースの状態に触れない。

### 6.1 PIE の事実（出所つき）

### 6.2 どこに入るか

整数にした後の `ser()` を 3 つに分けて見る。

| 部分 | 中身 | 16 ビットのレーンに入るか | 見込み（推定） |
| --- | --- | --- | --- |
| **P1 弦の端の回転と `ou()`** | 弦の端 19 個をカメラ座標へ回し、5 系列 × 弦 18 本の 4 面の判定 | **入る。** 除外は余白 30 m・`s`（4 m 以上）つきの判定なので、位置を Q3 m（0.125 m、±4,095 m）に落とし、余白を 1 m 足せば安全側に倒せる。積は `f` 12 ビット × 位置 15 ビットで、`QACC` の 40 ビットに入る | スカラーの整数で約 3〜4k 命令/フレーム（0.02〜0.03 ms）。PIE で半分以下になっても **0.01〜0.02 ms** |
| P2 弦ごとの投影・切り出し・LOD | Q16 × Q30 の 64 ビットの積 約 50、除算 約 5、`isqrt`、段の数だけ回るループ | **入らない。** 32 ビットの乗算が無い。16 ビットに落とすと、位置を Q5 m にして手前の面で 1.5 px の誤差（`f·δ/Z = 50 × 0.03`）。除算と `isqrt` はレーンをメモリへ出してスカラーで行う。LOD のループは弦ごとに回数が違うので、最大回数まで全レーンを回してマスクする | 対象は 6.5〜10.8k カウントの 6 割ほど。うまく行って **0.1〜0.2 ms**。asm は数百命令になる |
| P3 柱の列（plan の Newton のループ） | 今は Shiki の `prail`・`pt` が 1 本ずつ歩く | 形を変えれば入る（柱の位置は添字の 1 次式、逆数は両端からの補間 ＋ Newton 2 回、段の中の奥行きの比は √2 以下）。ただし plan を通さず native が線分を出す別の経路になる | 対象は Shiki の engine 全体で実機 0.5〜0.66 ms（実測、重い窓、全部の draw）。shiki-jit.md §24.3 は `prail`・`pt` を「合わない式」とし、柵は draw の固定費が支配すると結論している |

**利用者の見込み「SIMD にできればかなり速くなる」は、この仕事については数字が支えない。** 大きい利得は倍精度をやめること（−65〜69k カウント）で、PIE が触れるのはその後に残る 7〜11k カウント（0.3〜0.5 ms）の一部。1 フレームの弦は 28 本・候補 41 本で、レーンを埋める数が少ない。ただし推定なので、実機の数字で確かめる段（S3）を置く。

### 6.3 P1 の核の設計（asm）

- **データ（SoA、int16、16 B 整列）**: 弦の端ごとに、カメラ座標の横 `V0`・奥行き `V1`（Q3 m、飽和）、法線の向きの横・奥行き `V2`・`V3`（Q14）。4 面 × 24 要素（19 個を 8 の倍数に切り上げ）＝ 192 B。弦は「端 j」と「端 j+1」の組なので、1 要素ずらした 2 本目の面を持つ（ずらしたロードは整列が崩れるので、ずらした写しを作る。＋192 B）。
- **回転（フレームに 1 回）**: 世界の位置からカメラの位置を引いた差（スカラーで Q3 に丸めて飽和）に、向き `d`（Q14、`EE.VLDBC.16` で全レーンへ）を `EE.VMULAS.S16.QACC` で 2 項積み、`EE.SRCMB.S16.QACC` で 14 ビットずらす。Q14 の向きの誤差は 6 × 10⁻⁵ で、除外の余白に対して無視できる。
- **判定（系列ごと）**: 奥行き `d = V1 + w·V3`、横 `l = V0 + w·V2` を積和で作り、4 面（手前・奥・左・右）を両端について比較し、`EE.ANDQ` で「両端とも外」、`EE.ORQ` で 4 面をまとめる。左右の面 `160·d ± l·f + k` は `QACC` に 3 項積んで符号を取り出す。
- **マスクの取り出し（分岐なし）**: 結果のレーン（`0xFFFF`/0）を重み（1, 2, 4, …, 128）と `EE.ANDQ` し、`EE.VMULAS.S16.ACCX` で定数 1 の列と積和して `rur.accx_0` で 8 ビットを得る。3 ブロックで 24 ビットの「視野に入る弦」の集合になり、`ser()` はそのビットを `nsau` で拾って回る（今の `continue` の分岐が、ビットの走査になる）。
- **端数**: 弦は 18 本（端 19 個）で 8 の倍数ではない。詰めたレーンには「必ず外」になる値（奥行き −4,095 m）を入れておく。結果はビットの集合なので、書き戻しのマスクは要らない。
- **範囲に入らない弦**: 直線コース（弦 1 本）と、両端の ±10,000 m の弦は Q3 の ±4,095 m を越える。飽和した端は直線の向きを変えるので、この 2 本はスカラーで判定する（表に印を付ける）。
- **書き方**: 既存の核と同じ（`main/ui/kasane/ksn_proc_grid_pie.c`・`ksn_blend_pie.c` の C の中の asm、`loopgtz` の本体は 256 B 以内、`"=&a"` の早期上書き、PIE はコプロセッサ 3 なので割り込みの中で使わない。pie-simd.md §1.3・§8）。

### 6.4 検査（3 層）と MCP を使う手順

1. **命令の確認（書く前）**: 使う命令を MCP `get_instruction` で引き（TRM のページ）、`manual_errata` に載っていないことを見る。載っていれば `instruction_encoding`・`decode_instruction` でアセンブラの出す語を確かめる。
2. **組めるか（書きながら）**: 核の断片を MCP `check_asm` に通す（ファームと同じ binutils）。オペランドの範囲の誤りはここで出る。
3. **停止の見積もり**: 命令の並びを `instruction_pipeline`（表の段と、実機で測った停止）と `measured_timing` で見て、ロード・積和の直後に使う並びを避ける。`pie_cost_estimate` に「ブロック 3、命令数、ストア数、ブロックの外のサイクル」を入れて下限と 1.3〜1.4 倍の帯を出す。**これは見積もりで、測定ではない。**
4. **host の模型**: `tools/pie/models/` に C の算術モデル（`QACC` の 40 ビットの飽和、`SRCMB` の床と飽和）を足し、`tools/pie/run_models.py` で、整数のスカラーの `ou()`（Q3 に落とした版）と全部の入力で一致することを見る。`tools/pie/piesim.py` で asm そのものを回す。`main/` のパスを直書きするので、ファイルを動かしたら `grep -rn "main/" tools/` で洗う（CLAUDE.md）。
5. **実機の照合**: 実機で、PIE の核とスカラーの核を同じ入力（デモのレースの全フレーム）で両方回し、マスクが違えば数える（`DERBY PIECHK mismatch=`）。0 であること。QEMU（r5sim）は PIE を実行できないので、r5sim の像ではスカラーの核だけを組む。
6. **実機の時間**: §7.3。

## 7. 実施計画

### 7.1 一度にやるか、分けるか

**分ける。** 理由: (1) 整数にする利得（推定 3 ms 強）と PIE の利得（推定 0.2 ms 以下）は 1 桁違い、同じ変更に入れると PIE の分が命令キャッシュの揺れ（同じ核でビルド間 15%、CLAUDE.md）に埋もれる。(2) PIE の核はスカラーの整数の核とビット一致で検査するので、先にスカラーが要る。(3) r5sim は PIE を回せないので、r5sim で測れる段と実機でしか測れない段を分けたほうが、どの数字が何を言っているかがはっきりする。(4) ただし §6.3 のデータの並び（弦の端の SoA、ビットの集合で渡す視野）は S2 で先に入れておき、S3 は核の差し替えだけにする。

### 7.3 測り方

- **r5sim（S0〜S2）**: `tools/r5sim/fast.sh <dir> -DR5SIM_DEVICE=1 -DR5SIM_APP=derby`、`R5SIM_ICOUNT=shift=2,sleep=off`。段の前後は同じチェックアウトから組んだ像どうしで比べ、0.05% 未満の差は配置として読む（api-reorg-perf.md §2）。区間は `-DR5SIM_DERBY_PROF=1` の `R5SIM serprof`。着順・時計が前後で同じこと。
- **実機（S1〜S3）、同じバイナリの A/B**: broker の `app_session` で DERBY を開き、デモのレースを走らせ、レースの途中で `action: up` を押して経路を切り替える（[derby-runners-native.md](derby-runners-native.md) §7 と同じ作り）。
  - 今の `up` は走者の JS / NATIVE を反転する。**この作業の間は、`up` を「`ser()` の経路」の切り替えに使う**（案: 押すたびに `DERBY AB SER Q` → `DERBY AB SER D` →（S3 では `DERBY AB PIE 0`）→ 戻る）。既存の印 `DERBY AB JS`・`DERBY AB NATIVE` はバイト単位で残すか、走者の A/B を退役させるかは利用者の判断（§8）。
  - 切り替えは native の旗 1 つ（`pocket.derby` の関数 1 個）で、JS は旗を反転して印を出すだけにする。**切った側で、変更の全部が戻ること**を、計器 1 つ（`ser` の中のサイクルの合計）で確かめる（pie-simd.md §3.4「半分だけ戻すスイッチ」）。
  - 窓: `SHIKI_TURN` の draws が 45 以上・`pat=` が 37 以上のターンだけを重い WIDE 2 として集め、同じレースの中で A・B を交互に 4 窓以上取り、中央値を比べる（pie-simd.md §6.2）。切り替えの直後の 3 ターンは捨てる。
  - PIE（S3）は 1 ターンの時間では見えない見込みなので、`view()` と `ou()` を囲んだ `CCOUNT` の差を 64 フレームごとに合計して出す（`DERBY SERCY view= cull=`）。計器を入れた像で、入れる前と場面のカウントが変わらないことを r5sim で見る（pie-simd.md §6.5）。
  - 実機を使う間は、作業用の一時領域のロックで順番を取り、終わったら通常の像に戻す（CLAUDE.md）。
- **画素**: 実機では画素を読めない（MISO 未配線）。host の画素ハッシュと、実機の `FINISH` の全桁・draw の本数で見る。段 S1 の後に 1 回、利用者に実機の画面（重い WIDE 2 の柵・芝・スタンド）を見てもらう。

## 8. 利用者に決めてもらうこと

1. **画素の基準の作り直し。** 整数にすると、host の全画素ハッシュを 1 回取り直す。許容は「画面上の点が 1 px 以内、同値のときの柱・縞 1 本の入れ替わりは 1 万呼び出しに 1 回まで」（§5.1）。試作の実測は 0.1 px 以内・25 万呼び出しに 2 回。この基準でよいか、もっと緩く／厳しくするか。
2. **oracle の役割。** JS の `ser()`（`derby_ser_oracle.js`）を「幾何の参照」として残し許容差で照合する（推奨）か、JS の参照をやめて整数の C を仕様にするか。後者は検査が「C を C と比べる」ことになり、式の誤りを見つけられなくなる。
3. **倍精度の `ser()` を残すか。** 範囲外の戻り道と A/B のために残す（flash 約 5 KB、推奨）か、S2 の後に消す（範囲外はエラーにする）か。
4. **`up` の A/B。** 走者の JS / NATIVE の切り替え（`derby_ab.js`、P4b で測定済み）を退役させて `up` を `ser()` に使うか、状態を増やして両方残すか。
5. **`L = 0` の分岐。** アプリは使っていない。整数にしない（倍精度のまま残す）でよいか、分岐ごと消すか。
6. **PIE の試作を、利得が小さい見込みでも行うか。** 推定では P1 は 0.01〜0.02 ms で、1 ターンの時間には出ない。実機で「効かない」ことを確かめる意味はあるが、asm の核と 3 層の検査の手間がかかる。S1・S2 の実機の結果を見てから決める（推奨）か、先に約束するか。

## 9. 確信の低い点

- 実機の ms は全部推定（r5sim のカウント × 0.049 ms/1k）。r5sim は Shiki を C のモデルで回す。
- 整数の `ser()` の命令数（弦 1 本 1,500〜2,500）は、試作の静的な大きさからの推定で、実行して数えていない。S1 の r5sim で確定する。
- 除算の割合（約 40%）は、合成したカメラでの回数と、逆算した値段から。重い窓の実数は S0 で取る。
- float32 の fuzz の外れ（最大 147 px）の原因は調べていない。
- 試作の `ou()` は倍精度のまま。整数の `ou()`（S2）と PIE の `ou()`（S3）は余白を足して安全側に倒す設計で、候補の弦が数 % 増えうる（増えた弦は `lim()` で捨てられるので絵は変わらない。時間は少し増える）。
- 系列の表は、レース中に `s`・`g0` が変わらないことを前提にしている。段階（LIGHT・MID・HEAVY）をパドックで切り替えると系列が変わるので、`course()` で表を捨てる。レースの途中で段階が変わる経路があるかは確かめていない。
- Shiki の draw 1 回の固定費（d4 の根拠）は、今の Shiki v2 では測っていない。

## 利用者の決定（2026-11-13）

- **許容の基準:** 1 px より**緩くてよい**。見た目で破綻しなければ数 px の誤差を許す。検査は「描画が壊れない不変条件（飽和 0、本数 1〜255、弦のつなぎ目、Newton の始点と歩幅）」を必須とし、幾何の差は記録するが合否の門は見た目の破綻（欠け・跳び・裏返り）に置く。画素ハッシュは取り直す。JS の `ser()` は幾何の参照として残す。
- **倍精度の `ser()`:** 実機の同一バイナリ A/B が済むまで残す（範囲外の戻り道も兼ねる）。`up` のトグルを `ser()` の切り替えに使い、走者の JS/NATIVE（`derby_ab.js`）は退役させてよい。A/B の後に倍精度版を消す。
- **PIE:** 整数化（S1・S2）と**並行して**試作する（asm の核、esp32s3-hw MCP、実機の同一バイナリ A/B で利得を主張）。

## 10. PIE の試作 P1（段 S3 の核、2026-11-13、実装と host の検査）

利用者の決定（上）に従い、整数の `ser()`（S1、別の作業者が `pocket_derby.c` と `derby_ser_int.h` に書いている）と並行して、§6.3 の核を書いた。**`ser()` からはまだ呼んでいない。** 核とその仕様（スカラーの整数の参照）と検査だけで、既定 OFF の Kconfig `CONFIG_POCKET_DERBY_SER_PIE` の後ろにある（OFF ではファイルが空になり、製品の像は変わらない）。実機の数字はここにはまだ無い（§10.5 の欄を、実機で取ったら埋める）。

**データ（フレームに 1 回）**: 端ごとに、カメラからの差 `rx`・`rz`（世界の軸、Q3 m）と単位の法線 `nx`・`nz`（Q14）。回転の核がこれをカメラの向き（Q14、`EE.VLDBC.16` で全レーンへ）で回し、`lat`・`dep`（Q3）と `nlat`・`ndep`（Q14）を書く。`pocket_derby.c` の `VE[4j..4j+3]`（V0〜V3）の 16 ビット版。ブロック 1 つは `[rx|rz|nx|nz]` と `[lat|dep|nlat|ndep]` の 64 B ずつで、核は 1 本のポインタを 16 B ずつ進めるだけ。

**回転の核**（ブロックあたり 24 命令: ロード 4、`ZERO.QACC`・`VMULAS` 2・`SRCMB`（14 ビット）・ストアを 4 組）。`lat = ⌊(rx·cz − rz·cx)/2^14⌋` など。

**除外の核**（ブロックあたり 55 命令、`loopgtz` の本体 約 163 B）。系列（`w`, `m`）ごとに 1 回:

1. `l = ⌊(lat·2^14 + W·nlat)/2^14⌋`、`d` も同じ（`VMULAS` 2・`SRCMB` 14）。
2. 4 面を端ごとに判定し、レーンの中のビット（手前 1・奥 2・左 4・右 8）にまとめる: 手前 `d < TN`、奥 `TF < d`（どちらも `VCMP.LT`）、左右は `QACC = 1280·d + KA·KB + F·l` の符号と、そこから `F·l` を 2 回引いた値の符号（`SRCMB` をずらし 0 で使うと、飽和した 16 ビットの符号が残り、QACC はそのまま。左右で `1280·d + K` を 1 回しか積まない）。
3. 弦 j は端 j と j+1 の組。端のブロック e のビット `F_e` と、前のブロック `F_{e−1}` から、`EE.SRC.Q q0, F_{e−1}, F_e`（`SAR_BYTE = 2`）で 1 レーンずらした列を作り、`AND` が 0 でなければ「同じ面で両端とも外」。
4. 0 でないレーンを `VCMP.LT(0, x)` で `0xFFFF` にし、`EE.VMULAS.S16.ACCX` で重み (−1, −2, …, −128) と積和すると、`ACCX` がそのまま 8 ビットの集合になる。`RUR.ACCX_0` → `S8I` でブロックごとに 1 バイト。
5. ループはブロック 0 から回し、最初の周の出力（ゴミ）は捨てる（先頭を外に出さず、本体を 1 つに保つ）。DERBY の楕円は弦 18 本 → 弦のブロック 3、端のブロック 4、本体 4 周。

### 10.3 設計（§6.3）から変えたところ

- **端数の「必ず外」の値は、それだけでは足りない。** §6.3 は「詰めたレーンに必ず外になる値を入れれば、書き戻しのマスクは要らない」としたが、弦 `chords` は**本物の端** `chords` と詰めた端の組で、詰めた端が外でも本物の端と同じ面でなければ外にならない。核は詰めたレーンを 0 のまま回し、**結果を `valid`（範囲の中の本物の弦）で 1 回 `AND` する**。範囲の外の弦も同じ `valid` で外すので、追加の手間は 1 命令。
- **ずらした写し（＋192 B）は作らない。** 面の判定は端ごとに 1 回で済む（弦ごとにすると 2 回）ので、端ごとにビットを作り、ずらしは `EE.SRC.Q` でレジスタの中で行う。
- **右の面は左の QACC から引く**（`SRCMB` を 0 ビットで使うと QACC が変わらない）。`−2F` は int16 に入らない（`F` は 32,767 まで）ので `−F` を 2 回積む。
- **`derby_ser_int.h` はこの作業の木に無かった。** 参照は `tools/games/serq_proto/serq.c` と `pocket_derby.c` の `ou()` から自分で書き、`derby_ser_pie.h` に仕様として置いた。合流のときに S1 の整数の `ou()` と合わせる: (a) S1 の `ou()` がこの Q3 の形なら、その関数をこの参照で置き換える。(b) S1 が Q16 の正確な `ou()` なら、それを範囲外の戻り道として残し、核はこの Q3 の参照とビット一致、Q16 版とは「安全側（核が外なら Q16 版も外）」で照合する。入力は S1 の Q16 の位置・Q30 の向きをそのまま受け取る（`dsp_set_camera()`）。

### 11.1 入れたもの

### 11.7 実機の A/B の手順（まだ測っていない）

1. 通常の像を焼く（`up` の印は `DERBY AB INT` ／ `DERBY AB DOUBLE`。既定は整数）。

4. 切り替えの直後 3 ターンを捨て、A・B を交互に 4 窓以上取り、`KASANE_PAINT turn_ms` の中央値を比べる（§7.3）。受け入れ: 重い WIDE 2 で 2.5 ms 以上下がる、`LOADSTALL`・`FRAMEFAIL`・OOM なし、`memlog.py --port --check`。

- **実機の時間は全部推定。** r5sim の比（1k ≈ 0.049 ms）なら重い WIDE 2 で −83.7k ≈ −4.1 ms（11.6 → 約 7.5 ms）だが、r5sim は flash の待ちを数えず、整数のコード（`derby_ser_chord_q` 5.4 KB、-O2）は命令キャッシュに新しく載る。
- r5sim の `pocket_derby.c` は像の既定の -Os のまま（ファームは -O2）。前からの食い違いで、`derby_ser_int.c` だけはファームと同じ -O2 にした。
- native の heap（DERBY の実行中）: `course()` の塊 +約 1.2 KB（楕円: 端 19 個の整数の姿勢 380 B、Q16 の端 76 B、int16 の列 591 B、カメラの固定小数と plan の確認の表 約 140 B）と、系列の表 5 × 576 B ＝ 2,880 B（＋malloc の頭）。計 約 4.1 KB（計算）。倍精度の `VE` は残した（A/B の B のため）。**実機では `memlog.py --port` で確かめていない**（DERBY は native heap の余裕が 1〜2 KB と記録がある。docs/perf/frame-breakdown.md §9）。
- 整数の範囲（カメラ ±6,000 m、`s` 32 m 以下）はアプリと fuzz の範囲で決めた。範囲外は倍精度に戻るので絵は出る。
- 倍精度の経路は A/B の後に消す（利用者の決定）。消すと flash −約 5 KB、`ser_chord()` と `ou()` と `VE` が消える。

## 12. 実機で整数と倍精度の差が見えない件の診断（2026-11-13、STEADY）

### 12.1 問い

実機（`8bff275`、同一バイナリ、`up` で `DERBY AB INT` ↔ `DOUBLE`、`KASANE_PAINT turn_ms` の 30 フレーム平均）で、軽い CAM WIDE 2（draws 27〜29、`pat=9`）が INT 7.30〜7.46 ms・DOUBLE 7.24〜7.43 ms と差が無かった。VISION（33 draws）・CLOSE（20 draws）は横のカメラで `ser()` を呼ばないので、差が無いのは当然（r5sim でも ±0.1%）。問いは WIDE 2 だけ。

### 12.2 整数の経路は host で必ず通っているか（実測）

計装（§12.5 の `DERBY_SER`）を host の harness にも入れ（`KSN_HOST_CFLAGS=-DPOCKET_DERBY_SER_PROBE`、30 ターンに 1 行）、`run_derby.py --m32` の 16 構成を回した。

- plan の Q 形式の確認（`plan_q()`）がファームで外れる可能性: ファームの組み込みの表（`build/generated/ksn_shiki_rom.c`）の見出しを読むと、`derby.prail` `16,16,24,24,0,16,0,16`、`derby.pt` `16,16,24,24,0,16,16,24`、`derby.hl` `16×6,0,0`、`derby.crowd` `16×8` で、`derby_q_*` と一致する（実測）。host と r5sim と実機は同じ `ksn_shiki_register()` を通る。

### 12.4 費用の模型と候補（推定）

- **倍精度の算術はほぼ ROM。** `__divdf3`・`__muldf3`・`__adddf3`・`__subdf3`・`__divdi3`・`__udivdi3` は 0x4000xxxx（ESP32-S3 の内蔵 ROM、`nm` で確認）で、flash のキャッシュを通らない。整数の経路の 64 ビットの除算も ROM の `__divdi3`。
- **flash に載るコードの量は両方の経路で同じくらい**（-O2、`nm -S`、実測）: 倍精度は `js_ser` 1,836 B ＋ `ser_chord` 4,419 B ＋ `pose` 559 B ＋ `lim` 327 B ＋ libm の `floor`・`ceil`・`sqrt`（約 0.8 KB）＋ draw ごとの `ksn_shiki_from_double` 494 B。整数は `js_ser` ＋ `derby_ser_chord_q` 5,389 B ＋ `emit_q`・`plan_q`・`series_rows`（直線では `keep_mask` と回転・除外は走らない）。命令キャッシュは 32 KB・8 way・32 B の行（sdkconfig）、QIO のミス 1 回は約 450 サイクル（docs/vm/turn-icache.md §1.1.1、推定）。1 フレームの中で `ser()` の間に JS と Shiki が走るので、5 回の呼び出しのたびに冷えている（推定）としても、冷えたミスは両方の経路に同じくらいかかる。**命令キャッシュだけで 0.6 ms の差が消えるとは考えにくい（推定）。**
- `derby_ser_int.c` を -Os にすると `derby_ser_chord_q` は 3,771 B（＋`inrq` 175 B 等。-O2 は 5,389 B、実測）。行の数は約 3 割減るが、上の理由で決め手にはならない見込み（推定）。
- IRAM に置く（`CONFIG_POCKET_DERBY_SER_IRAM`、§12.5）と **DIRAM +6,552 B**（172,776 → 179,328、`idf.py size` 相当、実測）。全アプリのヒープから引かれる（CLAUDE.md）ので製品には入れない。測定の像で「flash の待ちの分」を分けるためだけに使う。
- **`turn_ms` の分母はフレームではなく tick。** `turn_ms = turn_sum/ticks` で、ターンの予算（`VM_TURN_BUDGET_US` 8 ms、L2c）で `frame()` が途中で止まると、続きのターン（continuation）も 1 tick として数える（`main/app_session.c`）。7.3 ms は予算の 8 ms に近く、倍精度の側だけ予算を越えて続きに分かれるフレームがあると、その窓の `turn_ms` は 1 フレームの JS の時間より小さく出る（推定。窓の中で何回分かれたかは今のログに無い）。計装は `ser()` の時間を view() 1 回（1 フレーム）あたりで出すので、この影響を受けない。
- 候補の順（推定）: (1) `turn_ms` の分母（続きのターン）か窓の場面の混ざりで、差が見えなかった。(2) 実機だけで整数の経路を外れている（native heap の `malloc` 失敗など）。(3) 実機で整数の経路のほうが命令あたり遅い（flash の待ち・`mull`/`muluh`・除算）。(1)〜(3) は全部 `DERBY_SER` の 1 行で切り分けられる。

### 12.5 入れたもの

- **`CONFIG_POCKET_DERBY_SER_PROBE`（既定 n）**: `main/pocket/pocket_derby.c` に計数と時間。既定の像では何も入らない（`SERP()`・`SERP_DRAW()` は空、関数表も前のまま。既定の像は Flash Code +4 B（下の直しの分）、DIRAM 0、実測）。ON の像は `KASANE_PAINT` の行の直後に 1 行:

  ```
  DERBY_SER mode=INT ticks=30 views=30/0 vfb=mode:0,qok:0,pos:0,f:0,zf:0 int=150 dbl=0
    fb=L:0,s:0,gw:0,plan:0,stands:0,malloc:0,table:0 tables=0
    int_cy=… int_draw=… dbl_cy=… dbl_draw=… view_cy=…/… draws=…/… chords=…/…
    int_insn=…/… int_ist=…/… dbl_insn=…/… dbl_ist=…/… badq=0:0000000000000000
  ```

  - `views=整数/倍精度`: その窓の `view()` の回数（パンのフレーム数）。`vfb`: `view()` が倍精度になった理由（`mode(1)`、コースが範囲外、カメラの位置・`f`・`zf`）。
  - `int=`・`dbl=`: `ser()` の呼び出しの数（経路別）。`fb`: 整数の `view()` の中で倍精度に戻った `ser()` の理由。`tables`: 作った系列の表。`badq`: Q 形式が合わなかった plan の入力数と Q 形式。
  - `int_cy`・`dbl_cy`: `ser()` 全体のサイクル（`esp_cpu_get_cycle_count`）、**パンの 1 フレームあたり**。`int_draw`・`dbl_draw`: そのうち Shiki の draw の分（幾何は差）。`view_cy`: `view()` のサイクル（整数/倍精度）。`draws`・`chords`: 窓の合計。
  - `int_insn=全体/draw`・`int_ist=全体/draw`（`dbl_` も）: コアの性能カウンタ（PM0 = 完了した命令、PM1 = 命令フェッチの停止サイクル。flash のキャッシュのミスはここに出る）、1 フレームあたり。`CONFIG_POCKET_VM_TURNPERF` と同じカウンタを使うので一緒に入れない。
  - host でも `-DPOCKET_DERBY_SER_PROBE` で同じ行（サイクルは 0）。
- **`CONFIG_POCKET_DERBY_SER_IRAM`（既定 n）**: `derby_ser_int.c` の毎フレームの関数（`derby_ser_chord_q`、`derby_ser_prepare`・`rotate_ref`・`cull_ref`・`cull_params`、`isqrt`・`plane`・`inrq`）を `IRAM_ATTR` に。測定の像だけ。
- **直し: `pocket_derby_reset()` が `ser_mode` を戻していなかった。** あるセッションで `up` を奇数回押して終わると、次の DERBY は JS の `AB = 0`（INT のつもり）のまま倍精度で走り、最初の `up` まで印と中身が逆になる。`reset()` で既定（整数）に戻すようにした。

### 12.6 実機の手順（親が broker で）

broker は既定の Kconfig でしか組めないので、一時の `measure:` コミットでマクロを直接立てる（`sdkconfig` が残っていても効く）。

1. **像 M1（計装）**: `main/pocket/pocket_derby.h` の `#ifdef ESP_PLATFORM` の直前に `#define POCKET_DERBY_SER_PROBE 1` を 1 行足したコミット（`measure: DERBY_SER probe`）。`main/Kconfig.projbuild` の `POCKET_DERBY_SER_PROBE` の `default n` を `y` にしても同じだが、ビルドディレクトリの `sdkconfig` に `# … is not set` が残っていると効かない。
2. broker の `app_session` で DERBY を開き、デモのレースを待つ。レースの間 `KASANE_PAINT` の直後に `DERBY_SER` が出る（パンの無い窓では出ない）。
3. WIDE 1/2/3 の間に `up` を押して `DERBY AB DOUBLE`、もう 1 回で `INT`。切り替えた直後の 1 窓は捨てる（`views=` が両方 0 でない窓）。
4. 読む値:
   - INT の窓で `views=N/0`・`int=5N`・`dbl=0`・`fb` が全部 0 なら、整数の経路は通っている。そうでなければ `fb`/`vfb`/`badq` が理由。
   - `chords=` が 1 フレーム 5（直線）か 18 以上（楕円）か。
   - 幾何のサイクル `int_cy − int_draw` と `dbl_cy − dbl_draw`（1 フレーム）。r5sim の見込み（直線、推定）は整数が倍精度より約 0.5 ms（約 12 万サイクル）少ない。
   - `int_ist − int_ist(draw)` と `dbl_ist − dbl_ist(draw)`: 幾何の命令フェッチの停止。`int_insn` が `dbl_insn` より大きく減っているのに `cy` が減っていなければ、停止の分が食っている。
   - `ticks` が `views` より多い窓は、フレームが予算で続きに分かれている（`turn_ms` の分母が増える）。
5. **像 M2（IRAM、M1 で幾何のサイクルが減っていなかったときだけ）**: M1 に加えて `main/pocket/derby_ser_int.h` の先頭（`#include` より前）に `#define POCKET_DERBY_SER_IRAM 1`。同じ手順で、整数の幾何のサイクルと `int_ist` を M1 と比べる（像が違うので配置の揺れ ±15% がある。比べるのは同じ像の中の倍精度との差）。
6. 終わったら通常の像に戻す。

### 12.7 確信の低い点

- 実機の場面が直線だったという読みは draws と `pat` の形だけによる（楕円の wide1 も 25・9）。`chords=` で確かめる。
- ms への換算（1k ≈ 0.049〜0.052 ms）は r5sim の比で、flash の待ちを数えていない。
- host の `--m32` の計装の像は既定の像と別のバイナリ（`-DPOCKET_DERBY_SER_PROBE`）。計数は経路の判定だけで、描画の結果は変えない（16 構成 PASS）。

### 12.8 次の段（利用者の方針、2026-11-13: 倍精度の `ser()` は残さない。まだ実装していない）

最終の形は「整数の `ser()` ＋ PIE の回転と除外の核（§10、実機の自己検査で核は 4.7 倍・不一致 0）」。§12.6 の M1 は倍精度を同じバイナリの参照に使うので、**M1 を測ってから**次の 2 段に進む。

1. **PIE を `view()`・`ser()` につなぐ（`up` は PIE ↔ スカラーの整数）。** `course()` で `dsp_set_course()`（法線は `qt30` の (−tz, tx)）、`view()` で `dsp_set_camera()`（`qpos`、`camq` の `ex`・`ez`・`dx`・`dz`）と `dsp_rotate_pie()` を 1 回、`ser()` ごとに `dsp_cull_consts()`＋`dsp_cull_pie()`、`valid` の外（±2,047 m を越える端）の弦は今の `derby_ser_cull_wide()`。スカラーの側は今の `derby_ser_rotate_ref()`・`derby_ser_cull_ref()`。PIE の除外の余白（m + 1 m）は整数の参照（m + 3 m）と違うので、残る弦の集合は違ってよいが、どちらも倍精度の `ou()` の安全側で、余分な弦は `lim()` で落ちる（host の画素ハッシュで確かめる）。`CONFIG_POCKET_DERBY_SER_PIE` は既定 y にし、host は `DERBY_SERPIE_HOST` の参照で回す。計装（§12.5）の `path` は「PIE / スカラー」に読み替える。
2. **倍精度の `ser()` を消し、範囲の戻り道を丸めに替える。** `L = 0` → 1、`s` → 0.25〜32 m に丸める、カメラの位置 ±6,000 m・`f` 32〜4,095 px・`zf` を範囲に丸める（アプリの範囲の中では何も変わらない。fuzz の範囲外の入力は絵が変わってよい）。`ser_chord()`・`ou()`・`VE`・`VC`・`mode()` の 1 を消す。host の `DERBY_SER_ORACLE` の倍精度のビット一致と `--ser-double` は、JS の oracle との許容差の照合（§11.4）だけを残す。flash −約 5 KB（§11.8）。
