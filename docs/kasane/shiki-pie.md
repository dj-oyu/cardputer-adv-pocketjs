# Shiki と PIE — PIE を前提にした形の見直し（草案 2、2026-11-01）

ユーザーの方針（2026-11-01）: **PIE 化を積極的に考える。PIE の都合で Shiki 側のインターフェースを変えることも射程に入れる。** この文書は、そのための事実の整理と、変える候補の比較。決定は §7 の一覧でユーザーに諮る。仕様（[shiki-spec.md](shiki-spec.md) v1.3）はまだ変えていない。

経緯: 草案 1（`71fbdf9`）→ SLOW の独立レビュー（重大 5・中 9・軽微 8）→ この草案 2。草案 1 からの主な訂正: 動機（§1。DERBY の背景の大半は解釈ではなく draw の固定費）、`crowd` の記述（今の `crowd` は `sin` を使わない）、`LINE_PATTERN` のブロックは 16 ビットに入らない（§3.2）、試作で測るもの（§6。QR 常駐は測る価値が無い）、SoA の番地の式、端数はマスクを推す（§3.4）。

## 1. どこに効き、どこに効かないか

- **v1.3 の PIE への下ろし（§8.4）は、実際の式に当たらない。** 下ろせるのは `EACH` の本体全体が `.H` と `i16` の `k = 0` の `FETCH`・`PUT` だけのときで、描画・`LOOKUP`・制御・32 ビットの命令を含む本体は下ろさない。DERBY の式（`apps/derby/derby_prog.js`）で、この条件を満たすループは 1 本も無い。
- **DERBY の背景の費用の大半は、解釈ではなく draw 1 回の固定費。** 実測（[derby-background-cost.md](derby-background-cost.md) §1・§3）: draw 1 回の固定費 約 100〜115 µs（JS→native、入力の読み取り、plan の開始）。柵・刈り目・距離標は 1 本 70〜80 µs で、大半が固定費。観客席 0.37 ms。**解釈が支配するのは観客（`crowd`）だけ**（1 draw 1,284 ステップ、846 µs。1 ステップ 約 0.45 µs）。したがって DERBY で PIE 化が取れる上限は、観客の解釈分 約 0.6〜1.2 ms/フレーム（推定）。
- **固定費の梃子の方が大きい。** 1 回の呼び出しで複数の handle を描く API（draw の束ね）は、この文書の範囲外だが、優先順位を比べる相手として挙げておく。データ領域（v1.3）は、すでに draw の回数を減らす方向の道具。
- **PIE の方向の正当化は、点の多い内容に置く。** 旧 API の型付きの点（`affineQ14Points`、最大 128 点。v1.3 でデータ領域に吸収し、PIE の速さを失った。[shiki.md](shiki.md) §5.12）、MEGADEMO の点の束、BIG WAVE の断面の列、これから書く粒子・群れ。ここでは要素ごとの計算を 8 レーンでまとめると、解釈の費用（命令 1 つ 55〜100 サイクル、[int-latency.md](../perf/int-latency.md)）が 8 要素に 1 回になる（推定）。

## 3. 見直しの軸（候補）

### 3.1 案 V: ベクトルの命令を式に持たせる（自動の下ろしをやめる）

8 レーンのベクトルの命令とレジスタを Shiki の命令集合に足し、その意味を **PIE の動きそのもの**で定義する。エンジンはループを探す解析も JIT もしない。

- **レジスタ**: ベクトル `v0..v7`（各 16 ビット × 8）、蓄積器 `acc`（40 ビット × 8）。**メモリ（`vm` の中、16 B 整列）に置く**。命令 1 つは「ロード 2・演算・ストア 1」程度で 5〜6 サイクル増えるだけで、振り分け（55〜100 サイクル）に比べて小さい。PIE の `QR` に命令をまたいで置く形（QR 常駐）は、買えるのが命令あたり 5〜15 サイクル、引き換えに `SAR` の共有・asm の順序・コプロセッサの退避の規則に依存するので、**仕様に書かず、採らない**（実装の都合で後から入れても意味は変わらない）。
- **ループ**: `VEACH 領域, 件数`。8 レコードを 1 ブロックとし、本体の命令は**ブロックに 1 回**解釈し、**1 回 = 1 ステップ**（10,000 の上限は時間の上限なので、振り分け 1 回が 1 ステップ）。本体の中では `BREAK_IF_GT`・`REPEAT`・入れ子の `EACH`/`VEACH`・描画を禁止する（登録で検査）。早期終了はスカラーで件数を求めて渡す。レーンごとの条件は比較と選択だけ。
- **命令（候補）**と意味:
  - `VLOAD v, 領域, 欄`・`VSTORE`（§3.3 の SoA の面から 8 レコード）。
  - `VADD.H`・`VSUB.H`（`sat16`）、`VMIN`・`VMAX`（符号付き）。
  - `VSPLAT v, r`: `sat16(r)` を全レーンへ（§2.3 の被演算子の規則と同じ）。
  - `VIOTA v`: レーンの番号 `ブロック·8 + レーン`。**`VEACH` の件数を 32,767 以下に限る**（黙って飽和させない）。
  - `VZACC`、`VMAC acc, a, b`（`acc_l = sat40(acc_l + a_l·b_l)`。飽和は結合しないので**命令の順が加算の順**）、`VMACK acc, a, r`（r は `sat16` してから）。
  - **`VACC32 acc, r`**: 32 ビットのスカラーを全レーンの蓄積器に正確に加える（`ksn_proc_points_pie.c` の並進と同じ分解、PIE の 4 命令）。Q16 の 32 ビットの原点（画素座標、`prail` の Q24 の z など）を、書き手が分解せずに扱える。例: `x = x0 + j·dx`（x0 は Q16 の 32 ビット）は `VZACC; VMACK acc, iota, dx; VACC32 acc, x0; VOUT v, acc, 12`。
  - `VOUT v, acc, s`（0 ≤ s ≤ 63）: `acc_l := ⌊acc_l / 2^s⌋`（40 ビットの算術右シフト）、`v_l = sat16(acc_l)`。**`VOUT` の後の `acc` はシフト後の値**（PIE の書き戻しのとおり）。
  - 比較 `VCMPLT`・`VCMPGT`・`VCMPEQ`: マスク（レーンが `0xFFFF` か `0` のビット列）を普通のベクトルのレジスタへ。`VSEL d, m, a, b` = ビット単位の `(a & m) | (b & ~m)`。
  - `VLOOKUP v, 表, i`: 表は **`i32` の領域**。添字は 16 ビットのレーンを符号付きとして読み、`0`〜`n − 1` に寄せ（`VMAX`・`VMIN`）、要素の**下位 16 ビット**（ビット列。飽和ではない）を取る。添字のシフト `g` は無い（16 ビットのレーンにシフトが無いため）。`SIN` の表（Q16、最大 65536）は 16 ビットに入らないので、Q15 の写しを別に持つ。補間は 2 回の表引き。`VUNZIP` のレーン順の実機確認が前提。
  - 横方向の還元 `VHMIN r, v`・`VHMAX`・`VHSUM`（外接矩形、和。PIE に命令が無いので、ストアしてスカラーで畳む）。
  - 入れないもの: 8 ビットの経路、`EE.VMUL.S16`（wrap、`SAR`）、32 ビットのレーン。
- **実装は 3 本**: PIE の asm、host 用の C の算術モデル（`ksn_proc_points_pie.c` の `KSN_PROC_POINTS_PIE_MODEL` と同じ形。`ksn_shiki.c` は host でもコンパイルして `shiki_diff.mjs` で比べているため）、JS の参照実装。**asm と C モデルの一致を、命令ごと・境界値ごとに実機で取る試験**（`local.shikitest` の拡張）を要件にする（今の §10.2 と同じ考え）。
- **エンジンの形**: ベクトルの case は `ksn_shiki_draw` に inline で足さない（`CUBIC` を inline していた頃の退行: 関数 8.1 KB、スタックへの追い出し、全命令 +6〜24 サイクル）。`data_op` と同じく `noinline` の関数 1 本へ。flash 約 1.5〜3 KB、`vm` に約 170 B（推定）。`ksn_shiki_vm` に `aligned(16)`。

比べた案: **案 L（今の方針の延長）**: スカラーの式から下ろせる列をエンジンが見つける。式の書き方が変わらない利点はあるが、§1 のとおり当たる式が無く、下ろした結果がスカラーと同じであることの証明が列ごとに要る。

### 3.2 案 E: 計算と描画を分け、列からまとめて描く

計算済みの列（データ領域）から **native のループで**まとめて描く命令を足す。1 本ごとの解釈が消える。

- `EMIT_POINTS`・`EMIT_LINES`（レコード = x0, y0, x1, y1）・`EMIT_POLYLINE`（ペンをつなぐ）・`EMIT_PATTERN`・`EMIT_CUBIC`。
- **座標は `i16` の領域の Q 形式で読む**（例 Q4 = 1/16 画素、±2,047 画素）。丸めは §4.5 の一般形 `⌊(raw + 2^(q−1)) / 2^q⌋`（q = 0 なら加算なし）。範囲外は今どおり **`INVALID`**（黙って捨てると、飽和した計算の誤りが隠れる）。途中で `LIMIT`／`INVALID` のときは `CUBIC` と同じく、それまでの線分は残りペンは動かない。1,024 線分・8,192 ラスタの上限は変えない（ベクトル化の後は、こちらが効いてくる）。
- **色**: レコードに持つなら、領域の型を見ず **16 ビットのビット列**として読む（`i16` の領域では 32768 以上の色が負に化けるため）。バッチの定数でもよい。
- **`LINE_PATTERN` のブロックは 16 ビットに入らない**（§4.7: `u0`・`u1` は Q16 で ±2^29、`w0`・`w1` は Q16 で ±2^24、`bits` は 24 ビット）。そこで `EMIT_PATTERN` は、座標と `u0`・`u1` を `i16` の領域の欄から読み（`u` は領域の Q 形式。例 Q3: DERBY の最大 2,714 セル × 8 = 21.7k が入る。Q16 へは engine が `SHIFT` する）、`w0`・`w1`・`bits`・色 A／B・周期を**バッチの定数**（レジスタか imm）にする。
- **今の `crowd`（P24、`derby_prog.js:97–116`）**は `sin` を使わない。段ごとに `move`＋`linePattern` が 3 本、`ya`・`yb`・`ua`・`ub` は段の番号 j について線形、色は段ごとに `cloth0`・`cloth1` が交互、模様は `body`・`head`、`w0`・`w1` は全段で同じ（`dy0`・`dy1`）。案 E では「段 = レコード、座標と u は `VIOTA` の線形で `VEACH` が作る → 偶数段と奇数段の 2 バッチ（色が交互のため）× 模様 2 種の `EMIT_PATTERN`」になる見込み。u の刻みが Q16 から粗くなるので、**画素は今と一致しない**（新しい命令なので許されるが、host の全画素の比べ方（`crowd_p24.mjs`）を作り直す費用がかかる）。
- **合わない式**: `gate`（`dx *= shrink`。前の周回に依存。9 回なのでスカラーのまま）、`prail`・`pt`（Newton の反復が前の値に依存）、`dust`（粒子ごとの 2 段の `break` → マスクで書けるが `sin` 3 回）、`bokeh`（1 レコードから 8 本で 16 欄、`k_rec` の上限 8 を超える。`EMIT_POLYLINE` を 1 粒子ずつか、`EMIT` が複数の領域を取る形か）。`runner`・`silk`・`pole` などループの無い式は対象外。`rail`・`turf`・`stands` は書けるが、§1 のとおり固定費が支配し得が無い。

### 3.3 案 S: データ領域を SoA にする

> 2026-11-01: 採用し、仕様 v1.4 に入れた（AoS は廃止）。JS API の形はこの節の案と違い、仕様 §9.3 のとおり**窓は詰め物を含む領域全体**で、欄ごとの view は別の呼び出し `shiki.fields(窓)` が要るときだけ作る。

- **欄ごとの面**（structure of arrays）。番地は **`c · stride + j`**（欄 c の面の中のレコード j）、`stride` = レコードの数を 8 に切り上げた値。面の先頭は 16 B に揃う（区画の 16 B 整列 × stride が 8 の倍数）。今の `c · k_rec + b + j`（AoS）を置き換える。スカラーの `FETCH`・`PUT`（§5.4 の 6）と検証の結果の行（§10.1 の領域の並び）も同時に変える。
- 理由: PIE の 128 ビットのロード・ストアは 16 B 整列必須・部分ストア無し。SoA なら欄の 8 レコードが 1 回のロード。AoS では `VUNZIP`・`VZIP` で分解・組み立てが要る（`k_rec` 3 以上は手間が増え、レーン順は未確認）。既存のカーネルもすでに SoA。
- **JS の窓**: `data()` は、窓（全体の型付き配列）と**欄ごとの `subarray` の配列**を返す（`{window, fields: [...]}`）。書き手は `fields[c][j]` で書ける。同一性の比較（§9.2）は窓のオブジェクトのまま。面の末尾の詰め物（stride − レコードの数）は窓の外に置く（`subarray` の長さはレコードの数）。

### 3.4 端数（8 の倍数でない件数）: マスクを推す

- **T2（マスク）を推す**: 最後のブロックだけ、`VSTORE` のときに旧値と混ぜる（旧値のロード・`VCMPLT iota, N`・`ANDQ`・`XORQ`・`ORQ`・ストア で約 6 命令、**ループに 1 回**）。振り分け 1 回より安い。v1.3 の「`N` 以降に触れない」（§5.3 の 4、§8.4）と `take(n)` の意味を変えずに済む。面の詰め物（窓の外）には自由に書いてよい、と決めれば、`N` = レコードの数のときはマスクも要らない。
- T1（ブロック単位で書く）は、同じ領域にスカラーとベクトルの両方が書く式で、書き込みの範囲が食い違う（書き手の穴）。

### 3.5 数の型

- ベクトルの側は **16 ビット + 40 ビットの蓄積器**に限る（PIE に 32 ビットの乗算が無い）。積の和は `VMAC` で 40 ビットに積み、最後に 1 回だけ取り出す。`.H` の `MUL.H` を連ねるより精度も命令数も良い。
- 32 ビットの値は `VACC32` で蓄積器に入れる（§3.1）。

### 3.6 `@shiki` の記法

- **変換器は自動でベクトル化しない。** 書き手がベクトルのループと型を宣言し、変換器はその型で命令を選ぶ。形の候補: `for (const [x, y] of pts.lanes())` の中では名前が 8 レーンのベクトル、`lane()` が `VIOTA`、蓄積器は式 `a*b + c*d + x0` を変換器が `VMAC`／`VACC32`／`VOUT` に割り付ける（シフト量は §8.3 の規則 4 と同じ考えで Q 形式から決める）。具体は仕様の草案で決める。

## 4. 変えない（変えるべきでない）もの

- 32 ビットのスカラーの命令（v1.2）と、その実機・host の突き合わせ。スカラーは制御・基準点・1 回きりの計算に残る。
- 「2 つの独立した実装がビット単位で一致する」こと（§1.4）。ベクトルの命令の意味を PIE の動きで定義し、JS の参照実装・C の算術モデル・PIE の asm を比べる。
- Shiki のヒープ・データ領域の寿命・`transfer` の門（v1.3 §9）。

## 5. v1.3 との互換

領域の並び（案 S）は v1.3 の番地の規則を変える。v1.3 を使うアプリはまだ無い（移行の段階 3 の前）ので、今なら変えられる。端数を T2 にすれば `take(n)` の意味は変わらない。

## 6. 仕様を書く前に試作して測ること（実機、同じバイナリの中で）

1. **ベクトルの命令の費用と比**: メモリ常駐の `VEACH`・`VLOAD`・`VSTORE`・`VIOTA`・`VMACK`・`VACC32`・`VOUT` を `noinline` の関数 1 本で試作し、128 点のアフィン変換を、スカラーの `EACH` の同じ計算と比べる（`cycle_bench` に行を足す）。得たい数は「ベクトルの命令 1 つのサイクル」と「スカラーとの比」。
2. **列からの描画の費用**: `EMIT_LINES` の native のループの 1 本あたりと、今の `MOVE`＋`LINE`（約 5 µs/本）。
3. **`crowd` を案 V＋E で書き直し、観客の 1 draw（今 846 µs、BGP）を測る。** DERBY で取れる唯一の実益なので、**この数が出るまで仕様に書かない**。host では全画素を比べ、差が u の刻みの分だけであることを説明できること。
4. ELF 全体の `ee.` の出現箇所の一覧、`EE.LD/ST.QACC` の往復のサイクル、`VZIP/VUNZIP` のレーン順（`VLOOKUP` を採るなら）。

## 7. ユーザーに決めてもらうこと（案）

| 1 | ベクトルの命令を式に持たせるか（案 V）、自動の下ろし（案 L）を続けるか | 案 V（レジスタはメモリ常駐） | 当たる式がある。解析と証明の負担が小さい |
| 2 | 列から描く命令を足すか（案 E） | 足す。16 ビットに入らないパターンの値はバッチの定数 | 描画 1 本ごとの解釈を消す |
| 3 | 領域を SoA にするか（案 S） | する（`c·stride + j`、欄ごとの `subarray`） | 128 ビットの整列ロード 1 回 |
| 4 | 端数 | マスク（T2） | `take(n)` と「N 以降に触れない」を保つ |
| 5 | ベクトルの数の型 | 16 ビット + 40 ビット、`VACC32`、横方向の還元 | PIE に 32 ビットの乗算が無い |
| 6 | 列の描画の範囲外 | 今どおり `INVALID` | 誤りを隠さない |
| 7 | 進め方 | §6 の試作 1〜3 を先に。仕様（v2 の草案）は数が出てから | 動機の大きさが推定 |
| 8 | draw の固定費（約 100 µs/回）を下げる API（束ね）を、この作業と比べてどちらを先にするか | （要相談） | DERBY の背景ではそちらが大きい |

## 8. 試作の結果（2026-11-01、実機）

§6 の 1・2 と、案 S（SoA）の効き目を、1 つのバイナリの中で測った。コードは `6b8e7c9`（P1: C モデル）・`50594ea`（P2: PIE）・`f3ec673`（案 S）。測ったのは `f3ec673`（ELF `03cb0b28…`）。ログは [logs/shiki-pie-20261101-f3ec673.txt](logs/shiki-pie-20261101-f3ec673.txt)。

### 8.1 試作の形（仕様ではない）

- **命令**（`main/ui/kasane/ksn_shiki.c`、op 27〜42）: `VEACH`（8 レコードを 1 ブロック、本体の命令 1 つをブロックに 1 回・1 ステップ、端数はマスク）、`VLOAD`・`VSTORE`（`i16` の領域の欄）、`VSPLAT`・`VIOTA`・`VADD`・`VSUB`・`VMIN`・`VMAX`（16 ビット、飽和）、`VZACC`・`VMAC`・`VMACK`・`VACCSET`・`VOUT`（40 ビットの蓄積器、`VOUT` は floor のシフトと sat16、シフトした値を書き戻す）、`EMIT_POINTS`・`EMIT_LINES`（領域の列から native のループで描く、§3.2）。登録の検査: `VEACH` の本体はベクトルの命令と `END` だけ、ベクトルの命令は `VEACH` の外に置けない、入れ子不可。
- **ベクトルのレジスタと蓄積器はメモリ**（`vm` の中、16 B 整列）。PIE の経路では蓄積器を QACC の像のまま置き（`EE.ST/LD.QACC_*` で命令ごとに退避と復帰）、C からはその並びを読まない。C モデル（`int64_t[8]`）と PIE は draw の始めに `ksn_shiki_vec_pie` で決まり、1 回の draw の中で混ざらない。
- **PIE の経路**: 整列した満杯のブロックの `VLOAD`（1 欄の面は `EE.VLD.128`、AoS の 2 欄は `EE.VUNZIP.16`）、`VSTORE`（面のみ）、2 項の演算、蓄積器の全命令。端数・非整列・AoS の 3 欄以上の読み・AoS の書き込み・`VIOTA` は C のレーンのループ（ベクトルのレジスタは同じメモリなので混ぜてよい）。
- **案 S**: 領域の表の byte 3 の bit 1 で、欄 c・レコード j を `c·records + j` に置く。試作ではレコード数を 8 の倍数に限る（stride = レコード数）。`FETCH`・`PUT`・`VLOAD`・`VSTORE`・`EMIT` が両方の並びを読む。
- **対になったプログラム**（`ksn_shiki_bench.c`）: 同じ値を 4 つの形（スカラー／ベクトル・束ね × AoS／SoA）で描き、host の試験（`tools/kasane_contract/test_shiki_vec.c`、109 件）が**全部の形で線分が一致する**ことを確かめる。affine128 は直接の計算とも一致する。

### 8.2 PIE と C モデルの照合（実機、11 件）

同じプログラムを C モデルと PIE で 1 回ずつ描き、状態・ステップ・ペン・レジスタ・線分・ベクトルのレジスタ・領域の中身のハッシュを比べた。

| 照合 | 結果 | わかったこと |
| --- | --- | --- |
| tail（N=13、飽和の加算・減算・min/max・`VSPLAT` の飽和） | 一致 | 端数の戻り道 |
| unzip（AoS 2 欄の読み） | 一致 | **`EE.VUNZIP.16 q0, q1` は q0 に偶数番目、q1 に奇数番目**（TRM に無いレーン順を実機で確定） |
| record3（AoS 3 欄、C の戻り道） | 一致 | |
| sat40 up／down（640 回の積和） | 一致 | `EE.VMULAS.S16.QACC` は 40 ビットで飽和する |
| writeback | 一致（31250） | **`EE.SRCMB.S16.QACC` が書き戻すのはシフトした値で、sat16 の前**（2047 ではない） |
| accset（int32 の 4 値） | 一致 | `VACCSET` の分解（`ksn_proc_points_pie.c` と同じ）と QACC の像の往復 |
| **shift32** | **不一致** | シフト 33 は一致、**40 か 63（またはその両方）で PIE と C が食い違う**。どちらかは未確定。試作は `VOUT` のシフトを 0〜32 に制限した（照合のプログラムも 32・31 に変更し、`f505b0e` の実機で一致。[logs/shiki-pie-20261101-f505b0e.txt](logs/shiki-pie-20261101-f505b0e.txt)） |

### 8.4 読み方

- **一番効くのは解釈を減らすこと**（実測）。affine128 はベクトルの命令にするだけで（C のまま）2.9 倍、lines100 は `EMIT_LINES` で 5.8 倍（1 本 3.0 µs → 0.52 µs）。命令 1 つの振り分けの床（`SET` 57 サイクル）が、レーンの計算より大きい。
- **PIE の上乗せは 1.46 倍**（ベクトル AoS、C モデル 62,159 → PIE 42,691 サイクル、実測）。命令 1 つあたりに直すと、C のレーンのループ 約 215 サイクル → PIE 約 125 サイクル（**推定**: 描画 `EMIT_POINTS` 128 点を lines100 の `EMIT` から 1 点 125 サイクルと見積もって差し引いた。点だけの費用は測っていない）。PIE の命令 1 つの残りは、振り分け（約 57）と、蓄積器の退避と復帰（QACC の 8 命令）と関数の呼び出し。
- **案 S（SoA）の効き目は、この負荷では小さい**（実測）: ベクトル・PIE で −1,417 サイクル（−3.3%）、C モデルで −0.7%、スカラー（`FETCH` の番地）と `EMIT` は差なし（±0.4%、命令キャッシュの揺れ ±15% の内側）。AoS の 2 欄の読みは `VUNZIP` で安く、差は `VSTORE` が AoS で C の戻り道に落ちた 32 回分（1 回 約 44 サイクル、計算）だけだった。**3 欄以上の AoS（C の戻り道）の時間は測っていない**ので、SoA が要るかは `k_rec` 3〜8 の負荷を測ってから決める。
- 空の draw は 264 サイクル（1.1 µs）。DERBY の draw 1 回の固定費（約 100〜115 µs、[derby-background-cost.md](derby-background-cost.md)）は、エンジンの外（JS→native、入力の変換、frame への複写）にある。
