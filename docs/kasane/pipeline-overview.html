Kasane の描画パイプライン

JS の frame() が呼ばれてから LCD に画素が届くまでを、コードを追って図にしたもの。画面全体の画素を RAM に持つ「フレームバッファ」は無く、画面は 8 行ずつの帯で毎回組み立てて送る。Shiki が持っているのは画素ではなく「線分の並び」（描き方の記録）で、それが複数ある理由も扱う。ファイルと行は c4d7a6c 時点（2026-11-03、Shiki の作業領域を廃止したコミット。file:行 で示す）。数値には 実測 推定・計算 未確認 の印を付ける。

0. 先に結論

画面は「状態から毎回組み立てる」

RAM にあるのは画面の説明（Kasane のコマンド最大 80 個と、Shiki の線分の並び）だけ。描くときは 240×8 画素（3,840 B）の帯 1 本を作業台にして、上から 17 本、説明を全部その帯に描き込んでは LCD へ送る。TypeScript の感覚で言えば、仮想 DOM を毎回 8 行分だけ実体化して送り、送ったら捨てるのに近い。

Shiki の「複数の並び」は、画素ではなく記録

1 面につき表示中（committed）と組み立て中（candidate）の 2 つ。どれも 10 B の線分を並べた配列で、画素は持たない。組み立て中を表示に切り替えるのは、LCD への転送が成功した後（pocket_shiki_frame.c:670）。c4d7a6c の直前までは、もう 1 つ、draw 1 回の下書きの作業領域（workspace、1,024 本分）があった。残る 2 つを 1 本にする案は見送った（§10）。画素を持つのは image の面の帯のキャッシュ 3,840 B だけ。

1. 1 ターンの全体

描画タスクは 1 つ（ui_task、main/main.c:1080）。アプリの実行中は 1 周ごとに tick_run() → app_tick() を呼び、その中で JS の frame() と転送が同じ関数の中で順に起きる。並行に走るのは SPI の DMA だけ。

  1. 入口。ui_task は実行中なら tick_run(have,&stroke)（main.c:1196）、その中でキーをボタンの bit にして app_tick(buttons)（main.c:964）。押した後に離した状態のターンをもう 1 回回す（main.c:966）。
  2. 前置き。app_tick の頭で、前のターンから残った提出物があれば先に転送だけして帰る（app_session.c:2248–2264）。続けて run_pumps() が各面の pocket_*_pump() を決まった順に呼ぶ（app_session.c:2140–2181）。ここで解決した Promise は、この後の frame() から見える。
  3. JS。dispatch_guest() → pocketjs_guest_frame()（app_session.c:2195–2200）。DERBY なら derby_scene.js:144 の SK.beginFrame(4) から derby_scene.js:176 の SK.commit() までが 1 フレームの Shiki の描画。Kasane のノード（文字・矩形）は patch / replace で別に提出する。
  4. 後始末。end_guest_turn()（app_session.c:2188）が pocket_proc_end_turn()（pocket_shiki_frame.c:562）を呼び、組み立て中のフレームを閉じる。frame() が VM に途中で止められた（park）ときだけは閉じずに次のターンへ持ち越す。
  5. 転送。present_frame()（app_session.c:2481）が表示ポート（作業台の帯 kasane_strip、送り口 kasane_send、240×135、8 行）を組んで Kasane に渡す（app_session.c:2507–2509）。Kasane は傷んだ帯だけを上から順に合成して送り、最後の DMA を待ってから「表示された」と記録する。
  6. 待ち。JS アプリの表示周期は 33 ms（VM_DISPLAY_PERIOD_MS、app_session.h:103）。使った時間を引いた残りを待つ（main.c:1401）。

2. なぜフレームバッファが無いか

大きさ

240 × 135 × 2 B（RGB565）= 64,800 B 計算。PSRAM は無く、内部 RAM は約 334 KiB。ホーム画面の空き heap は 280,932 B 実測（CLAUDE.md）で、アプリを動かすと JS のゲストに最大 160 KiB（app_session.c:1509）、Shiki の区画に既定 48 KiB を取る（DERBY は一時 56 KiB にし、94439f7 で 48 KiB に戻した。56 KiB の時の DERBY の起動後のシステムの空きは 37,308 B 実測、shiki-jit.md §21.3・§22.1）。64,800 B の 1 枚が丸ごと入る場所が、アプリの実行中には無い。

代わりに常駐するのは、作業台の帯 shared 3,840 B（board.c:37）と転送用の tx_buf 3,840 B（board.c:67）の計 7,680 B。フレームバッファの約 12%。

絵を覚えているのは LCD の側

パネル（ST7789）は自分の表示用メモリ（GRAM）を持ち、書かれた画素を送られ直すまで表示し続ける。だから変わった帯だけ送れば足りる。番地の窓を開く命令は CASET／RASET／RAMWR（board.c:478–482）で、可視の 240×135 は x=40、y=53 から始まる窓（パネルのメモリの方が大きい）。

ただし MISO が配線されていないので GRAM は読めない（board.c:357–361）。「いま画面に何が出ているか」は、ソフトの側の記録（Kasane の確定済みのコマンドと、Shiki の committed）でしか分からない。転送に失敗した帯は、記録から描き直す（修復、pocket_shiki_frame.c:677–688）。board_capture は byte swap の前の作業台を写すので、画面の正しさの証拠にはならない。

クラウドの言葉に置くと、LCD は「PUT はできるが GET ができない」オブジェクトストア。正本は手元の状態（説明）で、ストアには差分の帯を上書きしていく。

3. 帯（strip）と転送

帯は 8 行（STRIP_H、board.h:7）。135 行は 8 で割り切れないので 16 本 × 8 行 + 最後の 1 本 × 7 行 = 17 本（ksn_render.c:2098 の rows=band==16?7:8）。全幅の帯 1 本は 240 × 8 × 2 = 3,840 B、17 本で 64,800 B。

転送用バッファは 1 本（CLAUDE.md の「2 本」は古い）

CLAUDE.md のアーキテクチャの節は「転送用バッファ2本（tx_buf、1本が送信中のあいだにもう1本へ書く）」と書いているが、今のコードは tx_buf が 1 本（board.c:63–68 の注記「One TX payload; every write waits for the exact previous descriptor」）。634ac07（PR #37 の取り込み）で 1 本になった（kasane-dma-overlap.md の「単一 3,840 B TX payload」）。重なるのは「CPU が shared で次の帯を合成する」と「DMA が tx_buf を送る」の 2 つで、swap して写す処理は前の送信の完了を待つ。SPI は 80 MHz（board.c:363）、デバイスのキューは 1（queue_size=1）。

1 本の帯の送り方（コードの順）

  1. Kasane が shared に帯を合成（ksn_render.c:2096–2357）。
  2. kasane_send()（app_session.c:584）: テキスト欄を帯に重ねる（pocket_text_overlay、:604）。
  3. kasane_dma_submit()（app_session.c:565）: 前の帯の DMA の結果を回収（board_present_finish → tx_reap、board.c:660、94）。
  4. board_present()（board.c:436）: ペットとマイクの印を重ね（:438–443）、必要なら窓を開き（:476–483）、shared を byte swap しながら tx_buf へ（:504–507）、DC を上げて spi_device_queue_trans（:532）。待たずに戻る。
  5. 全帯の後、最後の DMA を待ち（ksn_render.c:2388–2389）、成功なら Kasane の確定（ksn_core_presented、:2394）。

時間の目安

17 帯の線の時間64,800 B × 8 bit ÷ 80 MHz = 6.48 ms 計算、命令とすき間を除く 全画面の転送7.7 ms 実測（main.c:1011 の注記） 40→80 MHzsend 15.5 → 9.1 ms 実測（board.c:356–358、当時の経路） 帯 1 本の固定費約 17 µs（8 行×240 の塗りほか）実測（derby-background-cost.md §2、2026-09-30） DERBY の render9〜10.5 ms、うち Shiki の帯の線描き 1.1〜2.6 ms、残り約 7.4 ms は全画面の image と HUD の文字の合成 実測（同 §1、2026-09-30。float の VM の頃の計測で、帯の経路は今と同じ）

5. 帯の中の重ね合わせ

帯 1 本を作るときは、その帯にかかる層を全部、下から順に shared へ描く（画家のアルゴリズム）。描き終わった帯はもう読まないので、次の帯で同じ 3,840 B を使い回せる。

Shiki が下地になる場合（backdrop）

面 0 を resource() で image にしていないアプリでは、Shiki のフレームが帯の下地そのもの。pocket_proc_backdrop()（pocket_shiki_frame.c:651–660）が帯を背景色で塗り、その帯にかかる線分を描く。この形の commit() は pocket_kasane_proc_publish() で画面全体を傷にする（pocket_kasane.c:2924）。帯ごとの hash による絞り込みは使わない。

Shiki が image になる場合（DERBY）

SK.resource({maxSegments: 768})（derby_view.js:9）で面 0 が image の資源になり（pocket_kasane.c:1086）、シーンの tx.image({resource: res, bounds: [0,0,240,135]})（derby_scene.js:29）が ② の APP の層に入る。合成はその image を 32 画素ずつ読む（image_span、pocket_shiki_frame.c:586）。commit() は帯の hash で傷を絞る（pocket_kasane.c:2941）。

6. Shiki の線分の並び

線分（segment）とフレーム

ksn_proc_segment = {int16 x0, y0, x1, y1; uint16 color} = 10 B（ksn_shiki_frame.h:16）。1 画素幅の直線（Bresenham）。両端が同じなら 1 点。座標は −480〜720 まで許す。模様の線（LINE_PATTERN）は 2 つ分を使う（ksn_shiki_frame.h:17–31）。

フレーム ksn_proc_frame = 見出し 6 B（count、raster_steps、ready、ext）+ 線分の配列（ksn_shiki_frame.h:36–42）。上限は 1,024 本（KSN_PROC_SEGMENTS）で 10,246 B。面ごとに maxSegments（1〜1,024）で短く取れる（pocket_shiki_frame.c:62–81）。DERBY は 768 本で 6 + 7,680 = 7,686 B 計算。DERBY の 1 フレームの最多は 583 本 host 実測（apps/derby/README.md:234）。

ラスタ化は帯ごと（ksn_proc_render_band、ksn_shiki_frame.c:129–168）。帯 1 本を描くたびに、フレームの線分を最初から最後まで全部見る。縦の範囲が帯にかからない線分は 1 回の比較で飛ばし（1 線分 × 1 帯で 50 ns 実測、derby-background-cost.md §2）、かかる線分は、帯の上端までの Bresenham の位相を割り算で復元してから（:142–158）帯の中だけ画素を置く。17 帯なら 17 回なめる。

線分の順が描く順なので、後の線分が前の線分を上書きする。

並びは 1 面に 2 つ（c4d7a6c の時点）

なくなった 3 つ目: workspace（c4d7a6c まで）

直前の 56949dc までは、draw 1 回分を必ず 1,024 本入る下書き（workspace、10,246 B）へ書き、出し終えてから「candidate の残りに入るか」を調べて memcpy していた。入らない draw を「全部か無か」にするための一時置き場で、共用体として image の帯のキャッシュも兼ねていた。c4d7a6c で VM が出してよい本数 cap を持つようになり（ksn_shiki_vm.cap、ksn_shiki.h:147、ksn_shiki_draw_index_cap :206）、下書きと写しが消えた。残ったのは image の面の帯のキャッシュ（image_band_buf、240×8×2 = 3,840 B、pocket_shiki_frame.c:123–124）。image の面が選ばれた時に取る（pocket_shiki_frame.c:577–584）。経緯は shiki-jit.md §22。

帯の hash（どの帯が変わったか）

commit() で band_signature()（pocket_shiki_frame.c:215–239）が、17 本の帯それぞれについて、その帯にかかる線分の生のバイトを順に FNV-1a で混ぜ、線分の左右の範囲も記録する。pocket_proc_band_damage()（:240–260）が committed の hash と比べ、違う帯だけを傷にし、列は 2 つのフレームの範囲の和。背景色が変わったか、まだ committed が無ければ全帯。帯の画素は「背景色と、その帯にかかる線分の並び」だけで決まるので、hash が同じなら描かずに済む。

別に frame_damage()（:184–214）が 2 つのフレームの全線分の外接矩形を出す。帯の hash が使えないときの予備（pocket_kasane.c:2943–2944）。

9. JIT の位置

JIT は ⑤ の draw の中だけに関わる。よく描かれる式（4 回目から）を Xtensa / PIE の機械語にして、インタプリタの代わりに走らせる（ksn_shiki.c の ksn_shiki_jit_run 呼び出し）。出力は同じ線分で、行き先も同じ candidate の末尾（線分は C の helper が出すので、cap の検査も同じものを通る。shiki-jit.md §22）。帯の合成・転送は何も変わらない。コードの置き場所は上の区画の上側の空きで、持ち主の確保が足りなくなれば返す。詳しくは Shiki JIT とメモリ配置（図解） と shiki-jit.md。

11. 研究: 帯のバッファ（ピンポン・一本化・並び替え）

2026-11-03 の議論と調査の記録。まだ何も入れていない（LCD の並び順の確認用ビルド d4fcfc4 を除く）。

今の形と、memcpy に見えるものの正体

帯のバッファは 2 本ある。描く用の shared（board_strip()、3,840 B）と、送る用の tx_buf（3,840 B）。CPU が shared に帯 N+1 を描く間、DMA は tx_buf から帯 N を送る（board.c の board_present()、g_board_async=1）。待ち合わせは、帯 N+1 を tx_buf へ移す一瞬だけ。

  • 移しは memcpy ではなくバイトの入れ替え。ST7789 は RGB565 を上位バイトから受け取り（リセット時の既定）、CPU は下位バイトから書く。入れ替えはどのみち全画素に要るので、入れ替えながら tx_buf に書けば（g_board_swap_into=1）、移しの手間はほぼ増えない コメントの値: 帯 1 本 約 10 µs。以前はその場で入れ替えてから memcpy していた（7fd965f、遅かった）。
  • 描く先を交互に変えない理由。描画先のポインタを 1 フレームの間持ち続ける呼び出し元が約 8 か所ある（render_rects の display->strip()、shell・editor・codeedit・tutorial・wifi_ui・workspace・pickmodal）調査の報告、行は未照合。交互にするには、すべてで帯ごとに取り直す改修が要る。
  • SPI は 80 MHz。帯 1 本 3,840 B は理論 384 µs、コメントの値で約 440 µs。非同期にした効果は FLOWER で 38.73 → 33.30 ms、fps 24.95 → 28.80 実測、docs/perf/pie-opt-plan.md。

1.N バッファ（輪の中で書き込み先と送信元をずらす）

  • 速さ: 1 秒にさばける量は「帯を描く時間」と「帯を送る時間」の遅い方で決まり、今の 2 本でほぼ全部重なっている。1.N にして縮むのは、移しの待ち 約 10 µs × 17 本 ≒ 最大 0.17 ms / フレーム 計算。空いた行を知るには帯を数行ずつの転送に分ける必要があり（SPI のドライバは転送の終わりしか知らせない）、転送 1 回ごとの手間が増える 推定。
  • メモリを減らす読み方（2 本 7,680 B → 1.25 本 4,800 B）では、Kasane が帯の中で層を重ねて描くので、帯 1 本分の空きができるまで描き始められず、描画と転送の重なりが減る。
  • DERBY のレースは CPU 側が重い: render_ms 4.6〜6.6、send_ms 1.0〜2.4 実測、30 フレーム平均（send_ms が何を測るかは 未確認）。

並び替えを外せるか: LCD の並び順の設定

  • ST7789 の RAMCTRL（0xB0）の第 2 引数の bit 3（ENDIAN）で、下位バイト先を受け付けるはず。ESP-IDF の ST7789 ドライバはこれを使う（既定 0xF0、下位バイト先なら | 0x08）。ただし 4 線 SPI で効くかは資料が見つからない（報告は 8080 の並列バスか、接続が不明なもの）。
  • 確かめ方: MISO が未配線で読み戻せないので、目で見るしかない。確認用ビルド d4fcfc4 は 2 秒ごとに「入れ替えあり（ENDIAN=0）」と「入れ替えなし（ENDIAN=1）」を切り替え、LCD_ENDIAN le= をログに出す（実機で切り替えは動いている ログで確認。画面が変わるかは 持ち主の目視待ち）。画面が変わらなければ、並び替えのパスが消える。
  • 出典: esp-idf #11416、esp_lcd_panel_st7789.c。

並び替えを描画の途中へ前倒しできるか（パイプラインの走査）

  • 前倒しできる場所は、作りとしては無い。帯へ最終の画素を書く経路が十数系統あり、半透明の合成・文字のアンチエイリアス・シーンの PIE カーネルなど約 15 系統が帯を読み戻す 調査の報告、行は一部のみ照合。帯を上位バイト先にすると、読み戻すたびに入れ替えて読み・書きが要る。
  • PIE に入れ替えながら書く命令は無い（EE.VST.128.IP は素のストア、TRM v1.8 p.275。入れ替えは EE.VUNZIP.8 + EE.VZIP.8、p.295、32 B に 2 命令）。
  • 単色の塗り（背景・不透明の矩形・Shiki の線）は色を前もって入れ替えればほぼ無料だが、同じ帯に読み戻しが 1 つでもあると混ざって壊れる。
  • 結論: 並び替えは「送る直前の 1 パス」のままがよい。ピンポンにも並び替えの撤去は要らない（描き終えた帯をその場で入れ替えて、そのまま DMA の送り元にできる。その場の入れ替えは 7fd965f の出荷版で使われていた実績がある）。
