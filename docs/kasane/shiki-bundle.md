# Shiki の draw の束ね — 固定費の内訳と、複数の handle を 1 回で描く API（2026-11-01、作業中）

[shiki-jit.md](shiki-jit.md) §24.1・§24.6 の続き。PIE の試作の後に行う、と決めた作業（ユーザー決定）。**数値は実測か推定かを必ず区別する。**

## 1. 動機と、今わかっていること

- 束ねの動機は「draw 1 回の固定費 約 100〜115 µs」（[derby-background-cost.md](derby-background-cost.md) §3）。これは**旧 API**（`pocket.kasane.procedural`、float の plan）で、算術 769 ステップの draw の時間をステップ数に回帰した**切片（推定）**で、直接は測っていない。
- 一方、Shiki のエンジンの中の空の draw（`SET` 1 つ）は**実測 264 サイクル＝1.1 µs**（[shiki-jit.md](shiki-jit.md) §24.6.3）。したがって、Shiki の draw の固定費の大半は、あるとすればエンジンの外（JS からネイティブへの呼び出し、引数の検査と入力の読み取り、handle とフレームの準備、フレームへの複写）にある。
- **束ねの設計の前に、Shiki の draw 1 回の費用を段ごとに実測する**（§2）。固定費が小さければ、束ねは要らないか、別の形になる。

## 2. 測り方

- アプリ `local.drawcost`（[apps/shikitest/draw_cost.js](../../apps/shikitest/draw_cost.js)、[README](../../apps/shikitest/README.md)）。JS のループ 200 回を `shikiDebug.cycles()` で包み、5 回の最小。
- 同時に `shikiDebug.drawProfile()` がネイティブの段を積む（`main/pocket/pocket_proc.h` の `pocket_shiki_draw_prof`）: `parse`（`js_draw` の引数の検査と入力の読み取り）、`lookup`（handle・フレーム・作業領域の準備）、`engine`（`ksn_shiki_draw`）、`copy`（線分をフレームへ）。`total` からこれらを引いた残りが、JS の呼び出しの費用（QuickJS の関数呼び出し、引数の受け渡し）。
- 対照: 空の JS 関数（`loop`）、ネイティブの空呼び出し（`native`、`cycles()` 自身）。

## 3. 結果（実機、`94aea92`、2026-11-01）

ログ: [logs/shiki-drawcost-20261101-94aea92.txt](logs/shiki-drawcost-20261101-94aea92.txt)。1 回あたりのサイクル（240 MHz、200 回 × 5 回の最小）。「JS 側」は `total` からネイティブの 4 段を引いた残り（計算）。

| 変種 | total | µs | parse | lookup | engine | copy | JS 側 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| `loop`（空の JS 関数） | 1,120 | 4.7 | | | | | 1,120 |
| `native`（空のネイティブ呼び出し） | 1,162 | 4.8 | | | | | 1,162 |
| `draw0`（入力 0） | 2,325 | 9.7 | 494 | 107 | 270 | 77 | 1,377 |
| `draw8`（入力 8、引数で） | 7,491 | 31.2 | 1,937 | 123 | 3,378 | 77 | 1,976 |
| `draw8arr`（入力 8、配列で） | 8,789 | 36.6 | 3,661 | 123 | 3,372 | 77 | 1,556 |
| `point`（入力 2、点 1 つ） | 3,907 | 16.3 | 850 | 138 | 1,294 | 103 | 1,521 |

読み方:
- **Shiki の draw 1 回の固定費は 約 10 µs（入力 0）〜31 µs（入力 8）**（実測）。旧 API の推定 100〜115 µs の 1/3〜1/10。束ねの動機の数字は、Shiki には当てはまらない。
- **最大の項目は入力の変換**: `engine` は入力 0 で 270、入力 8 で 3,378 サイクル。差の 3,108 を 8 で割ると、入力 1 つ 約 390 サイクル（計算）。`ksn_shiki_from_double` が double の `ldexp`・`floor` を使い、S3 には double の演算器が無いので、ソフトウェアの double 演算になっているため（推定。逆アセンブルで確かめる）。
- 次は `parse`（入力 1 つ 約 180 サイクル、配列なら 約 400）。`JS_DupValue`・`JS_ToFloat64`・`JS_FreeValue` を入力ごとに通るため。
- JS からネイティブを 1 回呼ぶ費用は、JS の関数を 1 回呼ぶのとほぼ同じ（約 1,100〜1,200 サイクル、ループの分を含む）。**束ねで消えるのはこの部分と `lookup`（約 120）で、1 draw あたり 約 1,300〜2,000 サイクル（5〜8 µs）**（計算）。

## 4. 入力の変換の整数化と、引数の読み取りの近道（`171dc4a`、実機）

| --- | --- | ---: | --- | --- |
| `draw0` | 2,325 → 2,331 | 9.7 | 494 → 501 | 270 → 278 |
| `draw8` | 7,491 → **4,500**（−40%） | 18.7 | 1,937 → 874 | 3,378 → 1,455 |

- 配列で渡す形（`draw8arr`）の `parse` は変わらない（`JS_GetPropertyUint32` を入力ごとに通るため）。

## 5. 束ねの試作: `shiki.drawMany(handles, inputs, stride)`

**試作。仕様にはまだ入れない**（数を測ってから v1.5 の草案にし、SLOW のレビューに回す）。

- `handles` は `Uint32Array`。`inputs` は 1 回の draw に `stride` 個（0〜8）ずつ、`handles` の順に並べた型付き配列: `Float64Array` なら JS の数として §2.4 で変換、`Int32Array` なら各入力の Q 形式の値そのもの（変換しない。入力から double をなくす形）。長さはちょうど `handles.length × stride`。
- 型付き配列にしたのは、ポインタを 1 回取れば入力は 1 つずつのメモリの読み出しになるため（配列の要素の読み取りは 1 つ 約 400 サイクル、§3）。
- 順に描き、最初に失敗した draw で `draw()` と同じ誤りを投げ、フレームを捨てる（`draw()` と同じ）。それより前の draw の書き込み（データ領域）は残る。
- エンジンは `ksn_shiki_draw_fixed`（入力が Q 形式済み）と `ksn_shiki_draw`（変換してから同じものを呼ぶ）に分けた。結果は変わらない（`shiki_diff` 2 万件）。
- 確認（host）: JS API の自己試験 46 件（実数・整数の経路の値が `draw()` と同じ、長さ・型・古い handle の誤り）。
- 計測: `draw_cost.js` の `many0`・`many8`・`many8fixed`（同じ 200 回を 1 回の呼び出しで）。結果は §6。

## 6. 束ねの効果（実機、`ad10726`）

ログ: [logs/shiki-drawcost-20261101-ad10726.txt](logs/shiki-drawcost-20261101-ad10726.txt)。1 draw あたりのサイクル（同じ 200 回、5 回の最小）。

| 入力 | 1 回ずつ `draw()` | `drawMany`（`Float64Array`） | `drawMany`（`Int32Array`、変換なし） |
| --- | ---: | ---: | ---: |
| 0 | 2,397（10.0 µs） | 577（2.4 µs、4.2 倍） | — |
| 8 | 4,674（19.5 µs） | 1,852（7.7 µs、2.5 倍） | **605（2.5 µs、7.7 倍）** |

- 束ねで、JS からの呼び出し（約 1,400〜2,000 サイクル）と引数の読み取り（`parse`）が消える。残るのは `lookup` 約 120、`engine`、`copy` 約 80（実測）。
- `Float64Array` では、入力の変換が 1 つ 約 156 サイクル残る（`many8` と `many8fixed` の `engine` の差 1,247 ÷ 8、計算）。整数版の変換でも、入力が多い式では変換が最大の項目。**`Int32Array`（Q 形式済み）で渡すと、入力 8 の draw が 0 の draw とほぼ同じ費用になる**。
- 1 回ずつの `draw()` は、`171dc4a` より 3〜7% 重い（`draw8` 4,500 → 4,674）。コードの配置が変わった分で、命令キャッシュの揺れ（±15%）の内側（推定）。
- DERBY に当てた見積もり（推定）: 背景の Shiki の draw が 1 フレームに 30 回・入力 8 なら、1 回ずつ 約 0.58 ms → `drawMany` の実数で 約 0.23 ms、整数で 約 0.08 ms。DERBY は旧 API のままで、移行（段階 3）の後の話。

**次**: この形を v1.5 の草案（§9.4 に `drawMany`）にして SLOW のレビューに回す。決める点（案）: 入力の型を両方受けるか、誤りの報告に何番目の draw かを含めるか、`handles` を `Uint32Array` に限るか、途中で失敗したときのデータ領域の書き込み（今は残る、`draw()` と同じ）。

## 7. v1.5 の草案（2026-11-01）

`drawMany` を仕様 v1.5 の草案に入れた（[shiki-spec.md](shiki-spec.md) §9.4・§9.1・§2.4・§10）。試作からの変更: `maxDrawsPerCall` = 256（ネイティブの中では割り込みの検査が走らないので、止められない時間を抑える。超えれば `LIMIT_EXCEEDED`）、失敗した draw の位置を誤りの `index` に付ける。JS API の自己試験は host で 48 件。

## 8. SLOW のレビューと反映（2026-11-01）

草案 `674c3c9` の独立レビュー（重大 2・中 5・軽微 4）。

- **重大 R1**: `maxDrawsPerCall` の根拠（「止められない時間を抑える」）が数で成り立っていなかった。1 draw は最大 10,000 ステップで 約 3〜4.5 ms（推定）、256 回で 約 0.8〜1.2 s で、ターンの期限 250 ms の 4 倍を超えうる。→ いったん draw と draw の間でセッションの監視を確かめる形にした（`c33603c`）が、draw 1 回 約 600 サイクルに対して監視（時刻の読み出しと比較）の費用が見合わないとして、**ユーザーの判断で外した**（2026-11-01）。止められない時間は最悪 約 1 秒（推定）と仕様に明記し、256 は長さの上限のまま。起きるのは停止への応答の遅れとそのフレームの遅れで、致命的ではない（ユーザーの判断）。
- **重大 R2**: 誤りの `index` が common-api §4 の `PocketError` の契約の外だった → common-api §4 に「面の仕様は読み取り専用のプロパティを足してよい」を足し、`outcome` は失敗した draw 自身を指すと書いた。
- **中**: `stride = 0` なら `inputs` を検査しない（M1）、登録されていない handle は範囲外の値も含めて `CLOSED`（`draw()` とはここが違う。M2）、draw `i` の handle と入力は draw `i` の始めに読む＝データ領域の窓を入力にすると前の draw の書き込みが映る（M3）、`Int32Array` の Q 形式は `handles[i]` の式の宣言による（M4）、検査の順と空の `handles`（M5）。
- **軽微**: 内部名 `BADINPUT` を §4.8 の 7 の誤りに、失敗した draw の `operation` は `"kasane.shiki.draw"`、§10 に別名・範囲外の handle・割り込み・実機の最悪時間の要件。
- 確認（host）: JS API の自己試験 50 件（整数の経路を変換と比べる、窓を入力にした別名、範囲外の handle、空の `handles`）。

## 9. v1.5 の版の実機の確認（`4392695`、2026-11-01）

ログ: [logs/shiki-drawcost-20261101-4392695.txt](logs/shiki-drawcost-20261101-4392695.txt)。
