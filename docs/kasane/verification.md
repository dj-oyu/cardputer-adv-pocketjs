# 実機ゲートと証拠の読み方

数字は Cardputer ADV / ESP32-S3 の特定 image・操作列に対するもの。host の画素一致は物理LCD GRAMの読戻しではなく、シリアル strip capture はSPI送信直前の画素で、captureを行うと転送時間が乱れる。ASan/UBSan・`-O2 -fstrict-aliasing`・ESP-IDF build は必要だが、実機の描画・音声の代替ではない。ログは当時 `.cache/kasane-*` にあり、Git対象外。残っていないログは表の要約以上に再現できる証拠として扱わない。

## 固定した回帰防止線

P0 の時間ゲートは最適化開始前に固定した。`KASANE_P0_PROBE=ON`、copy計数と追加bus probeはOFF。p99は主に128 µs幅（UI frameは1024 µs幅）の histogram **bucket上端**であり、異なる列のp99を足したり、同じbucket内の小差を推論しない。測定失敗後に閾値を緩めない。新しい workload の比較は、同一imageの A/B/B/A または再起動を挟む旧→新→旧→新を優先する。

| workload | 固定ゲートの主な値 |
| --- | --- |
| hello・180 Enter、181描画 | app turn p99≤383 µs、render p95/p99≤1,279/1,407 µs、send p95/p99≤895/1,151 µs、cold start込みrender/send max≤6,000/9,000 µs、12 ms超0、LCD≤210,720 B/557帯、free/min/largest≥218,000/113,000/102,400 B、stack未使用≥22,500 B。 |
| music overlay・SD曲、45秒＋2秒pause/resume | overlay work p99≤3,839 µs、draw p95/p99/max≤9,343/9,599/10,000 µs、send p99/max≤5,247/5,500 µs、UI frame p99/max≤12,287/200,000 µs、draw/sendの12 ms超0、UI frameの12 ms超≤1%、LCD≤64,800 B/17帯 per frame、free/min/largest≥210,000/40,960/65,536 B、stack未使用≥22,500 B、underrun/fault/IO ERROR=0。 |
| music 複合低heap | 16,384 B internal heap保持時は通常のfree/largest下限をそのまま適用しない。min≥20,000 B、その他の時間・stack・音声値は上の固定線。SYSTEM通知post/clear、pause/resume、overlay終了後Helloを含む。 |

これらは短時間の**回帰防止線**で、全SD曲、電源断、長時間、物理SPI故障を証明しない。とくに send max 5,500 µs はこの基準での上限であり、製品上の応答期限・音声要件との関係は未定義。通常アプリと前面占有の診断アプリは別 workload。後者ではホーム background が見えないことが仕様であり、通常 music overlay の不具合証拠ではない。16 KiB保持試験は min heap の代替下限を置いたが、largestの代替閾値や「必須確保が失敗しても有界復帰」の合格条件は未固定。

## 計測の落とし穴

- `overlay_work`、draw、send、UI frame は別区間。source取得・計画生成・提出・合成・LCD完了待ちのどこが律速か分ける。音楽で見えた9/16 msの揺れはbyte-swap/queueよりLCD reap待ちとpost-ISR→UI復帰に偏った。SD readとの同frame重複は相関であって単独の因果ではない。
- 転送量の総計やframe数が違う試行から速度の因果を推論しない。通常 music overlay は背景が独立して動くため、限定PATCHでも送信は概ね全画面のまま。
- 画素capture試行の時間値を性能ゲートへ入れない。diagnostic BSSが約6 KiB増えるbus/stage probeのheapを製品下限と比較しない。
- `MP3DEC worst_us` がpauseを跨ぐ集計窓なら、decoder計算が数秒かかったとは読まない。音声はunderrun/decoder fault/IO ERRORと再生位置、pause/resume受理、進行再開を別々に見る。
- 出荷imageと診断image、異なるコード配置で得た p99差は最適化の因果証明にしない。過去の多くの試験は元のapp領域を復元・verifyしたため、測定imageが現在の端末に残っているとは仮定しない。

P4の次の計測では「copy」を、**同じpayloadのバイトまたは構造を独立したメモリ領域へ複製する1操作**として数える。bank clone、schema所有、core受理、同じtextをrender scratchへ複製する操作を含み、複数destinationは各々1回と数える。QuickJS UTF-16→UTF-8、字形→RGB565などの**形式変換**はcopy回数と別に確保量・bytes・CPU時間を報告する。LCD DMA/SPIは**転送**として別計測し、copy回数に混ぜない。同じ処理で形式変換後のバイト列をさらに複製すれば、その複製はcopyに数える。

`KSN_P0_COPY_PROBE`の `source_text_watch` は `core_submit_text` の**内数**で、合計に二重加算しない。現行probeの `adapter_*`、`core_clone_*`、`core_submit_*`、`core_render_text`、`render_decode_*` は境界別call/bytesを示すが、1つのpayloadを最後まで追うIDと未計数のQuickJS内部操作がない。したがって単純なカテゴリ総和を「1 payloadのcopy回数」としない。該当workloadで lineage、各destination、peak保持量、CPU寄与、largest heap、stackを一組にし、時間ゲートはcopy計数OFFの同条件imageで別に判定する。厳格な全経路1-copyはこの範囲が揃うまで未達。

QuickJSの`JS_ToCStringLen`を実ソースとcustom allocator付きhost試験`tools/kasane_contract/run_qjs_utf8_cost.sh`で確認した。同じAPIでもASCII `TITLE` は新規allocation 0、Latin-1 `é` は1回/要求43 B、日本語 `リズム` は1回/要求50 Bだった。要求bytesはallocatorが受けた領域サイズであり、payload copy bytesや実機CPU時間ではない。従来の`utf8_materialized`計数は各呼出しの**入力文字長**を無条件に足していたため、ASCIIの0-copyもcopyのように表示していた。以後は`utf8_request`/`js_utf8_request`を要求量として別表示し、`observed_total`には加えない。下記の**旧image**の`observed_total`には旧計数法が含まれる可能性があるため、新形式の総量と数値比較しない。`apps/player/player.js`の音楽表示は入力・Promise/state callbackで`view.set`し、毎frameのJS描画関数を持たないため、この変換をframe毎の費用として見積もらない。日本語のQuickJS変換が必要な事実は分かったが、実musicでの呼出し頻度・実機CPU寄与はまだ未計測。

## binary text の PIE 候補（実機A/Bまで、2026-09-25）

既定ONの定色565ブレンドPIEとは別に、`ksn_text_port.binary_coverage` を宣言したfontだけが使える8画素maskカーネルを作った。組込み `ksn_font_port` は0/255だけを出すので宣言をONにし、一般の0..255被覆率portは既定falseのまま。カーネルはborrowした8 byte maskを `EE.VLD.L.64.IP` → `EE.VZIP.8` で8本の16-bit laneへ広げ、0またはコマンドalphaを選ぶ。**別のalpha配列・mask複製は作らない。** 16 byte整列のRGB565行と8 byte整列のmaskの両方がそろう時だけ呼び、0だけのmask blockは先に飛ばす。未整列・非binary・coarse `scale256`・alpha LUTの経路は従来描画へ戻す。`g_ksn_text_pie=0`が既定で、採用前の製品経路には載せない。

[esp32s3-hw-mcpのTRM抽出データ](https://github.com/dj-oyu/esp32s3-hw-mcp/blob/main/data/pie_instructions.json)でも、`EE.VLD.L.64.IP` はアクセス先の下位3 bitを0にして下位64 bitへロード（TRM v1.8 p168）、`EE.VZIP.8` は2つの8-bitベクタを交互に配置（p295）、`EE.VST.128.IP` はアクセス先の下位4 bitを0にして128 bitを格納（p275）と確認した。したがって単なる速度条件ではなく、mask/stripの整列を画素正しさの入口条件とする。同リポジトリの[実機例題データ](https://github.com/dj-oyu/esp32s3-hw-mcp/blob/main/data/pie_examples_measured.json)も128-bitバッファの4 byteずれでレーンがずれた事例を記録している。MCPサーバーは現在のセッションのツール面には公開されていないため、この照合はリポジトリの公開データを直接読んだもの。
