# Shiki の JIT — ベクトルの区間を PIE の機械語にする（草案、2026-11-02）

**決定（2026-11-02、ユーザー）:** 並列性を上げる方法として、ベクトルの区間を**登録時に PIE の機械語へ変換し、RAM に置いて実行する**（案 A）。リスクを取る判断で、実行時のメモリ保護（`CONFIG_ESP_SYSTEM_MEMPROT`）を切る。数値の出所は各行に書く。推定は推定と書く。

## 1. 理屈: パイプラインを何が空けているか

インタプリタは命令ごとに「命令を読む → 種類で分岐する → 被演算子をメモリから読む → 計算する → メモリへ書く」を踏む。次に何をするかが、直前にメモリから読んだ値で決まるので、CPU は先を重ねられない。命令 1 つの床 57 サイクル（`SET`、実測、[shiki-pie.md](shiki-pie.md) §8）はこの直列の連鎖の長さで、計算そのものは数サイクル。PIE の命令は 1 サイクルで 8 レーンを処理するが、その前後に振り分けと、ベクトルのレジスタ・蓄積器（QACC）のメモリとの往復（`ksn_shiki.c` の `pie_*`。QACC だけで退避 4 命令・復帰 4 命令）が挟まる。PIE の上乗せが 1.46 倍で止まったのはこのため（同 §8.4、実測）。

パイプラインを埋める原則:

1. **判断を N 個の値で分け合う。** スカラーは N = 1、ベクトルの命令は 8、理想はループ全体で判断 1 回（N = 全レコード）。本体を登録時に一度だけ解釈し、実行時は解釈しない。
2. **値をレジスタに置いたままにする。** `v0`〜`v7` を q0〜q7 に、蓄積器を QACC にそのまま割り当てる。本体の間、メモリへ退避しない。
3. **結果を待たない並びにする。** ロードと `EE.VMUL` は def 段 2（TRM 表 1.7-2）で、直後に使うと 1 サイクル止まる。独立な命令を挟むか、演算とロードを一緒に行う命令（`EE.VMUL.S16.LD.INCP` など、TRM p.199）を使う。
4. **本体の中で分岐しない。** 回数はゼロオーバーヘッドのループ（`loopgtz`）に任せる。条件は比較のマスクと AND/OR の選択で書く（v2.1 の命令、§7）。
5. **データを揃えておく。** 欄ごとの面（SoA、16 B 整列、`S` は 8 の倍数）は v1.4 で入っている。8 の倍数でない件数の末尾のブロックだけを別に扱う。

## 2. 実行できる RAM（段階 0）

- **メモリ保護を切る**（`sdkconfig.defaults`、`CONFIG_ESP_SYSTEM_MEMPROT=n`）。保護が有効だと `MALLOC_CAP_EXEC` の確保は不可能（IDF v6.0.1 の Kconfig の help）。理由と失うものは設定の横に書いた: 機体の上のコードはすべて所有者がビルドして焼くファームで、アプリは QuickJS のゲストの JS、ファームはネットワークのポートを開かない（IP は外向きの時刻同期だけ）。失うのは、ファームのバグの迷った書き込みがコードに当たったときに境界で例外にならないこと。
- **確保と書き込み:** `heap_caps_malloc(n, MALLOC_CAP_EXEC)` の番地（命令バス側）に、`esp_ptr_in_diram_iram()` ならデータバス側の別名（`esp_ptr_diram_iram_to_dram()`）から 32 ビット単位で書き、`memw; isync` の後に命令バス側の番地を関数として呼ぶ。内部 SRAM は命令キャッシュを通らないので、キャッシュの無効化は要らない。
- **関数の形:** windowed ABI（`entry a1, 32` … `retw.n`）。引数は a2 から。関数の先頭は 16 B に揃える（`loopgtz` の本体の整列を、アセンブラが関数の先頭からの位置で決めるため）。
- **確認（`cyclebench` の最後の行 `CB jit`、`main/ui/kasane/ksn_shiki_jit.c`）:** 手で組んだ 2 つの関数（8 レーンの飽和加算 1 ブロック、同じものを 16 ブロック `loopgtz` で）を書いて呼び、C の結果と比べて時間を取る。**結果: §8 に記録する。**

## 3. 生成するコードの形

対象は `VEACH … END` の区間で、本体がベクトルの命令（`VLOAD`〜`VOUT`、op 31〜44）だけのもの。それ以外を含む区間、レジスタが足りない区間は今のインタプリタで動く（§6）。

```
entry a1, 32
  ; 前置き: 本体が読むスカラーのレジスタ（VSPLAT・VMACK・VACCSET の r）を
  ;         ブロックの外で一度だけ読む（本体にスカラーの書き込みは無いので不変）
  ; 欄ごとのポインタ: (領域, 欄) の組ごとに AR 1 本 = 面の先頭 + 開始レコード
  ; VM の q0..q7 と QACC をメモリから読む（区間に入る前の状態）
loopgtz a_blocks, end
  ee.vld.128.ip   qX, a_field, 16        ; VLOAD
  ee.vadds.s16    qZ, qX, qY             ; VADD
  ee.vmulas.s16.qacc qX, qY              ; VMAC
  ee.srcmb.s16.qacc qZ, a_shift, 0       ; VOUT
  ee.vst.128.ip   qZ, a_field2, 16       ; VSTORE
end:
  ; q0..q7 と QACC をメモリへ書き戻す（区間の後のインタプリタ、端数のブロックが続きを読む）
retw.n
```

- **レジスタの割り当ては無い。** Shiki の `vN` は qN、蓄積器は QACC。AR は a2 = 文脈（下）、a3 = ブロックの数、a4 = 作業用、a5 = 定数の番地、a6〜a15 = （領域, 欄）の組ごとのポインタと `VOUT` のシフト量ごとに 1 本（合わせて 10 本まで）。ポインタは本体の中でその組を最後に使う命令の `.IP` で 16 進めるので、同じ欄を何度読み書きしても 1 ブロックに 1 回だけ進む。足りなければその区間は JIT にしない。
- **文脈（`ksn_jit_ctx`、draw ごとに C が作る）:** 0: ポインタ 10 本（最初のブロックの番地）、40: ブロックの数、44: `vraw`、48: QACC の像、52: シフト量 4 つ、80: 定数 8 つ（`sat16(r)`、16 B 境界）、96: `VACCSET` の像 2 つの番地。32 ビットの番地で書く（host はコードを作るだけで走らせない）。
- **`VSPLAT d, r`:** 定数の欄から `EE.VLDBC.16` で全レーンへ（`addi` で欄の番地を作って 2 命令）。
- **`VMACK a, r`:** 定数 8 つを前置きで q7 に読み、`EE.VSMULAS.S16.QACC qa, q7, 欄` で掛けて足す（ブロックごとの配る命令が要らない）。q7 を使うので、`VMACK` がある区間は本体が v7 を使わないときだけ JIT にする。
- **`VACCSET r`:** 全レーンを r にする QACC の像を、draw ごとにインタプリタの PIE 経路と同じ関数（`pie_accset`）で一度作り、本体では像から 4 命令で読む（区間に 2 つの値まで）。
- **JIT にしないもの（第 1 版）:** `VIOTA`（案: 前置きで iota を q に作り、ブロックごとに 8 を足す。q を 1 本使う）、スカラーの命令・`EMIT_*`・入れ子のループを含む本体、本体のコードが 256 B を越える区間（`loopgtz` の届く範囲）。
- **実行の条件（draw のとき、満たさなければその区間はインタプリタ）:** `vm->pie`（蓄積器が QACC の像の形）、開始レコードが 8 の倍数、どの面の番地も 16 B 境界（PIE の経路と同じ。外れはインタプリタが C のレーンのループで処理する）、満杯のブロックが 1 つ以上。
- **ステップの数（`LIMIT` の規則、spec §3.1）:** 1 ブロックは本体の命令数 + `END` の 1。満杯のブロックの分を足して上限に届く区間は JIT にしない（インタプリタが正確なステップで止まるので、結果を変えないため）。届かなければ、コードの後でその分を `vm->steps` に足す。
- **端数のブロック:** JIT は満杯のブロックだけを回し、q と QACC をメモリへ書き戻して、最後の 1 ブロックを今のインタプリタ（C のレーンのループ）で回す。状態の受け渡しは今の PIE 経路と同じメモリの形（`vraw`、QACC の像）なので、結果は区間全体をインタプリタで回したときと同じ。
- **待ちを消す並べ替え（原則 3）:** 第 1 版はしない（命令を本体の順に出す）。def 段 2 の結果を直後に使う所を数え、2 ブロックを交互に進めるソフトウェアパイプラインは第 2 版。

## 4. 機械語の作り方（エンコーダ）

- **表はアセンブラから作る。** 使う命令（`ee.vld.128.ip`・`ee.vst.128.ip`・`ee.vadds.s16`・`ee.vsubs.s16`・`ee.vmin.s16`・`ee.vmax.s16`・`ee.vldbc.16`・`ee.zero.qacc`・`ee.vmulas.s16.qacc`・`ee.srcmb.s16.qacc`・`loopgtz`・`entry`・`retw.n`・`l32i`・`movi` など）の形を、ファームをビルドするのと同じ `xtensa-esp32s3-elf-as`（esp-15.2.0）でオペランドの値を振って組み、ビットの位置を host のスクリプトで割り出して C の表にする。TRM の命令語の図はアセンブラと食い違うことがある（esp32s3-hw の `manual_errata`）ので、図からは作らない。
- **host の検査:** エンコーダが出したバイト列を `xtensa-esp32s3-elf-objdump` で逆アセンブルし、期待するアセンブリの文字列と比べる（`tools/kasane_contract/` に足す。ツールチェーンが無い環境では飛ばす）。全命令 × オペランドの全値。
- **意味の照合:** 実機で、JIT とインタプリタ（C モデル、PIE の命令ごとの経路）の 3 つを同じ入力で回し、結果の行の hash を比べる（`cyclebench` の `CB shiki check` に JIT の列を足す）。今の 10 件に、端数・整列・ステップ上限の境界を足す。

## 5. メモリ

- コードは plan ごとに登録時（`ksn_shiki_register` の最後、`ksn_shiki_jit_attach`）に確保し、plan の `jit` に置く。plan を解放する所はすべて先に `ksn_shiki_plan_dispose()` を呼ぶ（`pocket_proc.c` の detach と reset、`pocket_shiki_api.c` の登録の失敗、`pocket_shiki.c` のテストとベンチ）。`VEACH` の無い plan は何も確保しない（今の出荷アプリは 0 B）。大きさは命令 1 つ 3〜4 B ＋ 前置きと後始末（推定 60〜100 B）。affine128 の本体（約 13 命令）なら 1 区間 150 B 前後（推定）。
- 確保は `MALLOC_CAP_EXEC`（DIRAM。ゲストやシステムと同じプール）。Shiki heap（48 KiB の専用領域）は実行属性が無いので使えない。数を縛るため、1 plan の JIT コードの上限と全体の上限を決める（段階 2 で値を決める）。
- 確保に失敗したら、その plan はインタプリタで動く（失敗を JS に見せない。速さだけが変わる）。

## 6. インタプリタとの関係

- インタプリタ（C モデルと命令ごとの PIE）は残す。JIT は「同じ結果をより速く」出す実装の 1 つで、規範は C モデル（[shiki-v2.md](shiki-v2.md) §11 の §10.1 の例外）。
- 切り替え: `ksn_shiki_vec_pie` と同じく、JIT を使うかの旗を draw の開始で読む。ベンチは 3 つを 1 つのバイナリで比べる。
- host では JIT は無い（host のビルドはインタプリタだけ）。

## 8. 結果

### 8.1 段階 0（実機、2026-11-02、481f7ce）

記録: [logs/shiki-jit0-20261102-481f7ce.txt](logs/shiki-jit0-20261102-481f7ce.txt)。

- **動いた。** メモリ保護を切った版で、`MALLOC_CAP_EXEC` は命令バス側の DIRAM の番地（`0x403beb00`）を返し、データバス側の別名から書いた 2 つの関数が、どちらも C と同じ結果を返した（`one=same/42 loop=same/43`）。
- **時間（実測、7 回の最小）:** 16 ブロック（128 レーン）の「ロード・ロード・飽和加算・ストア」を `loopgtz` で回して、呼び出しを含めて **97 サイクル（1 ブロック約 6 サイクル）**。同じ和を C（-O2）で 1,319 サイクル。本体 4 命令に対して 1 ブロック 6 サイクルなので、パイプラインはほぼ埋まっている（残りは呼び出しと前置き）。
- 比べる相手: 今のインタプリタの PIE 経路は、affine128 のベクトル版（16 ブロック、1 ブロック約 13 命令）で 45,375 サイクル（同じ走行）。`EMIT_POINTS` の推定分（約 16,000）を引くと命令 1 つ約 140 サイクル（**推定**）で、JIT の本体は命令 1 つ約 1.5 サイクル（実測、ロードの待ちを含む）。affine128 を JIT にしたときの見込みは、本体 16 ブロック × 約 20 サイクルに `EMIT_POINTS` の 128 点（約 16,000 サイクル、[shiki-pie.md](shiki-pie.md) §8.4 の推定）を足した程度（**推定**）。ここから先は描画（`EMIT`）が支配する。

### 8.2 段階 2（実機、2026-11-02、2a78095）

- **エンジンはターンの 12〜39%。** 残り（DERBY の WIDE 2 で約 14.5 ms）は JS（レースのモデル、カメラ、Kasane の命令、`pocket.derby` の投影）。
- **MEGADEMO のステップは振り分けが支配している。** 1 ステップ 94〜118 サイクルは、命令ごとの床（57〜100 サイクル、§8 の `CB shiki` の行）にほぼ等しい。DERBY は線・模様の線を描く命令が多く、1 ステップが重い（129〜366 サイクル）。
- **スカラーの JIT の見込み（推定）:** 振り分けをなくして 1 ステップを 30〜40 サイクル前後にできれば、MEGADEMO で 1 フレーム 約 1.5〜2.3 ms（ターンの 15〜25%）、DERBY で 約 0.5〜1.3 ms（5〜10%）。描画の命令（`LINE`・`LINE_PATTERN`）そのものの仕事は残る。

## 11. 段階 3: プラン全体のスカラーの JIT

§9・§10 から、エンジンの時間の大半は命令の振り分け（1 ステップ 94〜118 サイクル）で、命令の 8 割前後は算術とループの制御だった。段階 3 は、プランの命令をすべて機械語に並べ、算術とループの制御をその場に書き、残りを C の関数で 1 命令ずつ実行する。

### 11.1 形

- **vm はメモリに置いたまま。** 機械語はインタプリタと同じ `vm->reg`・ループの frame・`depth`・`steps` を読み書きする（`r[k]` は `l32i.n` の `4k`）。どのブロックの頭でもインタプリタへ渡せるのは、このため。レジスタへの割り付けはしていない（符号を短くする余地として残る）。
- **アドレスレジスタ:** a2 実行の context（`ksn_jit_run`）、a3 vm、a4 ステップの上限、a5 入力、a6 `INT32_MAX`（飽和の直し）、a7 helper。a8〜a15 は 1 命令の中だけの作業用（`callx8` で helper に渡る）。
- **inline にする命令:** `SET`（movi、入らない値はコードの前の literal pool から `l32r`）、`INPUT`、`ADD`・`SUB`（符号で桁あふれを見て、a の符号で `INT32_MAX`/`MIN`）、`NEG`、`MUL`（`mull`+`mulsh` の 64 bit 積を `ssai`+`src` で床へ shift、`aux≥32` は上位語の shift だけで桁あふれしない）、`SHIFT`（右は `srai`、左は `sll`+`src` で上位語を作って検査）、`REPEAT`（定数回）、`END`、`BREAK_IF_GT`。
- **それ以外**（`SIN`・`MOVE`/`LINE`/`PLOT`・`EACH`/`FETCH`/`VEACH` と vector 命令・`EMIT_*`・`*_H`・`REPEAT_REG`・`DRAW_INDEX` など）は `ksn_shiki_jit_leaf(ctx, pc)` を呼ぶ。中身はインタプリタの 1 命令（`step()`、インタプリタのループと共有する `always_inline` の関数）そのものなので、意味が分かれない。戻り値は 0（続ける）、1（0 回のループ: END の次へ飛ぶ）、それ以外は状態 << 8。
- **ループの深さは字句で決まる**（登録が END と開き命令を対にしている）ので、frame のアドレスはコンパイル時に分かる。

### 11.2 ステップの数え方

ブロックは、開き命令・`END`・`BREAK_IF_GT` の次（と pc 0）から、次のそれらまで。ブロックの頭で長さ k を `steps` に足し、`steps + k > 10,000` ならその pc を返してインタプリタへ渡す（インタプリタが正確なステップで LIMIT にする）。飛び先はすべてブロックの頭なので、どの経路も頭を通る。`VEACH` の helper は段階 2 の機械語で `steps` を足すので、`VEACH` はブロックを終える（次のブロックはメモリから読み直す）。

結果の違いは 1 つだけ: **ブロックの途中で helper がエラー（INVALID・線の上限の LIMIT）を返すと、`vm->steps` はブロックの終わりまで数えた値になる。** 状態・レジスタ・線は同じ。`steps` は統計（`SHIKI_TURN`）にしか使われない。

### 11.3 いつコンパイルするか、メモリ

全部コンパイルすると DERBY は 21 本・887 命令で約 17 KB、MEGADEMO は 24 本・660 命令で約 13 KB（host の `test_scalar.py`、1 命令 約 19〜20 B）。実行可能なメモリはアプリと同じ heap から取るので、**プランは 32 回目の描画でコンパイルし、合計を `ksn_shiki_jit_budget`（16 KiB）で止める。** 失敗したプランは二度と試さない（`plan->heat`、構造体の詰め物の 2 バイト）。`SHIKI_TURN` の末尾 `jit=<on>/<bytes>` が、その時点の量。

### 11.4 検査

- **host（`tools/shiki_jit/test_scalar.py`、`run.sh` から）:** `ksn_shiki_bench_random()` のランダムなプログラム（int32 の境目の値・2 の冪・対数一様の大きさ、255 回までの入れ子ループでステップの上限、BREAK、線）をコンパイルし、出した命令だけの小さな Xtensa エミュレータで走らせてインタプリタと比べる。エミュレータは生成した命令表（アセンブラで確かめた表）で解読し、意味は ISA の記述から書いたので、エミュレータと compiler の両方が同じ読み違いをすると通ってしまう。そこは実機が見る。変異（飽和の直し・上限のずれ・shift 量・BREAK の飛び先）で落ちることを確かめた（`hi>>(s-1)` の変異は等価で落ちない）。さらに DERBY と MEGADEMO の全プランをコンパイルし、objdump で隙間なく解読できること、`l32r` の読む先が pool の中でエミュレータの読みと一致することを見る。
- **実機（cycle bench の `CB jit scalar 1/4`〜`4/4`）:** 同じランダムなプログラムを、実機の CPU で、インタプリタと機械語の両方で描き、観測できるもの（状態・レジスタ・線、DONE ならステップ・pen・raster・depth）を比べる。DONE のプログラムで 1 ステップのサイクルも出す。
- **アプリ:** `-DPOCKET_SHIKI_JIT_AB` のビルドは `SHIKI_TURN` の行ごとに JIT を入れ切りするので、同じバイナリで比べられる。

## 12. 描画の命令: SIN をその場に、線の命令を直接呼ぶ

§11.5 で残りの時間は描画の命令（helper）だと分かったので、そこを詰めた。

- **`SIN`:** 機械語に約 20 命令で書く（`extui` で位相を切り出し、奇数の象限で `0x4000 - w`、表 `ctx->sin` の `T[i]` に `floor((T[i+1]-T[i])*t/64)` を足し、象限 2・3 で符号を返す）。`T[i+1]` は `t > 0` のときだけ読むので、`w = 0x4000` は `T[256]` だけを読む（host のエミュレータは表の外を読むと止まる）。
- **`MOVE`・`LINE`・`PLOT`・`LINE_C`・`PLOT_C`:** 機械語がレジスタを読み、`ksn_shiki_jit_draw(ctx, x, y, colour, kind)` を直接呼ぶ。中身はインタプリタの同じ case（色の検査 → 座標の検査 → 線の追加 → pen）で、命令の振り分け（`step()` の switch）を通らない。flash の取りこぼしを避けるため IRAM に置いた（`coord`・`emit`・`floor_shift` は always_inline で中に入る）。色が 2047 を超える `LINE`/`PLOT` は literal pool から読む。
- 新しい形式 `extui`（幅 1/6/9/14）・`addmi`・`addx4` は他と同じくアセンブラで確かめた表から作る。ランダムなプログラムに `LINE_C`・`PLOT_C`・`SIN` を足し、変異 7 通り（符号・補間の shift・折り返し・種類・色のレジスタ・色の即値・literal）がすべて落ちることを確かめた。
- コードは 1 命令 約 22〜24 B に増えた（全部で DERBY 約 19 KB、MEGADEMO 約 14.5 KB。熱いものだけを 16 KiB の予算でコンパイルするのは変わらない）。

## 13. CUBIC の重みの表と、最内側のループ

### 13.1 CUBIC

区間 k（1..n）の重み `w0..w3` は k と n だけで決まり、制御点に依らない。JIT はプランごとにすべての CUBIC の重みを一度だけ表にし（`ksn_shiki_cubic_weights`、pc の順、最大 512 個の int32 = 2 KB、予算に数える）、機械語は CUBIC の行の位置を helper に渡す。表のある区間は割り算 1 回と `mul16` 6 回が無くなる。表を作れなかったとき（大きすぎる、予算）は helper がその場で計算する（インタプリタと同じ）。

`cubic` はループで書き直した（`mul16` と座標の検査が 1 か所ずつ）。-O2 で 4.3 KB あったものが -Os で 690 B になり、IRAM へ移した。IRAM のコードが flash を呼ばないよう、`mul16`・`sat32`・`floor_div`・`floor_mod`・`round_div` を always_inline にした（`cubic_weights` だけは、表の無い経路で flash を呼ぶ）。IRAM に置いた描画の関数は合わせて約 2.3 KB（-Os の見積もり）、ホーム画面の空きは 197,324 → 195,240 B（実測、2,084 B 減）。

検査: host のランダムなプログラムは、表を渡す回と渡さない回を交互にし、両方をインタプリタと比べる。CUBIC と LINE_PATTERN のレジスタ群を範囲内に置く組み立てを生成器に足した（3,000 本で CUBIC と LINE_PATTERN が合わせて約 950 回走る）。表の行を 4 ずらす・重みを 4096 ずらすと落ちる。重みを 1 だけずらしたものは座標が 1/65536 画素しか動かず、出力の画素に現れないので落ちない。参照実装との照合（shiki_diff）も通る。

### 13.2 最内側のループ

ループを含まず `BREAK_IF_GT` の無い本体の `REPEAT` / `REPEAT_REG` は、入口で `回数 × (本体 + END)` のステップを一度に数え（上限を越えるなら本体の頭の pc でインタプリタへ渡す）、回数を a7 に置く（`callx8` は a0..a7 を残す）。`END` は `addi` と分岐の 2 命令になり、1 周ごとのブロックの頭（4 命令）が無くなる。a7 を空けるため、helper の番地は呼ぶたびに context から読む。変異（数の 1 ずれ、頭の飛び先、減らす量、本体の位置）は 4 つとも落ちる。
