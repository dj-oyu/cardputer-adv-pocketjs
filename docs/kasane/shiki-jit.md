# Shiki の JIT — ベクトルの区間を PIE の機械語にする（草案、2026-11-02）

**決定（2026-11-02、ユーザー）:** 並列性を上げる方法として、ベクトルの区間を**登録時に PIE の機械語へ変換し、RAM に置いて実行する**（案 A）。リスクを取る判断で、実行時のメモリ保護（`CONFIG_ESP_SYSTEM_MEMPROT`）を切る。数値の出所は各行に書く。推定は推定と書く。

## 1. 理屈: パイプラインを何が空けているか

インタプリタは命令ごとに「命令を読む → 種類で分岐する → 被演算子をメモリから読む → 計算する → メモリへ書く」を踏む。次に何をするかが、直前にメモリから読んだ値で決まるので、CPU は先を重ねられない。命令 1 つの床 57 サイクル（`SET`、実測、[shiki-pie.md](shiki-pie.md) §8）はこの直列の連鎖の長さで、計算そのものは数サイクル。PIE の命令は 1 サイクルで 8 レーンを処理するが、その前後に振り分けと、ベクトルのレジスタ・蓄積器（QACC）のメモリとの往復（`ksn_shiki.c` の `pie_*`。QACC だけで退避 4 命令・復帰 4 命令）が挟まる。PIE の上乗せが 1.46 倍で止まったのはこのため（同 §8.4、実測）。

パイプラインを埋める原則:

1. **判断を N 個の値で分け合う。** スカラーは N = 1、ベクトルの命令は 8、理想はループ全体で判断 1 回（N = 全レコード）。本体を登録時に一度だけ解釈し、実行時は解釈しない。
2. **値をレジスタに置いたままにする。** `v0`〜`v7` を q0〜q7 に、蓄積器を QACC にそのまま割り当てる。本体の間、メモリへ退避しない。
3. **結果を待たない並びにする。** ロードと `EE.VMUL` は def 段 2（TRM 表 1.7-2）で、直後に使うと 1 サイクル止まる。独立な命令を挟むか、演算とロードを一緒に行う命令（`EE.VMUL.S16.LD.INCP` など、TRM p.199）を使う。
4. **本体の中で分岐しない。** 回数はゼロオーバーヘッドのループ（`loopgtz`）に任せる。条件は比較のマスクと AND/OR の選択で書く（v2.1 の命令、§7）。
5. **データを揃えておく。** 欄ごとの面（SoA、16 B 整列、`S` は 8 の倍数）は v1.4 で入っている。8 の倍数でない件数の末尾のブロックだけを別に扱う。

## 2. 実行できる RAM（段階 0）

- **メモリ保護を切る**（`sdkconfig.defaults`、`CONFIG_ESP_SYSTEM_MEMPROT=n`）。保護が有効だと `MALLOC_CAP_EXEC` の確保は不可能（IDF v6.0.1 の Kconfig の help）。理由と失うものは設定の横に書いた: 機体の上のコードはすべて所有者がビルドして焼くファームで、アプリは QuickJS のゲストの JS、ファームはネットワークのポートを開かない（IP は外向きの時刻同期だけ）。失うのは、ファームのバグの迷った書き込みがコードに当たったときに境界で例外にならないこと。
- **確保と書き込み:** `heap_caps_malloc(n, MALLOC_CAP_EXEC)` の番地（命令バス側）に、`esp_ptr_in_diram_iram()` ならデータバス側の別名（`esp_ptr_diram_iram_to_dram()`）から 32 ビット単位で書き、`memw; isync` の後に命令バス側の番地を関数として呼ぶ。内部 SRAM は命令キャッシュを通らないので、キャッシュの無効化は要らない。
- **関数の形:** windowed ABI（`entry a1, 32` … `retw.n`）。引数は a2 から。関数の先頭は 16 B に揃える（`loopgtz` の本体の整列を、アセンブラが関数の先頭からの位置で決めるため）。
- **確認（`cyclebench` の最後の行 `CB jit`、`main/ui/kasane/ksn_shiki_jit.c`）:** 手で組んだ 2 つの関数（8 レーンの飽和加算 1 ブロック、同じものを 16 ブロック `loopgtz` で）を書いて呼び、C の結果と比べて時間を取る。**結果: §8 に記録する。**

## 3. 生成するコードの形

対象は `VEACH … END` の区間で、本体がベクトルの命令（`VLOAD`〜`VOUT`、op 31〜44）だけのもの。それ以外を含む区間、レジスタが足りない区間は今のインタプリタで動く（§6）。

```
entry a1, 32
  ; 前置き: 本体が読むスカラーのレジスタ（VSPLAT・VMACK・VACCSET の r）を
  ;         ブロックの外で一度だけ読む（本体にスカラーの書き込みは無いので不変）
  ; 欄ごとのポインタ: (領域, 欄) の組ごとに AR 1 本 = 面の先頭 + 開始レコード
  ; VM の q0..q7 と QACC をメモリから読む（区間に入る前の状態）
loopgtz a_blocks, end
  ee.vld.128.ip   qX, a_field, 16        ; VLOAD
  ee.vadds.s16    qZ, qX, qY             ; VADD
  ee.vmulas.s16.qacc qX, qY              ; VMAC
  ee.srcmb.s16.qacc qZ, a_shift, 0       ; VOUT
  ee.vst.128.ip   qZ, a_field2, 16       ; VSTORE
end:
  ; q0..q7 と QACC をメモリへ書き戻す（区間の後のインタプリタ、端数のブロックが続きを読む）
retw.n
```

- **レジスタの割り当ては無い。** Shiki の `vN` は qN、蓄積器は QACC。AR は a2 = 文脈（下）、a3 = ブロックの数、a4 = 作業用、a5 = 定数の番地、a6〜a15 = （領域, 欄）の組ごとのポインタと `VOUT` のシフト量ごとに 1 本（合わせて 10 本まで）。ポインタは本体の中でその組を最後に使う命令の `.IP` で 16 進めるので、同じ欄を何度読み書きしても 1 ブロックに 1 回だけ進む。足りなければその区間は JIT にしない。
- **文脈（`ksn_jit_ctx`、draw ごとに C が作る）:** 0: ポインタ 10 本（最初のブロックの番地）、40: ブロックの数、44: `vraw`、48: QACC の像、52: シフト量 4 つ、80: 定数 8 つ（`sat16(r)`、16 B 境界）、96: `VACCSET` の像 2 つの番地。32 ビットの番地で書く（host はコードを作るだけで走らせない）。
- **`VSPLAT d, r`:** 定数の欄から `EE.VLDBC.16` で全レーンへ（`addi` で欄の番地を作って 2 命令）。
- **`VMACK a, r`:** 定数 8 つを前置きで q7 に読み、`EE.VSMULAS.S16.QACC qa, q7, 欄` で掛けて足す（ブロックごとの配る命令が要らない）。q7 を使うので、`VMACK` がある区間は本体が v7 を使わないときだけ JIT にする。
- **`VACCSET r`:** 全レーンを r にする QACC の像を、draw ごとにインタプリタの PIE 経路と同じ関数（`pie_accset`）で一度作り、本体では像から 4 命令で読む（区間に 2 つの値まで）。
- **JIT にしないもの（第 1 版）:** `VIOTA`（案: 前置きで iota を q に作り、ブロックごとに 8 を足す。q を 1 本使う）、スカラーの命令・`EMIT_*`・入れ子のループを含む本体、本体のコードが 256 B を越える区間（`loopgtz` の届く範囲）。
- **実行の条件（draw のとき、満たさなければその区間はインタプリタ）:** `vm->pie`（蓄積器が QACC の像の形）、開始レコードが 8 の倍数、どの面の番地も 16 B 境界（PIE の経路と同じ。外れはインタプリタが C のレーンのループで処理する）、満杯のブロックが 1 つ以上。
- **ステップの数（`LIMIT` の規則、spec §3.1）:** 1 ブロックは本体の命令数 + `END` の 1。満杯のブロックの分を足して上限に届く区間は JIT にしない（インタプリタが正確なステップで止まるので、結果を変えないため）。届かなければ、コードの後でその分を `vm->steps` に足す。
- **端数のブロック:** JIT は満杯のブロックだけを回し、q と QACC をメモリへ書き戻して、最後の 1 ブロックを今のインタプリタ（C のレーンのループ）で回す。状態の受け渡しは今の PIE 経路と同じメモリの形（`vraw`、QACC の像）なので、結果は区間全体をインタプリタで回したときと同じ。
- **待ちを消す並べ替え（原則 3）:** 第 1 版はしない（命令を本体の順に出す）。def 段 2 の結果を直後に使う所を数え、2 ブロックを交互に進めるソフトウェアパイプラインは第 2 版。

## 4. 機械語の作り方（エンコーダ）

- **表はアセンブラから作る。** 使う命令（`ee.vld.128.ip`・`ee.vst.128.ip`・`ee.vadds.s16`・`ee.vsubs.s16`・`ee.vmin.s16`・`ee.vmax.s16`・`ee.vldbc.16`・`ee.zero.qacc`・`ee.vmulas.s16.qacc`・`ee.srcmb.s16.qacc`・`loopgtz`・`entry`・`retw.n`・`l32i`・`movi` など）の形を、ファームをビルドするのと同じ `xtensa-esp32s3-elf-as`（esp-15.2.0）でオペランドの値を振って組み、ビットの位置を host のスクリプトで割り出して C の表にする。TRM の命令語の図はアセンブラと食い違うことがある（esp32s3-hw の `manual_errata`）ので、図からは作らない。
- **host の検査:** エンコーダが出したバイト列を `xtensa-esp32s3-elf-objdump` で逆アセンブルし、期待するアセンブリの文字列と比べる（`tools/kasane_contract/` に足す。ツールチェーンが無い環境では飛ばす）。全命令 × オペランドの全値。
- **意味の照合:** 実機で、JIT とインタプリタ（C モデル、PIE の命令ごとの経路）の 3 つを同じ入力で回し、結果の行の hash を比べる（`cyclebench` の `CB shiki check` に JIT の列を足す）。今の 10 件に、端数・整列・ステップ上限の境界を足す。

## 5. メモリ

- コードは plan ごとに登録時（`ksn_shiki_register` の最後、`ksn_shiki_jit_attach`）に確保し、plan の `jit` に置く。plan を解放する所はすべて先に `ksn_shiki_plan_dispose()` を呼ぶ（`pocket_proc.c` の detach と reset、`pocket_shiki_api.c` の登録の失敗、`pocket_shiki.c` のテストとベンチ）。`VEACH` の無い plan は何も確保しない（今の出荷アプリは 0 B）。大きさは命令 1 つ 3〜4 B ＋ 前置きと後始末（推定 60〜100 B）。affine128 の本体（約 13 命令）なら 1 区間 150 B 前後（推定）。
- 確保は `MALLOC_CAP_EXEC`（DIRAM。ゲストやシステムと同じプール）。Shiki heap（48 KiB の専用領域）は実行属性が無いので使えない。数を縛るため、1 plan の JIT コードの上限と全体の上限を決める（段階 2 で値を決める）。
- 確保に失敗したら、その plan はインタプリタで動く（失敗を JS に見せない。速さだけが変わる）。

## 6. インタプリタとの関係

- インタプリタ（C モデルと命令ごとの PIE）は残す。JIT は「同じ結果をより速く」出す実装の 1 つで、規範は C モデル（[shiki-v2.md](shiki-v2.md) §11 の §10.1 の例外）。
- 切り替え: `ksn_shiki_vec_pie` と同じく、JIT を使うかの旗を draw の開始で読む。ベンチは 3 つを 1 つのバイナリで比べる。
- host では JIT は無い（host のビルドはインタプリタだけ）。

## 8. 結果

### 8.1 段階 0（実機、2026-11-02、481f7ce）

記録: [logs/shiki-jit0-20261102-481f7ce.txt](logs/shiki-jit0-20261102-481f7ce.txt)。

- **動いた。** メモリ保護を切った版で、`MALLOC_CAP_EXEC` は命令バス側の DIRAM の番地（`0x403beb00`）を返し、データバス側の別名から書いた 2 つの関数が、どちらも C と同じ結果を返した（`one=same/42 loop=same/43`）。
- **時間（実測、7 回の最小）:** 16 ブロック（128 レーン）の「ロード・ロード・飽和加算・ストア」を `loopgtz` で回して、呼び出しを含めて **97 サイクル（1 ブロック約 6 サイクル）**。同じ和を C（-O2）で 1,319 サイクル。本体 4 命令に対して 1 ブロック 6 サイクルなので、パイプラインはほぼ埋まっている（残りは呼び出しと前置き）。
- 比べる相手: 今のインタプリタの PIE 経路は、affine128 のベクトル版（16 ブロック、1 ブロック約 13 命令）で 45,375 サイクル（同じ走行）。`EMIT_POINTS` の推定分（約 16,000）を引くと命令 1 つ約 140 サイクル（**推定**）で、JIT の本体は命令 1 つ約 1.5 サイクル（実測、ロードの待ちを含む）。affine128 を JIT にしたときの見込みは、本体 16 ブロック × 約 20 サイクルに `EMIT_POINTS` の 128 点（約 16,000 サイクル、[shiki-pie.md](shiki-pie.md) §8.4 の推定）を足した程度（**推定**）。ここから先は描画（`EMIT`）が支配する。

- **エンジンはターンの 12〜39%。** 残り（DERBY の WIDE 2 で約 14.5 ms）は JS（レースのモデル、カメラ、Kasane の命令、`pocket.derby` の投影）。
- **MEGADEMO のステップは振り分けが支配している。** 1 ステップ 94〜118 サイクルは、命令ごとの床（57〜100 サイクル、§8 の `CB shiki` の行）にほぼ等しい。DERBY は線・模様の線を描く命令が多く、1 ステップが重い（129〜366 サイクル）。

## 11. 段階 3: プラン全体のスカラーの JIT

§9・§10 から、エンジンの時間の大半は命令の振り分け（1 ステップ 94〜118 サイクル）で、命令の 8 割前後は算術とループの制御だった。段階 3 は、プランの命令をすべて機械語に並べ、算術とループの制御をその場に書き、残りを C の関数で 1 命令ずつ実行する。

### 11.1 形

- **vm はメモリに置いたまま。** 機械語はインタプリタと同じ `vm->reg`・ループの frame・`depth`・`steps` を読み書きする（`r[k]` は `l32i.n` の `4k`）。どのブロックの頭でもインタプリタへ渡せるのは、このため。レジスタへの割り付けはしていない（符号を短くする余地として残る）。
- **アドレスレジスタ:** a2 実行の context（`ksn_jit_run`）、a3 vm、a4 ステップの上限、a5 入力、a6 `INT32_MAX`（飽和の直し）、a7 helper。a8〜a15 は 1 命令の中だけの作業用（`callx8` で helper に渡る）。
- **inline にする命令:** `SET`（movi、入らない値はコードの前の literal pool から `l32r`）、`INPUT`、`ADD`・`SUB`（符号で桁あふれを見て、a の符号で `INT32_MAX`/`MIN`）、`NEG`、`MUL`（`mull`+`mulsh` の 64 bit 積を `ssai`+`src` で床へ shift、`aux≥32` は上位語の shift だけで桁あふれしない）、`SHIFT`（右は `srai`、左は `sll`+`src` で上位語を作って検査）、`REPEAT`（定数回）、`END`、`BREAK_IF_GT`。
- **それ以外**（`SIN`・`MOVE`/`LINE`/`PLOT`・`EACH`/`FETCH`/`VEACH` と vector 命令・`EMIT_*`・`*_H`・`REPEAT_REG`・`DRAW_INDEX` など）は `ksn_shiki_jit_leaf(ctx, pc)` を呼ぶ。中身はインタプリタの 1 命令（`step()`、インタプリタのループと共有する `always_inline` の関数）そのものなので、意味が分かれない。戻り値は 0（続ける）、1（0 回のループ: END の次へ飛ぶ）、それ以外は状態 << 8。
- **ループの深さは字句で決まる**（登録が END と開き命令を対にしている）ので、frame のアドレスはコンパイル時に分かる。

### 11.2 ステップの数え方

ブロックは、開き命令・`END`・`BREAK_IF_GT` の次（と pc 0）から、次のそれらまで。ブロックの頭で長さ k を `steps` に足し、`steps + k > 10,000` ならその pc を返してインタプリタへ渡す（インタプリタが正確なステップで LIMIT にする）。飛び先はすべてブロックの頭なので、どの経路も頭を通る。`VEACH` の helper は段階 2 の機械語で `steps` を足すので、`VEACH` はブロックを終える（次のブロックはメモリから読み直す）。

結果の違いは 1 つだけ: **ブロックの途中で helper がエラー（INVALID・線の上限の LIMIT）を返すと、`vm->steps` はブロックの終わりまで数えた値になる。** 状態・レジスタ・線は同じ。`steps` は統計（`SHIKI_TURN`）にしか使われない。

### 11.3 いつコンパイルするか、メモリ

全部コンパイルすると DERBY は 21 本・887 命令で約 17 KB、MEGADEMO は 24 本・660 命令で約 13 KB（host の `test_scalar.py`、1 命令 約 19〜20 B）。実行可能なメモリはアプリと同じ heap から取るので、**プランは 32 回目の描画でコンパイルし、合計を `ksn_shiki_jit_budget`（16 KiB）で止める。** 失敗したプランは二度と試さない（`plan->heat`、構造体の詰め物の 2 バイト）。**§14 で 4 回目に変え、予算・heap の失敗は 64 回の描画の後に試し直すようにした。**`SHIKI_TURN` の末尾 `jit=<on>/<bytes>` が、その時点の量。

### 11.4 検査

- **host（`tools/shiki_jit/test_scalar.py`、`run.sh` から）:** `ksn_shiki_bench_random()` のランダムなプログラム（int32 の境目の値・2 の冪・対数一様の大きさ、255 回までの入れ子ループでステップの上限、BREAK、線）をコンパイルし、出した命令だけの小さな Xtensa エミュレータで走らせてインタプリタと比べる。エミュレータは生成した命令表（アセンブラで確かめた表）で解読し、意味は ISA の記述から書いたので、エミュレータと compiler の両方が同じ読み違いをすると通ってしまう。そこは実機が見る。変異（飽和の直し・上限のずれ・shift 量・BREAK の飛び先）で落ちることを確かめた（`hi>>(s-1)` の変異は等価で落ちない）。さらに DERBY と MEGADEMO の全プランをコンパイルし、objdump で隙間なく解読できること、`l32r` の読む先が pool の中でエミュレータの読みと一致することを見る。
- **実機（cycle bench の `CB jit scalar 1/4`〜`4/4`）:** 同じランダムなプログラムを、実機の CPU で、インタプリタと機械語の両方で描き、観測できるもの（状態・レジスタ・線、DONE ならステップ・pen・raster・depth）を比べる。DONE のプログラムで 1 ステップのサイクルも出す。
- **アプリ:** `-DPOCKET_SHIKI_JIT_AB` のビルドは `SHIKI_TURN` の行ごとに JIT を入れ切りするので、同じバイナリで比べられる。

## 12. 描画の命令: SIN をその場に、線の命令を直接呼ぶ

§11.5 で残りの時間は描画の命令（helper）だと分かったので、そこを詰めた。

- **`SIN`:** 機械語に約 20 命令で書く（`extui` で位相を切り出し、奇数の象限で `0x4000 - w`、表 `ctx->sin` の `T[i]` に `floor((T[i+1]-T[i])*t/64)` を足し、象限 2・3 で符号を返す）。`T[i+1]` は `t > 0` のときだけ読むので、`w = 0x4000` は `T[256]` だけを読む（host のエミュレータは表の外を読むと止まる）。
- **`MOVE`・`LINE`・`PLOT`・`LINE_C`・`PLOT_C`:** 機械語がレジスタを読み、`ksn_shiki_jit_draw(ctx, x, y, colour, kind)` を直接呼ぶ。中身はインタプリタの同じ case（色の検査 → 座標の検査 → 線の追加 → pen）で、命令の振り分け（`step()` の switch）を通らない。flash の取りこぼしを避けるため IRAM に置いた（`coord`・`emit`・`floor_shift` は always_inline で中に入る）。色が 2047 を超える `LINE`/`PLOT` は literal pool から読む。
- 新しい形式 `extui`（幅 1/6/9/14）・`addmi`・`addx4` は他と同じくアセンブラで確かめた表から作る。ランダムなプログラムに `LINE_C`・`PLOT_C`・`SIN` を足し、変異 7 通り（符号・補間の shift・折り返し・種類・色のレジスタ・色の即値・literal）がすべて落ちることを確かめた。
- コードは 1 命令 約 22〜24 B に増えた（全部で DERBY 約 19 KB、MEGADEMO 約 14.5 KB。熱いものだけを 16 KiB の予算でコンパイルするのは変わらない）。

## 13. CUBIC の重みの表と、最内側のループ

### 13.1 CUBIC

区間 k（1..n）の重み `w0..w3` は k と n だけで決まり、制御点に依らない。JIT はプランごとにすべての CUBIC の重みを一度だけ表にし（`ksn_shiki_cubic_weights`、pc の順、最大 512 個の int32 = 2 KB、予算に数える）、機械語は CUBIC の行の位置を helper に渡す。表のある区間は割り算 1 回と `mul16` 6 回が無くなる。表を作れなかったとき（大きすぎる、予算）は helper がその場で計算する（インタプリタと同じ）。

`cubic` はループで書き直した（`mul16` と座標の検査が 1 か所ずつ）。-O2 で 4.3 KB あったものが -Os で 690 B になり、IRAM へ移した。IRAM のコードが flash を呼ばないよう、`mul16`・`sat32`・`floor_div`・`floor_mod`・`round_div` を always_inline にした（`cubic_weights` だけは、表の無い経路で flash を呼ぶ）。IRAM に置いた描画の関数は合わせて約 2.3 KB（-Os の見積もり）、ホーム画面の空きは 197,324 → 195,240 B（実測、2,084 B 減）。

検査: host のランダムなプログラムは、表を渡す回と渡さない回を交互にし、両方をインタプリタと比べる。CUBIC と LINE_PATTERN のレジスタ群を範囲内に置く組み立てを生成器に足した（3,000 本で CUBIC と LINE_PATTERN が合わせて約 950 回走る）。表の行を 4 ずらす・重みを 4096 ずらすと落ちる。重みを 1 だけずらしたものは座標が 1/65536 画素しか動かず、出力の画素に現れないので落ちない。参照実装との照合（shiki_diff）も通る。

### 13.2 最内側のループ

ループを含まず `BREAK_IF_GT` の無い本体の `REPEAT` / `REPEAT_REG` は、入口で `回数 × (本体 + END)` のステップを一度に数え（上限を越えるなら本体の頭の pc でインタプリタへ渡す）、回数を a7 に置く（`callx8` は a0..a7 を残す）。`END` は `addi` と分岐の 2 命令になり、1 周ごとのブロックの頭（4 命令）が無くなる。a7 を空けるため、helper の番地は呼ぶたびに context から読む。変異（数の 1 ずれ、頭の飛び先、減らす量、本体の位置）は 4 つとも落ちる。

## 14. コンパイルの時機と heap: 4 回目、試し直し、IRAM だけのメモリ

§13.3 の TWIST の外れ値を追った。

### 14.1 何が起きていたか

- **32 回目の描画は遅すぎた。** MEGADEMO は場面を再生しながらプランを登録する（TWIST の負の組は 60 フレーム目に登録され、122 フレーム目から 74 フレーム描かれる）。1 フレーム 1 回の描画だと 32 回目は場面の半ばで、半分をインタプリタで走らせていた。**`JIT_HEAT` を 4 にした**（1 回しか描かないタイトルのプランは、今もメモリを使わない）。
- **4 回目にすると heap の失敗が出た**（`SHIKI_TURN` 末尾に `jitfail=<拒否>/<予算>/<heap>` を足して数えた）。原因の 1 つは、コンパイラが一時に取っていた 4 KB の作業領域だった。**作業領域を無くし、長さを数えるだけのパス（バッファ無し）で長さを出し、その長さの実行可能メモリへ直接書く**ようにした。コンパイルは 2 回走るので、1 命令 約 4,400 → 約 7,900 サイクル（実機、cycle bench）。
- **その版では MEGADEMO のコンパイルがすべて失敗した**（jitfail heap 134、[logs/shiki-jit9-20261103-5e35e1f.txt](logs/shiki-jit9-20261103-5e35e1f.txt)）。heap が詰まると `MALLOC_CAP_EXEC` は DIRAM ではない領域を返す（当時は「IRAM だけの領域」と推定した。**§15 の実測で、実際は RTC fast memory（`0x600fe000`、8 KB）だった**）。DIRAM の別名から書く前提のコードは、それを断っていた。**エンコーダに語単位の書き込み（その語を読んで 1 バイトを差し替えて書く）を足し**、DIRAM でないときはそれで書く（`ksn_jit_buf.word_only`）。host の検査は、語単位で書いたバイト列が普通に書いたものと一致することも見る。コンパイルは 1 命令 約 8,300〜8,600 サイクル（語の 0 埋めの分が増えた）。
- **heap・予算の失敗は 64 回の描画の後に試し直す**（場面のプランは入れ替わり、heap も空く）。`heat` が負の間が待ち。コンパイラの拒否は二度と試さない。

### 14.2 試し直しが JIT を遅くした

2ced4c9（語単位の書き込み）の実機で、MEGADEMO のコンパイルは通った（TWIST の JIT 有りの窓で CUBIC 0.33〜0.35 ms、無し 0.44〜0.46 ms）。ところが **DERBY の WIDE 2 で、JIT 有りの窓の方が遅かった**（2.07〜2.54 ms、無し 1.68〜2.03 ms）。この窓では heap が足りずに入らないプランが 1 窓に 10〜13 回試し直され、**試し直すたびに長さを数えるパス（コンパイルと同じ重さ）を走らせてから、確保に失敗していた。**

直し（05d1a75）: 確保に失敗したプランは、そのとき要った長さを覚える（`plan->need64`、64 B 単位の切り捨て。`heat` を int8 にして空けた 1 バイト）。次の試し直しでは、まず `heap_caps_get_largest_free_block(MALLOC_CAP_EXEC)` を見て、覚えた長さより短ければ数えるパスを走らせずに失敗にする。切り捨てなので、飛ばすのは必ず失敗する場合だけ。

## 15. 実行用メモリの行き先と、Shiki の区画との共有

§14.3 の「残る限界」（DERBY のレース中、後から増えるプランの実行用メモリが取れない）を、推定ではなく実測で追った。

### 15.1 測ったもの（EXECMAP、6758888）

測定用のビルド（`ksn_shiki_jit.c` の `POCKET_SHIKI_JIT_EXECMAP`、今は既定で無効）は、最初のコンパイルと、heap で失敗している間の 3 秒ごとに、heap の領域ごとの種類・`MALLOC_CAP_EXEC` を出すか・空き・最大の空き・大きい使用ブロックを `EXECMAP` の行で出す。DERBY のレース中（実測、[logs/shiki-jit12-20261103-ba9d872.txt](logs/shiki-jit12-20261103-ba9d872.txt)）:

| 領域 | 大きさ | 実行可 | 空き（最大の塊） | 中身 |
| --- | ---: | :---: | --- | --- |
| DIRAM `0x3fcb5170` | 214,432 B | ○ | 2,232 B が 38 個に分かれる（最大 152 B） | 約 1,500 個の小さいブロック（大半はゲストの QuickJS）、Shiki の区画 49,152 B、32,768 B、10,752 B など |

- **DIRAM はゲストの小さいブロックで埋まり、実行用の確保はすべて RTC fast memory（8 KB）に落ちていた。** JIT のコードが 6.9 KB 前後で止まっていたのは、この 8 KB が上限だったため。
- **Shiki の区画（48 KiB）は DIRAM にある。** アプリの開始時、ゲストを作る前に 1 つの塊で取るので、命令バス側の別名（`esp_ptr_diram_dram_to_iram`）からそのまま実行できる。DERBY の区画の最大使用は 37,408 B（shiki.md §4.5.1）で、約 11 KB 空いている。

### 15.2 区画を JIT と共有する（ba9d872）

- **JIT のコードと CUBIC の重みの表は、まず Shiki の区画から取る**（`shiki_heap_spare(n, keep)`、16 B 境界）。取った後の最大の空きが `JIT_REGION_KEEP`（2 KB）を下回るなら取らない。区画に入らなければ、今までどおり `MALLOC_CAP_EXEC`（実際には RTC fast memory）。コードはデータバス側の番地からバイトで書き、命令バス側の番地で呼ぶ。
- **区画の持ち主（フレーム・作業領域・式・点・データ領域）が先。** 区画の確保が失敗すると、区画の reclaim hook（`shiki_heap_set_reclaim`）が呼ばれ、JIT は区画に置いたすべてのプランのコードと表を返し（`drop_scalar`、プランは `JIT_RETRY` 回の描画の後に作り直す）、確保をもう一度試す。JIT のコードの実行中（`jit_running`）は何も返さない。区画の確保はすべて描画の前（エンジンの状態・フレーム・登録）で起きるので、実行中に返す必要は生じない（コードで確認）。
- **host の検査:** `tools/kasane_contract/test_shiki_heap_spare.c`（`run.sh` から）。keep を守ること、16 B 境界、hook が無ければ持ち主の確保は失敗し、hook があれば余りを返して成功すること、成功時に hook を呼ばないこと。

## 16. 描かれなくなったプランのコードを捨てて場所を作る

§15.3 の残り（DERBY のレースの後半、CLOSE・VISION・FINISH のカメラで増えるプランが実行用メモリを取れない）への対策（5021a80）。DERBY はレースの開始時に全カメラのプランを登録するので、もう切り替わったカメラのコードが区画と RTC fast memory を塞いでいた。

- **描いた時刻を持つ。** コードのあるプランは、描くたびに `jit_clock`（コードのあるプランを描いた回数）を `last` に記録する。コードのある全プランを 1 本のリストに持つ（以前は区画にあるものだけ）。
- **入らなければ、冷えたプランから捨てる。** 新しいプランのコードが予算か実行用メモリに入らないとき、直近 `JIT_COLD_DRAWS`（1,024）回の描画で描かれていないプランのコードを、古い順に、入るまで捨てる（`make_room`）。捨てられたプランは熱さ 0 から。また描かれれば 4 回目に作り直す。JIT のコードの実行中は捨てない。
- **数える:** `SHIKI_TURN` の末尾に `jitdrop=<区画の reclaim>/<冷えて捨てた数>`。

## 17. コンパイルを速くする

§16 で、捨てたコードの作り直しが窓を 0.3〜0.6 ms 跳ねさせていた。コンパイルは 1 命令 約 8,500 サイクル（2 パス）で、生成する機械語 1 命令あたり 1,000 サイクルを超えていた。

### 17.1 どこが重いか（host、callgrind）

DERBY と MEGADEMO の組み込みの 45 本を、長さを数えるパス＋書くパスで 200 回ずつコンパイルした（x86 の命令数。比率だけを見る）。**91% がエンコーダ（`ksn_jit_emit`）** で、コンパイラ本体は 7%。

- エンコーダはオペランドのビットを 1 つずつ調べて XOR していた（1 命令 12〜18 回）。
- 長さを数えるパスも、命令の語を全部組み立ててから捨てていた。

### 17.2 直したこと（9e31ca5）

- **ビットの連なり（run）で符号化する。** 表の生成器（`gen_encoding.py`、アセンブラから作る）が、オペランドのビットと命令のビットが一緒に進む区間を run にまとめ、エンコーダは run ごとに shift と mask 1 回で入れる（`l32i.n` は 12 ビット → 3 run）。Python の照合側の符号化も run で行うので、`--check` の全範囲の照合と `test_encoder.py`（3,462 通り）が、run の表そのものをアセンブラと突き合わせる。
- **長さを数えるパスは長さだけ返す。**
- **区画では 1 パス。** `JIT_GUESS`（1 命令 32 B＋64 B）の大きさのブロックを区画から取り、1 回で書き、余りを返す（`shiki_heap_shrink`。TLSF は縮めるときその場で切るので番地は変わらない。万一動いても、コードは自分からの相対と context しか使わないので動く）。見積もりが足りないとき・区画に入らないときは、今までの 2 パスの道。
- host の命令数は 1,140M → 503M（2.3 倍）。

### 17.3 結果（実機、2026-11-03）

記録: [logs/shiki-jit14-20261103-b315417.txt](logs/shiki-jit14-20261103-b315417.txt)。`SHIKI_TURN` に `jitcc=<窓のコンパイル数>/<1 フレームあたりのコンパイルの ms>` を足した（b315417）。

## 18. 飽和チェックを外す（リスクで判断する）

ADD/SUB の飽和チェック（`xor, xor, and, bgez` と、飽和したときの直し）は ADD 26 B のうち 18 B を占め、生成コードの 1/4 だった（host、出荷プラン 45 本）。静的に「溢れない」と証明できる地点は ADD 3/327 しかない。そこで、実行中の値の大きさを見て、余裕のある地点からチェックを外す。証明ではなくリスクで外すので、外した地点が後で溢れると、飽和ではなく折り返す。

### 18.1 共有チェッカーと地点のログ枠（38a55ef）

各地点は検査を持たず、IRAM の 1 つのチェッカーへ `call0` する。`call0` の後ろの 4 B（語境界に揃える。手前の命令を幅広の形にして 1 mod 4 に合わせる）が、その地点のログ枠になる。チェッカーは飽和させたうえで |結果| を枠に OR し（bit31 は「まだ実行されていない」の印）、`ctx->ra` に退避したコードの a0 を戻して、枠の後ろへ `jx` で帰る。RTC の高速メモリに置かれたコードは `call0` が届かないので、インラインの検査で出す（0c9d701: そのとき長さが変わるので、ブロックを取り直す）。

速い入口（ログなし）もある。地点の `call0` の宛先を書き換えて、チェックだけを残す。

### 18.2 判断（12804a9）

最初の 16 draw は全地点のログを取り、最初の判断で 3 つに分ける。

| 最初のログの大きさ | 扱い |
| --- | --- |
| INT32_MAX まで 3 ビット以内（飽和を含む） | 常時チェック（速い入口） |
| 6 ビット以上の余裕 | その場で確定（チェックなし） |
| その間 | 休止とサンプル（18.3） |

### 18.3 休止とサンプル（59f2517）

外した地点は `call0` を枠を飛び越す `j` に書き換え、枠に予定（次に見る draw、これまでの最大ビット、休止の長さ）を書く。休止が終わると 1 draw だけログの入口に戻して測る。増えていなければ休止を 2 倍に、増えていれば「同じ増え方で余裕が 3 ビットになるまでの半分」にし、16 draw を切るか 3 ビット以内に近づけば常時チェックにする。休止が 128 draw（増えないサンプルが 3 回続いた）に届けば確定。

### 18.4 判断を残す（d626f39）

冷えたコードを捨てても、地点の状態を `jit_plan` に 2 B ずつ残し、同じ配置でコンパイルし直したときにそのまま当てる。

### 18.5 確定したプランを作り直す（7fe6d75）

プランの休止中の地点がすべて確定したら、コードを捨てて次の draw でコンパイルし直す。確定した地点は素の `add`（8 B、チェックも分岐もない）、常時チェックの地点と実行されなかった地点はインラインの検査。チェッカーとログ枠は消える。判断はプランの命令の FNV-1a をキーに 48 件覚えるので、登録し直された同じプラン（DERBY はシーンごとに登録する）は最初から作り直した形でコンパイルされる。

`call0` を `j` に変えるだけでは速くならなかった（59f2517、実機）: インラインの検査（分岐しない 4 命令）が分岐する `j` 1 本に替わるだけだからである。速さは作り直しで出る。

### 18.6 結果（実機、2026-11-03、12804a9）

## 19. RTC fast memory には JIT のコードを置かない

RTC fast memory（`0x600FE000`、8 KB）は ESP-IDF が普通のヒープに加えており、DIRAM が詰まると `MALLOC_CAP_EXEC` がここを返す。ここは APB クロックで動き、コードは遅い（§15: NEWS 2.3 ms、DIRAM で 0.8 ms）。共有チェッカー（§18）の `call0` も届かない。

- JIT は RTC fast memory を実行用メモリとして使わない（e3aa94c、スカラーのコード。VEACH の区間も同じ）。返ってきたら手放し、スカラーのコードは「場所がない」扱い（`need64`）で冷えたプランの場所を待つ。その間はインタプリタ。
- RTC fast memory は、遅くても困らない常駐の仕事に起動時に先に渡す。まず `input` タスクのスタック 4 KB（e3aa94c。実測の最大使用量は約 1,250 B）。Wi-Fi・時刻同期のタスクも収める見直しは [issue #116](https://github.com/dj-oyu/cardputer-adv-pocketjs/issues/116)。


### 19.1 確保の能力の指定で RTC を外す（c6119de）

e3aa94c の形（確保してから RTC なら手放す）は、DERBY のレースで JIT をほぼ止めた（実機、c4d872d）。`input` のスタックを置いた後の RTC の残り約 3.5 KB が、`MALLOC_CAP_EXEC` の最大の空きブロックだった。`fits()` はこれを数えて「入る」と答え、確保は RTC に当たって手放され、`make_room()` は冷えたプランを一度も捨てなかった。同じプランが 64 draw ごとにサイズの計算からやり直した。

- c4d872d のレース（実機）: `jitfail` の NOMEM が 274 まで増え、JIT のコードは 4,704 B で止まり、コンパイルの時間がターンあたり最大 0.6 ms。発走 1.36〜1.46 ms（12804a9 は 0.95〜0.97 ms、10,592 B）。
- 直し: 確保も `fits()` の大きさの検査も `MALLOC_CAP_EXEC|MALLOC_CAP_DMA` で行う。実行できて DMA も使えるのは DIRAM だけなので、RTC は候補にも空きの数にも入らない。手放す検査は保険として残す。

## 20. レジスタ保持（まっすぐな命令の並びの中で、VM のレジスタを CPU のレジスタに置く）

c4d872d（2026-11-03 ユーザー指示「レジスタ保持に戻って」）。共有チェッカーを使わないコード（§18.5 で確定した後のコード）に限る。

- `SET`・`INPUT`・`ADD`・`SUB`・`NEG`・`MUL`・`SHIFT` が続く間（まっすぐな並び）、VM のレジスタを CPU のレジスタ a8〜a15 に置く（LRU で割り当て、書き換えたものは印を付ける）。読みは、まだ持っている値を使い、メモリから読み直さない。結果は並びが終わるまでメモリへ書かない。並びの中で上書きされた結果は一度も書かない。
- 並びの終わり（helper の呼び出し、ループの制御、`BREAK_IF_GT`、`SIN`、プランの終わり、ブロックの頭）で、印の付いたものをメモリへ書き戻す。並びの外では、メモリの VM はインタプリタと同じ値になる（インタプリタ・helper・ブロックの頭からの手渡しがそれを前提にする）。
- 結果: 出荷しているプランの確定後のコードが 26,171 → 24,461 B（−6.5%、host で測定）。実機での速さの効果は単独では測っていない（同じ時期に RTC の扱い §19 と区画の管理 §21 が変わり、DERBY の数字はそちらの影響が大きい）。検査: `tools/shiki_jit/test_scalar.c` の 5 つの形（inline・checker・patched・plain・final）で、インタプリタと命令ごとに一致。

## 21. 区画の管理を固定長の表に替える

§19.3 の `shk=50164/3328/57344` のとおり、区画の空きは ESP-IDF の TLSF（`multi_heap`）の下で細切れになっていた。区画の持ち主は少なく（データ領域 16・リスト 8・プラン 32・フレームなど 4・JIT のコードと表）、大きさは確保の時に決まり、場面の切り替わりでまとめて解放される。TLSF の大きさの区分・ブロックの見出し・境界合わせの切り出しは要らない（2026-11-03 ユーザー決定: 自前のリストで管理し、初期化は 1 回、free 相当を減らし、use-after-free を避ける）。

`main/pocket/shiki_heap.c`（host と実機で同じコード）:

- **固定長の表。** 生きているブロックを 128 件の表（開始と長さを 4 バイト単位の 16 bit、計 512 B の `.bss`）に番地の順で持つ。区画の中はブロックの中身だけ。
- **持ち主は下から、JIT は上から。** 持ち主（`malloc`・`calloc`・`aligned`）は一番低い入る隙間に、`shiki_heap_spare`（JIT のコードと表）は一番高い入る隙間に置く。出入りの多い JIT のコードが、持ち主の間に挟まらない。
- **空きは常にゼロ。** 区画は取った時に 1 回だけゼロにし、解放したブロック（と縮めたブロックの後ろ）は返す時にゼロにする。`calloc` はゼロ埋めをしない。host では確保のたびに中身がゼロであることを確かめ、ゼロでなければ止める（解放後の書き込みを host で捕まえる）。
- **知らない番地の解放は断る。** ブロックの先頭でない番地の `free`（二重解放など）は、何もせずに記録する（実機は `SHIKI_HEAP_REFUSED` のログ、host は止める）。

まだしていないこと: ブロックを番号で引く形（世代つきの番号）と、場面の切り替わりでの詰め直し。JS の窓は `release()` が先に `ArrayBuffer` を外すので（§9.2 の順）、JS から解放済みのメモリには届かない。詰め直しは、この段の実機の `shk=` を見てから決める。

- **DERBY のレースは c6119de と同じ遅さ**（発走 1.33〜1.49 ms、WIDE 0.53〜0.55、WIDE 2 0.95〜1.57。JIT のコード 3.2〜4.9 KB）。区画は `shk=43264/2104/49152` 前後: 空き約 6 KB のうち一続きは約 2.1 KB。

- 直し: 共有チェッカーを呼ばないコード（§18.5 で確定した後のコード、ほとんどのプラン）は、自分と実行時の文脈しか番地で指さない（分岐と `l32r` は pc 相対、リテラルはブロックの中、16 B 単位で動かせば境界も保つ）。`shiki_heap_shrink_up` で、ブロックの上端を保ったまま中身を上へ寄せ、頭を返す。チェッカーを呼ぶコードは `call0` が絶対番地に依存するので、今までどおり後ろを返す。

アプリごとの予算（[shiki-spec.md](shiki-spec.md) §9.2 の manifest の `shiki: {bytes: N}`、ファームでは `app_registry.c` の `shiki_bytes`）で、DERBY だけ 56 KiB にする。他のアプリは既定の 48 KiB のまま。

- host の DERBY の検査（`tools/games/test_derby_host.c`）は既定の 48 KiB で区画を開いたまま。持ち主が 48 KiB に収まることの検査として残す。

### 21.4 区画を返すのは足りる分だけ、残す余裕は 0（2026-11-03 ユーザー決定）

- **返し方。** 持ち主の確保が失敗すると、区画は reclaim hook を、確保が通るか JIT に返すものが無くなるまで呼ぶ。hook は 1 回に 1 プランだけ、一番長く描かれていないプランの区画のブロック（コードと表）を返す。以前は 1 回で全プランが返していた（MEGADEMO の TWIST で、2 組目の登録の時に 12 プランすべて、§21.1 の記録）。
- **`JIT_REGION_KEEP` は 2 KB → 0。** 余裕は、全部を返す作りでの手放しを減らすためのものだった（§15）。足りる分だけ返すなら、余裕は JIT のコードの場所（プラン 2 つ分ほど）を減らすだけになる。
- 測ること（実機）: MEGADEMO の TWIST と DERBY の場面の切り替わりで、`jitdrop` の 1 つ目（返したプランの数）と engine_ms。

### 21.5 見込みの長さを実測に合わせる

`JIT_GUESS(n)` は 32 n + 64 → **24 n + 32**。出荷している 45 のプランのコードは 1 命令あたり最大 23.4 B（host の同じコンパイラで実測、`kasane.ci` 58 命令 1,356 B、共有チェッカーの版は `derby.pt` 59 命令 1,370 B）。区画での一回のコンパイル（§17）は見込みの長さの一続きの空きを要るので、32 n + 64 では、入るはずのコードが区画の詰まった時に取れず、二回の道（長さを測るコンパイルが 1 回増える）へ回っていた。超えるプランが出ても二回の道で正しくコンパイルされる。`tools/shiki_jit/test_scalar.py` は、出荷しているプランが見込みを超えたら失敗する。

## 22. 描画は描画中のフレームの末尾へ直接書く（作業領域を廃止）

2026-11-03 ユーザー決定。これまで 1 回の `draw()` は、面の部屋と関係なく 1,024 本入る作業領域（`workspace`、10,246 B）へ書き、終わってから「描画中のフレームの残りに入るか」を確かめ、入れば `memcpy` で写していた。入らない描画を「全部入るか、何も入らないか」にするための一時置き場だった。

- **直し。** エンジンの状態に、その描画で出してよい線分の数 `cap` を持たせる（`ksn_shiki_vm.cap`、`ksn_shiki_draw_index_cap`）。`pocket_proc.c` は描画中のフレームの末尾 `&candidate->segments[count]` を出力先にし、`cap` を残りの本数にする。超える描画はその場で `LIMIT` で止まり、フレームの本数（`count`）を進めないので、書きかけはフレームに入らない（「全部か無か」は保たれる）。部屋を使い切った `LIMIT` は、以前と同じ `frame drawing limit` として返す。
- `cap` を見るのは線分を出す 4 か所（`emit`、`LINE_PATTERN`、`EMIT_POINTS`・`EMIT_LINES` の速い道）。スカラーの JIT は線分を C の helper で出すので、同じ検査を通る。他の入口（`ksn_shiki_draw` など）は `cap = KSN_SHIKI_SEGMENTS`（今までどおり）。
- **作業領域は、画像の面の帯のキャッシュ（240 × 8 × 2 = 3,840 B）だけになった。** 画像の面が選ばれた時（`resource()`、`pocket_proc_image_mode_at`）か、画像の面の `beginFrame` で取る。画像の面を使わないアプリは取らない。DERBY も MEGADEMO も画像の面を使う（DERBY は `derby_view.js` の `SK.resource({maxSegments: 768})`）。
- 効果（コードからの計算）: 画像の面を使うアプリ（DERBY・MEGADEMO）で 10,246 − 3,840 = 6,406 B、使わないアプリで 10,246 B が区画から空く。描画ごとの `memcpy`（DERBY のレースで 1 フレーム数百本 × 10 B）も無くなる。実機では未測定。
- host の検査（`test_pocket_proc_turn_qjs.c`）は、面の確保が「フレーム 2 枚と作業領域」から「フレーム 2 枚」になったことを確かめる。

描画中と確定済みのリストを 1 つにする案は見送った（§23）。

面ごとの 2 つのリスト（組み立て中の candidate と、画面に出した committed）を 1 つにまとめ、`frame()` が例外で終わった時は描けた分を出す（flush）、という変更を一度実装した（b65e830、host の検査は通過）。ユーザーの判断で取り消した（Shiki の区画の削減は §22 の作業領域だけにする）。今の動作は 2 つのリストのまま:
