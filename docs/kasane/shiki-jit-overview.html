Shiki JIT とメモリ配置

Shiki の描画のプログラム（プラン）を、実行中に Xtensa の機械語へ変える JIT と、その機械語を置くメモリの話。2026-11-03 までの実験を、一続きの問いとして並べ直した図解。正本は shiki-jit.md（§番号はこの文書の節）。数値には 実測 推定・計算 未確認 の印を付け、どこで測ったか（実機 / host）を書く。

0. この文書の地図

全体の問題: Shiki はアプリが登録した小さな命令列（プラン）を、毎フレーム何十回もインタプリタで走らせて線分を作る（描画のパイプライン自体は Kasane の描画パイプライン で説明している）。インタプリタは命令の振り分けで時間を使うので、よく描くプランを機械語にして直接走らせたい（JIT）。ところがこの機体は PSRAM が無く、機械語を置けるメモリは、アプリ（QuickJS のゲスト）や描画データと取り合う DIRAM だけ。この文書の大半は「速いコードを、どこに、どれだけ置けるか」の話になる。

  1. 何を機械語にするのか — インタプリタの何が遅く、JIT は何を置き換えるか。出発点。ここで「機械語の置き場所」が必要になる。
  2. 機械語を置ける RAM はどこか — この石で命令を実行できるのはどのメモリか。1 章で作った機械語を置く場所の候補を絞る。
  3. Shiki の区画に相乗りする — 候補の DIRAM がゲストで埋まっているとき、どこから場所を借りるか。2 章の候補が実際には空いていなかったので、別の空きを探す。
  4. 飽和チェックをリスクで外す — 場所が限られるなら、コードそのものを小さく速くできないか。3 章で場所は得たが量が足りない。コードの 1/4 を占める検査を削る。
  5. レジスタキャッシュ — 検査を外したコードを、さらに短くできないか。4 章で検査を消したコードにだけ使える最適化。
  6. RTC fast memory を断る — 遅いメモリにコードを置かないと決めたら、何が起きたか。4 章の検査の仕組みが RTC では動かないことが、置き場所の見直しを迫った。
  7. 区画を大きくする実験 — 足りないなら区画を 8 KiB 増やせば済むか。6 章で「DIRAM そのものが足りない」と分かった、その素直な対策。
  8. 区画の管理を作り直す — 空きの総量はあるのに入らない（細切れ）を、どう無くすか。7 章で「増やす」は他のアプリを壊すと分かり、「詰め方」へ戻る。
  9. 作業領域を無くす — 区画の持ち主の側を減らせないか。8 章で詰め方は直ったが、48 KiB では量がまだ足りない。
  10. リストを 1 本にする案（見送り） — さらに削る案を、なぜ取り消したか。9 章の続きとして試し、振る舞いの変化を理由に戻した。
  11. 推移と今の姿 — 結局 DERBY はどれだけ速くなり、区画は今どう使われているか。全章の結果を 1 つの表と図にまとめる。
  12. 事実・推定・未確認

1. 何を機械語にするのか §9〜§14、§17

知っているもの: V8 の Ignition → TurboFan、JVM のインタプリタ → C1/C2。何回か呼ばれた関数だけを機械語にし、残りはインタプリタで走らせる、という段階分け。

違うところ: 機械語を置ける量が JIT の予算 16 KiB で、それもアプリと取り合う。deopt のような「推測が外れたら戻す」仕組みは無く、ブロックの頭でインタプリタへ渡せるだけ。

この章の問い: Shiki のインタプリタは何に時間を使っていて、JIT はそれをどう置き換えるのか。

Shiki のプランは、レジスタ 16 本と入れ子のループを持つ小さな命令列で、JS の draw() 1 回ごとに最後まで走り、線分を出す（プランと線分の並びは パイプラインの §6）。インタプリタは 1 命令ごとに「読む → 種類で分岐 → 被演算子をメモリから読む → 計算 → 書く」を踏み、1 ステップ 94〜118 サイクルのほとんどが振り分けだった 実測（実機、§9）。命令の約 8 割は算術とループの制御 host の内訳、§10。

段階 3 のスカラーの JIT（§11）は、プランの命令を順に機械語へ並べ、算術とループの制御はその場で書き、線を引く・SIN・ベクトルの区間などは C の関数（helper）を呼ぶ。ランダムなプログラムでは 1 ステップがインタプリタ 72〜84 → 機械語 28〜43 サイクル 実機、§11.5。

1 回の描画で JIT が何をするか（今のコード）

定数はコードで確かめた: JIT_HEAT 4、JIT_RETRY 64、予算 ksn_shiki_jit_budget 16,384 B、JIT_GUESS(n) = 24n+32、JIT_EXEC_CAPS = MALLOC_CAP_EXEC|MALLOC_CAP_DMA（main/ui/kasane/ksn_shiki_jit.c）。区画から取ったブロックも DIRAM の中にあることを確かめてから使う（in_diram()）。

なぜ 4 回目か

1 回しか描かないプラン（タイトルなど）にメモリを使わないため。以前は 32 回目で、MEGADEMO は場面の途中でプランを登録するので、場面の半分をインタプリタで走らせていた（§14.1）。

コンパイルの重さ

エンコーダをビットの連なり（run）で符号化し、区画では見込みの大きさで 1 回書く形にして（§17）、1 命令 約 8,500 → 3,170〜3,320 サイクル 実機 cycle bench。DERBY の中ではコンパイルは 1 フレームあたり最大 0.19 ms 実機、§17.3。

1 本のコードの並び

正しさの検査: エンコーダの表はアセンブラから作り（tools/shiki_jit/gen_encoding.py）、host ではランダムなプログラムを小さな Xtensa エミュレータで走らせてインタプリタと比べ（test_scalar.py）、実機の cycle bench でも 800 本を突き合わせる（§11.4、すべて一致 実機）。

機械語は作れるし速い。次の問題は「その機械語をどのメモリに置けば実行できるか」。

2. 機械語を置ける RAM はどこか §2、TRM v1.8 p.403

知っているもの: JIT が W^X のために、同じ物理ページを「書ける番地」と「実行できる番地」の 2 か所に mmap する二重マッピング。

違うところ: ここに MMU のページ管理は無く、どの RAM が命令バスから見えるかは石の配線で決まっている。メモリ保護（CONFIG_ESP_SYSTEM_MEMPROT）は切ってある（§2）。

この章の問い: この石で、JIT の機械語を置いて実行できるのはどのメモリか。

CPU から見える内部 RAM は 4 種類。命令を実行できるのは命令バスから見える所だけで、SRAM2 はデータ専用。

SRAM1 の同じバイトは、データバスでは 0x3FC8_8000 起点、命令バスでは 0x4037_8000 起点の番地を持つ（差は 0x6F_0000）。JIT はデータ側の番地に書き、命令側の番地を関数として呼ぶ。

候補は DIRAM（速い）と RTC FAST（8 KB、遅い）だけ。ところが DIRAM はアプリの実行中、ほとんど空いていない。次の章はその実測から始まる。

3. Shiki の区画に相乗りする §14.3、§15、§16

知っているもの: リクエストごとの arena（まとめて取ってまとめて捨てる）と、空いた容量を貸して必要になったら取り上げるスポットインスタンス。CDN のキャッシュが、最近使われていないものから追い出す（LRU）こと。

違うところ: 取り上げは同期で、描画のコードの実行中には返せない。追い出したコードは、また 4 回描かれたら作り直す（費用はコンパイル 1 回）。

この章の問い: DIRAM がゲストの小さなブロックで埋まっているとき、機械語の場所をどこから得るか。

測定用のビルド（EXECMAP、§15.1）で DERBY のレース中の heap を数えた。DIRAM はゲスト（QuickJS）の小さいブロック約 1,500 個で埋まり、空きは 2.2 KB が 38 個に散らばる（最大 152 B） 実機、ba9d872。実行用の確保（MALLOC_CAP_EXEC）はすべて RTC FAST に落ち、JIT のコードは 6.9 KB で頭打ちだった。

ゲスト（QuickJS）など 大きい確保（持ち主は未特定） Shiki の区画 データ専用 RTC FAST

区画の持ち主は Shiki（フレーム・式・データ領域など）で、JIT は余りを借りるだけ。持ち主の確保が失敗すると reclaim hook が呼ばれ、JIT が場所を返す（§15.2。返し方は 8 章で変わる）。区画に入らない新しいコードのためには、直近 1,024 回の描画で描かれていないプランのコードを古い順に捨てる（§16、JIT_COLD_DRAWS）。DERBY はレースの開始時に全カメラのプランを登録するので、切り替わった後のカメラのコードが場所を塞いでいた。

置き場所で 3 倍変わる

1 フレームあたりの Shiki のエンジンの時間（ms）。同じ JIT のコードでも、RTC FAST に置くと DIRAM（区画）の 2〜3 倍遅い 実機、別の実行どうしの同じ場面の窓。

インタプリタ（JIT 無し） JIT、コードは RTC FAST（2ced4c9・05d1a75） JIT、コードは Shiki の区画＝DIRAM（ba9d872）

記録は jit10、jit11、jit12。RTC が遅い理由は「命令の取り込みが遅い」と読んでいるが、取り込みの速さそのものは測っていない 推定。冷えたプランを捨てた後、DERBY の heap の失敗は 1 レースで 28 → 11 回 実機、§16.1、別のレースどうし。

場所は得たが、DERBY のレースではまだ足りない。置く量を増やす前に、コードそのものを小さく・速くできないかを見る。

4. 飽和チェックをリスクで外す §18

知っているもの: feature flag とカナリア（まず全部で監視し、問題が無ければ段階的に外す）、サンプリングプロファイラ（毎回ではなく間を置いて見る）。V8 の投機的最適化（型を仮定して速いコードを作る）。

違うところ: 外した後に仮定が外れても deopt は無い。溢れた足し算は飽和せず折り返す。証明ではなく、観測した値の大きさで決めるリスクの判断（ユーザー決定）。

この章の問い: コードの 1/4 を占める ADD/SUB の飽和チェックを、どう安全寄りに外すか。

Shiki の ADD/SUB は溢れると INT32_MAX/MIN に張り付く（飽和）約束で、その検査は ADD 26 B のうち 18 B、生成コードの約 1/4 だった host、出荷プラン 45 本。静的に「溢れない」と証明できる地点は ADD 3/327 しかない。

  1. 共有チェッカーとログ枠（§18.1、38a55ef）。 各地点は IRAM の 1 つのチェッカーへ call0 し、直後の 4 B をその地点のログ枠にする。チェッカーは飽和させた上で |結果| を枠に OR する（地点ごとに「どれだけ大きな値を見たか」が残る）。
  2. 最初の判断（§18.2、12804a9）。 最初の 16 draw は全地点のログを取り、INT32_MAX まで 3 ビット以内なら常時チェック、6 ビット以上の余裕ならその場で確定（チェックなし）、その間は休止とサンプルへ。
  3. 休止とサンプル（§18.3、59f2517）。 外した地点は休止の後に 1 draw だけ測る。増えなければ休止を 2 倍に、128 draw（増えないサンプル 3 回）で確定。
  4. 確定したら作り直す（§18.5、7fe6d75）。 call0 を j に変えるだけでは速くならなかった 実機。プランの地点が全部確定したらコードを捨ててコンパイルし直し、確定した地点は素の add（8 B）にする。判断はプランの命令の FNV-1a をキーに 48 件覚え（JIT_FINAL_CACHE）、同じプランを登録し直しても最初から作り直した形でコンパイルする。冷えて捨てたコードの判断も残す（§18.4）。

結果（実機、12804a9、§18.6）

  • DERBY と MEGADEMO のほぼ全プランが 16 draw 目に確定して作り直された（地点はほとんど 22〜25 ビットの値）。常時チェック・戻した地点は 0 実測。
  • DERBY のエンジン時間: レース序盤 1.17〜1.20 → 0.95〜0.97 ms、WIDE 0.57 → 0.44、FIELD 0.68 → 0.56、CLOSE 0.58 → 0.46。15〜23% 速い 実測。MEGADEMO NEWS 0.81 → 0.75 ms。
  • チェッカーの正しさ: 実機でランダムなプログラム 800 本が一致。host は 2 万本 × 5 通り（インライン、チェッカー、パッチ、作り直し途中、作り直し後）。
  • 代償: 共有チェッカーへの call0 は届く範囲が限られ、RTC FAST に置かれたコードからは届かない（そこではインラインの検査で出していた）。

検査が消えたコードは、レジスタの使い方も自由になる。次はそれを使ってさらに短くする。

5. レジスタキャッシュ §20（c4d872d）

知っているもの: Java の JIT がフィールドをローカル変数（レジスタ）に置いたまま計算し、最後に 1 回だけ書き戻すこと。write-back キャッシュ。

違うところ: helper の呼び出し・ループの制御・ブロックの頭ではインタプリタや C がメモリの vm を読むので、そのたびに全部書き戻す（flush）。だから効くのは「算術だけが続く区間」に限られる。

この章の問い: 検査を外したコードを、メモリの読み書きを減らしてどこまで短くできるか。

JIT のコードは vm のレジスタをメモリに置いたまま読み書きする（どのブロックの頭でもインタプリタへ渡せるように、§11.1）。c4d872d は、SET・INPUT・ADD・SUB・NEG・MUL・SHIFT が続く区間だけ、値を a8〜a15 に持ったままにする: 読みはレジスタに残っていればロードしない、結果は区間の終わりまで書かない、区間内で上書きされた結果は書かない。共有チェッカーの call0 はレジスタが決まっているので、チェッカーの無いコード（4 章で作り直した後のコード）だけに使う。

  • 出荷プランの最終コード 26,171 → 24,461 B（−6.5%）host、同じコンパイラ。
  • 実機での速さへの効果は、この変更だけでは測れていない 未確認。c4d872d・c6119de の実機は JIT の場所が無くほぼインタプリタで走っており、効果が見えたのは区画を 56 KiB にした fb30211 から（§19.3）。そこでは区画の大きさも同時に変わっている。

shiki-jit.md には §20 の節がまだ無い（§19.3 が「レジスタ保持（§20）」と参照している）。この章の内容は c4d872d のコミットメッセージと ksn_shiki_jit.c の「sec.20: the register cache」のコメントによる。

コードは小さく速くなった。ところが同じ時期に「RTC にはコードを置かない」と決めたことで、DERBY のレースは逆に遅くなった。

6. RTC fast memory を断る §19、§19.1、§19.2

知っているもの: スケジューラが、ラベルの条件だけ満たした遅いノード（古い世代のインスタンス）にポッドを置いてしまうこと。「入る」と答えるが、実際に置くと使えない。

違うところ: ここの「遅いノード」は RTC fast memory 8 KB で、遅い上に共有チェッカーへの call0 が届かない。しかも他に移す先（DIRAM）がほぼ無い。

この章の問い: RTC を断ったら何が壊れ、その直しの後に何が本当の上限だと分かったか。

  • 断る（e3aa94c）。 JIT は RTC fast memory をコードに使わない。返ってきたら手放し、「場所がない」扱い（need64）で冷えたプランの場所を待つ。代わりに RTC は遅くても困らない常駐の仕事に起動時に渡す: input タスクのスタック 4 KB（最大使用 約 1,250 B 実機）。
  • 退行（c4d872d）。 スタックを置いた後の RTC の残り約 3.5 KB が、MALLOC_CAP_EXEC の最大の空きだった。入るかの判定 fits() はこれを数えて「入る」と答え、確保は RTC に当たって手放され、冷えたプランは一度も捨てられなかった。DERBY のレースで NOMEM 274、JIT のコード 4,704 B、発走 1.36〜1.46 ms（12804a9 は 0.95〜0.97）実機、§19.1。
  • 直し（c6119de）。 確保も判定も MALLOC_CAP_EXEC|MALLOC_CAP_DMA で行う。実行できて DMA も使えるのは DIRAM だけなので、RTC は候補にも空きの数にも入らない（コードで確認: JIT_EXEC_CAPS）。
  • それでも足りない（§19.2）。 NOMEM は 194 回続き、JIT のコードは 2,400 B。発走 1.41 ms 実機。足りないのは DIRAM そのものだった。 12804a9 が速かったのは、RTC に 6〜7 KB ほどコードを置けていたためと読む 推定（RTC の空き 8 KB と、今 DIRAM に収まる量の差。EXECMAP では測っていない）。スタックを移して空いた 4 KB はデータ専用の SRAM 側から出ていたらしく、JIT の場所にはならなかった 推定。

RTC を使わないなら、DIRAM の中の機械語の場所＝Shiki の区画の余りを増やすしかない。まず素直に区画を大きくしてみる。

7. 区画を大きくする実験 §19.3、§21.3

知っているもの: 1 つのテナントのクォータを上げると共有クラスタの他のテナントが詰まること。ECS/K8s の bin-packing で、空きの合計は足りているのに 1 台に収まる連続の空きが無いこと（断片化）。

違うところ: スケールアウトは無い。全体は約 334 KiB の DRAM 1 つで、「他のテナント」はアプリ自身の JS のゲスト（評価中は定常の約 2 倍のピークを使う）。

この章の問い: 区画を 8 KiB 増やせば DERBY は速くなるか、その代償は何か。

5dda893 は、JIT が有効ならどのアプリも区画を 8 KiB 大きく取るようにし、fb30211 で SHIKI_TURN に shk=使用/最大の空き/大きさ を足して測った。

  • DERBY は速くなった。 発走 1.41 → 0.52 ms、WIDE 2 1.24〜1.73 → 0.61〜0.93、JIT のコード 8,788〜10,528 B、NOMEM 5（HEAD ON から）実機、fb30211。
  • 区画の空きは細切れ。 レース中 shk=50164/3328/57344: 空き 7,180 B のうち一続きは 3,328 B。約 3.9 KB が JIT の入らない隙間にあった 実機。区画の中は ESP-IDF の TLSF（multi_heap）で管理していた。
  • 代償: DERBY の起動時のシステムの空き 45,576 → 37,308 B 実機。
  • MEGADEMO が起動できなくなった。 チャンク wake の解析で 12,138 B の確保が失敗（START_FAILED）実機。区画の 8 KiB が、ゲストの評価のピークの余裕を食った。全アプリに 8 KiB を足す変更は戻した（3407064）。
  • アプリごとの予算（§21.3、750ed21）。 その後、manifest の shiki_bytes で DERBY だけ 56 KiB にした（ユーザー決定）。MEGADEMO は 48 KiB のまま。これは 9 章の後で外した。

増やすと他を壊す。そこで「空きはあるのに入らない」側、つまり区画の中の詰め方を直す。

8. 区画の管理を作り直す §21、§21.1〜§21.5

知っているもの: 汎用の malloc（jemalloc など）をやめ、用途の決まった slab / arena にすること。寿命の長いものと短いものを別の場所に置くこと（世代別 GC の発想）。昔のプロセスのスタックとヒープのように、両端から向かい合って伸ばすこと。

違うところ: 持ち主のブロックは動かせない（C と JS の ArrayBuffer が番地を握っている）ので、詰め直し（compaction）は無い。動かせるのは、自分しか指さない JIT のコードだけ。

この章の問い: 区画の空きを一続きに保ち、JIT に回せる量を増やすには、どう管理すればよいか。

区画の持ち主は少なく（データ領域 16・リスト 8・プラン 32・フレームなど・JIT のコードと表）、大きさは確保の時に決まり、場面の切り替わりでまとめて解放される。TLSF の大きさの区分・ブロックの見出し・境界合わせの切り出しは要らない（ユーザー決定）。main/pocket/shiki_heap.c（host と実機で同じコード）は:

固定長の表（c12cddd）

  • 生きているブロックを 128 件の表に番地の順で持つ。開始と長さは 4 B 単位の 16 bit（SLOTS 128u、表は 512 B の .bss。コードで確認）。区画の中はブロックの中身だけ。
  • 持ち主は下から、JIT は上から（alloc_low / alloc_high）。出入りの多い JIT のコードが、持ち主の間に挟まらない。

空きは常にゼロ

  • 区画は取った時に 1 回だけゼロにし、解放したブロック（と縮めた後ろ）は返す時にゼロにする。calloc はゼロ埋めをしない。
  • host では確保のたびに中身がゼロかを確かめ、ゼロでなければ止める＝解放後の書き込みを host で捕まえる。実機ではこの検査はしない。
  • ブロックの先頭でない番地の free（二重解放など）は断る（実機は SHIKI_HEAP_REFUSED のログ）。

表にしただけでは足りなかった（§21.1、eb5c12c）

MEGADEMO は 48 KiB で全場面を回った（NEWS 0.71 ms）実機。しかし DERBY のレースは c6119de と同じく遅く（発走 1.33〜1.49 ms）、shk=43264/2104/49152: 空き約 6 KB のうち一続きは約 2.1 KB 実機。原因は JIT の 1 回のコンパイル（§17）: 見込みの長さのブロックを隙間の上端に取り、書いた後で後ろを返すので、返した分がそのブロックと上の JIT のブロックの間の穴になる。

e877784 で JIT に入るコードは 3.2〜4.9 → 4.5〜6.8 KB、WIDE・FIELD は 56 KiB の時と同じ速さに戻った（WIDE 0.42、FIELD 0.54 ms）実機、§21.2。発走と WIDE 2 は描くプランが多く 9〜10 KB 要り、48 KiB では入らない（持ち主 約 39.5 KB、空き 約 4.6 KB）。

さらに 2 つの調整

  • 返すのは足りる分だけ、残す余裕は 0（§21.4、c5530a7）。 持ち主の確保が失敗すると、hook は 1 回に 1 プランだけ、一番長く描かれていないプランのブロックを返し、区画は確保が通るまで繰り返す。以前は 1 回で全プランが返していた（MEGADEMO の TWIST で 12 プラン）。全部返す作りのための余裕 JIT_REGION_KEEP は 2 KB → 0（コードで確認）。実機での jitdrop の測定は §21.4 が「測ること」として残している 未確認。
  • 見込みの長さを実測に合わせる（§21.5、56949dc）。 JIT_GUESS(n) は 32n+64 → 24n+32。出荷している 45 プランのコードは 1 命令あたり最大 23.4 B（kasane.ci 58 命令 1,356 B）host、同じコンパイラ。見込みが大きすぎると、詰まった区画で一続きの空きが取れず 2 パスの道へ回っていた。超えるプランが出ても 2 パスで正しくコンパイルされ、test_scalar.py は出荷プランが見込みを超えたら落ちる。

詰め方は直った。残りは純粋な量の不足で、48 KiB の区画では持ち主が多すぎる。次は持ち主の側を減らす。

9. 作業領域を無くす §22、§22.1

知っているもの: 一時ファイルに書いてからコピーするのをやめ、宛先へ直接ストリームで書くこと。Kafka のコンシューマが、処理が成功してから offset を進める（失敗したら進めないので、途中の結果は無かったことになる）こと。

違うところ: 宛先は「描画中のフレーム」の末尾で、書ける本数の上限をエンジンが毎命令守る必要がある。JIT のコードも線分は C の helper で出すので、同じ検査を通る。

この章の問い: 区画の持ち主の中で、無くせる大きな塊はどれか。無くしたら DERBY は 48 KiB に戻れるか。

これまで 1 回の draw() は、1,024 本入る作業領域（workspace、10,246 B）へ書き、描画中のフレームの残りに入れば memcpy で写していた。「全部入るか、何も入らないか」にするための一時置き場だった（フレームの仕組みは パイプラインの §6）。

  • 直し（c4d7a6c、ユーザー決定）。 エンジンにその描画で出してよい線分の数 cap を持たせ、描画中のフレームの末尾へ直接書く。超えたら LIMIT で止まり、フレームの本数（count）を進めないので、書きかけはフレームに入らない。
  • 作業領域は、画像の面の帯のキャッシュ（240 × 8 × 2 = 3,840 B）だけになった（pocket_proc.c の image_band_buf、コードで確認）。画像の面を使わないアプリは取らない。
  • 効果: 画像の面を使うアプリ（DERBY・MEGADEMO）で 10,246 − 3,840 = 6,406 B、使わないアプリで 10,246 B が区画から空く 計算。描画ごとの memcpy も無くなる。

結果（実機、4786558、DERBY の区画 56 KiB、§22.1）

  • レース: WIDE 0.43 ms、FIELD 0.51〜0.54、WIDE 2 0.58〜0.94 実測。JIT のコード 8.8〜9.6 KB、失敗 0 実測。
  • 区画 shk=42480/13548/57344: 空きは一続きの 13.5 KB（TLSF の時は空き 7.2 KB のうち一続き 3.3 KB）実測。
  • 持ち主は 42,480 − 9,396（JIT）≒ 33.1 KB 計算（実測の差）。48 KiB なら JIT に約 16 KB 残る 計算。レースの JIT（約 10 KB）が入るので、DERBY の 56 KiB の指定を外し、既定の 48 KiB に戻した（94439f7。システムの空きが 8 KiB 戻る）。
  • 48 KiB に戻した DERBY の実機の測定はまだ無い 未確認。上の数字はすべて 56 KiB の区画でのもの。

持ち主を減らす手はもう 1 つ考えられた（フレームのリストを 1 本にする）。試して、戻した。
