# 観客を「模様の線」と「タイル」で描く — 手続き描画の新しいプリミティブの設計と host 試作

2026-10-01、ブランチ `vm/crowd-prim`（`vm/main` 6098c13 から）。**試作と設計の検証で、出荷しない（マージしない）。実機では何も測っていない。** 数値は「host 実測（数えた量）」と「実機の推定（数えた量 × 単価）」を分けて書く。見た目の良し悪しは書かない（画と GIF をユーザーが見て決める）。

ユーザーの要望: DERBY WATCH の観客は点（チェッカー、1 draw 523 µs・767 ステップ・66 点）で、規則正しい点にしか見えない。「線分が多いのが重いなら、それっぽいノイズで軽く描けないか」「画像を貼る／2〜3 コマのアニメ／上下に揺らせば客に見える」。

## 結論

- **2 案とも host で動いた。** 手続き描画の VM と帯ラスタライザ（[`ksn_procedural.c`](../../main/ui/kasane/ksn_procedural.c)）に、試作の命令を 2 つ足した: 模様の線 `LINE_PATTERN`（案 1。24 ビットの模様のほかに、ハッシュで作るノイズと、遠近の補正を持つ）と、タイルの矩形 `TILE`（案 2）。12 場面の画は、この C の実装そのものが描いた。
- **費用（実機の推定、12 場面の平均、今のチェッカー観客 = 1.00）: 模様線 0.51、ノイズ線 0.63、タイル 0.61。** 横見だけなら 0.44／0.60／0.47、首振りだけなら 0.58／0.66／0.75。draw（VM）の側は 865 → 約 210〜230 µs に減り、帯描画の側は 85 → 約 260〜360 µs に増える（画素を塗る量が、点 66 個から 1,400〜8,400 画素になるため）。**帯描画の画素の単価は実機で測っていない**（Xtensa の `-O2` の命令数に、今の線の実測 34 サイクル/画素から出した 1.1 サイクル/命令を掛けた）。合計が今の半分前後、という桁は確からしいが、±50% は動きうる。
- **「桁違いに安い」にはならない。** タイルは UI の画像ノード（240×30 で約 2.5〜3 ms）の約 1/6〜1/7（推定）だが、今の観客と比べると半分前後。理由は、今の観客が「点 66 個」という極端に少ない画素しか塗っていないこと。新しい 2 案は、**同じかそれ以下の費用で、塗る画素を 20〜100 倍にする**（観客席を人で埋められる）、と読むのが正確。
- **既存の出力は変わらない。** 新しい命令を使わないフレームは、バイト列も描画の経路も今と同じ（フレームの大きさ 10,246 B も同じ）。host の手続き描画の試験 13 本（ASan/UBSan と `-O2`）、QuickJS の adapter の試験、DERBY の host、IR の等価検査が通る。
- **推奨: 載せるなら案 2（タイル矩形）を主、案 1 のノイズ線を従。** タイルは「人に見える絵・コマのアニメ・首振りでの拡大」が 1 つの仕組みで出る。模様線は横見では最も安いが、首振りの近景で人が 1〜3 px のまま大きくならない。規模は、両方で約 10 人日、タイルだけで約 7〜8 人日、模様線だけで約 6 人日（下の表）。**実機で確かめるまで、数字も見た目（LCD の発色、30 fps での流れ方）も未確定。**

## 1. 今の流れ（LINE／PLOT が IR から画素になるまで）

```text
JS  draw(handle, [入力 8 個])
 │   pocket_proc.c draw_impl: 入力を float にして plan を始める
 ▼
VM  ksn_proc_begin: 命令 (12 B × ≤64) を VM にコピー → 検証 (valid_program)
    ksn_proc_step を 1 命令ずつ: レジスタ 16 本 (float32)、入力 8、ループ深さ 8
      SET/INPUT/ADD/MUL/SIN/REPEAT/END/REPEAT_REG/BREAK_IF_GT … レジスタと制御
      MOVE a,b                … ペンを (reg[a], reg[b]) へ（四捨五入、-480..720）
      PLOT a,b / LINE a,b     … 点、またはペンから (a,b) への線分を emit、ペンを移す
      PLOT/LINE_COLOR_REG     … 色を reg[dst] から
      CUBIC                   … r0..r7 の 4 点から、native のループで線分を n 本
    上限: 10,000 ステップ、1,024 エントリ、ラスタ 8,192 歩（線分の長い辺 + 1 の和）
 ▼
フレーム  ksn_proc_frame { count, raster_steps, ready, segments[≤1024] }
    segments[i] = { int16 x0,y0,x1,y1; uint16 color }  10 B、命令順
    draw ごとに scratch（1,024 本ぶん）へ出し、面の candidate へ memcpy で継ぎ足す
 ▼
commit → 表示  8 行の帯ごとに: 下地を塗る → ksn_proc_render_band(frame, pixels, y, 8)
    全エントリを順に見る: 縦の範囲が帯に掛からなければ次へ（実測 50 ns/エントリ×帯）
    掛かれば Bresenham。帯の途中から入るときは、主軸の歩数から誤差項を復元する
    （端点を切り直すと同点の丸めが変わるため）。画素は pixels[(y-帯)*240+x] = color
    実測: 帯に入る 1 回 0.35 µs、横の 1 画素 0.143 µs（34 サイクル）
```

登録時: `ksn_proc_analyze`（読み書きするレジスタ、効果、失敗の種類、基本ブロック、ループ）→ 隣り合う算術 2 命令の融合の印（`ksn_proc_plan.c`）。組み込みの plan は命令が flash の表にあり、heap には 40 + 4 × 引数 B だけ（[flash-plan.md](flash-plan.md)）。フレームを歩く側は、帯描画のほかに damage の計算（`pocket_proc.c` `frame_damage`、`ksn_procedural_surface.c`）がある。

費用を決めているのは、VM 側が「ステップ 0.45 µs・SIN +1 µs・emit 約 1 µs・draw の固定費 50〜110 µs」、帯側が「エントリの数（0.85 µs/本/フレーム）と帯ごとの固定費 17 µs」（[derby-background-cost.md](derby-background-cost.md) の実測）。観客 1 人を点や線で描くかぎり、人数ぶんのステップと emit が要る。**新しいプリミティブの狙いは、人数に比例する部分を VM から帯ラスタライザの画素ループへ移すこと**（1 画素 10〜25 命令、VM の 1 ステップは約 108 サイクル）。

## 2. 設計

### 2.1 フレームへの載せ方（両案に共通）: 2 エントリ、エントリの大きさは変えない

拡張プリミティブは**連続する 2 エントリ**を使う。1 つ目は形（x0 に、座標が届かない値の偏りを足して種類を示す: 模様線 +4096、タイル +8192）、2 つ目は 10 B のパラメータ。フレームのヘッダの、今は詰め物の 1 バイトを `ext`（拡張エントリがあるか）に使う。

- フレームの大きさは変わらない（`_Static_assert` で固定）。**`ext == 0` のフレームは、今と同じループで描く**（拡張用のループは別の関数）。拡張エントリの判定は、拡張のあるフレームでだけ払う。
- フレームを歩く側（damage、検証）は `ksn_proc_frame_next()`（形だけを偏りを外して返し、パラメータを飛ばし、ラスタ費用を返す）を使う。`ext == 0` なら今と同じ値。
- 模様線 1 本 = 20 B、タイル矩形 1 個 = 20 B。1 フレーム 1,024 エントリの上限は 512 個ぶん。

棄却した載せ方:

| 案 | 棄却の理由 |
| --- | --- |
| エントリを 10 → 12 B に広げ、スタイル表の番号を持たせる | 使わないアプリのフレームも 2 割増える（1,024 本で +2,048 B、面ごとに 2 枚 + scratch）。DERBY は面 1 の連続領域で一度詰まっている（[surface-segment-cap.md](surface-segment-cap.md)） |
| 拡張プリミティブを別の配列に置き、線分より先（下）に描く | 命令順に重ねる、という今の契約が崩れる（タイルの上に線、線の上にタイル、が書けない）。観客（背景）だけなら足りるが、一般化できない |
| パラメータ側のエントリを y = 32767 にして、今の縦範囲の判定で自然に飛ばす | 残りが 6 B で、パラメータ（10 B）が入らない |

### 2.2 案 1: 模様の線 `LINE_PATTERN`（op 15）

`LINE` と同じくペンから `(reg[a], reg[b])` へ。`dst` から 7 本のレジスタを読む: 模様、色 A、色 B（−1 で「なし」）、端の模様座標 u0・u1（セル単位）、両端の奥行きの重み w0・w1。`value` が周期 N。

- **模様の持ち方**: 24 ビットは float32 で正確（2^24 未満の整数）。線の k 番目の画素（ペン側が 0、主軸 1 歩で 1。帯の途中から入っても同じ画素になる）は、セル `floor(u0 + k·du) mod N` を読む（8.8 固定小数、`du = (u1 − u0) / 歩数` は emit のとき native で 1 回割る）。ビットが 1 なら色 A、0 なら色 B、色 B が無ければ描かない。「色 A／色 B／透明」の 3 値は、同じ線を 2 回引くか、下のノイズで出す（2 bit × 12 セルにする案は、周期が 12 に縮むので採らなかった）。
- **ノイズ（N = 0）**: 模様のレジスタを「密度 8 bit << 16 | 種 16 bit」と読む。セルのハッシュ（乗算 2 回）の下位 8 bit が密度未満なら描き、別の 1 bit で A／B を選ぶ。周期は 256 セル（2 px のセルなら 512 px で、画面より長い）。ユーザーの「それっぽいノイズ」に当たる。種が 1 違えば別の列になる（段ごとに種を 1 ずらす）。
- **位相**: u0・u1 を世界の座標（スタンドに沿った m ÷ セルの幅）から JS が渡すので、カメラが進むと模様がスタンドと一緒に流れる。1 px 未満の送りも 8.8 の端数で出る。
- **遠近（首振り）**: スタンドの 1 段は空間の直線なので、画面でも 1 本の直線になる。ただし模様の間隔は奥ほど詰まる。w0・w1（1/Z。符号が同じで大きさが違うとき）を渡すと、**VM が native で線を 2・4・8 本の弦に割り、割り目の u を遠近の正しい値にする**（`CUBIC` が native で線分を並べるのと同じ流儀。弦の中は線形）。IR の側は 1 命令のまま。横見は w0 = w1 で 1 本。
- **観客の plan「fan」**: 入力 8 個（両端の x・y、段の送り dy0・dy1、u0・u1）で、段ごとに 3 本（頭の線、体の線 2 本）。段の送り dy = −2.4 m/Z' がそのまま奥行きの重みになる。**横見と首振りが同じ plan 1 本**（今は `crowd` と `pk` の 2 本）。37〜39 命令、レジスタ 16 本。首振りでも Newton を VM で回さない（両端の投影は JS が計算する: 1 フレームに 2 点）。
- 解析: 読むレジスタは a・b と dst からの 7 本、効果は PEN | DRAW、失敗は座標・値域（`COLOR` と同じ扱い）・エントリ・ラスタ。融合の対象外。登録時に `value` が 0..24 の整数か、`dst ≤ 9` かを見る。
- 帯ラスタライザ: 水平の線（観客の段）は Bresenham を通らない専用ループ（クリップして左から右へ）。斜めは今の線と同じ歩き方に、画素番号 k を足しただけ（帯の途中から入るときの復元も同じ式）。

### 2.3 案 2: タイルの矩形 `TILE`（op 16）

ペンと `(reg[a], reg[b])` を対角とする矩形（端を含む）を、タイル表の `color` 番のタイルで埋める。`dst` から 5 本: ペンの角のテクセル (u0, v0)、反対の角の外側の縁のテクセル (u1, v1)、コマ。

- 左から i 列目は `floor(u_左 + i·du) mod 幅`、`du = (u_右 − u_左) / 列数`。行も同じ。最近傍。u・v とも巻く（横は並べるため、縦は段の繰り返し）。負の刻みは「周期 − 刻み」になるので、鏡映もそのまま動く。キー色の画素は描かない。
- **コマ**: レジスタの値の床を、コマ数で巻いたもの。整数を要求しないのは、**入力が 8 個しかない**ため: 首振りの plan は pk の 6 個（x、dx、z、dz、列数、1/Z'）と u の始点・1 区画ぶんのテクセル数で 8 個を使い切る。コマは「u の始点 + 4096 × コマ」と 1 個に詰め、plan が 1/4096 を掛けてコマのレジスタに入れる（u は幅 64 で巻くので 4096 の倍数は見えない）。
- **アニメ**: コマの切り替え（入力で選ぶ）。上下の揺れは v0 をずらす（今回の絵は、コマの中で人を 1 テクセル持ち上げている）。
- **タイルの置き場**: `ksn_proc_tile { const uint16_t *px; w, h, frames; key }` の const の表（実機では flash）。試作は RGB565 + キー色、64×24 テクセル（4 段ぶん。段数の少ない段階は下から使う）× 3 コマ × 3 段階 = **27,648 B**。出荷時は 8 bit パレット（半分）か 4 bit（1/4、約 6.9 KB）にできる（画素ループにパレット引きが 1 回増える）。表は、組み込みの plan の表と同じく、ビルド時にアプリの資源から作る想定。
- **横見**: 矩形 1 個（11 命令・11 ステップ）。**首振り**: `crowd_look` の ser() の区画（6 m）ごとに矩形 1 個。大きさは区画ごとの 1/Z'（pk と同じ Newton 3 段）で、区画の中は一定。41 命令、**レジスタ 16 本を使い切る**（定数を置くレジスタを、使い終えてから別の定数に書き換えている）。
- ラスタ費用: 面積の 1/4（`KSN_PROC_TILE_COST`）。上限 8,192 は Bresenham の歩数（実測 0.143 µs）の単位で、テクセルのコピーはその 1/4〜1/3 と見積もったため。**この換算は推定で、実機で測ってから決め直す値。**
- 解析・登録: 模様線と同じ（読むのは 5 本、`dst ≤ 11`）。タイル番号とコマは draw のとき（表を見て）確かめる。表から消えたタイルを指すフレームは、何も描かない。

### 2.4 IR・コンパイラ・flash の plan との整合

- 命令の符号化（12 B: op, dst, a, b, value, color）は変えない。flash の plan の表（`ksn_proc_rom_entry`、引数のパッチ先 A／VALUE／COLOR）もそのまま使える（タイル番号は COLOR、周期は VALUE のパッチで登録の引数にできる）。
- **`plan_js.mjs`／`kir.mjs` は未対応**（試作の plan は手書きの IR）。出荷には、組み込み関数 `pline(x, y, pattern, a, b, u0, u1, w0, w1, N)` と `tile(x, y, id, u0, v0, u1, v1, frame)`、連続するレジスタ 7 本・5 本の割り当て（`CUBIC` の r0..r7 固定の処理が近い）、文字形式の文字 2 つ、float32 の参照実行（`reference()`）への追加が要る。
- `pocket_proc.c` の `entry()` は op を値として通すので、API の形は変わらない。`capabilities` の `limits` に出す値も変わらない。

## 6. 実機に載せるときの規模とリスク

| 作業 | 模様線だけ | タイルだけ | 両方 |
| --- | ---: | ---: | ---: |
| native（VM・帯描画・解析・歩く側）を出荷の形に | 1.5 | 1.5 | 2 |
| コンパイラ（`kir`／`plan_js`／参照実行）、flash の plan の表 | 1.5 | 1.5 | 2 |
| タイルの表の生成器・CMake・絵 | — | 1.5〜2 | 1.5〜2 |
| host 試験（契約、QuickJS adapter、DERBY の全画素参照の更新） | 1 | 1 | 1.5 |
| DERBY の plan と JS（入力の計算、ゲスト heap の確認） | 1 | 1 | 1.5 |
| 実機（時間の A/B、heap、表示の確認） | 1 | 1 | 1.5 |
| **合計（人日）** | **約 6** | **約 7〜8** | **約 10** |

リスク:

1. **既存の線の速さが動く。** `ksn_proc_render_band` は 0x232 → 0x99e B になる。経路は同じでも、命令キャッシュの配置で同じカーネルが 15% 動く機体なので、今のアプリの帯描画を同一バイナリの A/B で測り直す必要がある（拡張のループを別の関数・別のファイルに出せば影響を小さくできる）。
2. **帯描画の単価が推定。** 画素ループの命令数は数えたが、flash 上のタイルの読み出し（キャッシュ）、分岐の当たり方は測っていない。合計が今を超える場面が出る可能性は、首振りのタイル（今の 0.75〜0.98）にある。
3. **float から 8.8 への丸めが host と実機で一致するか未確認。** `fmodf`・`lroundf`・`floorf` と除算を使う。この機体には「host では起きない」前例がある（文字列のイテレータ、評価中の `null`）。
4. **入力 8 個・レジスタ 16 本の縁。** 首振りのタイルの plan は両方を使い切り、コマを u に詰めている。観客以外の用途では足りなくなる（入力を 9 個以上にするのは VM の構造体と解析に波及する）。
5. **タイルのラスタ費用の換算（1/4）と上限 8,192。** 推定に基づく定数で、画面いっぱいの矩形（32,400 画素）が 1 draw に入る。帯の時間の上限として妥当かは実測で決める。
6. **ゲスト heap（余裕 約 1.3 KB）と評価のピーク（余裕 約 22.7 KB）。** JS 側の差し替えの大きさは見積もっていない。
7. `KASANE_BGCOST_TRACE` の集計（`pocket_proc_bgcost_take`）は拡張エントリを知らない（診断ビルドだけ）。

## 確信の低い点

- 費用の合計（4.3）は、帯の側が推定の単価に強く依存する。模様線・タイルの 1 画素が見積もりの 2 倍なら、比は 0.51／0.61 → 約 0.7／0.9 になる。
- 首振りの模様線は、弦の中が線形で、弦の継ぎ目は座標を丸めた点。カメラが動くと継ぎ目の位置が 1 px 揺れうる（GIF に出ている範囲のもの）。体の線は 1 px のままで、近景でも太らない。
- 首振りの 800 m は強制した場面（実際は横見になる位置）。大型画面は描いていない。
- タイルの絵・色・密度（座席の埋まる割合 39%／64%／88%）、ノイズの密度（35%／55%／74%）、コマの速さ（2 フレームごと）は仮の値。
- `run_pocket_proc_rom_qjs.py` が元から落ちている原因は調べていない。
