# 楕円コース・首振りカメラの描画を速くする: 代数・VM・PIE の設計の考察

2026-10-01、ブランチ `vm/oval-design`（`vm/main` d587bec から）。対象は `vm/oval` e574c73（段階 4b、楕円を弦に分けて `ser()` を呼ぶ形）。**設計の考察で、出荷するコード（`apps/`・`main/`）は変えていない。実機は使っていない。** 足したのは host の数値実験 2 本（[`tools/games/ovalcost/`](../../tools/games/ovalcost/)）だけ。

数値の種類は 4 つに分けて書く。**実測（実機）**: 既存の文書の値（[derby-pan-camera-cost.md](../apps/derby-pan-camera-cost.md) の単価、[derby-pan-memory.md](../apps/derby-pan-memory.md) §10・§11、`vm/oval` のコミットの記録）。**計数（host）**: 今回、`vm/oval` の本物の `pose()`・`pan()`・`ser()` を Node で回して数えた呼び出しの回数。**推定**: 計数 × 実機の単価、または式からの計算。**数値実験（host）**: float32 を模した誤差の計算。この文書で新しく実機で測ったものは無い。

## 1. 結論

1. **曲線の 93 ms の半分以上は `pose()` で、原因は弦の数ではなく `pose()` の書き方。** 楕円の `pose()` は 1 回の呼び出しで `sin`/`cos` を平均 11.9 回呼ぶ（計数。依頼の前提の「2 回ずつ」ではない）。曲線のフレームは `pose()` 157.5 回・三角関数 1,874 回で、単価を掛けると三角関数だけで 23.4 ms、`pose()` 全体で 42.3 ms（推定）。区間の始点の位置と `cos`/`sin` を表に持てば、曲線の上で 2 回、直線の上で 0 回になる（結果は全桁一致、数値実験）。**JS だけの小さな変更で、曲線 8.9 → 約 13 fps、直線コースの首振り 22.6 → 約 25.6 fps（推定）。**
2. **27 fps に届くのは、`ser()`（視野の切り出し・LOD・弦のループ）を native に下ろした場合だけ**（推定）。27 fps は JS のターン 18 ms 以下で、首振りに使えるのは約 7 ms。表引きを全部入れても曲線は 46 ms（15 fps）で、残りは「弦 9.6 本 × 系列 6 本 = 57.7 個の `ser()` の本体」という構造の費用（1 個 約 0.5 ms）。1 系列を 1 回の呼び出しにすると、首振りの JS は約 2.6 ms、ターンは 15〜17 ms（28〜29 fps、曲線も直線も）。JS のコードが減るので、ゲストの heap は約 3〜6 KB 戻る（推定）。
3. **除算の命令（DIV/RCP）と PIE は、単独では効かない。** VM の中の Newton は 1 フレーム約 800〜1,100 ステップ = 0.36〜0.49 ms（推定）で、DIV に替えても +0.3 fps。PIE（8 点並列の変換＋逆数表＋Newton）は 1 点 約 17 サイクルにできる見込みだが、1 フレームの点は 100〜300 個で、スカラーの FPU でも 0.05〜0.14 ms しかかからない。**遅いのは算術ではなく、JS と VM の命令の取り出し（dispatch）と JS の倍精度（ソフトウェア）。** 代数で仕事を消し、残りを native に下ろすのが先で、PIE は HEAVY の観客（点が千個の桁）と、フレームの固定費 19 ms（帯描画 9.5 ms・転送 7.4 ms）に向く。
4. 棄却した案: 有理 2 次ベジエ（回転の漸化式が同じ手数で等間隔・入力が少ない）、チェビシェフの漸化式（float32 で回転の漸化式の 20〜160 倍の誤差）、直線を大きな半径の弧として同じ plan で歩く（100 歩で 0.2〜0.3 px、1,000 歩で 1.2〜1.8 px）、外挿＋Newton 1 段・3 次の反復（Newton 2 段より悪いか同じ）、PIE の sincos カーネル（三角関数は表で消える）。

### 2.3 実機が host の比（1.9 倍）より悪い（3.7 倍）理由の仮説

実機の単価で組み立てると、曲線 ÷ 直線コースは (11.0 + 74.9 + 1.4) ÷ (11.0 + 12.7 + 1.5) = **3.5 倍**になり、実測の 3.7 倍にほぼ届く。つまり 3.7 倍は「実機の単価の世界では普通の値」で、説明が要るのは host の 1.9 倍のほう。

- **H1（主因と考える）: 倍精度がソフトウェア。** S3 の FPU は単精度だけで、JS の number（double）の演算は整数命令のライブラリになる。実機の単価は、加算 2.3 µs に対して除算 4.9・`sqrt` 7.4・`sin` 12.5 µs（2.1〜5.4 倍）。host は倍精度の FPU があり、`sin` も加算も「インタプリタの 1〜数命令」の差しかない。曲線のフレームは三角関数 1,874 回・除算と `sqrt` が多く、この比が効く。host の時間の比は、実機の時間の見積もりに使えない。
- **H2: 確保の回数。** 曲線の 1 フレームは、配列を約 320 個（`pose` の戻り値 158、`pj` 74、`ser` の `q` 58、draw の入力 28）作って捨てる。実機の 8 要素の配列は 22.7 µs（実測）で、host の malloc より相対的に高い。単価に入っているので H1 と重なる。QuickJS は参照カウントなので、循環が無い限り（host で 0 バイトを確認済み）周期的な GC は走らない。**GC が原因という証拠は無い。**
- **H3: 命令キャッシュ。** モデルが実測より 6% 低い分の候補。`sin` の単価 12.1 µs は詰めたループで測った値で、`pose()` の中では、インタプリタの本体・倍精度のライブラリ・`sin`/`cos` の経路が交互に走る。flash からの実行なので、キャッシュから押し出されると 1 回ごとに高くつく。**未確認**（確かめるには、実機で `pose()` を n 回呼ぶ測定器が要る）。

## 3. 代数的な再定式化（B）

記号: カメラの位置 E、視線の単位ベクトル d、その右の単位ベクトル d⊥、焦点距離 f。世界の点 P のカメラ座標は `Z = (P − E)·d`（奥行き）、`X = (P − E)·d⊥`。画面は `x = 120 + f·X/Z`、高さ h の点は `y = 28 + f·(6 − h)/Z`。`ser()` は f と `120·Z` を先に畳んだ `X''`・`Z'` を使うが、ここでは素の形で書く。

### 3.1 直線: Möbius 変換と逆数

弦の上の点 `P_i = P_0 + i·s·t`（t は弦の単位ベクトル）は、`X_i = X_0 + i·dX`、`Z_i = Z_0 + i·dZ` で、画面の x は i の 1 次分数変換（Möbius 変換）

```
x_i = 120 + f (X_0 + i dX) / (Z_0 + i dZ)
```

になる。直線の像は直線なので、柵の線は両端の 2 点で足りる（今の `prail` がそうしている）。等間隔の柱は 1 点ごとに逆数 `r_i = 1/Z_i` が 1 つ要る。

- **除算なしの厳密な漸化式は無い。** `x_{i+1}` は `x_i` の Möbius 変換で、どう書いても 1 点に 1 回の除算が残る（`r_{i+1} = r_i / (1 + dZ·r_i)`）。3 項の関係 `2/r_i = 1/r_{i−1} + 1/r_{i+1}` も除算を消さない。多項式で近似すると、それは Newton 法の変形になる。
- **Newton 法の誤差**: `r ← r(2 − Zr)` は、相対誤差 ε を ε² にする。前の点の逆数から始めると初期の誤差は奥行きの歩幅の比 `δ = |Z_i − Z_{i−1}| / Z_{i−1}`、k 回で `δ^(2^k)`。前の点の誤差 ε′ は次の初期値に `δ + ε′` として入るだけで、積もらない（自己修正）。画面の誤差は `|x − 120|·ε ≤ 160·ε`（視野の端、40 px の余白込み）。

| 方法（数値実験、[`oval_math.mjs`](../../tools/games/ovalcost/oval_math.mjs) F1） | VM のステップ | 誤差 | 0.1 px に収まる δ | 0.5 px に収まる δ |
| --- | ---: | --- | ---: | ---: |
| Newton 1 回 | 3 | δ² | 0.025 | 0.056 |
| Newton 2 回 | 6 | δ⁴ | 0.158 | 0.236 |
| Newton 3 回（今の plan、`ser()` は δ ≤ 0.3 に制限） | 9 | δ⁸ | 0.398 | 0.486 |
| 1 次の外挿 `2r_i − r_{i−1}` ＋ Newton 1 回 | 6 | 4δ⁴/(1−δ)² | 0.106 | 0.154 |
| 3 次の反復 `r(1 + e + e²)`、`e = 1 − Zr` | 5 | δ³ | 0.085 | 0.146 |
| 4 次の反復 `r(1 + e)(1 + e²)` | 6 | δ⁴ | 0.158 | 0.236 |

float32 で 200 本を歩いた結果（F1b、視野の中の点の最大誤差 px）: δ = 0.05 で 1 回 0.43・2 回 0.001、δ = 0.1 で 1 回 2.0・2 回 0.016・3 回 0.00002、δ = 0.2 で 2 回 0.26・3 回 0.0004、δ = 0.3 で 2 回 1.4・3 回 0.010。式のとおり。

  - **MUL と ADD だけの命令セットでは、Newton 法が最良。** 1 ステップあたりの次数は Newton が 2^(1/3) = 1.26、3 次の反復が 3^(1/5) = 1.25、4 次が 4^(1/6) = 1.26 で、外挿は Newton 2 回より悪い。形を変えても得は無い（derby-pan-memory.md §5 の「これ以上畳めない」を、次数で確かめた形）。
  - **1 回で足りる条件は δ ≤ 0.056**（0.5 px）。柱 5 m なら奥行き 90 m より奥、観客の列 3 m なら 54 m より奥だけ。手前では足りないので、「1 段にする」は採れない。**2 回なら δ ≤ 0.236 で 0.5 px。** 今の「3 回・δ ≤ 0.3」（誤差 0.01 px）から「2 回・δ ≤ 0.236」にすると 1 点 3 ステップ（約 16%）減るが、0.3 → 0.236 で LOD の段（draw）が増えうる。効果は VM の 0.1〜0.2 ms（推定）で、単独では勧めない。
  - **逆数 1 つを何に使い回すか**: 同じ点の x・上端の y・地面の y は 1 つの `r` で出る（今もそう）。芝の縞は内柵と外柵で奥行きが違うので 2 つ要る（今の `pt` は 2 系列の Newton）。曲線では、同じ角度の点が半径方向に並ぶ（§3.2）が、奥行きは半径ごとに違うので、逆数は系列ごとに要る。

### 3.2 円弧: 回転の漸化式

円弧の中心を C、半径を ρ、角度 θ の単位ベクトルを n(θ) とすると、点は `P(θ) = C + ρ·n(θ)`。カメラ座標は

```
Z(θ) = Z_C + U(θ),  X(θ) = X_C + V(θ),   U = ρ n(θ)·d,  V = ρ n(θ)·d⊥
```

で、(U, V) は半径 ρ のベクトルをカメラの向きで見たもの。角度を Δ 進めると、(U, V) は回転する:

```
U' = cosΔ · U + sinΔ · V
V' = cosΔ · V − sinΔ · U        （向きは曲がる方向で決まる）
```

- **VM では 6 ステップ**（MUL 4・ADD 2、`−sinΔ` を先に持つ）。SIN 命令 2 回（`sin` と `cos`、約 3.8 µs）より安い（2.7 µs）。同心の円弧（内柵・外柵・観客席）は、同じ θ で (U, V) が ρ に比例するので、**1 フレームに `cos`/`sin` を 1 組（始点の角度）計算すれば、全系列の初期値が掛け算で出る**。
- **チェビシェフの漸化式 `u_{n+1} = 2cosΔ·u_n − u_{n−1}` は採らない。** VM では 1 成分 3〜4 ステップで回転と同じ手数になり、float32 の誤差が大きい（下の表）。丸め誤差が `1/sinΔ` 倍で増えるため、歩幅が細かいほど悪い。

  - **直線を「とても大きい半径の弧」として同じ plan で歩く案は棄却。** 中心が遠いと `X_C + V` の桁落ちで、100 歩で 0.2〜0.3 px、長い直線で 1 px を超える。直線と円弧は別の歩き方にする。
- **円弧＋除算の通し**（数値実験 F5。カメラは内柵の 25 m 内側、曲線全体 75 歩を float32 で歩き、1 点ごとに float32 の除算。厳密な投影との差）: 3 つの半径・3 つの向き（f は 1,500 まで）で **x の最大誤差 0.0002〜0.0005 px、y は 0.00002〜0.00004 px**。
- **円弧の上では、Newton の「奥から手前へ」が保てない。** 円弧の奥行きは角度に対して山形で、歩く向きを選んでも半分は奥へ向かう。同じ実験で、視野の外（カメラの横、奥行き 2 m まで）の点も歩かせると、Newton 2 回・3 回は発散した（奥行きの比が 2 を超える歩がある）。視野の中だけを歩かせれば収束するが、それは JS の切り出しが厳密であることに頼る。**円弧を VM で歩かせるなら、除算の命令が要る**（§4）。

### 3.3 有理 2 次ベジエ（棄却）

円弧は、制御点 3 つと重み (1, cos α, 1)（α は弧の半角）の有理 2 次ベジエで厳密に書ける。透視投影では、制御点を投影し、重みに奥行きを掛ければよい（`w_i' = w_i·Z_i`）。数値実験 F3 で、弧 11.25°〜90° について「制御点を投影した有理ベジエ」と「円弧の点を投影したもの」の差は 10⁻¹³ px（倍精度の丸め）で、閉じていることを確かめた。画面の x は「t の 2 次式 ÷ t の 2 次式」になり、2 次式は前進差分（1 歩 ADD 2 回）で歩ける。

それでも採らない。理由は 3 つ。

- **等間隔にならない。** t を等分しても角度は等分されない。ずれは弧 11.25° で 4 mm（0.03 px）、22.5° で 3 cm（0.26 px）、45° で 26 cm（2.1 px）、90° で 2.1 m（17 px）（F3）。柱を世界で等間隔に置くには、弧を 11〜22° に刻む必要があり、「弦 7〜10 本を弧 1〜2 本に」の得が無くなる。
- **手数が同じ。** 分子 X・分母 Z・重み W の 2 次式で ADD 6 回、逆数 1 回、`W·r` の MUL 1 回。回転の漸化式（6 ステップ＋逆数）と同じで、回転のほうは等間隔が厳密。
- **入力が足りない。** 2 次式 3 本の係数で 9 個、本数・色・高さで 12 個。draw の入力は 8 個まで。回転の漸化式は `X_C, Z_C, U_0, V_0, cosΔ, sinΔ, 本数` の 7 個。

有理ベジエが向くのは、柱が無く曲線だけを少ない点で描く場合（屋根の線など）。今の VM には多項式の `CUBIC` しか無く、有理の標本化は命令の追加になる。柵の上端の線は「柱から柱への折れ線」（柱 5 m は弦 23.6 m より細かい）で足りるので、追加しない。

### 3.5 近似

- 三角関数の多項式・Padé・区分線形: M0 の後、曲線の `pose()` の三角関数は 1 回 2 個で、P5 を入れれば 1 フレーム 20 個前後になる。JS で多項式にすると、5 次の奇多項式で乗算 4・加算 2 = 約 14 µs で、`Math.sin` の 12.5 µs より遅い。**JS の中では近似の得は無い。**
- 観客の散らし: `pk` は点ごとに `sin(位相)` で x を 1.5 px ずらす。位相は列と行だけで決まり、時間で変わらない（瞬きは色）。64 個の表にすると誤差 0.07 px（F4）で、SIN（1.9 µs/点）が消える。VM には表引きが無いので、native に下ろすとき（§5・P5）の話。点の並びが今と 1 px 未満ずれる。
- LOD: 今の「歩幅を倍にする」は、px の間隔と Newton の収束（δ ≤ 0.3）の 2 つの条件を兼ねている。除算があれば後者が消え、LOD は見た目だけで決められる。

## 4. VM の命令の拡張（C）

### 4.1 このコアの除算の事実

- **Xtensa LX7 の FPU（単精度）には、1 命令の除算も平方根も無い。** あるのは種と補正の命令（`recip0.s`・`div0.s`・`divn.s`・`nexp01.s`・`maddn.s`・`rsqrt0.s`・`sqrt0.s`・`mkdadj.s`・`addexp.s`）で、この機体のツールチェーン（`xtensa-esp32s3-elf-as`、esp-15.2.0）がアセンブルすることを確かめた。**GCC はこれらを使わず、`a / b` を `call8 __divsf3`、`sqrtf` を `call8 sqrtf` に出す**（同じツールチェーンの `-O2 -S` で確認。[pie-simd.md](../perf/pie-simd.md) の記述と一致）。
- `__divsf3` は **55〜67 サイクル（0.23〜0.28 µs）**（実測。pie-simd.md、MCP の `measured_costs` の `divsf3_55_to_67_cycles`。スイッチ 1 個の 2 本焼き、1 回あたりの平均）。整数の除算は約 16 サイクル（同、逆算）。
- TRM の該当ページは引けなかった（MCP の `search_manual` は本文のコーパスが無く、`check_asm` はこのセッションの MCP からツールチェーンが見えなかった。上の確認はローカルのツールチェーンを直接使った）。

### 4.2 DIV（または RCP）を足すと

- 1 命令の費用（推定）: VM の 1 ステップ 0.45 µs（約 108 サイクル。ほとんどが取り出しと検査）＋ `__divsf3` 0.25 µs = **約 0.7 µs**。Newton 3 回（9 ステップ = 4.1 µs）の約 1/6、2 回（2.7 µs）の約 1/4。
- 1 フレームの効果（推定、`oval_cost.mjs`）: 首振りの plan のステップは、MID で直線 3,208 → 2,124、曲線 2,945 → 2,150、HEAVY で直線 4,412 → 3,013、曲線 3,914 → 2,885。**−0.36〜0.49 ms（MID）、−0.47〜0.63 ms（HEAVY）**（DIV の 0.25 µs を足す前。足すと −0.3〜0.55 ms）。fps は直線の首振りで +0.3 前後、曲線では +0.03。**依頼の見込み「Newton の 6〜9 ステップが 1 ステップに」は 1 点については正しいが、1 フレームの点が 100〜250 個なので、合計が小さい。**
- 間接の効果（こちらが本体）: (1) `1/z` を入力で渡さなくてよい（入力が 1 個空く）。(2) 「奥から手前へ」の順序と δ ≤ 0.3 の制限が要らなくなり、`ser()` の LOD のループが短くなる（draw が減る）。(3) **円弧を VM で歩けるようになる**（§3.2）。(4) HEAD ON の 1 頭ごとの JS の除算を plan に入れられる。
- RCP（`1/x`）でなく DIV（`a/b`）にする: 費用は同じで、`x = X/Z` が 1 ステップで済む。JS → IR のコンパイラ（`tools/kasane_ir/`）は `/` をそのまま落とせる。

## 5. PIE をどこに使うか（D）

### 5.1 何が遅いのかを先に分ける

| 層 | 1 演算の費用（実測） | 中身 |
| --- | --- | --- |
| JS（QuickJS） | 2.3〜12.5 µs（550〜3,000 サイクル） | バイトコードの取り出し＋倍精度のソフトウェア演算 |
| 手続き型 VM | 0.45 µs（約 108 サイクル） | 命令の取り出し・検査（算術は float32 で数サイクル） |
| native のスカラー（FPU） | 乗算・加算は数サイクル、除算 55〜67 サイクル | 算術そのもの |
| PIE | 1 命令 1 サイクル、8 レーン（1.3〜1.4 倍の実動作） | 整数のベクトル |

1 フレームに投影する点は 100〜300 個（MID。線分 170〜270 本）。1 点の算術は、回転 6・加算 2・除算 1・乗算 3 で、native のスカラーなら約 110 サイクル = 0.46 µs。**全部で 0.05〜0.14 ms。** PIE で 1 点 17 サイクルにしても、得は 0.04〜0.12 ms。JS の 75 ms、VM の 1.4 ms は、算術の量ではなく取り出しの回数で決まっている。**PIE は「算術の量」を減らす道具で、ここで足りないのは算術の速さではない。**

esp32s3-hw-mcp の調査も同じ向きの結論を出している。`notes/cardputer-adv-project/vm-pie-fit.md` は、QuickJS の VM の 4 領域（呼び出し・アロケータ・スタック・中止可能モデル）のどこにも PIE はそのまま刺さらない（dispatch は 1 opcode 9 命令で、うち 6 が制御フロー。データ並列が無い）としている。手続き型 VM も同じ形（`switch` と検査）で、命令を 1 つずつ実行する限り、PIE の入る所は無い。

### 5.2 PIE が向く所

- **(a) 点の投影をまとめる（native のウォーカーの中で、HEAVY の観客）**: esp32s3-hw-mcp の例が部品になる。8 頂点の変換（`ex07_transform3d`、実機で動作）、透視除算と逆数表（`proposed/ex13_perspective`、host の検証のみ・実機は未実行）、矩形内のレーンマスク（`ex13_clip_quad`）。
  - 流れ: 奥行きと横位置を Q 形式の int16 にする（奥行きは 1/160 m 単位で 16〜410 m が 2,560〜65,535）→ 逆数表 → Newton → `x = X·r` → 画面内のマスク。
  - **逆数表だけでは足りない**（数値実験 F6）。ex13 の形（256 個の表、`w >> 8` で引く）は相対誤差 4.8%（視野の端で 7.6 px）。1,024 個でも 1.2%（2.0 px）。**表＋ Newton 1 回（32 bit レーン）で 0.23%（0.36 px）、2 回で 0.006%（0.01 px）。** 16 bit レーンのままだと逆数の有効桁が 7〜11 bit しか無く、Newton を回しても精度が出ないので、逆数の所だけ 32 bit レーン（4 点/命令）にする。
  - 費用（推定。MCP の `pie_cost_estimate`、出所は pie-simd.md の実測の式「命令数 + 0.6 × ストア数」× 1.3〜1.4）: アフィン 8 点が 31 命令・ストア 2 で 32.2 サイクル（今の `block8`）。逆数（ex13 の 36 命令）＋ Newton 2 回（32 bit レーン、8 点で約 24 命令）＋積とマスク（約 19 命令）を足して **8 点で約 110 命令、1 点 約 14 サイクル、実動作で約 19 サイクル（0.08 µs）**。スカラー（0.46 µs）の約 6 倍速い。
  - 得: MID で 0.04〜0.12 ms、点が 1,000 個の桁になる HEAVY の観客で約 0.4 ms（推定）。**ウォーカー（P5）をスカラーで入れた後の、最後の一押し**の位置づけ。
- **(b) 型付き点列の「動的アフィン」**: 今の `affineQ14Points` は係数と色が登録時に固定で、毎フレーム登録し直すと 74 µs/点（実測）。係数（6 個）と色を draw の入力で渡せるようにすると、登録済みのタイルを 1 点 0.69 µs（実測、JS のターン）で好きな位置・縮尺に置ける。
  - native の変更: `pocket_proc.c` の `draw` で入力 6〜7 個を `KsnProcAffineQ14` に入れる（今は登録時の値を使う所）。`ksn_proc_points_pie.c` はそのまま使える（係数は呼び出しごとに `PieTerms` へ展開している）。点を線でつながず 1 点ずつ打つ指定（観客は点）も要る。規模は 1〜2 日（推定）。
  - 価値: 観客を「区画ごとのタイル」にすると、点の費用が 6.9 µs → 約 2.1 µs（帯描画込み、実測の比で 1/3.5）。ただし JS から区画ごとに draw を呼ぶと、区画 1 つに投影 42 µs ＋配列 23 µs ＋固定費 37 µs がかかり、今の plan より高くなりうる（derby-pan-camera-cost.md §4 の結論）。**ウォーカーの中から区画ごとに呼ぶ形（JS の呼び出しは系列に 1 回）で初めて生きる。** 観客の見た目（市松＋散らし＋瞬き）は、タイルの点を今の式で作れば保てるが、散らしの 1.5 px が奥行きで縮む点が今と違う。**見た目の判断はユーザー。**
- **(c) フレームの固定費 19 ms（帯描画 `rn` 9.5 ms、転送 `sd` 7.4 ms）**: 画素を扱う所で、PIE の本来の持ち場。27 fps の 37 ms のうち半分を占める。首振りのフレームの `rn` の内訳（背景の塗り・線分・文字）は、この考察では調べていない。**次に測る価値がある。**

### 5.3 PIE が向かない所と理由

- **sincos のカーネル（Q15 の多項式、8 要素）**: 1 ブロック約 16 命令・ストア 2、呼び出し込みで 74〜80 サイクル（推定、`pie_cost_estimate`）= 1 要素 約 10 サイクル。`Math.sin` の 3,000 サイクルの 300 倍速い。**しかし、呼ぶ所が無い。** 曲線の三角関数 1,874 回は、8 個ずつまとめて計算できる並びではなく（`pose()` の中に散っている）、M0 の表で 315 回に、P5 で約 20 回になる。JS から型付き配列でまとめて渡す形にすると、配列の書き込みが 1 要素 4.3 µs で、`sin` 12.5 µs の 1/3 しか消えない。
- **円弧の角度の列を 8 レーンで並列に回す**: レーン i が角度 `θ_0 + iΔ` から `8Δ` ずつ進む形で、1 回の回転が `VMULAS` 4・`SRCMB` 2 ほど。Q14 の int16 では 1 歩ごとに 2⁻¹⁴ の丸めが入り、半径 149 m で 9 mm（0.07 px）ずつ積もりうるので、8〜16 歩ごとの初期化が要る。float32 の回転（75 歩で 0.01 px）より悪く、得は (a) と同じ 0.1 ms の桁。**設計としては成り立つが、採る理由が無い。**
- **VM の命令列そのもの**: 上のとおり、取り出しが支配的。登録時コンパイラ（D3a）がループを丸ごと PIE のカーネルに置き換える形なら別だが、除算と float を含む柱のループは今の認識（積和）の外。
- **JS の倍精度**: PIE は整数。double の演算には使えない。
- 共通の制約（pie-simd.md、MCP の `measured_costs`）: PIE はコプロセッサ 3 で割り込みの中では使えない、128 bit のストアは 16 B 整列（違反は例外にならず 4 B 手前を壊す）、16 bit レーンのシフトが無い、`SRCMB` のシフト量は AR レジスタ、QR のロード直後の使用は 1 サイクル止まる（[proc-pie-stall-options.md](proc-pie-stall-options.md)）。

### 6.1 P5 の形: 「投影した道に沿って plan の本体を繰り返す」

`ser()` がしていること（道の上の等間隔の点を、カメラの視野で切り、px の間隔で間引き、1 点ごとに画面の x と縮尺を出して同じ絵を描く）を、Kasane の手続き面の 1 つの呼び出しにする。DERBY 専用の命令ではなく、「奥行きのある道」を描くアプリ一般の部品として切る（`CUBIC` が「曲線 1 本を native のループで標本化する」のと同じ考え方）。

- **道の登録**（コースが決まったとき 1 回）: 始点 `[x, z, 向き]` と区間の列 `[長さ, 曲率]`（8 区間まで）。native が区間の始点（M0 の表）を持つ。
- **1 フレームの呼び出し**（系列 1 本につき 1 回）: `H.walk(plan, path, [カメラ x, z, 向き x, 向き z, f, 奥の限界], [w, 間隔 s, 格子の原点, 最小の px 間隔, 2 つ目の w（芝の外柵。無ければ省く）, 色などの値 2 個])`。
- **native の中**: 区間ごとに、(1) 視野の 4 つの半平面で範囲を切る（直線は今の `lim()` と同じ 1 次不等式。円弧は `A + ρ·cos(θ − φ) ≥ 0` の形になるので `acosf` 1 回で区間が出る。カメラが円の内側なら視野の中の弧は 1 本、奥の限界で 2 本に割れることがある）、(2) px の間隔から歩幅（s の 2 の冪倍）を決める、(3) 点を歩く（直線は加算、円弧は回転の漸化式。区間ごとに表から初期化するので誤差は積もらない）、(4) 1 点ごとに `r = 1/Z`（`__divsf3`）、レジスタに `[画面 x, r, 格子の番号, …]` を入れて **plan の本体を 1 回実行**する。
- **plan は「1 点ぶんの絵」になる**: 柱は「前の柱の上端から線、地面へ線、上端へ戻る」（ペンは点の間で保たれるので、柵の線が柱をつなぐ折れ線になる。円弧の上でも弦に切らない）。観客は 1 列ぶんの点。芝は内柵と外柵の 2 点を受けて線 1 本。段の線は、前の点の `(x, r)` をレジスタに残して段ごとに線。Newton の命令（1 点 9〜21 ステップ）と `1/z` の入力が消え、本体は今の半分以下の命令数になる。
- **検証は 1 回、実行は点の数だけ**: 今の `draw` は呼ぶたびに plan を写して検証する（native 側 約 12 µs）。ウォーカーは 1 回検証し、点ごとに `pc` を本体の先頭に戻す。ステップの上限（1 draw 10,000）・線分の上限（1,024）・座標の範囲（−480〜720）は今のまま、点をまたいで数える。
- **費用（推定）**: JS は系列 1 本 約 75 µs（入力の配列 2 つと呼び出し）× 6 = 0.45 ms。首振りの残りの JS（`shot()`・`wide()`・大型画面・距離標・走者 8 頭の `pose`＋`pj`）は、P0 と固定の点の使い回しで約 2.2 ms。native は、切り出しが区間 × 系列で数十 µs、点が 150〜250 個 ×（投影 0.5 µs ＋本体 8〜12 ステップ 約 4〜5 µs）= 0.7〜1.3 ms。**首振りの合計 3.3〜3.9 ms、ターン 14.3〜16.9 ms（モデルの残差 0〜2 ms を足した幅）、27.6〜29.2 fps。** 曲線と直線で差が出ない（弦が無くなる）。
- **メモリ（推定）**: JS から `ser()`・`lim()`・`inr()`・`pan()` の弦の選び出し・`CH`/`VC`・`hl` の呼び出しが消える。段階 3 の首振りがゲストに足した 14.4 KB（実測）のうち、この部分は 3〜4 割と見て **−3〜−6 KB**。native は、道の表（8 区間 × 28 B）と枠の表で DIRAM +0.3 KB、コードは flash に 3〜5 KB。ネイティブの空き（27〜30 KB）には響かない。
- **既存への影響**: 既存の命令・`draw`・登録の経路は触らない（新しい入口を足すだけ）。確かめ方は §4.3 と同じ（他アプリの画素ハッシュの一致、`draw_us` が ±15% の中）。
- **リスク**: (1) float32 の切り出しの境目が、倍精度の JS と 1 点ずれうる（視野の外の余白の中なので見えないはずだが、host の oracle は「厳密な投影との差 0.5 px 以下」と「線分の数」で検査する形に変える）。(2) 円弧の切り出しで、範囲が 2 本に割れる場合・区間の継ぎ目・カメラの真横の点の扱い。host の試験で、カメラを全周に置いて「描いた点がすべて視野の中、落とした点がすべて視野の外か LOD」を総当たりする。(3) `acosf`・`sinf`・`cosf` は ROM/newlib の呼び出しで、1 フレーム数十回（数十 µs）。

### 6.2 勧める順序と合格基準

1. **P0（すぐ、JS だけ）**。合格: host の全 16 回 PASS で画素ハッシュが `vm/oval` と全行一致、`oval_cost.mjs` の三角関数が曲線で 1,874 → 約 315 回、実機で曲線の JS が 93 → 65 ms 以下・直線コースの首振りが 25 fps 以上、ゲストの最大が 140,000 B 以下。**外れたら（JS が 80 ms 以上のまま）、§2.2 のモデルが違うので、P5 の見積もりも信用しない。** P0 は、モデルを実機で確かめる測定でもある。
2. **P5（ウォーカー）**。host で試作 → 厳密な投影との差 0.5 px 以下・視野の総当たり → 実機。合格: 首振り WIDE が曲線・直線とも 27 fps 以上（MID・HEAVY）、`LOADSTALL` なし、ゲストの最大が今より 3 KB 以上減る、他アプリの画素ハッシュが不変。走者の脚を plan に移す（M4、−0.8 ms）を一緒に入れると余裕が増える。
3. **（任意）P6 と固定費**。HEAVY が 27 に届かないとき、観客をタイル＋PIE の動的アフィンに（見た目はユーザーの判断）。並行して、首振りのフレームの `rn` 9.5 ms の内訳を測る。

P2（DIV）は、P5 を入れるなら要らない（除算はウォーカーの中でする）。P5 を見送る場合だけ、P0 → P1 → P2 → P3 の順になり、曲線は 24〜25 fps で止まる（推定）。P8 は、どの段階でも、設定 1 つで戻せる逃げ道として残す。

**27 fps に最低限必要なもの**: P0 と P5。P0 だけでは曲線 13 fps、P0 + P1 で 15 fps、VM の命令を足して円弧を歩かせても 24〜25 fps。首振りの JS を 5 ms 以下にするには、系列ごとの切り出しを JS の外へ出すしかない（1 系列の切り出しを JS で書くと、直線 1 本で約 0.47 ms、6 系列で 2.8 ms が下限。段階 3 の直線が 25 fps で止まっていたのと同じ壁）。

## 8. ユーザーが判断すること

- **P5 の入口を firmware に足してよいか。** 「道に沿って plan を繰り返す」は DERBY 以外でも使える形にしたが、今これを使うのは DERBY だけ。flash 3〜5 KB と、新しい API の検証・文書（`limits` に出す上限: 区間 8、歩数、道の登録数）が要る。
- **P0 を先に実機で測るか**（勧める）。半日で、この文書のモデルが合っているかが分かる。
- 観客の点の並びが 1 px 未満動くこと（P5 で散らしを表にする場合）、タイルにする場合の見た目（P6）。
- P5 までのつなぎとして、曲線を横見の展開図にするか（P8）。

## 9. 確信の低い点

- **項ごとの内訳は推定。** 呼び出しの回数は数えたが、関数の本体の µs は、ソースを読んだ手計算に実機の単価（小さなループでの実測）を掛けたもの。合計は実測の 2 点（直線コース 25.0 ms、曲線 93 ms）に −0%・−6% で合うが、項の間の配分（`pose` の本体 120 µs、`ser` の本体 290 µs など）は ±30% は動きうる。`pose()` が最大の項であること（三角関数の回数は計数で、単価は実測）は、その幅でも変わらない。
- 首振りの外の 11.0 ms は、直線コースの実測からモデルを引いた残り。曲線でも同じと仮定した。
- 計数の台本は、8 頭を 1.5 m 間隔に並べ、先頭を等間隔に動かしたもの。実機の監督が選ぶ台・場面の割合とは違う。大型画面が映るフレームは入れていない。
- P5 の費用は、まだ無いコードの見積もり。native の 1 点の本体（8〜12 ステップ）は、plan を「1 点ぶんの絵」に書き直した試作をしていない。ゲストの −3〜−6 KB も、段階 3 の増分の割合からの見積もり。
- 実機が host の比より悪い理由（§2.3）は、H1 が単価から説明できるというだけで、H2・H3 を切り分ける測定はしていない。
- FPU の種の命令（`recip0.s` など）は、アセンブルできることだけを確かめた。サイクル数と、手書きの逆数が `__divsf3` より速いかは未確認（要らないと判断した）。TRM のページは引けていない。
- esp32s3-hw-mcp の `ex13` は「提案」で、実機では走っていない（その文書の記述）。§5.2 の PIE の費用は、その命令数と pie-simd.md の式からの推定で、Newton を 32 bit レーンで足す部分は命令数も見積もり。
- 楕円の直線区間の fps（14〜16）は、モデルだけの値。実測の記録が無い。
