版: v1 草案 3（2026-10-31）。草案 1（`5fc813d`）に SLOW の独立レビューの指摘（重大 4・中 7・軽微）と 16 ビット幅を v1 に入れる決定（ユーザー決定）を反映したのが草案 2（`ebc55cb`）、その再レビュー（重大 1・中 8・軽微）を反映したのが草案 3。状態: **差分の再レビュー前**（S1 の `transfer`、M-a の座標の範囲、M-g の窓の寿命）。経緯・理由・計測は [shiki.md](shiki.md)、この文書は**規範**だけを置く。旧 API（`pocket.kasane.procedural` の float の plan）は [js-to-ir.md](js-to-ir.md)・[flash-plan.md](flash-plan.md)・コードが仕様で、この文書の対象外（§11 の移行で消す）。

## 0. 読み方

- 「〜する」「〜しなければならない」は規範。「推奨」は規範ではない。「（未決）」の項目は v1 の確定前に決める。
- 数値の上限は、コードで強制し `limits`（§9.1）に出す値だけを書く。性能の数値は書かない。
- 用語: **式**（1 本のプログラム）、**handle**（登録した式）、**Shiki エンジン**（式を実行する native。QuickJS の VM とは別物）、**データ領域**（式が読み書きする型付きの配列）、**Q 形式**（固定小数の小数部のビット数。`Qf`。例 Q16 は 1/65,536 刻み）、**参照実装**（§10.1）。
- 演算は数学の式で定義する（C の符号付きシフトなど、実装定義の動きに頼らない）。`⌊x⌋` は負の無限大方向への切り捨て、`sat32(x) = min(max(x, −2^31), 2^31−1)`、`sat16(x) = min(max(x, −2^15), 2^15−1)`。

## 1. 範囲と実行モデル

1. Shiki は、JS アプリが登録した式を native が実行し、Kasane の手続き面のフレームへ線分を出す仕組みである。式の種類は **線の式**（§3〜§6）と **格子の式**（§7）。
2. 描画タスクは 1 つで、式は JS の呼び出し（`draw`・`run`）の中で**同期に**実行される。Shiki エンジンがデータ領域を読み書きするのは、その呼び出しの間だけである。
3. 式の実行は有界でなければならない。上限（§9.1）を超える実行は `LIMIT` で止まる。
4. **決定性**: 同じ式・引数・入力・データ領域の中身からは、どの実装経路（スカラーの C、PIE、参照実装）でも、ビット単位で同じ状態・線分・データ領域への書き込みを生まなければならない（§10）。

## 2. 数の型と演算

### 2.1 型

| 型 | 中身 | 用途 |
| --- | --- | --- |
| `fixed` | 32 ビットの符号付き整数。値は `raw / 2^f`（`f` はその値の Q 形式、0〜30） | レジスタ、入力、引数、座標、計算 |
| `int` | `fixed` の `f = 0` | 回数、添字、色 |
| `half` | 16 ビット幅の値（−2^15〜2^15−1）。Q 形式を持つ | PIE に下ろす計算（§2.3、§8.4） |
| データ領域の要素 | `i16`・`u16`・`i32`。領域ごとに Q 形式を持つ（§5.1） | 表、点、状態 |

- float は Shiki のどこにも現れない。
- **Q 形式は命令が持たない。** 書き手が宣言し（§8.3）、変換器が掛け算のシフト量と `SHIFT` に畳み込む。Shiki エンジンは整数の命令だけを実行する。
- `half` も 32 ビットのレジスタに入るが、`.H` の命令（§4.3）だけが `half` を作り、その結果は必ず −2^15〜2^15−1 に入る。
- 色は `int`（0〜65,535）。

### 2.2 32 ビットの演算

| 演算 | 定義 |
| --- | --- |
| `ADD`・`SUB`・`NEG` | `sat32(a + b)`・`sat32(a − b)`・`sat32(−a)` |
| `MUL a, b, s`（0 ≤ s ≤ 62） | `sat32(⌊a · b / 2^s⌋)`（`a · b` は正確な 64 ビットの積） |
| `SHIFT a, k`（−31 ≤ k ≤ 31） | `k ≥ 0` なら `sat32(a · 2^k)`、`k < 0` なら `⌊a / 2^−k⌋` |
| 比較 | 符号付き整数の比較 |
| 正弦 | §4.4 |

- 0 での割り算は無い（割り算は変換器が定数の逆数の掛け算か、2 の冪ならシフトへ下ろす、§8.3）。非有限の値も無い。
- スカラーの C は、64 ビットの積を `MULL`・`MULSH` と漏斗シフトで作れる（Xtensa、アセンブルできることだけをレビューで確認。サイクル数は未計測）。

### 2.3 16 ビット幅の演算（`.H`、PIE と同じ意味論）

| 演算 | 定義 | 対応する PIE（TRM v1.8） |
| --- | --- | --- |
| 被演算子 | 32 ビットのレジスタの値を、まず `sat16` する | |
| `ADD.H`・`SUB.H` | `sat16(a + b)`・`sat16(a − b)` | `EE.VADDS.S16`・`EE.VSUBS.S16`（飽和） |
| `MUL.H a, b, s`（0 ≤ s ≤ 31） | `sat16(⌊a · b / 2^s⌋)`（`a · b` は 32 ビットに収まる） | `EE.VMULAS.S16.QACC`（p.215）で積を蓄積し、`EE.SRCMB.S16.QACC`（p.130）でシフトと 16 ビットの飽和 |
| `SHIFT.H a, k`（−15 ≤ k ≤ 14） | `k ≥ 0` なら `sat16(a · 2^k)`、`k < 0` なら `⌊a / 2^−k⌋` | 定数との `MUL.H` で表す（16 ビットのレーンのシフト命令は無い、[pie-simd.md](../perf/pie-simd.md)） |

- `EE.VMUL.S16`（p.198）は積の下位 16 ビットを取る（wrap）ので、`MUL.H` には使わない。
- `QACC`＋`SRCMB` の丸めが `⌊⌋` と飽和で上の定義どおりであることは、レビューが TRM で確かめた。**実機での確認は §10.2 の要件**。
- `MUL.H` のシフト量 `s` は、PIE では `EE.SRCMB.S16.QACC` のアドレスレジスタ（`as[5:0]`、TRM p.130）で渡す。命令ごとに違う `s` を使ってよい（`SAR` を使うのは `EE.VMUL.S16` で、`MUL.H` には使わない）。
- `EE.SRCMB.S16.QACC` はシフトした値を `QACC` にも書き戻すので、PIE の実装は `MUL.H` ごとに `QACC` を 0 にする（`EE.ZERO.QACC`）。

### 2.4 JS との境目

- JS の数 `v`（double）を Q 形式 `f` の `fixed` へ変えるときは、`x = min(max(v · 2^f, −2^31), 2^31−1)` を double で求め、`sign(x) · ⌊|x| + 0.5⌋`（半分は 0 から遠い方）とする。有限でない `v` は `INVALID_ARGUMENT`。
- 入力・引数の Q 形式は式が宣言する（§3）。JS は実数のまま渡し、変換は native が行う。`pocket.derby.ser()` のような native の呼び出し元も、実数を渡して同じ変換を通す。
- データ領域は、JS が要素の型のまま（`Int16Array` などの生の整数で）書く。Q 形式への換算は JS の責任。

組み込みの式（ビルド時の表）も、JS が渡す式（§9.4）も、**同じバイト列**で表す。リトルエンディアン。

| 部分 | 大きさ | 中身 |
| --- | --- | --- |
| ヘッダ | 12 B | `'SKI1'`（4 B）、版 `1`、種類 `0`（線の式）、命令の数 `n`（1〜64）、入力の数（0〜8）、引数の数（0〜8）、領域の数（0〜4）、当てはめの数 `p`（0〜32）、予約 0 |
| 入力の表 | 入力の数 × 1 B | 各入力の Q 形式（0〜30） |
| 引数の表 | 引数の数 × 1 B | 各引数の Q 形式（0〜30） |
| 領域の表 | 領域の数 × 4 B | 要素の型（0 `i16`、1 `u16`、2 `i32`）、Q 形式、1 レコードの要素の数 `k`（1〜8）、旗（bit0: 書く） |

- 引数は、登録時に当てはめの表どおり命令の `imm` か `aux` に書き込む（引数の Q 形式で変換した値）。**`op`・`dst`・`a`・`b` には当てはめない。** `aux` と、`int` を取る `imm`（`REPEAT` の回数、`SHIFT`・`SHIFT.H`・`FETCH`・`PUT`・`LOOKUP` の `k`、`LINE_PATTERN` の周期）へ当てはめる引数は Q0 でなければならない（§6.1）。
- バイト列の長さは、ヘッダから計算した大きさにちょうど等しくなければならない。

## 4. 線の式の命令

### 4.1 状態

- レジスタ `r0`〜`r15`（32 ビット）。draw の始めにすべて 0。
- ペン（座標と有効か）。draw の始めに無効。
- ループの段（8 段まで）。`EACH` も同じ 8 段に数える。各段の残りの回数は 0〜65,535。
- ステップ: 実行した命令 1 つを 1 ステップと数える（`REPEAT`・`EACH` は入るとき 1 回、`END` は 1 周ごとに 1 回）。
- フレームへ出した線分。

### 4.2 命令の形式

1 命令 12 バイト: `op`（8）、`dst`・`a`・`b`（各 8）、`imm`（符号付き 32）、`aux`（16）、予約 2 バイト（0）。

### 4.3 命令

`op` の番号は v1 で固定する。表に無い番号は予約で、登録で拒否する。0〜15 は旧 API の `ksn_proc_op` と同じ並び（意味は固定小数に変わる）。

| `op` | 命令 | 動き | 実行時の失敗 |
| ---: | --- | --- | --- |
| 0 | `SET dst, imm` | `r[dst] = imm` | |
| 1 | `INPUT dst, a` | `r[dst] = 入力[a]`（§2.4 で変換済み。draw が渡さなかった入力は 0） | |
| 2 | `ADD dst, a, b` | §2.2 | |
| 3 | `MUL dst, a, b, aux=s` | §2.2 | |
| 4 | `SIN dst, a` | §4.4 | |
| 5 | `REPEAT imm` | `imm` 回（1〜255）回すループ | |
| 6 | `END` | ループの終わり | |
| 7 | `MOVE a, b` | ペンを `(r[a], r[b])` に置く | 座標が範囲外なら `INVALID` |
| 8 | `PLOT a, b, aux=色` | 1 点を出し、ペンを置く | 座標が範囲外なら `INVALID`、上限なら `LIMIT` |
| 9 | `LINE a, b, aux=色` | ペンが有効ならペンから線分を出し、無効なら移動だけ。ペンを置く | 同上 |
| 10 | `REPEAT_REG a` | `r[a]` 回（`int`、0〜255）回すループ | `r[a]` が 0〜255 の外なら `INVALID` |
| 11 | `BREAK_IF_GT a, b` | `r[a] > r[b]` なら、いちばん内側のループ（`EACH` を含む）を抜ける | |
| 12 | `PLOT_C a, b, dst` | `PLOT` の色を `r[dst]` から | `r[dst]` が 0〜65,535 の外、座標、上限 |
| 13 | `LINE_C a, b, dst` | `LINE` の色を `r[dst]` から | 同上 |
| 14 | `CUBIC dst, a=分割数, aux=色` | §4.6 | 座標・上限 |
| 15 | `LINE_PATTERN dst, a, b, imm=周期, aux=色 A` | §4.7 | 座標・上限 |
| 16 | `SUB dst, a, b` | §2.2 | |
| 17 | `NEG dst, a` | §2.2 | |
| 18 | `SHIFT dst, a, imm=k` | §2.2 | |
| 19 | `ADD.H dst, a, b` | §2.3 | |
| 20 | `SUB.H dst, a, b` | §2.3 | |
| 21 | `MUL.H dst, a, b, aux=s` | §2.3 | |
| 22 | `SHIFT.H dst, a, imm=k` | §2.3 | |
| 23 | `EACH a` | §5.2 | |
| 24 | `FETCH dst, a, b, aux=m, imm=k` | §5.2 | |
| 25 | `PUT dst, a, b, aux=m, imm=k` | §5.2 | |
| 26 | `LOOKUP dst, a, b, aux=g, imm=k` | §5.2 | |

使わない欄は 0 でなければならない（登録で検査する）。

### 4.4 正弦

`SIN dst, a`: `r[a]` を Q16 の**回転数**（1 周 = 65,536）とし、その下位 16 ビット `p`（0〜65,535）を位相に使う。

1. `quad = ⌊p / 2^14⌋`、`w = p mod 2^14`。`quad` が 1 か 3 なら `w = 2^14 − w`。
2. `w = 2^14` なら `v = T[256]`。そうでなければ `i = ⌊w / 64⌋`、`t = w mod 64`、`v = T[i] + ⌊(T[i+1] − T[i]) · t / 64⌋`。
3. `quad` が 2 か 3 なら `v = −v`。`r[dst] = v`（Q16）。

`T` は 257 個の `i32` の組み込み表 `T[k] = round(sin(k·π/512) · 65536)`（k = 0〜256、`T[256] = 65536`）。表と手順は v1 の一部で、変えるには版を上げる。ラジアンからの換算は変換器が入れる（§8.3）。

精度の記録（[shiki.md](shiki.md) §5.5、host）: 位相の刻みは 1/65,536 周（約 9.6e-5 rad）。`sin(u * 137 + t)` のように sin の結果を大きく増幅して乱数代わりにする式では、この刻みが増幅される（DERBY の `dust` で最大 0.6 px、ランダムな入力で 2 px）。

### 4.5 座標

- 描画の命令は、レジスタを **Q16** の画素の座標として読み、`⌊raw / 65536⌋` を画素にする。
- `@shiki` の変換器は、描画に渡すすべての座標に 0.5（`raw` で 32,768）を足す。結果は最も近い画素で、ちょうど半分のときは**正の方向**に丸まる（旧 API の `lroundf` とは、負のちょうど半分だけ違う）。
- 範囲の判定は、エンジンが受け取った値で行う: `⌊raw / 65536⌋` が −480〜720 の外なら `INVALID`（変換器が足した 0.5 込み）。

### 4.6 `CUBIC`、4.7 `LINE_PATTERN`

旧 API と同じ形の出力（`CUBIC` は `a` 本の線分、`LINE_PATTERN` は 2 エントリ、[crowd-primitives-design.md](crowd-primitives-design.md)）を作る。**整数の手順は（未決）**で、参照実装と一緒に決める。分割数は 1〜255、周期は 1〜24。

## 5. データ領域

### 5.1 宣言と結び付け

- データ領域は Shiki のヒープ（§9.2）に、16 バイトの境界で確保する。JS には型付き配列の窓として渡す（§9.3）。
- 1 つの領域は、要素の型、Q 形式（0〜30）、1 レコードの要素の数 `k`（1〜8）、要素の数 `n`（`k` の倍数、レコードの数 `n / k` は 0〜65,535）を持つ。**大きさは確保したときに決まり、変わらない。**
- **結び付けは登録時に固定する。** 式の領域の表（§3）と渡した領域は、型・Q 形式・`k` がすべて一致しなければならない（不一致は `INVALID_ARGUMENT`）。- 1 つの領域を、複数の handle に結び付けてよい。
- `LOOKUP` に使う領域は、要素が 1 個以上でなければならない（登録で検査する）。

### 5.2 命令

| 命令 | 動き |
| --- | --- |
| `EACH a` | 領域 `a` のレコードの数だけ回すループ。カーソルは 0 から始まり、`END` で 1 進む。レコードが 0 個なら本体を飛ばす |
| `FETCH dst, a, b=位置, aux=個数 m, imm=k` | 領域 `a` を回している**いちばん内側の `EACH a`** のカーソルのレコードの、`b` 番目から `m` 個を `r[dst..dst+m−1]` へ。各要素 `e` は `SHIFT(e, k)`（§2.2）して Q 形式を合わせる。違う領域の `EACH` を入れ子にすれば、外側の領域のレコードも読める |
| `PUT dst, a, b=位置, aux=個数 m, imm=k` | 逆向き。`r[dst..dst+m−1]` を `SHIFT(·, k)` してから、要素の型の範囲（`i16`: −2^15〜2^15−1、`u16`: 0〜65,535、`i32`: そのまま）へ飽和して書く |
| `LOOKUP dst, a, b, aux=g, imm=k` | `i = min(max(⌊r[b] / 2^g⌋, 0), n − 1)` の要素を `SHIFT(·, k)` して `r[dst]` へ。**範囲外は端に寄せる**（ユーザー決定）。`k = 1` の領域だけ |

### 5.3 書き込みの規則（`PUT`）

1. 書き込みは命令の順に即座に見える。同じ draw の後の `FETCH`・`LOOKUP` も、同じフレームの後の draw も、書いた値を読む。
2. JS は、`draw` が戻った後に書いた値を読める（同じメモリの窓）。`draw` の途中で JS は動かない。
3. draw が失敗しても（`INVALID`・`LIMIT`）、それまでの書き込みは戻らない。フレームの線分は捨てられる。
4. v1 の書き込みは、`EACH` のカーソルのレコードの中だけ。

## 6. 登録時の検査と実行時の検査

### 6.1 登録時（1 つでも外れれば `INVALID_ARGUMENT`、handle を作らない）

| 対象 | 範囲 |
| --- | --- |
| ヘッダ・表 | §3 の値の範囲、当てはめの番号の昇順、予約が 0 |
| `op` | 既知の命令。予約の 2 バイトが 0 |
| レジスタ（`dst`・`a`・`b` がレジスタのとき） | 0〜15。複数を使う命令（`CUBIC` 8、`LINE_PATTERN` 6、`FETCH`・`PUT` `m`）は範囲全体が 0〜15 |
| `INPUT` の `a` | 宣言した入力の数未満 |
| `MUL` の `s`／`MUL.H` の `s` | 0〜62／0〜31 |
| `SHIFT` の `k`／`SHIFT.H` の `k`／`FETCH`・`PUT`・`LOOKUP` の `k` | −31〜31／−15〜14／−31〜31 |
| `LOOKUP` の `g` | 0〜31 |
| `REPEAT` の回数、`CUBIC` の分割数 | 1〜255 |
| `LINE_PATTERN` の周期 | 1〜24 |
| `EACH`・`FETCH`・`PUT`・`LOOKUP` の領域番号 | 宣言した領域の数未満。`LOOKUP` は `k = 1` の領域。`PUT` は書く宣言の領域 |
| `FETCH`・`PUT` | 同じ領域の `EACH` の中。`b + m ≤ k`、`m ≥ 1` |
| ループ | `REPEAT`／`REPEAT_REG`／`EACH` と `END` の対応、入れ子 8 段以内、`BREAK_IF_GT` はループの中 |
| 当てはめ | 表は（命令の番号, 欄）の昇順で、同じ組は 1 回だけ。`aux` と `int` を取る `imm` へ当てはめる引数は Q0。引数を当てはめた**後の**命令が上のすべてを満たす |
| バイト列 | 長さがヘッダから計算した大きさにちょうど等しい。使わない欄が 0 |
| 結び付け | §5.1 の型・Q 形式・`k` の一致。`LOOKUP` の領域は要素 1 個以上 |

登録後は、命令・引数・領域の結び付けが変わらない。実装はこれを構造で保証しなければならない（組み込みの式は const の表、JS の式は登録時に Shiki のヒープへ写し、JS の配列は以後読まない）。**draw のたびにはこの表の検査をしない。**

### 6.2 実行時（値によって決まるもの）

`REPEAT_REG` の回数、`PLOT_C`・`LINE_C` の色、座標の範囲、ステップ・線分・ラスタの上限。§4.3 の「実行時の失敗」の列がすべて。

## 7. 格子の式

v1 では、今の `pocket.kasane.grid` の int16 の IR（`CONST`・`LOAD`・`ADD`・`MUL`・`MIN`、[grid-js-notation.md](grid-js-notation.md)）を、意味を変えずに `pocket.kasane.shiki.grid` へ移す。線の式との番地の規則の統一は v2。

## 8. `@shiki` の記法

### 8.1 形

[js-to-ir.md](js-to-ir.md) §5 の `@plan` の部分集合（R1〜R6）を引き継ぎ、印を `@shiki` にする。

```js
/** @shiki prail inputs: x, dx, z, dz, posts, r, colour, top
 *  @q z=24, dz=24, pz=24
 *  @half vx, vy
 *  @data seats: i16 q8 record 3 write */
function prail() { ... }
```

### 8.2 足す書き方

| 書き方 | 命令 |
| --- | --- |
| `for (const [a, b, c] of seats)` | `EACH` ＋ `FETCH` |
| `seats.put(a, b, c)`（`for...of` の中で） | `PUT` |
| `table[i]` | `LOOKUP` |
| `a - b`、`-a` | `SUB`、`NEG` |

### 8.3 Q 形式（書き手が宣言する。値の範囲は推定しない）

1. **名前の Q 形式**: `@q 名前=ビット数` で宣言した名前はその値。次の名前は `int`（Q0）で、宣言と食い違えばエラー: `for` のループ変数、`REPEAT` の回数に使った名前、色と整数の描画引数（`line`・`plot` の色、`cubic` の分割数と色、`linePattern` の模様・色・周期）に使った名前、そして**それらと名前どうしの単純な代入（`a = b`、`let a = b`）でつながった名前すべて**（`const C0 = 0xffd9; let cu = C0; line(x, y, cu)` の `C0`）。それ以外は Q16。
2. **式の Q 形式は、受け取る側が決め、部分式もその Q 形式で直接計算する**: 代入なら代入先、入力・引数の宣言ならその値、描画の座標なら Q16、回数・色なら Q0。`SHIFT` で Q 形式を揃えるのは**名前だけ**（名前の宣言と、受け取る側の Q 形式が違うとき）。
3. `+`・`−`・単項 `−` の項は、規則 2 のとおり結果の Q 形式で計算する（項が名前なら `SHIFT`、式ならその Q 形式で直接）。
4. `a * b` の各項の Q 形式: 名前は宣言、**数の定数は int32 に入る最大の Q 形式（30 以下）**、それ以外の式は Q16 で計算する。`MUL` のシフト量は `s = qa + qb − q結果`。`s < 0` なら `MUL s=0` の後に `SHIFT −s` を足す。
5. 2 の冪の定数での割り算は、項が掛け算なら `s` に足し、そうでなければ `SHIFT` で右へずらす。負の定数なら `NEG` を足す。それ以外の定数での割り算は、`1/c` の掛け算として規則 4 に従う。
6. 数の定数は、規則 4 の場合を除き、使われる場所の Q 形式で §2.4 と同じ丸めをする。
7. 比較 `a > b` は、両辺の「自然な Q 形式」（名前は宣言、数の定数は相手の辺に従う、それ以外は Q16）の大きい方を受け取る側の Q 形式として、規則 2 で両辺を計算する（式の辺はその Q 形式で直接計算する）。
8. `sin(e)` は、`e` を Q16 のラジアンで計算し、`MUL` で `TURN = round(2^32 / 2π) = 683,565,276`、`s = 32` を掛けて Q16 の回転数にしてから `SIN` に渡す。
9. 決まらない場所はエラーにし、ファイル・式・行を示す: 数の定数がその Q 形式で int32 に入らない、`MUL` のシフト量が 62 を超える、`SHIFT` の量が ±31 を超える、など §6.1 が拒む命令を作る場所。黙って飽和させない。
10. `@half 名前, ...` で宣言した名前への代入は `.H` の命令で計算する（各項は `sat16` される、§2.3）。`half` の名前の Q 形式も規則 1 で決める。

[shiki.md](shiki.md) §5.6: DERBY の `prail`・`pt` は、出荷している関数に `@q z=24, dz=24, pz=24`（`pt` は `farZ`・`fz0`・`fz` も）を足すだけで、この規則のもとで double との誤差が 0.05 px 未満（host）。

### 8.4 PIE に下ろせる列

`EACH` の本体のうち、`.H` の命令と、`i16` の領域の `FETCH`・`PUT` だけからなる連続した列は、PIE に下ろしてよい。§2.3 の定義が PIE の動きそのものなので、下ろしてもスカラーとビット単位で同じでなければならない（§10.2）。32 ビットの命令・描画の命令・`LOOKUP` を含む列は下ろさない。

- 下ろす列の `FETCH`・`PUT` は `k = 0` に限る（16 ビットのレーンにシフト命令が無いため）。
- 列の外で決まったレジスタ（`INPUT` など）を列の中で使うときは、`sat16` してから全レーンへ配る（§2.3 の被演算子の定義と同じ）。
- `MUL.H` ごとに `QACC` を 0 にする（§2.3）。

## 9. JS API

### 9.1 capability

名前 `kasane.shiki`。`supported` はこのファームが Shiki を実装していれば true。`available` は、アプリが manifest で予算を宣言していれば true（§9.2）。`limits`（ファームのハードの上限だけ）:

| 名前 | v1 の値 |
| --- | ---: |
| `maxInstructions` | 64 |
| `registers` | 16 |
| `maxInputs`・`maxArguments` | 8・8 |
| `maxDataRegions`（1 本の式）／`maxSessionDataRegions`（セッション全体） | 4／16 |
| `maxHandles` | 32 |
| `maxSteps`（1 回の draw） | 10,000 |
| `maxSegments`（1 フレーム） | 1,024 |
| `maxRasterSteps`（1 回の draw） | 8,192 |
| `maxSurfaces` | 2 |
| `loopDepth` | 8 |
| `maxRecords`（1 領域） | 65,535 |

予算と使用量は `limits` ではなく `shiki.heap()`（§9.2）が返す。

### 9.2 Shiki のヒープと寿命

- アプリは manifest で予算を宣言する: `shiki: {bytes: N}`。セッションの開始時に、N バイトの連続した区画を 1 つ確保する。確保できなければアプリを起動しない。
- フレーム・作業領域・式・点・データ領域は、すべてこの区画から取る。足りなければ、その呼び出しが `LIMIT_EXCEEDED` で失敗する。`shiki.heap()` は `{bytes, used, largest}` を返す。
- **窓の持ち方**: Shiki は、作った窓の ArrayBuffer を**強い参照で持つ**。したがって JS が窓を捨てても、ガベージコレクタは ArrayBuffer を解放せず、`free_func` も呼ばれない。領域の寿命は JS の GC ではなく、次の明示的な操作だけで決まる。
- **領域の解放**: `shiki.release(窓)` で行う。結び付いた handle が残っていれば `BUSY`。残っていなければ、Shiki は**窓を detach し（`free_func` がこの中で同期に呼ばれる）→ 自分の参照を捨てる → 簿記を更新 → 区画の中の領域を解放**の順に行う。`release` しない領域はセッションの終わりまで残り、`maxSessionDataRegions` と予算を使い続ける。
- **簿記**（領域ごとの、窓の参照・結び付いた handle の数）は区画の外、`.bss` の固定表（`maxSessionDataRegions` 個）に置く。
- `free_func` は何もしない（Shiki が自分の detach の中で呼ばれることと、ゲストを壊すときに呼ばれることしか無い。どちらでも解放は Shiki が別に行う）。
- **終了**: `app_stop()` は、Shiki の handle とフレームを片付ける reset を今の位置（ゲストを壊す前）で行い、そこで全領域の窓を detach して参照を捨てる。**区画の解放はゲストを壊した後**（`pocketjs_guest_destroy()` の後）の別の呼び出しで行う。
- 常駐中断（common-api §5）の間の区画の扱いは（未決）。推奨は「区画を保ち、中断の空きの判定に予算を含める」。

### 9.3 データ領域の窓

- `shiki.data({type: 'i16' | 'u16' | 'i32', q, length, record})` は、Shiki のヒープ上に領域を作り、その窓（`Int16Array`・`Uint16Array`・`Int32Array`）を返す。中身は 0。
- 窓は外部メモリを指す ArrayBuffer で、伸びない（resizable ではない）。
- **要件: 外部メモリの ArrayBuffer の長さを変える経路は、外部メモリを realloc してはならない。** 対象は `transfer`・`transferToFixedLength`・`transferToImmutable`（QuickJS-ng ではどれも `js_array_buffer_transfer` で、長さが違えば `js_realloc` する。コードで確認）。`ArrayBuffer.prototype` は ROM の組み込み（`CONFIG_POCKET_VM_ROM_INTRINSICS`、既定 y）で、これらの属性は消せない（non-configurable）ので、メソッドを消す方法は取れない。実装は `js_array_buffer_transfer` に「`free_func` が `js_array_buffer_free` でなく、長さが変わるなら `TypeError`」の門を足す（推奨）。同じ長さの `transfer` は外部メモリと `free_func` を新しい ArrayBuffer へ渡すので、これも外部メモリには `TypeError` にする（Shiki の強い参照が古い ArrayBuffer を指したままになるため）。

### 9.4 呼び出し

| 呼び出し | 引数 | 誤り |
| --- | --- | --- |
| `register(name, args?, options?)` | 組み込みの式の名前 | 名前が無い、引数の数・値、領域の不一致、§6.1: `INVALID_ARGUMENT`。handle の上限・予算: `LIMIT_EXCEEDED` |
| `register(code, args?, options?)` | §3 のバイト列（`Uint8Array`）。登録時に一度だけ区画へ写す | 同上 |
| `options` | `{data: [領域, ...], points: {...}}` | |
| `unregister(handle)` | | 古い handle: `CLOSED` |
| `beginFrame`・`draw(handle, ...inputs)`・`commit`・`resource`・`createSurface` | 旧 API と同じ意味。`draw` の入力は §2.4 で変換する | 旧 API と同じ |
| `heap()` | | |
| `data(desc)`・`release(窓)` | §9.3、§9.2 | 予算・領域の数: `LIMIT_EXCEEDED`。結び付いた handle が残る: `BUSY` |
| `grid.*` | §7 | 旧 API と同じ |

## 10. 検証の要件

1. **参照実装**: host（Node）の参照実装を 1 つ持ち、Shiki エンジンの C と、全命令・全状態でビット単位で一致しなければならない。出発点は `tools/kasane_ir/q16_error.mjs` の `fix`（§2.2・§2.4・§4.4・§4.5（範囲の判定を含む）・§8.3（規則 9 のエラーを含む）を実装済み。`EACH` 系・`.H`・`CUBIC`・`LINE_PATTERN` は未実装）。
2. **PIE**: PIE へ下ろした列は、同じ入力でスカラーの経路とビット単位で一致しなければならない。`.H` の各命令について、`QACC`＋`SRCMB` の丸めと飽和が §2.3 の定義どおりであることを**実機で**確かめる（境界の値: ±2^15、積の符号、`s` = 0・15・31）。
3. **捕獲した入力**: DERBY・MEGADEMO・BIG WAVE の捕獲した入力とランダムな入力で、参照実装と C が一致すること、および double で計算した意図の座標との誤差を記録すること（[shiki.md](shiki.md) §5.5 の形）。
4. **寿命**: 外部メモリの窓に対して `transfer`・`transferToFixedLength`・`transferToImmutable`（長さ 0・同じ・違う）が `TypeError` になり、区画が realloc されないこと。`release`・`unregister`・`app_stop()` のあらゆる順序で、解放が 1 回だけ起き、解放後の区画に触らないこと（ASan の host 試験）。
5. **実機**: 実機でしか起きない不具合（評価中の `null`、strict aliasing など）がこのプロジェクトにはあるので、host だけで済んだことにしない。

## 11. 旧 API からの移行

1. Shiki エンジン（32 ビットと `.H`）、参照実装、§3 のバイト列と §6.1 の検査、試験。旧 API は並べて残す。
2. `@shiki` の変換器（§8.3）。
3. DERBY の式の移行（`prail`・`pt` は `@q` を足す）。`pocket.derby.ser()` は実数のまま渡す（§2.4）。MEGADEMO・BIG WAVE。
4. データ領域（`EACH`・`FETCH`・`PUT`・`LOOKUP`）と Shiki のヒープ、`js_array_buffer_transfer` の門。
5. `.H` の列の PIE への下ろし。
6. すべてのアプリが移ったら、旧 API（float の plan、`pocket.kasane.procedural`、グローバルの `gridFold`）を消す。
