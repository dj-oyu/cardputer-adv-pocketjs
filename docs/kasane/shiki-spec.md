## 0. 読み方

- 「〜する」「〜しなければならない」は規範。「推奨」は規範ではない。「（未決）」の項目は v1 の確定前に決める。
- 数値の上限は、コードで強制し `limits`（§9.1）に出す値だけを書く。性能の数値は書かない。
- 用語: **式**（1 本のプログラム）、**handle**（登録した式）、**Shiki エンジン**（式を実行する native。QuickJS の VM とは別物）、**データ領域**（式が読み書きする型付きの配列）、**Q 形式**（固定小数の小数部のビット数。`Qf`。例 Q16 は 1/65,536 刻み）、**参照実装**（§10.1）。
- 演算は数学の式で定義する（C の符号付きシフトなど、実装定義の動きに頼らない）。`⌊x⌋` は負の無限大方向への切り捨て、`sat32(x) = min(max(x, −2^31), 2^31−1)`、`sat16(x) = min(max(x, −2^15), 2^15−1)`。

## 1. 範囲と実行モデル

1. Shiki は、JS アプリが登録した式を native が実行し、Kasane の手続き面のフレームへ線分を出す仕組みである。式の種類は **線の式**（§3〜§6）と **格子の式**（§7）。
2. 描画タスクは 1 つで、式は JS の呼び出し（`draw`・`run`）の中で**同期に**実行される。Shiki エンジンがデータ領域を読み書きするのは、その呼び出しの間だけである。
3. 式の実行は有界でなければならない。上限（§9.1）を超える実行は `LIMIT` で止まる。
4. **決定性**: 同じ式・引数・入力・データ領域の中身からは、どの実装経路（スカラーの C、PIE、参照実装）でも、ビット単位で同じ状態・線分・データ領域への書き込みを生まなければならない（§10）。

## 2. 数の型と演算

### 2.1 型

| 型 | 中身 | 用途 |
| --- | --- | --- |
| `fixed` | 32 ビットの符号付き整数。値は `raw / 2^f`（`f` はその値の Q 形式、0〜30） | レジスタ、入力、引数、座標、計算 |
| `int` | `fixed` の `f = 0` | 回数、添字、色 |
| `half` | 16 ビット幅の値（−2^15〜2^15−1）。Q 形式を持つ | PIE に下ろす計算（§2.3、§8.4） |
| データ領域の要素 | `i16`・`u16`・`i32`。領域ごとに Q 形式を持つ（§5.1） | 表、点、状態 |

- float は Shiki のどこにも現れない。
- **Q 形式は命令が持たない。** 書き手が宣言し（§8.3）、変換器が掛け算のシフト量と `SHIFT` に畳み込む。Shiki エンジンは整数の命令だけを実行する。
- `half` も 32 ビットのレジスタに入るが、`.H` の命令（§4.3）だけが `half` を作り、その結果は必ず −2^15〜2^15−1 に入る。
- 色は `int`（0〜65,535）。

### 2.2 32 ビットの演算

| 演算 | 定義 |
| --- | --- |
| `ADD`・`SUB`・`NEG` | `sat32(a + b)`・`sat32(a − b)`・`sat32(−a)` |
| `MUL a, b, s`（0 ≤ s ≤ 62） | `sat32(⌊a · b / 2^s⌋)`（`a · b` は正確な 64 ビットの積） |
| `SHIFT a, k`（−31 ≤ k ≤ 31） | `k ≥ 0` なら `sat32(a · 2^k)`、`k < 0` なら `⌊a / 2^−k⌋` |
| 比較 | 符号付き整数の比較 |
| 正弦 | §4.4 |

- 0 での割り算は無い（割り算は変換器が定数の逆数の掛け算か、2 の冪ならシフトへ下ろす、§8.3）。非有限の値も無い。
- スカラーの C は、64 ビットの積を `MULL`・`MULSH` と漏斗シフトで作れる。
- **エンジンの実行時の計算の幅（v1.2）**: 積・和・差・シフトは 64 ビットを使ってよい。**割り算と剰余は 32 ビット ÷ 32 ビット（被除数・除数・商がすべて int32 に入る）に限る**。2 の冪での割り算はシフトとして扱い、この制限に数えない。各命令の手順（§4.6・§4.7）は、この制限に収まるように値の範囲を決めてある。理由は実測（[int-latency.md](../perf/int-latency.md)、2026-10-31）: 掛け算は値・ビット幅に依らず発行 1・レイテンシ 2 サイクルで、64 ビットの積は 2 命令。32 ビットの割り算（`QUOS`）は値に依って 2〜12 サイクル。64 ビットの割り算はライブラリの呼び出しで 87〜160 サイクル。

### 2.3 16 ビット幅の演算（`.H`、PIE と同じ意味論）

| 演算 | 定義 | 対応する PIE（TRM v1.8） |
| --- | --- | --- |
| 被演算子 | 32 ビットのレジスタの値を、まず `sat16` する | |
| `ADD.H`・`SUB.H` | `sat16(a + b)`・`sat16(a − b)` | `EE.VADDS.S16`・`EE.VSUBS.S16`（飽和） |
| `MUL.H a, b, s`（0 ≤ s ≤ 31） | `sat16(⌊a · b / 2^s⌋)`（`a · b` は 32 ビットに収まる） | `EE.VMULAS.S16.QACC`（p.215）で積を蓄積し、`EE.SRCMB.S16.QACC`（p.130）でシフトと 16 ビットの飽和 |
| `SHIFT.H a, k`（−15 ≤ k ≤ 14） | `k ≥ 0` なら `sat16(a · 2^k)`、`k < 0` なら `⌊a / 2^−k⌋` | 定数との `MUL.H` で表す（16 ビットのレーンのシフト命令は無い、[pie-simd.md](../perf/pie-simd.md)） |

- `EE.VMUL.S16`（p.198）は積の下位 16 ビットを取る（wrap）ので、`MUL.H` には使わない。
- `QACC`＋`SRCMB` の丸めが `⌊⌋` と飽和で上の定義どおりであることは、レビューが TRM で確かめた。**実機での確認は §10.2 の要件**。
- `MUL.H` のシフト量 `s` は、PIE では `EE.SRCMB.S16.QACC` のアドレスレジスタ（`as[5:0]`、TRM p.130）で渡す。命令ごとに違う `s` を使ってよい（`SAR` を使うのは `EE.VMUL.S16` で、`MUL.H` には使わない）。
- `EE.SRCMB.S16.QACC` はシフトした値を `QACC` にも書き戻すので、PIE の実装は `MUL.H` ごとに `QACC` を 0 にする（`EE.ZERO.QACC`）。

### 2.4 JS との境目

- JS の数 `v`（double）を Q 形式 `f` の `fixed` へ変えるときは、`x = min(max(v · 2^f, −2^31), 2^31−1)` を double で求め、`sign(x) · ⌊|x| + 0.5⌋`（半分は 0 から遠い方）とする。有限でない `v` は `INVALID_ARGUMENT`。
- 入力・引数の Q 形式は式が宣言する（§3）。JS は実数のまま渡し、変換は native が行う。例外は `drawMany` に `Int32Array` で渡す入力（§9.4、v1.5）で、各入力の Q 形式の `fixed` の値そのものとして読み、この変換をしない（Q 形式への換算は JS の責任。データ領域と同じ）。`pocket.derby.ser()` のような native の呼び出し元も、実数を渡して同じ変換を通す。
- データ領域は、JS が要素の型のまま（`Int16Array` などの生の整数で）書く。Q 形式への換算は JS の責任。

## 4. 線の式の命令

### 4.1 状態

- レジスタ `r0`〜`r15`（32 ビット）。draw の始めにすべて 0。
- ペン（座標と有効か）。draw の始めに無効。
- ループの段（8 段まで）。`EACH` も同じ 8 段に数える。各段の残りの回数は 0〜65,535。
- ステップ: 実行した命令 1 つを 1 ステップと数える（`REPEAT`・`EACH` は入るとき 1 回、`END` は 1 周ごとに 1 回）。
- フレームへ出した線分。

### 4.2 命令の形式

1 命令 12 バイト: `op`（8）、`dst`・`a`・`b`（各 8）、`imm`（符号付き 32）、`aux`（16）、予約 2 バイト（0）。

### 4.4 正弦

`SIN dst, a`: `r[a]` を Q16 の**回転数**（1 周 = 65,536）とし、その下位 16 ビット `p`（0〜65,535）を位相に使う。

1. `quad = ⌊p / 2^14⌋`、`w = p mod 2^14`。`quad` が 1 か 3 なら `w = 2^14 − w`。
2. `w = 2^14` なら `v = T[256]`。そうでなければ `i = ⌊w / 64⌋`、`t = w mod 64`、`v = T[i] + ⌊(T[i+1] − T[i]) · t / 64⌋`。
3. `quad` が 2 か 3 なら `v = −v`。`r[dst] = v`（Q16）。

`T` は 257 個の `i32` の組み込み表 `T[k] = round(sin(k·π/512) · 65536)`（k = 0〜256、`T[256] = 65536`）。表と手順は v1 の一部で、変えるには版を上げる。ラジアンからの換算は変換器が入れる（§8.3）。

精度の記録（[shiki.md](shiki.md) §5.5、host）: 位相の刻みは 1/65,536 周（約 9.6e-5 rad）。`sin(u * 137 + t)` のように sin の結果を大きく増幅して乱数代わりにする式では、この刻みが増幅される（DERBY の `dust` で最大 0.6 px、ランダムな入力で 2 px）。

### 4.5 座標

- 描画の命令は、レジスタを **Q16** の画素の座標として読み、`⌊(raw + 32768) / 65536⌋`（64 ビットで計算する）を画素にする（v1.1）。最も近い画素で、ちょうど半分のときは**正の方向**に丸まる（旧 API の `lroundf` とは、負のちょうど半分だけ違う）。
- 変換器は座標に何も足さない（v1 では変換器が 0.5 を足し、エンジンは `⌊raw / 65536⌋` だった）。
- 範囲の判定はこの画素で行う: −480〜720 の外なら `INVALID`。

### 4.6 `CUBIC`（v1.2）

`CUBIC dst, imm=n, aux=色`: 制御点 `P0`〜`P3` を `r[dst]`〜`r[dst+7]`（`(x0, y0, x1, y1, x2, y2, x3, y3)`、Q16 の座標）から読み、3 次のベジェ曲線を `n` 本（1〜255）の線分で描く。ペンを使わず、`P0` から始める。

1. 制御点の座標を `x0, y0, x1, y1, x2, y2, x3, y3` の順に §4.5 で画素にし、範囲外なら `INVALID`（線分を出さない）。
2. `k = 0, 1, …, n` の点 `B(k)` を、§2.2 の `MUL`（`s = 16`）と `ADD` で次のとおり計算する（`t` の割り算はエンジンの整数の計算。`3 ·` は `MUL` の結果を 3 倍する。`MUL(uu, 3t, 16)` とは値が違う）（`u`・`t` は 0〜2^16、重みは 0〜3·2^16。制御点が範囲内なら飽和は起きない）。
   - `t = ⌊k · 2^16 / n⌋`、`u = 2^16 − t`
   - `uu = MUL(u, u, 16)`、`tt = MUL(t, t, 16)`
   - `w0 = MUL(uu, u, 16)`、`w1 = 3 · MUL(uu, t, 16)`、`w2 = 3 · MUL(u, tt, 16)`、`w3 = MUL(tt, t, 16)`
   - `Bx = MUL(w0, x0, 16) + MUL(w1, x1, 16) + MUL(w2, x2, 16) + MUL(w3, x3, 16)`（左から `ADD` で足す）。`By` も同じ。
   - `B(k)` は `(Bx, By)` を §4.5 で画素にしたもの。`k = 0` は `P0`、`k = n` は `P3` にちょうど一致する（`t = 0`・`2^16` で重みが `2^16` と 0）。
3. `k = 1, …, n` の順に、`B(k)` を画素にして範囲を検査し（外なら `INVALID`）、`B(k−1)` から `B(k)` への線分を §4.8 の 4 で加える。`INVALID`・`LIMIT` で止まったら、それまでの線分は残り、ペンは動かない。重みは非負で和が 2^16 以下なので、`B(k)` は制御点と原点の凸包から、切り捨ての分（各座標で raw の 4 以内）しか出ない。範囲は 0 を含むので、この検査は安全網で、制御点が範囲内なら失敗する入力は見つかっていない（重みの和が 2^16 に欠ける点は原点の側へ寄るので下端を越えず、欠けの無い点で下端の近くを総当たりしても失敗しなかった。証明ではない）。実装は検査を省かない。
4. 終わったらペンを `B(n)`（= `P3` の画素）に置き、有効にする。ステップは命令全体で 1。

精度の記録（host、[shiki.md](shiki.md) §5.10）: 重みの切り捨てで和が最大 8/65,536 欠け、曲線は原点の側へ寄る。正確な曲線からの距離は最大 0.597 px（うち 0.5 は画素への丸め）、正確な曲線を丸めた画素と違う座標は 1.8%。

### 4.7 `LINE_PATTERN`（v1.2）

`LINE_PATTERN dst, a, b, imm=N, aux=色 A`: ペンから `(r[a], r[b])` へ、画素ごとに色を選ぶ線（模様）を描く。旧 API と同じ構造で、奥行きの重みが違えば 2・4・8 本の弦に分け、切れ目の模様の座標を透視補正する（[crowd-primitives-design.md](crowd-primitives-design.md)）。`N` は模様の周期（1〜24 セル）。

この節の値はすべて正確な整数で計算する。int32 に収まらない中間の値は、`(u1 − u0) · λ` の積（64 ビット）だけ。割り算はすべて、被除数と除数が int32 に収まる（§2.2 の制限。2 の冪の割り算はシフト）。

ブロック `r[dst]`〜`r[dst+5]`:

| レジスタ | 名前 | Q 形式 | 範囲（外なら `INVALID`） |
| --- | --- | --- | --- |
| `r[dst]` | 模様 `bits`（セル `c` の色は bit `c` が 1 なら A、0 なら B） | Q0 | 0〜2^24 − 1 |
| `r[dst+1]` | 色 B（−1 は「描かない」） | Q0 | −1〜65,535 |
| `r[dst+2]`・`r[dst+3]` | ペン・終点での模様の座標 `u0`・`u1`（セル） | Q16 | −2^29〜2^29（±8,192 セル、v1.2） |
| `r[dst+4]`・`r[dst+5]` | ペン・終点の奥行きの重み `w0`・`w1`（1/Z。比だけが意味を持つ） | Q16 | −2^24〜2^24（±256.0） |

1. `r[a]`・`r[b]` を §4.5 で画素 `(x, y)` にし、範囲外なら `INVALID`。ペンが無効なら、ペンを `(x, y)` に置いて終わる（何も描かず、ブロックも読まない）。
2. ブロックの値を上の表で検査する（`bits`・色 B・`u0`・`u1`・`w0`・`w1` の順）。外れたら `INVALID`。
3. **弦の数 `c`**: `w0`・`w1` が同じ符号（両方正か両方負）のとき、`W = max(|w0|, |w1|)`、`V = min(|w0|, |w1|)` として、`50W < 51V` なら 1、`5W < 6V` なら 2、`5W < 8V` なら 4、それ以外は 8（旧 API の比 1.02・1.2・1.6 の判定を整数で厳密にしたもの）。どちらかが 0 か、符号が違えば 1。
4. 弦 `j = 1, …, c` を順に作る。弦 `j` の始点 `(ax, ay, ua)` は、`j = 1` ならペンと `u0`、`j ≥ 2` なら弦 `j − 1` の終点。終点 `(bx, by, ub)` は、`j = c` なら `(x, y, u1)`、そうでなければ:
   - `bx = px + R((x − px) · j, c)`、`by = py + R((y − py) · j, c)`（`(px, py)` はペン。`R(p, q)` は `p / q` に最も近い整数で、ちょうど半分は正の方向: `⌊(2p + q) / 2q⌋`。分母が負なら分子と分母の符号を両方反転してから計算する。この節の `R` はすべて int32 の中で計算できる: `λ` は `2p + q < 2^31` がそのまま成り立ち、`d`・`u0q`・`ub` の `R` は `q` が正の偶数なので `⌊(p + q/2) / q⌋` と同じ（`d` は `2p` が int32 を溢れうるので、この形で計算する）。`p` は負になりうるので、C の 0 方向への切り捨ての割り算をそのまま使ってはならない（§0 の `⌊⌋`））。端は始点と終点の間なので範囲の内側。
   - `ub` は、透視補正した内分比 `λ` で求める（32 ビットの割り算に収めるため、**小さい方の重み**を 13 ビットに正規化する）:
     1. `A = |w0|`、`B = |w1|`（同じ符号なので両方 1 以上）。`e = max(0, L(min(A, B)) − 13)`（`L(v)` は正の整数 `v` のビット数、`⌊log2 v⌋ + 1`）。`A' = ⌊A / 2^e⌋`、`B' = ⌊B / 2^e⌋`（小さい方は 2^13 未満、大きい方は 2^24 以下）。`D = A' · (c − j) + B' · j`（1 以上 2^27 未満）。
     2. `B ≤ A` なら `λ = R(B' · j · 2^14, D)`、`A < B` なら `λ = 2^14 − R(A' · (c − j) · 2^14, D)`（Q14、0〜2^14。どちらも分子は小さい方の重みで 2^30 未満、`2p + q < 2^31`）。
     3. `ub = u0 + R((u1 − u0) · λ, 2^14)`（Q16。`ub` は `u0` と `u1` の間）。
5. 各弦について: `s = max(|bx − ax|, |by − ay|)`（画素の歩数）。模様の始まり `u0q = M(R(ua, 256), 256N)`（8.8 のセル。`M(v, m)` は `v − m · ⌊v / m⌋`、0〜m−1）。歩幅は `s = 0` なら 0、そうでなければ `d = R(ub − ua, 256 · s)` で、`|d| ≥ 2^16`（1 画素に 256 セル以上）なら `INVALID`、そうでなければ `duq = M(d, 256N)`。続いて §4.8 の 4 と同じ規則で、線分が 2 本分の空きが無い（すでに 1,023 本以上）か、ラスタの合計＋`s + 1` が 8,192 を超えるなら `LIMIT`。どちらでもなければ、2 エントリを加える（幾何: 始点・終点・色 A、模様: `bits`・`N`・色 B（または無し）・`u0q`・`duq`。エンコードは旧 API の `ksn_shiki_frame.h` と同じ）。
6. 旧 API（float）との差: (a) 切れ目の位置の丸めは、旧の `lroundf`（半分は 0 から遠い方）と負のちょうど半分で違い、右から左への線で切れ目が 1 画素ずれうる（例 `x − px = −7`、`c = 2`: 旧 −4、v1.2 −3）。(b) 切れ目の `ub` は、旧の float32 の 4 回の丸めではなく、正規化した重みと Q14 の `λ` から求めるので、2 本目以降の弦の `u0q` が動き、セルの境目の画素が 1 つずれうる。正確な透視補正からの差は、`λ` の Q14 の丸めで最大 `|u1 − u0| / 2^15`、重みの正規化で比が大きいほど増える（host: DERBY の `crowd` の実ゲームの入力で最大 0.030 セル、ランダムな入力で 0.071 セル、範囲の端を組み合わせた最悪で 1.35 セル。[shiki.md](shiki.md) §5.10）。(c) 比の判定は旧の `1.02f`（1.01999998…）と境界の極めて狭い帯で違う。
7. 途中の弦で `INVALID`・`LIMIT` になったら、それまでの弦は残り、ペンは動かない。すべて加えたら、ペンを `(x, y)` に置く。ステップは命令全体で 1。
8. 描画: 弦の `k` 番目の画素（始点が 0、主軸に 1 歩ずつ）のセルは `⌊M(u0q + k · duq, 256N) / 256⌋`。その bit が 1 なら色 A、0 なら色 B（無しなら描かない）。

### 4.8 実行の細部（v1 の明確化、2026-10-31）

v1 の凍結後、2 つの独立した実装（C のエンジンと参照実装）をビット単位で比べるために、仕様が書いていなかった細部を決めた。旧 API の VM（`ksn_shiki_frame.c`）と同じ動きで、§1〜§4.7 の意味は変えない。

1. **ステップ**: 各命令を実行する前に、ステップ数が 10,000 なら `LIMIT`（その命令は実行しない）。そうでなければステップ数を 1 増やして実行する。
2. **レジスタの書き込み**: 被演算子をすべて読んでから `dst` に書く（`dst` が `a`・`b` と同じでよい）。
3. **描画の命令の順序**: `PLOT_C`・`LINE_C` の色の検査 → `a` の座標 → `b` の座標 → 線分の追加 → ペンの更新。途中で失敗したら、それより後は行わない（失敗した命令はペンを動かさない）。
4. **線分の追加**: 費用は `max(|x1 − x0|, |y1 − y0|) + 1`（画素、`PLOT` は 1）。線分がすでに 1,024 本なら `LIMIT`。そうでなく、その draw のラスタの合計＋費用が 8,192 を超えるなら `LIMIT`。どちらでもなければ追加する。
5. **ループ**: `REPEAT`・`REPEAT_REG` は、回数が 0 なら対応する `END` の次へ飛ぶ（段を積まない）。1 以上なら段（始まりの命令の番号、残りの回数）を積む。`END` は残りを 1 減らし、0 でなければ始まりの命令の次へ、0 なら段を降ろして次へ。`BREAK_IF_GT` が成り立てば、いちばん内側の段の `END` の次へ飛び、段を降ろす。
6. **終わり**: 命令を実行した後、次の命令の番号が命令の数に等しければ `DONE`。
7. **入力**: draw の始めに、宣言した入力の数だけを §2.4 で変換する。渡された数が宣言より多ければ残りは捨て、少なければ足りない分は 0。有限でない入力は、実行を始めずに `INVALID_ARGUMENT`。
8. **失敗したときの状態**: `INVALID`・`LIMIT` で止まったときのレジスタ・ペン・ステップ数・それまでの線分は、決定的でなければならない（§1.4。フレームとしては捨てられる）。

## 5. データ領域

### 5.1 宣言と結び付け

- データ領域は Shiki のヒープ（§9.2）に、16 バイトの境界で確保する。JS には型付き配列の窓として渡す（§9.3）。
- 1 つの領域は、要素の型、Q 形式（0〜30）、1 レコードの要素の数 `k_rec`（1〜8）、レコードの数 `R`（**1〜65,535**）を持つ。**大きさは確保したときに決まり、変わらない。**
- **並び（v1.4、欄ごとの面）**: レコード `j` の `c` 番目の欄（`c` = 0〜`k_rec − 1`）は、領域の先頭から **`c · S + j`** 番目の要素。`S`（面の長さ）は `R` を 8 の倍数に切り上げた値 `⌈R / 8⌉ · 8`。領域の要素の数は `k_rec · S`。各面の末尾の `S − R` 個を**詰め物**と呼ぶ。**詰め物の値は draw の結果（状態・レジスタ・線分・書き込む値）に影響せず、draw の前後で変わらない**（観測で決める。実装が詰め物を読むこと、読んだ値をそのまま書き戻すことは許す。PIE の 128 ビットのアクセスは末尾のブロックで詰め物に触れるため。§5.4 の 6、§8.4）。JS は窓を通して詰め物に書いてよく、書いた値は残るが、エンジンには意味が無い。置ける数が `R` によって 0〜7 個と変わり、`fields()` からは見えず、`S` の式が変われば位置も変わるので、**アプリのデータの置き場としても推奨しない**（付随値は `shiki.data()` で別の領域を作る）（2026-11-01 ユーザー決定。別の用途の議論は [shiki.md](shiki.md) §5.18）。領域の先頭は 16 B に揃い、`S` が 8 の倍数なので、各面の先頭も 16 B に揃い（`i16`・`u16` は 1 面が 16 B の倍数、`i32` は 32 B の倍数）、**8 レコードのブロックの 128 ビットのアクセスは面の中に収まる**（末尾のブロックも面の外へ出ない。`S` を 8 の倍数に切り上げる理由は整列とこの 2 つ）。v1.3 の並び（レコードの欄が隣り合う、`j · k_rec + c`）は廃止した。理由: PIE の 128 ビットのロード・ストアは 16 B 整列が必須で、部分ストアが無い。面なら 1 つの欄の 8 レコードが整列したアクセス 1 回になり、`k_rec` によらない。実測で面の並びが遅かった場合は無い（スカラーの `FETCH` と列からの描画は差なし、ベクトル・PIE は 3.3% 速い、[shiki-jit.md](shiki-jit.md) §24.6）。 レコードの数を 1 以上にするのは、長さ 0 の外部 ArrayBuffer という角を無くすため（`js_array_buffer_constructor3` は外部の `buf` が NULL だと内部に 1 B を確保して `free_func` を `js_array_buffer_free` に差し替えるので、§9.3 の門が外部と見分けられず、Shiki の簿記と食い違う）。0 件を回したいときは `EACH` の件数のレジスタ（`aux = 1`）で 0 を渡す。
- 以下、命令の `imm` のシフト量を `k`、1 レコードの要素の数を `k_rec` と書き分ける。
- **結び付けは登録時に固定する。** 式の領域の表（§3）と渡した領域は、型・Q 形式・`k_rec` がすべて一致しなければならない（不一致は `INVALID_ARGUMENT`）。渡すのは `shiki.data()` が返した窓そのもの（同じオブジェクト）でなければならない。同じ ArrayBuffer の別の view は `INVALID_ARGUMENT`。
- 渡す領域の数は、式の領域の表の数にちょうど等しい（違えば `INVALID_ARGUMENT`）。`i` 番目に渡した領域が、領域番号 `i` に結び付く。
- 1 つの領域を、複数の handle に結び付けてよい。同じ窓を 1 つの handle の 2 つの領域番号に渡してもよい（同じメモリを 2 つの番号から読み書きする）。
- `LOOKUP` に使う領域は `k_rec = 1` でなければならない（登録で検査する）。引ける要素はレコード `0`〜`R − 1`（詰め物は引かない）。

### 5.2 命令

| 命令 | 動き |
| --- | --- |
| `EACH a, b, aux=f` | 領域 `a` のレコードを先頭から回すループ。`f = 0` なら全レコード（`b` は 0）、`f = 1` なら先頭の `r[b]` 件（v1.3）。カーソルは 0 から始まり、`END` で 1 進む。件数が 0 なら本体を飛ばす（§5.4） |
| `FETCH dst, a, b=位置, aux=個数 m, imm=k` | 領域 `a` を回している**いちばん内側の `EACH a`** のカーソルのレコードの、`b` 番目から `m` 個を `r[dst..dst+m−1]` へ。各要素 `e` は `SHIFT(e, k)`（§2.2）して Q 形式を合わせる。違う領域の `EACH` を入れ子にすれば、外側の領域のレコードも読める |
| `PUT dst, a, b=位置, aux=個数 m, imm=k` | 逆向き。`r[dst..dst+m−1]` を `SHIFT(·, k)` してから、要素の型の範囲（`i16`: −2^15〜2^15−1、`u16`: 0〜65,535、`i32`: そのまま）へ飽和して書く |
| `LOOKUP dst, a, b, aux=g, imm=k` | `i = min(max(⌊r[b] / 2^g⌋, 0), R − 1)` のレコードの要素を `SHIFT(·, k)` して `r[dst]` へ。**範囲外は端に寄せる**（ユーザー決定）。`k_rec = 1` の領域だけ |

### 5.3 書き込みの規則（`PUT`）

1. 書き込みは命令の順に即座に見える。同じ draw の後の `FETCH`・`LOOKUP` も、同じフレームの後の draw も、書いた値を読む。
2. JS は、`draw` が戻った後に書いた値を読める（同じメモリの窓）。`draw` の途中で JS は動かない。
3. draw が失敗しても（`INVALID`・`LIMIT`）、それまでの書き込みは戻らない。フレームの線分は捨てられる。
4. v1 の書き込みは、`EACH` のカーソルのレコードの中だけ。

### 5.4 実行の細部（v1.3）

§4.8 と同じく、2 つの独立した実装がビット単位で一致するために決める。ステップ・ループの段・失敗したときの状態は §4.8 に従う。

1. **`EACH a, b, aux=f`**: 入るときに 1 ステップ。件数 `N` は、`f = 0` なら領域 `a` のレコードの数、`f = 1` なら `r[b]`。`r[b]` が 0〜レコードの数の外なら `INVALID`（`REPEAT_REG` と同じく、整数として読む。§8.3 で件数は Q0）。`N = 0` なら対応する `END` の次へ飛ぶ（段を積まない）。1 以上なら段（始まりの命令の番号、残り `N`、カーソル 0、領域 `a`）を積む。ループの段は `REPEAT`・`REPEAT_REG` と同じ 8 段に数える。**`r[b]` は入るときに 1 回だけ読む**。本体で `r[b]` を変えても件数は変わらない（`REPEAT_REG` も同じ）。
2. **`END`**（`EACH` の段）: 1 ステップ。カーソルを 1 進め、残りを 1 減らし、0 でなければ始まりの命令の次へ、0 なら段を降ろして次へ。`BREAK_IF_GT` は `EACH` の段も降ろす（§4.8 の 5）。
3. **`FETCH dst, a, b, aux=m, imm=k`**: 1 ステップ。読むレコードは、この命令を字句的に囲む**いちばん内側の `EACH a`** の段のカーソル（登録時に決まる。§6.1）。実行時の段を内側から探して領域 `a` の段を取る実装も、実行時の段は字句の入れ子そのものなので常に同じ結果になり、どちらで実装してもよい。同じ領域の自己入れ子（`EACH a` の中の `EACH a` の中の `FETCH a`）は内側の `EACH a` に解決する。レコードの `b + j` 番目の要素 `e_j`（`j = 0, …, m − 1`）を、要素の型の値（`i16` は符号付き、`u16` は 0〜65,535）として読み、`r[dst + j] = SHIFT(e_j, k)`（§2.2）を `j` の昇順に書く。
4. **`PUT dst, a, b, aux=m, imm=k`**: 1 ステップ。先に `v_j = SHIFT(r[dst + j], k)` をすべて求め、要素の型の範囲（`i16`: −2^15〜2^15−1、`u16`: 0〜65,535、`i32`: そのまま）へ飽和して、`j` の昇順にレコードの `b + j` 番目へ書く。
5. **`LOOKUP dst, a, b, aux=g, imm=k`**: 1 ステップ。`i = min(max(⌊r[b] / 2^g⌋, 0), R − 1)`（`⌊ ⌋` は 2 の冪の割り算なのでシフト。§2.2 の割り算の制限に当たらない）、`r[dst] = SHIFT(e_i, k)`。`e_i` はレコード `i` の要素（`k_rec = 1` なので領域の先頭から `i` 番目）で、3 と同じく要素の型の値（`i16` は符号付き、`u16` は 0〜65,535）として読む。`R` は領域のレコードの数（`k_rec = 1` の v1.3 では要素の数 `n` と同じ。v1.4 では要素の数 `S` が詰め物を含むので、レコードの数で書く）。
6. 読み書きの番地（v1.4）: カーソル `cur` のレコードの欄 `b + i`（`i = 0, …, m − 1`）は、領域の先頭から **`(b + i) · S + cur`** 番目（§5.1）。登録時の検査（§6.1）と `N ≤ R` から、`FETCH`・`PUT`・`LOOKUP` の番地は範囲の外にも詰め物にも当たらない。draw の前後で値が変わってよい要素は、`PUT` が書いたレコードの欄だけ（レコード `N` 以降、書かない欄、詰め物は変わらない。§5.1）。

## 8. `@shiki` の記法

### 8.1 形

[js-to-ir.md](js-to-ir.md) §5 の `@plan` の部分集合（R1〜R6）を引き継ぎ、印を `@shiki` にする。

```js
/** @shiki prail inputs: x, dx, z, dz, posts, r, colour, top
 *  @q z=24, dz=24, pz=24
 *  @half vx, vy
 *  @data seats: i16 q8 record 3 write */
function prail() { ... }
```

### 8.2 足す書き方

| 書き方 | 命令 | 欄の決め方（v1.3） |
| --- | --- | --- |
| `for (const [a, b, c] of seats)` | `EACH`（全件）＋ `FETCH` | `EACH 領域, b=0, aux=0`。分解した名前は先頭からの並び（穴・`...` は無し）で、数 `m` は 1〜`k_rec`（超えればエラー）。名前を連続したレジスタ `dst..dst+m−1` に置き、本体の先頭で `FETCH dst, 領域, b=0, aux=m, imm=0`（名前の Q 形式は領域の Q 形式、§8.3 の規則 1） |
| `for (const [a, b, c] of seats.take(n))` | `EACH`（先頭の `n` 件）＋ `FETCH` | `EACH 領域, b=n のレジスタ, aux=1`。`n` は Q0（規則 1）。名前ならそのレジスタ、数の定数なら `SET` を 1 命令足す（整数でない、0〜65,535 の外ならエラー）、式なら規則 2 で Q0 として計算する（小数を含みうる式は規則 9 のエラー）。`FETCH` は上と同じ |
| `seats.put(e0, …)` | `PUT` | 同じ領域を回す `for...of` の中だけ（外ならエラー）、領域は書く宣言（`write`）でなければエラー。引数の数 `m` は 1〜`k_rec` で、レコードの先頭から書く。各引数は規則 2 で**受け取る側 = 領域の Q 形式**として計算し、連続したレジスタ `dst..dst+m−1` に置いて `PUT dst, 領域, b=0, aux=m, imm=0`。受け取る側と同じ Q 形式の名前は `SHIFT dst+j, 名前, imm=0` で写す（Shiki に移動の命令は無く、`sat32(a · 2^0) = a`）。写した先と元が同じレジスタに割り当たった写しは省いてよい（ビットは同じで、命令とステップの数だけが減る。2026-10-31 ユーザー決定）。ただし引数がすべて `FETCH` で置いたレジスタそのまま（`put(a, b, c)` の `a, b, c` が `dst..dst+2`）なら写さない |
| `table[i]` | `LOOKUP` | 領域は `k_rec = 1`。`b` は添字のレジスタ、`g` = 添字の Q 形式（名前なら宣言、式なら Q16 で計算して `g = 16`）、`k` = 受け取る側の Q 形式 − 領域の Q 形式（±31 の外は規則 9 のエラー） |
| `a - b`、`-a` | `SUB`、`NEG` | |

### 8.3 Q 形式（書き手が宣言する。値の範囲は推定しない）

1. **名前の Q 形式**: `@q 名前=ビット数` で宣言した名前はその値。**`for...of` で領域を回す分解した名前は、領域の Q 形式**を持ち、`@q` で宣言した名前と同じに扱う（`@q` で違う値を宣言すればエラー。Q0 の伝播には参加せず、別の Q 形式で受け取る場所では規則 2 の `SHIFT` が入り、Q0 の名前への代入は規則 9 に従う。v1.3）。次の名前は `int`（Q0）で、宣言と食い違えばエラー: `for` のループ変数（`for...of` の分解した名前を除く）、`REPEAT` の回数と `take(n)` の件数（v1.3）に使った名前、色と整数の描画引数（`line`・`plot` の色、`cubic` の分割数と色、`linePattern` の模様・色・周期）に使った名前、そして**それらと名前どうしの単純な代入（`a = b`、`let a = b`）でつながった名前すべて**（`const C0 = 0xffd9; let cu = C0; line(x, y, cu)` の `C0`）。それ以外は Q16。伝播するのは Q0 だけで、他の Q 形式は宣言でしか決まらない（`let pz = z` の `pz` は `z` の `@q` を継がない）。Q0 を継がせたくない名前は、名前だけの代入でつながないか、別の値から計算する。
2. **式の Q 形式は、受け取る側が決め、部分式もその Q 形式で直接計算する**: 代入なら代入先、入力・引数の宣言ならその値、描画の座標（`cubic` の 8 個を含む）と `linePattern` の模様の座標 `u0`・`u1`・奥行きの重み `w0`・`w1` なら Q16、回数・色（`cubic` の分割数、`linePattern` の模様・色・周期を含む）なら Q0。`SHIFT` で Q 形式を揃えるのは**名前だけ**（名前の宣言と、受け取る側の Q 形式が違うとき）。
3. `+`・`−`・単項 `−` の項は、規則 2 のとおり結果の Q 形式で計算する（項が名前なら `SHIFT`、式ならその Q 形式で直接）。
4. `a * b` の各項の Q 形式: 名前は宣言、**数の定数は int32 に入る最大の Q 形式（30 以下）**、それ以外の式は Q16 で計算する。`MUL` のシフト量は `s = qa + qb − q結果`。`s < 0` なら `MUL s=0` の後に `SHIFT −s` を足す。
5. 2 の冪の定数での割り算は、項が掛け算なら `s` に足し、そうでなければ `SHIFT` で右へずらす。負の定数なら `NEG` を足す。それ以外の定数での割り算は、`1/c` の掛け算として規則 4 に従う。
6. 数の定数は、規則 4 の場合を除き、使われる場所の Q 形式で §2.4 と同じ丸めをする。
7. 比較 `a > b` は、両辺の「自然な Q 形式」（名前は宣言、数の定数は相手の辺に従う、それ以外は Q16）の大きい方を受け取る側の Q 形式として、規則 2 で両辺を計算する（式の辺はその Q 形式で直接計算する）。
8. `sin(e)` は、`e` を Q16 のラジアンで計算し、`MUL` で `TURN = round(2^32 / 2π) = 683,565,276`、`s = 32` を掛けて Q16 の回転数にしてから `SIN` に渡す。
9. 決まらない場所はエラーにし、ファイル・式・行を示す: 数の定数がその Q 形式で int32 に入らない、`MUL` のシフト量が 62 を超える、`SHIFT` の量が ±31 を超える、など §6.1 が拒む命令を作る場所。黙って飽和させない。さらに、**Q0 の名前（規則 1）に、小数を含みうる値を与える式**（整数でない定数、Q0 でない名前、`sin`、割り算を含む）と、`REPEAT` の回数・`cubic` の分割数の定数が 1〜255 の外、`linePattern` の周期の定数が 1〜24 の外であることもエラーにする。整数の入力・引数は `@q 名前=0` と宣言する（DERBY の `turf` の `phase`: `green = 512 + phase * 288`）。
10. `@half 名前, ...` で宣言した名前への代入は `.H` の命令で計算する（各項は `sat16` される、§2.3）。`half` の名前の Q 形式も規則 1 で決める。

[shiki.md](shiki.md) §5.6: DERBY の `prail`・`pt` は、出荷している関数に `@q z=24, dz=24, pz=24`（`pt` は `farZ`・`fz0`・`fz` も）を足すだけで、この規則のもとで double との誤差が 0.05 px 未満（host）。

### 8.4 PIE に下ろせる `EACH`

v1.3 で PIE に下ろしてよいのは、次をすべて満たす `EACH` だけ。それ以外はスカラーで実行する。下ろしてもスカラーとビット単位で同じでなければならない（§2.3 の定義が PIE の動きそのもの。§10.2）。

1. **本体全体が列**: `EACH` と対応する `END` の間の命令が、`.H` の命令と、`i16` の領域の `k = 0` の `FETCH`・`PUT`（16 ビットのレーンにシフト命令が無いため）だけ。これらには実行時の失敗が無く、1 命令が 1 ステップなので、1 周のステップは `B + 1`（`B` は本体の命令の数、`+1` は `END`）に決まる。描画・32 ビットの命令・`LOOKUP`・制御の命令（`REPEAT`・`REPEAT_REG`・`BREAK_IF_GT`・入れ子の `EACH`）を含む本体は下ろさない。
2. **周回をまたぐ依存が無い**: 本体の中で書くレジスタは、同じ周回の中で先に書いてから読む（前の周回の値を読まない）。本体で書かないレジスタ（`INPUT` など、`EACH` の前に決まった値）は、`sat16` してから全レーンへ配る（§2.3 の被演算子の定義と同じ）。
3. **ステップが足りる**: `EACH` の命令を実行する前のステップ数を `s`、入るときに読んだ件数を `N` として、`(B + 1) · N + 1 ≤ 10,000 − s`。入るときに決められ、満たさなければ（途中で `LIMIT` になりうるので）スカラーで実行する。

下ろしたときの結果: 各レコードの書き込みはスカラーと同じ。実行後のレジスタはレコード `N − 1` のレーンの値（`N = 0` なら本体を実行しない）。ステップ数は `(B + 1) · N + 1` 増える。8 レーンで処理するとき、`N` が 8 の倍数でなければ末尾をマスクする。**`N` 番目以降のレコードと詰め物の値は変わらない**（§5.3 の 4、§5.1。旧値を読んで混ぜ、同じ値を書き戻すマスクは許す）。`N = R` でも `R` が 8 の倍数でなければマスクが要る。128 ビットのアクセスは `S` が 8 の倍数なので面の外へ出ない（§5.1）。`MUL.H` ごとに `QACC` を 0 にする（§2.3）。

本体の一部だけの列や、周回をまたぐ依存（累算）のある列を下ろすことは v2 の課題（§12）。

### 9.2 Shiki のヒープと寿命

- アプリは manifest で予算を宣言する: `shiki: {bytes: N}`。宣言しないアプリは既定の予算を使う。**既定の値は 48 KiB（49,152 B）**（2026-10-31 ユーザー決定。DERBY・MEGADEMO・BIG WAVE で Shiki の native 側が使う量の最大は実測で 41,916 B（BIG WAVE のタイトル画面）、[shiki.md](shiki.md) §4.5.1）。セッションの開始時に、N バイトの連続した区画を 1 つ確保する。確保できなければアプリを起動しない。**区画を取るのは manifest の capability（`required` か `optional`）に `kasane.shiki` を挙げたアプリだけ**で、挙げないアプリの空きは減らない（[shiki.md](shiki.md) §4.3。2026-10-31 の明確化）。
- フレーム・作業領域・式・データ領域は、すべてこの区画から取る。足りなければ、その呼び出しが `LIMIT_EXCEEDED` で失敗する。`shiki.heap()` は `{bytes, used, largest}` を返す。
- **窓の持ち方**: Shiki は、作った**窓（型付き配列のオブジェクト）**を強い参照で持つ（ArrayBuffer は窓を通して生きる）。したがって JS が窓を捨てても、ガベージコレクタは窓も ArrayBuffer も解放せず、`free_func` も呼ばれない。`release(窓)`・`register` の `options.data` の同一性は、この窓のオブジェクトで比べる（ArrayBuffer だけを持つと、捨てられた窓のアドレスが別のオブジェクトに再利用され、比べ方が成り立たない）。ArrayBuffer の `JSValue` も `data()` の時点で dup して簿記に持ち、detach はそれに対して行う（`JS_GetTypedArrayBuffer` は例外を投げうるので、終了の経路で呼ばない）。領域の寿命は JS の GC ではなく、次の明示的な操作だけで決まる。
- **領域の解放**: `shiki.release(窓)` で行う。窓は `shiki.data()` が返したオブジェクトそのもの（別の view は `INVALID_ARGUMENT`）、解放済みの窓は `CLOSED`。結び付いた handle が残っていれば `BUSY`。残っていなければ、Shiki は**窓を detach し（`free_func` がこの中で同期に呼ばれる）→ 自分の参照を捨てる → 簿記を更新 → 区画の中の領域を解放**の順に行う。`release` しない領域はセッションの終わりまで残り、`maxSessionDataRegions` と予算を使い続ける。
- **簿記**（領域ごとの、窓の参照・結び付いた handle の数）は区画の外、`.bss` の固定表（`maxSessionDataRegions` 個）に置く。
- `free_func` は何もしない。`data == NULL` でも呼ばれ、何度呼ばれてもよい（Shiki の detach の中、ゲストを壊すとき、`release` で参照を捨てた後の finalizer でも呼ばれる。`js_array_buffer_finalizer` は detach 済みかを見ずに呼ぶ）。解放は Shiki が別に行う。
- **終了**: `app_stop()` は、Shiki の handle とフレームを片付ける reset を今の位置（ゲストを壊す前）で行い、そこで全領域の窓を detach して参照を捨てる。**区画の解放はゲストを壊した後**（`pocketjs_guest_destroy()` の後）の別の呼び出しで行う。
- 常駐中断（common-api §5）の間は、区画を保つ（v1.2 で決定）。中断してよいかの空きの判定には、予算を含める。

### 9.3 データ領域の窓

- `shiki.data({type: 'i16' | 'u16' | 'i32', q, records, record})` は、Shiki のヒープ上に領域を作り、その窓（`Int16Array`・`Uint16Array`・`Int32Array`）を返す。中身は 0（詰め物も）。`records` は**レコードの数** `R`、`record` は `k_rec`（§5.1。未知の `type`、`q` が 0〜30 の外、`record` が 1〜8 の外、`records` が 1〜65,535 の外の整数でない値（丸めない。§2.4 の変換は入力と引数だけ）なら `INVALID_ARGUMENT`。**`length` という名前のプロパティがあれば、値によらず `INVALID_ARGUMENT`**（v1.3 の形。並びが変わったので、古い形の呼び出しを黙って通さない）。
- 領域は Shiki の区画から `k_rec · S · 要素の大きさ`（`i16`・`u16` は 2 B、`i32` は 4 B）バイトと割り当ての管理領域を取り、`heap().used` に含まれる（`R = 9` は 16 レコード分を取る）。
- **窓は領域全体**（長さ `k_rec · S`、詰め物を含む）。レコード `j` の欄 `c` は `窓[c · S + j]`。`S` は §5.1 の式で決まる（`S = Math.ceil(R / 8) * 8`）。
- `shiki.fields(窓)` は、欄ごとの view（窓と同じ型の型付き配列、長さ `R`、`c` 番目が欄 `c` の面）を `k_rec` 個の配列で返す。呼ぶたびに新しい view を作る（窓ごとに常に持つとゲストのヒープを使うため、要るときだけ作る）。view は窓と同じメモリを指すが、**同一性の比較（`register` の `options.data`、`release`）には使えない**（窓そのものを渡す。別の view と同じく `INVALID_ARGUMENT`）。`release` の後の view は長さ 0（ArrayBuffer が detach されるため）。窓が解放済みなら `CLOSED`、`data()` の窓でなければ `INVALID_ARGUMENT`。
- 同じ窓を 1 つの handle の `options.data` に 2 回渡してよく、結び付いた handle の数は handle ごとに 1 と数える（`release` の `BUSY` の判定は「この窓を使う handle が残っているか」）。
- 窓は外部メモリを指す ArrayBuffer で、伸びない（resizable ではない）。
- **要件: 外部メモリの ArrayBuffer の長さを変える経路は、外部メモリを realloc してはならない。** 対象は `transfer`・`transferToFixedLength`・`transferToImmutable`（QuickJS-ng ではどれも `js_array_buffer_transfer` で、長さが違えば `js_realloc` する。コードで確認）。`ArrayBuffer.prototype` は ROM の組み込み（`CONFIG_POCKET_VM_ROM_INTRINSICS`、既定 y）で、これらの属性は消せない（non-configurable）ので、メソッドを消す方法は取れない。実装は `js_array_buffer_transfer` に門を足す: **`free_func` が `js_array_buffer_free` でない ArrayBuffer への `transfer`・`transferToFixedLength`・`transferToImmutable` は、長さに関わらず（0・同じ・違う）`TypeError`**。門は `detached` の検査の直後、長さ 0 の分岐の前に置く（`js_array_buffer_transfer` は新しい長さが 0 のとき、長さを比べる前に `JS_DetachArrayBuffer` へ分岐するので、「長さが変わるなら」の門を realloc の直前に置くと `transfer(0)` がすり抜け、窓が detach されても Shiki の参照と結び付いた handle が残る）。同じ長さの `transfer` は外部メモリと `free_func` を新しい ArrayBuffer へ渡すので、これも拒む（Shiki の強い参照が古い ArrayBuffer を指したままになるため）。`resize` は今のコードが外部メモリを拒むので、門は要らない。

**`drawMany(handles, inputs, stride)`（v1.5）**: 複数の draw を 1 回の呼び出しで行う。

- 引数: `handles` は `Uint32Array`（Shiki の handle を描く順に）、`stride` は 1 回の draw の入力の数（0〜8 の整数）、`inputs` は `handles.length × stride` 個の要素を持つ `Float64Array` か `Int32Array`（draw `i` の入力は `inputs[i·stride .. i·stride + stride − 1]`）。`stride = 0` なら `inputs` は**読まず、検査もしない**（`null` でよい）。`subarray` などオフセットの付いた view でよく、同じ配列を別の呼び出しで使い回してよい。
- 意味: draw `i` は、`handles[i]` の式を、次の入力で実行する。`Float64Array` なら JS の数として §2.4 で変換する（`draw()` と同じ変換。有限でない値は §4.8 の 7 の誤り）。`Int32Array` なら、各値を **`handles[i]` の式が宣言した、その位置の入力の Q 形式の `fixed`** として読み、変換しない（同じ位置でも handle ごとに Q 形式が違いうる。換算は JS の責任）。式が宣言した入力より `stride` が大きければ残りは捨て、小さければ足りない分は 0（§4.8 の 7）。入力の変換と実行は、同じ入力で `draw()` を呼んだときと同じ。
- 読む時: draw `i` の handle と入力は、**draw `i` の始めに**読む。したがって `handles`・`inputs` がデータ領域の窓（またはその ArrayBuffer の上の view）なら、前の draw の `PUT` の書き込みが後の draw の handle と入力に映る。呼び出しの途中で JS は動かないので、配列の長さと detach の状態は始めに一度だけ検査する。
- 検査の順と誤り（どれも、どの draw も行わずに投げる）: `handles` が `Uint32Array` でない、`stride` が 0〜8 の整数でない → `INVALID_ARGUMENT`。`handles.length` が `maxDrawsPerCall` を超える → `LIMIT_EXCEEDED`。`stride ≥ 1` で `inputs` が `Float64Array`・`Int32Array` でない、長さが `handles.length × stride` でない、detach されている → `INVALID_ARGUMENT`。`handles.length = 0` なら何もせず戻る（`beginFrame` が無くても誤りにしない）。
- draw の誤り: draw `i` の誤りは、`draw()` と同じ `PocketError`（`code`・`operation` `"kasane.shiki.draw"`・`retryable`・`outcome`）に、**何番目の draw か（0 から）を読み取り専用の `index` プロパティで付けて**投げ、残りの draw は行わない（`index` は common-api §4 の、面が足すプロパティ）。`outcome` は失敗した draw 自身を指す。`handles[i]` が登録された Shiki の handle でない（0、別の種類の handle、2^31 以上を含む）なら `CLOSED`（`draw()` は範囲外の値を `INVALID_ARGUMENT` にするので、ここは `draw()` と違う）。フレームの扱いは `draw()` の失敗と同じで、そのフレームは捨てられる（前の draw の線分も）。前の draw がデータ領域に書いた値は残る（§5.3 の 3）。誤りがオブジェクトでない（ゲストのメモリが尽きた例外など）か、`index` を付けられなかった場合、`index` は無い。
- 割り込み: `drawMany` はネイティブの中で回り、その間はゲストの割り込みの検査（停止の要求、ターンの期限）が走らない。draw と draw の間でも確かめない（2026-11-01 ユーザー決定。draw ごとの確認の費用を払うほどの害が無いため）。したがって 1 回の呼び出しは、最悪で `maxDrawsPerCall`（256）回 × 1 回の draw の上限（最大 `maxSteps` のステップ、推定 3〜4.5 ms）＝**約 1 秒（推定、未測定）止められない**。起きるのは、停止（Back・外からの停止）への応答の遅れと、そのフレームの遅れ。止めるのは呼び出しが戻った後の、ゲストの次の割り込みの検査。
- 型付き配列にする理由（実測、[shiki-bundle.md](shiki-bundle.md) §3・§6）: JS からネイティブを 1 回呼ぶ費用は 約 1,200 サイクル、配列の要素の読み取りは 1 つ 約 400 サイクル。型付き配列ならポインタを 1 回取り、入力は 1 つずつのメモリの読み出しになる。入力 8 の draw は、1 回ずつ 19.5 µs、`Float64Array` で 7.7 µs、`Int32Array` で 2.5 µs。

**`sin(t)`・`cos(t)`・`sinMany(t, out, offset?)`（v1.5）**: `SIN` 命令（§4.4）を JS から使う。速さが要る三角関数を、JS の `Math.sin` ではなく Shiki の精度（Q16）で計算するため（2026-11-01 ユーザー決定: `Math.sin` は遅くても正確なまま、速さの要るものは Shiki）。

- 角度 `t` は**回転数の Q16 の整数**（1 回転 = 65,536。下位 16 ビットだけが効くので、int32 のどの値も一周の中に入る）、結果は **Q16 の整数**（−65,536〜65,536）。`sin(t)` は `SIN` 命令に `r = t` を与えた値と同じ（ビット単位）。`cos(t)` は `sin(t + 16,384)`（和は 2^32 で折り返す。下位 16 ビットだけが効くので結果は一意）。
- **整数だけを受ける**: `t` は −2^31〜2^31 − 1 の整数の値を持つ数（JS の整数。整数の値を持つ倍精度も受ける）。小数・範囲外・数でない値は、丸めずに `INVALID_ARGUMENT`。倍精度を作らず読まず、整数で返す（S3 には倍精度の演算器が無い）。
- `sinMany(t, out, offset)`: `t`・`out` は同じ長さの `Int32Array`（同じ配列でもよい）、`offset` は int32 の整数（省略すると 0）。`out[i] = sin(t[i] + offset)`（和は 2^32 で折り返す）を `i` の昇順に書く（同じ配列なら、`t[i]` は書く前に読む）。形が違えば、何も書かずに `INVALID_ARGUMENT`。`offset = 16,384` で `cos`。位相をずらした複数の値（脚の位相など）を 1 回で求めるため。

## 10. 検証の要件

1. **参照実装**: host（Node）の参照実装を 1 つ持ち、Shiki エンジンの C と、全命令・全状態でビット単位で一致しなければならない。出発点は `tools/kasane_ir/q16_error.mjs` の `fix`（§2.2・§2.4・§4.4・§4.5（範囲の判定を含む）・§8.3（規則 1 の伝播と規則 9 のエラーを含む）を実装済み。`EACH` 系・`.H`・`CUBIC`・`LINE_PATTERN` は未実装。`CUBIC`・`LINE_PATTERN` の手順は §4.6・§4.7 で、実装は §11 の 1 の続き）。
   - **データ領域（v1.3、並びは v1.4）**: 突き合わせの `CASE` 行は、領域ごとの（型・Q 形式・`k_rec`・中身）を持ち、結果の行は実行後の全領域の中身を含む。書式は CASE 行と結果の行で同じ（v1.4）: 領域ごとに `<型> <Q> <k_rec> <R>` の後、**中身の `k_rec · R` 個の値を欄ごとに**（欄 0 のレコード 0〜`R − 1`、欄 1 の …）、`i16`・`i32` は符号付き、`u16` は符号無しの 10 進で並べる（ハッシュにはしない）。結果の行は `<R>` と値だけ。v1.3 の行は 4 番目が要素の数 `n` だったので、`k_rec ≥ 2` の v1.3 の行は v1.4 のパーサでは値が足りず不正な行になる（`k_rec = 1` は並びも数も同じ）。`k_rec` が 1〜8 の外、`R` が 1〜65,535 の外、値が型の範囲の外は不正な領域（`shiki.data()` が断る形）で、その CASE は `REJECT`。`ALIAS j` の領域は、結果の行でも `j` と同じ中身を自分の番号で並べる。**詰め物は並べず、不変を別に確かめる**: 実行器は実行の前に詰め物を決まった値で埋め、実行の後に変わっていれば結果の行の末尾に ` PADDING` を足す（参照実装は詰め物を持たないので出さず、食い違いとして検出される）。今の文字の契約（`shiki_ref.mjs` の `format()` ＝ `ksn_shiki_result()`）は領域を出さないので、広げる。生成器は少なくとも次を含む: `EACH`（`aux` の両方、`N` = レコードの数。`aux = 1` で `N = 0`・範囲外）、`FETCH`・`PUT`（`u16` の 32768 以上、`i16` の負、`k` の正負、飽和）、`LOOKUP`（負の添字、`R − 1` を超える添字、`g = 0`・`31`。`R` が 8 の倍数でない領域を含む）、`BREAK_IF_GT` で抜けた `EACH`、途中で `LIMIT` になったときの書き込み済みのレコード、`R` が 8 の倍数でない領域と `aux = 1` で `N < R`（`N` が 8 の倍数でない）の `EACH`。
2. **PIE**: PIE へ下ろした列は、同じ入力でスカラーの経路とビット単位で一致しなければならない（`N` が 8 の倍数でない件数、§8.4 の 3 の境界の件数を含む）。`.H` の各命令について、`QACC`＋`SRCMB` の丸めと飽和が §2.3 の定義どおりであることを**実機で**確かめる（境界の値: ±2^15、積の符号、`s` = 0・15・31）。
3. **捕獲した入力**: DERBY・MEGADEMO・BIG WAVE の捕獲した入力（データ領域の中身を含む）とランダムな入力で、参照実装と C が一致すること、および double で計算した意図の座標との誤差を記録すること（[shiki.md](shiki.md) §5.5 の形）。
4. **寿命**: 外部メモリの窓に対して `transfer`・`transferToFixedLength`・`transferToImmutable`（長さ 0・同じ・違う）と `resize` が `TypeError` になり、区画が realloc されないこと。`release`・`unregister`・`app_stop()` のあらゆる順序で、解放が 1 回だけ起き、解放後の区画に触らないこと（ASan の host 試験）。
5. **`drawMany`（v1.5）**: `Float64Array` の結果（線分・データ領域の書き込み・誤りとその `index`）が、同じ入力で `draw()` を順に呼んだときと一致すること。`Int32Array` の結果が、§2.4 の変換の結果を `Float64Array` で渡した場合と一致すること（直値ではなく、変換と比べる）。引数の誤りでは draw を 1 つも行わないこと。登録されていない handle（範囲外の値を含む）が `CLOSED` になること。`inputs` がデータ領域の窓で、前の draw の `PUT` が後の draw の入力に映ること。**実機で**、最悪の draw（`maxSteps`）の時間と、`drawMany` 1 回（256 回）の最悪の時間を測ること（止められない時間の推定 約 1 秒を確かめる）。`sin`・`cos`・`sinMany` が、同じ角度で `SIN` 命令と一致すること（int32 の両端、四分の一回転の境目、負の角度を含む）、小数・範囲外を拒むこと。
6. **実機**: 実機でしか起きない不具合（評価中の `null`、strict aliasing など）がこのプロジェクトにはあるので、host だけで済んだことにしない。

## 11. 旧 API からの移行
