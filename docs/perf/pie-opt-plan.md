# PIE カーネル化: モチベーションと対象の絞り込み（`perf/pie-opt`）

このブランチ（`perf/pie-opt`、親 `vm/main` = `bd0fa43`）で、残っている重い描画パスを**per-pixel ごとベクタ化する**。
この文書は「なぜ今それをやるのか」と「どこから手を付けるか」を、既に記録されている実測だけで決めるためのもの。
**実機は別セッションが使っているため、このブランチの作業はホスト側の4層で閉じる**（§4）。実機の数字はここでは主張しない。

親を `vm/main` にした理由: 最新の PIE ツール（`tools/pie/` の `fuse_pixels.py` の厳密パース、`test_piesim.py`）、
PIE の知識（`docs/perf/pie-simd.md`、`docs/perf/backlog.md`）、canopy カーネルとその計器、パネル転送の非同期化、
装飾光線の4列グループ化が、この系列に揃っている。
`vm/design-contracts` にある SPLIT3（`rays` / `vegetation` / `dissolve` のブラケット）はここには無い。
**実機 A/B を取る段になったら、先にそれをマージするか摘み込むこと**（§4 の最後）。

## 1. モチベーション

### 1.1 予算に対して、残りがまだ偏っている

FLOWER（MODE 3）のフレームは、転送の非同期化（`send` 7.77 → 1.46 ms）、門番の unsigned 化（`rays` −1.46 ms）、
装飾光線の4列グループ化（`rays` −5.0 ms）を経て **39.2 ms / 25.5 fps → 32.2 ms / 31.0 fps**（`garden.c:1540-1547` の実測記録）。
30 fps の予算は 33.3 ms なので、**余裕は 1 ms 程度しかない**。内訳（記録済みの実測、`flower-perf.md` §1〜§2.1）:

| 項目 | 実測 (ms/frame) | 中身 |
|---|---:|---|
| `ray` = `total − garden` | 15.2–15.4 | `flower.c` の `ray_row` ほぼ全部（`shade` 5.33 / `bell` 4.41 / `span` 14.05 を含む） |
| `garden` | 20.3–22.0 | うち `pixels` 6.13（**PIE 済**）、`decor` 14.1–15.9 |
| ├ `rays`（装飾光線） | 7.6–13.7（**4列化後は約 −5 ms**） | スカラー。命令数の床 3.9 ms の**約2.4倍** |
| ├ `vegetation`（林冠＋幹＋草） | 5.0–5.9 | 林冠は PIE 化済（−0.71 ms）、幹・草・dissolve はスカラー |
| └ `rest` | 0.24–0.36 | 行の足場 |
| `hud` | 1.24–1.42 | `ovl` を含む |
| `send` | 1.46 | SPI の物理下限（非同期化済） |

`sqrtf` は 4,051–4,113 calls/フレーム = **2.14–2.23 ms**（実測、§3.2 の単価 174–188 cy × 本数）。

### 1.2 命令数を削る手は、この2つのパスではもう効かない

同一バイナリ A/B で測って、**3回続けてノーゲイン**だった（`pie-simd.md` §4.6）:

| 変更 | 性質 | 結果 |
|---|---|---|
| 装飾光線のプロファイル評価を 35.6% 削減 | 命令数 | **差なし**（rays −0.19、対照 veg −0.09 ms） |
| 固定小数点 sqrt | 命令数 | **差なし** |
| canopy 初期 PIE カーネル | 命令数 | **差なし**（decor −0.42、対照 veg −0.75 のノイズ内） |

理由も測れている: **スカラー行コードは命令数の床の約 2.4 倍かかる**（`rays` 床 3.9 ms に対し実測 7.6–13.7 ms、
`vegetation` 床 2.4 ms に対し 5.0–5.9 ms）。per-pixel の費用は算術ではなく **load/store・分岐・パイプライン** 側にある。
`ray`（`flower.c`）も同じで、`shade` は 677–689 cy/hit = **1.3 cy/命令**と既に床に張り付いており、
残りは `bell_hit` の6帯× (判別式＋平方根＋除算2本) を **外れる visit にも全部払っている**ことにある
（visits 6,793–7,038 に対し hits 1,867–1,888 = **約73%が外れ**）。

**したがって: per-pixel のパイプラインごとベクタ化する（= PIE 化する）以外に、この2つを動かす手は無い。**
これが既存文書の結論であり、このブランチの仕事。

### 1.3 「正確さ」も動機のうち

4列グループ化は `-5.0 ms` を買ったが**近似**で、**13.6% の画素が動く**（`garden.c:1540-1547`）。
厳密なベクタカーネルなら、同じ規模を**画素を動かさずに**取れる見込みがある（`pie-simd.md` §5.1 の「原則ビット一致」に戻せる）。
既存の PIE カーネルはこの原則で書かれている（海面だけが例外で、許容範囲をテストに書いてある）。

### 1.4 使う知識（事前調査の出所）

- このリポジトリ: `docs/perf/pie-simd.md`（PIE の性質・コストモデル・スカラーの値段・測定方法）、`docs/perf/backlog.md`、
  `tools/pie/README.md`（3層の検証ツール）。
- 姉妹リポジトリ [esp32s3-hw-mcp](https://github.com/dj-oyu/esp32s3-hw-mcp): TRM からの一次情報（命令語、パイプライン段、
  アセンブラ照合、実機で測った命令の意味）。効く制約だけ挙げる:
  **128bit アクセスは下位4bitを黙って0にする**（整列違反は例外にならない）、**16bit レーンのシフト命令は無い**（SAR を固定して
  `EE.VMUL` の定数乗算で表す）、**索引ロードは `EE.LDXQ.32` の1命令1レーン**、**`EE.VST.128.IP` だけ +0.6 サイクル**、
  **intrinsics は無くすべてインライン asm**、**PIE はコプロセッサ3 なので ISR では使えない**。
  ローカルには `xtensa-esp32s3-elf-gcc` が入っているので、実機無しでコンパイル・`objdump` まで確認できる。

## 2. 対象の絞り込み

「実測コスト」「ベクタの形があるか」「ローカルで証明できるか」の3つで切った。

| # | 対象 | 実測 | 形 | 判定 |
|---|---|---|---|---|
| **T1** | `bell_hit` の**帯棄却**をベクタ化（`flower.c:1266-1400`） | `bell` 4.41 ms/frame、visits の約73%が外れ | `o[j]=dx*oax[j]+ob[j]` なので `b,c,判別式` は **x の多項式**。8画素分を固定小数点で一括計算し、`d<0` が確定した画素をスカラー経路に入れない。**`flower.c:1287-1291` のコメントがこの案をそのまま書いている** | **やる（第一）** |
| **T2** | 装飾光線（`rays`）の**厳密な**ベクタカーネル（`garden.c:1504-1569`） | スカラーで −5.0 ms 済（近似）。床 3.9 ms | 8画素ブロック。行の load → dither をレーン化（x ごとのパターンを表から `EE.VLD.128` 1本）→ Q8 の profile/mix を 16bit レーンで → mask 付き store（「書かない」を「選んで書く」へ） | **やる（第二）** |

| — | `shade`（`flower.c:902-991`） | 677–689 cy/hit = **1.3 cy/命令** | 素材別分岐でベクタの形が無い | やらない（既に床） |
| — | テキストのマスク合成 | 上流 PocketJS の Rust 側（`backends/rgb565/src/lib.rs:715-745`） | `scale=1` ではグリフ窓が 6–12px で 16px ブロックが成立しない | 対象外（PIE 不成立と判明済み。除算を加算にする側は上流待ち） |

**絞り込みの結果**: T1・T2・T3 の3本。T1 が最大（`bell` 4.41 ms の大半＋`ray` 15.2 ms の外れ側）、
T2 は近似を返上できる（正しさが動機）、T3 は比が最大で**純算術なのでローカルで全数証明できる**。
T4 は効果の見積もりに根拠があるが、T1〜T3 の後（1シーンの1関数にしか効かない）。

## 3. 書く順と、各カーネルの設計メモ

### T1 `bell` 帯棄却（第一）

- 形: 行の8画素分について、6帯それぞれの `b`・`c`・判別式 `d=b*b−a*c` を固定小数点で計算し、
  **全帯で `d<0` が確定した画素だけ**落とす。`a` は (部品,帯) ごとの定数（`p->bell_a[]`）なので、ベクタ側は `b` と `c` の
  2次式（`x` の多項式）を作れば足りる。QACC（8レーン×40bit）は `EE.VMULAS` 系の積和にそのまま乗る。
- 保守性: `d≈0` の近傍は**必ずスカラーへ残す**（マスクを広めに取る）。契約は「落とした画素の輪郭・depth は
  参照実装と一致」で、`test_kernels.py` の全画素比較に落とす。レンジは `run_models.py` に総当たりで入れる。
- 危険: 固定小数点の丸めで `d` の符号をまたぐ画素が1つでも出ればシルエットが1画素変わる。
  §5 の「表現についての主張は総当たりで決着する」に従い、**丸めを含めた式の等価性をモデルで証明**してからアセンブリを書く。
- 期待: `bell` の外れ側（visits の約73%）から 6帯×(判別式＋平方根＋除算2本) が消える。実機の数字は入るまで書かない。

### T2 装飾光線の厳密カーネル（第二）

- 形: 8画素ブロックで、行の load（`EE.VLD.128.IP`）→ dither をレーンで取る → profile と mix を 16bit レーンで →
  **mask 付き store**。`dither` は x ごとの周期パターンなので、事前に 16 バイト整列した表を作れば `EE.VLD.128` 1本。
- 壁（`backlog.md` が明文化しているもの）: 32bit 中間値の扱い、被覆の外で「書かない」を「マスクして書く」へ変えること、
  dither のレーン化。**「書かない」を選んで書くに変えるのが近似を返上する鍵**（値は合っているが書かない画素、を作らない）。
- 期待: 現状は近似で −5 ms。厳密版で同程度〜やや劣る程度に収まり、13.6% の画素が戻るのが主眼。

### T3 MP3 FIR（第三）

- 形: 32 タップの畳み込み。リングバッファを2倍長にして、窓が連続 16 バイト格子に乗るようにする
  （`history[]` の書き込みを2箇所にする）。`EE.VMULAS.S16.QACC` ×4 ブロック → `EE.SRS.ACCX` で `sum>>14`。
- 契約: **ビット一致**（`sum/16384` → `sum>>14` の変更は負の端数で1LSB変わるだけなので、C 側も `>>14` に揃える）。
- ローカル検証が最も綺麗に閉じる（入力全域の総当たり＋ASA N レベルのランダム波形で参照実装と比較）。

## 4. 検証はホストの4層で閉じる（実機は使わない）

`tools/pie/README.md` の3層に、実コンパイラを足した4層。すべて今のホストで動くことを確認済み（2026-09-15）。

| 層 | 何を守るか | コマンド |
|---|---|---|
| 1. 算術 | 「その式は正しいか」— 式・表・丸めの全域証明 | `python3 tools/pie/run_models.py`（`models/*.c` を追加。現在 green） |
| 2. 意味 | 「アセンブリはその式か」— レーン・定数順・ポインタ・マスク | `python3 tools/pie/test_kernels.py`（`piesim.py` で命令レベル実行しスカラー参照と全画素比較。現在 7 tests green） |
| 3. 並び | 「その並びは速いか」— def=2 の直後使用、本体 256B | `python3 tools/pie/stalls.py <file> <kernel>`（0 ストールになるまで往復） |
| 4. 実物 | 実コンパイラで通ること・`loopgtz` の本体・レジスタ割当（`kp`/`k` 別、early-clobber `=&a`） | `xtensa-esp32s3-elf-gcc` でコンパイル → `objdump -d`（ホストに入っている） |

規約（`pie-simd.md` §6.1・§8）:
- **スカラー参照実装を先に書き、`__attribute__((unused))` でソースに残す**（アセンブリの唯一の説明になる）。
- **最適化には必ずスイッチ**（実行時変数が最も安全）。**最適化とその計測を同じコミットに入れない**。
- 1カーネル = 1コミット。テストは同じコミットに入れる（テストは計測ではない）。

**このブランチでは実機の数字を主張しない。** 実機 A/B は、`vm/design-contracts` の SPLIT3 ブラケット
（`garden_prof_rays` / `garden_prof_vegetation`）と `SCENE_AB` の窓反転を持ってきたうえで、
1本のツリー・1個の define・同一バイナリで取る（§6.2・§6.3）。用意だけしておき、実行はデバイスが空いてから。

## 5. 実装前の追加調査（同日）: T1 の形を実測記録から引き直した

アセンブリを書く前に `bell_hit`（`flower.c:1114-1200`）を読み直して、T1 の機構を修正した。**結論は「T1 は依然として最大、
ただし狙う場所が違う」**。

1. **帯ループに軸方向の事前棄却は無い。** `for(band=0..5)` は `lo`/`hi`/`slope`/`offset` を読んだあと、
   すぐ `r`・`b`・`c`・判別式（約9〜12 浮動小数演算）を計算する。`lo <= o[1]+d[1]*z <= hi` の判定は
   **roots を出した後**（`v`）にしか無いので、「軸範囲に入らない帯を安く捨てる」余地はもう使われている。
   plan の当初案（軸の区間で帯を絞る）は成立しない。
2. **どの帯が当たるかは判別式でしか分からない。** 円錐は凸なので、当たる光線は `t` の1区間だけを通り、
   その区間に重なる帯は連続した1〜3本になる。しかしその区間の端点は2次方程式の根そのもの
   （＝平方根。§3.2 で 174〜188 cy）。**帯の索引を式で出す道は無い。**
3. **帯の歩行の浪費は、上限が決まる。** `bell_reject`（円筒）が visit の 43.6% を先に落とす。
   残り 56% のうち当たるのは全体の 27% なので、**「6帯を歩いて全部外れる」visit は約 29%**
   （= 0.52 × 0.56）。`bell` の非平方根部分は約 2.5 ms（4.41 ms − `bell:sqrt` 1.9 ms）なので、
   **「全部外れの帯歩行を消す」だけの上限は約 0.7 ms**。ここが T1 の下側の見積もり。
4. **上側はベクタ前段そのもの**。6帯×8画素の判別式（スカラーで約 60 演算/画素）を、
   8画素分まとめて固定小数点の PIE で計算できれば、当たる visit にも効く。上限は約 1.8 ms。
   T1 の値打ちは 0.7〜1.8 ms で、これは依然このブランチで最大（T2 の混合のベクタ化 1〜2 ms、
   T3 の FIR 1.36 ms と同規模かやや上）。
5. **T4（`sqrtf`）は保留のまま**。`flower` には `sqrtf` が 4,051〜4,113 回/フレーム = **2.14〜2.23 ms**
   あり、`bell:sqrt`（1.17〜1.19 ms）＋楕円体側（1.00〜1.02 ms）で、**名前の付いた最大の項**。
   ただし ISA が定める種＋反復の列をそのまま書く必要があり、**このホストに Xtensa ISA リファレンスが無い**
   （TRM は PIE しか載せていない）。列を推測で書くとビット一致が黙って壊れるので、参照が手に入るまで着手しない。

**順序は変えない（T1 → T2 → T3）**が、T1 の最初の成果物は**アセンブリではなく、保守性の証明**にする:
`tools/pie/models/bell_reject_model.c` に、到達可能な幾何（種・位相・行から実際に生成される `o` と `d`）で
(a) 判別式の大きさの分布（Q 形式を決める）、(b) 固定小数点の丸め込みで `disc<0` が確定した画素を落としてよい条件
（誤差予算）、(c) それで何 % の画素が落ちるか、を出す。**ここで安全が言えなければ PIE 前段は書かない**
（§4 の1層目。`run_models.py` から走る形にする）。これが通ってから 8 レーンのアセンブリに入る。


## 6. 代数的な見直し（同日）: 式を畳んで命令を減らせる場所

命令の並べ替えではなく**式そのもの**を見直した結果。数値は既存の実測（§1.1）と上で数えた命令数から。

| # | 対象 | 代数 | 削れる量 | 正確さ |
|---|---|---|---|---|
| A1 | FIR の窓読み（T3） | 窓はタップごとに2バイト下がる。16バイト整列ブロックは**8タップごとに同じ3枚**なので、窓は「整列2枚＋`EE.SRC.Q`のバイトシフト」で作れ、各タップで必要なのは `wsr.sar`（シフト量は8通り、レジスタに入る）＋`src.q`＋`vldbc`＋`vmulas` の**4命令**。いまは6命令（2ロード＋src＋vldbc＋vmulas＋addi×2） | 28.4 → **約17命令/出力**（スカラー284比 1/17） | **ビット一致**（シフトはバイト単位で厳密） |
| A2 | FIR の対称畳み込み | `h[i]=h[31-i]`（sinc×Blackman が 15.5 対称）なので `Σh[k]·x[t-k]` は16項に畳める。**ただしPIEでは損**: 畳んだ和は17bit必要で `EE.VADDS` は飽和する（窓の68〜72%で飽和すると §1.4 に実測がある）。しかも各ペアの窓は別アドレスでロードが2倍必要 | 使えない | — |
| A3 | FIR の MAC 数 | 8出力×32タップ=256 MAC、8レーンで **32 VMULAS/ブロック**。これは既に最小 | 0 | — |
| A4 | `bell_hit` の判別式（T1） | `disc_k = b_k²-a_k c_k` を `b_k=b0-r_k dr_k`、`c_k=c0-r_k²` で展開すると `disc_k = P + Q_k r_k² + R r_k` になる。**ただしこれは得しない**: ルートは `z=(-b_k±√disc_k)/a_k` で、`b_k` は根の計算にそのまま要る（`a≈0` の早期分岐も `b` を使う）。`b` を消せないので `P` は `a_k c0`（1乗算）＋ `R` は `nb0·dr_k`（1乗算）＋ `Q_k` の配列追加、と数えると**バンドあたり7命令で現状と同じか微増**、しかも丸め順が変わる | **±0**（ゲインなし。当初の 9→6 は `b` が不要という誤った前提だった） | — |
| A5 | 楕円体の判別式 | `b` は x の1次、`c` は2次なので `disc(x)` は **x の2次**。1行1部品につき2次の係数3本を出せば、当たる x 区間を解の公式で先に絞れる（画素ごとの判別式 5,741 回 → 頂点＋端点の3評価） | 理論上は画素テストが消えるが、実測の上限は **約0.2 ms**（§5のP3。落ちるのは最安の画素） | 既に「順序は最後」と判断済み。代数はその判断を裏付ける（記録として残す） |
| A6 | 装飾光線の混合（T2） | 式を読んで確認（`garden_decor_mix`）。`r` は **厳密にアフィン**: `(light*(r+6))>>1 = (light*r)>>1 + 3*light`（`6*light` は偶数なので分解できる）で、`r*E + (light*r)>>1 = (r*(2E+light))>>1` も厳密（`2E*r` が偶数）。よって `r_out = (((r*M)>>1) + N)>>8`、`M=2E+light`（全チャネル共有）、`N=3*light+d`。**`g`・`b` は厳密には畳めない**: シフトが2で加数 `10*light`/`4*light` が4の倍数でないため `floor((a+b)/4)` が下位2ビットに依存する（`(a>>2)+((a&3)+b)>>2` の補正項が要る） | 画素あたり 7命令 → **4命令**（M,N を画素で1回作る）。g/b を近似で通すなら同時に | **r は厳密、g/b は近似**（補正項を落とす＝最下位ビットが違う）。120フレームの移動画素数をホストで測る（`tools/flower_decor_identity.c` の形） |
| A7 | 装飾光線のプロファイル（群共有） | 4列共有は「x だけの関数を4画素に1回」という近似。プロファイルが多項式（`garden_smooth`＋逆数）で書けるなら、**固定小数点の多項式評価**に置き換えて厳密にできる可能性がある | 未計測（式の形を確認していない） | 要調査。T2 の副産物として見る |

**T1 の位置づけがここで少し変わる**: バンド判別式のベクタ前段（8画素まとめて）は依然として最大の狙いだが、
A4 は**コードを読んで否定された**: 判別式を畳んでも `b_k` は根の計算に必要なので消えず、
バンドあたりの命令数は横ばい（`Q_k` の配列が増えるだけ）。よって T1 で残る手はベクタ前段
（8画素まとめて判別式を出し「全部外れ」の visit を落とす）だけで、これが**4例連続で
スカラー折り畳みが効かない**という結論に並ぶ。次は A6（T2 の混合のアフィン化）だが、
そこも 120 フレームの移動画素数をホストで測る必要がある（`tools/flower_decor_identity.c` の形）。

## 8. リング長の規則（呼び出し側の A/B で判明）

8出力をまとめて書くので、リングは「そのブロックが書く範囲」と「まだ読む範囲」が
重ならない長さが要る。書きの最大は block_start+7、読みの最小は block_start-31 なので
R >= 39。さらに位相（ブロック開始が常に8の倍数＝窓が16B整列）のため R は8の倍数 →
**R = FIR_TAPS + FIR_LANES = 40 スロット**（2倍コピーで 80 int16）。

R=32（窓の長さと同じ）だと、out(t) が31歩前として読むはずのサンプルを、同じブロックの
s(t+1)…s(t+7) が上書きする。タップ k=31..25 の7本が未来のサンプルを読み、出力が ±1 ずれる
（滑らかな波形では近い値になるので、大きな破綻ではなく1LSBのずれとして現れる）。

検証（呼び出し側, ホスト）:
- 実フレームでブロック経路とスカラー経路を A/B（48 kHz 2ファイル、合計 437,760 サンプル）→ 差 0。
  tools/test_mp3.c が両アームを回して全サンプルを比較、tools/host_fir_stub.c が asm の代役で
  16B整列も assert する。
- 落とし穴: R が2の冪でなくなったのでスカラーの読みは `(cursor + R - k) % R`。`cursor - k` は
  unsigned で桁溢れし、参照側だけが 45% のサンプルで ±1 ずれる（検証用の参照も壊れうる）。

層4: fir8_pie は非 static になったので単体で xtensa-esp32s3-elf-gcc -O2 -Wall -Wextra -Werror が通り、
objdump に PIE 命令が出る（呼び出しを付けた検査は不要になった）。

## 9. グループ幅（T2 の前処理、着手）

装飾ループの前処理（プロファイル2本・gain・dither）はグループ幅で割られるので、
4画素グループでは約8.5命令/画素、8なら4.3。mix 本体（21命令/画素）と同程度の塊なので、
ここが一番安い削りしろ。`g_garden_decor_group` を実行時スイッチにした（既定は暫定4）。

- group8 でテストが中断した原因は**不変条件の違反**だった（クラッシュではない）。
  `tools/test_garden_decor.c:65` は「中心から `half/2-6` 以内＝ビームの芯は装飾に触られない」を
  256フレーム分検査している。グループは開始列のプロファイルを全画素に使うので、芯に跨る
  グループができると芯が外側の値で照らされる。→ **グループを芯の手前で切る**（`center-(half/2-6)`
  でクリップ）ことで、幅によらず不変条件を厳密に保てるようになった。既定は 8。
- 8にするときの代償はプロファイルを8画素で1回評価すること（x 誤差が2倍＝バンディング方向）。
  実機で見て悪ければ 6 → 4 に撤退。

## 10. A6 のカーネル（T2 の混合、着地。未結線）

`garden_decor_mix8`（`main/scene/garden_decor_pie.c` / `.h`）。8画素1ブロック、グループ定数
`light`/`shadow`/`d` は引数のまま。呼び出し側の結線は**次のコミット**（今は誰も呼ばない＝挙動不変）。

式（A6 の表をそのまま実装した）:

- `r_out = (r*Mr + Kr)>>9`、`Mr = 2E+light`、`Kr = 6*light+2*d`（`E = 256-(shadow>>3)`）。厳密。
- `g_out = (g*Mg + Kg)>>10`、`Mg = 4E+light`、`Kg = 4*((10*light)>>2)+4*d`。
- `b_out = (b*Mg + Kb)>>10`、`Kb = 4*((4*light)>>2)+4*d`。
- フィールド抽出は `EE.VMUL.U16` の SAR=16 をシフトとして使う（`p*32>>16 = p>>11` はマスク不要、
  `p*2048>>16` を `&63`、`b = p&31`）。本文は `EE.MOV.U16.QACC`（定数プリロード）→
  `EE.VMULAS.U16.QACC` → `EE.SRCMB.S16.QACC`（>>9 / >>10）→ `EE.VMIN.S16`（クランプ）。
  定数は**シフトの前**に足す必要がある（後から足すと厳密性が落ちる）ので、加算は積算器のプリロード。

近似の大きさ（`tools/pie/models/garden_model.c` の `sweep_decor`、light・shadow・d を 0..255 ずつ動かした
立方体＝シーンの到達域の上位集合。dither が作れるのは 32/96/160/224 の4値だけ）:

| チャネル | スカラーの式との差 | 備考 |
|---|---|---|
| r | **0**（536,870,912 ケース中 0 件） | 3段の等式がそれぞれ厳密 |
| g | 0.098% のケースで 1 段（63段階中） | `10*light` の補正を**落とさず別に floor** した分。落とすと最大 2.5 段暗くなる |
| b | **0** | `4*light` は4の倍数なので補正が厳密に分解できる |

範囲: 積 1279、加数 3568、最長の積算 = 82,617（2^40 の余裕 23bit）、SRCMB 読み出しの山 80
（16bit 飽和に遠い）。畳んだフィールドは 31/63/31 に収まる＝pack の OR がスカラーの `|` と一致。

## 11. A6 の結線（T2 の混合、稼働。既定はカーネル）

`g_garden_decor_pie`（`garden.c` に定義、`garden.h` に extern、既定 1）。0 は `garden_decor_mix` の

呼び出し側（`garden_decor_row`）:

  `row+x` が**16バイト整列**のときだけ `garden_decor_mix8(row+x,light,shadow,d)` を1回呼ぶ。
  それ以外（クリップされた端、尾、整列しないグループ）は今までどおり1画素ずつスカラー。
