# PIE カーネル化: モチベーションと対象の絞り込み（`perf/pie-opt`）

このブランチ（`perf/pie-opt`、親 `vm/main` = `bd0fa43`）で、残っている重い描画パスを**per-pixel ごとベクタ化する**。
この文書は「なぜ今それをやるのか」と「どこから手を付けるか」を、既に記録されている実測だけで決めるためのもの。
**実機は別セッションが使っているため、このブランチの作業はホスト側の4層で閉じる**（§4）。実機の数字はここでは主張しない。

親を `vm/main` にした理由: 最新の PIE ツール（`tools/pie/` の `fuse_pixels.py` の厳密パース、`test_piesim.py`）、
PIE の知識（`docs/perf/pie-simd.md`、`docs/perf/backlog.md`）、canopy カーネルとその計器、パネル転送の非同期化、
装飾光線の4列グループ化が、この系列に揃っている。
`vm/design-contracts` にある SPLIT3（`rays` / `vegetation` / `dissolve` のブラケット）はここには無い。
**実機 A/B を取る段になったら、先にそれをマージするか摘み込むこと**（§4 の最後）。

## 1. モチベーション

### 1.1 予算に対して、残りがまだ偏っている

FLOWER（MODE 3）のフレームは、転送の非同期化（`send` 7.77 → 1.46 ms）、門番の unsigned 化（`rays` −1.46 ms）、
装飾光線の4列グループ化（`rays` −5.0 ms）を経て **39.2 ms / 25.5 fps → 32.2 ms / 31.0 fps**（`garden.c:1540-1547` の実測記録）。
30 fps の予算は 33.3 ms なので、**余裕は 1 ms 程度しかない**。内訳（記録済みの実測、`flower-perf.md` §1〜§2.1）:

| 項目 | 実測 (ms/frame) | 中身 |
|---|---:|---|
| `ray` = `total − garden` | 15.2–15.4 | `flower.c` の `ray_row` ほぼ全部（`shade` 5.33 / `bell` 4.41 / `span` 14.05 を含む） |
| `garden` | 20.3–22.0 | うち `pixels` 6.13（**PIE 済**）、`decor` 14.1–15.9 |
| ├ `rays`（装飾光線） | 7.6–13.7（**4列化後は約 −5 ms**） | スカラー。命令数の床 3.9 ms の**約2.4倍** |
| ├ `vegetation`（林冠＋幹＋草） | 5.0–5.9 | 林冠は PIE 化済（−0.71 ms）、幹・草・dissolve はスカラー |
| └ `rest` | 0.24–0.36 | 行の足場 |
| `hud` | 1.24–1.42 | `ovl` を含む |
| `send` | 1.46 | SPI の物理下限（非同期化済） |

`sqrtf` は 4,051–4,113 calls/フレーム = **2.14–2.23 ms**（実測、§3.2 の単価 174–188 cy × 本数）。

### 1.2 命令数を削る手は、この2つのパスではもう効かない

同一バイナリ A/B で測って、**3回続けてノーゲイン**だった（`pie-simd.md` §4.6）:

| 変更 | 性質 | 結果 |
|---|---|---|
| 装飾光線のプロファイル評価を 35.6% 削減 | 命令数 | **差なし**（rays −0.19、対照 veg −0.09 ms） |
| 固定小数点 sqrt | 命令数 | **差なし** |
| canopy 初期 PIE カーネル | 命令数 | **差なし**（decor −0.42、対照 veg −0.75 のノイズ内） |

理由も測れている: **スカラー行コードは命令数の床の約 2.4 倍かかる**（`rays` 床 3.9 ms に対し実測 7.6–13.7 ms、
`vegetation` 床 2.4 ms に対し 5.0–5.9 ms）。per-pixel の費用は算術ではなく **load/store・分岐・パイプライン** 側にある。
`ray`（`flower.c`）も同じで、`shade` は 677–689 cy/hit = **1.3 cy/命令**と既に床に張り付いており、
残りは `bell_hit` の6帯× (判別式＋平方根＋除算2本) を **外れる visit にも全部払っている**ことにある
（visits 6,793–7,038 に対し hits 1,867–1,888 = **約73%が外れ**）。

**したがって: per-pixel のパイプラインごとベクタ化する（= PIE 化する）以外に、この2つを動かす手は無い。**
これが既存文書の結論であり、このブランチの仕事。

### 1.3 「正確さ」も動機のうち

4列グループ化は `-5.0 ms` を買ったが**近似**で、**13.6% の画素が動く**（`garden.c:1540-1547`）。
厳密なベクタカーネルなら、同じ規模を**画素を動かさずに**取れる見込みがある（`pie-simd.md` §5.1 の「原則ビット一致」に戻せる）。
既存の PIE カーネルはこの原則で書かれている（海面だけが例外で、許容範囲をテストに書いてある）。

### 1.4 使う知識（事前調査の出所）

- このリポジトリ: `docs/perf/pie-simd.md`（PIE の性質・コストモデル・スカラーの値段・測定方法）、`docs/perf/backlog.md`、
  `tools/pie/README.md`（3層の検証ツール）。
- 姉妹リポジトリ [esp32s3-hw-mcp](https://github.com/dj-oyu/esp32s3-hw-mcp): TRM からの一次情報（命令語、パイプライン段、
  アセンブラ照合、実機で測った命令の意味）。効く制約だけ挙げる:
  **128bit アクセスは下位4bitを黙って0にする**（整列違反は例外にならない）、**16bit レーンのシフト命令は無い**（SAR を固定して
  `EE.VMUL` の定数乗算で表す）、**索引ロードは `EE.LDXQ.32` の1命令1レーン**、**`EE.VST.128.IP` だけ +0.6 サイクル**、
  **intrinsics は無くすべてインライン asm**、**PIE はコプロセッサ3 なので ISR では使えない**。
  ローカルには `xtensa-esp32s3-elf-gcc` が入っているので、実機無しでコンパイル・`objdump` まで確認できる。

## 2. 対象の絞り込み

「実測コスト」「ベクタの形があるか」「ローカルで証明できるか」の3つで切った。

| # | 対象 | 実測 | 形 | 判定 |
|---|---|---|---|---|
| **T1** | `bell_hit` の**帯棄却**をベクタ化（`flower.c:1266-1400`） | `bell` 4.41 ms/frame、visits の約73%が外れ | `o[j]=dx*oax[j]+ob[j]` なので `b,c,判別式` は **x の多項式**。8画素分を固定小数点で一括計算し、`d<0` が確定した画素をスカラー経路に入れない。**`flower.c:1287-1291` のコメントがこの案をそのまま書いている** | **やる（第一）** |
| **T2** | 装飾光線（`rays`）の**厳密な**ベクタカーネル（`garden.c:1504-1569`） | スカラーで −5.0 ms 済（近似）。床 3.9 ms | 8画素ブロック。行の load → dither をレーン化（x ごとのパターンを表から `EE.VLD.128` 1本）→ Q8 の profile/mix を 16bit レーンで → mask 付き store（「書かない」を「選んで書く」へ） | **やる（第二）** |
| **T3** | MP3 のダウンサンプル前 FIR（`main/pocket/mp3_decode.c:60-72`） | デコード本体 5.9–6.7 ms のうち約 1.36 ms | スカラー 284 命令/サンプル → PIE 見積り **24 命令**（比 11.8×）。レシピも既知: リングバッファを2倍長にして窓を連続にし、`sum>>14` にすると `EE.SRS.ACCX`（floor）と**ビット一致**（`sum/16384` とは負の端数で1LSB違うだけ） | **やる（第三）** |
| T4 | `sqrtf` を種命令＋Newton-Raphson へ | 4,051–4,113 calls/frame = 2.14–2.23 ms（単価 174–188 cy） | ISA の列を使う必要がある（種の精度は実装定義。反復回数を勘で減らすとビット一致が黙って壊れる）。フレーム全域の除算・平方根の掃引は `tools/test_flower_div.c` の形で書ける | **保留**（T1〜T3 の後。花の1関数にしか効かない） |
| — | 楕円体の棄却（`d<0` の早期脱出） | 5,741 visit の 61.7% が抜ける | 落ちるのは**最安の画素**（棄却率は時間の節約率ではない、§4.1） | やらない（既存判断を維持） |
| — | 林冠の追加削減（`wsr.sar` 重複、`dx` 保持、定数31の二重ロード、`f` の `EE.VMUL` 1本化） | 林冠は PIE 済で **0.69 ms/frame**・39命令・ストール0 | 命令数を削るだけ | やらない（このパスで命令数削減のノーゲインが3例。`backlog.md` の P1 はこれで消える） |
| — | 幹（15px スパン×3）・草（4px）の PIE 化 | 0.30 / 0.12 ms | 8レーンに満たない | やらない（`garden.c:227` の判断を維持） |
| — | `shade`（`flower.c:902-991`） | 677–689 cy/hit = **1.3 cy/命令** | 素材別分岐でベクタの形が無い | やらない（既に床） |
| — | テキストのマスク合成 | 上流 PocketJS の Rust 側（`backends/rgb565/src/lib.rs:715-745`） | `scale=1` ではグリフ窓が 6–12px で 16px ブロックが成立しない | 対象外（PIE 不成立と判明済み。除算を加算にする側は上流待ち） |

**絞り込みの結果**: T1・T2・T3 の3本。T1 が最大（`bell` 4.41 ms の大半＋`ray` 15.2 ms の外れ側）、
T2 は近似を返上できる（正しさが動機）、T3 は比が最大で**純算術なのでローカルで全数証明できる**。
T4 は効果の見積もりに根拠があるが、T1〜T3 の後（1シーンの1関数にしか効かない）。

## 3. 書く順と、各カーネルの設計メモ

### T1 `bell` 帯棄却（第一）

- 形: 行の8画素分について、6帯それぞれの `b`・`c`・判別式 `d=b*b−a*c` を固定小数点で計算し、
  **全帯で `d<0` が確定した画素だけ**落とす。`a` は (部品,帯) ごとの定数（`p->bell_a[]`）なので、ベクタ側は `b` と `c` の
  2次式（`x` の多項式）を作れば足りる。QACC（8レーン×40bit）は `EE.VMULAS` 系の積和にそのまま乗る。
- 保守性: `d≈0` の近傍は**必ずスカラーへ残す**（マスクを広めに取る）。契約は「落とした画素の輪郭・depth は
  参照実装と一致」で、`test_kernels.py` の全画素比較に落とす。レンジは `run_models.py` に総当たりで入れる。
- 危険: 固定小数点の丸めで `d` の符号をまたぐ画素が1つでも出ればシルエットが1画素変わる。
  §5 の「表現についての主張は総当たりで決着する」に従い、**丸めを含めた式の等価性をモデルで証明**してからアセンブリを書く。
- 期待: `bell` の外れ側（visits の約73%）から 6帯×(判別式＋平方根＋除算2本) が消える。実機の数字は入るまで書かない。

### T2 装飾光線の厳密カーネル（第二）

- 形: 8画素ブロックで、行の load（`EE.VLD.128.IP`）→ dither をレーンで取る → profile と mix を 16bit レーンで →
  **mask 付き store**。`dither` は x ごとの周期パターンなので、事前に 16 バイト整列した表を作れば `EE.VLD.128` 1本。
- 壁（`backlog.md` が明文化しているもの）: 32bit 中間値の扱い、被覆の外で「書かない」を「マスクして書く」へ変えること、
  dither のレーン化。**「書かない」を選んで書くに変えるのが近似を返上する鍵**（値は合っているが書かない画素、を作らない）。
- 期待: 現状は近似で −5 ms。厳密版で同程度〜やや劣る程度に収まり、13.6% の画素が戻るのが主眼。

### T3 MP3 FIR（第三）

- 形: 32 タップの畳み込み。リングバッファを2倍長にして、窓が連続 16 バイト格子に乗るようにする
  （`history[]` の書き込みを2箇所にする）。`EE.VMULAS.S16.QACC` ×4 ブロック → `EE.SRS.ACCX` で `sum>>14`。
- 契約: **ビット一致**（`sum/16384` → `sum>>14` の変更は負の端数で1LSB変わるだけなので、C 側も `>>14` に揃える）。
- ローカル検証が最も綺麗に閉じる（入力全域の総当たり＋ASA N レベルのランダム波形で参照実装と比較）。

## 4. 検証はホストの4層で閉じる（実機は使わない）

`tools/pie/README.md` の3層に、実コンパイラを足した4層。すべて今のホストで動くことを確認済み（2026-09-15）。

| 層 | 何を守るか | コマンド |
|---|---|---|
| 1. 算術 | 「その式は正しいか」— 式・表・丸めの全域証明 | `python3 tools/pie/run_models.py`（`models/*.c` を追加。現在 green） |
| 2. 意味 | 「アセンブリはその式か」— レーン・定数順・ポインタ・マスク | `python3 tools/pie/test_kernels.py`（`piesim.py` で命令レベル実行しスカラー参照と全画素比較。現在 7 tests green） |
| 3. 並び | 「その並びは速いか」— def=2 の直後使用、本体 256B | `python3 tools/pie/stalls.py <file> <kernel>`（0 ストールになるまで往復） |
| 4. 実物 | 実コンパイラで通ること・`loopgtz` の本体・レジスタ割当（`kp`/`k` 別、early-clobber `=&a`） | `xtensa-esp32s3-elf-gcc` でコンパイル → `objdump -d`（ホストに入っている） |

規約（`pie-simd.md` §6.1・§8）:
- **スカラー参照実装を先に書き、`__attribute__((unused))` でソースに残す**（アセンブリの唯一の説明になる）。
- **最適化には必ずスイッチ**（実行時変数が最も安全）。**最適化とその計測を同じコミットに入れない**。
- 1カーネル = 1コミット。テストは同じコミットに入れる（テストは計測ではない）。

**このブランチでは実機の数字を主張しない。** 実機 A/B は、`vm/design-contracts` の SPLIT3 ブラケット
（`garden_prof_rays` / `garden_prof_vegetation`）と `SCENE_AB` の窓反転を持ってきたうえで、
1本のツリー・1個の define・同一バイナリで取る（§6.2・§6.3）。用意だけしておき、実行はデバイスが空いてから。

## 5. やらないこと（明示）

- 命令数の削減だけを目的にした最適化（このパスでは3例連続でノーゲイン。床の比を変えない限り動かない）。
- 棄却率を根拠にした高速化（`§4.1`。落ちる仕事はたいてい安い）。
- 8レーンに満たないスパン（幹・草）、既に床にある関数（`shade`）、上流 Rust 側（テキストマスク）。
- このブランチからの実機計測・書き込み（デバイスは別セッションが使用中）。
