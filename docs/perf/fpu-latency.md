# この石のスカラー FPU の依存レイテンシ（実測）

2026-09-20、実機 COM3、`main/hal/fpu_latency.c`（ホーム画面で USB の `F`）。

`docs/perf/flower-shade.md` の3つの実験は、どれもこの数字で決まるのに**誰も持っていなかった**。
esp32s3-hw-mcp が測ったのは PIE 命令だけ、TRM はコプロセッサのパイプライン段数を印字しない。

## 方法

`experiments/pie-timing` と同じ —— 前の結果を食う命令を N 本並べた腕と、食わない命令を
N 本並べた腕を回し、差を取る。依存側はパイプラインを、独立側は発行率を払い、
**差がスケジューラの埋めるべき隙間**になる。128 命令を `.rept` で展開し 200 回、
7 走のうちの**最小**を採る（平均だと tick 割り込みが混ざる）。

**独立側は行あたり4命令**（宛先を散らさないと鎖が切れない）。初回はこれを1で割って
しまい、独立側が4倍に見え、本物の3サイクルのストールが「差なし」に化けた。
もうひとつ、`olt.s→bt` は最初 b1 を真に置いたので**taken と not-taken を比べていた**
（負のストールが出て気づいた）。どちらも直してある。

## 結果（cy/命令、`F` を2回叩いても同値）

| 組 | 依存 | 独立 | ストール |
| --- | ---: | ---: | ---: |
| `mul.s` | **4.07** | **1.02** | **+3.05** |
| `madd.s` | **4.07** | **1.02** | **+3.05** |
| `mul.s` → `rfr` | 2.55 | 2.04 | +0.51（対あたり +1.0） |
| `mul.s` → `trunc.s` | 2.55 | 2.04 | +0.51（対あたり +1.0） |
| `olt.s` → `bt` | 1.55 | 1.05 | +0.50（対あたり +1.0） |
| `wfr` → `mul.s` | 1.05 | 1.05 | **0.00** |
| `lsi` → `mul.s` | 1.05 | 1.05 | **0.00** |
| `s32i` → 同アドレス `lsi` | 1.05 | 1.05 | **0.00** |

## 読み方

**1. FPU は1サイクルに1本出せるが、結果は4サイクル後にしか使えない。**
依存鎖は独立列の **4倍**遅い。逆に言えば、**依存で詰まっている間に独立な命令を3本通せる**。

**2. FPU と汎用レジスタの往復は無料。** `wfr`（汎用→FPU）、`lsi`（メモリ→FPU）、
同一アドレスの store→load、いずれもストール 0。**「`l32r`+`wfr` が重い」は間違い**で、
あれは発行スロットを1本使うだけだった。

**3. FPU から汎用側へ出る向きだけ +1 サイクル。** `rfr` と `trunc.s`、
そして `olt.s`→`bt`。`shade` は色1チャネルごとに `trunc.s` を通すので、ここは経路に乗る。

## これが説明すること

`flower-shade.md` の空振り2件が、これで辻褄が合う。

- **§9（`lsi` 表引き、命令22本減）が動かなかった理由**: 消したのは `l32r`/`wfr`、
  つまり**ストール 0 の発行スロット**である。関数がレイテンシで詰まっている間、
  発行スロットは余っている。**余っているものを返しても速くならない。**
- **§12（逆平方根）が動かなかった理由**: 置き換えたのも**依存鎖**だった。
  Newton 2段は `y*(1.5-0.5*d*y*y)` が素直に直列で、鎖の長さがそのまま時間になる。
  ただし ROM の `sqrtf`（約30本の依存鎖 ≈ 120 cy、実測 106）に対して
  Newton 2段は依存 FPU 約11本 ≈ 44 cy のはずで、**60 cy 分が説明できていない**。
  これは未解決。整数シードの `rfr`/`wfr` 往復（0 のはず）でも、
  発行スロット（0 のはず）でもないので、次に測るならここ。

## 鎖を何本織れば埋まるか（同じプローブ、case 9-10）

| | cy/命令 |
| --- | ---: |
| 鎖1本 | 4.07 |
| 鎖2本を織る | **2.04** |
| 鎖3本 | **1.36** |
| 鎖4本 | 1.02（飽和） |

**パイプラインはちょうど4段。** 4本までは、何本織っても**実時間は鎖1本ぶんと同じ**になる
（2本なら 2×2.04 = 4.08 cy で2命令、1本なら 4.07 cy で1命令）。
2画素ぶんの FPU 鎖は、1画素ぶんの時間にちょうど収まる。

## これが開くこと

**独立な鎖を2本並べれば、片方のストールをもう片方が埋める** —— 上の表が実測で示したとおり、
2画素ぶんの FPU 鎖は1画素ぶんの時間に入る。`shade` を隣接2ヒットで呼ぶ `shade2`
（Fable の提案、`flower-shade.md` §13）は、**この表が初めて裏づけた最適化**である。
逆に、命令数を減らす方向は（`shade` が依存鎖で詰まっている限り）測る前から見込みが薄い。

### ただし取り分は「全部」ではない —— 上限の見積もり

`shade` は 529 cy/hit。経路上の FPU 演算はおよそ45本で、**全部が鎖なら 4×45 = 180 cy**、
つまり **529 のうち3分の1**しかない。残りは (a) `sqrtf` と `__divsf3` の呼び出し、
(b) 1 cy で発行される整数・分岐・ロード、である。

- (b) は2画素で**倍になる**。埋まらない。
- (a) は**呼び出しなので織れない**。2画素なら2回直列に走る。
  ここを取るには逆平方根のインライン化（§12 で単独では効かなかったもの）が要り、
  **2本織って初めて半額になる** —— これが「単独で効かなかった理由」の予言でもある。

したがって素朴な上限は **FPU 鎖ぶんの約90 cy/画素（17%）**、呼び出しもインラインにして
織れた場合で **150〜200 cy/画素（30%前後）**。29 ms の kernel に対して 1.2〜1.5 ms。
**これは算術であって実測ではない。** 今日この種の算術は2回外れている
（`flower-shade.md` §7 と §11）。書く前に切除アーム（同 §13）で上限を見ること。

## 道具

`F` をホーム画面で叩くと走る。約 0.1 秒、確保なし、owner タスク。
`CONFIG_KSN_DEVICE_PROBE` の外に置いてある —— 測りたいのは表示ではなく CPU で、

## 切除アーム: `shade` の中では鎖が織れない（2026-09-20）

上の表はハードウェアが2本の鎖を無料で織れると言う。**この関数がそれを使えるか**は別問題で、
`shade2` を書く前に切除アームで確かめた（`flower-shade.md` §13 の手順）。
`shade` の中へ余分な独立仕事を足し、`shade` cy/hit がどう動くかを見る。
基準は **529 cy/hit**。

| 足したもの | 追加 FPU 演算 | `shade` | 差 | 演算あたり |
| --- | ---: | ---: | ---: | ---: |
| 照明の鎖を3本複製（生存レジスタ多数） | 27 | 760 | +231 | **8.6 cy** |
| 依存27段の鎖1本（**生存レジスタ1本**） | 27 | 725 | +196 | **7.3 cy** |

**どちらも直列（4 cy/演算 = +108）より悪い。** 織れていれば +27 cy 程度のはずだった。

2本目はレジスタ不足を排除するために作った（生存値は `q` 1個だけ）のに 7.3 cy/演算。
命令数は 988 → 1045 で、madd.s が狙いどおり +27、**残り +30 は移動とスピル**である。

### 結論

**ハードウェアは2本の鎖を織れる。GCC はこの関数の中でそれをしない。**
合成ループ（`madd.s` だけ、生存2本）では 2.04 cy/演算まで落ちるのに、
本物の `shade` に鎖を1本足すと 7.3 cy/演算を払う。
`-O2` の xtensa は post-RA スケジューリングのみで、
100 行の浮動小数コードの中に新しい鎖を織り込むところまではやらない。

したがって **`shade2`（隣接2ヒットを1回で処理する版）は、書いても速くならない公算が高い。**
これは今日3度目の空振りになるはずだったものを、**約40行の切除アームで書く前に潰した**。
Fable が提案した手順（`flower-shade.md` §13）が、そのとおりに働いた形である。

### 残る道（測っていない）

- **`shade` を `ray_row` へインライン展開する**。鎖を織るのはコンパイラの仕事で、
  織る相手（次の画素の仕事）が同じ関数の中に見えていなければ始まらない。
  コード量と icache が代償。
- **手書きアセンブラ**。ハードウェアが 2.04 cy/演算を出せることは分かっているので、
  `shade` の鎖を自分で2本に織れば取れる。ただし 100 行の浮動小数コードを
  アセンブラで持つ保守コストは、1.2〜1.5 ms のために払うものではない。
- **呼ばれる回数を減らす**（`flower-shade.md` §12 末尾）。1,870 ヒット/フレーム。

## 手書きの順序で何が取れるか（case 11-12、2026-09-20）

切除アームは「GCC はこの関数で鎖を織らない」と言った。では**人間が順序を書いたら**取れるのか。
`shade` の照明ブロックと同じ依存構造（独立な部分鎖2本 —— 拡散の内積が3段、
鏡面の内積＋16乗が7段、計10演算）を、順序だけ変えた3通りで測った。
**この石は in-order なので、「織る」とは書く順序そのものである。**

| | cy/命令 | ブロックあたり |
| --- | ---: | ---: |
| `naive1`（部分鎖を順に書き切る＝素直な並び） | 3.43 | **34.3 cy**（1画素） |
| `woven1`（**1画素の中で**2本を交互に） | 2.62 | **26.2 cy**（1画素） |
| `woven2`（**2画素ぶん**4本を交互に） | 1.41 | **28.2 cy**（**2画素**） |

**2つ読める。**

1. **1画素の中だけで −24%。** 拡散と鏡面は元から互いに独立なので、
   2画素に広げなくても順序を変えるだけで取れる。
2. **2画素は1画素の 1.08 倍。** 素直な1画素（34.3）より、織った2画素（28.2）のほうが**安い**。

つまり**手書きの順序は効く。機構は本物である。**

### それでも `shade` には書かない

`shade` は 529 cy/hit、1,870 ヒットで 4.1 ms、29 ms の kernel の 14%。
仮に鎖の部分（多く見て180 cy）で「2画素を1画素の値段」が実現しても、
呼び出し2本と1 cy で発行される整数・分岐は倍になるので、取り分は**0.7 ms 前後（2.4%）**。
対して `shade` は12本の材質分岐と `sqrtf`/`rgbd` の呼び出しを含む100行の浮動小数コードで、
**アセンブラで保守する対象として最悪の形**である。この石で手書きが見合うのは
分岐の無い画素ループ —— つまり既に PIE カーネルとして書かれている場所のほう。

### `-fschedule-insns` を試した結果: 遅くなる（2026-09-20）

`-O2` の xtensa は post-RA スケジューリングのみ（`-fschedule-insns2`）なので、
レジスタ割付**前**に並べ替える `-fschedule-insns` を `flower.c` だけに足して測った。
同じ手順の同じ窓位置で比べる:

| 窓 1–8 | `shade` cy/hit |
| --- | ---: |
| 基準（post-RA のみ） | **515–525** |
| `-fschedule-insns` 追加 | **563–590** |

**約10%遅い。** 命令数は 988 のまま動いていないので、増えたのではなく**並びが悪くなった**。
pre-RA スケジューラは独立な演算を近づけて生存区間を伸ばすので、
16本しかない FPU レジスタでは割付が悪化する —— 教科書どおりの失敗の仕方である。

**1行と1回の計測で決着した。** 反転済み。
手書きの 24% は、コンパイラのスケジューラからは取れない。

## 手書きアセンブラ: 書いて、測って、戻した（2026-09-20）

上の 24% を実際に取りに行き、**戻した**。コードは残っていないので、残す価値のある
知見だけをここに書く。実物は `git show aa072c2`。

### 書いたもの

`shade` の照明ブロック（独立3本、分岐も呼び出しも無い）を29命令へ。
3本を交互に並べ、定数は `lsi` で FPU レジスタへ直接読む。

### 測れたこと

| | `shade` |
| --- | ---: |
| 手書き | 556.1 cy/hit |
| C（GCC の並び） | 566.9 cy/hit |

**−10.8 cy/hit、隣り合う7対すべてで手書きが下。** 照明ブロックの 59 cy に対して 18% で、
合成ループが予告した 24% とおおむね一致する。
全体では `shade` の 1.9%、**kernel の 0.3%（0.084 ms/フレーム）**。

### 戻した理由

速度ではなく**検証が成立していなかった**から。3つの穴が同時に見つかった。

1. **`madd.s` は fused**（`FPU_MADD_FUSED YES result=3a000400`、いまは probe が毎回出す）。
   したがって GCC が「どちらの積を fma へ縮約するか」で**ビットが変わる**。
   `shade` の C 腕は `y·b` を先に丸め、手書きは `x·a` を先に丸めていた ——
   **同じ関数ではなかった。**
2. **自己検査が比べる相手を間違えていた。** `flower_lite_check` は
   **自分の中へインライン展開された C 版**とアセンブラを比べる。`shade` の中の C 版は
   別インスタンスで縮約順序が違う。`PASS checked=1729 mismatched=0` は
   「同じ順序どうしが一致した」としか言っていない。
3. **`flower_frame_dump` も見えない。** ホストは x86 で既定では縮約しないので、
   **第3の意味論**であり、縮約順序の差に構造的に盲目である。

つまり `aa072c2` は「ビット一致」と主張しながら、出荷画素の下位ビットを
変えていた可能性が高い（ulp 級で絵には出ないが、主張が違う）。
**0.3% のために、この3つを抱える価値は無い**と判断して戻した。

### 次に誰かが浮動小数を書き直すときの必須手順

- **`FPU_MADD_FUSED` を見る。** fused なら、縮約順序を変える書き換えは
  ビット一致では**ない**。順序を固定したいなら `__builtin_fmaf` で明示する。
- **検査は「出荷するインスタンス」と比べる。** 検査関数の中へ別途インライン展開した
  コピーと比べても何も証明できない。`noipa` で1つの実体にするか、
  出荷側から呼ばれる同じ関数を両腕で使う。
- **ホストのビット比較は縮約差に盲目。** x86 と Xtensa は fma の有無が違う。
  実機で比べること。
- **A/B スイッチ自身が非対称になりうる。** 片方の腕が out-of-line に置かれると
  taken 分岐2本を余計に払う。`flower-shade.md` §13-2 の「定義順を入れ替えて
  符号を見る」を毎回やること（この測定ではやっていない —— −10.8 の一部が
  スイッチの配置である可能性は残っている）。

## この石について確定したこと（道具: `main/hal/fpu_latency.c`、ホーム画面で `F`）

| | |
| --- | --- |
| スカラー FPU の依存レイテンシ | **4.07 cy**、独立発行 **1.02 cy**（3サイクルのストール） |
| パイプラインの深さ | **4段**。2本織れば 2.04、3本で 1.36、4本で 1.02 と飽和 |
| FPU へ入る往復 | `wfr`→使用、`lsi`→使用、同アドレス `s32i`→`lsi` いずれも **0** |
| FPU から出る | `rfr` / `trunc.s` / `olt.s`→`bt` は +1（ただし下の注記） |
| `madd.s` | **fused**（`3a000400`） |
| 手書きの順序 | 1画素の中で **−24%**、2画素を織れば **1.08 倍**で2画素 |
| コンパイラ | `-O2` は post-RA のみ。`-fschedule-insns` は **10% 遅い** |

**注記（Fable の指摘、未修正）**: 「出る向きだけ +1」は probe の設計による。
`rfr`/`trunc` のケースは消費側が自己依存の `mul` 鎖の後ろにいるので、
in-order では対 = max(4, L+1) となり、測定の 5 cy/対は **L=4（普通の消費者と同じ）**
とも読める。`olt.s→bt` の 3 対 2 cy/対だけが本当に **L=2** である。
きれいに測り直すなら `mul.s f0,f7,f1; rfr a8,f0`（自己鎖なし）のケースを足すこと。

## 一般化するか（Fable の査定、2026-09-20）

- **`bell_hit`（4.2 ms、`shade` と同規模）が唯一の実候補。** 6帯が互いに独立なのに
  `continue`（`flower.c:1447`）で GCC は反復を織れず、sqrt が visit あたり平均 344 cy（37%）。
  「2本織って初めて半額」の唯一の的。**先に測るべきは visit あたりの sqrt 本数の分布** ——
  1本以下が大半なら取り分は無い。
- **整数側（rays / veg / `ksn_render.c`）は効かない。** 整数 ALU は依存0ストール
  （esp32s3-hw-mcp 実測）。4サイクルは FPU 固有。効くのは命令数・taken 分岐・呼び出し。
- **PIE も変わらない。** 依存対は M→E 1 ストール、E→E 0 の深さ1のパイプで、
  `stalls.py` が既に数えている。スカラー FPU の表は持ち込めない。
- **まだ誰も測っていない一撃**: XTPERF のカウンタ（`core-isa.h` に2本、
  IDF の `perfmon` は xtensa で建つ）。SPLIT の窓ごとに cycles と INSN を取れば
  IPC が出て、「レイテンシ律速か発行律速か」がコード変更なしに決まる。
  この石でカウンタが動くかの検査は5分。
