# ESP32-S3 PIE（SIMD）で描画カーネルを書く

このボード（ESP32-S3FN8、240MHz、PSRAMなし）でPIEカーネルを書く・スカラーコードを最適化するための参照。海面・波・blend・バイトスワップ・庭の画素ループ・canopyという実際に書いた複数のカーネルと、その過程で当たった／外れた予測から作った。

数値はすべてCardputer ADV実機の実測です。推測・静的解析はその旨を明記します（実測 / 推定 / [obj]（objdumpからの静的カウント）/ host（ホストでの計測、実機時間の代用にはならない））。命令の節番号は[ESP32-S3 Technical Reference Manual](https://documentation.espressif.com/esp32-s3_technical_reference_manual_en.pdf)第1章のものです。未着手の最適化候補は[docs/perf/backlog.md](backlog.md)にある。

## 1. PIEとは何か、何が無いか

PIE（Processor Instruction Extensions）はESP32-S3のXtensaコアに載る128bit SIMDです。**コプロセッサ3**として実装されており、FPUと同じくタスク切り替え時に退避・復元されます。したがって**タスク内では安全、割り込みハンドラ内では使えません**。

### 1.1 制約

| 項目 | 内容 |
| --- | --- |
| intrinsics | **存在しない**。すべてインラインアセンブリで書く |
| ベクタレジスタ | q0〜q7 の8本のみ。16bitレーンなら8要素 |
| アキュムレータ | QACC（8レーン×40bit）が1本 |
| 16bitレーンのシフト命令 | **存在しない**（§1.2で回避法） |
| ギャザー（索引ロード） | `EE.LDXQ.32` のみ、**1命令で1レーン**（§2.3） |
| レーン選択・ブロードキャスト | `EE.VLDBC.*`（メモリから）のみ。**QR内の1要素を全レーンへ配る命令は無い** |
| 128bitアクセスのアラインメント | 16バイト。**違反しても例外にならず、下位4bitが黙って0にされる**（§1.3） |

### 1.2 シフトは「定数との乗算」で表現する

16bitレーンを直接シフトする命令が無いため、`EE.VMUL.S16` / `EE.VMUL.U16`（§1.8.122 / §1.8.128）を使います。この命令は32bit積の**下位16bitをSARだけ右シフトした値**を返すので、SARを固定しておけば乗数の選び方で左右どちらのシフトにもなります。

SAR=11 に固定した場合:

```
x << 3   →  EE.VMUL.U16 with 16384    (x * 2^14 >> 11)
x >> 2   →  EE.VMUL.U16 with 512      (x * 2^9  >> 11)
x << 4   →  EE.VMUL.U16 with 32768    (上限。x << 8 は2回に分ける)
x >> 3   →  EE.VMUL.U16 with 256
```

`wsr.sar` は**関数の先頭で1回だけ**実行します。途中でSARを切り替えると往復2命令が増え、多くの場合それだけで利得が消えます。左シフトの上限は ×16（RGB565の8bit左寄せは`×32768`を2回）。

**SARは`SAR[5:0]`まで有効**なので、積が32bitに収まる限り`>>16`以上の右シフトも1命令で厳密です（TRM p198/p204、[esp32s3-hw-mcp](https://github.com/dj-oyu/esp32s3-hw-mcp)実機例題で確認）。上の「左シフトは×16まで」はSARを固定したときの話で、右シフトはもっと広く取れます。

### 1.3 アラインメント・レジスタ共有・loopgtzの制限

**128bitアクセスはアドレスの下位4bitを黙って0にします。例外は上がりません。** アラインメントされていないバッファを渡すと意図しない場所を読み書きして静かに壊れます。カーネルに渡すバッファには必ず`__attribute__((aligned(16)))`を付け、行の途中から始まる場合（blendの矩形が奇数x始まりなど）は16バイト境界までをスカラーで前後処理します。行の長さが16の倍数なら基底さえ揃えば各行の先頭は自動的に揃う（240px×2B=480Bはこの条件を満たす）。

**定数表を歩くポインタには`"=&a"`（early-clobber）が必須**です。`"+a"(kp)`と書くとGCCが`kp`と`k`に同じレジスタを割り当てることがあり、ブロックごとの巻き戻し`mov`が無効化されて2ブロック目以降が表の範囲外を読みます。コンパイルは通り、テストによっては通ってしまいます。同様に`loopgtz`はハードウェアループレジスタを操作するため、コンパイラが駆動するループの内側に置いてはいけません。カーネルは`__attribute__((noinline))`で切り出します。

**`loopgtz`のループ本体は256バイト以内**（PIE命令はおおむね3〜4バイトなので実質70命令程度が上限）。超える場合は`addi`/`bnez`の通常ループにします（blendカーネル、本体292B、1ブロックあたり+2命令）。逆にアンロールで本体を256B超にすると`loopgtz`が使えなくなり、命令数が減っても損をすることがあります（海面カーネルの2倍アンロールは`mov`1本/2ブロック分の得にしかならず見送り）。

### 1.4 esp32s3-hw-mcpで確認した追加のISA仕様

[esp32s3-hw-mcp](https://github.com/dj-oyu/esp32s3-hw-mcp)の実機例題（三重照合）とTRM抽出から。詳細はMCPツールの`example_measured_semantics`/`measured_timing`/`manual_errata`。

- **`VMUL`は折り返し、飽和しない。** 16bitの加算は飽和する`EE.VADDS`しか無いので、飽和させたくない和は16bitレーンでは作れない。対称FIRを畳むと`w[k]+w[31-k]`が飽和する（実測で窓の68〜72%）。CELTは32bitで折り返すので`VADDS`を使うと別の演算になる。
- **u8レーンは使いどころが狭い。** `EE.VMUL.U8`は結果が8bitしか残らず`/256`を作れない。`EE.SRCMB.S8.QACC`は127で飽和する。8bitデータは`EE.ZERO.Q`+`EE.VZIP.8`でu16に広げてから扱う。
- **未整列読み込みはできる。未整列書き込みはできない。** `EE.LD.128.USAR.IP`+`EE.SRC.Q`で16B格子から外れた窓をコピー無しで読める（第1オペランドが下位側）。ストアはすべて番地の下位4bitを切り捨てる。`EE.SRCQ.128.ST.INCP`もずらすのはデータで番地ではない。`EE.VLD.L.64.IP`は下位3bitだけ切り捨てるので8B格子の64bitデータに使える。
- **128bitのポストインクリメントは常に16バイト刻み。** 8バイトの行（4×4 int16行列など）をこれで歩くと1行おきに読む。
- **`piesim.py`はレジスタ番号を1文字しか読まない。** `q10`をq1として黙って受け付けるので、q0〜q7だけで書くこと（`8b61301`）。

参考資料として[esp-dlのPIEスキル](https://github.com/espressif/esp-dl/tree/master/tools/agents/skills/esp32s3-pie-simd)がありますが、**不完全かつ一部不正確**です。`EE.LDXQ.32`の記載が無く、パイプライン段の記述（§2.2）も「0-1 cycle」と誤っています。TRMの表1.7-2が一次情報です。

## 2. コストモデル

### 2.1 PIEは1命令1サイクル、例外はストアだけ

**規則**: PIE命令は種類を問わず1サイクルで発行される。唯一の例外は128bitストアで+0.6サイクル。融合ロード（`.LD.INCP`）も索引ロード（`EE.LDXQ.32`）も追加コストはゼロ。したがって理論上の下限は：

```
サイクル/ブロック = 命令数 + 0.6 × ストア数 + ストール数
```

**経緯（1〜2文）**: 海面カーネルv1（64命令）が123サイクル/ブロックに見え、ストール除去でも`ldxq`全廃でも「残差」が消えなかったため、3つのエージェントが独立に「`ldxq`の部分書き込みがread-modify-writeになっている」と推測し、近似化まで実施した。推測をやめて機械の素の速度を測ったところ、この式で説明がついた（推測は証拠ではない、という教訓は§2.7）。

**測定（実測、30ブロックのループで本体だけ差し替え）**:

| ループ本体 | サイクル/ブロック |
| --- | --- |
| `EE.VADDS.S16` を40命令 | 40.9 |
| `EE.VMUL.S16` を40命令 | 40.9 |
| `EE.VPRELU`/`EE.VRELU` を12本混ぜて40命令 | 40.9 |
| 40命令のうち1本を`EE.VST.128.IP`に | 41.5 |
| ループ1回に1命令だけ | 1.7 |

| `.LD.INCP`の本数（41命令中） | 0 | 8 | 16 | 24 | 32 | 16（分散） |
| --- | --- | --- | --- | --- | --- | --- |
| サイクル/ブロック | 41.9 | 42.0 | 42.0 | 42.1 | 42.2 | 41.9 |

| `EE.LDXQ.32`の本数（42命令中） | 0 | 8 | 16 | 24 | 24（散在） | 24（同一レジスタ） | 24（2本交互） |
| --- | --- | --- | --- | --- | --- | --- | --- |
| サイクル/ブロック | 43.3 | 43.2 | 42.9 | 42.9 | 42.9 | 42.9 | 44.0 |

実カーネル`ocean_row_pie`（40命令、ストア1本）は下限40.6に対し単独実測45.5。差の約4は行あたりの前処理（定数21個の構築とブロードキャスト）を30ブロックで割ったぶん。

### 2.2 パイプライン: def=2の結果を直後に読むと1サイクル止まる

**規則（最も効いた知見）**: TRM表1.7-2のuse/defステージより、ロード系・`EE.VMUL`・`EE.VRELU`はdef=2。use=1の命令がその結果を直後に読むと必要間隔`D=max(SA-SB+1,0)=2`分、1サイクル止まる。間に独立命令を1本挟めば止まらない。

| 命令 | use | def |
| --- | --- | --- |
| `EE.VLD.128.IP` / `EE.VLDBC.16.IP` / `EE.LDXQ.32` / `EE.VLD.L.64.IP` | 1 | **2** |
| `EE.VMUL.S16` / `EE.VMUL.U16` | 1 | **2** |
| `EE.VRELU.S16` | 1 | **2** |
| `EE.VADDS` / `EE.VSUBS` / `EE.ANDQ` / `EE.ORQ` / `EE.VUNZIP` / `EE.VMIN` / `EE.VMAX` | 1 | 1 |
| `EE.VST.128.IP` | 1 | — |

対策は3つとも機械的：①定数を複数レジスタでダブルバッファし使用の2〜3命令前にロード、②索引ロードの書き込み先をA→B→A→Bと交互にする、③乗算の結果をすぐ足さず独立した計算を挟む。

海面カーネルでの効果（出力ビット一致のまま）：

| | 命令数 | loop | サイクル/ブロック | サイクル/命令 |
| --- | --- | --- | --- | --- |
| v1 | 64 | 1.43ms | 123 | 1.90 |
| v2 | 62 | **1.06ms** | **86** | 1.39 |

**26%の短縮が演算を1つも変えずに得られた。** 新しくカーネルを書くときは最初からこの順序で書く。

### 2.3 テーブル引きは「命令が遅い」のではなく「本数が要る」

索引ロードは`EE.LDXQ.32`（§1.8.37）だけで、1命令につき32bitレーン1本しか読めない。8要素を引くには8命令、2つの表なら16命令。命令そのものは§2.1のとおり1サイクルで他と変わらない。**高いのは、8要素を集めるのに8命令使うという構造のほう。**

**設計上の含意**: 正弦表などを引く設計はスカラーコードほど有利ではない。海面カーネルでは2つの正弦表を放物線近似（`u(128-|u|)`と補正項1つ）で置き換えて16本の`ldxq`と2本の`vunzip`、2本のマスクが丸ごと消え、命令数が62→40、時間が1.06ms→0.89msになった（§5.1のとおりビット一致を捨てる判断）。

**表引きが避けられない場合は表そのものに定数を畳み込む**ことで命令を減らせる。海面カーネルは正弦表を`(sine[i]/6)*16 - 180*16`として持ち、除算・スケーリング・オフセット加算を表の初期化に押し込んでいる。波のカーネルは明度とその重み付き値（/4, /3, /2）を`lo | (hi << 16)`の形で1つの32bitエントリに詰め、1回の索引ロードで両方を取得して`EE.VUNZIP.16`で分離する。

### 2.4 QACCの補足

- **QACCを介したストールは、読む命令によって違う。** `VMULAS.*.QACC`直後の`EE.SRCMB.S16.QACC`は**0サイクル**、`EE.ST.QACC_L.L.128.IP`は**1サイクル**（実測、2000反復、アンカー5件一致）。TRMの表からは両方1サイクルと予測される。`stalls.py`がQACCをモデル化していないのは、結果として`SRCMB`については正しい。
- **`EE.SRCMB.S16.QACC`はアキュムレータに書き戻す**（read-modify-write）。同じQACCを別のシフト量で2回読むと2回目は1回目の結果を読む。
- **融合ロードは`VADDS`/`VSUBS`/`VMUL`のS16だけではない。** `VMIN`/`VMAX`、S8/S32の形、`VMUL.U16`、`CMUL.S16`、`VSMULAS.*.QACC`にもある（TRM抽出、20種）。§2.1の「融合ロードは無料」はこれら全部に及ぶ。

### 2.5 下限が数えないもの：行あたりの足場

**規則**: §2.1の式はループ本体だけの下限で、1行あたりの前後の足場（run ドライバ、関数呼び出し、コーナー計算、除算）は別に数える必要がある。数えずに見積もると、行が複数のrunに割れるカーネルでは2割程度外れる。

**経緯**: 庭（`main/scene/garden.c`）の画素ループをPIE化したとき`kernel=`を38〜44msと予測して実測48.9ms。ストールゼロ、命令数も設計どおり、`test_kernels.py`は全画素一致——式は合っていて、式に入れなかったものが足りなかった。

`objdump`で数えた内訳（1行）：

| 内訳 | サイクル | |
| --- | --- | --- |
| ベクタ本体3ループ（30ブロック×180.8） | 5,424 | §2.1の式が当てる部分 |
| runごとの足場（13.25 run×174） | 2,306 | 見積もりは1,170。**2倍の数え落とし** |
| 画素パスの前後（k[40]構築95＋ブロードキャスト109） | 204 | |
| 行のセットアップ（corner 12回、逆数3本、motion 1回） | 1,447 | ほぼ丸ごと勘定に入れていなかった |
| **合計** | **9,381** | 予測は7,024 |

ベクタ本体は1行の58%しかなく、残り42%はアセンブリの外側（9,381×135行=1.27Mサイクル=5.28ms、予測3.95ms。§2.6の係数1.3〜1.4を掛けて6.9〜7.4ms）。

**なぜ海面・波では起きなかったか**: `ocean_row_pie`/`wave_row_pie`は1行=1ループで、行あたりの足場は「定数21個のブロードキャスト」だけ（§2.1の「差の約4」がそれ）。庭のカーネルは行をrunに切る（格子セルの境界でコーナー値が変わるため）ので、1行に13回の関数呼び出し・ブロードキャスト・`loopgtz`立ち上げが入り、第2項が第1項と同じ桁になる。

**数え方**: 見積もらずに`objdump -d`で数える。`loopgtz`/`bnez`の外側にある静的命令数が1回の呼び出しあたりのコスト。

```
garden_broadcast    static   7   ループ本体 2   ループ外  5
garden_coarse_pie   static  57   ループ本体 22  ループ外 32   （+ 8反復のrcv充填）
garden_pixels_pie   static 230   ループ本体 135 ループ外 95
```

`ee.vst.128.ip`の0.6を忘れないこと（40定数のブロードキャストなら+24サイクル）。**このコアのハードウェア除算は1命令だが約32サイクル。** 庭は画素ループから除算を全廃したが、行の足場に28本（`garden_corner` 12、逆数3、runドライバ13）残っていた（1行900サイクル、1フレーム0.5ms）。ループから追い出した除算がループの外に溜まっていないか見ること。

補正した形：

```
サイクル/行 = ブロック数 × (命令数 + 0.6×ストア数 + ストール数)      §2.1が当てる部分
            + run数     × (ドライバ + カーネルのループ外 + 呼び出し)   objdumpで数える
            + 行のセットアップ（除算は1本32サイクルで数える）
```

そのうえで実動作は1.3〜1.4倍（§2.6）。掛ける前の中身を数え落としていると、係数をいくら正確にしても当たらない。

### 2.6 単独計測と実動作は3〜4割違う

海面カーネルを単独で回すと1行1365サイクル（98行で0.557ms）だが、実際のフレームの中では`kernel=0.69〜0.74ms`と2〜3割高く出る。行あたりの前処理を足すと下限に対して3〜4割増し（波も同じ比率）。理由は描画タスクが他タスク（5msごとのキー走査、音、USB）に割り込まれ、PIEはコプロセッサ3なので切り替えのたびに8本のQRを含む状態の退避・復元が起きるため——**カーネル側で対処できることはない**。

海面v3は40.6→単独45.5→実動作56、波v2は69.6→実動作95。どちらも下限の3〜4割増しに収まる（行あたり前処理で約1割、プリエンプションで約2割）。新しいカーネルがこの範囲に入っていれば正常、それ以上外れているときだけ疑うこと。

### 2.7 教訓

- **推測が3人一致しても証拠ではない。** §2.1の`ldxq`犯人説は全員が同意し誰も測っていなかったが、実際には無料だった。
- **機械の下限を先に測る。** 「40命令のループは何サイクルか」は10分で測れて数時間の推測を不要にする。
- **係数は本数を振って決める。** 最初に「融合ロード1本0.37サイクル」と出したのは1点だけを測った結果で、0〜32本振ったら正しい答えは0だった。
- **合成された計測値をその一部の指標として使わない。** `loop`は「1行あたりの描画」であってカーネルではない。`PERF`で`kernel=`を分けて出す。

なお、海面の放物線近似（`d266ecf`）は残差を消す目的では不要だった（正体は§2.5・§2.6の数え落とし）が、命令数を62→40に減らしたこと自体は正しく効いており（1.06→0.89ms）有効なので残している。

## 3. このコア上のスカラーコード

### 3.1 float の `/` `sqrtf` `floorf` は関数呼び出しで、逆アセンブルから見えない

**規則**: このコアのFPUに除算・平方根命令は無く、GCCは`__divsf3`/`sqrtf`などのROM呼び出しへ`-mlongcalls`経由で2命令（`l32r`+`callx8`）に割って出す。mnemonic検索や素朴な`grep`では見つからない。呼び出しは演算コストだけでなく、soft-float ABIの引数受け渡し（`rfr`/`wfr`）とレジスタスピルを伴うため、命令数の見た目より重い。

```c
float dx = (x + .5f - 180) / SCALE - p->c.x;   // SCALE は定数。これが呼び出し1本
float d  = dot(a, p->axis[j]) / p->radius[j];  // これも
float m  = fmaxf(0, x);                        // これも
float r  = sqrtf(v);                           // これも
```

`SCALE`がコンパイル時定数でも畳まれない（`1/37.0f`が正確に表現できず、`-freciprocal-math`なしでは逆数乗算に置き換わらない）。GCCはseed命令（`div0.s`/`recip0.s`/`sqrt0.s`）を一度も出さない（イメージ全体で14本見つかるが、すべてWi-FiとROMのコード）。

**なぜgrepで見つからないか**: `-mlongcalls`が`l32r a8, ...`＋`callx8 a8`に割る。`div`をmnemonic検索しても`call8 <symbol>`を検索しても出ない（`__divsf3`はROMの絶対アドレスで`nm`のTにもWにも並ばない）。見つけ方は`callx8 aN`直前の`l32r aN`を辿ってリテラルを解決すること。**もっと安いのは`.s`を出して名前で数える**こと——`l32r`+`callx8`への分割はアセンブラの仕事で、コンパイラの出力にはまだ`call8 __divsf3`と書いてある（`build_*/compile_commands.json`のコマンドの`-c file -o obj`を`-S file -o file.s`に替える）：

```
flower_draw   sqrtf x2  __divsf3 x2   (ray_row と bell_hit を inline したもの)
shade         sqrtf x1  __divsf3 x1  floorf x2

```

最適化の前後で`.s`を2本出して`call8`を数えれば「呼び出しを何本消したか」は数え上げで確定する（時間は§3.2の実測に聞くしかない）。

**`-ffp-contract=fast`が既定**：`flower.c`1ファイルで`madd.s`104本`msub.s`22本。浮動小数の式を並べ替えてビット一致を主張するときは両方の綴りが同じように融合されるか見ること（`x*x+y*y-z*z`は`madd`+`msub`の2命令で丸めは2回のみ）。ホスト側の再現は`gcc -mfma -mavx2 -ffp-contract=fast`（`-ffp-contract=off`と両方通れば並べ替えは融合に依存していない）。

### 3.3 なぜ150〜250という推定が生まれ、外れたか

古い推論：「`sqrtf`は約95命令で188サイクル、ゆえにこのクラスのソフトルーチンは2.0サイクル/命令、`__divsf3`も同規模だから150〜250」。**間違っていたのは2.0のほうではなく「同規模だから」のほう**——単精度のソフト除算は本来短く、95命令は`sqrtf`固有の長さだった。命令数を数えずに「同じクラス」で括ったのが誤りで、比例定数のほうは疑われてすらいなかった。この150〜250は一度も測られないまま少なくとも3つの判断の土台になっていた。推定と実測の差が4倍あるので、この数字を使った過去の見積もりは符号は合っていても倍率は当てにならない。

この巻き上げのフレーム効果を150〜250で予測すると−2.3〜−8.7msだが実測は**−1.33ms**。実測67を入れると4,770×67=320kサイクル=**1.33ms**と一致する——モデルは合っていて定数だけが4倍だった（§3.5の「命令数はサイクルを予測しない」の逆で、ここは本数は完全に予測できていて1本の値段だけが推定だった）。

### 3.4 直し方・スイッチの作法・精度の掃引

**呼び出し本数を減らす**（算術ではなく）：逆数をフレームに1回（`p->radius[j]`→`inv_radius[j]`、bellのvisitごとに6本消える）／除数を共有する（`(-b±sd)/a`は`1/a`を1回）／定数除算を明示的に逆数乗算へ（`x/SCALE`→`x*(1.0f/SCALE)`）／`fmaxf(0,x)`を三項演算子へ（NaN意味論が不要なら完全に等価）。

**半分だけ戻すスイッチは、スイッチが無いより悪い。** `FLOWER_NO_BAND_INVA`は最初、`bell_hit`から6本の除算を外しながらそれを肩代わりする`petal_reciprocals`の6本を両方のビルドに残していた。画素はどちらでも一致するので絵の証明は何も言わず、`petals=`がスイッチをまたいで動かないという形でだけ出る。**切ったビルドで、そのスイッチが変更の全部を戻すことを確認すること**（動かすはずの計器を1つ名指ししておき、動かなければスイッチを疑う）。

**精度は掃引すること。** どれも恒等式ではない——`a/b`と`a*(1/b)`は1ulp違い、判別式の1ulpは`d<0`の反対側に落ちるシルエット画素になる。`tools/test_flower_div.c`が両方の形をビルドして全画素比較する（8種×8位相=207万画素で1画素、緑1段）。「たぶん動かない」ではなく**動く量の上限をテストにする**（§5.6も参照）。

### 3.5 レジスタ溢れ：命令数はサイクルを予測しない

**規則**: 生存集合が使えるレジスタ本数を超えている領域では、命令数の削減がスピル/フィルの往復ごと消えるため、命令数比ではなく圧力の比で効く。命令数からの見積もりは下限にしかならない。**見分け方**: `objdump`で`ssi`/`lsi`（floatのストア・ロード）を数え、`.s`で終わる演算命令と比べる。1:1に近ければその関数は溢れていて、命令数からの見積もりは下限止まり。

**実例（14倍の過小評価）**: `bell_hit`のsetupを`o[j]=dot(origin,axis[j])*inv_radius[j]`（9乗算+6加算）から`o[j]=dx*oax[j]+ob[j]`（3乗算+3加算）に書き換えたとき、命令数から0.2〜0.4msと予測して実測は約2.4ms（1,580→1,163 cy/visit）だった。`ray_row`は浮動小数演算134に対し float ストア45・ロード89——バンドループの生存集合が16本のfloatレジスタを超えて常に溢れているため、演算を1つ減らすとその演算とスピル/フィルの往復が一緒に消える。`shade`も同じ機構で呼び出しを10本消して命令数14%減・時間39%減だった（§3.1のsoft-float ABIの話）。

### 3.6 隠れたフレーム定数：ピクセルに見えて実は(部品,帯)ごとの値だった除算

**規則**: 式に画素の変数が見当たらなくても、複数の局所変数とループの内側にあるというだけで「画素ごとの式」に見えることがある。ループから追い出した除算がループの外に溜まっていないかだけでなく、**追い出されなかった除算がループの中に残っていないか**も見ること。見分ける機械的な方法は§3.1の`.s`の`call8`カウント。

`main/scene/flower.c`の`bell_hit`は6緯度帯それぞれで二次方程式を解く。先頭係数`float dr=slope*d[1]; float a=d[0]*d[0]+d[2]*d[2]-dr*dr;`（`d`=部品の光線方向、`slope`=帯のプロファイル）は**ピクセルを一つも含まない**——`a`も`fabsf(a)<1e-7f`の分岐も`1.0f/a`も、フレームのあいだ(部品,帯)ごとに定数だったが、visitごと・帯ごと・毎フレーム計算されていた。同じループの`2.0f*band/LAT`という**書いてある**除算は`flower_prepare`へ既に巻き上げ済みだったのに、`1.0f/a`という**書いていない**除算（§3.1のとおり逆アセンブルにもmnemonic検索にも出ない）は見落とされていた。

**本数**: 「visitあたり最大6本、ただし全部走るvisitは多くない」が唯一の見積もりだったが、数えたら6本中**4.5〜5.4本**（棄却を生き延びたvisitあたり、`tools/test_bell_reject.c`、14種×24位相）:

| 種 | `disc>=0`（生存visitあたり） |
| --- | --- |
| valley | 4.51 |
| daffodil | 5.35 |
| calla | 4.50 |
| fritillaria | 5.18 |

`disc>=0`の回数は`sqrtf`の回数でもあり巻き上げ前は`__divsf3`の回数でもあった——平方根と除算は同数で、`SPLIT`行の`bell:sqrt`のcallsがそのまま除算の本数（§3.2の測定はこれを利用している）。**数えるときの罠**: `FLOWER_BELL_CHECK`は棄却を計算するが従わないビルドなので、その中でただ数えると棄却済みvisitの帯まで数える（4.5のはずが11.5になる）。出荷ビルドが歩かないvisitは分子からも分母からも外すこと。

**ビット一致**: `p->ba0`は`bd[0]*bd[0]+bd[2]*bd[2]`そのもので、巻き上げ先は`p->ba0 - dr*dr`と元の式と語順を揃えてある。`tools/test_flower_div.c`で14種×8位相×32,400画素=362万画素が完全一致（`-ffp-contract=fast -mfma`と`-ffp-contract=off`の両方）。

### 3.7 `floorf`/`ceilf`をifloor/iceilへ

**規則**: `floorf`/`ceilf`も§3.1の呼び出し。C の `(int)` キャストは`trunc.s`1命令で負の側の丸め方だけが違うので置き換えられるが、「引数は構造上非負」という**値についての主張**で置き換えると、丸め誤差で稀に負へ振れたときに1画素ずれる。代わりに**表現についての恒等式**を使えば前提が要らない：

```c
static inline int ifloor(float x) { int t=(int)x;return t-(x<0.0f&&(float)t!=x); }
static inline int iceil (float x) { int t=(int)x;return t+(x>0.0f&&(float)t!=x); }
```

`(float)t != x`は「小数部があった」そのもので符号がキャストの間違えた向きを選ぶ。`main/scene/flower.c`には6本あった（`shade`のCHECKER市松に2本、`flower_prepare`の画面ボックスに`floorf`2本+`ceilf`2本、最大種で224本/フレーム）。`.s`で数えて置換後は全部0本。

**主張が表現についてなら総当たりで決着する**（§5.6）——`tools/test_flower_floor.c`が2^32個のfloatビットパターン全部をライブラリと突き合わせ、NaN・無限大・intに入らない大きさだけ外して26.5億通り一致（10秒）。条件が無いことが利点で、あとから負を渡す呼び出しが増えても証明し直すものがない。

### 3.8 ハードウェアにseed命令はあるがGCCが出さない

§3.1の「GCCが出さない」は「命令が存在しない」ではない。ハードウェアのseed命令は実在しインラインアセンブリで呼べる（確認済み）：

```
sqrt0.s  rsqrt0.s  recip0.s  div0.s  divn.s  maddn.s
nexp01.s  addexp.s  addexpm.s  mksadj.s  const.s
```

11個すべて`xtensa-esp32s3-elf-gcc`のインラインアセンブリで組み立てが通る（esp-15.2.0_20251204）。一方**`-mhard-float-div`/`-mhard-float-sqrt`/`-mhard-float-recip`/`-mhard-float-rsqrt`はこのツールチェインに存在しない**（`--help=target`にあるのは`-mfused-madd`だけ）——フラグ1つで手に入る話ではなく、Newton-Raphsonの列を手で書く話。

値段の目安：`sqrtf`実測174〜188サイクル、種+2回の反復は10命令台のはずなので当たれば1桁。`bell_hit`は生存visitあたり4.5〜5.4回の`sqrtf`を呼ぶので（§3.6）そこだけでvisitあたり780〜940サイクルが対象になる。**まだ誰も書いておらず、いま書く価値は§3.2の実測（`__divsf3`が推定の1/4）を踏まえると下がっている。** `sqrtf`は依然として最大の項だが単体計測なので信用でき、手書きNewton-Raphsonが買うのは1シーンの1関数であって根拠のある見積もりが取れるまで着手しない、というのが現在の判断（未着手候補としてbacklog.mdにも記載）。書くならISAが定める列をそのまま使うこと——種の精度は実装定義なので反復回数を勘で減らすとビット一致が黙って壊れる。

## 4. 何を最適化するか決める

### 4.1 棄却率は時間の節約率ではない

**規則**: 「visitのN%を棄却する」は「時間のN%を節約する」ではない。落ちる仕事はたいてい平均より安いので、節約は棄却率×**落ちた仕事の条件付きコスト**で決まり、全体平均を使うと外れる。ある画素が早く抜けるのは遠く外れているからで、それはまさにテストが捕まえやすい画素——安い保守的テストは安い仕事を落とす。

```
節約 = 棄却率 x 棄却された visit のコスト
                 ^ 「安かったから棄却できた」もので、平均ではない
```

| テスト | 棄却率 | 実測の時間効果 | なぜ |
| --- | --- | --- | --- |
| `tools/flower-rejection/`（楕円体のspan狭め） | visitの27〜50% | **0.2ms/30ms** | 落とすのは`d<0`で即抜ける最安の画素。関数の時間は残る画素にある |
| 鐘の外接円筒、半径だけ | 21.8% | **2.7%**（2,045→1,989 cy/visit） | 円筒の外の光線は既に6バンド全部を`disc<0`で抜けていた |
| 同、高さ上限つき | 40.8% | **20.6%**（1,989→1,580 cy/visit、下記の注） | 6バンドを`disc>=0`で歩き切っていた光線を落とす |

棄却率は1.9倍にしかなっていないが効果は大きく変わった——落とす対象が変わったため。20.6%の行には注が要る：そのコミット（`714f712`）は高さ上限と**バンド境界のホイストの両方**を含み、409cy/visitはその合計（どちらが何を出したか未分離）。**表に「その変更だけ」と言えるのは2行目だけ。**

**設計の順序**: テストを選ぶ前に、生き残ったvisitが「どこで」落ちているかを数えること。鐘では、円筒を通り抜けてなお外れたvisitの38〜48%が「円錐には当たったがそのバンドの高さの外だった」——高さ上限はそこを狙って書いた。棄却率×**平均**visitコストでの予測（590cy/visit）は実測56に対して外れる。**要るのは条件付き平均。**

### 4.2 疎な仕事では探索が支配する

**規則の裏側**: 「落とす仕事は平均より安い」の裏返しは「**残す仕事を選ぶ判定は、選ばれた仕事より高いことがある**」。

```
sparse な仕事のコスト = 描画 + 「どれを描くか」の探索
                                  ^ 疎であるほど、こちらが支配する
```

**実例**: 庭の光柱に入れた14個の羽虫。見積もりは触れる画素で立てた（14×3画素×2行=84画素、約4.6us）が、「実測」は1.0ms（`pixels` 5.94→6.94ms、200倍）。外したのは画素の数ではなく、その84画素を**見つけるための**14×135=1,890回の行×粒子テスト（ヒットは27〜28個）——描くより描くかどうかを決めるほうが2桁高い。直し方は判定を行からframeへ動かすこと：`garden_prepare`が135語のビットマスクを1回書き、行はそれを1語読んで立っているビットだけを回る（`GARDEN_MOTE_INDEX`）。

**そして、この1.0msという数字自体が誤りだった。** スイッチで測ると`GARDEN_MOTE_INDEX=1`で6.80ms、`=0`で6.86ms（11サンプル平均）——1,863回のテストを消して**60us**（1回あたり8サイクル、計算した127の1/16）。索引は正しくゼロコストだが今日の粒子数では何も買っていない。より悪いのは、それを作らせた1.0msのほうが**群れの無いビルドと有るビルドを比べた値**だったこと——同じカーネルはi-cacheアラインメントでビルド間15%動き（§6.4）、6msの15%は0.9msで、1.0msは自分のノイズの中に入っていた。

教訓は2つ：①棄却率でも命令数でもなく「その仕事は本当に高いのか」を先に測る（8サイクルの判定を1,890回やっても15us）。②2つのビルドを比べるのは測定ではない——1本のツリー・1個のdefine・他は完全に同じ、が唯一差を出せる形（§6.1）。ホスト側では同じ1,890回を回しても0.29ms/frameから動かず差はノイズに沈む（`tools/garden_bench.c`）——「ホストは実機を再現できていない」ではなく**ホストは本当のことを言っていた**（数えられる量1,890→27だけを契約にするのが正しく、それを時間の主張に翻訳したのが誤り。§6.8）。

### 4.3 overlayは毎ストリップ呼ばれる、重なる走査は本数に比例しない

**規則1**: `shell_draw`は`overlay`をストリップごとに毎フレーム**17回**呼ぶ。描画対象がその一部にしか無くても呼ばれる回数は変わらないので、届かないストリップでの色生成・合成は行の範囲チェックで早期に飛ばす。

**規則2**: 同じ領域を複数回走査する描画（掃引の重ね合わせなど）は走査本数に線形では増えない——重なりの分だけ余計に高くなる。

**実例**: 背景に足した飾りが3.3〜4.0ms（`hud` 1.6→5.5、`fps` 23.7→19.9）かかったため取り外した。飾りは56列×4掃引で各列に格子読み2回・混色4回。帯は17本のうち5本にしかかからず、行が届かない掃引を飛ばす1行を足すと色生成回数/フレームが813→201（612回、3/4が捨てられていた）。**画素数からは見えない**——飾りは画素1153に対し合成2369・色生成813だった。省略できるのは「その行がこのストリップに届かないと分かった後の仕事だけ」で、そこが偶然いちばん高かった：`if(bot<y0||top>=y0+height)continue;`（状態更新の後、色生成の前）。

重なる走査の実測：

| 掃引 | 合成/フレーム | 点灯画素 | 画素あたり合成 |
| --- | --- | --- | --- |
| 1 | 690 | 690 | 1.00 |
| 2 | 1197 | 897 | 1.33 |
| 3 | 1751 | 1084 | 1.62 |
| 4 | 2369 | 1153 | **2.06** |

画素は4倍、時間は6〜7倍。この飾りは5往復して見た目を良くし、最後に**測って落とした**——3.3msは林冠を丸ごとベクトル化して得た0.5msの7倍で、朝にHUDのホイストで取り戻した4.4msとほぼ同額だった。見た目の良し悪しではなくカウンタ1つで決まった。

### 4.4 半径は歩幅で買う、区間は形ではない

**規則**: 一極IIRのボケ半径を買うなら係数（極）を上げるのではなく歩幅を上げる。歩幅は半径を歩幅倍に伸ばしつつ触る画素をその分の一に減らすが、極を上げると画素あたりの命令が増えるだけで触る画素は減らない。

| 買い方 | 極 | 最大半径 | px/frame |
| --- | --- | --- | --- |
| 入れ子 | 7/8 | 13.0px | 16,262 |
| 歩幅 | 3/4 | **19.7px** | **6,541** |

画素2.5分の1で半径1.5倍。極7/8が不要になったことで5bitパネルの尾の短さ（極1/2で赤青5・緑6タップ、3/4で8・10、7/8で11・16）からFIR化＝PIE化の道が開く——極を上げると閉じ、歩幅を使うと開く。**外挿の罠**: 画素数だけから費用を外挿すると外れる——実測`px`16,419に対し予測16,262はほぼ完璧だったが動いたのは`cy/px`のほう（22→34、極を上げると1画素あたりの演算が増えるのは当然で、外挿は実際に動く項を固定していた。§3.5の別の現れ方）。

**区間は形ではない**: 行の最左・最右（`tlo`/`thi`）は一区間で、外へD画素広げると斜めや曲がった縁では実際の境界から遠い背景に届き、どの行も同じ端点から同じ量だけ伸びるので垂直な柱＝階段状の矩形になる（「葉から四角い切れ端が生える」「鐘が黒い箱に入る」）。画素ごとの答えは`depth[]`に最初からある——`ray_row`が毎行書き行頭でリセットされ花弁が書かれた画素を持つ。そこから「覆われている、かつ隣が覆われていない」で真の輪郭が取れる（1行240演算、追加記憶ゼロ）。1つの描画器に「行の中の縁」が三つある（`depth[]`の画素単位、`tlo..thi`の区間、それを広げたもの）——効果ごとにどれを指すか言わないと次の効果が同じ矩形を作る。

### 4.5 計器は別の性質を測っていることがある

「厳しいか」より先に「何を数えているか」を問うこと。同じ日に四つあった：

- **入れ子の計器**: `bell:sqrt`は`bell`の内側で計られているのに行はそう言っておらず、七つの数を素直に足すと1.8msの穴が開いて計器が壊れたように見えた（実際には合っていた、入れ子が読めなかっただけ）。
- **書式と引数のずれ**: `ESP_LOGI`にformat属性が効かず、ホストは`#ifdef ESP_PLATFORM`で見もしないのでコンパイラが検出しない。varargsで昇格したfloatのbitが整数枠から出力されていた。`tools/test_flower.c`の`LOGFMT_OK`が唯一available な検査。
- **差ではなく性質を読む必要がある**: 「N視点ある」と「サイズの階段がある」はほぼ同一の四枚が満たす主張。`VIEWS_OK`は画素差を見るので同じ大きさを別角度で撮った四枚は堂々と通る——隣接ショットのサイズ比など性質を読むassertが要った。
- **最強の例**：カメラの`zoom`と`aim`が一度もガラスに届いていなかった（`view_pending`を一人目の読み手が消し二人目が常に0を見ていた）。ショットは数秒離れて採取されるので株の揺れと姿勢が違い、カメラがバイト単位で同一でも画素は違う——「四つの視点がある」の証拠に画素差を使うのは**主張が入力についてなのに出力を比べている**ということだった。今は投影に届いた`cam_s`そのものを検査する。

共通するのは不正確だったのではなく**別のものを測っていた**こと。動いていないのに通り続けるものが危ない。

### 4.6 装飾のスカラーパスは命令数の床の2.4倍かかる

**規則**: 装飾光線のスカラーパスは、命令数から出る床（§2.1の式）の**約2.4倍**かかる（`rays`3.9msの床に対して実測7.6〜13.7ms）。命令を削ってもこの比率では縮まない。次のカーネルを書く前に、そのパスだけを`rsr.ccount`で括り床との比を出すこと。比が§2.6の1.3〜1.4から大きく外れているなら残り時間はメモリ・分岐・パイプラインの側にあり、そこで命令を減らしても当たらない。

**実例（同一バイナリA/B、実機、2026-09-15）**：命令数削減が3回続けて効かなかった。

| 変更 | 性質 | 結果 |
| --- | --- | --- |
| プロファイル評価を35.6%削る | 命令数 | **差なし**（−0.19ms、対照−0.09） |
| 固定小数点sqrt | 命令数 | **差なし** |
| canopyの初期PIEカーネル（`714ec7b`、画素一致） | 命令数 | **差なし**（decor−0.42ms、対照veg−0.75ms、154ペア） |

**効いたのは仕事の置き方を変えた構造変更だった**（§7の表）。命令数を削るだけの最適化は、床の2.4倍という比率そのものを変えない限り効かない。

## 5. 正確性：ビット一致・近似・検証

### 5.1 原則

カーネルは原則として**ビット一致**で書き、近似はそれ以外に手がなくなってから絵を見比べて判断する。海面カーネルだけが近似（`d266ecf`、RGB565が変わる画素10.1%、段差はR/B最大1・G最大2）——表引きを消すのに他の方法が無かったため。ビット一致を原則とする理由は2つ：blendは条件を満たせない入力（グローバルα<255、マスク非整列）でソフト経路にフォールバックするため1でもずれると同じ画面上で段差が見える。海面・波はスカラー参照実装をソースに残せるため、それがアセンブリの唯一の説明になる——近似を入れた瞬間この関係が崩れる。

### 5.2 16bitレーンに収まらない式を書き換える

blendの合成式`s*a + d*(255-a)`は最大65025でsigned 16bitレーンに入らない。恒等式で書き換える：

```
c = min(s,d) + floor(|s-d| * a' / 255)      a' = (s<d) ? 255-a : a
```

`|s-d|`は`VMIN`/`VMAX`/`VSUBS`、`a'`は`EE.VCMP.LT.S16`の結果を`0x00FF`でマスクして`a`とXOR。分岐は要らない。

### 5.3 /255を厳密に計算する

`floor(x/255)`（x≤65152）は`(x + (x>>8) + 1) >> 8`と厳密に一致する（総当たりで確認）。xが16bitに収まらないのでQACC（8レーン×40bit）で計算する：

```
EE.ZERO.QACC
EE.VMULAS.U16.QACC diff, a'      ; QACC = x
EE.VMULAS.U16.QACC k127, k1      ; QACC = x + 127
EE.SRCMB.S16.QACC  q, sh8, 0     ; QACC = x >> 8 = t
EE.VMULAS.U16.QACC diff, a'      ; QACC = t + x
EE.VMULAS.U16.QACC k128, k1      ; QACC = t + x + 1
EE.SRCMB.S16.QACC  q, sh8, 0     ; q = (x + t + 1) >> 8
```

`EE.SRCMB.S16.QACC`（§1.8.54）のシフト量はSARではなくARレジスタから来る。定数1との乗算加算はQACCへ定数を足す常套手段。

### 5.4 丸め方向の違いに注意

**`EE.SRS.ACCX`はfloor、Cの`/`はゼロ方向に切り捨て。** 負で端数があるときだけ1ずれる。C側を`>>`に揃えるほうがカーネル側で補正するより安い。§3.7のifloor/iceilと同種の問題（floorf相当の丸めが欲しい場所でCのデフォルト丸めを信用しない）。

### 5.5 検証の手順

書いたカーネルは実機に載せる前にホストで検証する：

1. **チャネル単位の総当たり**: 合成式やビット複製の展開を入力の全域で参照実装と突き合わせる（blendではs 256通り×dst 5/6bit全値×a 256通り）。
2. **関数丸ごとのランダムテスト**: `-DRENDER_ACCEL_HOST_MODEL`のようなフラグでアセンブリを「同じレーン演算のC」に差し替え、ランダムな矩形・マスク・色で参照実装と`memcmp`。先頭/末尾のスカラー処理とポインタ計算はここでしか担保できない。
3. **起動時の自己検査**（採用は場合による）: バイトスワップでは`board_init`が両実装を同じバイト列に対して走らせ、一致した場合のみPIE版を有効にする。

海面カーネルでは、スカラー版との10.3億通りの総当たりを書き換えのたびに再実行した。

### 5.6 恒等式なら総当たりで決着する

主張が「値について」（引数はいつも非負、など）なら標本でしか確かめられないが、主張が「表現について」（`ifloor`の`(float)t!=x`は小数部の有無そのもの、など）なら総当たりで決着する。`tools/test_flower_floor.c`は2^32個のfloatビットパターン全部を検査して26.5億通り一致（§3.7）。`tools/test_flower_div.c`はULPの掃引で「たぶん動かない」ではなく動く量の上限をテストにする（§3.4、§3.6）。同じ形が`garden_model.c`のlobe逆数の掃引にもある。条件が無いことが利点で、あとから入力が増えても証明し直すものがない。

## 6. 測定方法

### 6.1 最適化には必ずスイッチを付ける

**規則**: 最適化とその計測を同じコミットに入れない。両方入れると効果が分解できなくなる。すべての最適化にコンパイル時（または実行時）スイッチを付け、両方焼いて引き算する。

**実例（分解できなくなった例）**: `bell_reject`（円筒）はそれを測るカウンタと同じコミットで出て、実機の効果は復元不能になり、あとから`FLOWER_NO_BELL_REJECT`を足して測り直すしかなかった。次のコミットは高さ上限とバンド境界ホイストの2つを含み、その次のコミットメッセージは前のコミットの変更をcreditしていた——円筒の21.8%→2.7%がクリーンなのはたまたまカウンタの改名が境界になったからで設計の結果ではない。

```
FLOWER_DIV_EXACT   FLOWER_NO_BAND_HOIST   FLOWER_NO_SPAN_AFFINE
FLOWER_NO_BELL_REJECT   FLOWER_BELL_CHECK   GARDEN_NO_CANOPY_RECIP
```

スイッチは**存在するだけでなくコンパイルが通ることを確認する**こと（4つ作って3つしか通らず、通らなかったのはいちばん必要だった1つ——棄却が無効だと`bell_reject`が未使用になり`-Werror`が止める）。**半分だけ戻すスイッチはスイッチが無いより悪い**（§3.4）。

スイッチは実行時変数にするのが最も安全。`g_board_async`/`g_garden_canopy_pie`/`g_garden_scalar_tweaks`/`GARDEN_NO_MOTES`/`GARDEN_MOTE_INDEX`/`GARDEN_PIE_FUSE`はどれも1バイナリに両方の経路を持ち、§6.4のビルド間15%変動を避ける唯一の形——機能を書くのと同じコミットでスイッチを書くのが唯一の防ぎ方。

### 6.2 同一バイナリの中で窓ごとにスイッチを反転する

同一バイナリの中で、窓ごとにスイッチを反転し隣接する窓のペアで差を取る。その変更で動かないはずの欄（`veg`など）を対照として同時に出し、ノイズ床にする。canopyではdecorの差（中央値−0.61）が対照（−0.75）より小さかったので「差なし」と判定できた（§4.6・§7）。`shell.c`の`SCENE_AB`がPERFの2秒窓ごとにスイッチを1つずつ落とす形（§7の実測はこの方式）。60フレーム窓が2秒窓と揃わない場合は隣接窓の平均とペアにする。

ホストで保証できるのは絵の一致だけ——120フレームのframebufferハッシュをアーム間で比べる（`tools/flower_decor_identity.c`）。**時間はホストでは測れない。**

他リポジトリの実機例題（[esp32s3-hw-mcp](https://github.com/dj-oyu/esp32s3-hw-mcp)）は160MHzで動いている。向こうのµsをこちらの240MHzに持ち込むときはサイクル数に戻してから換算すること。

### 6.3 2つのビルドを比べるのは測定ではない

**規則**: 命令キャッシュのアラインメントで同じカーネルがビルド間で**15%**動く。それ未満の差を主張するなら同一バイナリでの比較が要る。波のカーネルは他の場所にコードを足しただけのビルドで1.30msと1.54msを行き来した（15%、関数配置がずれてi-cache 16KB両コア共有の当たり方が変わるため）。

**実例**: 庭の羽虫探索インデックス（§4.2）で「1.0ms節約」と見えた数字は群れの無いビルドと有るビルドを比べた値で、6msの15%＝0.9msという自分のノイズの中に入っていた。真の効果は同一バイナリのスイッチで測って60usだった。**1本のツリー・1個のdefine・他は完全に同じ、それだけが差を出せる。**

### 6.4 共有ツリーでは、ソースが動いていないかを確認する

複数セッションが1つの作業ツリーを共有するとき、比較する複数のビルドが同じソースから出たことを検査する（1コマンド）：

```
find main components apps -type f \( -name '*.c' -o -name '*.h' -o -name CMakeLists.txt \) -newermt "<開始時刻>"
```

**実例**: A/B/C/Dの4本を作っている30分のあいだに別セッションが`main/main.c`と`main/ui/shell.c`と`main/CMakeLists.txt`を書き替えていた。4本のうちDだけが旧ソース、AとCが新ソースで、気づいたのはAのサイズが2,324,480→2,329,616へ動いたから——**変更を入れていないビルドのサイズが動いたら、それは自分のツリーではない。** 4本まとめて焼き直して上の`find`が空を返してから渡す（窓は4分で済む）。

**「自分が変えたつもりのない変数」を疑うこと**——他人の未コミット変更を拾ったビルドで3回誤った結論を出した例があり、うち1回は「命令キャッシュを32KBにしたら転送が40%速くなった」という物理的にありえない数字で、正体は別セッションが入れたSPIクロックの変更だった。**測定対象の設定値を起動時にログへ出す**のが安い対策（`board.c`が`LCD SPI %d Hz`を出すのはこのため）。

### 6.5 計器が測定対象を変えていないか

**規則**: 計測ツール自身が測定対象を変えていないか確認する。

**実例1**: `loop`という計測値にカーネル以外のものが入っていた（§2.1の海面の例）——海面は水平線より上の37行を1ピクセルずつ塗っており、そこに毎ストリップ2回の`esp_timer_get_time()`（1回0.90µs、フレームあたり30µs）とループの足場が乗る：

| 内訳（OCEAN、1フレーム） | |
| --- | --- |
| 海面カーネル98行 | 0.69ms |
| 空の塗りつぶし37行（スカラー） | 0.08ms |
| タイマ呼び出し34回 | 0.03ms |
| ループの足場・プリエンプション | 約0.09ms |
| **`loop`合計** | **0.89ms** |

これを30ブロック×98行で割ってカーネルのせいにしたのが「残差33サイクル」の正体だった（§2.1）——割り算の分母が間違っていただけ。

**実例2**: JSアプリのベンチマーク`jsperf.py`は0.2秒ごとにEnterを押して再描画を促すため、その間ずっと効果音が鳴っていた。効果音1回の合成に**25.6msのCPU**を使っており（音の長さ59.4msの43%）、`audio_task`は優先度7でIDFがFPUを最初に使ったコアへ自動ピン留めするため描画タスクと同じcore 0に張り付いてCPUを時分割していた。波形を起動時に一度だけ生成する方式（`bf82769`）で解消した。修正後・80MHzでの実測は`turn 1.62 / render 7.92 / send 7.67`。**キー入力で画面を動かす計測は、その入力の副作用ごと測っている。**

### 6.6 合成された指標を要素の代理に使わない

最初に得た「pixels 18.6ms」という数字は、ループ(14.2)・HUD(3.9)・準備(0.9)を混ぜたものだった。分割した瞬間に優先順位が変わった。カーネルを書く前に、まず**削ろうとしている部分だけを切り出して測る**こと。

### 6.7 ホストで証明できるのは不在の証明だけ

ホストは実機のタイミングを再現しない（§4.2）。数えられる量（1,890→27のようなテスト回数）を契約にするのは正しいが、それを時間の主張に翻訳すると誤る。ホストのAB比較（例：`tools/garden_bench.c`が同じ1,890回を回しても0.29ms/frameから動かず差がノイズに沈む）は「この変更が実機で見えないほど軽い可能性がある」の**傍証**にはなるが、実機のnsやmsを主張する根拠にはならない。

### 6.8 最適化のつもりで遅くした例

バイトスワップを16bitずつではなく32bitずつ処理する版を書いたところ転送が16.5ms→24.2msに悪化した——`board.c`はプロジェクト既定の`-Os`でビルドされており4バイトの`memcpy`が関数呼び出しのまま残っていたため。**最適化の前後は必ず実測すること**——「明らかに速いはず」の変更が逆効果になることは実際に起きる。同様に除算をビットシフトや逆数乗算に置き換える試みも測定可能な差が出なかった（このコアにはハードウェア除算器があるため。§3.2）。これは元に戻した。

| **（負の結果、取り下げ）** canopyの描画範囲を`f!=0`で厳密に切り出す | canopy | — | — | 1行+102サイクル（遅くなった、26ペア全て同方向）。ホスト総当たりでは21.3%の画素が恒等だったが実機では棄却判定の方が高くついた（§4.1と同じ形） | 2026-09-15、取り下げ |
| **（負の結果）** バイトスワップを32bit単位に | 全画面転送 | 16.5ms | 24.2ms（悪化） | `-Os`ビルドで4バイトmemcpyが呼び出しのまま残っていたため | 元に戻した |

canopyカーネルの中身：融合ロード9本、ブレンドを`c + (((l-c)·f)>>8)`と書き直して`g=256-f`を省略、`f`とフィールド取り出しはSAR=16の`EE.VMUL.U16`1本ずつ。算術は`canopy_model.c`のFで総当たり検証、アセンブリは`test_kernels.py`の5ブロックまでの模擬実行で検証。全部入りの窓でcanopyは0.69ms/フレーム、1行1,064サイクル。旧カーネル（`31cad81`）との直接比較は無い（旧カーネルはdecor全体の中で「差なし」と測られており、canopy単独カウンタはこの計測で初めて入った）。直接スワップの正しさはソフトからは検証できず（送るバイト列が変わらないという論証のみ、MISO未配線）、表示の物理確認が要る。

庭の行は3つのループ（粗い格子22命令、細かい格子22、画素135→融合後114）でストールはゼロ。画素ループの40個の定数のうち21個が`.LD.INCP`に乗った（`GARDEN_PIE_FUSE`、生成は`tools/pie/fuse_pixels.py`）。融合できる上限は「ホストが空いていること」ではなく**歩く順序**で決まる——定数のwalkはloadの**プログラム順**そのものなので、loadが別のloadを追い越すと2つの定数が静かに入れ替わり、組み立ても実行も通ってどこかの色だけが狂う。候補は`stalls.py`のモデルで両方の綴り（融合版と対照版）を検査してから採用する。`kernel=`は画素ループだけの値ではない（幹・林冠・草はまだスカラーで同じ`garden_row`の中にいる）——内訳は`flower.c`の`SPLIT`行が`pixels=`/`decor=`として出す（予測を2割外した理由は§2.5）。

海面はスカラー版14.2msから通算で**16倍**。

ホーム画面の内訳（現在）:

```
LEVEL WAVE     mode=0 fps=30.3 draw=21.11 | prep=0.99 loop=1.75 (kernel=1.67) hud=2.63 send=15.68
OCEAN + STARS  mode=1 fps=30.3 draw=19.93 | prep=1.06 loop=0.89 (kernel=0.69) hud=2.44 send=15.47
```

`kernel`はベクトル行だけの時間。波は全135行を描くので`loop`とほぼ一致し、海面は水平線より上の37行をスカラーで塗るぶんだけ差が出る（§2.6）。

JSアプリ（組み込みHello World）の内訳。`kernel_ms`はPIEカーネルが自分で数えたサイクル（**SFXによる水増しの経緯は§6.5**、修正後の実測は`turn 1.62 / render 7.92 / send 7.67`、80MHz）:

```
PAINT render_ms=9.52 kernel_ms=3.74 send_ms=21.9 accel=53 software=2
```

**render_msのうちPIEカーネルは4割弱で、残りはRust側のマスク生成**（`composite_mask`のper-pixelループ）。アクセラレータの差し込み口の外なので、PIEでJSアプリをこれ以上速くする余地は小さい（この比率自体は音の有無で変わらない：9.52/3.74と8.1/3.2はどちらも約4割）。

描画カーネルの高速化がフレームレートに効くとは限らない——ホーム画面では`send=15.4ms`が支配的で、海面の`loop`を1.43→1.06msにしてもfpsは30.3のまま動かない。効いたのはJSアプリのblendだけ（`render_ms`がフレーム時間の主要項だったため）。

## 8. 新しいカーネルを書くときのチェックリスト

0. **機械の下限と引き算する。** §2.1のとおり`命令数 + 0.6×ストア数 + ストール数`が下限で、実動作ではそこに3〜4割乗る（§2.6）。`python tools/pie/stalls.py <file> <kernel>`が出す。届いているなら、そこから先は命令を減らすしかない。
1. 削ろうとしている処理を**単独で計測**する。フレーム全体のどれだけを占めるか、その計測値に他のものが混ざっていないかを確認する（§6.5・§6.6）。
2. スカラー参照実装を先に書き、`__attribute__((unused))`で**ソースに残す**（§5.1）。
3. バッファに`__attribute__((aligned(16)))`を付ける。行の途中から始まる場合はスカラーの頭・尾を用意する（§1.3）。
4. SARを1つ決めて先頭で`wsr.sar`、以降のシフトはすべて定数乗算で表現する（§1.2）。
5. **ロード・`VMUL`・`VRELU`の結果を直後に使わない。** 定数は複数レジスタでダブルバッファし、2〜3命令前にロードする（§2.2）。
6. 定数表を歩くポインタは`"=&a"`で宣言する（§1.3）。
7. 本体が256Bを超えるなら`loopgtz`ではなく`addi`/`bnez`を使う（§1.3）。
8. ホストで検証してから実機に載せる。手順は[tools/pie/README.md](../../tools/pie/README.md)：`run_models.py`（式の総当たり）→`test_kernels.py`（アセンブリを命令レベルで実行してスカラー参照と比較）→`stalls.py`（§2.2のストールを静的に列挙）。
9. 実機で計測し、**キャプチャで見た目も確認する。** 数値が良くても絵が壊れていることがある。
10. **書く前に、対象のパスを単独で測って命令数の床と比べる**（§4.6）。床の2倍を超えているなら、カーネルで命令を減らしても当たらない。A/Bは同一バイナリで窓ごとに反転し、対照の欄を同時に出す（§6.2）。
11. すべての最適化にスイッチを付け、最適化とその計測を同じコミットに入れない（§6.1）。
