# 1 フレームの内訳（表示の周期 16 ms、2026-11-09）

[性能と描画の文書](README.md) / [60 fps への道のり](60fps-roadmap.md)

60 fps に向けて「JS と 描画・転送を 2 コアで重ねたら何 ms 縮むか」を決めるために、1 フレーム（`frame()` の周期 1 回）の中身を実機で分けた。[60fps-roadmap.md](60fps-roadmap.md) §4 の「三つの計時の外の 1.5〜5 ms」もこれで分かれた。

## 0. 結論

- **三つの計時（JS・描画・転送）の外は 1 フレーム約 0.85 ms しかない**（実測、どのアプリ・場面でも 0.79〜0.88 ms）。内訳は `app_tick` の中の JS 以外（pump・Kasane の advance など）0.59〜0.72 ms、UI ループの残り 0.15〜0.17 ms。以前の「1.5〜5 ms の差」の大半は、周期の待ちと、ログを書くフレームだった（下の 2 と 3）。
- **周期の刻みで約 0.5〜1 ms 失っている**（実測の値からの推定）。周期 16 ms に対し、仕事が 13.4 ms のパドックでも周期は 16.5 ms になる。仕事が 16 ms を超えるフレーム（レース・STRESS）は、超えた後にさらに 1 tick（`vTaskDelay(1)`、CPU 1 の idle のため）待つので、周期は 17.2〜18.8 ms になる。
- **ログを書くフレームは約 8 ms 長い**（推定）。60 フレームの窓の最長フレームは、パドックでも毎窓 21.7〜22.4 ms（平均の仕事は 13.4〜13.9 ms）。窓あたり `KASANE_PAINT`・`SHIKI_TURN` が 2 行ずつ（と、この計測の `FRAME_BD` が 1 行）出るので、それを書くフレームと見ている（1 フレームずつの時刻は取っていない）。60 fps では 1 秒に 2 フレーム落とす。
- **2 コアで JS と描画・転送を重ねると、DERBY のレースは 1 フレーム約 16.3 ms → 約 9 ms、STRESS は約 17.3 ms → 約 10 ms になる見込み**（推定。下の 4）。重ねない場合に JS をどれだけ削っても、描画と転送の 7〜10 ms は残る。

## 1. 測り方

- 計測: `CONFIG_POCKET_FRAME_BREAKDOWN`（`main/hal/frame_bd.c`、既定 n）。`frame()` の周期 1 回ごとに、JS の turn（続きのターンも含む）、描画、転送の待ち（`present_frame()` のすべての提示）、`app_tick` 全体、UI ループ 1 周の仕事、周期全体を足し、60 周期ごとに `FRAME_BD` を 1 行出す。
  - `tick_other` = `app_tick` − JS − 描画 − 転送。`loop_other` = UI ループの仕事 − `app_tick`。`wait` = 周期 − UI ループの仕事。
  - `late16` / `late33` は 16.7 / 33.4 ms を超えた周期の数。周期は 1 ms の tick で刻まれるので、平均 16.5 ms でも 17 ms の周期が多く数えられる。`late16` は「遅れた」ではなく刻みの粗さを含む。
- ビルド: bce1737（計測、既定 n）＋ 074c058（測定専用: 計測を有効にし、`VM_DISPLAY_PERIOD_MS` を 33 → 16）。測定後に 490ae82 で revert した。
- 実機: ブローカーのジョブ `fbd-derby-1`、`fbd-derby-2`（DERBY、デモのレース）、`fbd-stress-1`（STRESS LV1）。実機は測定後に通常 image（bc96d3f）へ戻した。

## 3. 周期で失っているもの

**(a) 周期の刻み（推定）。** パドックは仕事 13.4 ms、待ち 3.0 ms で周期 16.5 ms。16 ms の周期なら待ちは 2.6 ms のはず。`main.c` は経過時間を ms に切り捨てて残りを tick（1 ms）で待つので、平均で約 0.5 ms 長くなると見ている。60 fps の 16.67 ms ちょうどに合わせるには、µs で期限を持つ待ちが要る。

**(b) 周期を超えたフレームの 1 tick（推定）。** 仕事が 16 ms を超えると、`rest` も `floor_ms` も 0 で、`vTaskDelay(1)` を通る（CPU 1 の idle タスクを飢えさせないため。`docs/kasane/shiki.md` §5.11）。レースと STRESS の待ち 1.1〜1.3 ms はほぼこれで、16.3 ms の仕事が 17.3 ms の周期になる。毎フレームではなく、例えば idle が一定時間走れていないときだけ譲れば、レースと STRESS で 1 フレーム約 1 ms 縮む見込み（推定、未実装）。

**(c) ログを書くフレーム（推定）。** 上の 0 のとおり。出荷版でも `KASANE_PAINT` と `SHIKI_TURN` は 30 フレームごとに出る。33 ms の出荷設定では周期の中に収まるが、16 ms では収まらない。

## 4. 2 コアで重ねたときの見込み（推定）

今は 1 フレームの中で「JS → 描画・転送」を順に回している。JS を片方のコア、描画・転送をもう片方に分け、フレーム N の描画・転送とフレーム N+1 の JS を同時に回すと、1 フレームは和ではなく大きい方になる。

| 場面 | JS 側（JS ＋ tick_other） | 表示側（描画 ＋ 転送） | 今の和 | 重ねたとき（大きい方 ＋ loop_other） |
| --- | --- | --- | --- | --- |
| DERBY レース | 7.8〜9.2 | 6.8〜8.2 | 15.6〜16.9 | 約 8.4〜9.4 |
| DERBY パドック | 4.5〜5.2 | 8.7〜8.8 | 13.4〜14.1 | 約 9.0 |
| STRESS LV1 | 7.5〜7.6 | 9.6〜9.9 | 17.2〜17.5 | 約 10.0 |

- 転送の待ちは、描画が SPI の DMA に追いつかれた時間なので、表示側の下限はバスの速さで決まる。重ねた後も表示側は縮まない。
- 代償（未検討の項目を含む）: Kasane のシーンを JS 側が書き換える間に表示側が読むので、確定したフレームを渡す仕組み（今の `commit` の単位で 2 面、またはロック）が要る。Shiki のヒープ（48 KiB）にはロックが無い。音（`sfx` タスクは CPU 0 に固定）とコアの取り合い。2 コアは flash の命令キャッシュを共有するので、JS の作業集合（約 42 KiB）と描画の作業集合が同じ 32 KiB を取り合う（JS の turn が伸びる可能性）。表示が 1 フレーム遅れる。
- 重ねないで JS を削る場合（`shiki.sinMany`、`drawMany` のまとめ）は、JS 側だけが縮む。DERBY のレースでは JS を 2 ms 削っても和は約 14.5 ms で、60 fps に届くが余裕は小さい（推定）。

## 5. 次の手

1. 3(b) の 1 tick を毎フレームから外す（小さい変更。レース・STRESS で約 1 ms）。
2. 3(a) の周期を µs の期限にする（60 fps の 16.67 ms に合わせる）。
3. 3(c) のログを 16 ms のときは減らすか、書く時刻をずらす。
4. 2 コア化の設計（4 の代償の洗い出し）。共有の命令キャッシュでの JS の伸びを先に測る。

## 6. 待ち方の A/B とメモリ逼迫（2026-11-10、実測）

Fable（コード読解のみ）が出した方針の 1〜4 番を 1 つのビルドで確かめた。`CONFIG_POCKET_FRAME_BD_PACE_AB` が 60 フレームの窓ごとに待ち方を巡回させる。

- `old`: 出荷の規則（周期 16 ms、周期を超えたフレームは必ず `vTaskDelay(1)`）。
- `noyield`: 周期は同じ。超えたフレームの 1 tick は、UI のコア（CPU 1）の idle が 500 ms 走れていないときだけ。
- `deadline`: `noyield` に加え、16,667 µs の絶対期限まで待つ（借りは 1 周期まで）。

ビルドは 48d3491（計測、既定 n）＋ 2c09d21（測定専用）。2d29601 で revert した。ジョブは `pace-stress-1`、`pace-derby-1`。`FRAME_BD` に周期の 1 ms ごとのヒストグラム（`<15, 15, …, 23, ≥24`）、ログ 2 行の時間 `max_log`、超過の 1 tick の回数 `yields`、ネイティブヒープの逼迫フラグが立っていたフレーム数 `press` を足した。

**STRESS LV1**（JS 6.8〜6.9、描画 6.7〜6.9、転送 2.8〜3.0 ms。窓ごとの周期の平均、ms）

| 待ち方 | 窓 1 | 窓 2 | 窓 3 | fps |
| --- | --- | --- | --- | --- |
| old | 18.756 | 18.843 | 18.872 | 53.0〜53.3 |
| noyield | 17.666 | 17.813 | 17.852 | 56.0〜56.6 |
| deadline | 17.662 | 17.411 | 17.626 | 56.7〜57.4 |

- `old` は 60 周期中 47〜49 回 1 tick を払い、待ちが 1.19〜1.29 ms。`noyield` / `deadline` は 0 回で、待ちは 0.17〜0.55 ms。**1 tick を外すだけで 1 フレーム約 1.05 ms 縮む**（同一バイナリ、窓 3 つずつ）。WDT の警告は出ていない（35 秒の範囲）。
- **ログ 2 行（`KASANE_PAINT`＋`SHIKI_TURN`）は 8.56〜8.74 ms**（`max_log`、全窓）。窓あたり 2 回なので、平均で 1 フレーム約 0.29 ms、60 fps では毎秒 2 フレームの落ち。§0 の推定 8 ms を実測で確かめた。
- ヒストグラムの `≥24` に毎窓 2〜3 周期が入る（ログ 2 回 ＋ `FRAME_BD` の行）。

**DERBY パドック**（仕事 13.4 ms）: `old` 16.52〜16.62、`noyield` 16.48〜16.57、`deadline` 16.74〜16.76 ms。`old` でも周期の 23〜34% が 17 ms の区間に入る（ヒストグラム）ので、「周期に収まるフレームはちょうど 16.000 ms」という読みは当たらない。`deadline` は目標 16.667 ms に対して +0.07〜0.09 ms（ログのフレームの分）で、16 と 17 の区間に 2:1 で分かれる。

**DERBY レース**: 場面が窓ごとに変わる（WIDE・FIELD・CLOSE・WIDE 2）ので、待ち方の比較は同じ場面の隣の窓どうしでしか言えない。FIELD（仕事約 14.9 ms）で `deadline` 16.667 対 `old` 16.983、WIDE 2（JS 13 ms 台）で `noyield` 19.83 / `deadline` 19.69〜20.15 対 `old` 22.21〜22.72。今回の WIDE 2 は JS 12〜13.4 ms で、[60fps-roadmap.md](60fps-roadmap.md) の 13〜14.5 ms の場面にあたる。

**メモリ逼迫（新しい発見）**: `press` は**パドックで 0、レースの最初の窓で 39/60、以後のレースのすべての窓で 60/60**。レースの間ずっとネイティブヒープの逼迫フラグ（`FREE` か `LARGEST`）が立ち、`sample_memory_pressure()`（`main/app_session.c`）がゲストの block cache を切っている。入る条件は空き < 24,576 B か最大ブロック < 16,384 B、出る条件は 36,864 B / 24,576 B が 500 ms 続くこと（`main/pocket/pocket_memory.c:18-21`）。block cache が切れたことでレースの JS がどれだけ遅くなるかは、まだ測っていない（同じ場面で逼迫フラグを窓ごとに強制する A/B が要る）。§2 の「レース後のパドックで JS +14%」と同じ原因かも未確認（今回のジョブはレース後のパドックまで届かなかった）。

**まとめ（実測）**: 待ち方の直し（1 tick を条件つきに、µs の期限）で STRESS は 53 → 57 fps、DERBY のパドックは 60.0 fps に合う。STRESS は仕事そのもの（17.2〜17.5 ms）が 16.67 ms を超えるので、待ち方だけでは 60 fps に届かない。

## 7. 出荷に入れた 2 つの変更と、block cache の値段（2026-11-10、実測）

6d04053 で出荷の挙動を 2 つ変えた（881887f は include の順の修正）。

- **周期を超えたフレームの 1 tick を、UI のコア（CPU 1）の idle が 500 ms 走れていないときだけにした**（`main/main.c` の `ui_idle_starved()`、idle hook）。§6 の `noyield` を出荷の規則にしたもの。
- **`ESP_LOG` の 1 行を 384 B のバッファに組んでから 1 回で送る**（`main/hal/usb_console.c` の `log_vprintf`）。行が収まらないときと、他のタスクが同時に書いているときは、元の経路に落とす。静的 DRAM は +384 B と mutex 1 つ。

計測は 48d3491 / 6d04053 の探針に、5b9c3e7（測定専用、周期 16 ms、`POCKET_FRAME_BD_PRESS_AB` と `POCKET_FRAME_BD_LOG_AB` を有効にした版。48070f4 で revert）を重ねたビルドで行った。ジョブは `press-derby-1`（起動直後の DERBY）、`press-stress-1`、`press-derby-2`（STRESS の後の DERBY）。

**ログ（同一バイナリ、窓ごとに切り替え）**

| | 2 行のログの時間 `max_log` | `tick_other` | 周期の平均（STRESS） |
| --- | --- | --- | --- |
| 1 回で送る | 0.85〜0.96 ms | 0.42〜0.45 ms | 17.46〜17.70 ms |
| 元の経路 | 8.59〜8.74 ms | 0.68〜0.71 ms | 18.00〜18.09 ms |

ログのフレームの最長の周期は、DERBY のレースで 23〜26 ms から 17〜21 ms に下がった。元の経路が遅い理由は、libc が unbuffered な stdout に行を小分けに渡し、その一片ごとに `transmit()` がロックを取るためと見ている（推定。小分けの回数は数えていない）。

**block cache の逼迫フラグ（同一バイナリ、窓ごとに「測ったまま／強制 ON／強制 OFF」）**

| 場面 | 測ったまま | 強制 ON（cache を切る） | 強制 OFF |
| --- | --- | --- | --- |
| STRESS LV1（JS、ms） | 6.85、6.92、6.93 | 7.76、7.81 | 6.87、6.97 |
| DERBY レースの FIELD（JS、ms） | 7.23、7.19 | 7.78、7.69 | 7.32 |

- **block cache を切ると JS は STRESS で約 +0.9 ms（+13%）、DERBY の FIELD で約 +0.5 ms（+7%）遅くなる。**
- 今回の 3 つのジョブでは、逼迫フラグは自然には一度も立たなかった（`press=0`）。§6（`pace-derby-1`）ではレースの間ずっと立っていた。違いは分かっていない。どちらも同じ起動の中で STRESS の後に DERBY を動かしている。ビルド（ヒープの配置）、レースの抽選、Wi-Fi の状態が候補。フラグが立った回には、レースの JS がこの分だけ遅れていたはず（推定）。
- 逼迫の閾値（`main/pocket/pocket_memory.c:18-21`）を変えるかどうかはメモリの方針なので、持ち主が判断する。判断の材料は、立った回の頻度と、そのときの空き・最大ブロックの値。

## 8. 逼迫判定の記録と、2 コア化の P0（2026-11-10、実測）

**逼迫判定のログ。** b25ddd1 から、出荷版でも判定のビットが変わるたびに `MEM_PRESSURE mask=… was=… free=… largest=… guest_free=… episode=…` を 1 行出す（`main/pocket/pocket_memory.c`）。0064e75 の探針（`FRAME_P0`）は、窓ごとのネイティブヒープの空きの最小と最大ブロックの最小も出す。

| アプリ・場面 | 判定が立った瞬間（`MEM_PRESSURE`） | 以後の窓の空き最小 / 最大ブロック最小 | 解除 |
| --- | --- | --- | --- |
| DERBY、レース開始（plan を 26 個登録） | `mask=0x2 free=23488 largest=20480` | 26,140〜26,332 / 20,480 B | レースの間ずっと解除されない |
| MEGADEMO、NEWS（plan を 14 個登録） | `mask=0x2 free=24408 largest=21504` | （未取得） | 以後の窓は `press=60/60` |

- 立つのは `FREE`（空き < 24,576 B）のほう。入るのは、plan を登録する一瞬の谷。
- 解除の条件（空き ≥ 36,864 B が 500 ms 続く）は、DERBY のレース中の定常（約 26.2 KB）より約 10 KB 上にある。MEGADEMO も起動時点で空きが 31,388 B しかない。**一度立つと、そのセッションのうちは解除されない**（DERBY は実測、MEGADEMO は起動時の値からの推定）。
- 立つかどうかは毎回同じではない（STRESS の後の DERBY でも、立つ回と立たない回があった）。谷の深さが 24,576 B をまたぐかどうかで決まると見ている。
- 判定が立つと block cache が切れ、JS は 7〜13% 遅くなる（§7）。DERBY のレースで約 0.5 ms、STRESS 相当の負荷で約 0.9 ms。

**P0（[two-core-pipeline.md](two-core-pipeline.md) §5）。** `FRAME_P0` は、`frame()` のターンを最初の join 地点（Shiki の `commit` か Kasane の tx の開始）で分けた時間（`js_pre` / `js_post`）、重ねられたはずの present の割合、UI タスクの空き stack を窓ごとに出す。ジョブは `p0-stress-1`、`p0-derby-1`、`p0-derby-2`、`p0-bigwave-1`、`p0-megademo-1`、`p0b-derby-1`。

| DERBY パドック | 3.9 | 2.53〜2.61 | 1.37〜1.41 | 65% | 60/60 |
| DERBY レース（WIDE・FIELD・CLOSE） | 7.7〜9.1 | 5.87〜7.79 | 1.80〜1.95 | 76〜80% | 60/60 |
