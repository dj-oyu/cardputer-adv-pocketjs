# 拡大縮小画像スパンのソース添字 — 商と剰余の加算ステップ（切替つき）

対象: `perf/kasane-stretch`、基点 `origin/perf/kasane-imgopt` = `8e57dcb`（回転の加算ステップの直上）。
実機には触れていない（`/dev/ttyACM0` は別セッション）。**ミリ秒は 1 つも無い**。ここにある数は
target ツールチェーンの `objdump`/`size`/`nm`/`objdump -d` の実測、ホストで走らせたテストの出力、
そして gcov の行カウント（gcc 12.2 host）である。調査と候補の判断は
`docs/perf/kasane-image-transform-recon.md`、回転側の同型の仕事は
`docs/perf/kasane-image-transform-step.md`。

---

## 1. 変えたもの

`main/ui/kasane/ksn_render.c` の stretch 経路の**画素ごとの 32bit 除算 2 本**を、回転側と同じ
「商と剰余の加算ステップ」に置き換え、`g_ksn_image_stretch_step`（`ksn_render.h`、既定 `true`）で
切り替える。

stretch の逆写像は、宛先列 `dx` に対して

    sx(dx) = source_x + floor((dx*source_width + source_width/2) / width)

で、スパン内で使う添字は **この商の差**である（現行の `image_sample_index` は画素ごとに
`stretch_sample(dx+offset, sw, width) - stretch_sample(dx, sw, width)` を計算していた = 1 画素 2 本）。
分子は `source_width` ずつ進む定数なので、`source_width = q*width + r`（`q = floor(sw/width)`,
`0 <= r < width`）と書くと、同じ除算の商と剰余が

    rem + r >= width なら index += q+1, rem -= width-r
    そうでなければ     index += q,   rem += r

で **1 回の比較と 1 回の条件付き減算**だけ進む（`rem, r ∈ [0,width)` なので桁上がりは高々 1 回、
除算結果と厳密に同じ値になる）。丸めを近似していない。

- 旧経路（`g_ksn_image_stretch_step == false`）は `image_sample_index` に**そのまま残した**
  （`ksn_render.c:198-200` の 2 本の `stretch_sample`）。
- 新経路（既定）は、スパン（宛先 16 画素以下）ごとに `image_read` が**そのスパンの添字を表に詰める**
  （`ksn_render.c:178-185`、`scratch->image.stretch[16]`）。呼び出し側は画素ごとに 1 バイト読むだけ
  （`ksn_render.c:197`）。回転側が `image_read` の中で添字を進めているのと同じ置き方で、添字を
  消費する順序への依存が無い（表は添字そのものなので、呼び出し順が変わっても値は変わらない）。
- 表は 16 バイトで、`ksn_span_scratch` の `image` メンバに足した（96 → 112 B）。
  `sizeof(ksn_span_scratch)+256+8+128 <= 512` の `_Static_assert` は 504 で不変。
- スパンのクランプ（ソース 32 画素を超えないよう `*count` を縮める）は、**同じ値の再計算をやめた**
  （旧: `while(... sample(dx+*count-1) ...)` の判定ごと + 最後に `n` のためもう 1 本。新: 最初の
  1 本を `last` に持ち、縮めたときだけ引き直し、`n` はその `last` を再利用）。削減量は
  **スパンあたり除算 1 本**（実測: 402,563 スパンで 402,563 本）。
- `n` と `dx=start` は同じ値のままで、受け入れ・取得は従来どおり（`0 <= sx < sw` の形は変えていない）。

## 2. 厳密性

1. **算術の総当たり**（ホスト、使い捨ての `/tmp/stretch/sweep.c`）: ソース窓 1..256 × 宛先幅
   1..65,535 の**全組**を 4 つの列で、さらに `count` 1..16 と乱数 20,000,000 組で、
   **1,569,048,152 点**を旧式（画素ごとの 2 除算）と比較して**不一致 0**。同時に
   - クランプ後の `count` / `n` / 開始列が旧ループと一致すること（125,457,664 スパンで不一致 0）、
   - アンカー（`start`）が旧式の分子を割った値と一致すること（不一致 0）、
   - 表の添字が **uint8 に収まる**こと（最悪の添字 **31**。スパンのクランプが 32 ソース画素を
     超えさせない）
   を課している。
2. **既存の独立参照テスト**: `tools/kasane_contract/test_image_render.c` は倍精度の
   oracle（`acos`/`cos`/`sin`/`floor`）と全 32,400 画素を比べる。この文書のコミットで
   **回転 0 の stretch を 40 通り追加**した（宛先幅 1/2/3/16/63/64/65/96 × ソース窓 1/2/3/16/38、
   計 1,296,000 画素）。新経路が既定で通る:

   ```
   image render PASS: crop/scale/alpha/group/retry, 240 moving and 360 stretch PATCH/full comparisons, 40 pure-stretch windows
   ```

   **同じ拡張テストは基点 `8e57dcb` の `ksn_render.c` でも通る**（拡張が新しい差を隠していない）。
   ついでに oracle の形 `floor((2dx+1)*sw/(2*width))` と実装の形 `(dx*sw+sw/2)/width` が
   **全点一致**することを 8,376,576 点で確認した（差 0）。理由: `sw` が偶数なら分子が同じ有理数、
   奇数なら差は `1/(2*width)` だが真値が整数にならない（`(2dx+1)*sw` が奇数なので `2*width` で
   割り切れない）。つまり oracle は実装の丸めをそのまま検証している。
3. **アーム比較テスト（新規）**: `tools/kasane_contract/test_image_stretch_arms.c`。
   1 バイナリの中に両アームを持ち、場面を**アームごとに作り直して**全画素を比べる。出力:

   ```
   stretched panel: 2025 spans for 240x135 destination pixels
   animated stretch track: 120 frames both arms, alternating arm identical, 43692 fetches
   image stretch arms PASS: 131 configs, 259 panel hashes, worst pixel step 0, fetches identical
   ```

   - 131 通りの場面（宛先寸法 8 × ソース窓 6 の比の格子、source 原点 16、clip/不透明度/群 56、
     画面外から入る 20 PATCH の動き 6、フレーム差し替え 2）で、PATCH は**位置と寸法の両方**を
     変える（分母が毎フレーム変わる）。
   - 各場面で「壊れたフレームのアーム」と「全面再描画のもう一方のアーム」を 32,400 画素で比較。
     **最悪の画素差 0**。provider の取得回数も両アームで**一致**することを課している。
   - 120 フレームの animated stretch（位置 + 拡大縮小、回転 0、30 fps、loop）を
     既定・旧・**フレームごとに交互**の 3 通りで回して同一ハッシュ。
   - 非空虚性: 240x135 全面をソース 160x160 で拡大する場面で、provider 取得が
     **ちょうど 15 × 135 = 2,025 回**（= 16 列ごとのスパン 1 回、クランプに入らない）であることを
     課している。スイッチが無視されて経路が 1 本しか無い場合、この数は変わらないが、
     下の 4 がその証明になっている。
4. **スイッチが経路を選んでいること（gcov）**: 同じテストを gcov 付きで
   「全場面 ON」「全場面 OFF」の 2 回走らせ、`ksn_render.c` の行カウントを読んだ。

   | 行 | 全場面 ON | 全場面 OFF |
   | --- | ---: | ---: |
   | 表の格納（`scratch->image.stretch[i]=...`、`:182`） | **5,912,192** | 12,288 |
   | 旧経路の 2 除算（`stretch_sample(...)-stretch_sample(...)`、`:199`） | **0** | **5,899,904** |
   | スパンごとの設定（`:180`、q/r/rem の 3 除算） | 402,563 | 768 |

   ON では**変換画素 5,912,192 点がすべてステップ経路**を通り旧経路は 1 回も走らない。
   OFF では逆に 5,899,904 点が旧経路（画素ごとの除算 2 本 = 11,799,808 本）を通る。
   OFF 側に残る 12,288 = 3 × 4,096 は、animated 場面の**ループ前の REPLACE フレーム 3 枚**
   （テストがスイッチを倒す前に描く既定経路）で、合計 5,912,192 と一致する。
   スパン数 402,563 と変換画素 5,912,192 から **1 スパン = 14.69 画素**（実測）。
5. **コミットをまたぐ確認**: 基点 `8e57dcb` の `ksn_render.c` をそのままリンクした同じテスト
   （スイッチのシンボルだけダミーで与える）で、全 128 場面の集約ハッシュが
   **`211896b2`** で、新しい木の ON / OFF 両アームと同じ値になる:
   4 通りの実行（新 ON / 新 OFF / 基点 / 基点で ON の場面だけ）が同じハッシュを出す。
   つまり**計器を入れた木の OFF アームは変更前の木が描いたものを描いている**。
6. **run.sh 全体**: 基点の木と新しい木で、sanitizer フラグのテキストだけ外した同じ `run.sh` を
   走らせ、出力の diff は**新しいケースの行だけ**（`image render PASS` の語尾と stretch-arms の
   3 行、各 2 回 = 2 つのオプション集合）。他の行は 1 文字も動いていない。

## 3. target `-Os` の実測（命令数・除算・オブジェクト）

`objdump -d` の逆アセンブルから、stretch の 1 変換画素が実際に実行する命令を数えた
（`-Os -std=gnu11 -Wall -Wextra -Werror -Imain/ui/kasane`。IDF の include を足したビルドでも
同じ範囲・同じ数になることを確認済み）。

| 項目 | 基点 `8e57dcb` | 変更後 |
| --- | ---: | ---: |
| `image_sample_index` の stretch 画素経路（回転判定 → 表読み → 戻り） | **18 命令**（`0x9de`-`0xa0d`）、うち **`quou` 2 本** | **9 命令**（`0xa3a`-`0xa4f`）、うち除算 **0** |
| `image_read` のスパン索引表（画素あたり） | 無し（**0**） | **6 命令**（`0x9d8`-`0x9eb`。繰り上がり時 7）: 表の格納 1・比較 1・加算 2・索引 +1・ループ判定 1 |
| **1 変換画素の合計** | **18 命令 / 32bit 除算 2 本** | **15-16 命令 / 除算 0 本** |
| スパン 1 本の除算（実測 14.69 画素/スパン） | **4.02 本**（アンカー 1、probe 1.021、`n` の再計算 1、`dy` 1） | **6.02 本**（設定 3 = `quou`+`remu`+`remu`、アンカー 1、probe 1.021、`dy` 1） |
| **1 変換画素の除算（÷命令）** | **2.27 本** | **0.41 本** |
| `image_read` 全体 | 604 命令 | **637 命令**（両アーム同居。回転前の基点 `e323e56` では 346） |
| `ksn_render.o` `.text` | 6,184 B | **6,308 B**（+124） |
| `.literal` | 44 B | **52 B**（+8: スイッチと表のアドレス） |
| `.rodata`（sine 表 514 + bayer 16 ほか） | 566 B | **566 B**（不変） |
| `.data` | 1 B | **2 B**（スイッチ `g_ksn_image_stretch_step`） |
| `.bss` | 0 B | **0 B** |
| libgcc の呼び出し | `__divdi3` | `__divdi3` のみ（`__moddi3` は出ない） |
| スタック（`-fstack-usage`）: `ksn_render_rects` / `image_read` / `image_sample_index` | 960 / 160 / 32 B | **976** / 160 / 32 B（+16 = スパンの添字表） |

つまり **1 変換画素あたりの除算は 2 → 0 本**（スパンあたりで数えても 2.27 → 0.41 本）、
命令数は 18 → 15-16 で**減る**（表の格納 6-7 と読み 1 の合計が、旧式の掛け算 2 本 + `quou` 2 本 +
引き算 + 分岐より軽い）。増えるのは `.text` +124 B、`.literal` +8 B、`.data` +1 B、
スタック +16 B だけで、`.rodata` と `.bss` は動かない。**DRAM を食う表は増えていない**
（索引表はスパンごとにスタック上で作り直す）。

`image_read` のスパン設定に残った 3 除算（`:180`）は、`q = sw/width` と `r = sw - q*width`、
`rem = numerator - start*width` で、**`q` と `r` は同じ除算の商と剰余**なのに gcc が
`quou`+`remu` の 2 本を出し、`rem` も `remu` に畳まれている（乗算 2 本にできれば -2 本/スパン =
-0.14 除算/画素）。これは「除算を軽い演算にする」話で、この文書の主対象（画素ごとに除算を
呼ばない）とは別なので**測った値だけ残して据え置き**とする。

## 4. 残っているコスト（次の一手）

- スパンあたり 6.02 本の除算のうち **1 本はアンカー**（16 画素に 1 回、回転側と同じ）。
  調査文書 §6 候補 A の残り（アンカーをコマンド先頭から帯／行をまたいで引き継ぐ）は未実装。
  いまの密度では 0.07 除算/画素で、画素ループ本体（15-16 命令）に対して約 2 命令ぶん。
- スパン設定 12 命令 + 3 除算（0.82 命令 + 0.20 除算/画素）は、`image_read` がスパンごとに
  呼ばれる構造から来る。同じコマンドの中で `width` は変わらないので、将来「コマンドごとに
  1 回」に持ち上げる余地はある（今回は 1 コミット 1 関心事のため入れていない）。
- 実機の時間は未測定（この容器では測れない）。除算器の値段（約 16 cycles/本）は
  `/workspace/esp32s3-hw-mcp` の記録からの引用であって、この容器の実測ではない。
