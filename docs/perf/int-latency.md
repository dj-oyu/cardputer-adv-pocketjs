# 整数の掛け算・割り算・シフトのサイクル数（実測、2026-10-31）

Shiki の仕様（[shiki-spec.md](../kasane/shiki-spec.md)）で「積を 64 ビットにしてよい場所」「割り算を置いてよい場所」を決めるために、ベース ISA の MUL32・DIV32 の命令と、GCC が 64 ビットの演算で呼ぶライブラリ関数のサイクル数を、この石で測った。esp32s3-hw-mcp の実測は PIE の命令だけで、TRM はベース ISA の命令のレイテンシを載せていない。これまでの整数の割り算の値（約 16 サイクル、[pie-simd.md](pie-simd.md)）は逆算だった。

- **測り方**: `main/hal/int_latency.c`（[fpu_latency.c](fpu-latency.md) と同じ方法）。各命令 P を、`a8 = x`・`a9 = y` に固定したレジスタで展開した 3 本の列で測る。`thr` は独立な P を 4 本続けたときの 1 本あたり（発行の費用）。`lat` は P の結果を ALU 2 命令（`xor`・`or`、値を変えない）を通して次の P が読む列から、ALU の 2 サイクルを引いたもの（ALU が使う側に見える P の結果のレイテンシ）。`ind` は同じ 3 命令で依存を切った列。7 回の最小値から、空の呼び出しの分を引く。64 ビットの演算は C のループ（volatile の int64 を 2 つ読み、結果を xor で畳む）から、xor だけのループを引く。Shiki の命令は `ksn_shiki_draw` の中で、`REPEAT 200` に同じ命令を 16 個並べた式を 7 回 draw した最小値を 3,200 で割る（値は毎回同じ）。
- **実行**: `apps/shikitest/cycle_bench.js`（`local.cyclebench`、メニューに出さない）を USB broker の `app_session` で起動した。コミット `24efb3a`、ESP-IDF v6.0.1・Xtensa GCC 15.2、COM3、240 MHz。ログは [logs/int-latency-20261031.txt](logs/int-latency-20261031.txt)（broker の app ログの `CB` 行を書き写したもの）。
- **較正**: `add` は thr 1.00・lat 1.00（ALU の依存はストールしない、fpu_latency.c の較正と同じ）。

## 掛け算: ビット幅によらず、発行 1・レイテンシ 2

| 命令 | 値（x, y） | thr | lat |
| --- | --- | ---: | ---: |
| `mull`（32×32 の下位） | 7·3、0x7fff²、0x7fffffff·3、3·0x7fffffff、0x7fffffff²、(−1)²、0x12345678·−0x7654321 | 1.00（0x7fff² で 0.99） | 2.00（0x7fff² で 1.95） |
| `mulsh`（符号付きの上位） | 7·3、0x7fffffff²、(−1)² | 1.00 | 2.00 |
| `muluh`（符号無しの上位） | 7·3、0xffffffff² | 1.00 | 2.00 |
| `mul16s`・`mul16u` | 7·3、0x7fff²、(−0x8000)²、0xffff² | 1.00 | 2.00 |

- **値の大きさにも、16 ビットか 32 ビットかにも依らない。** 16 ビットの掛け算が速いということは無い。32×32 → 64 ビットの積は `mull`＋`mulsh` の 2 命令（独立なので 2 サイクルで発行できる）。
- 結果を次の命令が読むと 1 サイクル待つ（lat 2）。間に独立な命令を 1 つ置けば隠れる。

## 割り算: 値で 2〜13 サイクル、パイプライン化されていない

| 命令 | x / y | thr＝lat |
| --- | --- | ---: |
| `quos` | 7 / 3、0x7fffffff / 0x7ffffff0、3 / 0x7fffffff | **2** |
| `quos` | 0x7fff / 3 | **7** |
| `quos` | 0x7fffffff / 3、0x7fffffff / 0x7fff、−0x7fffffff / 3、0x7fffffff / −1 | **12** |
| `quou` | 7 / 3、0xffffffff / 0xfffffff0 → 2、0xffffffff / 3 → 12 | 2〜12 |
| `rems`・`remu` | 商の場合 + 1（3〜13） | 3〜13 |

- **時間は値で決まる（データ依存）。** 商が小さい（被除数と除数の桁が近い）と 2、15 ビットの被除数で 7、31 ビットの被除数で 12（測った範囲の最大）。除数の大きさだけでは決まらない（0x7fffffff / 0x7fff は商 17 ビットで 12）。式は求めていない。
- **thr と lat が同じ**: 割り算の間は次の割り算を発行できない（パイプライン化されていない）。
- [pie-simd.md](pie-simd.md) の「約 16 サイクル」（逆算）より小さい。測った範囲の最悪で 12。

## 64 ビットの演算（GCC の出力、C のループで測った追加分）

| 演算 | 値 | サイクル |
| --- | --- | ---: |
| `int64 / int64`（`__divdi3`） | 100 / 7 | 88 |
| 〃 | (2^40+123) / 1000003 | 98 |
| 〃 | (2^62+5) / (2^40+7) | 104 |
| 〃 | −2^50 / 12345 | 152 |
| 〃 | (2^63−1) / 3 | **160** |
| `uint64 / uint64`（`__udivdi3`） | (2^40+123) / 1000003 | 87 |
| `int64 % int64`（`__moddi3`） | 同上 | 97 |
| `int64 * int64`（インライン） | (2^40+3)·(2^20+5) | 6 |
| `(int64)int32 * int32`（`mull`＋`mulsh`） | | ループに隠れて 0（−1.00） |
| 同じ積 `>> 16`（定数のシフト） | | 2 |
| `int64 >> 変数`（`b & 63`） | −2^60 >> 37 | **25** |
| `int32 / int32`（C、`quos`） | 0x7fffffff / 3、7 / 3 | 10、0（ループに隠れる） |

- **64 ビットの割り算はライブラリの呼び出しで 87〜160 サイクル**。32 ビットの `quos` の 7〜80 倍。
- **64 ビットの積は安い**（32×32 → 64 は 2 命令、64×64 でも 6）。
- **変数の量の 64 ビットのシフトは 25 サイクル**（32 以上か未満かの分岐を含む GCC のインライン列）。定数のシフトは 2。

## Shiki の命令 1 つ（`ksn_shiki_draw` の中、1 命令あたり）

| 命令 | 値 | サイクル |
| --- | --- | ---: |
| `SET`（床: 取り出し・振り分け・ループの分） | | **50.4** |
| `NEG` | | 55.4 |
| `MUL s=0`（飽和する値） | 0x7fffffff² | 60.7 |
| `ADD`／飽和する値 | 5+7／0x7fffffff·2 | 72.8／76.8 |
| `MUL s=16`／`s=40` | 小さい値・大きい値 | 74.7〜74.8 |
| `SUB` | | 80.7 |
| `SHIFT −5`／`+5` | | 82.7／86.7 |
| `SIN` | | 90.8 |
| `ADD.H`／`MUL.H s=8`／`SHIFT.H +3` | | 76.8／97.7／98.8 |

- **費用の大半は命令 1 つを解釈する費用（約 50 サイクル）**で、演算そのものは 5〜48 サイクル。`MUL` の 64 ビットの積は `ADD` とほぼ同じ。
- **`MUL` は値の大きさに依らない**（小さい値・大きい値・`s` = 16・40 がすべて 74.7）。`s = 0` だけ 14 サイクル安いのは、変数の量の 64 ビットのシフト（上の 25 サイクル）が `s = 0` で省かれるため（推定。コードの経路から）。
- **`.H` はスカラーのエンジンでは 32 ビットより遅い**（`sat16` の分）。`.H` は PIE へ下ろすための命令（仕様 §8.4）。
- **この表はビルドで動く**（実測）: エンジンに `CUBIC`・`LINE_PATTERN` を足した後のビルド（`a53193b`、2026-10-31）で測り直すと、ベース ISA の行と 64 ビットの行は同じ（差は 0.3 サイクル以内）だったが、Shiki の命令は `SET` 60.2・`ADD` 78.5・`MUL s=16` 98.5・`SIN` 84.5 など、+6〜+24 サイクル動き、`SUB`・`SHIFT −5` のように下がった行もある。エンジンのコード（振り分けの `switch` の並びと配置）が変わったためで、命令キャッシュの配置で同じカーネルが 15% 動くこと（CLAUDE.md）と同じ種類。Shiki の命令の費用を比べるときは同じバイナリの中で比べる。この回からベンチは画面に蓋絵（進み具合）を出し、ケースを 2 フレームに 1 回だけ測る（LCD の転送と重ねない）。

## 仕様への含意

1. **積は 64 ビットにしてよい。** 掛け算はビット幅に依らず発行 1・レイテンシ 2 で、Q16 や 16 ビットに制限しても速くならない。
2. **実行時の割り算は 32 ビットに限る。** 64 ビットの割り算は 87〜160 サイクルで、Shiki の命令 1〜2 つ分。32 ビットの `quos` は 2〜12。
3. **費用は命令の数で決まる。** 1 命令の解釈に約 50 サイクルかかるので、演算の幅より命令を減らすことが効く（v1.1 で座標の 0.5 をエンジンへ移した判断、`CUBIC`・`LINE_PATTERN` を 1 命令にする判断と同じ向き）。
4. 実装の注意: `MUL` のシフト量は命令の定数なので、エンジンは変数の量の 64 ビットのシフトを避けられる（`s < 32` と `s ≥ 32` で分ける、など）。測ってから入れる。
