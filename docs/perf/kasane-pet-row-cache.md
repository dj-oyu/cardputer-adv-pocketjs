# PET 画像 provider の重複復号 — 64 行キャッシュ（切替つき）

対象: `perf/kasane-pet`、基点 `perf/kasane-imgopt`（`8e57dcb`）。**実機には触れていない**
（`/dev/ttyACM0` は別セッション）。**ミリ秒は 1 つも無い**。ここにある数は target ツールチェーンの
`objdump` / `size` / `fstack-usage` の実測と、ホストで走らせたテストの出力である。
調査（1 取得あたり約 480 命令、回転 1 フレーム 2,112 取得）は
`docs/perf/kasane-image-transform-recon.md` §4。

---

## 1. 変えたもの

`main/pet/ksn_pet.c` の `read_span` は、**16 画素の要求ごとに 64 画素の行を復号し直していた**
（`pet_pixels_row` 140 命令 + `pet_pixels_face` 118 命令。同じ行が 1 フレームに何度も要求される）。

- 復号済みの行を internal SRAM に保持する（64 行 × 64 画素 × `uint16_t` = **8,192 B**）。
- キーが同じなら復号を飛ばし、変換ループだけを回す。
- 切替 `g_ksn_pet_row_cache`（`ksn_pet.h`、既定 `true`）。`false` で**旧経路そのまま**
  （`read_span` の局所配列へ毎回復号）に戻る。両アームは同一バイナリに同居する。
- ホスト計数 `g_ksn_pet_fetches` / `g_ksn_pet_decodes` は `-DKSN_PET_ROW_STATS` のときだけ存在する。
  **ファームはこの計器を持たない**（`main/pet/ksn_pet.c` の `COUNT_FETCH`/`COUNT_DECODE` は空になる）。

## 2. キーと不活性化規則

| 何が | いつ stale にするか | 実装 |
| --- | --- | --- |
| 借用画像のポインタ | 別の画像を渡すと（同じバイト列でも別アドレスなら）全部落とす | キー比較（4 B） |
| `variant`（ペット 0..11） | 変われば全部落とす | キー比較（2 B） |
| `frame`（mood 0..5） | 変われば全部落とす。**顔の刻印が行そのものに入る**のでキーに要る | キー比較（2 B） |
| 行 `y` | 行ごとに別スロット。有効性は 64 bit のマスク 1 語 | `valid` ビットマップ（8 B） |
| フレーム番号（描画の世代） | **stale にしない**。animated transform は source のバイトを変えないので、ポーズ・回転・拡大が毎フレーム動いても行は有効 | — |

「他に stale にするものが無い」ことの根拠は借用契約である（`main/pet/ksn_pet.h`:
PPT2 のバイト列はこの owner の資源が reset されるまで不変・生存）。したがって
**フレーム境界での一括無効化はしない** — それがいちばん効く（§4 の animated track は
120 フレームで 64 行しか復号しない）。

**最悪ケースは退行しない**: キーが毎回変わる描き方（2 枚の画像を交互に置く、variant を毎フレーム
変える）では行が 1 つも残らず、復号回数は旧経路と**同じ**になる（代わりに 1 取得あたり +16 命令）。
`variant`/`frame` を毎フレーム変えるテスト（`still_scenes`、`rotate_scenes` の variant 掃引）は
その最悪ケースを毎フレーム通っている。

## 3. サイズの根拠（行数を決めた実測）

行数を「1 行」「16 行」「64 行」から選ぶために、**実際の要求列**（合成した provider ではなく
本物の PET provider を本物の compositor 経由で呼び、`read_span` の全要求を記録したもの。ホストの
計数プログラム、**未コミット**。recon §0 と同じ方法）に LRU を当てて数えた:

| 行数 | バイト | 全要求列 355,526 件 | うち animated track 330,420 件 | うち回転 24,522 件 |
| ---: | ---: | ---: | ---: | ---: |
| **1** | 144 | **5.7%** | **5.0%** | 14.2% |
| 4 | 528 | 6.1% | 5.3% | 15.3% |
| 16 | 2,064 | 14.9% | 13.2% | 36.7% |
| 32 | 4,112 | 33.6% | 28.6% | 99.9% |
| **64** | 8,208 | **100.0%** | **100.0%** | 99.9% |

読み方: 回転したスパンの要求は **source の行を掃引し、1 フレームのうちに全 64 行を何度も訪れる**。
作業集合は画像 1 枚ぶん（64 行）で、それより小さいキャッシュは掃引に踏み潰される
（32 行でも animated track は 71% を取りこぼす）。**重複復号を実際に消せる最小の構成は全行**で、
それが 8,192 B である。**1 行キャッシュ（144 B）は measured negative** — 5.7% のために
キー比較と分岐を毎取得に足すだけになるので採らない。

コスト: **8,208 B**（行 8,192 B + `valid` 8 B + ポインタ 4 B + `variant` 2 B + `frame` 2 B）。
`.data` はスイッチの **1 B**。`read_span` のスタックフレームは 160 → **176 B**
（旧経路の局所行配列 128 B は切替の向こうに残るのでスタックは減らない。合成器の 512 B
スクラッチ予算の `_Static_assert`（`ksn_render.c:51`）は変更なしで通る）。

## 4. 実測（ホストのテスト出力）

`tools/kasane_contract/test_pet_row_cache_arms.c` の出力そのまま。取得回数は**アームに依存しない**
（キャッシュは要求そのものを変えない）ので、両アームで一致することを課している。

```
provider arms: 46080 spans, fetches off/on 46080/46080, decodes off/on 46080/4608
animated 120 frames: 330420 fetches in all four arm runs, decodes old/cache 330420/64,
                    alternating arm decodes 165338 of 330420 fetches
  rotation    0 old   arm: fetches    256 decodes    256
  rotation  200 old   arm: fetches   3874 decodes   3874
  rotation    0 cache arm: fetches    256 decodes     64
  rotation  200 cache arm: fetches   3874 decodes      0
  total old   arm: fetches 17590 decodes 17590
  total cache arm: fetches 17590 decodes 64
pet row cache arms PASS: 48495 panel comparisons, worst pixel step 0, hash d6eb4edb,
                        cache decodes 0.019% of the fetches, 64 of 330420
```

- **provider 直接**: 12 ペット × 6 mood × 64 行 × 10 span = 46,080 取得。旧 46,080 復号 →
  新 **4,608 復号**（= 12 × 6 × 64 = 行ごとにちょうど 1 回）。
- **120 フレーム animated transform track**（位置・拡大縮小・2 回転ぶんの回転、30 fps、loop）:
  330,420 取得（4 通りのアーム実行すべてで同一）。**旧 330,420 復号 → 新 64 復号**（= source の
  全行を一度だけ。フレーム 1 で 64 行を充填し、以降の 119 フレームは 1 行も復号しない）。
  フレームごとに交互にアームを切り替えた実行でも、ハッシュも取得回数も同じ（165,338 復号 =
  半分のフレームを旧経路で描いたぶん）。
- **回転 64x64 固定キー**（recon §4 の場面）: 1 フレームあたり 256〜3,874 取得。キャッシュは
  **最初のフレームで 64 行を充填し、以降は 0**。旧アームは毎フレーム取得回数ぶん復号する。
- 比較したパネル 48,495 枚、**最悪画素差 0**、フレームハッシュ `d6eb4edb`。

## 5. target `-Os` の命令数とオブジェクト

`objdump -d` の命令数（recon §2 と同じ数え方: アドレス範囲で数える）。

| 対象 | 基点 | 変更後 | 出所 |
| --- | ---: | ---: | --- |
| `read_span` 全体（両アーム同居） | 83 | **137** | `objdump -d`、`0x00-0x168` |
| うち 検証 + 切替判定 | — | 37 | `0x00-0x63` |
| うち キー比較 + 不活性化（ヒット時） | — | 17 | `0x66-0x91` |
| うち マスク判定 + 行アドレス | — | 10 | `0x92-0xac` |
| うち 充填（ミス時のみ） | — | 21 | `0xb2-0xe3` |
| うち 旧経路（切替 off のとき） | — | 11 | `0xe6-0xfd` |
| うち 変換ループ（16 画素。両アーム共通） | 同上 | 37 | `0x100-0x163` |
| `pet_pixels_row` / `pet_pixels_face` | 140 / 118 | 140 / 118（不変） | `main/pet/pet_pixels.c` |
| `ksn_pet_image` | 17 | 17 | `objdump -d` |

1 取得あたり: **旧 341 = 83 + 140 + 118** → **新 ヒット 101（37 + 17 + 10 + 37）/ ミス 380**。1 行あたりの 258 命令
（行復号 + 顔）がヒットでは 0 になる。削減量を上の実測回数で掛けると:

| 場面 | 取得 | 復号 旧→新 | 命令 旧 | 命令 新 | 差 |
| --- | ---: | ---: | ---: | ---: | ---: |
| provider 直接（46,080 span） | 46,080 | 46,080 → 4,608 | 15,713,280 | 5,939,712 | **−9,773,568（62.2%）** |
| 回転 64x64 固定キー 7 角度 | 17,590 | 17,590 → 64 | 5,998,190 | 1,794,446 | **−4,203,744（70.1%）** |
| 回転 200/1024 の 1 フレーム | 3,874 | 3,874 → 0 | 1,321,034 | 391,274 | **−929,760（70.4%）** |
| animated 120 フレーム | 330,420 | 330,420 → 64 | 112,673,220 | 33,390,276 | **−79,282,944（70.4%）** |

（変換ループは両側とも 1 回として数えている。実際は 16 画素ぶんループするが、両アームで同じなので
差には効かない。差は「行復号 258 命令 + 充填の 21 命令」だけである。）

オブジェクト（`size -A` / `nm -S`、`xtensa-esp32s3-elf-gcc -Os` の単体コンパイル）:

| 節 | 基点 | 変更後 |
| --- | ---: | ---: |
| `.text` | 258 B | **406 B** |
| `.data` | 0 B | **1 B**（切替） |
| `.bss` | 0 B | **8,208 B**（`cache_rows` 8,192 + `cache_valid` 8 + `cache_data` 4 + `cache_pet` 2 + `cache_mood` 2） |
| `.literal` | 12 B | 36 B |
| `read_span` のスタック | 160 B | **176 B** |

**DRAM の増分は 8,209 B**（`.bss` 8,208 + `.data` 1）、flash は 148 B（`.text`）+ 24 B（`.literal`）。
この 8 KiB の正当化は §3 のヒット率の崖だけである — 32 行（4 KiB）では animated track の
71% を取りこぼす。DRAM の予算は `tools/memlog.py` が記録する（この容器ではファームを
ビルドできないので、このブランチでは memlog を取っていない。§7）。

## 6. 厳密性（3 段の証拠）

1. **既存 suite**: `tools/kasane_contract/run.sh` の出力が**変更の前後でバイト単位で同一**
   （`diff` が空）。切替の既定が `true` なので、suite の中の `test_pet_provider.c`
   （12 ペット × 6 mood × 全行 × 全 span を、その場で復号した行と比較する）は**キャッシュ経路を
   通って**通っている。ほかのテストは合成 provider を使うので影響しない = 差が出ないこと自体が証拠。
2. **アーム比較テスト（新規）**: `tools/kasane_contract/test_pet_row_cache_arms.c`。
   1 バイナリに両アームを持ち、場面を**アームごとに作り直して**全パネルを `memcmp` する。
   48,495 枚の比較、最悪画素差 0、4 通りのアーム実行でハッシュと取得回数が一致。
   場面は provider 直接（46,080 span）、crop/stretch の直経路と群経路（variant/frame を毎フレーム
   変えて不活性化を踏む）、全 1024 回転 × 直・群、**同一バイト列を別アドレスに置いた 2 枚の画像**、
   そして 120 フレームの animated transform track（固定アームと、フレームごとに交互のアーム）。
3. **コミットをまたぐ比較**: 基点 `8e57dcb` の provider に**同じテストファイル**を
   `-DKSN_PET_ROW_STATE_ABSENT`（切替も計器も無い）で当てて走らせると、同じ
   `hash d6eb4edb`・同じ 48,495 比較・最悪画素差 0 を出す。つまり off アームは
   **変更前のバイナリと同じ絵**を出し、on アームもそれと一致する。
4. **ASan + UBSan**: 同じテストをそのまま `-fsanitize=address,undefined` でも走らせて通る
   （汚染レポート 0、ハッシュ同じ）。**この段は実装の途中で本物の欠陥を捕まえた** —
   旧経路を分岐の中に書いたとき `decoded[64]` がスコープを抜けて返っており、ASan 無しでは
   黙って動いていた（`main/pet/ksn_pet.c` の局所配列は関数スコープに置いてある）。
   この容器の ASan は起動が不安定なだけなので、通った実行だけを根拠にしている。

## 7. 負っているもの

- **実機の時間は未測定**（この容器では測れない）。主張は命令数と回数の掛け算までである。
- **8,208 B を払う判断はこの文書で確定させていない**。ヒット率は 64 行で崖になる（§3）が、
  DRAM 予算との引き換えは `tools/memlog.py --port --check` の実測で見るしかない。
  ファームのビルドはこの容器では不可能（cmake が `Missing pocketjs_idf_ui_core for esp32s3` で
  停止する）ので、ここにあるのは単体 TU の `size` である。**実機に焼いて `memlog.py` を走らせる
  までは「8 KiB 払ってよい」とは言えない。**
- キーは 1 つだけである。**2 枚の画像を交互に描く画面では効かない**（最悪 = 旧経路、退行はしない）。
  キーを 2 つ持つ（way を分ける）拡張は、その画面が実在してから測る。
- `run.sh` へのテスト登録は入れていない（本タスクの制約）。1 行の追記で済む:
  `main/pet/ksn_pet.c main/pet/pet_pixels.c tools/kasane_contract/test_pet_row_cache_arms.c`
  を `-DKSN_PET_ROW_STATS` つきでリンクする。
- 行数を選んだヒット率曲線は**未コミットの計数プログラム**による（recon §0 と同じ流儀）。
  コミットしたテストが測るのは両アームの回数であって、曲線そのものではない。
