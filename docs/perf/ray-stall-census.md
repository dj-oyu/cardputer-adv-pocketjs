# 装飾光線に余地は無いのか — ハードウェアカウンタで見る（2026-09-20）

「rays はもう速くならない」という主張は、3回の失敗の上に立っていた。Fable はこれを
**証明されていない**と指摘した — 3回の失敗は床の証拠ではなく、命令数の下限の2.4〜3.5倍で
回っていることの説明を誰もしていない、と。

XTPERF がそれを答える。この文書はその測定と、出てきた答えである。
答えは Fable の疑いを支持し、そして Fable の元の予想とは別の場所に着地した。

計測器は `GARDEN_RAY_PERF` ビルドだけに入る（`main/scene/garden.c`、報告は `flower.c` の
SPLIT3 の隣）。PM0 は常に cycles、PM1 は1窓に1イベントで11種を巡回する。

## 0. 最初の測定は嘘だった（読む前に）

最初の実行は `pm0_cy=194,992` を返し、同じ区間の ccount は 48,700,000 だった。**250倍。**
同じ窓の `insn/cycle` は 0.55 で、IPC 0.55 は完全にもっともらしい数字である。

原因は `PMCTRL_KRNLCNT` の読み違えで、これは「`CINTLEVEL > TRACELEVEL` のとき数える」
＝ kernelcnt=1 は**割り込み中だけ数える**。タスクコードは一切数えていなかった。

（当初はここに「`icachemiss` が 0 なのも同じ理由」と書いたが、これも違った。
kernelcnt を直しても 0 のままで、理由は §2.5 にある別のものである。
**一つの誤りで二つの異常を説明できたと思ったのが、二つ目の誤りだった。**）

**`pm0_cy` と ccount の両方を毎回印字していなければ、IPC 0.55 は信じられていた。**
このリポジトリは「もっともらしい間違った数字を返すカウンタは、カウンタが無いより悪い」を
すでに一度学んでいる（`bell_hit` の `div` カウンタ）。同じ罠に同じ形で入り、
同じ場所に置いた交差検査だけが止めた。

## 1. 光線1行のサイクルの内訳

kernelcnt=0 に直したあと。`pm0_cy` と ccount は一致する（例: 50,303,432 対 49.7M）。

| イベント | rays / cycle |
|---|---|
| 命令が退役した | **0.54〜0.57** |
| I_STALL 合計 | 0.27〜0.29 |
| バブル合計 | 0.098〜0.108 |
| D_STALL 合計 | 0.017〜0.021 |

合計 ≈ 1.01。閉じている。**CPI は 1.75。**

I_STALL を割ると、候補として最初に疑ったものが全部消える:

| I_STALL の内訳 | rays / cycle |
|---|---|
| **命令RAM/ROM ビジー** | **0.26〜0.30** |
| FastL32R | 0.027〜0.029 |
| 反復除算 | 0.003〜0.005 |
| 反復乗算 | 0.000 |
| 外部 RunStall | 0.000 |
| **命令キャッシュミス** | **0.000** |

バブルの内訳ではレジスタ依存が 0.042〜0.051、つまりバブルの約半分。

唯一大きいのは命令メモリポートのビジーである。

**当初ここには「整数除算でも乗算でもキャッシュミスでもない」と書いた。前半は正しく、
後半は間違っていた。** §2.5 を読むこと。

## 2. それは rays の性質か、機械の性質か

同じ2本のカウンタで、同じフレームの中で、**pixels パス**（`garden_pixels_row`、PIE の
SIMD カーネル、コードも命令構成もアクセスパターンも別物）を並べて挟んだ。

| | rays | pixels |
|---|---|---|
| 命令退役 / cycle | 0.54〜0.57 | 0.64〜0.67 |
| **命令RAM/ROM ビジー / cycle** | **0.26〜0.30** | **0.20〜0.21** |
| FastL32R | 0.027〜0.029 | 0.016 |
| 反復除算 | 0.003〜0.005 | 0.0035〜0.0038 |
| バブル合計 | 0.098〜0.108 | 0.079〜0.084 |
| レジスタ依存 | 0.042〜0.051 | 0.050〜0.053 |
| D_STALL | 0.017〜0.021 | 0.010 |
| 命令キャッシュミス | 0.000 | 0.000 |

**形の違う2つのカーネルが同じ分数を出すなら、それはどちらの性質でもない。**
命令フェッチ待ちの約20ポイントは rays のものではなく、rays に帰せるのはその上の
6〜9ポイントだけ。この推論はここまで正しく、そして「ではその20ポイントは何なのか」の
答えを §2.5 まで取り違えていた —— 機械の**床**ではなく、機械の**設定**だった。

## 2.5 `I_STALL_BUSY` は命令キャッシュだった（訂正）

`I_MEM_CACHE_MISSES` と `I_STALL_CACHE_MISS` がどの窓でもきっかり 0 だったことを根拠に
「キャッシュミスではない」と書いた。**これは弱い推論だった** — カウンタが永遠に厳密な0を
返すのは「無い」の証拠ではなく「数えていない」の証拠であることのほうが多く、
§0 でまさにその失敗を一度している。今度は交差検査を置いていなかった。

疑うべき理由は既にリポジトリの中にあった:

> 命令キャッシュのアラインメントで、同じカーネルがビルド間で15%動く（CLAUDE.md）

サイクルの2〜3割が flash キャッシュのフェッチ待ちなら当たり前の話で、逆に本当にミスが0
なら配置がそこまで効く理由が無い。この15%は独立した証拠として何年も置いてあった。

**検証はコード0行で済んだ。** `CONFIG_ESP32S3_INSTRUCTION_CACHE` を 16 KB から 32 KB に
するだけ（共有 sdkconfig は触らず複製に対して行い、`-DSDKCONFIG` で指す）:

| / cycle | rays 16KB | rays 32KB | pixels 16KB | pixels 32KB |
|---|---|---|---|---|
| **命令RAM/ROM ビジー** | **0.26〜0.30** | **0.044〜0.056** | **0.20〜0.21** | **0.043** |
| I_STALL 合計 | 0.27〜0.29 | 0.06〜0.12 | 0.22〜0.23 | 0.058〜0.060 |
| 命令退役 | 0.54〜0.57 | **0.72〜0.76** | 0.64〜0.67 | **0.82〜0.83** |
| D_STALL | 0.017〜0.021 | 0.007〜0.010 | 0.010 | 0.003〜0.004 |
| 命令キャッシュミス | 0.000 | 0.000 | 0.000 | 0.000 |

**ビジーは5〜6倍に崩壊し、IPC は 0.55 → 0.75 / 0.65 → 0.83 へ上がった。**
ESP32-S3 の命令キャッシュは Espressif が flash 用に外付けしたもので、LX7 の性能カウンタが
見ている ICache ではない。だからミスは 0 と表示され、その待ち時間は全部 `I_STALL_BUSY`
に出る。**`I_STALL_BUSY` はこの石では「flash キャッシュミス待ち」と読むこと。**

計測器を外した実フレーム時間（FLOWER、PERF 24サンプルの中央値）:

| | icache 16 KB | icache 32 KB |
|---|---|---|
| draw | **31.38 ms**（26.05〜37.27） | **23.56 ms**（21.28〜27.81） |
| send | 1.42 ms | 0.48 ms |
| fps | 29.70（最小 25.90） | 29.80（最小 29.30） |

**−7.8 ms/frame、−25%。** 代償は DRAM 16 KiB
（idle_free 250,032 → 233,632、アプリ実行中の最大連続ブロック 110,592 → 94,208）。
JSアプリ4本（hello / imucal / pet / companion）はいずれも評価を通る。
ビルド間比較なので配置差は乗るが、効果は15%の窓をはるかに超えている。

## 2.6 DRAMを払わずに削る — 出荷ビルドに入っていた計測コード

「16 KiB を払わずに、FLOWER のコードのほうを削れないか」。正しい問いで、まず
**どこが溢れているのか**を分けた。行番号で割ると答えが出る:

| | 早い行(0-15) | 遅い行(16-134) |
|---|---|---|
| istall_busy / cycle | 0.28〜0.29 | 0.22〜0.24 |

**ほぼ一様。** 1フレーム1回の準備コード（`flower_build_botanicals` 9,725 B、
`flower_prepare` 3,135 B、`garden_prepare_layout` 1,916 B）が毎フレーム一掃している
なら早い行だけが跳ねる。跳ねていない以上、**行ループ自身が 16 KB に入っておらず、
走りながら自分を追い出している。** 削る対象は行ループの中にある。

そこで見つかったもの: **シーンの計測ブラケットが出荷ビルドに入っていた。**
`flower.c` に27本、うち**14本が `ray_row` の中**、`garden.c` に14本。それぞれ
`PROF_FENCE`（`"memory"` クロバー）で挟まれているので、命令が増えるだけでなく
コンパイラがまたいでスケジュールできず、生きているレジスタの退避も強制される。
**シーンを測るコードが、シーンそのものを測られる対象にしていた。**

`SCENE_PROF` を立てたときだけ入るようにした（既定は出荷＝無効）。カウンタは
死に書き込みになって最適化で消える。flash −3,760 B、DIRAM −200 B。

| icache 16 KB | draw 中央値 | 最悪 | fps 下限 |
|---|---|---|---|
| 計測あり（従来の出荷） | 31.38 ms | 37.27 | 25.90 |
| 計測なし（現在の出荷） | **29.51 ms** | **32.00** | **29.70** |

**−1.87 ms、DRAM は1バイトも払っていない。** 中央値より最悪値とfps下限の改善が大きい。

ただし §2.5 の 23.56 ms までは届かない。**残り約6 ms はまだキャッシュミスで、
埋めるには 37 KB のシーンからさらに 12 KB ほど削る必要がある。** 次に大きいのは
`flower_build_botanicals` 9,725 B（1フレーム1回、14種の分岐）と `flower_draw`
6,043 B。前者は表駆動にできる形をしており（`tools/make_scene_tables.py` が既にある）、
後者は bell と楕円体の2経路が同じ関数に展開されている。どちらも**未着手**。

## 3. Z の判定

- **「3回失敗したから床だ」は依然として論証ではない。** Fable の指摘は正しかった。
- **しかし測ってみると、rays 固有の余地は小さい。** CPI 1.75 に対し、よく最適化されたと
  見なされている PIE の pixels カーネルが CPI 1.50。差は 0.25、うち命令フェッチ待ちの
  差が 0.06〜0.09。**算術には余地が無い** — 除算0.4%、乗算0%、データ待ち2%、
  レジスタ依存5%。3回の試みが失敗したのは、3回とも算術を触ったからである。
- **そして余地は rays の外にあった。** §2.5 の通り、命令キャッシュを倍にするだけで
  draw が 31.4 → 23.6 ms になる。**カーネルを1行も書き換えずに、
  一日かけた X と Y の合計（−5.2 ms）より大きい。**
- **そして「DRAMを払わずに削る」も部分的に効く。** §2.6 の通り、出荷ビルドに入っていた
  計測コードを外すだけで −1.87 ms。残り6 msは本物のコード削減が要る。
- したがって rays を個別に追うのはここで打ち切る。**根拠は「3回失敗した」ではなく
  「サイクルの内訳がこうなっている」に置き換わった。** それが Z の成果である。

## 4. 代わりに出てきたもの（未解決、rays より大きい）

**描画ループの全コードが、サイクルの約20%を命令キャッシュミスではない命令フェッチ待ちに
払っている。** rays でも pixels でも、そして測っていないが同じ理由で veg でも decor でも
起きているはずである。フレーム全体が30 ms前後なら6 ms規模の話で、これまでこの
リポジトリが個別のカーネルで削ってきた量より大きい。

**原因は特定済み（§2.5）: 16 KB の命令キャッシュに、このシーンのホットコードが入らない。**
当初ここには候補として DMA 競合・キャッシュポート競合・もう一方のコアを挙げたが、
キャッシュを倍にすると消えるので、そのどれでもない。

残っているのは**判断**であって測定ではない。32 KB にすると DRAM を 16 KiB 取る。
この機体は PSRAM が無く、ゲストの部屋は既にこのリポジトリが何度も削って確保してきたもので、
`app_largest` は 110,592 → 94,208 に落ちる。現状の4本は通るが、余裕は減る。
**フレーム時間25%とゲストの16 KiB のどちらを取るかは、測って決まる種類の問題ではない。**

なお `sdkconfig.defaults` に書くと**全ビルドディレクトリの次回ビルドに効く**（CLAUDE.md）。
採用するならそこを意識すること。この節の測定は複製した sdkconfig を `-DSDKCONFIG` で
指して行い、共有の設定には触れていない。
