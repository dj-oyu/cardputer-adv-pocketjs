# Kasane 画像変換（crop / stretch / rotate / アニメーション）の最適化調査

基点 `e323e56`（`perf/kasane-imgopt`、`origin/vm/design-contracts` 上）。2026-09-15。
対象は直近で入った画像プリミティブ 5 コミット（`ec37a10` crop、`bb18d1d` provider、
`4a5495c` stretch、`7f84e93` rotate、`8e6b251` animated tracks、`1c0d8c5` rotate の加算化）。

**実機には一切触れていない**（`/dev/ttyACM0` は別セッションのもの）。IDF ヘッダが無いので
ファームウェアもビルドしていない。したがってここにある値は「target ツールチェーンの
objdump / nm」「ホストで走らせた回数カウンタ」「既存ドキュメントの引用」のいずれかで、
**ミリ秒は 1 つも無い**（ホストでは時間を測れない）。負荷の単位は命令数と回数である。

## 1. 経路の構造

`image_read`（`main/ui/kasane/ksn_render.c:62-103`）が 1 本の入口で、4 つの経路を持つ。
呼び出し側は群の経路（`:244-261`）と直接経路（`:371-383`）の 2 つで、どちらも
**16 画素以下の窓**ごとに `image_read` を呼び、窓の中の画素ごとに
`image_sample_index`（`:104-113`）→ `image_sample_color`（`:118-120`）→
`premultiply_over`（:171）または `blend`（:288）を回す。

| 経路 | 分岐 | 1 画素あたりの座標計算 | 出所 |
| --- | --- | --- | --- |
| crop / 1X | `:91-102`（rotation 0、scale 1X） | 無し。窓の中で source index = 窓内オフセット | `ksn_render.c:111` |
| 2X / HALF | 同上 | dx/dy のシフトのみ（`/2`、`*2`、`:92-93`） | `ksn_render.c:92-93,110-111` |
| stretch | `:94-99`、per-pixel は `:106-109` | **画素ごとに `stretch_sample` 2 回**、各 1 本の 32bit `quou` | `ksn_render.c:58-61` |
| rotate | `:64-90` | **画素ごとに 64bit 除算 2 本**（`u*sw/umax`、`v*sh/vmax`） | `ksn_render.c:76-77` |

rotate の分岐は `1c0d8c5` で「分子を加算で進める」形になっており（`:73` の `u+=2*c,v-=2*s`）、
**trig はホットパスに無い**（正弦は Q14 の 257 エントリ表、`ksn_image_transform.h:4-11`、
`-Os` で 12 命令）。同時に、この変更で `ksn_image_sample`（`ksn_image_transform.h:31-41`）は
**呼び出し元を失った**（`grep -rn ksn_image_sample main/ tools/` が 0 件、`ksn_render.o` に
シンボルも出ない）。つまり「1 画素 1 回の有理除算」は rotate の分岐にだけ残っている。

## 2. 1 変換画素あたりの命令（target `-Os` 実測）

`objdump -d` の命令数。rotate の分岐は `image_read` の `0x540`-`0x677` が
「1 画素ぶんの本体 + 末尾のループ判定」、`0x641`-`0x67c` が「画素を捨てて次へ行く」経路。

| 対象 | 命令 | 出所 |
| --- | ---: | --- |
| `image_read` の rotate ループ本体（1 画素、`u`/`v` の域外判定を含む最長経路） | **121** | `objdump -d ksn_render.o`、`0x540`-`0x677` |
| 同、うち「域外なので捨てる」経路 | 37 | `0x540`-`0x555` + `0x641`-`0x677` |
| `image_read` の rotate 設定部（1 窓 = 16 画素に 1 回） | 140 | `0x3cc`-`0x53b` |
| `__divdi3`（libgcc、**1 画素あたり 2 回呼ばれる**） | **223** ×2 | `objdump -d libgcc/_divdi3.o`（`.text` 606 B、未定義シンボル無しの自己完結） |
| `image_sample_index`（画素ごと。rotate では先頭で `offset` を返す） | 32（うち rotate の早期戻りは約 6） | `objdump -d`、`0x74c`-`0x7a1` |
| `image_color`（画素ごと） | 20 | `0x1c0`-`0x1f9` |
| `blend`（直接経路、画素ごと） | 50 | `0x894` |
| `premultiply_over`（群の経路、画素ごと） | 58 | `0x2ec` |
| `ksn_image_footprint`（コマンドごと、`ksn_image_bound` 58 を含む） | 101 | `0xbc` |

**したがって rotate の 1 変換画素は約 121 + 2×223 = 567 命令**（`image_read` の中だけで。
呼び出し側の `image_sample_index`/`image_color`/`blend` を足すと約 660-670）。
同じ領域の crop は 1 画素あたり約 32 命令（`image_sample_index` の同一戻り +
`image_color` + `blend`）で、差は **画素あたり 2 本の 64bit 除算**にある。

stretch は画素ごとに `stretch_sample` が 2 回（`:108`）で、`-Os` では `image_sample_index`
の中へ展開され、各回が `mull` + 加算 + **`quou`（32bit 除算、`1c0d8c5` 以前の計測で
16-18 cycles/本、`docs/perf/pie-simd.md:233`）** になる。1 画素 = 2 本。

## 3. 1 フレームの変換画素数と取得回数（ホスト実測）

場面は 240x135 のパネル、背景 + 画像 1 枚を REPLACE 全面で描く。カウンタは
`/tmp/imgcount/ksn_render_counted.c`（複製）で数えた。

| 場面 | 変換画素/フレーム | `image_read` 呼び出し | provider のブロック取得 | 取得したソース画素 |
| --- | ---: | ---: | ---: | ---: |
| crop 1X 64x32 | 2,048 | 128 | 128 | 2,048 |
| 2X 64x32 | 2,048 | 128 | 128 | 1,024 |
| stretch 64x32 → 80x40 | 3,200 | 200 | 200 | 2,600 |
| **rotate 64x64 @200/1024 turns** | **6,724**（回転矩形の面積は 4,096） | 492 | **2,112** | **33,792** |
| animated track の 1 フレーム（120 フレームの平均） | **6,585**（最悪 8,464） | 466 | **1,561**（最悪 2,196） | - |

rotate の内訳（実測と計算）:

- 反復する画素数は `ksn_image_footprint`（`ksn_image_transform.h:18-28`）の矩形 =
  **6,724** で、回転した画像の実面積 4,096 の **1.64 倍**。差分
  **2,624 画素（39%）は `u`/`v` の域外判定で捨てられる**が、それでも 1 画素あたり
  37 命令を払う（§2）。この 39% は `ksn_render.c:75` の判定が画素ごとである限り消えない。
- **provider のブロック取得が 2,112 回/フレーム**で、crop の 128 回の **16.5 倍**。
  1 回は 16 画素のソース行ブロックなので、**33,792 ソース画素 = 変換画素の 5.0 倍**を
  読んでいる（回転では隣の画素が別の行・別のブロックを指すため、`:79` の
  ブロックキャッシュが窓の中でほとんど当たらない）。
- 120 フレームの animated transform track（bounds + rotation、30 fps、`:8e6b251` の
  native track）では **1 フレームごとに 1 回の change**（120 フレームで 120 回）で、
  毎回 6,585 画素・1,561 ブロックを描き直す。**アニメーションは新しい経路を
  持たず、rotate の経路を毎フレーム呼ぶだけ**である。

120 フレーム合計（実測）: 回転画素 790,208、うち捨てた画素 331,544、ブロック取得 187,271、
`image_read` 呼び出し 55,936。

## 4. provider / 取得側のコスト

ブロック取得 1 回あたりは `image_read` の外にも仕事がある。

| 対象 | 命令 | 出所 |
| --- | ---: | --- |
| `ksn_core_image_span`（1 取得 = 1 回） | 99 + `payload_read` ×2 + `find_image` | `objdump -d ksn_core.o`、`main/ui/kasane/ksn_core.c:758-782` |
| pet provider `read_span`（1 取得 = 1 回） | 83 | `main/pet/ksn_pet.c:4-17` |
| 同 `pet_pixels_row`（**要求 16 画素でも行 64 画素ぶん復号する**） | 140 | `main/pet/pet_pixels.c` |
| 同 `pet_pixels_face` | 118 | 同 |

つまり pet 画像の回転では、1 ブロック取得あたり約 480 命令（16 画素しか使わないのに
64 画素ぶん復号）が **2,112 回/フレーム**走る。これは 1 フレームあたり約 1.0 M 命令で、
§2 の画素あたりコスト（4,096 × 567 + 2,624 × 37 ≈ 2.4 M）と同じ桁である。

参考: 同じ場面の crop は取得 128 回で、provider 側は約 61 k 命令。

**除算の値段（引用）**: このコアの整数除算はハードウェア除算器で、命令 1 本・約 16 cycles
（`/workspace/esp32s3-hw-mcp` の `measured_costs` id `integer_division_about_16_cycles_back_calculated`、
出所は兄弟プロジェクト cardputer-adv-pocketjs の docs/pie-simd.md からの逆算で、この容器での実測ではない）。
一方 **64bit 除算は libgcc の `__divdi3`（223 命令）呼び出し**で、そちらは 1 本あたり
命令数だけで 16bit 除算の 10 倍以上である。同じ MCP は「除算をシフトや逆数乗算に置き換える試みは
測定可能な差が出なかった（ハードウェア除算器があるため）」も記録しているので、
**残る課題は「除算を軽い演算にする」ことではなく「画素ごとに除算を呼ばない」こと**である。

## 5. 浮動小数と除算

- **target の画像経路に浮動小数は無い**。`ksn_render.o` の未定義シンボルは
  `__divdi3` と `memset`、`ksn_core_*` だけで、soft-float の補助関数
  (`__adddf3`/`__muldf3`/`__divdf3` 等) は 1 つも出ない。
- 浮動小数と三角関数はホスト側のテストの oracle にだけ居る:
  `tools/kasane_contract/test_image_render.c:33-42` が画素ごとに
  `acos(-1.0)`・`cos`・`sin`・`round`・`floor` を回して独立参照を作る。
  **これは実機で走らない**（ホストの検証専用）。
- 除算は rotate で **画素あたり 2 本の 64bit 除算**（`ksn_render.c:76-77`。libgcc の
  `__divdi3`、223 命令/本）。stretch では画素あたり 2 本の 32bit `quou`
  （`:108`）と、窓あたり数本（`:95-98`）。
  被除数 `u*sw` は `w ≤ 240`・`sw ≤ 256` で最大 **2,013,265,920 < 2^31-1**、
  除数 `umax = w*32768` も 32bit に収まる（座標が受け入れられる画素では `u ≥ 0`）。
  **「2 本の 64bit 除算」は 2 本の 32bit 除算と同じ結果を出す範囲に収まっている**が、
  それでも 1 画素 2 本であること自体は変わらない。
- `ksn_image_sin` は表引き + 分岐の 12 命令で、`1c0d8c5` 以降は窓あたり 2 回だけ。

## 6. 何が最適化の対象か

| 候補 | 消える命令/1 変換画素（推定） | 確度 | 備考 |
| --- | ---: | --- | --- |
| **A. rotate の 2 本の有理除算を「商と剰余の加算ステップ」へ** | 121 + 446 → 約 30-40（画素あたり） | 高（算術が厳密に一致することを証明できる。§7） | 窓あたり 2 本の除算（アンカー）は残る: 446 命令/16 画素 = 28/画素 |
| B. 棄却画素（footprint の 39%）を払わない | 2,624 × 37 ≒ 0.10 M/フレーム | 中 | footprint を画素単位で先に解く必要がある。A の後では相対的に小さい |
| C. provider ブロック取得 2,112 回の重複を潰す | 最大 1.0 M/フレーム（pet） | 中 | 行ごとのブロック表が要る。1 フレーム内の重複とは限らない（隣接画素が別行） |
| D. 呼び出し側の画素ごと 3 分岐（`image_sample_index`/`image_color`/`blend`） | 約 102 × 6,724 ≒ 0.69 M/フレーム | 中 | 経路共通。rotate 専用ではない |

**A が本命**である。理由は (1) 消えるのが最大（1 画素あたり約 567 → 約 40 命令）、
(2) `u` が (x,y) についてアフィンで、増分がコマンドごとの定数（`2c`, `-2s`）であること、
(3) 厳密性が剰余付きの加算だけで証明できること（丸めを近似しない）。

## 7. 厳密に一致する加算ステップの形

現行コードは受け入れた画素について

    sx = source_x + floor(u * sw / umax),  umax = w * 32768,  sw = source_width

を計算する（`u ≥ 0` なので C の切り捨て = floor）。`u` は画素ごとに `du = 2c` だけ進む。
`U = u * sw`, `B = umax` と置き、`D = du * sw`（**コマンドごとの定数**）を

    D = q*B + r,   q = floor(D/B),  0 ≤ r < B

と書くと（`D` が負でも q を floor に取れば r ≥ 0）、
`(U_i mod B) ∈ [0,B)` と `r ∈ [0,B)` から `U_i mod B + r < 2B` なので

    U_{i+1} = U_i + D  ⟹  sx_{i+1} = sx_i + q + (rem_i + r ≥ B),  rem_{i+1} = rem_i + r - (B if 桁上がり)

が **1 回の比較と 1 回の条件付き減算**で厳密に出る（画素あたり除算は 0 本）。
`v`/`sy` も同じ（`dv = -2s`、`B = vmax`、`sh`）。

さらに受け入れ判定は除算結果の側に移せる:
`0 ≤ U < B*sw` ⟺ `0 ≤ sx < sw`（`rem ∈ [0,B)` だから）かつ `u≥0 ⟺ sx≥0`。
つまり `u`/`v` の分母スケール判定（`:75`）と**同じ画素集合**を、`sx`/`sy` の
レンジ判定で厳密に表現できる。

アンカー（窓の先頭画素 = 16 画素に 1 回）だけは 64bit の floor/mod が要る（現行と同じ
`__divdi3` 2 本）。負の分子は C の切り捨てを floor に直す 2 命令で合わせる
（`ksn_image_bound`（`ksn_image_transform.h:12-17`）と同じ型の補正）。

この形は `perf/kasane-rowtable`（x 依存の画素値を行ごとの表に畳む）や
`perf/kasane-opt` の「スイッチ + 両アーム同居 + 同一バイナリ A/B」と同じ作法である。

実装した結果（命令数）は `docs/perf/kasane-image-transform-step.md` を参照。精度を落とす
表の候補と多項式の候補は §9・§12 で数字を出して**採らない**と判定した。

## 8. 三角関数と除算の頻度（どこで・何回）

画像変換の経路で sin/cos/atan2/sqrt を計算するのは **1 箇所だけ**である。

| 何を | どこで | 回数（実測、ホストの計数） |
| --- | --- | --- |
| sin/cos の表引き（`ksn_image_sin`、`ksn_image_transform.h:7-11`、12 命令） | `ksn_image_footprint`（同:20）と rotate の設定部（`ksn_render.c:78`） | crop/1X/2X/HALF/stretch の場面: **0 回/フレーム**（`rotation==0` で分岐に入らない。stretch は三角関数を使わない）。rotate 64x64: **1,018 回/フレーム** = 変換画素の **0.151 回/画素**（= 16 画素の窓あたり 2 回 + 帯あたり 2 回）。animated track の 1 フレーム: 1,054 回 / 7,396 画素 = 0.142 回/画素 |
| `ksn_image_footprint`（101 命令、うち `ksn_image_bound` 58） | 群の bounds パス、直接経路のコマンドごと、`command_bands`（damage） | rotate の全面フレームで **17 回/フレーム**（= 帯ごと 1 回）、animated の damage フレームで **11 回/フレーム** |
| **除算** | rotate: `ksn_render.c:76-77` で **64bit 除算 2 本/画素**。stretch: `:108` で **32bit `quou` 2 本/画素** + 窓あたり数本（`:95-98`、実測 7,200 呼び出し/3,200 画素 = 2.25 回/画素） | crop/2X/HALF: **0 本/画素** |
| atan2 / sqrt / pow / libm | main/ui/kasane と main/pet に **1 つも無い**（`grep -rn "sqrt\|atan2\|pow(\|acos\|double"` が 0 件。`ksn_render.o` の未定義シンボルは `__divdi3`/`memset`/`ksn_core_*` のみで soft-float 補助関数が無い） | - |
| 浮動小数の三角関数 | **ホストのテスト oracle だけ**（`tools/kasane_contract/test_image_render.c:33-42` が画素ごとに `acos(-1.0)`・`cos`・`sin`・`floor`）。実機では走らない | - |

**三角関数は 1 変換画素あたり 0.14 回の表引き（12 命令）で、画素ごとではない。**
window あたり・コマンドあたりの仕事であり、`docs/perf/pie-simd.md` の言う「per-pixel の
ジャックポット」ではない。**触る価値が無い側である**（画素あたりに換算して約 1.7 命令、
同じ画素の rotate 経路が 567 命令）。除算は rotate で 2 本/画素、stretch で 2 本/画素のままで、
こちらが画素あたりのコストの本体である（§7 の候補 A）。

## 9. 正弦表の形・精度と、より小さな表のコスト（実測）

`ksn_sine_quarter`（`ksn_image_transform.h:6`）の形:

| 項目 | 値 |
| --- | --- |
| エントリ数 | **257**（int16、`static const`、.rodata = flash） |
| 固定小数 | **Q14**（16384 = 1.0） |
| 生成 | `round(sin(i*pi/512)*16384)`（1/4 波、i = 0..256） |
| 対称 | 1/4 波 + 折り返し。`index = (quadrant&1) ? 256-index : index`、`quadrant>=2` で符号反転 |
| 添字 | `angle &= 1023`（**1024 分割/回転**）。`quadrant = angle>>8`、`index = angle&255` |
| 大きさ | 表 514 B（257×2）。`ksn_render.o` の `.rodata` は **566 B**（表 + `bayer4` 16 B + `shifts[4]` 16 B など）。基点 `e323e56` の値で実測 |

**精度はパネルに対して「余っている」のではなく「ちょうど足りている」。**
出荷表と倍精度の理想 sine（`round(cos/sin*16384)`）を、1024 回転 × 240x135 の全画素
（33,177,600 画素評価、うち受け入れ 4,194,768）で比べた実測:

```
shipped Q14 table vs ideal double sine: source index differs for 0 of 33,177,600 destination pixels, worst step 0
```

つまり**現行の表はこの解像度で 1 画素も動かない**（表の量子化誤差は、受け入れ判定と
ソース添字のどちらも変えない）。したがって「精度は粗くてよい」は、**現行より粗くすると
必ず画素が動く**という意味になる。粗くしたときの実測コスト:

| 表 | .rodata | 表引きの差で受け入れが変わる画素 | ソース添字が変わる画素 | 合成後の画素が変わる画素 | 最悪のソース移動 | 最悪の RGB565 段差（和/127） |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| **257（現行）** | **514 B** | 0 | 0 | 0 | 0 | 0 |

   2 回読まれる」までで、514 B は数回のアクセスで温まる量である。

## 10. 表はレジスタに入るか、多項式で置き換えられるか（表ごと）

LX7 には**動的に添字を選べるレジスタファイルが無い**（命令語のレジスタ指定子は即値フィールド
である。例: `EE.MOVI.32.Q` の命令語は `as[3:0]`・`qs[2:1]`・`sel4[1:0]` を語の中に持つ —
`/workspace/esp32s3-hw-mcp` の `get_instruction EE.MOVI.32.Q`、TRM 1.8 p119）。
したがって表をレジスタへ置けるのは **添字が静的な場合だけ**で、画素ごとに変わる添字は
レジスタでもメモリでも同じ「ロード」であり、レジスタ化は効かない。

| 表 | エントリ | 添字の種類 | 画素ごと? | レジスタ/ブロードキャスト | 多項式にする価値 |
| --- | --- | --- | --- | --- | --- |
| `ksn_sine_quarter` | 257×int16 = 514 B（.rodata） | **per-command / per-span の即値インデックス**（角度はコマンドの定数。`angle&1023` で表サイズにマスク） | いいえ（0.151 回/変換画素） | 表引きの**結果**（`c`,`s`）は既にレジスタのスカラで、その先は全部レジスタ演算。最適化後は `c`,`s` が span ごとの `qu/ru/qv/rv` に畳まれる。PIE へブロードキャストする経路（`EE.MOVI.32.Q qs, as, sel4` = AR→QR の 1 レーン書き込み、sel4 は即値。TRM 1.8 p119 / MCP）は、**この木では画像合成がスカラ**（`ksn_blend_pie` は `main/CMakeLists.txt` に入っていない）ので使う相手が無い | **いいえ**。1/4 波を多項式で近似すると次数 2〜3 + 象限・符号の処理で 10〜15 命令になり、12 命令の表引きに勝てない。しかも 0.151 回/画素なので差は 1 画素あたり 0.5 命令未満。浮動小数にすると更に悪い（このコアの FPU に除算・平方根命令が無く GCC は seed 命令を出さない — MCP `no_fpu_divide_or_sqrt_and_gcc_never_emits_seeds`。`__divsf3` は 55〜67 cycles の実測 — MCP `divsf3_55_to_67_cycles`） |
| `bayer4`（`ksn_render.c:114`） | 16×uint8 = 16 B | 画素ごと（`x&3`,`y&3`）の動的インデックス | はい、ただし **dither 経路だけ**（画像変換は `dither=false` で通るので触らない） | 不可（動的添字） | 無意味（4x4 のパターン）。16 B で 1 行に収まる |
| rotate のブロックスクラッチ（`ksn_render.c:49`） | 16+16 エントリ = 48 B | 画素ごとの動的インデックス | はい | 不可。ただし**スタック（SRAM）であって flash ではない**ので、表引きの遅さは無い | 無意味 |
| 最適化が足すコマンド定数（`qu/ru/qv/rv`、`umax/vmax`） | 4〜6 スカラ | コマンドごと | いいえ（16 画素に 1 回） | **既にレジスタのスカラ**。ベクトルに配る相手が無い | 対象外 |

**結論（measured negative として確定）**: 画像変換の表は (a) 動的添字の小さなパターン
（`bayer4`、ただし経路外）と (b) **コマンド/span ごとの即値添字**（sine 表）だけで、
**per-pixel の動的添字は 1 つも無い**。sine 表は引いた結果が即スカラレジスタになり、
その先の画素ループはレジスタだけで回っている。レジスタ化・ブロードキャスト・多項式化の
どれも、この経路では命令数も flash アクセスも減らさない。

## 11. 逆写像の導出単位と、増分ステップの厳密性

| 問い | 答え | 出所 |
| --- | --- | --- |
| 逆写像（destination→source のアフィン）はどこで導出されるか | **コマンド/span ごと**（16 画素に 1 回）。`ksn_render.c:78-85` が `c`,`s`,`w`,`h`,`umax`,`vmax`,`u`,`v` を作る。画素ごとに三角関数も係数も作り直さない | `ksn_render.c:78-85` |
| 画素ごとに残る計算 | 分子の加算（`u += 2c`, `v -= 2s`）と**有理除算 2 本**（`:76-77`） | 同上 |
| `1c0d8c5` の増分は厳密か | **分子は厳密**（`u` は int64 で `2c` ずつ加算。丸めは無い）。ただし**商は画素ごとに割り直していた**ので、その意味では「厳密だが除算は画素ごと」だった | `1c0d8c5` の差分、`:73` |
| 最適化後のステップは同じ丸めか | **同じ**。`floor(U/B)` と `U mod B` の組を、`D = q*B + r`（`q = floor(D/B)`, `0 <= r < B`）として `rem += r; q + (rem >= B)` で進める。`rem, r ∈ [0,B)` なので桁上がりは高々 1 回で、除算結果は画素ごとの整数除算と**同じ値**になる。負の増分も q を floor に取ることとアンカーで切り捨て商を floor に直すことで同じ | §7、`docs/perf/kasane-image-transform-step.md` |
| 受け入れ判定は同じ画素集合か | **同じ**。`0 <= U < B*sw` ⟺ `0 <= floor(U/B) < sw`（余りが `[0,B)` のため）。よって `u<0 || u>=umax` の判定と `sx<0 || sx>=sw` の判定は同値 | §7 |

厳密性の証拠は 3 段: ①算術の総当たり（852,295,680 点で不一致 0、`/tmp` の使い捨て）、
②既存の独立参照テスト（`test_image_render.c` は倍精度 oracle で 32,400 画素 × 360 回転
ケースを比較。既定でステップ経路を通る）、③アーム比較テスト
（`tools/kasane_contract/test_image_rotate_arms.c`）。

## 12. 表ごとの資源・読み出し頻度と、多項式（MAC）で置き換えられるか

「小さい表にして flash を削る」「多項式にしてロードを消す」の判断に要る値を、表ごとに分けて
target オブジェクトと実行回数の実測から並べる。**flash と DRAM は別の資源である**:
`.rodata` の `const` 表は flash に置かれ flash キャッシュ越しに読まれる。**表を消しても DRAM は
1 バイトも空かない**（DRAM を空けたいなら SRAM に置いた配列を消すこと）。この経路で DRAM を
食っているのは表ではなく**スクラッチ**である（`ksn_span_scratch` 96 B + 群の tile 256 B +
provider 行 128 B = 512 B 予算、`ksn_render.c:45-51`。いずれもスタック）。

| 表 | 何を保持するか | 添字 | 読み出し頻度（実測） | flash | DRAM | MAC 多項式に置き換えられるか |
| --- | --- | --- | --- | ---: | ---: | --- |
| `ksn_sine_quarter`（`ksn_image_transform.h:6`） | **滑らかな関数**（sin 1/4 波、Q14） | コマンド/span の即値（`angle&1023`） | rotate 64x64 で **1,018 回/フレーム = 0.151 回/変換画素** | **514 B**（`nm -S` が `ksn_sine_quarter` 0x202 = 514 B） | 0 B | 置き換えても**得しない**（下表） |
| `bayer4`（`ksn_render.c:114`） | **パターン**（4x4 閾値、非関数） | 画素ごとの動的（`x&3`,`y&3`） | **画像変換経路では 0 回**（画像は `dither=false` で通る）。dither を使う他経路のみ（`kasane-opt-survey.md` の demo 場面で 4,320 画素/フレーム） | 16 B | 0 B | **不可**。パターンは関数ではないので多項式化の対象外（規則: パターンと線形ランプは置き換えない） |
| `interpolate` の `shifts[4]={24,16,8,0}`（`ksn_render.c:154`） | **線形ランプ**（シフト量） | 4 回展開される静的な反復 | gradient のみ（画像変換では 0 回） | **0 B**（`nm` にシンボルが無い = gcc が即値へ畳んだ。`ssai 24/16/8/0` 相当が命令に埋まっている） | 0 B | **不可/不要**。ランプ 1 対は引き算 1 本で、表より安い |
| 回転ブロックのスクラッチ（`ksn_render.c:49`、`block_rgb[16]`+`block_alpha[16]`） | 表ではなく**データ**（provider が返した 16 画素） | 画素ごとの動的 | 取得 1 回につき 1 回読み（0.31 回/画素） | 0 B | **48 B（スタック）** | **不可**。動的な添字の配列は多項式にできない |

**sine 表を多項式（整数 Horner）にした場合の実測**（同じ掃引: 1024 回転 × 240x135 = 33,177,600 画素評価。
係数は表そのものの最小二乗フィット、評価は target と同じ整数形）:

| 候補 | 係数が表と違う回転 | 受け入れが変わる画素 | ソース添字が変わる画素 | 最悪のソース移動 | 合成後が変わる画素 | 最悪 RGB565 段差 | **命令数**（target `-Os`、同じ呼び出し規約） |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 表引き（現行） | 0/1024 | 0 | 0 | 0 | 0 | 0 | **12** |
| 4 次 Horner | 1,020/1024 | 928 | 13,984 | **2 px** | 12,816 | 69/127 | 31（int32 形）/ 39（int64 形） |
| 5 次 Horner | 1,012/1024 | 1,024 | 13,488 | **1 px** | 12,344 | 69/127 | **31** |

読み方: 5 次（5 MAC）でも**表の整数値を再現できない**（最悪 1 ソース画素の移動、13,488 画素が動く）。
そして命令数は 12 → 31 と **2.6 倍**。1 変換画素あたり 0.151 回しか使われないので、
多項式にすると画素あたり **+2.9 命令**（(31−12)×0.151）を払って絵が動く。
**判定: 置き換えない（measured negative）。** 規則（「最悪ステップ ≤ 1 かつそれを明言する場合のみ
近似を許す」）に照らすと 5 次は最悪 1 px で条件は満たすが、*安くならない*ので採る理由が無い。
実装もしない（既定 OFF の近似を増やすだけになる）。

**優先順位の規則（per-pixel 動的添字の表が本命）に照らした結論**: この経路に per-pixel 動的添字の
**関数表**は存在しない。per-pixel の動的添字は (a) `bayer4`（パターン、かつ経路外）と
(b) スタックの画素ブロック（表ではなくデータ）だけで、sine 表はコマンド/span ごとに引かれる。
つまり **MAC 多項式route が払う相手がこの経路には居ない**。コマンドごとの表は 1 回のロードで
足りており、≤32〜64 エントリで 2 ラインに収まる表は既に実効レジスタ速度である。
定数表をレジスタへ上げる話も同様に空振りする（§10）。
