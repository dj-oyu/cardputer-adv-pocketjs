# 画像スパンの変換コスト削減（回転・拡大縮小）

> 吸収した旧文書: `kasane-image-transform-step.md`、`kasane-image-transform-anchor.md`、`kasane-image-transform-reject.md`、`kasane-image-transform-stretch-step.md`。各節の中の節番号（§N）は旧文書のものを保つ。

`main/ui/kasane/ksn_render.c` の画像スパン（回転と拡大縮小）から、画素ごとの除算・アンカー計算・域外判定を順に外した4段の記録。どれも切替つき・厳密（出力画素は変わらない）・既定は有効で、出荷済み。調査と候補の判断は [kasane-image-transform-recon.md](../archive/perf/kasane-image-transform-recon.md)。

読む順は step（回転の商・剰余ステップ）→ anchor（アンカー表）→ reject（域外判定）。stretch-step は拡大縮小側の step と同型の仕事。

## 回転スパンのソース添字: 商と剰余の加算ステップ（旧 kasane-image-transform-step.md）

対象: `perf/kasane-imgopt`、基点 `origin/vm/design-contracts` = `e323e56`。
実機には触れていない（`/dev/ttyACM0` は別セッション）。**ミリ秒は 1 つも無い**。ここにある数は
target ツールチェーンの `objdump`/`size`/`nm` の実測と、ホストで走らせたテストの出力である。
調査と候補の判断は `docs/archive/perf/kasane-image-transform-recon.md`。

---

### 1. 変えたもの

`main/ui/kasane/ksn_render.c` の `image_read` の rotate 分岐に、**厳密に同じソース添字を出す
加算ステップ経路**を足し、`g_ksn_image_rotate_step`（`ksn_render.h`、既定 `true`）で切り替える。

- 旧経路（`g_ksn_image_rotate_step == false`）は**そのまま残した**。1 画素ごとに
  `u*sw/umax` と `v*sh/vmax` を 64bit 有理除算で求める（`ksn_render.c:83-101`）。
- 新経路（既定）は、同じ `floor(U/B)` と `U mod B` を **1 画素あたり加算・比較・条件付き減算
  だけ**で進める（`ksn_render.c:102-146`）。除算は **16 画素の窓に 2 本**（アンカー）だけ。
- 受け入れ判定もソース添字側へ移した（`0 <= U < B*sw` ⟺ `0 <= sx < sw`）。同値である理由は
  調査文書 §7・§11。
- `!sw || !sh || !w || !h`（退化した窓）と `rotation == 0` は従来どおりの経路に入る。
  スイッチは**変更の全部を戻す**（切ればアンカーの除算も含めて旧経路に戻る）。

増分の定義は調査文書 §7 のとおり: `D = du*sw` を `D = q*B + r`（`q = floor(D/B)`, `0 <= r < B`）に
分け、`rem += r` が `B` を跨いだら `q+1` を足して `rem -= B`。`rem, r ∈ [0,B)` なので跨ぎは
高々 1 回で、条件は `rem >= B - r` と書き換えて**加算のオーバーフローを避けている**。

## 回転スパンのアンカーを行ごとの表へ（旧 kasane-image-transform-anchor.md）

---

### 1. 変えたもの

`main/ui/kasane/ksn_render.c` の `image_read` の rotate 分岐で、**スパンごとに払っていた
64bit 除算 2 本（`__divdi3` を 2 回）を行ごとのアンカー表からのロードに置き換えた**。
切替は `g_ksn_image_rotate_anchor`（`ksn_render.h`、既定 `true`）。切れば全てのスパンが
従来どおりその場で割る（前コミットのステップ経路も、`g_ksn_image_rotate_step` を切れば
さらに前の画素ごと有理除算経路に戻る）。

#### 表の中身と作り方

アンカー（スパン先頭画素の `floor(U/umax)` と `U mod umax`、`U = u*source_width`）は
`x` についてアフィンである。16 画素ぶんの分子の増分 `D16 = 16*du*source_width` を
`D16 = q*B + r`（`q = floor(D16/B)`, `0 <= r < B`, `B = umax`）と書くと、
**画素ごとのループと同じ桁上がり規則**（`rem >= B - r` なら `q+1` して `rem -= B - r`）で
次のスパンのアンカーが厳密に出る。したがって表の第 j エントリは
`x = base_x + 16j` の除算の**商と剰余そのもの**である。

- `ksn_anchor_row`（`.bss`）: キー 4 ワード（rotation、`x0|x1`、`y0|y1`、`sw|sh`）と行 `y`、
  `base_x`、構築済みエントリ数、16 画素ぶんの増分対（`q16u,r16u,q16v,r16v`、`um`、`vm`）、
  そして 16 スパンぶんの `sx`/`remu`/`sy`/`remv`。
- 第 0 エントリは**その画素の除算そのもの**（従来の式）で作り、以降のエントリを
  `anchor_extend` が桁上がり規則で足していく。表は行を左から右へ読むにつれて遅延構築される。
- 使用条件は「キーが一致し、`x - base_x` が 0 以上 16 の倍数で 256 未満」の 1 条件だけ。
  どれか外れたら従来どおり割り、その x で表を作り直す（**厳密な値から作り直すので、
  条件を満たす限り表の値は常に正しい**）。キーは、その行のアンカーと増分対を決める入力
  （rotation → `c`/`s`、bounds → `w`/`h`/`x0+x1`/`y0+y1`、窓 → `sw`/`sh`、行 → `y`、
  `x` は `base_x` とグリッド条件）を**全部**含む。`source_x`/`source_y` はアンカーに
  入らない（後で添字に足すだけ）ので含めない。
- ホスト計器用に `ksn_render_rotate_anchor_state()`（構築済みエントリ数と `base_x` を返す
  だけの関数）を公開した。描画経路はこれを読まない。`-DKSN_ANCHOR_COUNT` を付けた時だけ
  構築回数のカウンタが生える（出荷オブジェクトには入らない）ので、ハーネスは
  「表が本当に使われた」を数で主張できる。

前コミットでステップ経路の定数部から `u`/`v` を作る計算を除いた：アンカーを割る分岐でしか
使わないので、表で済んだスパンはその 15 命令も払わない。

## 回転スパンの域外判定をスパン単位の区間判定へ（旧 kasane-image-transform-reject.md）

対象: `perf/kasane-anchor`、前コミット `590f5aa`（行ごとのアンカー表）の上。
実機には触れていない（`/dev/ttyACM0` は別セッション）。**ミリ秒は 1 つも無い**。
ここにある数は target ツールチェーンの `objdump`/`size` の実測、ホストで走らせた
テストの出力、`/tmp` の使い捨て掃引プログラムの出力である。
候補の位置づけは `docs/archive/perf/kasane-image-transform-recon.md` §6 候補 B。

---

### 1. 変えたもの

回転経路は、footprint の矩形のうち**ソースの外に出る画素（レコン文書の場面で 39%）を
1 画素ずつ判定して捨てるために 1 画素あたり約 37 命令**を払っていた。これを
**スパン（16 画素以下の窓）単位の区間判定**に置き換え、丸ごと外だと証明できたスパンは
判定 1 回とスクラッチの消去だけで済ませる。切替は `g_ksn_image_rotate_reject`
（`ksn_render.h`、既定 `true`）。切れば従来どおり全画素を判定する。

#### なぜスパン単位で判定できるか

- スパン内のアンカー（`sx`, `sy`）は**単調**である。1 画素の増分は `floor(su/um)` と
  `floor(sv/vm)` で、その符号は分子の増分 `step_u = 2c` / `step_v = -2s` の符号に一致し
  （`step_u > 0 ⇒ qu >= 0`、`step_u < 0 ⇒ qu <= -1`）、桁上がりは +0/+1 しか足さない。
- したがって「その軸の画素が全部 0 未満」は**最大値**で、「全部ソース幅以上」は**最小値**で
  決まる。最小・最大は両端のアンカーから分かり、減少側の端は「もう 1 画素先」の値なので、
  1 画素の商を 1 回引けば（`ux_end - qu - 1`）下限が出る。
- 両軸の区間がそれぞれ `[0, ソース幅)` と交わらなければ、そのスパンの画素は全部棄却される。
- **最初の画素が受け入れられるスパンは受け入れ画素を 1 つ持つ**ので、区間判定は
  「先頭画素が域外」のときだけ走らせる（これがスパンあたり 11 命令の前置フィルタ）。

スパンの先頭と「`x + count`」のアンカーは、**表が 16 画素幅のスパンを供給していれば
表が持つ 16 画素ぶんの増分対 1 組の桁上がり**で出る（除算なし・表の追加エントリなし）。
それ以外の幅では同じ規則の「`count` 画素ぶん」の増分対をその場で割って作る。

#### 画素が動かない理由

棄却された画素に対してループが書くのは `scratch->rotated.rgb[i] = 0` と
`alpha[i] = 0` だけで、呼び出し側は `alpha = 0` の画素を合成しない
（直接経路は `blend` が `a == 0` で `dst` を返し、群の経路は `premultiply_over` が
`mul8(color & 255, 0) = 0` で `dst` をそのまま返す）。スキップ経路は同じ 0 を
`count` 個書いて戻るだけなので、**書き込まれる画素も取得されるブロックも同じ**である。

## 拡大縮小スパンのソース添字: 商と剰余の加算ステップ（旧 kasane-image-transform-stretch-step.md）

対象: `perf/kasane-stretch`、基点 `origin/perf/kasane-imgopt` = `8e57dcb`（回転の加算ステップの直上）。
実機には触れていない（`/dev/ttyACM0` は別セッション）。**ミリ秒は 1 つも無い**。ここにある数は
target ツールチェーンの `objdump`/`size`/`nm`/`objdump -d` の実測、ホストで走らせたテストの出力、
そして gcov の行カウント（gcc 12.2 host）である。調査と候補の判断は
`docs/archive/perf/kasane-image-transform-recon.md`、回転側の同型の仕事は
`docs/perf/kasane-image-transform.md`。

---

### 1. 変えたもの

`main/ui/kasane/ksn_render.c` の stretch 経路の**画素ごとの 32bit 除算 2 本**を、回転側と同じ
「商と剰余の加算ステップ」に置き換え、`g_ksn_image_stretch_step`（`ksn_render.h`、既定 `true`）で
切り替える。

stretch の逆写像は、宛先列 `dx` に対して

    sx(dx) = source_x + floor((dx*source_width + source_width/2) / width)

で、スパン内で使う添字は **この商の差**である（現行の `image_sample_index` は画素ごとに
`stretch_sample(dx+offset, sw, width) - stretch_sample(dx, sw, width)` を計算していた = 1 画素 2 本）。
分子は `source_width` ずつ進む定数なので、`source_width = q*width + r`（`q = floor(sw/width)`,
`0 <= r < width`）と書くと、同じ除算の商と剰余が

    rem + r >= width なら index += q+1, rem -= width-r
    そうでなければ     index += q,   rem += r

で **1 回の比較と 1 回の条件付き減算**だけ進む（`rem, r ∈ [0,width)` なので桁上がりは高々 1 回、
除算結果と厳密に同じ値になる）。丸めを近似していない。

- 旧経路（`g_ksn_image_stretch_step == false`）は `image_sample_index` に**そのまま残した**
  （`ksn_render.c:198-200` の 2 本の `stretch_sample`）。
- 新経路（既定）は、スパン（宛先 16 画素以下）ごとに `image_read` が**そのスパンの添字を表に詰める**
  （`ksn_render.c:178-185`、`scratch->image.stretch[16]`）。呼び出し側は画素ごとに 1 バイト読むだけ
  （`ksn_render.c:197`）。回転側が `image_read` の中で添字を進めているのと同じ置き方で、添字を
  消費する順序への依存が無い（表は添字そのものなので、呼び出し順が変わっても値は変わらない）。
- 表は 16 バイトで、`ksn_span_scratch` の `image` メンバに足した（96 → 112 B）。
  `sizeof(ksn_span_scratch)+256+8+128 <= 512` の `_Static_assert` は 504 で不変。
- スパンのクランプ（ソース 32 画素を超えないよう `*count` を縮める）は、**同じ値の再計算をやめた**
  （旧: `while(... sample(dx+*count-1) ...)` の判定ごと + 最後に `n` のためもう 1 本。新: 最初の
  1 本を `last` に持ち、縮めたときだけ引き直し、`n` はその `last` を再利用）。削減量は
  **スパンあたり除算 1 本**（実測: 402,563 スパンで 402,563 本）。
- `n` と `dx=start` は同じ値のままで、受け入れ・取得は従来どおり（`0 <= sx < sw` の形は変えていない）。

### 2. 厳密性

1. **算術の総当たり**（ホスト、使い捨ての `/tmp/stretch/sweep.c`）: ソース窓 1..256 × 宛先幅
   1..65,535 の**全組**を 4 つの列で、さらに `count` 1..16 と乱数 20,000,000 組で、
   **1,569,048,152 点**を旧式（画素ごとの 2 除算）と比較して**不一致 0**。同時に
   - クランプ後の `count` / `n` / 開始列が旧ループと一致すること（125,457,664 スパンで不一致 0）、
   - アンカー（`start`）が旧式の分子を割った値と一致すること（不一致 0）、
   - 表の添字が **uint8 に収まる**こと（最悪の添字 **31**。スパンのクランプが 32 ソース画素を
     超えさせない）
   を課している。
2. **既存の独立参照テスト**: `tools/kasane_contract/test_image_render.c` は倍精度の
   oracle（`acos`/`cos`/`sin`/`floor`）と全 32,400 画素を比べる。この文書のコミットで
   **回転 0 の stretch を 40 通り追加**した（宛先幅 1/2/3/16/63/64/65/96 × ソース窓 1/2/3/16/38、
   計 1,296,000 画素）。新経路が既定で通る:

   ```
   image render PASS: crop/scale/alpha/group/retry, 240 moving and 360 stretch PATCH/full comparisons, 40 pure-stretch windows
   ```

   **同じ拡張テストは基点 `8e57dcb` の `ksn_render.c` でも通る**（拡張が新しい差を隠していない）。
   ついでに oracle の形 `floor((2dx+1)*sw/(2*width))` と実装の形 `(dx*sw+sw/2)/width` が
   **全点一致**することを 8,376,576 点で確認した（差 0）。理由: `sw` が偶数なら分子が同じ有理数、
   奇数なら差は `1/(2*width)` だが真値が整数にならない（`(2dx+1)*sw` が奇数なので `2*width` で
   割り切れない）。つまり oracle は実装の丸めをそのまま検証している。
3. **アーム比較テスト（新規）**: `tools/kasane_contract/test_image_stretch_arms.c`。
   1 バイナリの中に両アームを持ち、場面を**アームごとに作り直して**全画素を比べる。出力:

     変える（分母が毎フレーム変わる）。
   - 各場面で「壊れたフレームのアーム」と「全面再描画のもう一方のアーム」を 32,400 画素で比較。
     **最悪の画素差 0**。provider の取得回数も両アームで**一致**することを課している。
   - 120 フレームの animated stretch（位置 + 拡大縮小、回転 0、30 fps、loop）を

     課している。スイッチが無視されて経路が 1 本しか無い場合、この数は変わらないが、
     下の 4 がその証明になっている。
