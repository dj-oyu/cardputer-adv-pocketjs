# 回転画像スパンのアンカーを行ごとの表に置き換える（切替つき・厳密・既定は有効）

対象: `perf/kasane-anchor`、基点 `perf/kasane-imgopt` = `8e57dcb`。
実機には触れていない（`/dev/ttyACM0` は別セッション）。**ミリ秒は 1 つも無い**。ここにある数は
target ツールチェーンの `objdump`/`size`/`nm` の実測、ホストで走らせたテストの出力、
および `/tmp` に置いた計数用の複製の出力である。候補の判断は
`docs/perf/kasane-image-transform-recon.md`（§6 候補 A の残り）と
`docs/perf/kasane-image-transform-step.md`（§4 が次段として挙げたもの）。

---

## 1. 変えたもの

`main/ui/kasane/ksn_render.c` の `image_read` の rotate 分岐で、**スパンごとに払っていた
64bit 除算 2 本（`__divdi3` を 2 回）を行ごとのアンカー表からのロードに置き換えた**。
切替は `g_ksn_image_rotate_anchor`（`ksn_render.h`、既定 `true`）。切れば全てのスパンが
従来どおりその場で割る（前コミットのステップ経路も、`g_ksn_image_rotate_step` を切れば
さらに前の画素ごと有理除算経路に戻る）。

### 表の中身と作り方

アンカー（スパン先頭画素の `floor(U/umax)` と `U mod umax`、`U = u*source_width`）は
`x` についてアフィンである。16 画素ぶんの分子の増分 `D16 = 16*du*source_width` を
`D16 = q*B + r`（`q = floor(D16/B)`, `0 <= r < B`, `B = umax`）と書くと、
**画素ごとのループと同じ桁上がり規則**（`rem >= B - r` なら `q+1` して `rem -= B - r`）で
次のスパンのアンカーが厳密に出る。したがって表の第 j エントリは
`x = base_x + 16j` の除算の**商と剰余そのもの**である。

- `ksn_anchor_row`（`.bss`）: キー 4 ワード（rotation、`x0|x1`、`y0|y1`、`sw|sh`）と行 `y`、
  `base_x`、構築済みエントリ数、16 画素ぶんの増分対（`q16u,r16u,q16v,r16v`、`um`、`vm`）、
  そして 16 スパンぶんの `sx`/`remu`/`sy`/`remv`。
- 第 0 エントリは**その画素の除算そのもの**（従来の式）で作り、以降のエントリを
  `anchor_extend` が桁上がり規則で足していく。表は行を左から右へ読むにつれて遅延構築される。
- 使用条件は「キーが一致し、`x - base_x` が 0 以上 16 の倍数で 256 未満」の 1 条件だけ。
  どれか外れたら従来どおり割り、その x で表を作り直す（**厳密な値から作り直すので、
  条件を満たす限り表の値は常に正しい**）。キーは、その行のアンカーと増分対を決める入力
  （rotation → `c`/`s`、bounds → `w`/`h`/`x0+x1`/`y0+y1`、窓 → `sw`/`sh`、行 → `y`、
  `x` は `base_x` とグリッド条件）を**全部**含む。`source_x`/`source_y` はアンカーに
  入らない（後で添字に足すだけ）ので含めない。
- ホスト計器用に `ksn_render_rotate_anchor_state()`（構築済みエントリ数と `base_x` を返す
  だけの関数）を公開した。描画経路はこれを読まない。`-DKSN_ANCHOR_COUNT` を付けた時だけ
  構築回数のカウンタが生える（出荷オブジェクトには入らない）ので、ハーネスは
  「表が本当に使われた」を数で主張できる。

前コミットでステップ経路の定数部から `u`/`v` を作る計算を除いた：アンカーを割る分岐でしか
使わないので、表で済んだスパンはその 15 命令も払わない。

## 2. 厳密性

1. **算術の総当たり**（ホスト、使い捨ての `/tmp/kanchor/anchor_sweep.c`、リポジトリには
   入れていない）: `anchor_put`/`anchor_extend` を書き写し、回転 0..1023 × 6 寸法 ×
   6 窓 × 行 × `base_x` ×  bounds オフセット × 16 エントリについて、表の 4 値を
   従来の 64bit 除算式（切り捨て商 + 剰余 + floor 補正）と比べた。

   ```
   anchor sweep: spans verified 334430208 (values 1337720832), mismatches 0,
   accepted spans 37046748 vs 37046748 in the division arm
   PASS: every table entry equals the per-span division
   ```

   **3.34 億スパン（13.4 億値）で不一致 0**、受け入れ判定も同数。
2. **アーム比較テスト（既存ハーネスを 3 アームへ拡張）**:
   `tools/kasane_contract/test_image_rotate_arms.c`。1 バイナリの中に
   表アーム / スパンごと除算アーム / 画素ごと除算アーム（従来の全経路）を同居させ、
   場面をアームごとに作り直して全 32,400 画素・フレームハッシュ・**provider の取得回数**を比べる。

   ```
   animated track: 120 frames in all arms, alternating arm identical
   anchor table: largest row served 15 entries (build count needs -DKSN_ANCHOR_COUNT)
   image rotate arms PASS: 5917 configs, 11832 panel hashes, worst pixel step 0, fetches identical
   ```

   - 5,917 通り（回転 0..1023 の全部 + サイズ・窓・原点・clip/不透明度/群 + 新しい
     掃引 855 通り + 動く場面）、**パネル比較 11,832 回 = 3.83 億画素値**、最悪画素差 0。
   - `-DKSN_ANCHOR_COUNT` を付けたビルドでは構築回数も印字し、
     `g_ksn_image_anchor_builds > 0` を課す。付けないビルドでも
     **「最大 15 エントリの行を実際に供給した」**を `ksn_render_rotate_anchor_state()` で
     主張する（この assert が無いと、表が一度も使われなくても 2 アーム比較は素通りする）。
3. **リポジトリの全スイート**: `tools/kasane_contract/run.sh` を `/tmp` に複製し、
   **sanitizer のフラグ文字列だけ**を外して（この容器の ASan は 1/6 で DEADLYSIGNAL の
   無限ループに入るため）`cd` をこの worktree に向けて実行 → **exit 0、全 PASS**
   （この複製はリポジトリに入れていない。リポジトリの `run.sh` は 1 バイトも変えていない）。
   アーム比較テストの行だけが `2104 configs → 5917 configs` に変わった。
4. **数えた本数（`/tmp` の計数用複製、`ksn_render_counted.c`）**: レコン文書の場面
   （240x135 に 64x64 を (50,30)、source 64x64、rotation 200、REPLACE 全面）で

   | アーム | `image_read` の rotate スパン | 表から読んだ数 | 表の作り直し | スパン除算（`__divdi3` ×2） |
   | --- | ---: | ---: | ---: | ---: |
   | 表（既定、直接経路） | 492 | **410** | **82** | **82 回 = 164 本** |
   | 表（既定、群の経路） | 492 | 410 | 82 | 82 回 = 164 本 |
   | スパンごと除算 | 492 | 0 | 0 | 492 回 = **984 本** |

   つまり **1 フレームあたりの `__divdi3` は 984 本 → 164 本（6 分の 1）**。
   表の作り直しは 1 行あたり 1 回（82 行ぶん）。

## 3. target `-Os` の実測（命令数・オブジェクト）

ベース（`8e57dcb`）と本コミットを、同じレシピ
（`xtensa-esp32s3-elf-gcc -Os -std=gnu11 -Wall -Wextra -Werror -DESP_PLATFORM
-DCONFIG_IDF_TARGET_ESP32S3=1 -fstack-usage`、IDF ヘッダ込み）で `ksn_render.c` 単体
コンパイルし、`objdump -d` の基本ブロックを静的に数えた（`/tmp/kanchor/path.py`、
フォールスルーを辿るので「成功側が一直線」な gcc の配置をそのまま読める）。

| 項目 | 基点 | 変更後 | 出所 |
| --- | ---: | ---: | --- |
| スパン 1 本のアンカー代（表が供給した場合） | **516**（設定 70 + `__divdi3` 2 本 446） | **48** | `objdump -d` のブロック和 |
| 同（表を作り直した場合） | — | 約 **580**（キー判定 48 + 除算と `anchor_put`） | 同上 |
| うちキー判定 | — | 26（194-201 行） | 同上 |
| rotate の 1 画素（ループ本体、変更なし） | 92（取得あり）/ 66（キャッシュ命中）/ 37（域外） | 同じ | 前コミットと同じ範囲、桁上がり経路で ±3 |
| 1 転送画素あたりのアンカー代（場面重み） | **37.8** | **10.0** | 下記 |
| 1 フレームの `__divdi3` 本数（同一場面） | 984 | **164** | 計数用複製 |
| `image_read` 全体 | 604 命令 | 863 命令（両アーム同居、うち表の構築とキー判定） | `objdump` の範囲計数 |
| `ksn_render.o` `.text` | 6,264 B | **6,964 B（+700）** | `size -A` |
| `.rodata`（flash） | 566 B | **566 B（+0）** | `size -A` |
| `.bss`（DRAM） | 0 B | **308 B（+308）** | `size -A` |
| `.data`（DRAM） | 1 B | **2 B（+1、切替）** | `size -A` |
| `.literal` | 44 B | **56 B（+12）** | `size -A` |

**画素あたりの出し方**（この節の数はすべてこの式）:

    アンカー代/画素 = (作り直し回数 × 580 + 供給スパン数 × 48) / その行の画素数

レコン文書の場面（82 行 × 6 スパン = 492 スパン、6,724 画素）では
`(82×580 + 410×48)/6724 = 10.0`、基点は `492×516/6724 = 37.8`。
**差 −27.8 命令/画素**で、ループ本体（変更なし、場面重み 62.4 命令/画素）を足した
rotate 経路は **約 100 → 約 72 命令/画素（−28%）**。

**資源の内訳（どのバイトがどちらに載るか）**: 表は実行時に作るので **flash は 1 バイトも
増えない（`.rodata` 不変）**。増えたのは `.bss` の 308 B（表そのもの、SRAM）と `.data` の
1 B（切替）だけで、残りの +700 B は `.text`（命令、flash）である。表を定数にして
`.rodata` に置く設計は取っていない（値は回転・寸法・窓・行に依存するので定数にならない）。

## 4. 残っているもの

- **スパンごとの定数設定はそのまま残っている**: `c`/`s` の表引き 2 回（各約 19 命令）と
  増分対の計算（約 50 命令）は今もスパンごとで、供給されたスパンの 48 命令と合わせて
  **1 スパンあたり約 120 命令**が表の外に残る。同じキーでキャッシュできるので次段の候補
  （この表に相乗りさせると効くが、1 コミット 1 関心事のため入れていない）。
- 域外画素（footprint の 39%）はまだ画素ごとに判定している。次コミットの主題。
- **実機の時間は未測定**（この容器では測れない。上の数は命令数・回数・オブジェクト
  サイズだけである）。
