## 群の層の連なりを 1 枚のアフィン写像へ畳む（候補 3c、第1段 = 不透明群）（旧 kasane-group-affine.md）

2026-09-15、ブランチ `perf/kasane-affine`（親 `origin/perf/kasane-opt` = `87eb92a`）。
対象は `docs/perf/kasane-opt-survey.md` の候補 3c（境界3「command/group 符号化 → 仕事」と
境界4「per-pixel」）で、`main/ui/kasane/ksn_render.c` の `render_group` が持つ

群ごとに 1 枚のアフィン写像へ畳む。この文書は第1段（不透明群、ビット一致）の記録である。
第2段（不透明でない子への近似拡張）は別コミットで、その節をこの文書の末尾に追記する。

**この作業は 2 段に分かれている。**

| 段 | 対象 | 丸め | 状態 |
| --- | --- | --- | --- |
| 1 | 群の不透明度 255 かつ子が全部不透明 | 途中の床が 1 つも効かない → **ビット一致** | 既定で有効（`g_ksn_group_affine=1`）。§1〜§4 |

### 1. 何を畳んだか

`render_group` の群の合成は次の連なりである（`ksn_render.c` の変更前の経路）。

1. 子ごと・画素ごとに `premultiply_over` で 64 画素タイル（premultiplied RGBA8、256 B）へ
   `over` する。α は `mul8(color_alpha, 子の opacity)` で、各チャネルは
   `mul8(色, α) + mul8(タイル, 255-α)` を `clamp8` する。**各段で床に落ちる。**
2. タイルを（タイルの端まで、被覆していない画素も含めて）`group_over` で RGB565 へ落とす。
   α は `mul8(タイルの α, 群の不透明度)`、各チャネルは `mul8(タイル, 群の不透明度) +
   mul8(背景, 255-α)`。ここも床に落ちる。

`ksn_cache.h:54-55` は「instance は opacity 255 でも隔離 premultiplied 合成を使う
（PATCH 下で丸めを安定させるため）」と明記しており、この連なりは契約として書かれている。
畳めるのは、**床が 1 つも画素を動かせない場合だけ**である。

#### 1.1 不透明な子はタイルを上書きする（証明）

群の不透明度 255、子の不透明度 255、色の α 255 のとき:

- `a = mul8(255,255) = (255*255+127)/255 = 255`、`inverse = 0`。
- `mul8(x,255) = (x*255+127)/255 = x + 127/255` の床 → **x**。`mul8(y,0) = 0`。
- よって `tile.ch = mul8(color.ch,255) + mul8(tile.ch,0) = color.ch`、
  `tile.a = clamp8(255+0) = 255`。`clamp8` は一度も噛まない（演算はすべて 255 以下）。
- **前のタイルの中身は生き残れない。** つまりタイルの値は「その画素を被覆する最後の子
  （＝最上位の被覆子）の色」そのもので、α は 255 である。

最上位の被覆子が変わるのは子のループの順序（昇順、後の書き込みが勝つ）だけで決まる。
dither の provenance も同じ: `group_pixel` は `alpha==255` のときビットを*消し*、
勾配かつ dither のとき立てるので、**最上位の被覆子が dither 付き勾配かどうか**が
その画素の dither になる（`has_dither` が偽なら誰もビットを触らない）。

#### 1.2 群の合成も恒等になる

α=255・群の不透明度 255 なので `alpha = mul8(255,255) = 255`、`inverse = 0`、
`group_over` の各チャネルは `clamp8(mul8(tile.ch,255) + mul8(背景,0)) = tile.ch`。
`pack565(tile.r, tile.g, tile.b, dither, x, y)` は変更前の経路が最後に呼ぶものと
**同じ引数・同じ式**である。被覆していない画素は `group_over` が `alpha==0` で
早期 return して背景を残すが、畳んだ経路はそこに書き込まない（同じ結果）。

したがって第1段は次の 1 枚の写像に等しい:

```
out = A*src + B*dst + C     （A=255, B=0, C=0、全チャネル）
```

適用は「最上位の被覆子の値をそのまま書く」= ストア 1 回である。

#### 1.3 前条件（`child_opaque`）

- 不透明度 255、かつ色の α が 255（RECT / ROUND_RECT / STROKE は `shape.color`、
  GRADIENT は `from` と `to` の両方）。GRADIENT の補間は `interpolate` の式が
  `(255*(last-i)+255*i+last/2)/last = 255` を返すので、両端 255 なら中間も厳密に 255。
- **TEXT は除外する。** α が `mul8(色の α, coverage[x])` で、255 になるのは被覆が
  たまたま 255 の画素だけであり、その集合はフォントのものでこの描画器のものではない。
- `visible` でない子と不透明度 0 の子は連なりに影響しない（変更前の経路も
  `continue` する no-op）ので、前条件はそれらを跨ぐ。
- 不透明でない子が 1 つでもあれば**群ごと**旧経路に残す（画素ごとの混合はしない）。

前条件は bounds パスの中（子が既に手元にある場所）で集める。追加の `ksn_core_read` は
1 回も発生せず、条件に落ちた群は変更前の連なりを 1 ビットも変えずに通る。

#### 1.4 `g_ksn_row_coverage` とタイルループとの関係（見つけた制約）

- 画素集合は**旧経路と同じ解法**を使う: `g_ksn_row_coverage` が 1 なら
  `coverage_runs`（行ごとの x 区間）、0 なら画素ごとの `covers`。畳んだ経路も両方の
  アームを持つ（`test_group_affine.c` が 4 通りを全部通す: タイル経路 × 2 と
  畳んだ経路 × 2 の全画素一致）。
- **タイルは消える。** 旧経路は群の bbox × 64 画素ブロックを回り、被覆していない
  画素にも `group_over` を通していた（調査書 境界3「tile の量子化」の空回り。
  42 画素幅の instance では 22/64 が空回り）。畳んだ経路は子ごとの被覆区間だけを
  回るので、この空回りは 0 になる。
- **位相カウンタの意味が 1 つ動く。** `tile` の括り（群全体）は変わらないが、
  `blend` の括りは「1 タイル 1 回」から「畳んだ群 1 行 1 回」に変わる。したがって
  **`blend_n` はスイッチの腕によって比較できない**（`read_n` が 2a の腕で比較できない
  のと同じ形）。スイッチを切れば変更前の数に戻る。既定のプロファイル場面
  （`test_render_prof.c` の群は不透明度 137 で前条件に落ちる）では数は 1 つも動かない。
- 行の走査が「子ごと」である点は変わらない: 畳んだ経路は子を昇順に回り、被覆区間へ
  書く（後の子が勝つ）。1 画素を複数の子が被覆する場合、その画素を*計算*する回数は
  旧経路の `group_pixel` と同じで、節約は 2 パス目（タイル → 565）とタイルの
  メモリ往復の分である。最上位の子だけを書く形（被覆済みビットマップ）は画素を
  1 つも動かさないが、このコミットには入れていない。

              (whole panel, independent scalar reference, both arms; 974937 dither differences)

### 3. やっていないこと（第1段の範囲）

1. 実機の時間（`_cy` はホストで 0。`g_ksn_prof` の腕を実機で回す必要がある）。

### 5. 第2段: 不透明でない連なりへの近似拡張（`g_ksn_group_affine==2`、既定では無効）

別コミット。既定は 1 のままで、2 は明示的に選んだときだけ通る（撤退線は §5.4）。

#### 5.1 何を畳んだか

子のタイルへの書き込みは

```
tile.ch = mul8(color.ch, a) + mul8(tile.ch, 255-a)          (a = mul8(色のα, 子の不透明度))
```

で、ここが 1 子 1 チャネルあたり 1 回、8 ビットへ床に落ちる。同じ式を 8.8 固定小数点で持つと

```
acc = acc + (((color.ch<<8) - acc) * w + 128) >> 8,   w = round(a*256/255)
```

になる（`acc*(256-w) == acc*256 - acc*w` で 1 乗算にまとめた形。`fold_pixel`）。床が
8 ビット下がるので途中の丸めが落ちる、というのが第2段の近似の中身である。

- `a == 255` で `w == 256` ちょうどなので、**不透明な子は acc を厳密に上書きする**
  （`acc = color.ch<<8`、delta が 0 で丸めも 0）。したがって**第1段が畳む連なりでは
  第2段もビット一致**で、しかも第1段の前条件（群の不透明度 255）が要らない。
- α の連なり（`clamp8(a + mul8(alpha, 255-a))`）と群の段（`alpha = mul8(tile.a, 群の不透明度)`
  と `group_over` の式、`pack565` の引数）は**旧経路の 8 ビット式のまま**にしてある。
  よって dst の重み・透明判定（`alpha==0` の早期 return）・dither の provenance は
  1 ビットも変わらず、動くのは「premultiplied な色の床」だけである。
- TEXT の子も畳める（`span` をチャンクごとに引き、coverage で α を割るのは旧経路と同じ）。
- 実装は 32 画素チャンク。64 画素だと acc が 512 B 要るが、32 画素なら
  3×32×2 + α 32 = 224 B で、変更前のタイル 256 B を共用する union に収まる（§5.3 のスタック）。

#### 5.2 計測（同じバイナリの 0 と 2、`tools/kasane_contract/run_group_affine.sh`）

```
group affine: step 2 moved 86650 of 3888000 pixels over the parameter space (worst 8-bit
              channel step r/g/b=9/5/9, worst 565 step 1; 53498 of 224736 pixels under a
              covering child with a<255 moved, 0 elsewhere)
group affine: step 2 covering-child classes (moved/total): none=0/592974, one=38223/181446,
              two=15275/111975, three+=0/20805
group affine: step 2 over 120 frames: 117 frames moved a pixel, worst frame 464 of 32,400
```

- パラメータ空間は不透明な連なり 3 通り（群の不透明度 255 / 254 / 1）と、不透明でない
  連なり 6 通り（不透明な子の 1 つだけを半透明にした 2 通り、α が 0..255 で動く勾配と
  半透明の角丸矩形、TEXT の子 2 通り）× 原点 4 通り = 36 画面、それに 120 フレーム。
- **動く画素は 86,650 / 3,888,000（2.2%）**。内訳: 被覆する子が 1 つの画素で
  38,223 / 181,446（21.1%）、2 つの画素で 15,275 / 111,975（13.6%）、3 つ以上は 0 / 20,805、
  被覆する子が無い画素（群が塗らない）は 0 / 592,974。
- **半透明の子が被覆する画素に限る**: その 224,736 画素のうち 53,498（23.8%）が動き、
  それ以外の画素（被覆する子が全部不透明）は **0 画素**しか動かない。これが「不透明な
  連なりでは厳密」という主張の計測側の裏付けである（TEXT の子を含む画面は coverage を
  参照側で持たないので分類せず、「動きうる側」に数えている）。
- **最悪の段差は 5/6/5 の 1 レベル**（8 ビット展開で r/g/b = 9/5/9 は、それぞれ
  赤・緑・青がちょうど 1 レベル動いた値である。5 ビットの隣接レベルは 8 か 9、
  6 ビットは 4 か 5 だけ離れる）。dither の provenance と透明判定は式が同一なので
  反転しない（反転すればディザ模様ごと動くので、段差 1 レベルには収まらない）。
- 120 フレームでは 117 フレームが 1 画素以上動き、最悪のフレームで 32,400 画素中 464
  （1.4%）が動いた。

#### 5.3 命令数（ターゲット `-Os`、objdump。被覆 1 画素、子 1 つ、dither なし）

| 経路 | 中身 | 命令/画素 |
| --- | --- | ---: |
| 変更前 | `group_pixel` 103 + 呼び出し 1 | 104 |
| 変更前 | タイル→565 ループ 80 + `pack565` 37 | 117 |
| | **計** | **221** |
| 第2段 | `fold_pixel` 90 + 呼び出し 1 | 91 |
| 第2段 | 群の段のループ 92 + `pack565` 37 | 129 |
| | **計** | **220** |

- 連なりの段は 104 → 91 と安くなるが、**群の段が 117 → 129 と高くなる**（acc は 8.8 の
  3 ワード + α バイトなので、8 ビットのタイル 4 バイトより読み出しと桁合わせが重い）。
  合計は **221 → 220 でほぼ同じ**である。第2段はタイルを消していないので、第1段の
  1.97 倍は付かない。
- `ksn_render.o`: `.text` 5239 → 6395 B（第1段からの +1156）、`.data` 12 B のまま、
  `.bss` 5868 B のまま、`ksn_render_rects` のスタック 576 → 592 B（union の整列）。
- 群の段の `mul8(acc>>8, 群の不透明度)` を `(acc * g8) >> 16` に畳む変種は**採らなかった**:
  1 チャネルあたり 1 乗算ぶん安くなるが、群の不透明度が 255 でない不透明な連なりでも
  画素が動くようになり、「不透明な連なりは厳密」という §5.2 の性質を失う。

#### 5.4 撤退線と結論

- **撤退線**: `g_ksn_group_affine` を 0 か 1 に戻せば旧経路に完全に戻る（旧経路のコードは
  1 行も変えていない。§2 のとおり第1段の腕はそのまま）。既定は 1 で、2 は選んだときだけ通る。
- **結論**: 第2段は画素を最大 1 レベル（5/6/5）動かし、命令数はほぼ変わらない
  （221 → 220）。つまり候補 3c の値は**不透明な群（第1段）にあり**、不透明でない連なりに
  対しては「途中の丸めを落とす」だけでは速度にならない。**この腕は既定にしない。**
- 次に試すなら、被覆集合ごとに重み `W_k` / `W_dst` を群で 1 度だけ合成し、画素あたりの
  乗算を子ども数ぶんから 1 本へ減らす線形重みの形である（丸めは 1 段も残らないが、
  画素ごとの被覆マスクと、行ごとの被覆クラス表が要る）。本コミットの範囲外で、測ってもいない。

## Kasane タイル面 — 到達判定・ブロック幅・滑らかな層の増分書き（旧 kasane-tile.md）

対象は `docs/perf/kasane-opt-survey.md` の境界 3（command/group 符号化 → 仕事）の
候補 3a（群の bbox が届かないブロック）と 3b（tile を 64 → 16 画素）に加えて、
同調査が最後に残したタイル面の手法（滑らかな層をブロックごとに 1 度だけ評価し、
定数＋画素ごとの増分で書く）。分岐は `perf/kasane-tile`（`origin/perf/kasane-imgopt`
上）。**実機には触れていない**（`/dev/ttyACM0` は別セッションのもの）。したがって
ここにある数は「ホストで数えた命令数」「ホストで数えた画素」「目標ツールチェーンの
objdump」だけで、**ミリ秒に翻訳した値は 1 つも無い**。

---

### 0. 何を変えたか（3 つのスイッチ）

`render_group` は群の子命令を 64 画素のスクラッチタイルへブロック単位で合成する。

| スイッチ | 既定 | 意味 | 撤退線 |
| --- | --- | --- | --- |
| `g_ksn_tile_pixels` | **64** | ブロックの幅（64 か 16） | 64 に戻す |
| `g_ksn_tile_reach` | **1** | 厳密: 子のループをその子のクリップ済み x 区間だけ回し、どの子も届かないブロックは丸ごと飛ばす | 0 で変更前の一様タイル |
| `g_ksn_tile_smooth` | **1** | 滑らかな層: ブロックの両端を厳密に評価し、画素ごとの増分で書く（1 = 厳密な剰余歩進、2 = 8.16 の近似増分、0 = 旧経路） | 0 で旧経路（1 行も変えていない） |

計器（`-DKSN_TILE_COUNT` / `-DKSN_TILE_MEASURE`）は本番ビルドには入らない。
`g_ksn_tile_smooth` の既定を 1（厳密）にしてあるのは §4 の条件（ビット一致か、
0.1% 以下しか動かず段差が 1 レベル）を満たすためで、**近似側（2）は既定では無効**。

### 1. 到達判定（3a）— 厳密、既定で有効

変更前の子ループは、その子の箱が**ブロックの一部にしか掛からない場合でも全幅を回って**
いた。箱の外の画素では `covers` が偽を返すだけなので、その 1 画素につき
`covers` の 52 命令 + 呼び出しが捨てられていた。これが調査の「42 画素幅の instance で
64 画素のうち 22 画素が空回り」の正体である。

いまは子のクリップ済み x 区間を `lo..hi` に落とし、その範囲だけ `covers` を引く。
さらに **どの子も届かないブロック**は、タイルのクリア・子の読み出し・`group_over`
の段ごと飛ばす。どちらも画素を 1 つも変えない（箱の外は `covers` が偽、タイルが
全ゼロなら `group_over` は `dst` を返す）。

到達表（子ごとのクリップ済み箱、最大 16 個）は**境界パスで同時に埋める**。境界パスは
既に全部の子を手に持っているので `ksn_core_read` は 1 回も増えない。これを
ブロックループから引くと子 1 つ・ブロック 1 つにつき 139 命令 + 176 B のクリアが
余計に掛かる。群の子が 16 個を超える場合は到達判定をあきらめて従来どおり回す
（**飛ばすのは仕事であって画素ではない**）。

#### 測定（`tools/kasane_contract/test_group_tile.c`、`-DKSN_TILE_COUNT`）

調査と同じ形の場面（42 画素幅の instance と 14 画素幅の勾配を含む群、union は 3..145）:

| 腕 | タイル画素 | 被覆 | 空回り | 子ループ画素 | 子ループ空回り | ブロック | 飛ばした | 動いた画素 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| tile64 到達判定 off | 5,822 | 3,478 | 40.26% | 17,040 | 79.59% | 123 | 0 | — |
| tile64 到達判定 on | 4,500 | 3,478 | 22.71% | 4,770 | 27.09% | 100 | 23 | **0** |
| tile16 到達判定 off | 5,822 | 3,478 | 40.26% | 17,040 | 79.59% | 369 | 0 | — |
| tile16 到達判定 on | 4,116 | 3,478 | 15.50% | 4,770 | 27.09% | 262 | 107 | **0** |

- 「タイル画素」はブロックループが入った画素、「被覆」は子が実際に書いた
  （タイルの α が非ゼロの）画素、「子ループ画素」は子ループが `covers` を引いた画素。
- 到達判定で子ループの画素は **17,040 → 4,770（−72%）**、空回り率は 79.59% → 27.09%。
  ブロック 23 個を丸ごと飛ばしている。
- 画素は 5 アーム（tile64/到達判定 off・tile64/on・tile16/on・smooth=1 の 2 通り）で
  完全一致。ハーネスはこの 5 アームをパラメータ空間と 120 フレームで全画素比較し、
  `exact arms` の行で **4,050,000 画素が一致**する。
- 到達判定そのもののコストは、届くブロックでは 1〜2 個目の箱で早期に抜けるので
  数命令、届かないブロックでは最大 16 個 × 約 6 命令 = 約 96 命令。飛ばすブロック
  1 つあたりの節約は（クリア 256 B ≈ 32）+（子 1 つ = 139 + memset(176) + memcpy ≈ 350）
  +（`group_over` の段 64 画素 × 約 12 ≈ 770）で、子 2 つなら約 1,500 命令。
  **96 を払って 1,500 を返す**ので、届かないブロックが 1 つでもあれば元が取れる。

### 2. ブロック幅（3b）— 16 画素は採らない（測って却下）

16 画素にすると、到達判定**なし**では 1 つも数が変わらない（子ループは全幅を回るので、
ブロックの切り方だけでは空回りは減らない）。到達判定と併用したときだけタイル画素が
4,500 → 4,116（−8.5%）になり、ブロック数は 100 → 262（2.6 倍）になる。
ブロックごとのコストは変わらない（クリアは 16 画素でも 64 画素でも `tile[64]` の
256 B を消す）ので、**増えるクリアと到達判定の回数が、減る 384 画素の
`group_over`（約 12 命令/画素 ≈ 4,600 命令）を食い潰す**。

つまり 3b の利得は 3a が取ってしまい、16 画素は純増である。既定は 64 のまま。

### 3. 滑らかな層 — ブロックごとの定数＋画素ごとの増分

滑らかな層（勾配。radius 0 なら `covers` はクリップ済み箱の全体で真）は、
**ブロックの両端を厳密に 1 回ずつ評価**すれば、その間は漸化式で書ける。旧経路は
1 画素ごとに `covers`（52 命令）と `sample`（57 命令、うち 4 回の `quou`）を
呼んでいたので、ここが丸ごと消える。

2 通りの書き方を持ち、`g_ksn_tile_smooth` で選ぶ。

#### 3.1 厳密な剰余歩進（`g_ksn_tile_smooth==1`、既定）

鎖の式は `floor((from*(last-i) + to*i + last/2) / last)`、`i = x - bounds.x0`、
`last = length-1`。勾配は `i` について有理傾き `D/last`（`D = to-from`）のアフィンなので、
`D = q*last + rs`（`q = floor(D/last)`、`0 <= rs < last`）と割り、**剰余を足して桁上がりを
見る**だけで商の列がそのまま再現できる:

```
rem += rs; off += q; if(rem >= last){ rem -= last; off++; }   value = base + off
```

初期値は `rem = from*(last-i0) + to*i0 + last/2 - base*last`（`base` はブロック先頭の
厳密値で、`0 <= rem < last` になる）。**丸めが 1 つも入らない**ので `sample` と
ビット一致し、クリップも要らず、ドリフトもしない。`y` 方向だけの勾配（`axis != 0`）
と長さ 1 の勾配は x について定数なので、増分 0 の同じ式に落ちる（つまり厳密）。

#### 3.2 8.16 の近似増分（`g_ksn_tile_smooth==2`、既定では無効）

両端の厳密値から `step = ((end-base)<<16)/(n-1)` を切り捨てで作り、
`value = base + ((offset + 32768)>>16)`、`offset += step`。切り捨てなので
`|offset| <= |span|<<16` が全画素で成り立ち、値は両端の閉区間から出ない
（＝クリップが 1 つも要らない）。残るのは増分の量子化だけで、それを測ったのが §4。

### 4. 近似の測定（動いた画素と最悪段差）

#### 4.1 算術の総当たり

`test_group_tile.c` は両方の書き方を鎖の式と突き合わせる。境界つきの掃き（5,439,488
ブロック）に加えて、**1 回だけ全数**を回した（8 ビットの端点の全対 65,536 × 長さ
2..240 × 全開始位置 × 全 run = **1,174,863,872 ブロック**）:

- 厳密な剰余歩進の不一致: **0**
- 8.16 の近似の最悪 8 ビット偏差: **1**（`from=0 to=1 length=4 i0=0 n=3 j=1`）
- その 5 ビットレベルの段差: **1**（隣接レベルの最小差が 8/9 なので 8 ビットの 1 は
  5 ビットの 1 レベルにしかならない）

#### 4.2 パラメータ空間（全画面比較）

混合の場面（両軸の勾配・dither あり/なし・radius>0 の勾配・隠れた子・不透明度 0 の子・
画面外の子）× 群の不透明度 255/254/1 × 原点 5 通り（Bayer 4 位相・タイル端・帯端・
画面外）＋ run 長を変える場面＋TEXT の子:

- 比較 1,555,200 画素のうち **9,942 が動く（0.64%）**。
- 内訳: **x 方向に変化する半径 0 の勾配が被覆する 569,452 画素のうち 9,942（1.75%）**、
  y 方向だけの勾配が被覆する 76,254 画素では **0**、半径 0 の勾配が被覆しない画素では
  **0**（＝動くのは勾配の値そのものだけで、`covers`・dither の provenance・
  透明判定は動かない）。ハーネスはこの 2 つを assert している。
- 最悪段差は **5/6/5 の 1 レベル**（8 ビット展開で 9 = 隣接 5 ビットレベルの差そのもの）。
- 厳密側（`smooth=1`）は同じ空間で **0 画素**（旧経路と完全一致）。

#### 4.3 120 フレーム

demo.js 形の 8 子（勾配 4・矩形・角丸・stroke、PATCH で矩形/色/可視/群不透明度を動かし、
17 フレームごとに全面再描画）:

- 120 フレームすべてで 1 画素以上動き、**合計 73,388 / 3,888,000 画素（1.89%）、
  最悪のフレームで 902 / 32,400 画素（2.78%）**（この場面は勾配が画面の多くを覆うので、
  被覆画素あたりの率は §4.2 の 1.75% と同程度）。
- 段差は同じく 1 レベル。旧経路の PATCH と全面再描画は毎フレーム一致（損傷経路の差を
  近似の差と読み違えないため）。
- 厳密側は 120 フレーム × 32,400 = **3,888,000 画素が一致**（PATCH/全面混在のまま）。

#### 4.4 既定の判断

`docs/perf/pie-simd.md` の規約（ビット一致、または 0.1% 以下しか動かず段差 1 レベルなら
既定で有効。それ以外は無効にして数を報告する）を当てると:

- 厳密（1）: ビット一致 → **既定で有効**。
- 近似（2）: 動くのは 1.75%（勾配が被覆する画素のうち）＝ 0.1% を超える → **既定では無効**。

### 5. 命令数（目標 xtensa-esp32s3-elf-gcc -Os、objdump）

`-DKSN_TILE_MEASURE` でタイルの各段を out-of-line に固定して数えた。数え方は
「1 画素ごとに走る命令（内側のチャネルループは実行回数を掛ける）+ 呼び出した関数の本体」
で、ブロックごとの設定は 64 画素の run で割って足した。被覆 1 画素あたり:

| 段 | 旧経路 | 厳密（1） | 近似（2） |
| --- | ---: | ---: | ---: |
| 群のタイル内 per-pixel ループ本体（ゲート・`covers` 呼び出し・provenance・`premultiply_over` 呼び出し） | 60 | — | — |
| `covers` | 52 | — | — |
| `sample` | 57 | — | — |
| ブロック先頭の `sample` とチャネルごとの設定（64 画素の run で按分） | — | 4.3 | 4.8 |
| 滑らかな層の本体（`smooth_exact_block` は歩進 25×4 + 前後処理 36、`smooth_chord_block` は 56） | — | 136 | 56 |
| `premultiply_over` | 58 | 58 | 58 |
| **子の合成 計** | **227** | **198（−13%）** | **119（−48%）** |
| タイル→565 の段（`tile_row_over` のループ 80 + `pack565` 37。両アーム同じ） | 117 | 117 | 117 |
| **合計** | **344** | **315（−8%）** | **236（−31%）** |

関数の大きさ（同じ objdump、命令数）: `group_pixel` 49、`tile_row_over` 99（うちループ 80）、
`smooth_exact_block` 135、`smooth_chord_block` 112（うちループ 56）、`smooth_block`（呼び分け）80、
`covers` 52、`sample` 57、`premultiply_over` 58、`pack565` 37。
`smooth_exact_block` の 135 はコードの大きさで、1 画素あたりに走るのはチャネルのループ
（25 命令 × 4 回）+ 前後処理 36 = 136 命令ぶん、残り（4 チャネルの商と剰余 ≈ 135）が
**ブロックごとに 1 回**の設定である。

- **厳密側の利得は小さい（子の合成で −13%、端から端までで −8%）**。理由は歩進の状態
  （4 チャネル分の剰余・商・値）が -Os ではスタックに落ち、1 画素あたり 4 回のロードと
  4 回のストアを払うため。旧経路が消す `sample` の 4 本の `quou`（実測 16〜18 cycles/本）と
  ほぼ同じ重さがここに戻ってくる。
- 近似側は 4 つのアキュムレータを足すだけなので −48% になる。
- **設定はブロックごとに約 270〜310 命令**（`sample` 1〜2 回 + 呼び分け + チャネル設定）。
  1 画素あたりの節約は厳密で 29、近似で 108 なので、**run 長が約 10 画素（厳密）／
  3 画素（近似）を切ると元が取れない**。タイルの run はふつう数十画素あるが、クリップの
  端では数画素の run も出る（そこは小さな損。下限は入れていない）。
- `ksn_render.o` の大きさ（`size -A`）: `.text` 6,184（基点）→ 6,408（+224、到達判定と
  計器）→ 8,402（+2,218。うち滑らかな層の 2 アームが +1,994）。`.data` 1 → 9 → 9
  （スイッチ 2 本）、`.rodata` 566 のまま。**厳密側を既定で有効にするとフラッシュを
  約 2 KB 使う**（表と定数は増えていない）。
- `ksn_render_rects` のスタック（`-fstack-usage` の実測）: 960 → 1,216 B
  （到達表 16 × 8 B と滑らかな層の locals。`kasane-progress.md:229` の 1 KiB 目標に
  対しては未認定のまま）。

### 6. 兄弟 `perf/kasane-affine` との関係

あちらは群の連なりを**群ごとの 1 枚のアフィン写像へ畳む**（`g_ksn_group_affine`、
第 1 段は不透明な連なり限定でビット一致、第 2 段は近似で既定無効）。畳まれた行は
**タイルを通らない**（`group_opaque_row` が最上位の被覆子の値を 1 回ストアする）ので、
こちらの滑らかな層の腕はそこでは走らない。つまり:

- **同じ場面で競合しない**。あちらは「不透明な連なり」という最も効く場合を取り、
  こちらはその前条件が成り立たない場面（子が不透明でない、群の不透明度が 255 でない、
  radius>0 の勾配、TEXT の子）でタイルの中の `sample` を消す。**両方入れると、
  効く場面が分かれるので利得は加算されない**（併用時はどちらか一方しか走らない）。
- **テキストは同じ場所で衝突する**。あちらも `render_group` の per-pixel 合成を
  `group_pixel` として切り出しており、引数もほぼ同じ。統合時は片方の定義を残し、
  他方の呼び出し側（`fold_pixel` / `smooth_block`）をその定義に合わせる。第 2 段は
  タイルそのものを 32 画素の acc チャンクへ置き換えるので、**併用するなら順序は
  「こちら（タイル内の増分）→ あちら（畳み）」**が安全（あちらの前条件が成り立つ場面では
  こちらの腕は使われなくなるだけで、画素は変わらない）。
- `g_ksn_tile_reach` / `g_ksn_tile_pixels` はタイルの回し方だけなので、あちらとは独立。

### 7. やっていないこと・残っていること

- **実機の時間は 1 つも測っていない。** この面の前例（`pie-simd.md` §4.6）では命令数の
  削減が続けて差を出さなかったので、**命令数が時間に翻訳されるとは主張しない**。
  同一バイナリ A/B（`g_ksn_tile_*` を窓ごとに落とし、`AB` 行に値を出す）は次の実機
  セッションの仕事。
- **run 長の下限が無い。** §5 のとおり約 10 画素（近似なら 3 画素）未満の run では損をする。
  実機で測ってから `count >= 8` のような下限を入れるのが順当（今は入れていない）。
- **到達表は 16 子まで。** それを超える群（例: 全命令を 1 群にした 20 子）は
  従来どおり一様タイルへ落ちる。契約ではなく最適化なので、落ちても画素は同じ。
- **スタックが 128 B 増えた**（928 → 1,056 B）。`kasane-progress.md:229` の
  「描画追加 stack 1 KiB」目標に対しては未認定のまま（実機のピークは未計測）。
- `tools/kasane_contract/run.sh` には**結線していない**。この容器の sanitizer の腕は
  完了しない（`kasane-opt-integration.md` §0）ので、`run.sh` の複製（sanitizer の
  文字列だけ外したもの）で suite を回し、この候補は
