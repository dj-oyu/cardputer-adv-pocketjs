# FLOWER のショット定義ガイド

数字を1つ動かすと画面と速度に何が起きるか、そして限界がどこにあるか。カメラの定義（`main/scene/flower_shots.h` の `FLOWER_SHOTS`）を編集する人と、それを編集するアプリを書く人のための文書。

レンダラの内部仕様は同ヘッダの CONTRACT 節にある。こちらは**数字を動かす側から見た挙動**を書く。重複はしていて構わない。

---

## 1つの花に1つのカット

種が変わる間隔（`FLOWER_ROTATE_S` = 40秒）のあいだ、カメラは動かない。ディゾルブは種が変わる瞬間の1回だけ。テーブルの要素は1つで、その `hold` が40秒。

種の途中でカットを割ることは、テーブルに要素を足せば構造上は可能で、フェード処理もスワップ処理もそのまま動く。ただし後述のとおり**ズームはフレーム時間を直接食う**ので、複数カットは「いちばん重いカットを、その種の表示時間の一定割合で必ず払う」ことを意味する。

ショットは4つの数字で決まる。

| フィールド | 意味 | 範囲 |
|---|---|---|
| `pitch` | カメラの高さ。負が下から見上げ、正が見下ろし | ±0.349 rad（20度） |
| `zoom` | カメラの寄り。**0以下で「この株が窓に収まる倍率」**（種ごとに自動計算）。正の値は固定倍率 | 0以下、または 1.0 〜 4.0 |
| `aim` | 何を画面中央に置くか。株の高さに対する割合 | 0.0 〜 1.0 |
| `hold` | このショットを保持する秒数 | 合計が `FLOWER_ROTATE_S` |

---

## 引きの画は `zoom` に 0 を書く

`zoom` が0以下のとき、レンダラは**その株が窓に収まる倍率**をワールド座標のバウンディングボックスから計算する。余白は各辺6px、1.00より拡大はしない。

**定数では引きは必ずどこかの種で切れる。** 収まる倍率は種によって 0.80 〜 1.00 の間に散らばる（25%の幅）。定数 1.00 を書くと14種中13種がはみ出す — 株全体を見せることが仕事のショットが、株全体を見せていない状態になる。

理由は `aim` が行番号ではなく割合である理由と同じ：**種の大きさの差は、ショット間の差より大きい。**

| | |
|---|---|
| 最も小さく収まる | nigella 0.803 |
| 最も大きく収まる | crocus 1.000（上限に当たる） |
| `aim` の扱い | **無視される。** 株全体の画は、同時に一部を狙うことができない |

寄りのショットは定数のままでよい。寄りで株が切れるのは framing であって不具合ではない。

## コストを決めるのは `zoom` ではなく「窓の中にどれだけ株が入っているか」

**`zoom` 単体ではフレーム時間を予測できない。`zoom` と `aim` の組み合わせが決める。**

`zoom` は画像の拡大ではなくカメラの前進で、上げれば株は大きくなる。同時に、大きくなった株は窓からはみ出して**画面の外へ出ていく**。`aim` を花の位置まで上げると、株の下半分（葉と茎）は窓の外に出る。走査するものが減るので、寄せたほうが安くなることがある。

つまりコストは倍率に対して単調ではない。**両端が安く中間が高い株もあれば、寄るほど高くなる株もある。** どちらになるかは、その株の質量が「頭」にあるか「全体」にあるかで決まる。

| sunflower | 7468 | 9341 | 20368 | 20848 | 19035 | **-7%** |

| platycodon | 3994 | 5123 | 10574 | 11118 | 11336 | **+7%** |
| fritillaria | 3901 | 4485 | 10141 | 10842 | 10940 | **+8%** |
| crocus | 19950 | 19950 | 35345 | 41626 | 40531 | **+15%** |
| tulip | 5993 | 7142 | 14303 | 14770 | 17548 | **+23%** |

| anemone | 5572 | 6673 | 14724 | 17897 | 19835 | **+35%** |

見出しの `1.55/0.72` は「`zoom` 1.55、`aim` 0.72」。右端は 1.55 から 2.20 へ寄せたときの増減。

**すずらんは寄せると45%安くなり、echinacea は42%高くなる。同じ操作である。** すずらんは細長い花序なので、`aim` を上げると株の大部分が窓の外へ出る。echinacea は頭状花そのものが質量なので、`aim` を上げるとその頭が画面いっぱいに来る。

**「寄せれば安くなる」を一般則にしてはいけない。** 実機で最も落ちた種（echinacea、17.3 fps）は、寄せると**さらに**重くなる側にいる。

### 実機の fps

| 種 | `zoom` 1.00 | 1.28 | 1.55 | 2.35 |
|---|---|---|---|---|
| snowdrop（種2） | 27.0 〜 30.2 | 26.5 〜 27.9 | 26.2 〜 28.4 | 27.5 〜 29.0 |
| echinacea（種8） | 未測定 | 21.0 〜 27.3 | 23.0 〜 23.6 | **17.3** |

同じ `zoom` 2.35 が、snowdrop では 27.5〜29.0 fps、echinacea では 17.3 fps。**段の数字だけでは決まらず、種と framing の組み合わせで決まる。** 30fps を目標にする画面で 17.3fps は見て分かる落ち方をするので、**framing を変えたら重い側の種で実機を測ること。** ホストの2つの表は傾向を見るためのもので、fps の予測値ではない。

## `zoom` の上限を決めるのは、クランプではなく「その花に見えるか」

アサーション上の上限は 4.0 だが、実際の上限はもっと手前にある。**ただし「寄りすぎ」は `zoom` 単体では決まらない。** `aim` が花を指していない状態で倍率だけ上げると、拡大されるのは葉と茎で、花はむしろ小さく見える。

| framing | すずらん（最も早く壊れる種） |
|---|---|
| `zoom` 2.20 / `aim` 0.94 | 釣鐘が大きく写る。ベル部品が走査量の50%を占める |
| `zoom` 2.35 / `aim` 0.93 | 弓なりの花序に釣鐘が3つ |
| `zoom` 2.60 / `aim` 0.80 | 緑の塊と白い点が3つ。**倍率ではなく `aim` が低すぎて、拡大されたのが葉だった** |
| `zoom` 2.80 / `aim` 0.93 | 釣鐘が2つに減り、echinacea では頭状花の中心が画面外に出る |

**編集する人は1種類を見ながら、14種すべてに適用される数字を決めている。** 効く種を挙げる。

- **すずらん（valley）が律速。** 最初に識別できなくなる。`zoom` を上げたら必ずこれを見る。
- **スノードロップ、フリチラリア** も株が細く部品が少ないので、次に識別が苦しくなる。
- **sunflower / anemone / crocus / iris** は 2.35 以上で画面からはみ出す。はみ出すこと自体は寄りの画では普通に起きるが、頭がどこまで切れるかはこの4種で決まる。

## `pitch` は見た目ほど効かない

カメラは**正射影**。奥行きによる縮小がないので、角度を変えても遠近感は生まれない。

- **見上げの収束も、三点透視も、この角度指定では作れない。** それらは遠近法の効果で、割り算のない投影には存在しない。
- **20度を超えると「カメラが動いた」ではなく「株が倒れた」に見える。** だから ±0.349 rad で止まる。
- **効きは寄っているときのほうが大きい。** `zoom` 1.00 では株が小さく、±0.2 rad 動かしても花の面の縮み方がわずかに変わる程度。寄った段では顔の見え方が実際に変わる。
- **`zoom` と違って画素数を増やさない。** `pitch` は速度に対して無料。

### `yaw` は存在しない

水平方向にカメラを回すことはできない。`rotate()` が混ぜているのは画面上のx軸とy軸、つまり視線まわりの**ロール**なので、視点の角度として渡すと株が画面内で傾く。ゼロで固定されていて、テストがそれを検査する。**編集アプリは水平回転のUIを出してはいけない** — 値を持てないので、出せば必ず嘘になる。

---

## `aim` は行番号ではなく、株の高さに対する割合

`0.0` が株元、`1.0` が先端。その位置が画面の**65行目**に来る。

窓は 12〜134行目なので中央は73行目。65行目はそれより8行上で、**上に53行、下に69行**という非対称な配分になる。上寄りの構図になり、下に余白が残る。

**行で指定しない理由**：種ごとの背丈の差が、ショットどうしの差より大きい。行で書くと、背の高いアイリスで合わせた数字が背の低い株では空を指す。割合で書けば、同じ数字が「花の顔」を14種すべてで指す。

目安として、`0.5` で株全体、`0.9` 前後で花の部分が中央に来る。寄りの段ほど `aim` の効きが大きい（画面に入る範囲が狭いため）。

---

## `hold`：効くのは合計だけ

種のスワップは**テーブルの最後のショットが終わったときに起きる**。だから：

- **合計が `FLOWER_ROTATE_S`（40秒）である限り、内訳をどう変えても種の表示時間は変わらない。** スワップ回数も変わらない。
- **合計を変えると、その両方が変わる。**
- 各ショットの前後には `FLOWER_FADE_S`（1.2秒、前後に0.6秒ずつ）のディゾルブが乗る。短いショットほど、その時間に占めるディゾルブの割合が高くなる。
- **`FLOWER_VIEW_MIN_S` は最も短い `hold` と一致させること。** ディゾルブの時間比率の上限がこの値を基準に検査されるので、ずれると検査が実態と違う数字を測る。

---

## ファームウェアが拒否する定義

テーブルは検査を通ってからでないと使えない。**編集アプリは、これらを入力の時点で止めるべき。** 拒否される定義を組み立てられるアプリは、限界を説明するアプリより悪い。

| ルール | 値 |
|---|---|
| `pitch` の絶対値 | 0.349 rad（20度）以下 |
| `yaw` | 常に 0。指定できない |
| `zoom` | 0以下（窓に合わせる）、または 1.0 以上 4.0 以下 |
| `aim` | 0.0 以上 1.0 以下（`zoom` が0以下のときは無視される） |
| `hold` | 4.0 秒以上、`FLOWER_ROTATE_S` 以下 |
| `hold` の合計 | `FLOWER_ROTATE_S`（40秒）にちょうど一致（誤差 0.01 秒） |
| 隣り合うショットの `zoom` 比 | 大きいほう ÷ 小さいほう > 1.16（ショットが2つ以上のときのみ） |
| `FLOWER_VIEW_MIN_S` | 最も短い `hold` と一致 |

`zoom` 比のルールは、**最後のショットと最初のショットの間（種が変わるところ）も隣り合いとして数える**。ショットが1つのときは自分自身との比較になるため適用されない。

このルールがある理由：サイズの近い2ショットを続けると、視点が変わったのではなく被写体がわずかにずれたように見える。観客はカットをまずショットサイズで読む。

## 動かす前に見る

実機に焼かずにホスト側で全種の絵を出せる。

```bash
bash tools/preview_flower_shots.sh      # 各定義を全14種でレンダリングし、PNGの一覧を作る
bash tools/flower_shot_cost.sh          # 各段の画素コストを種ごとに出す
```

`tools/preview_flower_shots.sh` は定義ごとに `.cache/variants/<名前>/` を作り、そこに `flower.c` の複製と差し替えた `flower_shots.h` を置いてビルドする。`main/` には触らないので、比較したい定義をいくつでも並べられる。出力は `.cache/flower-<名前>-shot-<番号>.png`（1ショットあたり全14種）と `.cache/flower-<名前>-ladder.png`。

**`zoom` を変えたら必ず全種を見ること。** 1種類で決めた数字が14種に適用され、識別できなくなる種もフレーム時間が落ちる種も、その1種類ではない場合がある。
